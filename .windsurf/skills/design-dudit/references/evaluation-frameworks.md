# 设计走查标尺（Evaluation Frameworks）

走查时逐页对照的清单。若用户仓库中存在自己的设计规范（色板、字号、tokens），以其为准，本文件作为兜底与补充。

## 目录

- 一、交互维度（基于 Nielsen 十大启发式）
- 二、界面与布局维度
- 三、视觉维度（色彩 / 字体 / 一致性）
- 四、文案维度
- 五、状态完整性矩阵（最易遗漏，重点检查）

---

## 一、交互维度

基于 Nielsen 十大可用性启发式，转写为可直接验证的检查项：

| # | 原则 | 检查项 |
|---|---|---|
| 1 | 系统状态可见 | 每个耗时操作（>300ms）是否有加载指示？操作成功/失败是否有明确反馈？当前所在位置（导航高亮、面包屑）是否可见？ |
| 2 | 贴近用户语言 | 界面用词是否是用户语言而非技术黑话（如"持久化""实例化""回调"出现在 UI 上即为问题）？ |
| 3 | 用户可控与自由 | 误操作能否撤销/返回？弹窗能否关闭（Esc、遮罩点击、×按钮三处都试）？破坏性操作（删除、清空）前是否有确认？ |
| 4 | 一致性与标准 | 同类操作在不同页面是否行为一致？是否违背平台惯例（如 logo 点击不回首页、下拉框行为怪异）？ |
| 5 | 错误预防 | 表单是否在提交前就校验必填与格式？危险按钮是否与常规按钮有视觉区分？是否有防重复提交？ |
| 6 | 识别优于回忆 | 需要的信息是否就近可见，而非要求用户记住上一页内容？输入是否有占位符/示例/历史记录辅助？ |
| 7 | 灵活高效 | 高频操作是否有快捷路径（快捷键、批量操作、默认值）？ |
| 8 | 简约设计 | 界面是否存在与当前任务无关的元素？信息是否按优先级分层呈现，而非平铺堆砌？ |
| 9 | 错误恢复 | 报错信息是否说人话（出了什么问题 + 怎么办），而非仅"Error 500"或红字一闪而过？ |
| 10 | 帮助与引导 | 新用户面对空页面时是否有引导（空态说明、示例、下一步提示）？ |

## 二、界面与布局维度

- **对齐**：同层级元素边缘是否对齐？文本与图标、标签与输入框是否基线对齐？随手截图放大看，错位 1–2px 也算（记 P3）。
- **间距**：间距是否成体系（通常基于 4px 或 8px 倍数）？相邻区块间距是否忽大忽小无规律？元素与容器边缘的内边距是否一致？
- **信息层级**：扫一眼页面，能否 3 秒内指出"这个页面最主要的操作是什么"？主按钮是否一眼可辨？标题/正文/辅助文字层级是否清晰？
- **布局稳定性**：内容加载前后是否跳动（布局偏移）？不同内容长度（长文本、空数据、超多数据）下布局是否崩溃？
- **响应式**：三档宽度（1440 / 768 / 375）下分别检查：内容是否溢出、出现横向滚动条、元素重叠、按钮挤压变形、触摸目标过小（移动端 < 44px）。
- **密度与留白**：是否过挤（元素间喘不过气）或过空（大片无意义留白）？留白是否用于分组而非均匀摊派？

## 三、视觉维度

### 色彩

- **对比度**：正文文本对比度 ≥ 4.5:1（WCAG AA），大字号（≥18pt 或 14pt 粗体）≥ 3:1。重点检查：灰色辅助文字、按钮文字、深色模式下的次级文本、placeholder。可用取色工具取样计算。
- **色彩语义**：成功/警告/错误/信息色是否全产品统一？红色是否同时被用于"错误"和"普通强调"（语义混乱）？
- **用色数量**：主色是否克制（1 个主色 + 中性色为主）？是否出现与色板无关的"野颜色"（尤其各处蓝色/灰色色值微妙不同）？
- **深浅模式**：若产品支持双模式，两模式是否都完整检查一遍？切换后是否有元素忘记适配（白字白底等）？

### 字体

- **字号体系**：字号是否成有限阶梯（如 12/14/16/20/24），还是每个页面随手取值？
- **字重**：粗体使用是否有规律（标题用、强调用），还是遍地加粗导致没有强调？
- **可读性**：正文字号是否 ≥ 13px？行高是否舒适（约 1.5–1.7 倍）？行长是否过长（中文 > 40 字/行、英文 > 75 字符/行）？
- **字体回退**：中英文、数字混排是否协调？是否出现默认衬线字体 fallback（说明字体加载失败）？

### 一致性（设计师最敏感的维度，单独强调）

- 同类元素必须同款：所有主按钮、卡片圆角、阴影、输入框高度、图标风格（线性/填充/尺寸）、弹窗样式，跨页面逐一比对。
- 图标：是否混用不同图标库风格？相邻图标视觉大小是否一致（实际尺寸相同 ≠ 视觉重量相同）？
- 交互反馈一致：hover 效果是否全站统一（有的卡片浮起、有的变色、有的没反应，即为问题）？

## 四、文案维度

- **清晰**：按钮文案是否是具体动作（"保存草稿"优于"确定"）？用户能否不看说明就理解每个功能？
- **一致**：同一概念全站同一称谓（不要"项目/工程/工作区"混用）；标点、大小写、全角半角风格统一。
- **语气**：错误提示不指责用户（"你输入错误"→"请输入正确的邮箱格式"）；空态文案是否有引导性（"暂无数据"→"还没有标注任务，点击右上角创建第一个"）。
- **完整性**：是否有 lorem ipsum、TODO、"test"、未翻译的键名（如 `common.submit`）残留？

## 五、状态完整性矩阵

**这是业余与专业产品差距最大的地方。** 对每个页面/组件，确认以下状态都被设计过：

| 状态 | 检查要点 |
|---|---|
| 空态（empty） | 首次使用/无数据时是否有说明与引导，而非一片空白或"暂无数据"四字 |
| 加载态（loading） | 数据加载中是否有骨架屏/spinner；按钮触发异步操作后是否有 loading 并防重复点击 |
| 错误态（error） | 网络失败、接口报错、权限不足时页面长什么样？（可断网或改请求测试） |
| 成功态（success） | 操作成功后有无确认反馈？反馈停留时间是否合适？ |
| 悬停/聚焦（hover/focus） | 所有可点击元素都有 hover 反馈；键盘 Tab 能否走通全页、焦点可见 |
| 禁用（disabled） | 不可用时是否有禁用样式；最好说明为何禁用 |
| 极限内容 | 超长文本（换行/截断/省略号？）、超长列表（分页/虚拟滚动？）、零值、极大数字、特殊字符、超长用户名 |
| 部分失败 | 批量操作中部分成功部分失败时的呈现 |

检查方法提示：空态可用新账号/清数据触发；错误态可断开网络或拦截请求；极限内容直接往输入框里粘贴超长文本。
