# 设计走查（Design Audit）

像真实设计师验收产品一样：启动产品 → 画出完整地图 → 逐页逐流程实际操作 → 对照设计框架记录问题 → 输出分级报告。

核心纪律：**覆盖率优先于深度**。宁可每页发现一个真问题，也不能只在首页深挖而漏掉半个产品。所有结论必须来自亲眼所见（截图/实际操作），禁止凭代码想象界面。

## 工作流程

### 阶段 0：准备与标尺确认

1. 定位项目：阅读 README、package.json（或等价文件），确定技术栈、启动命令、端口。
2. 安装依赖并启动 dev server，确认首页可访问。启动失败时修复环境问题（依赖、端口占用、环境变量），修不了就如实报告并停止——不要在不可运行的产品上"走查"。
3. **收集检查标尺**（按优先级）：
   - 仓库内用户自己的设计规范：查找 DESIGN.md、design-system、tokens、主题配置文件（tailwind.config、CSS 变量、theme.ts 等），提取色板、字号、间距规范作为第一标尺；
   - 内建框架：阅读 [references/evaluation-frameworks.md](references/evaluation-frameworks.md)，作为兜底标尺；
   - 两者冲突时以用户规范为准，并在报告中说明。

### 阶段 1：产品测绘（保证不漏页）

1. **从代码侧穷举页面**：读路由配置文件（router、app/ 目录、pages/ 目录等），列出全部路由清单。
2. **从界面侧验证**：打开产品，遍历导航栏、侧边栏、菜单、页脚的每一个入口，对照代码清单补充隐藏入口（弹窗、抽屉、二级页面）。
3. **识别关键用户流程**：列出 3–7 条核心任务流（如：注册→创建→编辑→删除；导入→标注→导出），包含每个流程的空态、加载态、错误态、成功态。
4. 产出「走查地图」：页面清单 × 待测状态清单，作为后续阶段的对账表。页面超过 15 个时，按核心度分批，先主流程后边缘页面，但清单必须完整记录。

### 阶段 2：走查（像用户一样操作）

对地图中的每个页面/状态：

1. **实际操作**，不只是看：点击每个按钮和链接、提交每个表单（含非法输入）、触发 hover/focus/disabled、调整窗口宽度（桌面 1440 / 平板 768 / 手机 375 三档，除非产品明确只支持桌面）、刷新页面、走一遍完整任务流。
2. **逐页截图存档**，截图命名含页面与状态（如 `03-标注页-空态.png`），存入工作目录供报告引用。
3. **对照标尺逐项检查**，检查维度与具体条目见 [references/evaluation-frameworks.md](references/evaluation-frameworks.md)：
   - 交互：反馈、状态完整性、导航与回退、错误预防与恢复
   - 界面：布局、对齐、间距、信息层级、响应式
   - 视觉：色彩与对比度、字体、一致性（同类元素同款样式）
   - 文案：清晰、一致、有引导性
4. **发现问题当场记录**，不要攒到最后凭记忆补。每条问题立即记下：页面/位置、证据（截图文件名）、现象描述、违反的标尺条目、严重度初判。

走查节奏提示：每完成 3–5 页回顾一次地图对账表，确认进度与覆盖率。

### 阶段 3：复核与分级

1. 汇总全部原始记录，合并同一根因的问题（如"全局主按钮 hover 无反馈"在 5 个页面出现，合并为 1 条全局问题，列出全部出现位置）。
2. 按严重度分级：
   - **P0 阻断**：阻碍核心任务完成，或导致数据/状态错误（如按钮点击无响应、表单无法提交、对比度低到内容不可读）
   - **P1 严重**：显著损害体验或专业感，用户必然感知（如无加载态、错误无提示、层级混乱导致找不到主操作）
   - **P2 中等**：影响品质但不妨碍使用（间距不一致、对齐偏差、文案不统一）
   - **P3 细节**：锦上添花（微交互缺失、可优化的细节质感）
3. 每条问题给出**具体的改进建议**（改什么、改成什么样），不写"建议优化体验"这类空话。建议引用标尺条目或用户自己的设计规范作为依据。

### 阶段 4：输出报告

按 [references/report-template.md](references/report-template.md) 的模板输出 Markdown 报告，要点：

- 报告开头必须有**走查地图对账表**（列出所有页面/状态，标注"已查/未查"）——这是覆盖率自证，未覆盖处必须说明原因；
- 问题按严重度排序，每条含：位置、证据截图、现象、违反标尺、建议；
- 结尾附总结：问题分布统计（按维度 × 严重度）、最值得优先修复的 3 件事；
- 报告存为文件（如 `设计走查报告-YYYYMMDD.md`），截图存于同目录文件夹，报告中用相对路径引用。

## 降级模式

- **只有线上 URL、无代码仓库**：跳过代码侧穷举，仅靠界面遍历 + 站点地图测绘，并在报告中声明"可能存在未发现的隐藏页面"。
- **只有截图/设计稿**：仅做静态视觉审查（布局、视觉、文案维度），交互维度标注"无法验证"，并在报告开头声明此限制。

## 反模式

- 只走查首页和显眼页面，把抽查当全局检查
- 凭代码或类名推断界面长什么样，不实际打开看
- 只记录"感觉不好"，没有对应标尺条目和证据
- 报告里全是 P2/P3 级别的吹毛求疵，回避真正的结构性问题
- 发现启动失败、页面 404 等技术问题时静默跳过而不记录（"入口失效"本身就是 P0 问题）
- 擅自修复问题——本 skill 的职责是发现与描述，修复是用户确认后的下一个任务
