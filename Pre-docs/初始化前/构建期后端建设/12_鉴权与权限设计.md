## 一、文档目的

定义：

- 用户如何登录
- 身份如何建立
- 用户与管理员分别能做什么
- 数据访问如何隔离

本文件不负责定义数据库字段细节，也不负责定义具体页面交互，而是负责把“身份”和“权限”这两件事说清楚，确保后续迁移、用户系统、后台方案都建立在同一套访问控制前提之上。

---

## 二、鉴权目标

本轮鉴权与权限设计需要同时满足以下目标：

1. **让用户能够建立正式账号身份**
2. **让用户数据与账号绑定，而不是继续依赖浏览器本地状态**
3. **让普通用户只能访问自己的私有数据**
4. **让管理员具备最小可运营权限，但不越权读取所有私有资产**
5. **让权限控制同时存在于前端、后台入口和数据库层**
6. **让关键后台动作具备可追踪性与可撤销性**

这意味着本方案不接受以下做法：

- 只在前端按钮层面做权限隐藏
- 默认允许管理员任意读取所有用户私有内容
- 继续把用户身份和业务数据关系建立在本地匿名状态上

## 三、登录方式设计

### 3.1 总体原则

第一阶段采用 **统一认证入口**：

- 用户和管理员共用一套登录体系
- 管理员不是单独一套后台账号，而是“普通用户 + 管理员资格”

这样可以避免维护两套身份系统。

### 3.2 第一阶段推荐登录方式

第一阶段建议以 `Supabase Auth` 提供的 **邮箱登录能力** 作为主方案，优先选择低摩擦方式：

- 邮箱验证码
- 或邮箱 magic link

设计原因：

- 实现成本低
- 容易与托管 Auth 结合
- 足以满足当前构建期的账号化要求

第一阶段**不要求**：

- 自建用户名密码体系
- 自建短信登录体系
- 一开始就接入多种第三方 OAuth

后续若用户规模或渠道需要，再扩展 OAuth 登录即可。

### 3.3 登录后的初始化动作

用户完成认证后，系统需要立即完成以下动作：

1. 获取 `auth.users.id`
2. 确保存在对应的 `profiles` 记录
3. 查询该用户是否具备有效 `admin_roles`
4. 在前端建立统一身份上下文

也就是说，登录成功并不等于“权限已经准备好”，还需要完成产品层身份装配。

## 四、会话与身份模型

### 4.1 会话来源

会话由 `Supabase Auth` 统一提供，前端不自行发明第二套会话机制。

会话中最重要的信息是：

- 当前是否已登录
- 当前用户是谁
- 当前会话是否仍有效

### 4.2 产品身份上下文

前端在完成认证后，应形成统一的产品身份上下文，可理解为：

```markdown
Identity Context =
  Auth User
  + Profile
  + Admin Role Status
  + Session Status
```

即至少包含：

- `user_id`
- `profile.status`
- `has_completed_initial_migration`
- `is_admin`
- `session_valid`

### 4.3 匿名态与登录态

第一阶段系统允许存在两种访问状态：

- **匿名态**：未登录
- **登录态**：已登录并具备正式身份

匿名态下：

- 可使用有限的前端能力
- 可保留本地数据
- 不能访问用户云端私有数据
- 不能进入后台

登录态下：

- 可访问自己的云端资产
- 可触发本地到云端的数据迁移
- 若具备管理员资格，可进入后台

### 4.4 管理员身份的建立方式

管理员身份不是登录时单独生成的，而是通过 `admin_roles` 判定：

- 用户先是普通登录用户
- 系统再检查该用户是否存在有效管理员资格
- 若存在，则开放后台入口与后台权限

这种模式的好处是：

- 普通用户体系和后台体系一致
- 权限来源清晰
- 便于未来撤销管理员资格

## 五、角色模型

第一阶段采用**最小角色模型**。

### 5.1 普通用户

普通用户是默认角色。

普通用户的核心能力：

- 登录与登出
- 访问自己的 `profiles`
- 访问自己的 `articles`
- 访问自己的 `bookmarks`
- 访问自己的 `reading_marks`
- 读取对外发布的 `featured_articles`

普通用户不能：

- 访问他人的私有数据
- 修改管理员资格
- 访问后台管理数据
- 写入审计日志中的管理员动作

### 5.2 管理员

第一阶段管理员角色固定为：`admin`。

管理员具备两层能力：

1. **普通用户全部能力**
2. **后台最小运营能力**

管理员额外能力包括：

- 进入后台管理端
- 管理 `featured_articles`
- 查看用户基础资料与状态
- 查看基础运营数据
- 查看后台审计日志
- 执行需要后台权限的运营动作

管理员第一阶段**默认不具备**以下权限：

- 任意浏览所有用户文章正文
- 任意浏览所有用户收藏内容
- 任意导出所有用户私有学习资产

这样设计的原因是：

- 当前后台目标是“能运营”，不是“全量读私有数据”
- 用户私有阅读资产应遵循最小暴露原则

如果未来出现客服、申诉处理、内容审核等真实场景，再补充新的决策与更细权限模型。

### 5.3 后续可扩展角色

第一阶段虽然只落一个管理员角色，但模型上保留未来扩展空间，例如：

- `content_admin`
- `support_admin`
- `super_admin`
- `analyst`

但这些角色**不是第一阶段需要实现的内容**。

## 六、权限边界

### 6.1 普通用户边界

普通用户只应操作自己的私有资产。

边界定义如下：

- `profiles`：只能读写自己的资料
- `articles`：只能读写自己的文章
- `bookmarks`：只能读写自己的收藏
- `reading_marks`：只能读写自己的阅读进度
- `featured_articles`：只能读取已发布内容，不能管理

### 6.2 管理员边界

管理员的后台权限仅覆盖：

- 推荐内容管理
- 用户基础状态查看
- 后台指标与日志查看
- 后台动作执行

管理员不应因为“是管理员”就自动拥有所有用户私有数据的无限读取权。

### 6.3 前端权限边界

前端需要做的不是“真正授权”，而是：

- 根据身份隐藏或展示入口
- 在进入受限路由前做拦截
- 在权限不足时做明确提示

但真正的访问控制不能只靠前端，因为前端可被绕过。

### 6.4 数据库权限边界

最终的权限真相必须在数据库层体现。

也就是说：

- 即便前端写错
- 即便请求被伪造
- 也不能突破数据库层的用户隔离规则

## 七、数据库层访问控制策略

第一阶段建议以 `Supabase` 的数据库权限控制能力为核心，采用 **RLS（Row Level Security）+ 角色约束** 模式。

### 7.1 `profiles`

建议策略：

- 普通用户只能读取自己的 `profiles` 行
- 普通用户只能更新自己的可编辑字段
- 普通用户不能修改自己的管理员资格信息
- 管理员可读取后台需要的用户基础资料，但应限制字段范围与使用场景

### 7.2 `articles`

建议策略：

- 用户只能读取自己的文章
- 用户只能创建属于自己的文章
- 用户只能更新自己的文章
- 用户只能软删除自己的文章
- 管理员默认不直接读取全部用户文章正文

### 7.3 `bookmarks`

建议策略：

- 用户只能读取自己的收藏
- 用户只能创建属于自己的收藏
- 用户只能更新自己的收藏
- 用户只能软删除自己的收藏
- 管理员默认不直接读取全部用户收藏内容

### 7.4 `reading_marks`

建议策略：

- 用户只能读取自己的阅读进度
- 用户只能写入自己的阅读进度
- 用户只能覆盖更新自己的阅读进度

### 7.5 `featured_articles`

建议策略：

- 已发布内容可按产品需要开放只读访问
- 草稿与归档内容仅管理员可见
- 创建、更新、发布、归档仅管理员可执行

如果产品第一阶段继续保留“未登录也能看推荐内容”，则匿名访问也只能读取：

- `status = 'published'`

### 7.6 `admin_roles`

建议策略：

- 普通用户不能读写所有 `admin_roles`
- 后台鉴权或受控服务端逻辑可以校验管理员资格
- 管理员资格的授予与撤销应通过受控流程完成，不应开放给普通前端直接修改

### 7.7 `audit_logs`

建议策略：

- 普通用户无权读取
- 普通用户无权写入
- 管理员可读取与后台有关的审计日志
- 审计日志写入应由后台受控动作触发
- 审计日志原则上只追加，不允许任意修改或删除

## 八、后台权限控制策略

### 8.1 路由级控制

后台路由必须同时满足：

- 用户已登录
- 会话有效
- `admin_roles` 存在有效管理员资格

任一条件不满足，都不能进入后台。

### 8.2 页面级控制

后台页面应按能力开放，例如：

- 推荐内容页：管理员可进入
- 用户状态页：管理员可进入
- 审计日志页：管理员可进入

第一阶段由于只有单一管理员角色，不需要再做复杂页面矩阵，但仍要保留未来可细分的结构。

### 8.3 动作级控制

不仅页面要受限，动作也要受限。

例如：

- 发布推荐文章
- 下架推荐文章
- 修改用户状态
- 撤销管理员资格

这些动作都必须在执行时再次校验管理员身份，而不是仅凭“用户已经打开后台页面”。

需要特别说明的是：

- 管理员资格授予或撤销虽然属于高风险权限动作
- 但第一阶段不默认把它作为后台 UI 常规页面能力开放
- 更适合通过受控流程执行，并保留审计要求

### 8.4 审计要求

以下后台动作建议默认写入 `audit_logs`：

- 推荐文章创建
- 推荐文章发布/下架/归档
- 用户状态变更
- 管理员资格授予或撤销

这样后续排查问题时，才能回答：

- 谁做的
- 何时做的
- 改了什么

## 九、异常与安全场景处理

### 9.1 会话过期

当会话失效时：

- 前端应立即失去受限能力
- 需要重新拉取或清空身份上下文
- 用户访问私有数据或后台时应被要求重新登录

### 9.2 `profiles` 不存在或初始化失败

用户虽然认证成功，但如果 `profiles` 未成功建立：

- 不应直接进入完整业务态
- 应进入受控异常流程
- 需要提示用户稍后重试或联系支持

因为此时“能登录”不等于“产品身份可用”。

### 9.3 用户被禁用

若 `profiles.status = 'disabled'`：

- 应禁止继续访问私有业务能力
- 必要时强制退出登录态下的受限页面
- 后台可以保留查询与审计，但前台不应继续正常使用

### 9.4 管理员资格被撤销

若管理员的 `revoked_at` 生效：

- 应立即失去后台入口
- 已打开的后台页面应在下一次权限校验时被阻断
- 后台动作不能依赖旧页面缓存状态继续执行

### 9.5 越权访问尝试

若用户尝试访问不属于自己的数据：

- 前端可以提示无权限
- 数据库层必须直接拒绝请求
- 必要时对高风险后台越权动作记录审计日志

### 9.6 匿名用户与迁移期用户

迁移期需要特别处理一种情况：

- 用户本地有历史数据
- 但还没有登录

此时系统允许其继续保留本地数据，但：

- 不授予云端私有数据访问权
- 不允许进入后台
- 不应伪装成“已拥有正式账号资产”

## 十、总结

本次鉴权与权限设计的核心结论是：

- 采用 `Supabase Auth` 作为唯一认证入口
- 采用 `auth.users + profiles` 组成正式产品身份
- 采用“普通用户 + 单一管理员”作为第一阶段最小角色模型
- 采用前端拦截 + 后台路由控制 + 数据库 RLS 的三层权限防线
- 采用最小暴露原则保护用户私有阅读资产

这套设计既能支撑账号化与数据迁移，也能为后台最小可运营能力提供稳定的权限基础。
