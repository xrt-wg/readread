## 一、文档目的

定义核心业务数据如何在云端落地，包括：

- 表结构
- 字段设计
- 主外键关系
- 索引与约束
- 软删除/审计/扩展策略

本文件的目标不是一次性定义最终数据库形态，而是为构建期第一阶段提供一套可落地、可迁移、可扩展的正式数据结构。

本次设计采用以下已确认前提：

- **建立 `profiles` 表**，承接产品用户资料与状态
- **`featured_articles` 第一阶段正式入库**，作为后台可管理内容
- **后台第一阶段采用单一管理员角色**，通过 `admin_roles` 管理

---

## 二、设计原则

### 2.1 认证信息与产品资料分离

- `auth.users` 负责认证身份
- `profiles` 负责产品资料、迁移状态、用户状态

这样做可以避免把产品字段直接塞进认证层。

### 2.2 云端为主源，本地结构尽量平滑迁移

当前本地数据已经具备明确结构：

- `rr_articles`
- `rr_bookmarks`
- `rr_reading_marks`

因此数据库字段语义尽量与现有结构对齐，优先降低迁移复杂度。

### 2.3 用户资产必须显式归属

所有长期用户资产类数据都必须带有 `user_id`，不能仅依赖前端上下文推断所属关系。

### 2.4 业务对象 ID 优先保持兼容

第一阶段对 `articles`、`bookmarks`、`featured_articles` 采用文本型业务 ID，而不是强制改成新的 UUID 主键。

原因是：

- 当前前端已经使用字符串业务 ID
- 本地迁移时可直接沿用现有 ID
- 能降低文章、收藏、阅读进度之间的映射复杂度

认证用户仍以 `auth.users.id` 的 UUID 作为身份主标识。

### 2.5 最小可运营优先

第一阶段只覆盖当前确实需要的表与约束，不提前引入复杂事件流、推荐算法表、标签体系等增长期结构。

## 三、核心实体关系图

```markdown
auth.users
    ↓ 1:1
profiles
    ↓ 1:N
articles
    ↓ 1:N
bookmarks

profiles
    ↓ 1:N
reading_marks

profiles
    ↓ 1:N
admin_roles

profiles
    ↓ 1:N
audit_logs

featured_articles
    独立作为后台内容表
```

关系说明：

- 一个认证用户对应一个 `profiles` 记录
- 一个用户可以拥有多篇个人文章
- 一篇文章可以拥有多个收藏
- 一个用户对一篇文章最多保留一条阅读进度记录
- `featured_articles` 属于后台运营内容，不属于普通用户私有资产
- 管理员身份附着在普通用户之上，而不是单独维护另一套后台账号体系

## 四、表设计

### 4.1 `profiles/users`

第一阶段正式设计的产品用户表为 `profiles`。

说明：

- `auth.users` 是 Supabase Auth 自带认证表
- 业务层不重复定义认证敏感字段
- 产品资料与状态统一落在 `profiles`

建议字段如下：

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `user_id` | `uuid` | PK, FK -> `auth.users.id` | 用户唯一标识 |
| `display_name` | `text` | nullable | 用户显示名称 |
| `avatar_url` | `text` | nullable | 头像地址 |
| `status` | `text` | not null, default `'active'` | 用户状态 |
| `has_completed_initial_migration` | `boolean` | not null, default `false` | 是否完成首次迁移 |
| `initial_migrated_at` | `timestamptz` | nullable | 首次迁移完成时间 |
| `last_seen_at` | `timestamptz` | nullable | 最近活跃时间 |
| `created_at` | `timestamptz` | not null | 创建时间 |
| `updated_at` | `timestamptz` | not null | 更新时间 |

设计说明：

- `profiles` 不保存密码等认证敏感信息
- 迁移标记放在 `profiles` 中，避免散落在前端本地状态里
- 后续若增加语言偏好、会员状态、实验分组，也优先扩展在 `profiles`

### 4.2 `articles`

`articles` 承载用户导入或创建的个人文章资产。

建议字段如下：

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | `text` | PK | 文章业务 ID，沿用现有 `art_*` 风格 |
| `user_id` | `uuid` | not null, FK -> `profiles.user_id` | 文章所属用户 |
| `title` | `text` | not null | 标题 |
| `text` | `text` | not null | 纯文本正文 |
| `markdown` | `text` | nullable | Markdown 正文 |
| `word_count` | `integer` | not null, default `0` | 词数 |
| `source_type` | `text` | not null, default `'manual'` | 来源类型 |
| `source_url` | `text` | nullable | 来源 URL |
| `created_at` | `timestamptz` | not null | 创建时间 |
| `updated_at` | `timestamptz` | not null | 更新时间 |
| `deleted_at` | `timestamptz` | nullable | 软删除时间 |

设计说明：

- 保留 `text` 与 `markdown` 双字段，兼容当前内容结构
- 保留文本型业务 ID，降低迁移成本
- 使用 `deleted_at` 支持文章软删除，给恢复与审计留空间

### 4.3 `bookmarks`

`bookmarks` 承载阅读过程中产生的收藏资产。

建议字段如下：

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | `text` | PK | 收藏业务 ID，沿用现有 `bm_*` 风格 |
| `user_id` | `uuid` | not null, FK -> `profiles.user_id` | 收藏所属用户 |
| `article_id` | `text` | not null, FK -> `articles.id` | 所属文章 |
| `type` | `text` | not null | `word` / `phrase` / `sentence` / `paragraph` |
| `text` | `text` | not null | 收藏原文 |
| `translation` | `text` | nullable | 译文 |
| `context_sentence` | `text` | nullable | 所在句子 |
| `context_translation` | `text` | nullable | 语境译文 |
| `translation_status` | `text` | not null, default `'pending'` | 翻译状态 |
| `paragraph_index` | `integer` | nullable | 所在段落索引 |
| `char_offset` | `integer` | nullable | 段落内起始偏移 |
| `review_count` | `integer` | not null, default `0` | 复习次数 |
| `next_review_at` | `timestamptz` | nullable | 下次复习时间 |
| `familiarity` | `smallint` | not null, default `0` | 熟悉度，0-5 |
| `created_at` | `timestamptz` | not null | 创建时间 |
| `updated_at` | `timestamptz` | not null | 更新时间 |
| `deleted_at` | `timestamptz` | nullable | 软删除时间 |

设计说明：

- 保持与当前 `createBookmark` 结构对齐
- 第一阶段不对“语义重复收藏”施加强唯一约束，避免误伤已有用户数据
- `review_*` 相关字段继续保留，为后续复习系统预埋空间

### 4.4 `reading_marks`

`reading_marks` 记录用户对某篇文章的阅读进度。

当前本地结构已经体现：

- 一个用户对一篇文章只需要一条阅读进度记录

因此第一阶段采用组合主键，而不是再引入随机记录 ID。

建议字段如下：

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `user_id` | `uuid` | PK(1), FK -> `profiles.user_id` | 用户 |
| `article_id` | `text` | PK(2), FK -> `articles.id` | 文章 |
| `paragraph_index` | `integer` | nullable | 当前阅读位置 |
| `completed` | `boolean` | not null, default `false` | 是否读完 |
| `created_at` | `timestamptz` | not null | 创建时间 |
| `updated_at` | `timestamptz` | not null | 更新时间 |

设计说明：

- `(user_id, article_id)` 唯一，即一个用户对一篇文章只有一个进度状态
- `completed = true` 时 `paragraph_index` 可为空，不强制保留最后位置
- 该结构与当前前端 `readingMarkStore` 的语义完全一致

### 4.5 `featured_articles`

`featured_articles` 第一阶段正式入库，作为后台运营内容表。

建议字段如下：

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | `text` | PK | 推荐文章业务 ID，兼容现有 `featured_*` |
| `title` | `text` | not null | 标题 |
| `source` | `text` | nullable | 来源站点 |
| `description` | `text` | nullable | 简介 |
| `text` | `text` | not null | 纯文本正文 |
| `markdown` | `text` | nullable | Markdown 正文 |
| `cover_image_url` | `text` | nullable | 封面图 |
| `status` | `text` | not null, default `'published'` | 内容状态 |
| `sort_order` | `integer` | not null, default `0` | 排序值 |
| `published_at` | `timestamptz` | nullable | 发布时间 |
| `created_by` | `uuid` | nullable, FK -> `profiles.user_id` | 创建人 |
| `updated_by` | `uuid` | nullable, FK -> `profiles.user_id` | 更新人 |
| `created_at` | `timestamptz` | not null | 创建时间 |
| `updated_at` | `timestamptz` | not null | 更新时间 |
| `deleted_at` | `timestamptz` | nullable | 软删除时间 |

设计说明：

- 这张表把当前静态推荐内容升级为后台可维护内容
- 第一阶段建议状态至少支持：`draft` / `published` / `archived`
- `sort_order` 用于首页或推荐位排序

### 4.6 `admin_roles`

第一阶段后台采用**单一管理员角色**。

因此 `admin_roles` 的目标不是构建复杂 RBAC，而是先把“谁是管理员”这件事清楚记录下来。

建议字段如下：

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `user_id` | `uuid` | PK, FK -> `profiles.user_id` | 管理员用户 |
| `role` | `text` | not null, default `'admin'` | 第一阶段固定为 `admin` |
| `granted_by` | `uuid` | nullable, FK -> `profiles.user_id` | 由谁授予 |
| `granted_at` | `timestamptz` | not null | 授权时间 |
| `revoked_at` | `timestamptz` | nullable | 撤销时间 |
| `created_at` | `timestamptz` | not null | 创建时间 |
| `updated_at` | `timestamptz` | not null | 更新时间 |

设计说明：

- 第一阶段虽然只有单一管理员，但仍保留 `role` 字段，便于未来扩展
- `revoked_at` 用于管理员资格失效的留痕，而不是直接物理删除
- 后续若出现内容运营、客服、超管等分工，再在该表上扩展即可

### 4.7 `audit_logs`

`audit_logs` 用于记录关键后台动作与重要系统操作。

建议字段如下：

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | `bigserial` | PK | 审计日志主键 |
| `actor_user_id` | `uuid` | nullable, FK -> `profiles.user_id` | 操作者 |
| `actor_role` | `text` | nullable | 操作时角色 |
| `action` | `text` | not null | 动作类型，如 `featured_article.publish` |
| `target_type` | `text` | not null | 目标对象类型 |
| `target_id` | `text` | nullable | 目标对象 ID |
| `payload` | `jsonb` | nullable | 变更详情 |
| `ip_address` | `text` | nullable | 来源 IP |
| `created_at` | `timestamptz` | not null | 操作时间 |

设计说明：

- 第一阶段重点审计后台动作，而不是记录所有普通用户行为
- `payload` 使用 `jsonb`，便于记录前后值或上下文信息
- 审计日志默认只追加，不做业务上的更新覆盖

## 五、索引与约束策略

### 5.1 主键与基础索引

- `profiles.user_id` 主键
- `articles.id` 主键
- `bookmarks.id` 主键
- `reading_marks(user_id, article_id)` 组合主键
- `featured_articles.id` 主键
- `admin_roles.user_id` 主键
- `audit_logs.id` 主键

### 5.2 常用查询索引

建议增加以下索引：

- `articles(user_id, created_at desc)`
- `articles(user_id, deleted_at)`
- `bookmarks(user_id, article_id, created_at desc)`
- `bookmarks(user_id, deleted_at)`
- `bookmarks(article_id)`
- `reading_marks(user_id)`
- `featured_articles(status, sort_order)`
- `admin_roles(role, revoked_at)`
- `audit_logs(actor_user_id, created_at desc)`
- `audit_logs(target_type, target_id)`

### 5.3 业务约束建议

- `profiles.status` 限定在允许集合内，如 `active` / `disabled`
- `bookmarks.type` 限定在 `word` / `phrase` / `sentence` / `paragraph`
- `bookmarks.translation_status` 限定在允许集合内，如 `pending` / `done` / `failed`
- `bookmarks.familiarity` 限定为 `0 <= familiarity <= 5`
- `featured_articles.status` 限定在 `draft` / `published` / `archived`
- `admin_roles.role` 第一阶段虽固定为 `admin`，但仍建议保留枚举约束

### 5.4 关联一致性约束

- `bookmarks.article_id` 必须关联存在的用户文章
- `reading_marks.article_id` 必须关联存在的用户文章
- 后台内容与用户资产分离，不允许普通用户数据直接引用 `featured_articles` 作为私有资产主表

## 六、删除与归档策略

第一阶段建议采用“**用户资产软删除 + 审计日志追加写入**”策略。

### 6.1 软删除对象

建议以下表支持软删除：

- `articles`
- `bookmarks`
- `featured_articles`

原因：

- 给误删恢复留空间
- 便于迁移期核查与后台审计
- 避免第一阶段就因为物理删除造成不可逆数据损失

### 6.2 不建议软删除的对象

- `reading_marks`：可直接覆盖更新，不需要保留历史版本作为第一阶段能力
- `audit_logs`：只追加，不删除
- `admin_roles`：通过 `revoked_at` 表示失效，不建议物理删除

### 6.3 归档策略

第一阶段不单独建设归档库。

若未来出现以下情况，再考虑归档：

- 审计日志增长明显
- 推荐内容历史版本增多
- 用户删除恢复需求变复杂

## 七、未来扩展字段预留

以下方向已在当前设计中预留扩展空间，但第一阶段不要求落地：

### 7.1 用户侧扩展

- 语言偏好
- 会员状态
- 学习目标与学习档案
- 实验分组 / 功能开关

### 7.2 内容侧扩展

- 文章标签
- 文章封面与附件资源
- 推荐内容专题与分组
- 内容上下架原因与版本记录

### 7.3 学习与复习侧扩展

- 收藏复习计划
- 复习结果历史
- 记忆曲线策略参数

### 7.4 后台与审计扩展

- 更细的角色体系
- 操作审批流
- 更完整的事件日志
- 风险操作告警机制

---

## 八、总结

本次数据库设计的核心结论是：

- 以 `auth.users + profiles` 作为用户基础结构
- 以 `articles`、`bookmarks`、`reading_marks` 作为用户核心资产表
- 以 `featured_articles` 作为第一阶段正式入库的运营内容表
- 以 `admin_roles` 与 `audit_logs` 作为后台最小可运营的数据基础

这套结构既能承接当前本地数据迁移，也能支撑后续用户系统、权限设计和后台建设继续展开。
