## 一、文档目的

用于回答整体技术路线如何落地，包括：

- 系统边界如何划分
- 各组件承担什么职责
- 数据如何流动
- 为什么采用当前组合方案

本文件不是数据库细节设计，也不是实施排期文档。它的职责是把已确定的技术路线落成一张清晰的系统图，并回答：

- 哪些能力留在前端
- 哪些能力放在 `Netlify Functions`
- 哪些能力交给 `Supabase Auth`
- 哪些能力交给 `Supabase Postgres`
- 后台在整体系统中的位置是什么

## 二、总体架构图

当前采用的总体架构为：

```markdown
用户前端 / 管理后台前端
        ↓
   React + Vite（Netlify 静态部署）
        ↓
┌──────────────────────────────────────┐
│              前端调用层              │
│ - 用户界面状态                       │
│ - 本地缓存                           │
│ - 与云端 API / Auth 的交互           │
└──────────────────────────────────────┘
        ↓                ↓
        ↓                └──────────────→ Supabase Auth
        ↓                                   - 注册 / 登录 / 会话
        ↓                                   - 用户身份
        ↓
        ├──────────────→ Supabase Postgres
        │                  - articles
        │                  - bookmarks
        │                  - reading_marks
        │                  - featured_articles
        │                  - admin_roles
        │                  - audit_logs
        │
        └──────────────→ Netlify Functions
                           - 第三方翻译 / AI 代理
                           - URL 抓取代理
                           - 需要保管密钥的服务端逻辑
                           - 后续必要的轻聚合逻辑
```

与当前架构相比，关键变化不是“多了一个服务器”，而是：

- **用户业务数据从本地浏览器主存储迁移到云端数据库**
- **用户身份从匿名本地状态升级为正式账号体系**
- **前端不再直接承担长期数据持久化责任**

总体上，本方案采用的是：

> **静态前端 + 托管身份与数据库 + 轻服务端函数层**

## 三、核心组件与职责

### 3.1 前端

前端继续基于当前 `Vite + React` 形态演进，职责如下：

- 承担用户阅读体验与后台操作界面
- 负责页面状态管理、交互流程、加载态与异常提示
- 负责调用 Auth、数据库访问层和函数层接口
- 在迁移期承担本地数据检测、迁移引导与有限缓存职责

前端**不再承担**以下职责：

- 长期业务数据的唯一正式存储
- 第三方密钥管理
- 需要服务端权限保护的业务判断

前端内部的推荐演进方向是：

- 保留现有组件结构和阅读路径
- 将 `storage.js` 从本地适配器演进为“云端主源 + 本地缓存”的访问层入口
- 用户前台与管理员后台先采用**同仓、不同路由空间**的方式建设；若后续后台复杂度显著提升，再拆分独立工程

### 3.2 Netlify Functions

`Netlify Functions` 在总体方案中的定位是：**轻服务端边界层**，而不是完整业务后端。

当前已存在的职责：

- 翻译与 AI 代理
- 外部网页抓取代理
- 服务端环境变量与第三方密钥保护

后续继续保留它的原因：

- 这些能力本来就不适合放在浏览器执行
- 仍然需要一个靠近前端部署体系的轻服务端入口
- 可避免把所有逻辑都压入数据库或前端

但函数层**不应承担**：

- 所有核心业务数据的长期主存储
- 重型领域服务编排
- 提前复杂化的统一 API 网关角色

因此，本方案中函数层的边界是：

- **处理需要服务端保密或代理的能力**
- **处理少量必要的服务端聚合逻辑**
- **不抢占数据库与 Auth 的职责**

### 3.3 Supabase Auth

`Supabase Auth` 在本方案中负责：

- 用户注册与登录
- 会话管理
- 身份建立与用户唯一标识
- 为数据库访问控制提供身份上下文

它解决的是当前系统最缺失的一层：

- 谁是用户
- 哪些数据属于哪个用户
- 用户在不同设备上如何识别为同一个人

采用托管 Auth 的原因是：

- 比自建认证更快补齐构建期基础能力
- 与托管数据库更容易协同
- 有利于后续做数据隔离和角色控制

### 3.4 Supabase Postgres

`Supabase Postgres` 是本方案的正式数据底座，负责：

- 承载长期用户资产
- 承载后台运营数据
- 提供可查询、可约束、可审计的数据结构基础

数据库中承载的核心对象包括：

- 用户文章
- 收藏
- 阅读进度
- 推荐内容
- 管理员角色
- 审计日志

数据库在本方案中的角色是：

> **业务事实来源（source of truth）**

也就是说：

- 前端本地缓存可以存在
- 本地迁移输入可以存在
- 但长期主数据最终必须落在数据库中

### 3.5 运营后台

运营后台不是附属工具，而是这次构建期建设的正式组成部分。

它的职责包括：

- 管理推荐内容
- 查看用户与内容状态
- 进行最小必要的运营动作
- 记录并追踪关键后台操作

在总体方案里，后台的技术定位是：

- 与用户前台共享同一技术栈和部署外壳
- 通过独立路由与权限隔离控制访问
- 使用与用户端一致的数据底座和身份体系

这样做的好处是：

- 可减少额外工程成本
- 可统一部署与配置管理
- 可减少早期后台系统的结构分裂

## 四、核心数据流

### 4.1 用户注册/登录

总体数据流如下：

```markdown
用户打开前端
    ↓
进入登录 / 注册流程
    ↓
前端调用 Supabase Auth
    ↓
Auth 返回用户身份与会话
    ↓
前端持有登录态
    ↓
后续用户数据读写带上身份上下文
```

这一流转的目标是：

- 用户从匿名状态进入账号状态
- 云端数据访问具备归属关系
- 多设备登录建立同一身份前提

### 4.2 文章写入

文章写入分两类来源：

- 本地输入 / 粘贴 / 上传
- URL 导入

总体路径为：

```markdown
用户导入文章
    ↓
前端完成基础整理
    ↓
若是 URL 导入，需要通过 proxy function 获取正文
    ↓
前端得到标准化文章数据
    ↓
写入云端 articles
    ↓
前端刷新本地状态与缓存
```

这里的关键点是：

- URL 抓取仍由函数层承担
- 文章主数据最终落数据库
- 本地仅保留缓存，不再作为唯一持久化来源

### 4.3 收藏与阅读进度同步

收藏与阅读进度是最典型的长期资产数据，路径如下：

```markdown
用户阅读中产生收藏 / 阅读进度
    ↓
前端更新当前 UI 状态
    ↓
同步写入云端 bookmarks / reading_marks
    ↓
成功后更新本地缓存
    ↓
后续在任意设备登录后从云端恢复
```

这一流的设计重点是：

- 前端体验仍然顺滑
- 云端是最终权威源
- 本地缓存服务于性能与容错，而不是长期事实存储

### 4.4 本地迁移到云端

迁移是本方案中的关键过渡流：

```markdown
老用户登录
    ↓
前端检测 localStorage 中是否存在历史数据
    ↓
触发迁移引导
    ↓
按 articles / bookmarks / reading_marks 顺序上传到云端
    ↓
云端校验与落库
    ↓
前端显示迁移结果并切换到云端主模式
```

这里的总体原则是：

- 迁移必须显式、可校验、可重试
- 迁移完成后，产品应切换为账号化数据主路径
- 本地老数据不再继续作为长期真相来源

### 4.5 后台管理与审计

后台操作流如下：

```markdown
管理员登录后台
    ↓
系统校验管理员角色
    ↓
读取后台所需数据
    ↓
执行内容管理或运营动作
    ↓
写入业务结果
    ↓
记录 audit_logs
```

后台流的关键要求是：

- 后台与普通用户流必须隔离
- 后台动作必须具备角色约束
- 关键操作必须可追踪

## 五、边界与非目标

本总体方案明确以下边界：

- **不构建重型自建后端服务**
- **不先建设复杂统一 API 平台**
- **不先做复杂离线优先同步系统**
- **不在第一阶段引入完整 BI 或数据平台**
- **不把所有业务都塞进函数层**

这份总体方案关注的是：

- 建立稳定运行的基本结构
- 明确组件分工
- 保证后续数据库、权限、迁移、同步文档有共同架构前提

它不解决的细节问题包括：

- 具体表字段与约束
- 具体角色权限矩阵
- 具体迁移幂等策略
- 具体页面信息架构

这些将由后续专题文档展开。

## 六、技术选型落地说明

本方案落地到当前项目中的含义如下：

### 6.1 前端与部署

- 当前 `Vite + React` 保持不变
- 当前 `Netlify` 静态部署方式保持不变
- 用户端与后台端优先共用同一前端工程与部署体系

### 6.2 函数层

- 继续保留现有 `translate` 与 `proxy` 函数
- 后续仅在“必须由服务端承担”的能力上扩充函数层
- 避免函数层演化为早期重型 BFF

### 6.3 存储层

- 现有 `storage.js` 仍是重要演进锚点
- 但其职责将从“直接操作 localStorage”演进为“统一数据访问入口”
- 组件层尽量继续通过统一存储入口工作，降低迁移冲击

### 6.4 后端底座

- 引入 `Supabase Auth` 解决身份问题
- 引入 `Supabase Postgres` 解决长期存储问题
- 通过数据库侧权限能力建立访问边界

## 七、关键设计原则

本方案遵循以下设计原则：

1. **前端体验优先，但数据真相在云端**
2. **身份、存储、代理三层职责分离**
3. **保留现有前端价值，不推翻已验证路径**
4. **优先选择托管能力补齐基础设施短板**
5. **先做最小可用架构，再根据复杂度升级**
6. **把复杂性放在真正必要的地方，而不是平均分配到每一层**

这些原则会直接约束后续：

- 数据库设计
- 权限模型
- 数据迁移方案
- 同步与缓存策略
- 后台方案

## 八、主要风险与技术折中

本总体方案的主要折中包括：

### 8.1 托管后端换取速度，但接受平台边界

这是有意识的折中。

- 我们牺牲部分完全自定义能力
- 换取更快补齐构建期需要的基础设施

### 8.2 函数层继续存在，但不把它做成大后端

- 继续使用函数层可最大化复用现有结构
- 但必须克制函数层膨胀，否则会形成新的架构混乱

### 8.3 前台与后台先共仓部署，但保留未来拆分空间

- 共仓能降低第一阶段复杂度
- 若后台复杂度显著增加，再拆分更合理

### 8.4 先采用在线优先同步，而不是复杂离线优先

- 这不是能力不足，而是阶段性选择
- 当前阶段更重要的是稳定、可控、易验证

总体上，本方案的技术折中方向是：

> **优先稳定落地，而不是优先追求最终形态。**
