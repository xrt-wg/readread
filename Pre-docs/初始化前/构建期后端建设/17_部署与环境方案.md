## 一、文档目的

定义系统运行所需的环境划分、部署方式、配置管理与密钥管理。

本文件不重复定义数据库结构、权限细节或监控细则，而是负责回答：

- 当前系统应划分为哪些运行环境
- 前端、函数层、数据库分别如何部署与连接
- 环境变量和密钥应放在哪里管理
- 第一阶段发布前如何进行预发布验证
- 出现问题后如何进行回滚或止损

也就是说，这份文档的重点是把“系统怎么安全运行起来”这件事说清楚。

## 二、环境划分

### 2.1 第一阶段采用的环境模型

第一阶段采用以下环境划分：

- **本地开发环境**
- **正式环境**

本轮明确**不单独维护长期存在的预发布环境**。

这样选择的原因是：

- 当前阶段优先目标是尽快建立稳定可用的正式后端底座
- 若一开始同时维护开发、预发布、正式三套长期环境，会明显提高配置、数据和发布管理复杂度
- 现阶段更适合采用“本地开发 + 正式部署前验证”的方式控制风险

### 2.2 本地开发环境

本地开发环境的职责是：

- 前端页面开发与联调
- 后台页面开发与联调
- 函数层本地开发与基础调试
- 发布前的开发自测

本地环境的关键特征是：

- 前端在开发服务器中运行
- 需要通过本地环境变量连接云端能力
- 不承担正式对外服务职责

第一阶段由于不单独维护长期非正式 Supabase 项目，因此本地开发需要特别注意：

- 不应把本地开发当作可随意破坏数据的沙盒
- 涉及真实云端写入的联调必须使用受控测试账号和可识别的测试数据
- 高风险数据操作、结构调整和批量写入不应在随手联调中直接执行

### 2.3 正式环境

正式环境是第一阶段唯一长期承载真实用户数据与正式访问流量的环境。

正式环境承载：

- 用户前台
- 管理后台
- `Netlify Functions`
- `Supabase Auth`
- `Supabase Postgres`

正式环境的关键要求是：

- 对外访问稳定
- 配置来源清晰
- 密钥不暴露
- 发布可控
- 问题可回退或可止损

### 2.4 预发布验证的定义

虽然第一阶段不维护第三套长期环境，但**正式发布前仍必须进行预发布验证**。

这里的“预发布验证”指的是：

- 在正式发布前，对即将上线的构建结果进行一次受控验证
- 验证构建、路由、鉴权、函数调用和关键页面是否正常

它**不等同于**：

- 一套长期存在、独立维护的完整预发布基础设施

因此第一阶段的策略是：

- **有预发布验证机制**
- **但没有长期常驻的第三环境**

## 三、部署拓扑

第一阶段建议采用以下部署拓扑：

```markdown
用户前台 / 管理后台
        ↓
 Netlify 静态站点部署
        ├── 前端静态资源
        └── Netlify Functions
                ↓
         第三方代理 / 密钥保护逻辑

前端 / 函数层
        ↓
   Supabase Auth + Supabase Postgres
        ↓
   正式身份与正式业务数据
```

### 3.1 前台与后台共用部署外壳

第一阶段延续既有总体方案：

- 用户前台与管理后台优先共用同一前端工程
- 通过不同路由空间组织前台与后台页面
- 通过权限控制决定后台入口是否可访问

这样做的好处是：

- 减少额外工程与部署成本
- 统一前端构建与配置管理
- 保持当前阶段的复杂度可控

### 3.2 Netlify 继续作为交付外壳

当前项目已经存在明确的 `Netlify` 构建配置：

- 构建命令：`npm run build`
- 发布目录：`dist`
- 函数目录：`netlify/functions`

这意味着第一阶段不改变交付外壳，继续采用：

- 静态资源由 `Netlify` 发布
- 函数与站点同体系部署
- SPA 路由通过重定向规则回到 `index.html`

### 3.3 Supabase 作为唯一正式后端项目

第一阶段采用**一个正式 Supabase 项目**作为云端身份与数据底座。

它统一承载：

- `Auth`
- `Postgres`
- 后续所需数据库权限控制能力

这样做的核心目的不是追求最终理想形态，而是：

- 先用最小复杂度把正式身份和正式数据底座建立起来

## 四、环境变量与密钥管理

### 4.1 基本原则

环境变量与密钥管理遵循以下原则：

1. **前端可公开配置与服务端密钥必须分层管理**
2. **所有密钥优先放在托管平台配置中，不写入仓库**
3. **本地开发使用本地环境文件，不提交到版本库**
4. **任何高权限密钥都不能暴露到浏览器端**

### 4.2 前端可见配置

前端运行时需要的公开配置，例如：

- `Supabase URL`
- `Supabase Anon Key`

这类配置可以作为前端可见环境变量存在，但必须满足：

- 它们本身不具备高权限
- 即使被前端看到，也不会突破数据库权限边界

也就是说：

- 前端可以使用公开客户端配置
- 真正的数据访问边界仍应由数据库权限与身份体系保证

### 4.3 服务端密钥

以下类型密钥必须只放在服务端受控环境中：

- 第三方翻译服务密钥
- AI 服务密钥
- 任何高权限数据库密钥
- 任何仅应在函数层或受控后台动作中使用的密钥

这些密钥应放在：

- `Netlify` 的环境变量配置
- 或 `Supabase` 后台的受控配置中

它们不应：

- 出现在前端源码中
- 进入前端构建产物
- 被写入公共文档截图或调试输出

### 4.4 本地开发变量管理

本地开发应采用本地环境文件，例如：

- `.env.local`
- 或团队约定的本地私有配置文件

要求如下：

- 不提交到版本库
- 不共享真实高权限密钥到不必要的本地环境
- 变量命名与正式环境保持一致，降低切换成本

### 4.5 密钥轮换与变更管理

第一阶段虽不建立复杂密钥平台，但仍应遵循基本变更规则：

- 密钥变更后要同步检查受影响函数与部署配置
- 怀疑泄露时优先轮换，而不是继续沿用
- 密钥轮换后应执行一次最小验证，确认主要链路未失效

## 五、前端部署约束

### 5.1 构建与发布约束

前端继续采用当前静态站点构建方式：

- 通过 `npm run build` 产出静态资源
- 发布目录为 `dist`
- 通过 `Netlify` 对外发布

第一阶段不引入额外前端部署平台，不拆出独立后台前端部署链路。

### 5.2 路由约束

由于当前是 SPA 结构，因此部署层需要保证：

- 非静态资源路径可回退到 `index.html`
- 用户前台和管理后台的前端路由都能被正确接管

当前 `netlify.toml` 中的重定向规则已经满足这一基础要求。

### 5.3 配置注入约束

前端构建过程中需要的环境变量必须来自平台配置或本地环境文件，不能采用以下做法：

- 在源码中硬编码环境地址
- 在组件中散落写死密钥或域名
- 用手工改源码的方式完成环境切换

### 5.4 预发布验证范围

正式发布前，前端至少应验证以下内容：

- 站点可正常构建
- 关键页面路由正常
- 登录入口正常
- 管理后台受限路由行为正常
- 关键页面无明显资源加载错误

由于没有长期独立预发布环境，因此这里的重点是：

- 验证“将要上线的构建产物是否可用”
- 而不是在另一整套长期环境中做完整仿真运营

### 5.5 前端回滚边界

若前端发布后出现问题，应优先考虑：

- 回退到上一版稳定部署
- 暂时关闭问题入口或受影响路由
- 通过快速修复重新发布

前端回滚本身应尽量避免与数据库高风险变更绑定在同一个不可拆分步骤里。

## 六、函数层部署约束

### 6.1 与站点同体系部署

第一阶段函数层继续部署在 `Netlify Functions` 中，并与站点保持同体系发布。

这样做意味着：

- 函数部署与前端部署节奏一致
- 环境变量管理集中在同一平台中
- 不新增独立函数运行平台

### 6.2 函数职责边界

函数层继续承担：

- 第三方请求代理
- 需要隐藏密钥的服务端调用
- 少量必要的轻聚合逻辑

函数层不应承担：

- 重型业务编排
- 长期主数据存储
- 绕开数据库权限体系的随意后门能力

### 6.3 配置与密钥约束

函数层使用的密钥必须来自平台环境变量。

必须避免：

- 在函数文件中硬编码密钥
- 在前端调用参数中透传敏感服务端密钥
- 在日志中打印完整密钥内容

### 6.4 发布前验证要求

函数层发布前至少要验证：

- 路由可调用
- 基础参数校验正常
- 关键第三方依赖未因配置缺失而失效
- 常见错误路径能返回可理解的失败信息

若函数改动涉及密钥、外部 API 或权限边界，验证优先级应进一步提高。

### 6.5 函数层回滚策略

若函数层发布后出现问题，应优先考虑：

- 回退到上一版稳定部署
- 暂停相关入口调用
- 以最小修复重新发布

若问题来源是第三方密钥或配置错误，则应优先修正配置，而不是盲目重复发布。

## 七、数据库环境约束

### 7.1 第一阶段数据库环境选择

第一阶段采用**一个正式 Supabase 项目**作为唯一正式数据库环境。

这是一项明确的阶段性取舍：

- 降低环境管理复杂度
- 优先把正式身份与数据链路稳定跑通

相应代价也必须正视：

- 数据库变更容错空间更小
- 本地联调与正式数据边界必须更谨慎地控制

### 7.2 本地联调约束

由于没有长期独立的云端测试库，因此本地开发与联调必须遵循以下约束：

- 使用专门测试账号，而不是随意混用真实业务账号
- 测试数据应可识别、可清理
- 批量写入、批量迁移、结构实验不应直接在日常联调中执行

这部分约束的核心目标是：

- **在单一正式项目策略下，尽量降低误污染正式数据的风险。**

### 7.3 结构变更约束

数据库结构变更在第一阶段应尽量遵循：

- 优先采用可审查、可复现的变更方式
- 避免长期依赖随手在控制台直接修改结构
- 高风险变更应与普通前端页面发布区分看待

尤其是以下变更，应视为高风险：

- 删除字段
- 改变字段语义
- 大规模数据回填
- 影响 RLS 或权限边界的变更

### 7.4 数据变更约束

正式数据库是系统长期事实来源，因此应明确：

- 后台运营动作可以写正式数据，但必须受权限和审计约束
- 数据迁移动作必须显式执行，不应混入普通页面发布中静默触发
- 任何会大范围影响用户资产的数据操作，都应先确认影响范围与恢复手段

### 7.5 数据库回退思路

数据库回退通常比前端回退更困难，因此第一阶段应遵循：

- 能做增量、兼容式变更时，优先不做破坏式变更
- 出问题时优先考虑前向修复，而不是轻率依赖物理回退
- 高风险数据库操作不应与其他无关改动同时混发

更完整的备份与恢复策略将在后续 `18_监控、备份与安全方案.md` 中展开。

## 八、发布与回滚策略

### 8.1 第一阶段发布原则

第一阶段采用：

- **正式环境发布前必须完成预发布验证**

但同时保持：

- **不单独维护长期第三环境**

这意味着发布流程必须更强调“单次发布前验证质量”，而不是依赖环境层数来兜底。

### 8.2 推荐发布流程

推荐采用以下顺序：

```markdown
本地开发完成
    ↓
本地自测
    ↓
生成待发布构建结果
    ↓
进行预发布验证
    ↓
确认关键链路通过
    ↓
执行正式发布
    ↓
发布后快速检查
```

### 8.3 预发布验证清单

第一阶段建议至少覆盖以下验证项：

- 前端构建成功
- 关键页面路由正常
- 登录链路正常
- 管理后台权限拦截正常
- 关键函数可调用
- 基础环境变量已正确注入

若本次发布涉及以下内容，则应提高验证强度：

- 鉴权逻辑
- 用户迁移链路
- 后台权限逻辑
- 数据库结构变更
- 第三方密钥变更

### 8.4 正式发布后的快速检查

正式发布完成后，不应认为流程已经结束，还应立即执行一次最小上线检查，例如：

- 首页是否可访问
- 登录入口是否正常
- 关键受限页面是否仍能正确鉴权
- 关键函数是否可调用

其目标是尽快发现“构建成功但运行异常”的问题。

### 8.5 回滚策略

不同层的回滚策略应区分对待：

- **前端静态资源**：优先回退到上一稳定部署
- **函数层**：优先回退到上一稳定部署或修正配置后重发
- **环境变量配置**：按变更项回退到上一个稳定值
- **数据库结构与数据**：优先前向修复，避免把数据库回退当作默认常规动作

### 8.6 发布节奏上的约束

第一阶段不建议：

- 把高风险数据库变更与大量页面改动一次性混发
- 在未完成最小预发布验证前直接推正式环境
- 把迁移逻辑上线当作普通 UI 小改一样处理

发布策略的核心目标是：

- **在环境数量较少的前提下，仍然保持发布可控。**

---

## 九、总结

本次部署与环境方案的核心结论是：

- 第一阶段环境划分采用“本地开发 + 正式环境”，不单独维护长期预发布环境
- 第一阶段继续以 `Netlify` 作为前端与函数层的统一交付外壳
- 第一阶段以一个正式 `Supabase` 项目为主，优先建立正式身份与数据底座
- 正式发布前必须进行预发布验证，但该验证是发布流程的一部分，而不是第三套长期环境
- 在单一正式数据库项目策略下，必须强化本地联调约束、结构变更约束和发布前检查

这份方案的作用，是在当前阶段以最小复杂度建立可运行、可发布、可回退的环境与部署基础，为后续监控、备份与安全方案提供前提。
