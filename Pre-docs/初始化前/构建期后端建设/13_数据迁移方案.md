# 构建期后端建设 — 数据迁移方案

- **日期**：2026-05-09
- **状态**：已完成
- **依据**：
  - `11_数据库设计.md`
  - `12_鉴权与权限设计.md`

---

## 一、文档目的

定义现有 `localStorage` 数据如何安全迁移到云端。

本文件关注的不是“是否迁移”，而是“如何在不丢数据、不重复导入、不制造混乱的前提下完成迁移”。

本次迁移的核心目标是：

- 让已有本地用户平滑进入账号化体系
- 让本地数据成为迁移输入，而不是长期权威源
- 让迁移过程可重复、可校验、可恢复

---

## 二、迁移目标

本轮迁移需要同时满足以下目标：

1. **把用户现有本地资产迁移到云端主存储**
2. **保留现有业务 ID，降低映射复杂度**
3. **在迁移失败时不破坏用户本地原始数据**
4. **允许中断后重试，而不产生重复数据**
5. **迁移完成后，把账号云端数据切换为主路径**

这意味着本次迁移方案不追求：

- 一次请求完成全量迁移
- 全局单事务回滚
- 迁移完成后立即强制删除本地所有原始数据

本次迁移追求的是：

> **安全优先、可重入优先、校验优先。**

## 三、迁移对象

当前本地数据主要来自 `storage.js` 中的三类正式业务数据。

### 3.1 `rr_articles`

本地结构：数组。

代表含义：

- 用户导入或创建的文章资产

迁移目标表：

- `articles`

建议迁移映射关系：

| 本地字段 | 云端字段 | 说明 |
| --- | --- | --- |
| `id` | `id` | 原样保留，沿用现有 `art_*` 业务 ID |
| `title` | `title` | 标题 |
| `text` | `text` | 纯文本正文 |
| `markdown` | `markdown` | Markdown 正文 |
| `wordCount` | `word_count` | 字段命名转换 |
| `createdAt` | `created_at` | 保留原始创建时间 |
| `createdAt` | `updated_at` | 第一阶段若无独立更新时间，可先沿用 |

补充字段：

- `user_id`：来自当前登录用户
- `source_type`：默认设为 `manual`，若后续能识别 URL 来源再补充
- `source_url`：当前本地结构无正式字段时可先为空
- `deleted_at`：默认为空

### 3.2 `rr_bookmarks`

本地结构：数组。

代表含义：

- 用户阅读中产生的收藏资产

迁移目标表：

- `bookmarks`

建议迁移映射关系：

| 本地字段 | 云端字段 | 说明 |
| --- | --- | --- |
| `id` | `id` | 原样保留，沿用现有 `bm_*` 业务 ID |
| `articleId` | `article_id` | 关联文章 |
| `type` | `type` | 收藏类型 |
| `text` | `text` | 收藏原文 |
| `translation` | `translation` | 译文 |
| `contextSentence` | `context_sentence` | 上下文句子 |
| `contextTranslation` | `context_translation` | 上下文译文 |
| `translationStatus` | `translation_status` | 翻译状态 |
| `paragraphIndex` | `paragraph_index` | 段落索引 |
| `charOffset` | `char_offset` | 字符偏移 |
| `reviewCount` | `review_count` | 复习次数 |
| `nextReviewAt` | `next_review_at` | 下次复习时间 |
| `familiarity` | `familiarity` | 熟悉度 |
| `createdAt` | `created_at` | 创建时间 |
| `createdAt` | `updated_at` | 第一阶段若无独立更新时间，可先沿用 |

补充字段：

- `user_id`：来自当前登录用户
- `deleted_at`：默认为空

迁移前约束：

- 只有在关联文章已存在于本次迁移后的 `articles` 中时，收藏才允许导入

### 3.3 `rr_reading_marks`

本地结构：对象，以 `articleId` 为 key。

代表含义：

- 用户对某篇文章的阅读进度状态

迁移目标表：

- `reading_marks`

建议迁移映射关系：

| 本地字段 | 云端字段 | 说明 |
| --- | --- | --- |
| `articleId` | `article_id` | 文章 ID |
| `paragraphIndex` | `paragraph_index` | 阅读位置 |
| `completed` | `completed` | 是否读完 |
| `updatedAt` | `updated_at` | 最近更新时间 |

补充字段：

- `user_id`：来自当前登录用户
- `created_at`：若本地无独立创建时间，可先使用 `updatedAt`

迁移前约束：

- 只有在对应文章存在时，阅读进度才允许导入

## 四、迁移触发时机

### 4.1 触发前提

迁移应在以下条件同时成立时触发：

- 用户已完成登录
- `profiles` 已成功建立
- 当前用户 `has_completed_initial_migration = false`
- 当前设备 `localStorage` 中存在可识别的历史业务数据

### 4.2 触发时点

推荐触发时点：

- 用户首次登录成功后
- 产品身份上下文已建立后
- 用户开始正式读写云端数据之前

也就是说，迁移应尽量发生在“账号已建立、云端主路径尚未开始大量使用”的窗口期。

### 4.3 用户交互方式

迁移不建议默默后台自动执行到不可见状态，而应采用：

- 检测到本地历史数据
- 弹出显式迁移提示
- 说明迁移对象和目的
- 用户确认后开始迁移

这样做的原因是：

- 用户会理解为什么需要登录后处理数据
- 用户对“本地数据将进入账号资产”有明确预期
- 迁移失败时更容易解释与重试

若用户此时选择稍后处理，则系统应保持“待迁移态”而不是直接把用户送入正常云端主路径。

该状态下应明确：

- 用户已完成认证，但未完成本设备历史数据并入账号
- 不进入正常云端私有数据读写主路径
- 不把“未迁移”伪装成“已完成账号主路径切换”
- 后续仍应在关键节点继续提示迁移，而不是静默视为已完成

### 4.4 无历史数据的情况

若用户登录后检测不到本地历史数据：

- 不执行迁移写入
- 可以将该用户视为“无需迁移”并完成首次迁移检查
- 后续直接进入账号云端主路径

## 五、迁移流程

推荐采用以下阶段化流程：

```markdown
Step 1：登录成功，建立身份上下文
Step 2：检测本地是否存在历史数据
Step 3：生成本地迁移快照
Step 4：做结构校验与预检查
Step 5：迁移 articles
Step 6：迁移 bookmarks
Step 7：迁移 reading_marks
Step 8：执行迁移后校验
Step 9：标记 profiles.has_completed_initial_migration = true
Step 10：切换到云端主路径
```

### 5.1 生成迁移快照

开始迁移前，应先把当前本地数据整理成一个稳定快照，而不是边读边写。

可以直接利用当前导出结构概念：

- `version`
- `exportedAt`
- `articles`
- `bookmarks`
- `readingMarks`

这样做的好处是：

- 迁移输入固定
- 便于重试时复用同一批数据逻辑
- 便于后续问题排查

### 5.2 预检查

预检查建议包含：

- 本地数据格式是否合法
- `articles` 是否为数组
- `bookmarks` 是否为数组
- `readingMarks` 是否为对象
- 关键字段如 `id`、`articleId` 是否存在

预检查失败时：

- 不开始正式写入云端
- 提示迁移失败并允许重试

### 5.3 迁移顺序

推荐严格按以下顺序迁移：

1. `articles`
2. `bookmarks`
3. `reading_marks`

原因：

- 收藏依赖文章存在
- 阅读进度依赖文章存在
- 先迁依赖源，再迁依赖项，最稳定

### 5.4 迁移完成后的切换

只有当迁移后校验通过时，才执行以下动作：

- 将 `profiles.has_completed_initial_migration` 标为 `true`
- 记录 `initial_migrated_at`
- 让前端后续以云端为正式主路径

第一阶段建议：

- **不立即物理清空本地原始数据**
- 但**不再把本地数据作为正式权威源**

这样做可以降低误删与回退风险。

## 六、幂等与去重策略

迁移方案必须是**可重入**的，也就是：

- 用户重复点一次，不应重复插入
- 上一次迁到一半失败，下次可以继续补齐

### 6.1 `articles` 的幂等策略

- 以 `id + user_id` 作为唯一识别
- 若云端已存在同 ID 文章，则视为“已迁移”或“已存在”，不重复创建
- 不因重复迁移而产生第二篇同义文章

### 6.2 `bookmarks` 的幂等策略

- 以 `id + user_id` 作为唯一识别
- 若云端已存在同 ID 收藏，则跳过重复创建
- 重试时只补插缺失的收藏

### 6.3 `reading_marks` 的幂等策略

阅读进度适合采用 **upsert** 思路：

- 唯一键：`(user_id, article_id)`
- 若云端不存在，则创建
- 若云端已存在，则按“更合理的进度”合并

建议合并规则：

- 若任一方 `completed = true`，结果取 `true`
- 否则取更大的 `paragraph_index`
- `updated_at` 取较新的时间

### 6.4 为什么不追求全局事务回滚

迁移过程跨多张表、跨网络请求，很难在第一阶段优雅实现一次性全局事务回滚。

因此本方案选择：

- **不追求全局回滚**
- **追求每个步骤幂等且可重试**

这是更符合当前阶段的稳定方案。

## 七、冲突处理策略

### 7.1 本地与云端同时存在同 ID 文章

处理原则：

- 若云端已存在同 ID 文章，优先视为已存在，不重复覆盖
- 第一阶段不尝试做复杂内容合并

原因：

- 当前文章 ID 来源于本地生成，正常情况下同 ID 就应代表同一资产
- 为避免覆盖用户已经存在的云端数据，第一阶段默认偏保守

### 7.2 收藏引用了不存在的文章

处理原则：

- 该收藏不导入
- 记录为迁移警告项
- 不自动创建“幽灵文章”补洞

原因：

- 收藏必须建立在合法文章资产上
- 自动补造文章会污染数据语义

### 7.3 阅读进度引用了不存在的文章

处理原则：

- 该阅读进度不导入
- 记录为迁移警告项

### 7.4 用户已在另一设备产生少量云端数据

处理原则：

- 对 `articles` 和 `bookmarks` 采用“存在则跳过，不存在则插入”
- 对 `reading_marks` 采用合并逻辑
- 不做“用本地全量覆盖云端”这种高风险策略

### 7.5 内容格式异常

若单条记录关键字段缺失或格式异常：

- 不阻塞整批迁移
- 跳过异常记录
- 在迁移结果中记录失败数量与原因

这比“因为一条坏数据导致整批失败”更符合用户安全与产品稳定性。

## 八、失败重试与回滚策略

### 8.1 失败分类

迁移失败可分为三类：

- **预检查失败**：本地数据结构异常
- **写入失败**：网络错误、权限错误、服务端异常
- **校验失败**：写入似乎成功，但数量或关联关系不一致

### 8.2 重试策略

重试原则：

- 保留本地原始数据不动
- 重新读取或复用迁移快照
- 按同样顺序再次执行迁移
- 依赖幂等策略跳过已成功记录

这样就能做到：

- 第一次只迁成功一部分也没关系
- 第二次继续迁不会重复造数据

### 8.3 回滚策略

第一阶段建议采用：

- **不做全局自动回滚**
- **做局部失败隔离 + 可重复迁移**

原因：

- 自动回滚很容易把已经安全写入的数据再删掉，风险更高
- 对用户来说，“保留成功数据并允许补齐”通常比“全删后重来”更安全

### 8.4 本地数据保留策略

迁移成功后：

- 本地数据先继续保留一段过渡期
- 但产品逻辑切换为云端主源
- 后续是否清理本地缓存，由后续同步与缓存策略文档统一约束

### 8.5 用户提示策略

失败时应明确告诉用户：

- 哪一步失败了
- 是否已经有部分数据成功迁入
- 可以直接重试
- 本地原始数据仍然保留

这能显著降低用户对“迁移是否会丢数据”的恐惧。

## 九、迁移校验标准

迁移成功不能只看“接口没报错”，还需要做结果校验。

### 9.1 数量校验

至少校验以下计数：

- 本地 `articles` 数量 = 云端成功迁入数 + 跳过数 + 失败数
- 本地 `bookmarks` 数量 = 云端成功迁入数 + 跳过数 + 失败数
- 本地 `reading_marks` 数量 = 云端成功迁入数 + 跳过数 + 失败数

### 9.2 关联校验

至少校验：

- 已迁移收藏关联的文章在云端存在
- 已迁移阅读进度关联的文章在云端存在

### 9.3 用户归属校验

至少校验：

- 所有迁入数据的 `user_id` 都属于当前登录用户
- 不允许把本地数据误写到其他账号下

### 9.4 状态校验

迁移完成后应校验：

- `profiles.has_completed_initial_migration = true`
- `profiles.initial_migrated_at` 已正确记录

### 9.5 产品行为校验

从用户体验角度，迁移完成后至少应满足：

- 刷新页面后能从云端读到迁移后的文章
- 对应文章下能看到原有收藏
- 对应文章能恢复原有阅读进度
- 清理本地浏览器缓存后，登录同一账号仍可取回核心数据

## 十、总结

本次迁移方案的核心结论是：

- 迁移对象为 `rr_articles`、`rr_bookmarks`、`rr_reading_marks`
- 迁移在登录成功且身份初始化完成后触发
- 迁移顺序为 `articles → bookmarks → reading_marks`
- 迁移采用“保留业务 ID + 幂等跳过 + 局部合并”的策略
- 迁移失败时不破坏本地原始数据，允许重复重试
- 迁移完成后切换为云端主路径，但第一阶段不立即清空本地源数据

这套方案的目标，不是做出最复杂的迁移系统，而是让已有用户能够安全、稳定地进入正式账号与云端数据体系。
