## 二、当前状态（Where we are）

### 2.1 产品阶段

ReadRead 当前已从验证期进入 **构建期**。

判断依据如下：

- 已有可运行产品，核心阅读路径已经形成
- 用户已经产生实际使用行为，而非仅口头反馈
- 已出现重复使用信号，说明产品并非一次性体验
- 当前主要问题已从“有没有价值”转向“能否长期稳定承载使用”

因此，当前阶段的核心问题不再是继续证明价值，而是：

> **如何建立稳定运行所需的数据、身份与运营基础设施。**

### 2.2 当前用户价值验证结论

目前可以确认的验证结论：

- 以英文阅读为核心场景的产品方向成立
- 导入文章、阅读、划词翻译、收藏等核心用户路径已经形成闭环
- 收藏、阅读进度、后续复习潜力说明该产品具备长期使用属性
- 产品价值已经开始从“即时翻译工具”转向“长期阅读与学习载体”

这意味着：

- 用户数据不再是临时状态，而是长期资产
- 数据一旦丢失，将直接破坏用户复用和沉淀
- 后续产品价值越来越依赖账号化、同步、后台运营和数据治理能力

### 2.3 当前系统架构现状

当前系统可概括为：

- 前端：`Vite + React`
- 部署：`Netlify`
- 轻服务端：`Netlify Functions`
- 当前数据主存储：浏览器 `localStorage`
- 当前后端数据底座：**尚未建立**

当前已有服务端能力主要用于：

- 代理调用翻译/AI 服务
- 保管第三方 API Key
- 代理抓取外部网页内容

当前尚不存在：

- 正式数据库
- 用户身份系统
- 云端主存储
- 权限隔离机制
- 运营后台
- 数据备份与审计机制

### 2.4 当前系统短板

当前最关键的系统短板包括：

- **数据安全不足**：文章、收藏、阅读进度仍依赖本地浏览器存储
- **账号能力缺失**：用户无法登录，数据无法与身份绑定
- **多端同步缺失**：换设备或清缓存会导致使用连续性中断
- **后台能力缺失**：推荐内容、用户状态、运营动作无法通过正式系统管理
- **权限与审计缺失**：没有正式访问控制，也没有后台操作留痕机制
- **长期扩展基础不足**：复习系统、行为分析、稳定运营都缺乏云端基础支撑

### 2.5 当前主要风险

如果继续维持当前状态，主要风险如下：

- 用户长期积累的数据可能因为清缓存、换设备、浏览器异常而丢失
- 数据无法跨设备恢复，削弱长期留存
- 无法建立正式用户系统，导致后续产品化能力受阻
- 运营动作只能依赖改代码或人工维护，效率低且不可审计
- 后续若直接在现有本地架构上继续叠功能，会增加迁移复杂度和返工成本

## 三、目标状态（Where we want to go）

### 3.1 数据安全目标

本轮建设完成后，应达到以下状态：

- 用户核心数据以云端为权威主源，不再依赖 `localStorage` 作为唯一正式存储
- 用户数据可绑定账号，可恢复、可迁移、可校验
- 关键数据具备备份、审计和基础安全边界
- 历史本地数据可平滑迁移，避免老用户资产流失

### 3.2 用户系统目标

本轮建设后的用户系统至少应支持：

- 用户注册/登录
- 用户身份与文章、收藏、阅读进度绑定
- 多设备访问同一账号时的数据一致性
- 基本会话管理与退出机制
- 为后续会员体系、复习记录、行为数据积累预留基础

### 3.3 运营后台目标

本轮建设后的后台能力至少应支持：

- 推荐内容的管理与上下架
- 用户基础信息与状态查看
- 基础运营动作的权限控制
- 关键后台操作的审计留痕
- 最小范围的运营概况查看，如推荐内容概况、用户活跃概况、首次迁移完成概况和基础异常提示

### 3.4 构建期完成标志

从本轮后端建设角度，构建期阶段性完成可用以下标准判断：

- 用户可以通过账号持有自己的核心数据
- 用户数据从本地存储迁移到云端主存储
- 阅读、收藏、进度等核心路径在账号体系下可正常运行
- 管理员可以通过后台执行最小运营动作
- 系统具备基础备份、权限控制和可追踪能力
- 后续功能开发不再建立在 `localStorage` 唯一正式存储之上

## 四、本轮建设范围

### 4.1 本轮确认要做

本轮明确纳入范围的建设内容：

- 正式后端数据底座建设
- 用户系统接入
- 核心业务数据云端化
- 本地数据迁移方案与实现
- 基础同步机制
- 最小可运营后台
- 基础权限、审计、备份与运行安全能力

对应到系统层面，重点覆盖：

- `articles`
- `bookmarks`
- `reading_marks`
- 用户身份与角色
- 推荐内容管理
- 管理后台核心操作

### 4.2 本轮明确不做

本轮明确暂不纳入范围的内容：

- 自建重型后端服务
- 复杂离线双向同步引擎
- 完整 BI / 数据中台能力
- 成熟会员计费体系
- 复杂推荐系统
- 大规模对象存储体系（若未出现明确图片/附件业务压力）
- 过度提前的微服务化拆分

本轮原则是：

> **优先补齐稳定运行所必须的基础设施，而不是提前建设规模化系统。**

### 4.3 依赖前提

本轮建设默认依赖以下前提成立：

- 已接受当前后端路线决策：`Netlify + Supabase`
- 前端现有核心阅读路径保持不推翻
- 现有本地数据结构可作为迁移输入来源
- 文档、设计、实现之间遵循“先设计后编码”的顺序
- 后续数据库、权限、迁移、同步文档会作为本文件的下游补充

## 五、关键约束

本轮工作必须遵守以下约束：

1. **不再新增以 `localStorage` 为唯一正式存储的数据能力**
2. **所有长期用户资产必须可与账号绑定**
3. **云端必须成为权威数据源，本地仅作为缓存、迁移通道或降级手段**
4. **不因建设后端而推翻已被验证的核心用户路径**
5. **后台建设以最小可运营为目标，不做超前复杂化设计**
6. **若后续出现重大方向变化，必须先补充决策记录，再调整专题设计**

这些约束的作用是：确保本轮建设服务于“构建期稳定运行”，而不是偏向新的探索性路线。

## 六、阶段性成功标准

本文件层面的阶段性成功，不是代码上线，而是以下认知达成一致：

- 对当前阶段与核心问题的判断一致
- 对本轮建设目标状态的理解一致
- 对本轮建设范围与非范围的边界一致
- 对后续文档应如何展开具备共同基础

若以落地视角进一步细化，本轮后端建设成功至少应表现为：

- 关键用户数据具备账号化与云端持久化能力
- 老用户数据可安全迁移
- 用户系统与后台系统都具备最小可用版本
- 实现工作可以基于文档推进，而不是边做边猜

## 七、已收敛前提与后续观察项

随着后续专题文档完成，本轮已有若干关键前提完成收敛：

- 首期登录入口采用 `Supabase Auth` 的邮箱验证码或 magic link 低摩擦方案
- 后台与主前端同仓组织，并优先复用同一前端工程和部署外壳
- `featured_articles` 在第一阶段即作为正式数据结构入库
- 首期采用 `auth.users + profiles` 组成正式产品身份

当前仍可继续观察、但不阻碍本轮文档成立的问题主要是：

- 图片/附件类存储是否已经达到需要单独引入对象存储的程度

该问题不会阻止当前后端建设成立，但若后续出现明确图片、附件或更大对象存储压力，应补充相应决策记录与专题方案。
