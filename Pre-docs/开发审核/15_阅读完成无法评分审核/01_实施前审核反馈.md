## 四、方案合理性与有效性审核

### 4.1 改动 A（推荐区内容读完不立即 `onBack`）— 方向正确，根因级命中

- **数据层 / 导航层分离干净**：`returnToShelf(articleId, { completed: true, ... })`（[ReaderPage.jsx:581](src/components/ReaderPage.jsx#L581)）**保留无条件执行**——文章的 `reading_status → completed` 照常落库，D2「读完自动放回书架」的**数据语义未变**；仅「导航返回」`onBack()` 变为条件调用。这一分离是方案的正确核心，避免了「为展示评分而牺牲还书」或「为还书而踢出页面」的两难 ✅；
- **停留后 `useEffect` 天然补上 `recSubmissionId`**：`setReadingMark(mark)` 后 `readingMark.completed` 变化触发 [ReaderPage.jsx:218-228](src/components/ReaderPage.jsx#L218-L228) 重跑，设置 `recSubmissionId` → 评分组件出现，无需手动前置设置或改动评分组件渲染逻辑 ✅；
- **依赖数组补 `article.origin` 正确**：`article` 为 prop，阅读会话期间由 `handleOpen` 一次注入、稳定，补入依赖无副作用 ✅；
- **非推荐区内容行为完全不变**：`fromRecommendation` 为 false 时走原 `onBack()`，回归风险归零 ✅；
- **新增样式合规**：`--surface-bg`/`--surface-border`/`--ink-muted`/`--gold-dark` 均为 `src/index.css` 既有变量（[index.css:20-21](src/index.css#L20-L21)、[:100](src/index.css#L100)、[:14](src/index.css#L14)），无硬编码颜色，符合项目颜色规范 ✅。

### 4.2 改动 B（「已读完」态补「返回书架」按钮）— 合理但需说明定位

- **功能上与头部返回按钮重复**：阅读页头部 `ReaderHeader` 已有 `onBack` 返回按钮（[ReaderHeader.jsx:23-34](src/components/ReaderHeader.jsx#L23-L34)，`ArrowLeft`），二者最终都调 `onBack` → `setArticle(null)`。新增按钮属「已读完」态**就地便捷出口**（该态位于正文末尾，且头部按钮在 `headerVisible` 为 false 时隐藏），非唯一出口。定位合理，但方案未点明这层关系，建议补一句（见 P3）；
- **语义正确**：`onClick={onBack}` 直接导航即可——「已读完」态下 `returnToShelf(completed: true)` 已在 `handleMarkCompleted` 内完成（含「再次打开已完成文章」场景，文章状态本就为 completed），无需再调 `returnToShelf` ✅；
- **对所有「已读完」态可见（含再次打开）** 语义一致 ✅。

### 4.3 选型理由与备选方案

- 方案 A 优于备选 B（统一停留）：精确命中「推荐区」而非一刀切改所有内容 UX ✅；
- 优于备选 C（书架卡片评分）：改动面小、贴合用户主诉「阅读完成时评分」✅；

## 六、问题清单（按严重程度排序）

### P1（中，建议补正）— 停留条件与评分组件渲染条件未对齐

**现象**：改动 A 的停留条件 `fromRecommendation` 只判断 `article.origin`（③），而评分组件实际渲染需要 `recSubmissionId` 非空，即 ③ + ④（`shareSourceId` 非空）**同时成立**。

**源码事实**：[ReaderPage.jsx:220-222](src/components/ReaderPage.jsx#L220-L222) 中 `setRecSubmissionId(article.shareSourceId)` 被 `if (article.origin === ...) { if (article.shareSourceId) { ... } }` 嵌套包裹，`shareSourceId` 为空时 `recSubmissionId` 保持 null，评分组件不渲染（[ReaderPage.jsx:957](src/components/ReaderPage.jsx#L957)）。

**影响**：当 `origin ∈ {featured, featured_legacy}` 但 `share_source_id` 为 null（云端数据残缺 / 迁移残留，即分析自己标记的兜底风险同类场景）时，修复后行为从「读完即返回」变成「读完停留但无评分组件」，是**无收益的行为变更**——用户停在页面却看不到评分，反而多一次手动返回。

**修复建议**：将停留条件与渲染条件精确对齐：

```js
const fromRecommendation =
  (article.origin === 'featured' || article.origin === 'featured_legacy') &&
  article.shareSourceId
```

成本为零，且使「停留」这一动作与「评分组件将出现」严格同真同假，杜绝边界态。

### P2（低，措辞）— 验证清单 §3.1 第 3 步「add_count / recommend_score 已随评分更新」不准确

**现象**：修复方案 §3.1 第 3 步断言「该条 `add_count` / `recommend_score` 已随评分更新」。

**事实**：`add_count` 由「加入书架」动作驱动（`addRecommendationToBookshelf`），与评分无因果关系；评分只通过触发器更新 `recommend_score`（缓存字段）与评分分布（设计文档 §5.3、:738）。故评分后 `add_count` 不变化。

**修复建议**：改为「该条 `recommend_score` / 评分分布已随评分更新（`add_count` 不随评分变化，仅随加入书架变化）」。不影响实施。

### P3（低，说明）— 「返回书架」按钮与头部返回按钮的关系未写明

**现象**：阅读页头部 `ReaderHeader` 已有返回按钮（[ReaderHeader.jsx:23-34](src/components/ReaderHeader.jsx#L23-L34)），方案未说明新增「返回书架」按钮与其的定位差异。

**事实**：二者最终都调 `onBack`，功能等价；差异仅在位置（正文末尾 vs 头部）与可见性（头部按钮 `headerVisible` 为 false 时隐藏）。新增按钮是「已读完」态的**就地便捷出口**。

**修复建议**：在方案 2.2 说明中补一句「该按钮为『已读完』态的就地便捷出口，与头部返回按钮功能等价，非新增唯一返回路径」，避免后续被误读为「必须经此返回」。

### P4（低，潜在边界）— 匿名用户看到评分按钮但点击无效

**现象**：[ReaderPage.jsx:222](src/components/ReaderPage.jsx#L222) `setRecSubmissionId(article.shareSourceId)` 位于 `if (userId)` 之外；而 `handleRecRate`（[ReaderPage.jsx:230-241](src/components/ReaderPage.jsx#L230-L241)）首行 `if (!recSubmissionId || !userId) return` 静默短路。

**事实**：若匿名用户持有 `featured` 来源 + `shareSourceId` 的内容，停留后会看到评分按钮，点击无任何反应（无提示、无高亮）。

**评估**：实际可达性极低——推荐内容仅在云端配置 + 登录态下加载（[ImportPage.jsx:312-324](src/components/ImportPage.jsx#L312-L324) 依赖 `isSupabaseConfigured` 与认证），匿名用户几乎不可能持有 featured 内容。故列为**潜在边界**而非阻塞项。

**修复建议（可选）**：在评分组件渲染条件外补 `userId &&`（`{recSubmissionId && userId && (...)}`），或在 `handleRecRate` 对 `!userId` 分支给出可见提示。属本次修复外延，可作后续独立项。

### P5（可选，范围提示）— 设计文档「改评分需确认」未在本次体现

设计文档 `03_实施方案.md` §4.5（:576-578）要求「已评分 → 改评分时确认『将评分从「推荐」改为「一般」？』」，当前 `handleRecRate` 直接提交、无确认。此属评分交互细节，**超出本次「让评分组件可见」的范围**（方案已声明不触碰评分服务层），仅提示可作为后续独立项，不影响本次实施。
