## 二、逐条处理

### 2.1 P1 — 停留条件与评分组件渲染条件未对齐（已修正）

| 项目 | 内容 |
|------|------|
| **审核指出** | 改动 A 的 `fromRecommendation` 只判断 `article.origin`（③），而评分组件实际渲染需 ③ + ④（`shareSourceId` 非空）同时成立。当 `origin` 命中但 `share_source_id` 为 null 时，修复后从「读完即返回」变成「读完停留但无评分」，是无收益的行为变更 |
| **验证** | 源码 [ReaderPage.jsx:220-222](src/components/ReaderPage.jsx#L220-L222) 中 `setRecSubmissionId(article.shareSourceId)` 被 `if (origin) { if (shareSourceId) {...} }` 嵌套包裹，`shareSourceId` 为空时 `recSubmissionId` 保持 null，组件不渲染。判定成立 |
| **修正** | `01_修复方案.md` §2.1：`fromRecommendation` 改为 `(origin === 'featured' \|\| origin === 'featured_legacy') && article.shareSourceId`；依赖数组补 `article.shareSourceId`；注释补「与评分组件渲染条件严格对齐」 |
| **核心结论** | 不变——根因修复方向正确，仅补一处条件对齐，成本为零，使「停留」与「评分组件将出现」严格同真同假 |

### 2.2 P2 — 验证清单 add_count 表述不准确（已修正）

| 项目 | 内容 |
|------|------|
| **审核指出** | §3.1 第 3 步断言「该条 `add_count` / `recommend_score` 已随评分更新」，但 `add_count` 由「加入书架」驱动，与评分无因果关系 |
| **验证** | `add_count` 由 `addRecommendationToBookshelf` 驱动，评分只经触发器更新 `recommend_score`（缓存字段）与评分分布。判定成立 |
| **修正** | `01_修复方案.md` §3.1 第 3 步改为「该条 `recommend_score` / 评分分布已随评分更新（列表按 score 重排）；`add_count` 不随评分变化，仅随加入书架变化」；并追加验证项 6 对应验证 |

### 2.3 P3 — 返回书架按钮与头部返回按钮关系未写明（已补充）

| 项目 | 内容 |
|------|------|
| **审核指出** | 阅读页头部 `ReaderHeader` 已有 `onBack` 返回按钮，方案未说明新增「返回书架」按钮与其定位差异 |
| **验证** | 二者最终都调 `onBack` → `setArticle(null)`，功能等价；差异仅在位置（正文末尾 vs 头部）与可见性（头部按钮 `headerVisible=false` 时隐藏）。判定成立 |
| **修正** | `01_修复方案.md` §2.2 说明补一句：「该按钮与阅读页头部 `ReaderHeader` 的返回按钮（同样调 `onBack`）功能等价，属『已读完』态的就地便捷出口——头部按钮在 `headerVisible=false` 时隐藏，正文末尾的返回按钮保证停留态仍有可见出口，并非新增唯一返回路径」 |

### 2.4 P4 — 匿名用户评分边界（列为后续独立项）

| 项目 | 内容 |
|------|------|
| **审核指出** | `setRecSubmissionId` 位于 `if (userId)` 之外，匿名用户理论上会看到评分按钮但点击静默无效 |
| **评估** | 认可审核对可达性的判断——推荐内容仅在云端配置 + 登录态下加载，匿名用户几乎不可能持有 featured 内容。属潜在边界而非阻塞项 |
| **处理** | **本次不实施**，列为后续独立项：在评分组件渲染条件补 `userId &&`（`{recSubmissionId && userId && (...)}`），或在 `handleRecRate` 对 `!userId` 分支给出可见提示。待后续专项评估 |

### 2.5 P5 — 改评分确认交互（列为后续独立项）

| 项目 | 内容 |
|------|------|
| **审核指出** | 设计文档 §4.5 要求「已评分 → 改评分时确认『将评分从「推荐」改为「一般」？』」，当前 `handleRecRate` 直接提交、无确认 |
| **评估** | 认可——此属评分交互细节，超出本次「让评分组件可见」的范围（方案已声明不触碰评分服务层） |
| **处理** | **本次不实施**，列为后续独立项：为 `handleRecRate` 增加「改评分确认」交互，符合设计文档 §4.5。待后续专项评估 |
