## 八、问题清单（按严重程度排序）

### P1（低-中，建议补正）— 「每一次收藏都会触发全量重挂载」缺云端/本地环境限定

**现象**：报告根因第 2 环断言「`loadReaderState` 每次都产生新引用的 `readingMark` 对象（内容相同也是新对象）」。

**源码事实**：该断言仅对**云端路径**成立（[readings.js:153-168](src/services/readings.js#L153-L168) `mapReadingMarkRow` 每次新建对象）。**本地路径**下 `readingMarkStore.get` 返回 `_marksCache[articleId]` 缓存共享引用（[storage.js:128-131](src/store/storage.js#L128-L131)、[:209-211](src/store/storage.js#L209-L211)），内容不变时引用稳定 → `setReadingMark` 同引用 → React  bailout → **本地模式预测不触发重挂载、不发作**。

**影响**：
1. 结论普适性措辞需加限定（探针会话运行在 `localhost:7100` 且观察到了 12 次爆发，可推断当时为云端模式，但报告未写明这一前提）；
2. 该差异同时是一个**零成本反向验证**：若本地模式确实不发作，根因再获一重独立印证；若本地模式也发作，则说明存在第二条触发路径，需回头修订；
3. 对 F1 选项 2 的影响：内容比较主要服务云端路径（本地路径天然免疫），不影响方案成立。

**修复建议**：在报告根因第 2 环补注「云端路径每次新对象；本地路径返回缓存共享引用、内容不变时引用稳定，故本机制预测本地模式不发作」，并将「本地模式对照验证」列入修复后验证清单。

### P2（低-中，建议写明）— F1 选项 1 的关键实施约束：readingMark 必须继续作为 prop 保留

**现象**：F1 选项 1 提出「闭包引用改为 `readingMarkRef`，useMemo 依赖收窄为 `[sectionId]`」，但未写明 `readingMark` prop 的去留。

**分析**：`components` 依赖收窄后，`p` 渲染器内 `isMarked` 的重算依赖 `MarkdownContent` 自身重渲染；而 `MarkdownContent` 是 memo 组件，**重渲染的唯一触发源是 prop 变化**。若实施时把 `readingMark` 从 props 中删掉（「既然用 ref 了」），则阅读标记更新时组件不重渲染、标记视觉静默失更——功能回归且极难察觉。正确做法：`readingMark` 继续作为 prop 传入（仅用于触发重渲染），渲染器内改读 `readingMarkRef.current`。

**修复建议**：在 F1 选项 1 中补一句「`readingMark` 保留为 prop 以触发重渲染，仅将渲染器内的读取改为 ref」；或直接采用选项 2（内容比较）规避此风险。**两个选项均有效，审核不指定选型**——选项 1 更彻底、选项 2 更稳妥。

### P3（低，实施时覆盖）— F2 队列的 3 处边缘条件未展开

1. **flush 兜底**：若 mouseup 在内容区外释放（拖出窗口松手）或窗口 blur，「选区活跃」标志可能长期不清除、队列不落地——需增加 blur / 全局 mouseup / 超时兜底；
2. **两波排队去重**：wave1 与 wave2 可能都落入同一拖选窗口，flush 时应只应用最新一次结果（或 flush 时重新 `loadReaderState` 一次），避免旧值覆盖新值；
3. **预读模式时序**：预读 mouseup 处理函数自身会 `removeAllRanges` 并同步进入收藏管线（[ReaderPage.jsx:256-282](src/components/ReaderPage.jsx#L256-L282)），「标志解除」与「本次收藏的状态落地」的先后顺序需明确，避免本次收藏的状态被自己刚设的标志错误排队。

**修复建议**：实施时在 F2 设计稿中补上述三条；亦可考虑等价简化——「拖选活跃时仅置 dirty 标志、跳过落地，mouseup/折叠后统一 `loadReaderState` 一次」，天然规避去重与时序问题。
