## 五、分析完备性审核

### 5.1 根因分析 — 完备且准确

1. ✅ 「去重只存在于 UI 层、且只覆盖一条路径」——`isPopupBookmarked` 仅用于非预读弹窗按钮；预读分支直接 `createBookmark`+`saveBookmark`；数据层 `bookmarkStore.save`/`saveBookmark` 均按 `id` upsert、无位置查重。与源码完全一致。
2. ✅ 「去重谓词漏了 `charOffset`，是『按文本去重』」——`isPopupBookmarked` 谓词仅 `text + paragraphIndex + sectionId`，确无 `charOffset`。
3. ✅ 「同一词形不同位置是不同学习对象」的业务认知与复习语义自洽（词/句各自成复习项）。

### 5.2 方案演进与放弃项 — 完备

起点（补 `charOffset`）→ 分析（按文本去重本身错）→ 最终决策（按位置去重 + 收敛两路径）的演进链完整；放弃项（完全不去重 / 仅补 `charOffset` / 数据层唯一约束）的放弃理由自洽（污染复习队列 / 治标不治本 / 迁移成本高）。

### 5.3 完备性缺口

- **缺口 1（对应 P1）**：D2 的理由「现有 `saveBookmark` / `bookmarkStore.save` 仅有两个调用点、都在 `ReaderPage`」**与源码不符**。详见 P1。
- **缺口 2（对应 P2）**：02 §七「边界与已知限制」只覆盖了「历史书签 `charOffset` 缺失」，未覆盖「历史云端书签 `paragraph_index` 为 null」的同类边缘。详见 P2。
- **缺口 3（对应 P3）**：D3 去掉「已收藏」提示后，重复点「收藏」将**静默关闭弹窗、无显式反馈**，该 UX 取舍未被显式点名。详见 P3。

### 6.2 方案有效性

## 七、问题清单（按严重程度排序）

### P1（中等，建议修订）— D2 理由「`saveBookmark` / `bookmarkStore.save` 仅有两个调用点、都在 `ReaderPage`」与源码不符

**现象**：01 D2 理由原文：「现有 `saveBookmark` / `bookmarkStore.save` 仅有两个调用点、都在 `ReaderPage`，在保存前判定即可覆盖全部路径」。

**源码事实**（`grep` 全库核实）：

- `saveBookmark` 实有 **5 个调用点**：
  1. [ReaderPage.jsx:249](src/components/ReaderPage.jsx#L249)（预读新建，**新建型**）
  2. [ReaderPage.jsx:303](src/components/ReaderPage.jsx#L303)（`handleBookmark` 新建，**新建型**）
  3. [ReviewPanel.jsx:76](src/components/ReviewPanel.jsx#L76)（复习回写：`saveBookmark({ ...bookmark, ...updated })`，**更新型**）
  4. [useBookmarkAI.js:73](src/hooks/useBookmarkAI.js#L73)（翻译回写：`saveBookmark(updated, ...)`，**更新型**）
  5. [readings.js:971](src/services/readings.js#L971)（导入迁移：`saveBookmark(bookmark, options)`，**导入型**）
- `bookmarkStore.save` 实有 **1 个调用点**：[readings.js:785](src/services/readings.js#L785)（位于 `saveBookmark` 内部），并非「两个、都在 ReaderPage」。

**影响**：决策**结论仍成立**——因为 3/4/5 三处均为「更新/导入型」，携带已有 `id`、经 `onConflict:'id'` upsert，不会生成新 `id`、不产生新重复，故「去重只放 `ReaderPage` 即可覆盖全部**新建**入口」依然正确。但**前提陈述错误**，会误导后续维护者误判 `saveBookmark` 的改动波及面（例如误以为可放心在 `saveBookmark` 内加位置去重而不影响复习/翻译回写）。

**修复建议**：将 D2 理由更正为「**新建收藏的入口仅 `ReaderPage` 两处**；`saveBookmark` 另有 `ReviewPanel`（复习回写）、`useBookmarkAI`（翻译回写）、`readings.js` 导入迁移三处**更新/回写型**调用，均带已有 `id` 且不产生新 `id`，故去重只需落在 `ReaderPage` 的保存入口即可覆盖全部**新建**路径，无需改数据层、无迁移风险」。

### P2（低，建议补充）— 边界说明未覆盖「历史云端书签 `paragraph_index` 为 null」的同类边缘

**现象**：02 §七「边界与已知限制」只写了「历史书签 `charOffset` 缺失」，未提 `paragraph_index` 缺失。

**源码事实**：`isSameBookmarkLocation` 仅对 `sectionId`/`charOffset` 做 `?? null` 归一化，`text`/`paragraphIndex` 用严格相等。云端历史书签的 `paragraph_index` 允许为 null（`saveBookmark` 云路径写 `paragraph_index: bookmark.paragraphIndex ?? null`；`mapBookmarkRow` 原样映射 `paragraphIndex: row.paragraph_index`）。

**影响**：`null === 数值` 为 `false` → **仅可能漏判一条重复（不误伤）**，与已记录的 `charOffset` 缺失边界同性质——非破坏性、可手动删除。因方向安全，不影响结论，仅建议补一句以避免后续读者只知 `charOffset` 一种缺失态。

**修复建议**：在 02 §七 边界中补一句：「同理，历史书签若 `paragraph_index` 为 null，与任意新选区的 `paragraphIndex` 恒不等 → 仅可能漏判（不误伤），与 `charOffset` 缺失同属非破坏性边缘」。

---

### P3（低，确认项）— 去掉「已收藏」提示后，重复点「收藏」静默关闭、无显式反馈

**现象**：D3 移除「已收藏」禁用态后，收藏按钮恒为「收藏」、恒可点；此时若用户对**已收藏的同一位置**再点「收藏」，流程为「判定已存在 → `closePopup()` → 不保存」，弹窗静默关闭，**无任何视觉/文案反馈**（无 toast、无「已收藏」字样）。

**分析**：这并非缺陷——它是 D3「是否已收藏靠正文高亮 + 收藏列表判断」的直接推论，且 D4 的连点防护本就要求「点了就关」。但「正文高亮」依赖 `buildLayers` 的 `charOffset` 定位成功渲染；若个别边界（如 `paragraphIndex === -1` 的标题/表格单元格选区）高亮未渲染，则用户点「收藏」后既无高亮又无提示，观感上像「点了没反应」。

**建议**：不改方案的前提下，在 02 §四「预期效果」或 §五「验证清单」中**显式记录**该 UX 取舍（「重复收藏 = 静默关闭、不弹提示，已收藏状态由正文高亮 + 收藏列表承载」），便于后续测试与产品确认预期一致；若后续反馈认为需要轻提示，再作为独立迭代项。
