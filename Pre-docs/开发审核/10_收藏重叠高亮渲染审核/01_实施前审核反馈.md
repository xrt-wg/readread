- **`renderBgs` 基本正确**：逐条推演了「区间在前 / 在后 / 跨边界 / 相邻」四种情形，裁剪与游标推进均正确（前提是 `bgRanges` 已按 `start` 升序且无重叠，`resolveRanges` 恰好保证这一点）。

### 6.2 方案有效性

- **双层嵌套渲染**：`ulRanges` 为外层连续 span（不在词处切开，保证下划线连续），内部递归渲染相交的 `bgRanges`——先藏词后藏句、先藏句后藏词两种顺序均同时可见。机制成立。✅
- **hover 委托化**：`mouseover`/`mouseout` 委托 + `closest('[data-bookmark-id]')` 取最内层，天然满足 D3；`relatedTarget` 判断避免「词 → 句非词部分」时卡被误清空。逐 span → 委托的切换理由（嵌套下 `onMouseLeave` 清空后外层 `onMouseEnter` 不重触发）成立。✅
- **`charOffset` DOM Range 定位**：TreeWalker 累加文本节点长度求段落内偏移，方向正确；「前导空白修正」逻辑正确（`charOffset` 指向 `trim()` 后文本起点）。已核对 `anchorEl.textContent === rawText`（三个挂载点均只渲染 ParagraphRenderer，无其它文本子节点），偏移与 `ParagraphRenderer` 的 `paraText` 基准一致。✅

## 七、问题清单（按严重程度排序）

### P1（中等，建议修复）— 删除 `getCharOffset` 时遗漏 `ReaderPage.jsx:24` 的 import 同步移除

**现象**：02 计划删除 `textUtils.js` 的 `getCharOffset`（§2.3、§六），但只提及替换第 214 行的**使用处**，未提及第 24 行的 **import**。

**根因**：`getCharOffset` 在 `ReaderPage.jsx` 有两处出现——[ReaderPage.jsx:24](src/components/ReaderPage.jsx#L24)（`import { ... getCharOffset } from '../utils/textUtils'`）与 [ReaderPage.jsx:214](src/components/ReaderPage.jsx#L214)（使用）。若只替换 214 行、删除 textUtils 导出而不改 import，将产生「从已删除导出处引入命名导出」的构建错误（Vite/Rollup 报 `getCharOffset is not exported by ...`）。

**修复建议**：在 02 §六 与 §2.3 中显式补充——`ReaderPage.jsx` 第 24 行 import 移除 `getCharOffset`（与替换 214 行、删除 textUtils 导出三处联动）。

### P2（中等，建议修复）— `renderBgs` 在「短语完全包住已收藏句子 / 跨两个相邻已收藏句子」时产生重复 React key

**现象**：02 §2.1 的 `renderBgs` 用 `key={`bg-${r.bookmark.id}`}` 作为背景 span 的 key。当一条 phrase（bg）跨过一条**完全被它包住**的 sentence（ul）收藏，或跨过**两条相邻**的 sentence 收藏时，该 phrase 会在外层容器里被裁成**两段 gap 片段**，二者同为外层 `<span>` 的直接子节点，key 相同 → React 重复 key 警告 + 潜在的重渲染错位。

**根因**：02 §2.1 只考虑了「短语跨**单**句边界 → 句中一段 + 间隙一段（不同父节点，key 不冲突）」。但一般情形下，同一 bgRange 可能被裁成「间隙 A + 句中 + 间隙 B」多段，其中「间隙 A」「间隙 B」都落在外层容器的**同一父节点**下。`data-bookmark-id` 复用同一 id 是正确且必要的（hover/删除都靠它），但 React **key** 必须在同一父节点内唯一。

**触发路径**（罕见）：选中文本含句内标点（如「the cat. The dog」，≤6 词、非句末标点 → 判为 `phrase`）且横跨一个已收藏句子的完整区间。低频，但一旦命中会产生控制台报错。

**修复建议**：key 追加裁剪区段去重（`data-bookmark-id` 保持不变）：

```js
nodes.push(
  <span key={`bg-${r.bookmark.id}-${s}-${e}`} data-bookmark-id={r.bookmark.id} style={bgStyle(r.bookmark)}>
    {text.slice(s, e)}
  </span>
)
```

并在 02 §2.1「渲染规则」的「短语跨句边界」说明里，把「裁成两段」扩展为「可裁成多段，key 需按区段去重」。

### P4（低，预存）— `ulStyle` 沿用的硬编码 indigo 与双下划线

现有下划线样式 [ParagraphRenderer.jsx:88-93](src/components/ParagraphRenderer.jsx#L88-L93) 同时设置了 `borderBottom: 2px solid var(--hl-sentence-border)` 与 `textDecoration: underline` + `textDecorationColor: 'rgba(99,102,241,0.5)'`（硬编码 indigo），既形成双下划线、又违反 CLAUDE.md「颜色必须经 CSS 变量引用」（indigo 不在允许的硬编码例外清单）。本次重构 `ulStyle` 会原样沿用。建议顺手收敛为单一 `border-bottom`（变量），或至少作为已知项在方案中记录。**非阻塞**（预存，非本次引入）。

### P5（低）— `getSelectionStartOffset` 兜底返回「段尾偏移」语义不佳

02 §2.3 的 helper 在 `range.startContainer` 非文本节点（罕见：键盘选区 / 元素边界选区）时返回累加后的 `offset`（即段落**末尾**偏移），语义上更接近「定位失败」。虽然后续 `buildLayers` 的 `slice === text` 校验会把这种书签过滤掉（不渲染、仅存一条错偏移数据，与现状 `indexOf` 返回 0 相当），但建议兜底值改为 `0` 或显式 `return -1` 并交由调用方跳过，避免误导后续维护者。

### P6（低）— D1 措辞「改动集中在 ParagraphRenderer」略窄

01 D1 理由称「改动集中在 `ParagraphRenderer`」，但本次实际触及 3 个文件（`ParagraphRenderer`、`ReaderPage`、`textUtils`）。建议措辞收敛为「**渲染**改动集中在 `ParagraphRenderer`；另含 `ReaderPage` 的定位修正与 `textUtils` 的死代码清理」，避免「单文件改动」的误读。
