## 三、Phase 0：类型定义与数据层升级

### 阶段目标

在不改变任何现有功能行为的前提下，建立 Document 类型体系并完成数据库 schema 扩展和 localStorage 数据回填。

### 本阶段核心任务

#### 任务 0.1：JSDoc 类型定义文件

- 在 `src/types/` 下创建类型定义文件：
  - `document.js` — Document、Section 类型
  - `bookmark.js` — Bookmark、ReadingProgress 类型
  - `extractor.js` — ExtractionResult、ExtractionSection、ExtractorInput 类型
- 使用 JSDoc `@typedef` 语法，项目保持纯 JavaScript
- 导出类型供全项目 IDE 类型提示使用

#### 任务 0.2：向后兼容映射工具

- 实现 `migrateArticleToDocument(article): Document`
- 在 `library.js` 的 `mapArticleRow` 中调用，返回的对象同时兼容旧结构和新结构
- 过渡期策略：返回旧字段（text、markdown）+ 新字段（sections、format）

```js
function mapArticleRow(row) {
  return {
    // 旧字段（保持现有调用方不报错）
    id: row.id,
    title: row.title,
    text: row.text,
    markdown: row.markdown,
    wordCount: row.word_count,
    // 新字段
    author: row.author,
    format: row.format,
    coverUrl: row.cover_url,
    lang: row.lang,
    sourceUrl: row.source_url,
    sections: row.sections,
    sectionCount: row.section_count,
    // ...
  }
}
```

#### 任务 0.3：数据库迁移脚本

- 新增 Supabase migration 文件：
  - `ALTER TABLE articles ADD COLUMN author, format, cover_url, lang, sections, section_count`
  - `ALTER TABLE bookmarks ADD COLUMN section_id, section_heading`
  - `ALTER TABLE reading_marks ADD COLUMN section_id, completed_sections`
- 对现有数据执行回填（一次性 SQL）
- 添加 CHECK 约束

#### 任务 0.4：store/storage.js 适配

- `createArticle` 升级为 `createDocument`：
  - 使用 `doc_` 前缀
  - 构建单 section（id: "s_main"）
- 保留旧 `createArticle` 作为 `@deprecated` 别名（内部调用 `createDocument`）
- `createBookmark` 增加 `sectionId` 和 `sectionHeading` 字段

#### 任务 0.5：localStorage 数据回填与兼容（新增）

- 在应用启动时执行 `migrateLocalStorageArticles()`
  - 检测 `localStorage` 中的旧格式 articles
  - 缺少 `sections` 字段者自动调用 `migrateArticleToDocument()` 升级
- `readingMarkStore` 兼容：保持 `articleId` 为 key，内部结构增加 `sectionId` 和 `completedSections`
- `bookmarkStore` 兼容：旧 bookmark 的 `sectionId`/`sectionHeading` 为 null 时正常读写

#### 任务 0.6：导出格式 v1 → v2 升级（新增）

- `exportData()` 的 `version` 字段升级为 `2`
- `importData()` 增加版本检测：
  - `version: 1` → 每个 article 经 `migrateArticleToDocument()` 升级后写入
  - `version: 2` → 直接写入
- 导出/导入支持 sections、format、author 等新字段

#### 任务 0.7：ExtractorInput buffer 类型 + format 枚举（新增）

- 定义 `ExtractorInput` 类型（含 `buffer` 变体）
- `DocumentFormat` 类型联合中保留 `'pdf'`
- `EXTRACTORS` 注册表中 `pdf` 键位值为 `null`
- 前端文件上传路径：`file.arrayBuffer()` → `{ type: 'buffer', ... }`

### 本阶段不要求完成的事情

- 任何 UI 改动
- 提取器接口的实际切换
- 多 section 的渲染支持

### 完成标志

- [ ] JSDoc 类型定义文件已创建且全项目可引用
- [ ] 数据库迁移脚本已执行，新增字段已存在
- [ ] 旧数据回填完成（所有现有行 sections 不为空）
- [ ] `createDocument` 函数可用，`createArticle` 保留为 deprecated 别名
- [ ] `library.js` 的读写路径对新旧字段兼容
- [ ] **localStorage 旧数据回填验证通过**（应用启动后，旧 localStorage 数据可正常加载和阅读）
- [ ] **导出格式 v2 可正常导入 v1 旧格式备份**
- [ ] 现有功能（导入、阅读、收藏、回顾）未受影响

### 风险点

| 风险 | 应对 |
|------|------|
| 回填数据量过大导致迁移超时 | 分批 UPDATE，每批 100 行 |
| JSONB 构建格式错误 | 先在 staging 分支验证 SQL |
| 旧调用方仍引用 `.text` 等字段 | 过渡期保持旧字段映射 |
| localStorage 回填后旧浏览器不兼容 | 回填前备份原数据（不删除原始 key） |

### 回滚策略

- migration 文件支持 `DROP COLUMN IF EXISTS` 回滚
- `mapArticleRow` 中有条件分支，可通过 feature flag 切换
- localStorage 回填：写入前先备份旧数据（不覆盖），验证失败时恢复

## 四、Phase 1：提取器重构与 EPUB 支持

### 阶段目标

建立统一的提取器接口，将所有现有导入路径适配为新接口，并基于 epub2MD 新增 EPUB 提取器。

### 本阶段核心任务

#### 任务 1.1：提取器接口实现

- 在 `src/services/extractors/` 下建立提取器模块：
  ```
  src/services/extractors/
    ├── index.js            ← EXTRACTORS 注册表 + createDocument 工厂 + deriveParentIds
    ├── urlExtractor.js     ← 现有 fetchArticleFromUrl 适配
    ├── pasteExtractor.js   ← 现有粘贴/文件逻辑提取
    ├── markdownExtractor.js ← 现有 .md 处理 + ##/###/#### 标题扫描
    ├── htmlExtractor.js    ← 现有 .html 处理 + h1-h6 扫描
    └── epubExtractor.js    ← epub2MD 适配层
  ```
- 每个提取器返回 `ExtractionResult`，统一由 `createDocument()` 装配

#### 任务 1.2：现有提取器适配

- `urlExtractor.js`：复用 `fetchArticleFromUrl`，返回格式改为 `ExtractionResult`（单 section）
  - `sourceUrl` 传入 `meta` 和 ExtractionResult 上下文
- `pasteExtractor.js`：从 ImportPage 的 handleFile / handleSubmit 逻辑中抽取
- `markdownExtractor.js`：新增 `##` / `###` / `####` 扫描逻辑
- `htmlExtractor.js`：新增 h1-h6 扫描逻辑

#### 任务 1.3：ImportPage 重构

- 将 ImportPage 中的内联提取逻辑替换为调用提取器接口
- 三 Tab 的提交路径统一为：
  ```js
  const extractor = EXTRACTORS[format]
  if (!extractor) throw new Error(`${format} 支持即将推出`)
  const result = await extractor(input, signal)
  const document = createDocument(result)
  await saveArticle(document, options)
  await loadLibraryState()
  ```
- `.epub` 扩展名加入文件上传接受列表

#### 任务 1.4：epub2MD 适配器（替换原手写方案）

1. `npm install epub2md`
2. 创建 `src/services/extractors/epubExtractor.js`：
   - `epub2md.parseEpub(fileBuffer)` → Epub 对象
   - 遍历 `Toc.tree`（递归）→ 为每个 TocItem 分配 `depth` 和 `order`
   - 通过 `sectionId` 关联 TocItem 和 Section → 填充 `heading`
   - 调用 `section.toMarkdown()` → `body.markdown`
   - 从 `structure.opf.metadata` → `meta.title`、`meta.author`、`meta.language`
   - 封面图提取（任务 1.6）
   - 返回 `ExtractionResult { meta, sections }`
3. 在 `EXTRACTORS` 注册表中注册
4. EPUB 提取器依赖通过动态 import 按需加载

> **注意**：`ExtractionSection` 不设置 `parentId`。`parentId` 由 `createDocument` 中的 `deriveParentIds()` 推导。

#### 任务 1.5：ExtractionSection parentId 工厂函数推导（新增）

- 在 `createDocument` 中增加 `deriveParentIds(sections)` 函数
- 规则：向前找最近的 depth 更小的 section，为其 parent
- 与 `buildTocTree` 算法逻辑同源

#### 任务 1.6：EPUB 封面图提取（新增）

- 通过 OPF manifest 中 `<meta name="cover">` 定位封面图 item
- Canvas 缩放至 max 300px → `data:image/jpeg;base64,...`
- 存入 `meta.coverUrl`
- 内嵌图片（< 50KB）保留 epub2MD 的 base64 嵌入；大图位置插入 `[Image: alt_text]` 占位符

### 本阶段不要求完成的事情

- 多 section 的阅读页渲染
- PDF 提取器
- EPUB 内嵌图片的完整存储管理

### 完成标志

- [ ] 提取器接口 `EXTRACTORS` 注册表可用
- [ ] `url`、`paste`、`markdown`、`html` 四个提取器已适配
- [ ] `epub` 提取器可成功提取含 N 个章节的 EPUB
- [ ] ImportPage 的三 Tab 导入路径全部走提取器接口
- [ ] 现有功能（导入、阅读、收藏）行为无退化
- [ ] 提取的 EPUB Document 中 sections 数量正确、层级结构正确
- [ ] **EPUB 提取器在 5 本以上不同结构的 EPUB 上验证通过**：
  - 标准 EPUB3（小说）、EPUB2（旧格式）、无 toc 降级 EPUB、中文 EPUB、多级嵌套 toc EPUB
- [ ] **至少 3 个多 section EPUB 文档的完整导入→阅读链路端到端验证通过**
- [ ] 封面图 base64 提取并正确显示
- [ ] 损坏的 EPUB 给出明确错误提示

### 风险点

| 风险 | 应对 |
|------|------|
| epub2MD 版本更新导致 API 变化 | 锁定主版本，Phase 1 期间测试固定版本 |
| EPUB toc 结构不标准 | 三级容错：nav.xhtml → toc.ncx → spine 平铺 |
| 内嵌图片过多导致 JSONB 过大 | 大图用占位符 + 标注 alt text |
| 动态 import 兼容性 | 确保 Vite 正确处理动态 import |

### 回滚策略

- 提取器注册表使用策略模式，单个提取器出问题只回退该提取器
- EPUB 提取失败时给出明确错误提示，引导用户转换为 Markdown 格式

## 五、Phase 2：渲染层适配

### 阶段目标

让 ReaderPage 支持多 section 文档的阅读，包括 section 切换、TOC 导航和段落索引的正确映射。单 section 文档行为完全不变。

### 本阶段核心任务

#### 任务 2.0：旧 bookmark paragraphIndex 兼容处理（新增）

- 对 `sectionCount === 1` 的文档，bookmark.paragraphIndex 保持原值不变
- 对 `sectionCount > 1` 的新文档，bookmark.paragraphIndex 是 section 内局部索引
- 渲染时通过 `data-para-index` 分配的值与存入 bookmark 的值一致

#### 任务 2.1：ReaderPage 的 section 上下文

- 新增状态：`currentSectionIdx`
- 从 `document.sections[currentSectionIdx]` 读取当前 section 的 body
- 渲染逻辑复用当前 MarkdownContent（单 section body 渲染）
- paragraphIndex 在 section 内部从 0 开始分配
- 切换 section 时：`key={section.id}` 强制重挂载 + scrollTo(0, 0)

#### 任务 2.2：TOC 侧栏

- 新增组件 `SectionTocPanel.jsx`
- 仅在 `document.sectionCount > 1` 时显示
- 使用 `buildTocTree(sections)` 生成 TOC 树结构
- 树节点按 depth 正确缩进
- 点击节点 → 切换 `currentSectionIdx`
- 当前 section 节点高亮

#### 任务 2.3：顶栏面包屑

- 顶栏标题区增加 section 信息（sectionCount > 1 时）：
  ```
  [返回]  文档标题  ·  Section 标题  ·  词数  ·  进度%
  ```
- 单 section 文档（sectionCount = 1 且 heading = null）：不显示 section 信息

#### 任务 2.4：收藏定位适配

- `handleMouseUp` 中，paragraphIndex 使用 section 内局部索引
- `anchorEl.dataset.paraIndex` 保持 section 内语义
- bookmark 创建时填充 `sectionId` 和 `sectionHeading`

#### 任务 2.5：阅读进度适配

- `handleSetReadingMark` 记录的 paragraphIndex 为 section 内局部索引
- 新增 `sectionId` 记录当前 section
- `handleJumpToReadingMark`：先切换到正确 section，再滚到段落
- `handleMarkCompleted`：单 section 行为不变；多 section 增加确认

### 本阶段不要求完成的事情

- 多 section 之间的连续滚动（每 section 独立渲染即可）
- 全文档全文搜索
- 跨 section 的收藏批量操作

### 完成标志

- [ ] 多 section 文档可通过 TOC 切换阅读
- [ ] TOC 树正确展示层级缩进
- [ ] 段落索引在 section 内正确分配
- [ ] 收藏正确记录 sectionId 和 sectionHeading
- [ ] 阅读进度正确记录当前 section
- [ ] 单 section 文档行为完全无变化（回归验证）
- [ ] 字号调节对所有 section 生效
- [ ] 旧 bookmark（无 sectionId）在单 section 文档上正常

### 风险点

| 风险 | 应对 |
|------|------|
| MarkdownContent 的 paraIdx 在多 section 间残留 | 切换 section 时调用 `key={section.id}` 强制重挂载 |
| TOC 树错误（depth 不连续） | `buildTocTree` 增加防御：depth 间隙过大时自动修正 |
| 切换 section 滚动位置不重置 | 切换时 `scrollTo(0, 0)` |

### 回滚策略

- 如果 ReaderPage 改造影响单 section 稳定性，通过 `sectionCount === 1` 走完全旧路径

## 六、Phase 3：下游系统适配

### 阶段目标

让回顾面板、文章库列表、备份导入导出等下游系统正确处理多 section 文档。

### 本阶段核心任务

#### 任务 3.1：回顾面板适配

- 卡片展示 `sectionHeading` 作为来源上下文
- "跳转原文位置"逻辑适配：先切换到对应 section，再滚到段落
- 回顾面板加载 bookmark 时预取关联 Document metadata（至少 `sections` 数组），以支持 `resolveSectionHeading` 回退查询
- 单 section 文档的回顾展示无变化

#### 任务 3.2：文章库列表适配

- 列表项显示格式信息（sectionCount > 1 时展示章节数）
- 进度百分比计算适配多 section：
  - 多 section 文档进度 = 已完成 section 词数 / 总词数
- 排序规则不变（未读 → 正在读 → 已读完）

#### 任务 3.3：备份导入导出适配

- 导出格式 v2 包含完整的 Document 结构（含 sections）
- 导入时验证 sections 结构完整性
- v1 旧格式导入自动升级（经 `migrateArticleToDocument`）
- 导入导出在单/多 section 文档上均正常

#### 任务 3.4：数据迁移脚本适配

- `localMigration.js` 和 `remoteMigration.js` 中增加新字段的映射：
  - `author`、`format`、`coverUrl`、`lang`、`sourceUrl`
  - `sections`（JSONB）、`sectionCount`
  - bookmark: `sectionId`、`sectionHeading`
  - readingMark: `sectionId`、`completedSections`

### 完成标志

- [ ] 回顾面板正确展示多 section 收藏的来源章节
- [ ] 文章库列表正确展示格式和章节信息
- [ ] 备份文件包含完整的 sections 结构
- [ ] 新旧备份格式互相兼容
- [ ] 迁移流程正确同步新字段

### 回滚策略

- 各模块内部通过 `sectionCount === 1` 条件分支保持单 section 路径不变

## 十、延期与回退策略

### 延期原则

若某阶段延期：
- Phase 0 延期 → 阻塞全部后续阶段，优先解决
- Phase 1 延期 → Phase 2/3 可使用硬编码的单 section Document 做预研
- Phase 2 延期 → Phase 3 的部分适配（回顾面板、备份格式）可提前做

### 回退原则

- **优先局部回退，不优先整体推翻**
- Phase 0 出问题 → 优先修补数据迁移脚本，不推翻 Document 模型
- Phase 1 出问题 → 单个提取器出问题只回退该提取器
- Phase 2 出问题 → 单 section 路径不受影响，多 section 路径可单独回退
- Phase 3 出问题 → 每个下游系统独立回退，不影响阅读核心路径

### 最重要的回退底线

无论哪个阶段出现问题，都应守住：
- **单 section 文档（当前所有现有数据）的完整功能不被破坏**
- 不丢失用户已存在的本地原始数据
- 不让未验证的多 section 路径成为默认

## 十二、总结

本次分段实施计划的核心结论是：

- 按 **"Phase 0（类型+数据层）→ Phase 1（提取器+epub2MD）→ Phase 2（渲染）→ Phase 3（下游适配）"** 的顺序推进
- Phase 0 是全部后续工作的基础，新增了 localStorage 回填、导出 v2、JSDoc 三个遗漏任务
- Phase 1 的 EPUB 提取器改为集成 epub2MD（MIT, ~100KB），替代手写 JSZip 方案
- Phase 4（PDF）已移除——在需求验证且后端条件成熟前，不投入前端 PDF 提取
- 每阶段以"单 section 文档行为不变"为回退底线
