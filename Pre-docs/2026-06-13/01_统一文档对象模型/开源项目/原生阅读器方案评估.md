# 原生阅读器方案评估

- **日期**：2026-06-13
- **核心问题**：是否应该放弃"提取→转换→Document 模型"路线，改为直接内嵌 EPUB/PDF 原生阅读器，在其上改造标注功能？

---

## 一、这个思路好在哪里

回到需求本质——用户导入 EPUB/PDF 是为了**阅读**，不是为了让系统做数据转换。原生阅读器路线有四个不可否认的优势：

### 1.1 保真度 100%

```
提取路线：EPUB → 解析 XHTML → 转 Markdown → 渲染
          ↑ 每一步都在丢失信息（字体、颜色、排版、图片位置）

原生路线：EPUB → epub.js 渲染
          ↑ 零信息丢失，出版商的排版原样呈现
```

对于技术类 EPUB（代码块配色、表格对齐、公式渲染），这个差别是决定性的。

### 1.2 消除整条提取链路

不需要 epub2md、不需要 `##`/`###` 扫描、不需要 Turndown、不需要处理图片的 base64 嵌入、不需要担心段落切分规则——整套提取器代码直接清零。

### 1.3 图片天然可用

EPUB 内嵌图片在 epub.js 里直接在正确位置渲染，不需要 base64 嵌入、不需要 Supabase Storage、不需要占位符。PDF 同理。

### 1.4 阅读进度天然准确

"读到第 3 章第 12 页" 比 "读到 paragraphIndex 847" 对用户更有意义。epub.js 和 pdf.js 都提供原生的位置追踪。

---

## 二、核心障碍：标注系统需要重新设计

当前 ReadRead 的标注链路：

```
用户选中文字 → mouseUp 事件 → 读取 data-para-index →
创建 bookmark { articleId, paragraphIndex, charOffset, text, contextSentence } →
ParagraphRenderer 根据 paragraphIndex 高亮 →
BookmarkPanel 根据 paragraphIndex 跳转 →
ReviewModal 展示 text + contextSentence（不依赖 paragraphIndex）
```

这条路线的每步都建立在 **"我们自己渲染文本，所以我们可以控制 DOM 结构"** 的前提上。

原生阅读器改变了这个前提：

| 标注步骤 | 当前方案 | epub.js 原生方案 | 难度 |
|---------|---------|-----------------|------|
| **选中文字** | 自定义 React 组件内的 mouseUp | `rendition.on('selected', cb)` → 获取选中文本 + CFI | ✅ 成熟 API |
| **创建 bookmark** | `data-para-index` + `charOffset` | CFI 字符串 | ✅ epub.js 内置 CFI 支持 |
| **高亮显示** | ParagraphRenderer 的 gold bg | `rendition.annotations.highlight(cfi, data, callback)` | ✅ epub.js 内置注释系统 |
| **跳转回去** | `querySelector([data-para-index])` | `rendition.display(cfi)` | ✅ epub.js 内置导航 |
| **段落级 bookmark 按钮** | ParagraphRenderer 注入 gold button | 需要通过 hooks 注入自定义 UI | ⚠️ 需要在 iframe 中注入 React 组件 |
| **翻译面板** | React Portal 弹出 | 需要在 iframe 中注入 | ⚠️ iframe 隔离 |
| **ReviewModal** | 展示已存的 text + contextSentence | 同上——创建时已提取 | ✅ 不受影响 |
| **sectionHeading** | 从 Document.sections 读取 | 从 epub.js TOC 读取 | ✅ epub.js 提供 TOC |

### 2.1 好消息：epub.js 的注释系统相当成熟

epub.js 是 EPUB 阅读器的事实标准。它的注释和标注系统经过了多年的打磨：

```js
// 选中文字 → 获取 CFI 范围
rendition.on('selected', (cfiRange, contents) => {
  // cfiRange: "epubcfi(/6/4[chap01]!/4/1:0,/4/1:5)"
  // contents: 可以从中提取选中文本和上下文

  // 创建高亮
  rendition.annotations.highlight(
    cfiRange,           // CFI 范围
    { type: 'bookmark', text: selectedText },  // 自定义数据
    (e) => { /* 点击回调 */ },
    'rr-bookmark-gold', // CSS class
    { fill: 'rgba(255,215,0,0.3)' }
  );
});

// 跳转到书签位置
rendition.display(bookmark.cfi);
```

这些 API 覆盖了 ReadRead 标注系统的核心功能。而且 epub.js 的注释会**自动持久化到 section 并随内容加载重新渲染**——不需要自己管理高亮的生命周期。

### 2.2 坏消息：iframe 隔离是 UI 集成的噩梦

epub.js 把 EPUB 内容渲染在 iframe 中（安全原因：EPUB 可以包含 JavaScript）。这意味着：

1. **gold bookmark 按钮**：当前在 ParagraphRenderer 中通过绝对定位注入的段落级收藏按钮，在 iframe 中需要通过 `rendition.hooks.content.register()` 注入 HTML/CSS/JS
2. **翻译弹窗**：当前通过 React Portal 渲染的翻译面板，无法跨越 iframe 边界。需要改为在 iframe 内自行渲染，或使用 postMessage 通信
3. **HoverCard**：同上，DOM 隔离导致无法使用 React 组件

**这不是不可解**——epub.js 提供了 hooks 系统来注入内容：

```js
rendition.hooks.content.register((contents, rendition) => {
  // contents.document → iframe 内的 document 对象
  // 可以在此注入 CSS、添加事件监听、创建 UI 元素

  const doc = contents.document;

  // 为每个段落添加收藏按钮
  doc.querySelectorAll('p').forEach((p, i) => {
    const btn = doc.createElement('button');
    btn.className = 'rr-bookmark-btn';
    btn.dataset.paraIndex = i;
    btn.onclick = (e) => {
      // postMessage 到父窗口 → React 组件响应
      window.parent.postMessage({
        type: 'BOOKMARK_PARAGRAPH',
        paraIndex: i,
      }, '*');
    };
    p.insertBefore(btn, p.firstChild);
  });

  // 在 iframe 内创建翻译弹窗（原生 DOM）
  const tooltip = doc.createElement('div');
  tooltip.className = 'rr-tooltip';
  doc.body.appendChild(tooltip);
});
```

但这条路意味着：**ReadRead 的标注 UI 需要维护两套实现**——React 组件树（URL/粘贴文章）和原生 DOM 注入（EPUB/PDF）。任何 UI 改动都需要同步两处。

## 三、PDF 的原生方案更复杂

PDF.js 的注释系统和 epub.js 相比有明显差距：

| 能力 | epub.js | PDF.js |
|------|---------|--------|
| **文本选中事件** | ✅ `selected` 事件 + CFI | ⚠️ 需要从 text layer 手动获取 |
| **位置标识** | ✅ CFI（精确到字符） | ⚠️ pageNumber + textRects（不如 CFI 精确） |
| **高亮 API** | ✅ `annotations.highlight()` | ⚠️ 需要手动创建 overlay div |
| **跳转到位置** | ✅ `display(cfi)` | ⚠️ `pageNumber` + 手动滚动 |
| **自定义 UI 注入** | ✅ hooks 系统 | ❌ 无 hooks，完全手动 |

PDF.js 在 v5.x (2025) 增加了内置的注释编辑器（highlight + comment floating button），但这些是面向终端用户的交互式工具，不是面向开发者的程序化 API。要实现 ReadRead 的"选中文字 → 自动翻译 → 创建 bookmark"，需要大量自定义代码。

## 四、对 "统一文档对象模型" 的影响

如果采用原生阅读器路线，整个 Document + Section 模型对 EPUB/PDF 就不再有意义——epub.js 自己就是文档模型，它管理 TOC、sections、阅读位置。

但这不意味着统一模型没有价值——**它仍然适用于 URL 文章、粘贴文本、Markdown 文件。** 准确地说，会有两个文档域：

```
┌─────────────────────────────────────────────┐
│              ReadRead 内容域                 │
├─────────────────────┬───────────────────────┤
│ 文本型内容           │ 原生格式内容           │
│ (URL/粘贴/Markdown)  │ (EPUB/PDF)            │
├─────────────────────┼───────────────────────┤
│ Document 模型        │ epub.js Book 对象      │
│ Section[]            │ pdf.js PDFDocument    │
│ paragraphIndex       │ CFI / pageNumber      │
│ MarkdownContent      │ epub.js Rendition     │
│                     │ pdf.js PDFViewer       │
└─────────────────────┴───────────────────────┘
```

两个域之间的统一靠 **Bookmark 模型** 来桥接：

```ts
interface Bookmark {
  // 通用字段（所有格式共用）
  id: string
  type: 'word' | 'phrase' | 'sentence' | 'paragraph'
  text: string
  translation: string | null
  contextSentence: string | null
  contextTranslation: string | null
  sectionHeading: string | null   // 冗余字段，回顾面板展示

  // 位置字段（格式相关，union type）
  position: ParagraphPosition | EpubCfiPosition | PdfPosition
}

interface ParagraphPosition {
  type: 'paragraph'
  documentId: string
  sectionId: string
  paragraphIndex: number
  charOffset: number
}

interface EpubCfiPosition {
  type: 'epubcfi'
  documentId: string
  cfi: string
}

interface PdfPosition {
  type: 'pdf'
  documentId: string
  pageNumber: number
  textRects: { x: number, y: number, width: number, height: number }[]
}
```

**关键洞察**：ReviewModal 不需要知道 bookmark 的 position 类型——它只展示 `text`、`translation`、`contextSentence`、`sectionHeading`，这些字段在创建 bookmark 时就已经提取完毕。position 只在两个场景使用：高亮渲染和跳转。这两个场景天然是 reader 相关的。

## 五、两种路线对比

| 维度 | 提取转换（当前方案） | 原生阅读器 |
|------|-------------------|-----------|
| **EPUB 文本保真** | ⭐⭐⭐ 95%，丢失排版 | ⭐⭐⭐⭐⭐ 100% |
| **PDF 文本保真** | ⭐⭐ 取决于提取质量 | ⭐⭐⭐⭐⭐ 100% |
| **图片处理** | ⭐⭐ 需要 base64/存储 | ⭐⭐⭐⭐⭐ 原生渲染 |
| **表格/公式/代码** | ⭐⭐ 可能丢失格式 | ⭐⭐⭐⭐⭐ 原生渲染 |
| **标注 UI 实现** | ⭐⭐⭐⭐⭐ 和现有完全复用 | ⭐⭐ 需要 iframe 内重建 |
| **阅读体验统一性** | ⭐⭐⭐⭐⭐ 所有内容同一 UI | ⭐⭐ URL 和 EPUB 的 UI 不同 |
| **ReviewPanel** | ⭐⭐⭐⭐⭐ 完全不受影响 | ⭐⭐⭐⭐⭐ 也不受影响（创建时已提取） |
| **跳转回原文** | ⭐⭐⭐⭐⭐ 简单 DOM query | ⭐⭐⭐⭐ epub.js display(cfi) 可靠 |
| **阅读进度** | ⭐⭐⭐ section 内 paragraphIndex | ⭐⭐⭐⭐⭐ "第3章 第12页" |
| **EPUB 开发工作量** | ⭐⭐⭐⭐ epub2md + 适配层~200行 | ⭐⭐ epub.js 集成 + 标注系统改造~800行 |
| **PDF 开发工作量** | ⭐ pdfjs-dist 手写启发式 | ⭐⭐ PDF.js 集成 + 标注改造~1000行 |
| **长期维护** | ⭐⭐⭐⭐ 一种渲染路径 | ⭐⭐ 两种渲染路径 |
| **搜索（全文档）** | ⭐⭐⭐⭐⭐ 遍历 sections text | ⭐⭐ epub.js iframe + PDF.js text layer 分别搜索 |

## 六、一个折中方案：混合架构

不一定要非此即彼。可以走**原生渲染 + 结构化提取并行**的路线：

```
EPUB 文件
   │
   ├──→ epub.js 渲染（阅读用）
   │    └── 标注使用 CFI
   │    └── 进度使用 section/page
   │
   └──→ epub2MD 提取（数据用）
        └── 构建 Document 模型
        └── 供回顾面板展示 sectionHeading
        └── 供全文档搜索
```

epub2MD 的提取结果**不用于渲染**，只用于构建结构化索引。标注系统使用 CFI 定位，但 bookmark 的 `sectionHeading` 从 Document 模型中读取。

**优点是**：阅读保真度 100% + 数据结构化 100%。**缺点是**：两个系统都在跑，运维复杂度翻倍。

这个方案的定位是"等到 ReadRead 有后端服务时再考虑"，当前阶段不值得。

---

## 七、结论：什么时候该走原生阅读器路线

### 现在不该走。理由：

1. **EPUB 文本类内容占绝对多数**。英语学习者读的是小说、传记、通俗非虚构——这些书的排版复杂度低，epub2md 的 Markdown 转换几乎无损。epub2md 方案对这类内容已经足够好。

2. **标注系统是 ReadRead 的核心差异点**。把标注 UI（gold button、翻译弹窗、HoverCard）在 iframe 中重建一遍，在"构建期"阶段是性价比最低的工作。

3. **维护两套渲染路径的实际成本被低估了**。每次改 ReaderPage 的功能（字号、主题、标注交互），都需要同时确认 epub.js iframe 内的行为一致。

4. **epub2md 方案已经验证可行**——数据模型映射清晰，适配层薄。现在切换方案会丢掉已有的明确路径。

### 但应该为它留好门。具体做法：

**1. Bookmark position 使用 union type**：

```ts
// 当前设计文档的方案：
bookmark { documentId, sectionId, paragraphIndex, charOffset }

// 改为：
bookmark {
  documentId,
  position: {
    type: 'paragraph',    // 未来可扩展 'epubcfi' | 'pdf'
    sectionId: string,
    paragraphIndex: number,
    charOffset: number,
  }
}
```

这纯粹是数据建模层面的决策，零额外工作量，但保证未来引入 CFI 时不需再次迁移 bookmark schema。

**2. ReaderPage 预留 reader 类型切换点**：

```jsx
// 当前：
<MarkdownContent text={section.body.markdown} />

// 改为（现在就加 switch，但只有 markdown 分支）：
{section.readerType === 'markdown' && <MarkdownContent ... />}
{/* 未来: readerType === 'epub-native' && <EpubReader ... /> */}
```

**3. 不要给 epub2md 适配层写死假设**。提取器和 ReaderPage 之间的接口保持干净，让 ReaderPage 将来可以用 epub.js 替换 epub2md 作为"阅读渲染层"。

### 什么时候重新评估原生阅读器：

1. **PDF 成为主要导入格式**（> 30%）且用户普遍反馈提取质量不可接受
2. **技术类 EPUB 需求爆发**——代码、公式、表格密集的书籍，Markdown 转换后损失严重
3. **ReadRead 进入商业化阶段**——有足够资源维护两条渲染路径
4. **epub.js 或 pdf.js 的 React 封装成熟**——有现成的 `<EpubReader>` 和 `<PdfReader>` React 组件，不需要从零做 iframe 集成

**在此之前，epub2md 提取转换方案是正确的选择。**
