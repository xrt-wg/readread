# 四项目综合对比与选型建议

- **日期**：2026-06-13
- **分析项目**：epub2MD、E2M、Marker、MarkItDown

---

## 一、一句话定性

| 项目 | 一句话 | 最适合的场景 |
|------|--------|------------|
| **epub2MD** | 专精 EPUB→Markdown 的 TypeScript 工具，输出带 TOC 树 + 章节数组的结构化数据 | 浏览器/Node.js 端的 EPUB 解析 |
| **E2M** | Python 的"一切转 Markdown"管道，Parser 提取文本 + LLM Converter 清洗格式 | 服务端 RAG 数据预处理 |
| **Marker** | 质量最高的 PDF→Markdown，深度学习模型 + 32 种 Block 类型 + 可选 LLM 增强 | 复杂 PDF（论文、表格、公式）的高质量转换 |
| **MarkItDown** | 微软出品，格式支持最广，API 最简单——输入文件，输出一个 Markdown 字符串 | LLM  ingestion 管道，快速集成 |

---

## 二、核心数据结构对比（关键！）

这是对 ReadRead 最重要的维度——ReadRead 需要 `Document { sections: Section[] }`，即带层级的有结构数据，不是一坨字符串。

### epub2MD 的输出

```ts
// 调用 parseEpub(file) 返回 Epub 对象：
Epub {
  structure: {
    opf: {
      manifest: Manifest,   // 所有资源文件的索引
      metadata: {           // 书名、作者、语言、出版社
        title: "Clean Code",
        author: ["Robert C. Martin"],
        language: "en",
        ...
      },
      spine: Record<string, number>  // 阅读顺序: { itemId → index }
    },
    toc: Toc {              // 层级目录树
      tree: TocItem[]       // 递归结构: { name, sectionId, children[] }
    }
  },
  sections: Section[]       // 按 spine 顺序的章节数组
}

Section {
  id: string,               // manifest item id, e.g. "chapter_001"
  htmlString: string,       // 原始 XHTML
  toMarkdown(): string,     // → Markdown 字符串
  toHtmlObjects(): HtmlNodeObject[]  // → 结构化 HTML 树（含 base64 图片）
}
```

**关键特征**：TOC 是原生的递归树结构（`TocItem.children[]`），可直接遍历推导 depth + parentId。sections 按阅读顺序排列，与 TOC 节点通过 `sectionId` 关联。

### Marker 的输出

```python
# JSON 模式
JSONOutput {
  children: BlockOutput[]   # 递归的 Block 树
}

BlockOutput {
  id: str,                  # 路径式 ID
  block_type: Literal[      # 32 种类型之一
    "SectionHeader", "Text", "Table", "Figure",
    "Code", "Equation", "Form", "Footnote", ...
  ],
  html: str,
  children: BlockOutput[],  # 递归子 Block
  section_hierarchy: dict,  # { heading_level: block_id }
  images: dict,             # { block_id: base64_image }
}
```

**关键特征**：这是所有项目中最丰富的结构模型。`section_hierarchy` 显式记录了每个 Block 在各层级下的归属。但它是 Python，需要 GPU。

### E2M 的输出

```python
E2MParsedData {
  text: str,                # 所有文本拼接为一个字符串
  images: Dict[str, E2MParsedImageData],
  attached_images: Dict[str, E2MParsedImageData],
  metadata: Dict
}
```

**关键特征**：章节结构完全丢失。即使 unstructured 库在内部识别了 Title/Header/Section-header 元素类别，最终输出也全部拼成了平文本。

### MarkItDown 的输出

```python
DocumentConverterResult {
  markdown: str,            # 一个 Markdown 字符串
  title: str | None
}
```

**关键特征**：最简输出。所有结构隐式存在于 Markdown 的 `#`/`##` 标题中，没有程序化访问入口。

### 结构保真度排名

```
Marker (32 种 Block 类型 + section_hierarchy)  >  epub2MD (TOC 树 + sections)
  >>  MarkItDown (implicit in markdown headings)
    >>  E2M (flat string, structure discarded)
```

## 三、与 ReadRead 技术栈的适配性

| 维度 | epub2MD | Marker | MarkItDown | E2M |
|------|---------|--------|------------|-----|
| **语言** | TypeScript | Python | Python | Python |
| **浏览器端可用** | ✅ fflate 纯 JS 解压 | ❌ 需要 PyTorch + GPU | ❌ Python 运行时 | ❌ Python 运行时 |
| **npm 包** | ✅ `epub2md` | ❌ | ❌ | ❌ |
| **体积（估算）** | ~100KB | > 3GB（含模型） | ~50MB | > 3GB（含模型） |
| **无外部服务依赖** | ✅ 纯本地 | ⚠️ LLM 可选 | ⚠️ Azure 可选 | ⚠️ LLM 可选 |
| **许可证** | MIT | GPL-3.0 | MIT | MIT |

## 四、EPUB 处理专项对比

| 能力 | epub2MD | Marker | MarkItDown | E2M |
|------|---------|--------|------------|-----|
| **EPUB 解析方式** | 原生 ZIP→OPF→Spine→XHTML | EPUB→weasyprint→PDF→处理 | ZIP→OPF→Spine→BeautifulSoup→Markdown | ebooklib→ZIP→unstructured |
| **TOC 层级保留** | ✅ 递归 TocItem 树 | ❌ 转 PDF 后丢失 EPUB TOC | ❌ 不保留 | ❌ 丢弃 |
| **Metadata 提取** | ✅ title, author, language, publisher, description | ⚠️ 经 PDF 转换可能丢失 | ✅ title | ⚠️ 有限 |
| **封面图** | ⚠️ 通过 manifest 可获取但未专门暴露 | ❌ 经 PDF 转换丢失 | ❌ 不提取 | ⚠️ epub_util 可提取但未集成到输出 |
| **章节内图片** | ✅ 内部图→base64/文件；外部图→可选下载 | ❌ EPUB 先转 PDF | ⚠️ data: URI 嵌入 | ✅ 提取为文件，但文本中插入逻辑未完成 |
| **内部链接重写** | ✅ 章节间链接自动重写为正确路径 | ❌ | ❌ | ❌ |
| **中英文排版** | ✅ autocorrect（中英文间自动加空格） | ❌ | ❌ | ❌ |

**结论：epub2MD 在 EPUB 处理上全面领先。** Marker 把 EPUB 转成 PDF 再处理是明显的架构缺陷——这丢失了 EPUB 原生的 TOC 层级、metadata 和内部链接结构。

## 五、PDF 处理专项对比

| 能力 | Marker | MarkItDown | E2M(marker 引擎) | epub2MD |
|------|--------|------------|-----------------|---------|
| **文本提取** | ✅ 高质量 | ✅ pdfplumber+pdfminer | ✅ 高质量 | N/A |
| **标题/层级检测** | ✅ surya 布局分析 + SectionHeader 类型 | ⚠️ 隐式（字体大小推断） | ✅ 同 Marker | N/A |
| **表格** | ✅ 结构化提取 + LLM 增强 | ✅ pdfplumber 表格检测 | ✅ 同 Marker | N/A |
| **公式** | ✅ texify 专用模型 | ❌ | ✅ 同 Marker | N/A |
| **图片/图表** | ✅ 裁剪 + base64 | ❌ | ✅ surya_layout 裁剪 | N/A |
| **多栏布局** | ✅ surya 阅读顺序 | ⚠️ 有限 | ✅ surya 阅读顺序 | N/A |
| **扫描版 PDF** | ✅ surya OCR | ❌ 需外部 OCR | ✅ surya OCR | N/A |
| **GPU 需求** | ✅ 需要 | ❌ 不需要 | ✅ 需要 | N/A |
| **许可证** | GPL-3.0 ⚠️ | MIT ✅ | MIT ✅ | N/A |

**结论：Marker 是 PDF 质量之王，但 GPL-3.0 + GPU 是两大硬门槛。** MarkItDown 是唯一不需要 GPU 且 MIT 许可的 Python PDF 方案。

## 六、图片处理机制对比

| 能力 | epub2MD | Marker | MarkItDown | E2M |
|------|---------|--------|------------|-----|
| **EPUB 内部图片** | base64 嵌入或提取为文件 | N/A（先转 PDF） | data: URI | 提取为文件 |
| **远程图片** | 可选下载本地化 | N/A | 保留原 URL | 可选下载 |
| **PDF 内嵌图片** | N/A | 裁剪 + base64 嵌入 | ❌ | surya_layout 裁剪 |
| **透明背景过滤** | ❌ | ❌ | ❌ | ✅ epub_util |
| **图片插入回文本** | ✅ 自动 | ✅ 自动 | ⚠️ 保留引用 | ❌ 未完成 |
| **LLM 图片描述** | ❌ | ✅ 可选 LLM 描述替代原图 | ❌ | ✅ ImageConverter |
| **输出格式** | `![](images/file.png)` 或 base64 | base64 嵌入 JSON | 原 URL 或 data: URI | 文件路径引用 |

**对 ReadRead 的启示**：
- epub2MD 的 `toHtmlObjects()` 方法能将内部图片转为 base64——这正是 ReadRead 需要的"可持久化封面图"方案
- E2M 的透明背景过滤值得借鉴（装饰性图片自动跳过）
- Marker 的 LLM 图片描述是远期可能性（技术类 EPUB 的图表→文字描述）

## 七、最终选型建议

### 对于 EPUB（Phase 1 核心目标）

**选择 epub2MD，这是唯一正确的选择。**

理由：
1. TypeScript，浏览器端直接可用——和 ReadRead 技术栈一致
2. 输出结构化的 `sections[]` + `Toc` 递归树——几乎 1:1 映射到 ReadRead 的 `Document.sections: Section[]`
3. `metadata` 直接提供 `title`/`author`/`language`/`publisher`
4. `toMarkdown()` 内置 HTML→Markdown 转换，ReadRead 不用再引入 Turndown 做 EPUB 路径的转换
5. 图片 base64 嵌入——天然解决 Blob URL 不可持久化的问题
6. MIT 许可
7. 已有 autocorrect（中英文排版），对中国用户友好

**映射关系**：

```
epub2MD 输出                    →  ReadRead Document 模型
──────────────────────────────────────────────────────────
Epub.structure.toc.tree         →  遍历递归树，分配 depth + parentId + order
Epub.sections[i].id             →  Section.id (直接使用)
Epub.sections[i].toMarkdown()   →  Section.body.markdown
Epub.structure.opf.metadata     →  Document.title, Document.author
```

**适配工作量估算**：一个薄适配函数（~50 行），核心逻辑是 TOC 树 → 平铺 sections 的 depth/parentId 推导。

### 对于 PDF（Phase 4 远期目标）

**选择 pdfjs-dist + 借鉴 Marker 的启发式规则，不引入任何 Python 后端。**

理由：
1. PDF 是 Phase 4，优先级最低，不应引入运维复杂度
2. Marker 虽然质量最高，但 GPL-3.0 许可对商业使用有风险，且 GPU 需求意味着必须部署后端
3. 如果未来 PDF 需求强烈且前端方案不达标，可以引入 **marker-pdf 作为独立微服务**（只部署 PDF 相关部分，不用整个 E2M 家族）
4. 当前阶段：参考 Marker 的 32 种 Block 类型定义和标题检测逻辑，改进 pdfjs-dist 的启发式规则

### 对于图片处理

**采用 epub2MD 的 base64 嵌入策略 + E2M 的透明背景过滤 + 自建占位符方案**：

```
EPUB 内部图片：
  小图（< 50KB）    → epub2MD 原生 base64 嵌入
  大图（≥ 50KB）    → 占位符 ![](placeholder) + 标注 alt text
  透明背景图         → 借鉴 E2M，自动跳过（装饰元素）

EPUB 封面图：
  → epub2MD manifest 获取 cover item → base64 → 缩放到 300px → 存入 coverUrl

远程图片：
  → epub2MD 的 --localize 模式（可选下载）
```

## 八、不选其他三个的理由

### 不选 E2M

- 输出是平文本，章节结构完全丢失——这是**致命缺陷**
- Python 后端，需要 GPU + LLM API key
- 图片插入文本的逻辑标记为 `# todo`，未完成
- 设计目标是 RAG 数据预处理，不是交互式阅读工具

### 不选 Marker（当前阶段）

- Python + GPU 强依赖，无法在浏览器端运行
- GPL-3.0 许可证——对商业产品是法律风险
- EPUB 被转为 PDF 处理——丢失了 EPUB 的章节结构和 metadata，本末倒置
- 是 PDF 质量最高的方案，但 ReadRead 当前的核心矛盾不是 PDF 质量

### 不选 MarkItDown

- 输出是单一 Markdown 字符串——没有结构化数据
- 虽然格式支持最广、API 最简单，但这恰恰意味着它对 ReadRead 的帮助最小：ReadRead 需要章节层级，MarkItDown 只给一坨文本
- 唯一的价值是作为"如果未来要做 DOCX/PPTX 导入"的参考实现

## 九、总结

```
ReadRead EPUB 导入的推荐方案：

  EPUB 文件
     │
     ▼
  epub2md (npm, ~100KB, 纯前端)
     │
     ├── structure.toc.tree  ──→ 遍历推导 depth + parentId + order
     ├── sections[].toMarkdown() ──→ Section.body.markdown
     ├── structure.opf.metadata  ──→ Document.title, author, language
     └── manifest cover image   ──→ base64 → 缩放 → Document.coverUrl
     │
     ▼
  ExtractionResult { meta, sections }
     │
     ▼
  createDocument() 工厂函数
     │
     ▼
  Document { sections: Section[] }
```

**四个项目中，epub2MD 是唯一一个在"数据模型匹配度 + 技术栈兼容性 + 许可证友好度 + 浏览器端可用性"四个维度上都满足 ReadRead 需求的方案。** 其余三个（E2M、Marker、MarkItDown）都是 Python 后端工具，各有专长，但不适合嵌入一个纯前端阅读工具。
