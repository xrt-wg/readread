# 后端服务化方案评估

- **日期**：2026-06-13
- **前提假设**：暂时不考虑技术栈适配性，将"导入→解析→构建 Document 对象"作为独立后端服务

---

## 一、约束放开后，局面完全不同

之前分析的核心约束是"必须在浏览器里跑"。拿掉这个约束后：

| 之前不可行的 | 现在可行的 |
|------------|----------|
| Python 库（E2M、Marker、MarkItDown） | ✅ 服务端随便跑 |
| GPU/ML 依赖（torch、surya、marker 模型 > 3GB） | ✅ GPU 实例上跑 |
| LLM API 调用（清洗文本、描述图片） | ✅ 服务端可控 |
| 文件系统访问（提取图片、缓存模型） | ✅ 天然支持 |

**但代价也随之而来**：需要部署、监控、扩容一个 GPU 后端服务。

## 二、四个项目在"后端服务"视角下的重新排名

### 2.1 Marker：从"无法使用"到"核心引擎"

去掉浏览器约束后，Marker 成为最有力的候选：

**输出格式直接对号入座**：

```
Marker JSON 输出                    ReadRead Document 模型
─────────────────────────────────────────────────────────
metadata.table_of_contents[].title     →  section.heading
metadata.table_of_contents[].heading_level →  section.depth
blocks[].block_type == "SectionHeader" →  section 边界标记
blocks[].block_type == "Text"          →  section.body.text
blocks[].block_type == "Figure"        →  图片 section 或 body 内嵌图片
blocks[].html                          →  HTML→Markdown→section.body.markdown
blocks[].section_hierarchy             →  推导 parentId（见下文）
metadata.title（来自 PDF metadata）     →  document.title
```

**关键：`section_hierarchy` 字段**。Marker 的每个 Block 都有一个 `section_hierarchy` 字典：

```json
{
  "section_hierarchy": {
    "1": "/page/10/SectionHeader/0",   // ← h1 标题的 block id
    "2": "/page/10/SectionHeader/1"    // ← h2 标题的 block id
  }
}
```

这意味着任意一个 Text Block 都知道自己归属于 "h1=某个 SectionHeader" 和 "h2=某个 SectionHeader"。这个信息可以用来推导平铺 sections 的 `parentId`。

**但有一个实际问题**：Marker 的 block tree 是 **按页组织的**（Page → Block[]），而 ReadRead 的 sections 是 **按文档章节组织的**。一个跨 3 页的 Chapter 在 Marker 里会被拆成 3 个 Page 下的多个 Block。要把它们重新组装成 1 个 Section，需要在后处理中做**跨页合并**。

**另一个实际问题**：Marker 处理 EPUB 的方式是 `ebooklib → weasyprint → PDF → 处理`。这意味着 EPUB 原生的 TOC 结构在 weasyprint 转 PDF 的过程中丢失了。对于 EPUB，Marker 的 `table_of_contents` 是靠 surya 的布局分析从 PDF 页面中**重新检测**出来的标题——这和直接读 EPUB 的 NCX/NAV TOC 相比，有额外的误差。

---

### 2.2 epub2MD：优势依然成立

epub2MD 在后端场景下依然有价值，而且可以跑在廉价的 Node.js 实例上（不需要 GPU）：

```
epub2MD (Node.js, 无 GPU) → EPUB 解析 → TOC 树 + sections
   ↓
适配层 (50 行)
   ↓
ReadRead Document 模型
```

它的 TOC 是直接从 EPUB 元数据读取的，不需要 OCR 或布局检测——**100% 准确**。对比 Marker 的"EPUB→PDF→重新检测标题"路径，epub2MD 在 EPUB 场景下更可靠。

---

### 2.3 E2M：结构丢失问题可以通过"不丢弃元数据"修复

E2M 最大的问题是 `_prepare_unstructured_data_to_e2m_parsed_data` 把 unstructured 的元素类别丢弃了。但在后端场景下，可以直接绕过这个方法，从 unstructured 的 element list 中提取层级信息：

```python
# E2M 目前的代码（有问题）：
text = "\n".join([e.text for e in elements])  # 全拼在一起

# 改为：
for element in elements:
    if element.category == "Title":
        # → depth 0 section
    elif element.category == "Header":
        # → depth 1 section
    elif element.category == "NarrativeText":
        # → section body
```

这样修复后，E2M 的 EPUB 解析也能产出结构化 sections。但修复工作量不亚于直接写一个 EPUB 提取器。

---

### 2.4 MarkItDown：输出太扁平，后端也无法弥补

MarkItDown 只输出一个 Markdown 字符串。即使在后端，ReadRead 仍然需要自己扫描 `#`/`##` 来重建章节结构。它的价值在于格式覆盖广度（DOCX/PPTX/XLSX/音频等），如果 ReadRead 未来需要支持这些格式，可以作为参考实现。

## 三、后端服务的三种架构方案

### 方案 A：单一 Marker 服务（最大化质量）

```
              ┌─────────────────────────────────┐
              │     Marker Service (Python)      │
              │                                 │
  EPUB/PDF ──►│  marker.converters.pdf           │
              │  .PdfConverter                   │
              │         ↓                        │
              │  Rendered (JSON mode)            │
              │         ↓                        │
              │  后处理：Block Tree → Document   │
              │         ↓                        │
              │  Document { sections: [...] }    │
              │                                 │
              │  需要 GPU (H100/A100/T4)         │
              └─────────────────────────────────┘
```

**优点**：
- PDF 质量业界最佳（surya 布局 + texify 公式 + 可选 LLM 增强）
- 32 种 Block 类型，对复杂文档（论文、表格、公式）支持最好
- `section_hierarchy` 字段直接提供层级信息
- 统一的 PDF/EPUB/DOCX/PPTX/HTML 入口
- 支持 `--use_llm` 做 LLM 增强（纠正表格合并、公式识别等）

**缺点**：
- GPL-3.0 许可——如果 ReadRead 未来商业化，需要购买 commercial license
- GPU 成本：单个 worker 峰值 5GB VRAM，推荐 H100（~$2/h）或 T4（~$0.5/h）
- EPUB 处理链路绕了弯路（EPUB→weasyprint→PDF→解析），TOC 依赖 OCR 重建
- 延迟：一个 200 页 PDF 约 10-30 秒（H100），T4 上更慢
- 后处理复杂：需要将按页组织的 Block tree 合并为按章节组织的 Section 数组

**适用场景**：ReadRead 用户大量导入技术类 PDF（论文、教材），且愿意为质量付费。

---

### 方案 B：双引擎混合（EPUB 用 epub2MD，PDF 用 Marker）

```
              ┌──────────────────────────────────┐
              │        API Gateway                │
              └────────┬─────────────┬────────────┘
                       │             │
              EPUB     │             │    PDF
                       ▼             ▼
              ┌──────────────┐ ┌──────────────────┐
              │ epub2MD      │ │ Marker Service   │
              │ (Node.js)    │ │ (Python + GPU)   │
              │ 无 GPU       │ │                  │
              │ TOC 100%准确  │ │ 布局分析+OCR     │
              └──────┬───────┘ └────────┬─────────┘
                     │                  │
                     ▼                  ▼
              ┌──────────────────────────────────┐
              │   统一适配层 → Document           │
              └──────────────────────────────────┘
```

**优点**：
- EPUB 解析用 epub2MD，TOC 从原始元数据读取，100% 准确
- PDF 解析用 Marker，获得最佳布局分析和 OCR 质量
- epub2MD 跑在廉价的 Node.js 实例上（$5-10/月），只有 PDF 才需要 GPU
- 两个引擎各自做自己最擅长的事

**缺点**：
- 两套运行时（Node.js + Python），运维复杂度增加
- 两种不同的适配层代码
- 如果用户同时上传 EPUB 和 PDF，体验不一致（EPUB 秒级返回，PDF 需要等 GPU）

**适用场景**：ReadRead 的 EPUB 和 PDF 都是重要场景，且愿意承担一定的运维复杂度。

---

### 方案 C：轻量全格式（MarkItDown + 结构增强）

```
              ┌─────────────────────────────────┐
              │   MarkItDown Service (Python)    │
              │   无 GPU，CPU 即可               │
              │                                 │
  EPUB/PDF/   │  MarkItDown 转换                 │
  DOCX/PPTX ─►│         ↓                        │
              │  Markdown 字符串                  │
              │         ↓                        │
              │  ##/### 扫描 → 重建 Sections     │
              │         ↓                        │
              │  Document { sections: [...] }    │
              └─────────────────────────────────┘
```

**优点**：
- 格式覆盖最广（PDF/EPUB/DOCX/PPTX/XLSX/HTML/音频/YouTube...）
- 无 GPU 需求，运维成本最低
- MIT 许可，无商业化限制
- API 最简单，集成工作量最小

**缺点**：
- 章节结构依赖 Markdown `#`/`##` 扫描——不可靠（PDF 提取的文本可能没有规范的 Markdown 标题）
- PDF 质量远不如 Marker（无 OCR、无布局分析、无公式识别）
- EPUB 处理后也是平文本，丢失了 TOC 结构
- 本质上只是"把问题推迟到了结构扫描阶段"

**适用场景**：ReadRead 想快速支持 DOCX/PPTX 等额外格式，且对 PDF 质量要求不高。

## 四、关键决策因素

### 4.1 PDF 质量的不可压缩成本

高质量的 PDF 文本提取本质上需要解决三个问题：
1. **布局分析**（哪块是正文、哪块是页眉、多栏顺序）
2. **字符识别**（扫描版 PDF 的 OCR，数学公式）
3. **结构重建**（标题层级、表格、列表）

这三个问题中，布局分析和字符识别都需要深度学习模型。不存在一个"体积小、质量高、不需要 GPU"的方案。如果要高质量 PDF，就必须接受 GPU 依赖。

### 4.2 EPUB 的讽刺

EPUB 天生就包含了结构化的 TOC 和 metadata。用 ML 模型从 PDF 页面布局中"猜测"标题层级，是一种倒退——EPUB 解析不需要任何 ML，只需要正确读取 XML。Marker 把 EPUB 转成 PDF 再分析的做法，实际上是**把确定性的结构化信息变成了概率性的布局推断**。

这意味着：对于 EPUB，无论后端用什么方案，**epub2MD 都是比 Marker 更正确的选择**。

### 4.3 延迟与用户体验

| 场景 | epub2MD (CPU) | Marker (T4 GPU) | Marker (H100) |
|------|--------------|-----------------|---------------|
| 50 页 EPUB | **< 1 秒** | 10-20 秒（先转 PDF） | 3-5 秒 |
| 200 页 PDF | N/A | 60-120 秒 | 10-30 秒 |
| 10 页论文 PDF | N/A | 5-10 秒 | 2-5 秒 |

用户上传一个 EPUB 等 10 秒才能开始阅读，这是不可接受的。异步处理（"导入后在后台处理，完成后通知"）可以缓解但无法消除这个体验差距。

### 4.4 成本估算

| 方案 | 月基础成本 | 每 1000 页成本 |
|------|----------|--------------|
| 方案 B（epub2MD + Marker on T4） | ~$40（Node.js $5 + T4 GPU $35） | ~$1-3（仅 PDF 走 GPU，EPUB 免费） |
| 方案 A（Marker on H100） | ~$200+ | ~$2-5（EPUB 也走 GPU） |
| 方案 C（MarkItDown on CPU） | ~$5-10 | ~$0（仅 CPU） |

以 ReadRead 当前的个人工具定位，方案 C 最经济，方案 B 是质量和成本的合理折中。

## 五、推荐方案与实施路径

### 当前阶段（构建期个人工具）：暂不引入后端

ReadRead 目前是个纯前端个人工具。引入后端服务会带来一系列现阶段不该承担的成本和复杂度。建议的路径是：

```
现在（纯前端）                      未来（引入后端）
────────────────────────────────────────────────────
EPUB: epub2MD (npm)           →    保持不变（前端 epub2MD 已经完美）
PDF:  pdfjs-dist + 启发式      →    替换为 Marker 后端
图片: base64 + 占位符          →    Supabase Storage + 后端提取
```

### 引入后端的触发条件

以下任一条件满足时，重新评估后端方案：

1. **PDF 导入成为高频需求**（> 20% 的导入量来自 PDF）且用户反馈前端提取质量不可接受
2. **ReadRead 进入商业化阶段**，有能力承担 GPU 实例成本
3. **需要支持 EPUB/PDF 以外的格式**（DOCX、PPTX），且前端无可用库

### 届时推荐方案：方案 B（双引擎混合）

```
EPUB → epub2MD (Node.js, CPU, < 1s)
PDF  → Marker   (Python, GPU, 10-30s)
```

理由：
- EPUB 是确定性解析，不需要 ML；epub2MD 的 TOC 精度是 100%
- PDF 需要 ML 才能高质量提取；Marker 是目前开源最佳
- 两个引擎各自负责自己最擅长的格式
- Marker 的 GPL-3.0 问题：如果 ReadRead 商业化，要么购买 commercial license，要么在 PDF 路径上换用 MarkItDown（质量降级但无许可问题）

## 六、Block Tree → Document Sections 的映射方案（技术备忘）

如果未来使用 Marker 的 JSON 输出，后处理映射逻辑大致如下：

```python
def marker_json_to_document(rendered_json) -> Document:
    """
    Marker JSON output → ReadRead Document
    """
    sections = []
    toc = rendered_json["metadata"]["table_of_contents"]

    # 1. 从 table_of_contents 生成 Section 骨架
    for i, entry in enumerate(toc):
        sections.append({
            "id": f"s_{i}",
            "heading": entry["title"],
            "depth": entry["heading_level"] - 1,  # h1→0, h2→1
            "parentId": _find_parent(toc, i),      # 向前找最近的更浅层级
            "order": _count_siblings(toc, i),
        })

    # 2. 从 blocks 中提取每个 section 的 body
    all_blocks = _flatten_blocks(rendered_json["children"])
    for block in all_blocks:
        if block["block_type"] in ("Text", "Code", "ListItem", "Table"):
            section_idx = _resolve_section(block["section_hierarchy"])
            sections[section_idx]["body.text"] += block["html"]
            sections[section_idx]["body.markdown"] += html_to_markdown(block["html"])

    # 3. 计算 wordCount，构建 Document
    return create_document(sections, rendered_json["metadata"])

def _find_parent(toc, i):
    """向前找最近的 heading_level 更小的条目"""
    for j in range(i - 1, -1, -1):
        if toc[j]["heading_level"] < toc[i]["heading_level"]:
            return f"s_{j}"
    return None
```

这个映射的核心挑战不是逻辑复杂度，而是**跨页合并**——Marker 的 blocks 是按页组织的，同一个 section 的文本可能分散在多个 page 的多个 block 中。需要按 `section_hierarchy` 聚合。

## 七、总结

| 问题 | 结论 |
|------|------|
| 后端化后哪个方案最好？ | **方案 B（epub2MD + Marker）**——EPUB 用 epub2MD（100% 准确），PDF 用 Marker（最高质量） |
| 现在就该做后端吗？ | **不**。纯前端 epub2MD 已经完美解决 EPUB。PDF 后端化等有明确需求时再启动 |
| Marker 的 EPUB 处理能用吗？ | 能用但不如 epub2MD。它把 EPUB 转 PDF 再解析，丢失了原生 TOC |
| GPL-3.0 怎么办？ | 如果商业化，需要购买 Marker commercial license，或 PDF 路径降级到 MarkItDown |
| 后端化最大的坑是什么？ | Marker 的 Block tree → Document sections 的跨页合并逻辑，以及 EPUB/PDF 两条路径的维护成本 |
