# 统一文档对象模型 — 决策记录

- **日期**：2026-06-13
- **状态**：已决策
- **项目阶段**：构建期
- **决策主题**：在支持多格式导入（EPUB、PDF 等）之前，应将内部文档模型从当前单篇 Article 升级为统一的 Document + Sections 结构

---

## 一、背景

ReadRead 当前的内部文档模型是 Article：

```js
Article {
  id, title, text, markdown, wordCount, createdAt
}
```

这个模型建立在以下隐含假设之上：
- 内容是"一篇短文"（几百到几千词）
- 正文是线性的一维段落数组
- 阅读进度 = 一个 paragraphIndex
- 收藏定位 = paragraphIndex + charOffset
- 不存在章节、分节等层级

当前所有功能——渲染、收藏、阅读进度、回顾、数据迁移——都直接建立在这个模型之上。

随着导入格式扩展（EPUB、PDF、含多级标题的 Markdown 长文），上述假设将被打破。一本 EPUB 可能有 15 章、每章有子节；一篇长 Markdown 教程可能有 3 级标题嵌套。

因此需要决策：是将 Article 模型改造为能容纳这些内容的统一模型，还是继续保持当前扁平模型并只在导入时做降级处理（如拼接全部文本）。

---

## 二、决策目标

1. 定义一个统一的内部文档对象模型，使所有格式的提取结果都映射到同一结构
2. 保持对当前 Article 模型和所有下游功能的向后兼容
3. 在"足够的表达能力"和"不引入过度复杂度"之间取得平衡
4. 为后续渲染层、收藏系统、进度跟踪、回顾系统的升级提供明确的类型约束

---

## 三、决策结论

**将当前 Article 模型升级为统一的 Document 模型，核心结构如下：**

```ts
Document {
  id:              string
  title:           string
  author?:         string | null
  format:          string          // 'url' | 'epub' | 'pdf' | 'paste' | 'markdown' | 'html'
  coverUrl?:       string | null
  lang?:           string

  sections:        Section[]       // 平铺的一级数组

  totalWordCount:  number
  sectionCount:    number
  createdAt:       string
  updatedAt?:      string | null
}

Section {
  id:        string                // 稳定唯一标识
  heading:   string | null         // 节标题
  depth:     number                // 层级深度，0 为顶层
  parentId:  string | null         // 父节 ID
  order:     number                // 排序序号

  body: {
    text:      string              // 纯文本，始终存在
    markdown:  string | null       // 富文本格式，可选
    wordCount: number
  }
}
```

核心设计决策：
- **sections 使用平铺数组 + depth + parentId，不使用嵌套 children**
- **每个 section.body 是独立、互不重叠的文本块，父节与子节的 body 不存在包含或继承关系**
- **下游引用使用 `documentId + sectionId + paragraphIndex` 三级索引替代当前 `articleId + paragraphIndex` 二级索引**
- **sections 作为 JSONB 存储在 articles 表，不拆独立表**
- **文档模型不记录原始格式的细节（CSS、页面引用、EPUB spine 信息等）**

---

## 四、候选方案比较

### 方案 A：维持现状，导入时降级

导入 EPUB/PDF 时将所有章节文本拼接为一个 text 字符串，丢弃所有章节结构和标题信息。

#### 优点
- 零改动成本
- 所有现有功能保持不变

#### 致命问题
- 一本书 500 页，收藏的 paragraphIndex 是 4200，用户无法知道这个收藏来自哪一章
- 阅读进度无章节上下文，回归到"全文 45%"
- 章节标题全部丢失
- 回顾时随机抽出的收藏完全脱离语境

#### 结论
**否决。** 该方案在导入 EPUB 等结构化内容时会丢失大量语义信息，导致英语学习场景下的核心功能（收藏定位、进度跟踪、语境回顾）价值大幅下降。

---

### 方案 B：嵌套 sections（sections 内递归 children）

```ts
Section {
  id, heading, depth, order,
  body: { text, markdown, wordCount },
  children: Section[]       // 递归嵌套
}
```

#### 优点
- TOC 树可直接从数据结构渲染，无需推导
- 父子关系在模型内自描述
- 遍历子树直观

#### 代价
- 段落索引需要锚定到树节点路径而非单一 sectionId（`{ path: ["ch1", "ch1-s1"], paraIndex: 3 }`）
- 阅读进度：完成判定需要递归计算（"Chapter 1 完成" = 所有子孙节点完成）
- 数据库查询：查某章所有收藏需要先递归获取所有子孙 sectionId
- 渲染层：当前 MarkdownContent 的线性 paraIdx 分配机制完全失效
- 收藏面板展示："这个单词来自 ch1 > 1.1 > macOS > 第 3 段" 需要额外的路径到字符串的格式化逻辑
- 95% 的内容（单篇 URL 文章、粘贴文本）只有 1 个 section，嵌套结构对它们完全没有意义，却要承受全部复杂度

#### 结论
**否决。** 嵌套模型在表达能力上过剩，但让每一个下游系统（渲染、收藏、进度、数据库、回顾）都付出递归处理的复杂度代价。

---

### 方案 C：平铺 sections + depth + parentId（采用）

```ts
Section {
  id, heading,
  depth: number,          // 层级深度，0/1/2
  parentId: string | null, // 父节 ID
  order: number,           // 排序序号
  body: { text, markdown, wordCount }
}
```

sections 是平铺的一级数组。父子关系和 TOC 树从 depth + parentId 推导，而不是存储在嵌套结构里。

#### 优点
- 数据存储简单：一个数组，无递归
- 段落索引直接：`sectionId + paragraphIndex`，无树路径
- 阅读进度简单：当前 sectionId + 已完成 sectionId 列表
- 数据库查询简单：WHERE section_id = 's_ch1-s1'，无需递归
- 向后兼容好：单 section 文档退化为当前 Article 行为
- 95% 的简单内容保持简单
- TOC 树在渲染层通过 `depth + parentId` 推导，推导算法 O(n)，sections 不超过 200 个

#### 代价
- 父子关系查询需要 filter 或遍历（O(n)，但 n 上限约 200，可忽略）
- 完成判定中"某章的所有子孙"需要扫描一次 sections 数组
- 相比纯嵌套，多了一个 `parentId` 冗余字段

#### 结论
**采用。** 这是最小可行抽象——让 95% 的单层内容保持简单，同时让 5% 的多层内容可用。

---

## 五、关键决策点与取舍

### 5.1 不放嵌套层级

详见上文方案对比。核心理由：嵌套让每个下游系统付出复杂度税，而收益只惠及极少比例的内容。平铺 + depth + parentId 在信息表达上等价于嵌套，但在下游系统处理上简单得多。

### 5.2 sections 的 body 互不重叠、互不继承

父节 body 和子节 body 是独立、互斥的文本块：
- 父节 body：出现在父标题之后、第一个子标题之前的引言或过渡内容
- 子节 body：出现在子标题之后、下一个同级标题之前的具体内容

它们之间没有包含关系，渲染时各自独立显示，不拼接。

### 5.3 sections 作为 JSONB，不拆独立表

sections 始终一起加载、一起保存、一起删除。不存在"只查某一章"的独立查询场景。JSONB 在此场景下足够。

如果未来确实需要独立操作某个 section（如协作编辑），再考虑拆表。

### 5.4 文档模型不记录原始格式细节

EPUB 的 spine、CSS、页面引用，PDF 的坐标信息——这些在提取后丢弃。模型只保留对阅读和学习有意义的信息（文本、标题、结构）。

### 5.5 下游引用升级为三级索引

```
升级前：bookmark { articleId, paragraphIndex }
升级后：bookmark { documentId, sectionId, paragraphIndex }
```

单 section 文档的 sectionId 为 `"s_main"`，paragraphIndex 保持当前语义不变，实现向后兼容。

## 六、向后兼容策略

旧的 Article 模型是 Document 的一个退化实例：

```js
// 旧 Article → 新 Document 映射
{
  id:             article.id,
  title:          article.title,
  author:         null,
  format:         "paste",            // 保守默认值
  coverUrl:       null,
  lang:           "en",
  sections: [
    {
      id:        "s_main",
      heading:   null,
      depth:     0,
      parentId:  null,
      order:     0,
      body: {
        text:      article.text,
        markdown:  article.markdown,
        wordCount: article.wordCount,
      },
    },
  ],
  totalWordCount: article.wordCount,
  sectionCount:   1,
  createdAt:      article.createdAt,
  updatedAt:      article.updatedAt || null,
}
```

旧 bookmark 的 `sectionId` 为 null 时，代码中处理为 `sectionId ?? "s_main"`。

旧 reading_marks 的 `sectionId` 同理。`completedSections` 为空数组时，若 `reading_marks.completed = true`，视为全文完成。

## 七、决策范围

### 已确认
- 统一 Document 模型的字段定义和类型约束
- sections 的平铺结构与 depth + parentId 方案
- body 之间的独立互斥关系
- 下游引用的三级索引方案（documentId + sectionId + paragraphIndex）
- 向后兼容的映射规则

### 暂不确认（属于后续设计规范的范围）
- 数据库 schema 的具体 ALTER 语句
- 各提取格式到 Document 的精确映射规则
- 提取器接口的精确类型签名
- 分段实施的具体阶段拆解

---

## 八、实施约束

基于本决策，后续设计与实施工作应遵循以下约束：

1. 新增或修改的上游功能（导入、提取），以 Document 作为唯一输出目标类型
2. 下游功能（渲染、收藏、进度、回顾）逐步从 `articleId + paragraphIndex` 迁移到 `documentId + sectionId + paragraphIndex`
3. `Article` 类型名逐步废弃，统一使用 `Document`
4. 不再新增对旧模型（扁平 Article）的强依赖
5. 所有提取器只负责从原始格式提取 structure 和 content，不负责生成系统内部 ID 或计算 wordCount
6. 提取结果与 Document 之间的装配由一个统一的工厂函数完成

---

## 九、复审条件

若出现以下任一情况，应重新评估当前模型：

1. 需要支持 section 内部的子层级嵌套超过 3 层且语义不可降级
2. 需要独立管理某个 section（如将一篇文章的某一节单独分享或发布）
3. sections 数组大小接近 JSONB 字段上限
4. 出现需要单独查询某个 section 而不加载整个文档的稳定需求

---

## 十、总结

本次决策的核心结论是：

> **以平铺 sections + depth + parentId 替代嵌套结构，建立统一的 Document 模型。这个模型让一篇 URL 文章（1 个 section）、一本 EPUB（N 个 section）、一段粘贴文本（1 个 section）收敛到同一个数据结构，让渲染层、收藏系统、进度跟踪、回顾系统的升级有明确的类型边界和语义约束。**
