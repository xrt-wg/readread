## 二、结构性调整

### 2.1 EPUB 提取器：用 epub2MD 替代手写方案

**原方案**（03_分段实施计划 任务 1.4）：

```
JSZip 解压 → container.xml → .opf → spine → toc.ncx/nav.xhtml
→ 每章 XHTML → DOMParser → Readability → Turndown → Section
```

**问题**：这条链路的 JSZip→OPF→Spine→TOC 部分是纯 EPUB 协议解析，与 ReadRead 的业务无关。四个开源项目中，epub2MD 已经完美解决了这个问题，且输出天然结构化。

**改进方案**：

```
npm install epub2md
→ epub2md.parseEpub(fileBuffer)
  ├── structure.opf.metadata  → Document.title, author, language
  ├── structure.toc.tree      → 遍历递归树 → depth + parentId + order
  ├── sections[].toMarkdown() → Section.body.markdown
  └── manifest cover image    → base64 (max 300px) → Document.coverUrl
```

**收益**：
- 删除 ~300 行 EPUB 协议解析代码（JSZip、OPF、spine、toc.ncx 解析）
- 适配层约 50 行（TOC 树遍历 + 字段映射）
- TOC 层级从原始 XML 读取，100% 准确（vs Marker 的"转 PDF 再 OCR 重建标题"）
- MIT 许可，TypeScript，浏览器端直接可用
- 内置中英文 autocorrect（中文用户友好）
- 图片 base64 嵌入原生支持

**实施**：将原任务 1.4 替换为：

> **任务 1.4：epub2MD 适配器**
>
> 1. `npm install epub2md`
> 2. 创建 `src/services/extractors/epubExtractor.js`：
>    - `epub2md.parseEpub(fileBuffer)` → Epub 对象
>    - 遍历 `Toc.tree`（递归） → 为每个 TocItem 分配 `depth`、`parentId`、`order`
>    - 通过 `sectionId` 关联 TocItem 和 Section → 填充 `heading`
>    - 调用 `section.toMarkdown()` → `body.markdown`
>    - 从 `structure.opf.metadata` → `meta.title`、`meta.author`、`meta.language`
>    - 提取封面图（通过 OPF manifest 中 `<meta name="cover">` 定位）→ 缩放到 300px → base64 → `meta.coverUrl`
>    - 返回 `ExtractionResult { meta, sections }`
> 3. 在 `EXTRACTORS` 注册表中注册
> 4. ImportPage 文件上传接受列表增加 `.epub`

### 2.2 移除 Phase 4（PDF 实验性支持）

**原方案**：Phase 4 独立实现 PDF 提取（pdfjs-dist + 启发式标题检测 + 坐标聚类）。

**移除理由**：

1. **需求未验证**：当前没有数据表明 ReadRead 用户需要阅读 PDF。在 EPUB 支持上线前，投入 PDF 提取是解决一个可能不存在的问题。
2. **质量不可达**：纯前端 pdfjs-dist + 启发式标题检测对双栏论文、扫描版、技术书的提取质量极差。Marker（Python+GPU）是唯一能达到可接受质量的方案，但它不能跑在浏览器端。
3. **正确的验证路径**：EPUB 上线后，观察用户是否主动要求 PDF 支持。如果需求被验证，先做可行性 spike（5 本真实 PDF → pdfjs-dist 提取 → 评估质量），根据结果决定是"纯前端够用"还是"必须上 Marker 后端"。

**保留内容**：
- `DocumentFormat` 类型联合中保留 `'pdf'`（类型层面预留）
- `EXTRACTORS` 注册表保留 `pdf` 键位（值为 `null` 或抛出"即将支持"）
- pdfjs-dist 的动态 import 延迟加载策略（未来复用）

**从实施计划中删除**：
- Phase 4 全部任务
- 实施后审核清单第六节（Phase 4 审核）
- 阶段依赖关系图中 Phase 4 节点

## 三、Phase 0 增强：扩展性锚点

以下修改成本为零（纯类型定义或配置），确保未来引入后端提取服务时不需要修改数据模型。原生阅读器路线已被否决，不再为之预留扩展。

### 3.1 ExtractorInput 增加 buffer 类型

**当前设计**（02_设计与规范 8.2）：

```ts
type ExtractorInput =
  | { type: 'url', url: string }
  | { type: 'file', file: File }        // File 是浏览器 API
  | { type: 'text', text: string, title?: string }
```

**问题**：`File` 类型是浏览器特有。如果未来引入后端提取服务，后端接收的是文件路径或 buffer。用 `File` 会阻止 Extractor 接口在后端复用。

**改进为**：

```ts
type ExtractorInput =
  | { type: 'url', url: string }
  | { type: 'buffer', buffer: ArrayBuffer, fileName: string, mimeType: string }
  | { type: 'text', text: string, title?: string }
```

前端：`file.arrayBuffer()` → `{ type: 'buffer', buffer, fileName: file.name, mimeType: file.type }`
后端：文件系统读取 → `{ type: 'buffer', buffer, fileName, mimeType }`

### 3.2 Document.format 枚举保留未来格式

```ts
type DocumentFormat = 'url' | 'epub' | 'pdf' | 'paste' | 'markdown' | 'html'
//                          ↑ 实现    ↑ 预留    ↑ 现有
```

`'pdf'` 保留在类型定义中，即使 Phase 4 被移除。这确保当 PDF 需求被验证时，类型系统不需要修改。

### 4.1 localStorage 数据迁移（原审核 1.2）

**新增任务 0.5：localStorage 数据回填**

```js
// 应用启动时检测并自动升级
function migrateLocalStorageArticles() {
  const articles = articleStore.getAll()
  const needsMigration = articles.some(a => !a.sections)

  if (!needsMigration) return

  const migrated = articles.map(a => a.sections ? a : migrateArticleToDocument(a))
  writeJSON(KEYS.ARTICLES, migrated)
}

// bookmark 字段保持扁平——sectionId/paragraphIndex/charOffset 不变，
// 仅补充 sectionHeading（旧数据为 null，读取时通过 resolveSectionHeading 回退）
```

**完成标志**：匿名用户升级后，已有文章正常加载、收藏正常展示、阅读进度正常恢复。

### 4.2 导出格式版本升级（原审核 3.3）

### 4.4 ID 前缀策略显式声明（原审核 2.1）

在 `02_设计与规范.md` 增加：

> **ID 前缀策略**：现有文章的 ID（`art_` 前缀）保持不变。新创建的文章使用 `doc_` 前缀。`documentId` 字段接受任一种前缀，不做批量重命名。`migrateArticleToDocument()` 保留原始 `id` 不变。

### 4.5 `sourceType`/`sourceUrl` 映射（原审核 2.2）

决策：
- `sourceType` → `format` 映射表：

  | sourceType | format |
  |-----------|--------|
  | `'manual'` + 无文件 | `'paste'` |
  | `'manual'` + .md 文件 | `'markdown'` |
  | `'manual'` + .html 文件 | `'html'` |
  | `'url'` | `'url'` |

- `sourceUrl` → 保留为 Document 可选字段 `sourceUrl?: string | null`，在数据库 `articles` 表中保留 `source_url` 列。
- 迁移时 `source_url` 不解构为 `format`，仅作为元信息保留。

### 4.6 `ExtractionSection` 移除 `parentId`（原审核 2.3）

**改进**：

```ts
// 改前
interface ExtractionSection {
  heading: string | null
  depth: number
  parentId: string | null    // ← 移除
  order: number
  body: { text: string, markdown: string | null }
}

// 改后
interface ExtractionSection {
  heading: string | null
  depth: number
  order: number
  body: { text: string, markdown: string | null }
}
```

`parentId` 在 `createDocument()` 工厂函数中根据 depth 推导：

```js
function deriveParentIds(sections) {
  const stack = []  // 记录最近的各级父节点
  for (const section of sections) {
    while (stack.length > 0 && stack[stack.length - 1].depth >= section.depth) {
      stack.pop()
    }
    section.parentId = stack.length > 0 ? stack[stack.length - 1].id : null
    stack.push(section)
  }
}
```

这和 `buildTocTree` 算法的逻辑一致。

### 4.7 封面图存储方案修正（原审核 1.1）

**改前**：EPUB 封面 → Blob URL → 存入 `coverUrl`

**改后**：EPUB 封面 → Canvas 缩放 (max 300px) → `data:image/jpeg;base64,...` → 存入 `coverUrl`

在 epub2MD 适配层中实现（约 15 行）。单张封面 base64 通常 15-30KB，对 JSONB 可接受。

### 4.8 `completedSections` 语义补充（原审核 1.3）

增加明确定义：

> - 用户在某 section 的阅读进度 >= 90% 时，该 sectionId 加入 `completedSections`
> - 用户回到已完成的 section 重新阅读时，从 `completedSections` 中移除
> - "全文完成" = `completedSections.length === document.sectionCount`
> - 用户显式点击"标记已读完"时，所有 sectionId 加入 `completedSections` 且设置 `completed = true`

### 4.9 `lang` 字段默认值修正（原审核 4.2）

默认值从 `'en'` 改为 `'auto'`。当 `'auto'` 时，后续可根据 `navigator.language` 或文本内容推断。

### 4.10 数据库字段命名一致性声明（原审核 4.5）

在规范中显式声明：
> JSONB `sections` 内部字段使用 `camelCase`（与 JS 端对象属性一致）。数据库列名使用 `snake_case`（与 PostgreSQL 惯例一致）。`mapArticleRow` 负责 `snake_case` ↔ `camelCase` 转换，sections JSONB 内部不做转换。

## 十、总结

原实施计划的**阶段顺序、回滚策略、总体原则是正确的**，本次改进建议聚焦于：

| 类别 | 改动 | 动机 |
|------|------|------|
| **技术方案** | EPUB 用 epub2MD 替代手写 JSZip | 省代码、高准确、MIT 许可 |
| **范围** | 移除 PDF Phase 4 | 需求未验证，提取质量不可达 |
| **设计修正** | `ExtractionSection` 去掉 `parentId`，工厂推导 | 修复 ID 引用断裂 |
| **设计修正** | 封面图 Blob URL → base64 | 修复不可持久化缺陷 |
| **扩展性** | ExtractorInput buffer 类型 + format 枚举预留 | 零成本，后端可复用 |
| **遗漏补充** | localStorage 迁移、导出 v2、JSDoc 方案 | 审核反馈中指出的缺失 |
| **语义补充** | `completedSections` 精确语义、ID 前缀策略、`lang` 默认值 | 规范完善 |

核心不变：**平铺 sections + depth + parentId 的 Document 模型，按 Phase 0→1→2→3 从底层向上层推进，每个阶段以"单 section 文档行为不变"为回退底线。**
