## 一、致命问题（必须在 Phase 0 启动前解决）

### 1.1 Blob URL 作为 coverUrl 的持久化方案不成立

**问题**：[02_设计与规范.md](02_设计与规范.md) 第 50-51 行定义 `coverUrl` 为 "封面图 URL 或 Blob URL"，EPUB 提取规范（第 389 行）写 "封面图（如有）→ Blob URL 存入 document.coverUrl"。

**实际约束**：Blob URL (`blob:https://...`) 仅在创建它的浏览器会话中有效。一旦存入数据库并在后续会话中读取，Blob URL 将指向一个已释放的内存对象，图片无法加载。

**建议**：二选一：
- **方案 A（推荐）**：EPUB 封面提取为 base64 data URL 存入 `coverUrl`（图片通常 50-200KB，对 JSONB 可接受但偏大；考虑单独存储或限制尺寸）
- **方案 B**：将封面图上传至 Supabase Storage，`coverUrl` 存储公开访问 URL

无论哪种方案，都应在阶段实施计划中增加对应的处理逻辑和存储空间评估。

---

### 1.2 localStorage 数据迁移完全缺失

**问题**：设计文档的 Phase 0 数据库迁移只覆盖了 Supabase（PostgreSQL），完全没有提到 localStorage 路径。但实际代码中：

- [storage.js:114-144](src/store/storage.js) `articleStore` 使用 `localStorage` 读写 articles
- [storage.js:148-181](src/store/storage.js) `bookmarkStore` 同上
- [storage.js:185-227](src/store/storage.js) `readingMarkStore` 以 `articleId` 为 key 的字典结构
- [library.js:9-11](src/services/library.js) 通过 `useCloudSource()` 判断走哪条路径——未登录用户完全依赖 localStorage

**影响**：
- 未登录用户的 articles 缺少 `sections`、`format`、`author` 等新字段，library.js 的 `mapArticleRow` 读取时这些字段为 `undefined`
- `readingMarkStore` 的 key 是 `articleId`（如 `art_1718000000_a3f2b`），升级后 key 不变（设计说保持向后兼容），但内部结构从 `{ articleId, paragraphIndex, completed }` 变为 `{ documentId, sectionId, paragraphIndex, completedSections, completed }`，需要在读取端做兼容

**建议**：
1. Phase 0 增加 **任务 0.5：localStorage 数据回填**——在应用启动时检测旧格式数据并自动升级
2. `mapArticleRow`（本地路径走 `articleStore.getAll()`）返回的数据也需要包装为 Document 结构
3. 或者：本地路径也走 `migrateArticleToDocument()` 统一转换

---

### 1.3 reading_marks 表的主键约束与多 section 进度跟踪矛盾

**问题**：当前 [reading_marks 表 DDL](supabase/migrations/20260509170000_create_core_user_tables.sql) 的主键是 `(user_id, article_id)`——每个用户每篇文章只有一条记录。

设计文档 [02_设计与规范.md](02_设计与规范.md) 第 253-273 行定义的 `ReadingProgress` 包含：
- `sectionId: string | null` —— 当前阅读所在的单个 section
- `completedSections: string[]` —— 已读完的 section 列表

**矛盾**：`completedSections` 存储在单条记录中，这意味着每篇文章仍然只有一条 reading_mark 记录。但设计同时说 `sectionId` 记录当前 section，且 `completedSections` 跟踪各 section 完成状态。这里有两个语义问题：

1. `sectionId` 是"当前正在读的 section"，同一时刻只有一个——这在单条记录模型下是自洽的
2. `completedSections` 是一个数组，记录"已读完的 section 列表"——也在单条记录下自洽

**这个设计是自洽的，但有一个边界情况需要明确**：如果用户读完 section A（加入 completedSections），开始读 section B（sectionId = B），然后又回到 section A 读了一段——此时 completedSections 是否应该移除 A？设计文档没有定义"未完成"的语义。

**建议**：在规范中补充 `completedSections` 的精确语义：
- 哪些操作会向 `completedSections` 添加 sectionId？
- 哪些操作会从 `completedSections` 移除 sectionId？
- "全文完成" 的定义是 `completedSections.length === document.sectionCount` 还是用户显式标记？

## 二、高优先级问题（Phase 0/1 实施前需要决策）

### 2.1 ID 前缀变更策略不明确

**问题**：当前代码库使用 `art_` 前缀（[storage.js:263](src/store/storage.js)），设计文档的工厂函数使用 `doc_` 前缀（[02_设计与规范.md:635](02_设计与规范.md)）。

**影响**：
- 现有 bookmarks 的 `articleId` 指向 `art_xxx`，如果新文章用 `doc_xxx`，新旧 ID 共存
- 设计文档的解决方式是 `documentId` 字段"即原来的 articleId"，说明不打算重命名已有 ID——这是正确的
- 但文档没有明确说明这个策略，实施者可能误以为需要批量重命名

**建议**：在设计文档中显式声明：
> 现有文章的 ID（`art_` 前缀）保持不变。新创建的文章使用 `doc_` 前缀。`documentId` 字段接受任一种格式。不做批量 ID 重命名。

---

### 2.2 `sourceType` / `sourceUrl` 与 `format` 的映射关系未定义

**问题**：当前数据库有 `source_type` 和 `source_url` 两个字段（[library.js:5](src/services/library.js)），设计文档用 `format` 替代了 `sourceType`，但没有提及 `sourceUrl` 的去留。

当前 `source_type` 的可能值（从代码推断）：
- `'manual'` — 粘贴/手动输入
- `'url'` — URL 导入（对应 `source_url`）

设计文档的 `format` 枚举：`'url' | 'epub' | 'pdf' | 'paste' | 'markdown' | 'html'`

**问题**：
1. `sourceType: 'manual'` 映射到 `format: 'paste'` 还是 `format: 'markdown'`？当前粘贴入口可以粘贴纯文本或 Markdown，而文件入口可以上传 `.md` / `.html`
2. `sourceUrl` 字段在 Document 模型中没有对应项——是删除、合并到其他字段、还是保留？

**建议**：
1. 明确 `sourceType` → `format` 的映射表
2. 决定 `sourceUrl` 的去留：建议保留为 Document 的可选字段（用户可能想知道原文来自哪个 URL），或在迁移时将其丢弃
3. 若保留，需在 Document 接口和数据库 schema 中增加 `sourceUrl` 字段

---

### 2.3 `ExtractionSection.parentId` 的 ID 引用问题

**问题**：[02_设计与规范.md](02_设计与规范.md) 第 578-587 行定义的 `ExtractionSection` 包含 `parentId: string | null`，但 `ExtractionSection` 本身没有 `id` 字段。ID 是由工厂函数 `createDocument` 按数组索引分配的（`s_${i}`）。

这意味着提取器在生成 `ExtractionSection` 时，需要用一个**临时 ID 方案**来设置 `parentId`，然后工厂函数需要将临时 ID 映射为最终 ID。

**举例**：EPUB 提取器发现 "1.1 Installation" 是 "Chapter 1" 的子节。提取器用 `parentId: "ch1"` 标记，但工厂函数最终分配的 ID 是 `s_3`。工厂函数需要知道 `"ch1"` 对应 `s_2`，并把 `s_3.parentId` 设为 `"s_2"`。

**建议**：两种修复方式任选其一：
- **方案 A**：提取器同时输出临时的 `id` 字段，工厂函数建立 `tempId → finalId` 映射，替换所有 `parentId` 引用
- **方案 B**：提取器不设置 `parentId`，只设置 `depth` 和 `order`；工厂函数根据 depth 推导 parentId（利用"最近的 depth 更小的 section 是父节点"规则）

方案 B 更简单，且与 TOC 推导算法逻辑一致。建议采用方案 B，从 `ExtractionSection` 中移除 `parentId`，在工厂函数中推导。

---

### 2.4 项目是纯 JavaScript，设计文档全部使用 TypeScript

**问题**：三份设计文档大量使用 TS 语法（`interface`、`type`、`DocumentFormat` 类型联合等），但当前项目是纯 JS（`.js` / `.jsx`），无构建工具。

这不是阻止问题，但需要在实施计划中增加一个决策：
- 是否引入 TypeScript？（会增加构建复杂度）
- 或使用 JSDoc 注释达到类型提示效果？（零成本，工具支持好）
- 或保持纯 JS，类型仅作为文档参考？

**建议**：考虑到项目规模和"构建期"阶段定位，建议采用 **JSDoc 方案**：
```js
/**
 * @typedef {Object} Document
 * @property {string} id
 * @property {string} title
 * @property {string|null} author
 * @property {'url'|'epub'|'pdf'|'paste'|'markdown'|'html'} format
 * ...
 */
```
在 Phase 0 的实施计划中显式声明类型表达方式。

## 三、中优先级问题（建议在实施中注意）

### 3.1 `sectionHeading` 冗余字段的陈旧风险

**问题**：[02_设计与规范.md](02_设计与规范.md) 第 226-229 行：bookmark 中存储 `sectionHeading` 作为冗余字段，"写入时从 section.heading 同步"。

**风险**：如果用户编辑了文档的 section 标题（未来功能），已有 bookmarks 中的 `sectionHeading` 会过时。虽然当前没有编辑功能，但冗余字段的设计应注明陈旧处理策略。

**建议**：在规范中增加说明：
> `sectionHeading` 是创建时的快照。如果 section.heading 后续被修改，已存在的 bookmark 不会自动更新。回顾面板展示时优先使用 `sectionHeading`，若为空则回退到查询 section.heading。

当前代码库中 `resolveSectionHeading` 函数（[02_设计与规范.md:552-557](02_设计与规范.md)）已实现了这个回退逻辑，只需要在规范文本中显式声明陈旧策略。

---

### 3.2 paragraphIndex 语义变更的渲染层影响被低估

**问题**：设计文档假设 paragraphIndex 从"全局索引"变为"section 内局部索引"是一个简单的切换。但从实际代码来看：

- [ReaderPage.jsx:45-174](src/components/ReaderPage.jsx) 的 `MarkdownContent` 使用 `useRef` 计数器 `paraIdxRef`，在每次渲染时从 0 开始递增
- 切换到 section 局部索引后，每个 section 独立渲染，自然从 0 开始——这个是自洽的
- **但**：当前 bookmarks 存储的是全局 paragraphIndex（旧数据），迁移后这些值需要重新计算或标记为兼容模式

**建议**：在 Phase 2 实施计划中增加一个任务：
> **任务 2.0：旧 bookmark paragraphIndex 兼容处理**
> 对 `sectionCount === 1` 的文档，bookmark.paragraphIndex 保持原值不变。对 `sectionCount > 1` 的新文档，bookmark.paragraphIndex 是 section 内局部索引。渲染时通过 `data-para-index` 分配的值与存入 bookmark 的值一致。

---

### 3.3 备份数据版本管理

**问题**：[storage.js:231-257](src/store/storage.js) 当前导出格式 `version: 1`。引入 Document 模型后：
- 导出数据将包含 `sections`、`format`、`author` 等新字段
- 旧版导出的 articles 不含这些字段

**建议**：
1. 在 Phase 0 中升级导出版本号为 `2`
2. 导入时检测 version：version 1 的旧格式 → 先用 `migrateArticleToDocument` 升级再写入；version 2 直接写入
3. 在设计文档中增加版本兼容矩阵

---

### 3.4 `listAllBookmarks` 在 ReviewModal 中的使用

**问题**：[ReviewModal.jsx:278](src/components/ReviewModal.jsx) 使用 `listAllBookmarks()` 获取全部书签并随机抽取 10 张。当前 ReviewModal **不展示** 书签所属文章的信息。设计文档 [02_设计与规范.md](02_设计与规范.md) 第 278-293 行的回顾面板展示包含 `sectionHeading`（如 "Chapter 3 · 第 12 段"）。

**这意味着**：ReviewModal 需要加载 bookmarks 对应的 document 信息来展示章节来源。当前 ReviewModal 不依赖 article 数据，这个改动会增加一次批量查询。

**建议**：在 Phase 3 的回顾面板适配任务中增加：
> 回顾面板需要加载书签对应的 Document 信息（至少 `sections` 数组），以便展示 `sectionHeading`。考虑在加载书签时预取关联的 document metadata，或按需懒加载。

---

### 3.5 单 section 文档中 heading 的处理

**问题**：当前所有文章（URL 导入、粘贴文本）在迁移后都是单 section 文档，`heading: null`。设计文档的向后兼容策略使用 `sectionId: "s_main"`。这个是正确的。

但设计文档对"单 section 文档的 heading 是否可为 null"没有明确表态。按照规范，heading 为 null 表示"无标题"，这对单 section 是正确的。但如果用户粘贴一段带 `# 标题` 的 Markdown，是否应该把 `# 标题` 提取为 section heading？

**建议**：在格式映射规范中明确：
> 单 section 文档（URL 导入、粘贴文本）的 heading 始终为 null。即使内容中包含 `# 标题`，也不提取为 section heading——因为单 section 文档的 title 已经承担了标题的语义角色。仅当内容中存在多个 `##` 级别标题且切分为多个 section 时，heading 才非 null。

## 四、低优先级建议（可在实施中按需采纳）

### 4.1 TOC 算法对 sections 顺序的隐含依赖

[02_设计与规范.md](02_设计与规范.md) 第 669-692 行的 `buildTocTree` 算法使用 depth 栈推导树结构。它**不依赖** `parentId` 字段，但**隐含假设** sections 数组是文档序（深度优先遍历序）。如果 sections 的 order 被打乱，TOC 树会错误。

**建议**：在算法注释中显式声明：
> 前提：sections 数组必须按文档顺序排列（即 sections[i] 在文档中出现在 sections[i-1] 之后）。算法利用 depth 的增减判断父子关系。

---

### 4.2 `lang` 字段默认值

`lang` 默认值为 `'en'`（[02_设计与规范.md:56](02_设计与规范.md)），但这是一个面向中文用户的阅读工具。对粘贴的中文文本标记为 `lang: 'en'` 可能影响未来的语言相关功能。

**建议**：默认值改为 `'auto'` 或根据浏览器 `navigator.language` 推断，或允许为 `null`（未知）。

---

### 4.3 EPUB 内嵌图片处理的范围界定

Phase 1 的任务 1.4 说"第一阶段不处理图片，仅提取文本"。但 EPUB 中的图片可能包含关键内容（技术书籍的截图、图表）。如果全部丢弃，阅读体验会下降。

**建议**：在任务描述中增加：
> 第一阶段提取文本时，在图片位置插入占位标记（如 `[Image: alt_text]`），保留图片的语义信息，为后续图片支持留下扩展点。

---

### 4.4 PDF 提取的投入产出比

Phase 4 独立于主路径，这是正确的。但 PDF 提取的复杂度可能被低估：
- pdfjs-dist ~2MB gzip
- 双栏 PDF、扫描版 PDF、表格 PDF 的文本提取质量极差
- 标题检测的启发式规则（字号/居中/加粗）在不同 PDF 中表现差异巨大

**建议**：Phase 4 在启动前先做一个 **可行性 spike**：用 pdfjs-dist 对 5 本不同类型的 PDF（小说、技术书、论文、双栏杂志、扫描版）提取文本，评估提取质量。如果小说和技术书的效果可接受（>90% 准确），再正式进入 Phase 4。否则，考虑将 PDF 支持降级为"建议用户先转换为 EPUB/Markdown"。

---

### 4.5 数据库字段命名一致性

当前数据库使用 `snake_case`（`word_count`, `source_type`, `created_at`），JS 端使用 `camelCase`。新增 JSONB `sections` 字段内部使用 `camelCase`（`parentId`, `wordCount`）。

**建议**：在选择 JSONB 内部字段命名时，要么统一用 camelCase（与 JS 端一致），要么统一用 snake_case（与数据库其他列一致）。目前用 camelCase 是合理的选择（因为 sections 主要在 JS 端操作），但应在规范中显式声明。

## 五、实施计划整体评估

### 阶段顺序：✅ 正确

Phase 0 → 1 → 2 → 3 → 4 的依赖关系分析准确。从类型层到底层到视图层的顺序避免了"先建 UI 再填数据"的反模式。

### 阶段切换条件：⚠️ 需补充

## 六、总结

三份文档的设计方向是正确的——平铺 sections 方案在表达能力和实现复杂度之间取得了恰当的平衡。方案的核心理由（"让 95% 的单层内容保持简单，让 5% 的多层内容可用"）在审核代码后得到了进一步验证。

在进入实施前，必须解决的三个致命问题：

| # | 问题 | 影响 |
|---|------|------|
| 1 | Blob URL 无法持久化 | EPUB 封面图功能不可用 |
| 2 | localStorage 迁移缺失 | 未登录用户数据损坏 |
| 3 | `ExtractionSection.parentId` ID 引用断裂 | 提取器无法正确标记父子关系 |

加上 2.1-2.4 的高优先级决策点，在 Phase 0 启动前需要一个补充设计回合来处理这些问题。建议更新 `02_设计与规范.md` 和 `03_分段实施计划.md` 后再开始写代码。
