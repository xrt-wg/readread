#### 任务 0.5：创建 score 更新触发器

创建 migration 文件 `{timestamp}_create_score_update_trigger.sql`：

```sql
CREATE OR REPLACE FUNCTION public.update_recommendation_score()
RETURNS trigger
LANGUAGE plpgsql
AS $$
DECLARE
  target_id text;
BEGIN
  -- DELETE 时 NEW 为 NULL，使用 OLD.submission_id
  target_id := COALESCE(NEW.submission_id, OLD.submission_id);
  UPDATE public.recommendation_submissions
  SET recommend_score = public.compute_recommendation_score(target_id)
  WHERE id = target_id;
  RETURN COALESCE(NEW, OLD);
END;
$$;

CREATE TRIGGER trg_rec_ratings_update_score
  AFTER INSERT OR UPDATE OR DELETE ON public.recommendation_ratings
  FOR EACH ROW
  EXECUTE FUNCTION public.update_recommendation_score();
```

#### 任务 0.6：创建 SECURITY DEFINER RPC 函数

创建 migration 文件 `{timestamp}_create_recommendation_rpc_functions.sql`，包含 3 个 RPC 函数（完整定义见 `02_设计与规范.md § 八点五`）：

1. **`get_import_item_for_recommendation(p_import_item_id)`** — 跨用户读取 import_item 完整数据。安全门控：仅当存在活跃推荐条目时才允许读取。
2. **`increment_recommendation_add_count(p_submission_id, p_user_id)`** — 从 `import_items` 表实时计算 `COUNT(DISTINCT user_id)` 作为权威 add_count 值，同时更新 `recommend_score`。
3. **`check_import_item_reading_completed(p_import_item_id, p_user_id)`** — 单 SQL JOIN 查询验证用户是否已完成对某 import_item 对应文章的阅读。

均使用 `SECURITY DEFINER SET search_path = public`，与项目现有 `delete_import_item`、`soft_delete_article` 模式一致。`GRANT EXECUTE TO authenticated`。

#### 任务 0.7：配置 RLS + GRANT

在任务 0.2 和 0.3 的 migration 文件中已包含。此处单独列出以强调验证：

- `recommendation_submissions`：anon 可 SELECT active 条目 ✅
- `recommendation_submissions`：authenticated 可 INSERT/UPDATE 自己的提交 ✅
- `recommendation_ratings`：anon 可 SELECT ✅
- `recommendation_ratings`：authenticated 可 INSERT/UPDATE 自己的评分 ✅

#### 任务 0.8：staging 环境验证

- 在 staging 执行全部 migration（含 RPC 函数）
- 验证跨用户隔离（用户 A 无法 UPDATE 用户 B 的 submission）
- 验证匿名可读（anon key 可 SELECT active 条目）
- 验证 score 触发器（INSERT rating → score 自动更新；DELETE rating 下 COALESCE(NEW, OLD) 正确）
- 验证 RPC 函数（跨用户读取 import_item、add_count 计算正确性、原子更新）
- 验证 origin 扩展（四个值均可 INSERT）

### 本阶段不要求完成的事情

- 任何服务层代码
- 任何前端 UI
- 任何旧数据迁移

### 完成标志

- [ ] `import_items.origin` CHECK 约束扩展为 4 个值
- [ ] `recommendation_submissions` 表创建成功，所有约束和索引生效
- [ ] `recommendation_ratings` 表创建成功，联合 PK 生效
- [ ] `compute_recommendation_score()` 函数可用，STABLE 标记正确
- [ ] score 更新触发器：INSERT/UPDATE/DELETE rating 后 score 自动更新（DELETE 场景 COALESCE 正确）
- [ ] 3 个 RPC 函数（get_import_item_for_recommendation / increment_recommendation_add_count / check_import_item_reading_completed）可用，SECURITY DEFINER 权限正确
- [ ] RLS：匿名可读 active 条目，已登录用户可提交/评分
- [ ] GRANT：anon 有 SELECT，authenticated 有 INSERT/UPDATE，RPC 函数 GRANT EXECUTE 正确
- [ ] 现有功能（书架 CRUD、移入、阅读、收藏、回顾）未受影响

### 风险点

| 风险 | 应对 |
|------|------|
| RLS 策略配置错误导致推荐条目不可见 | staging 用 anon key 测试 `SELECT * FROM recommendation_submissions WHERE status='active'` |
| origin 约束变更后现有数据有非法值 | 变更前 `SELECT DISTINCT origin FROM import_items` 确认仅 'imported'/'shared' |
| score 触发器循环调用 | 触发器仅作用于 recommendation_ratings，UPDATE recommendation_submissions 不触发自身触发器 |
| 多个 migration 文件顺序依赖 | 按时间戳命名确保顺序：先 origin 扩展 → 建表 → 函数 → 触发器 → RPC 函数 |
| RPC 函数安全门控不够严格 | `get_import_item_for_recommendation` 内部校验活跃推荐条目存在性；`increment_recommendation_add_count` 校验 submission 状态为 active |

### 回滚策略

```sql
-- 按反向顺序回滚
DROP TRIGGER IF EXISTS trg_rec_ratings_update_score ON public.recommendation_ratings;
DROP FUNCTION IF EXISTS public.update_recommendation_score();
DROP FUNCTION IF EXISTS public.get_import_item_for_recommendation(text);
DROP FUNCTION IF EXISTS public.increment_recommendation_add_count(text, uuid);
DROP FUNCTION IF EXISTS public.check_import_item_reading_completed(text, uuid);
DROP FUNCTION IF EXISTS public.compute_recommendation_score(text);
DROP TABLE IF EXISTS public.recommendation_ratings CASCADE;
DROP TABLE IF EXISTS public.recommendation_submissions CASCADE;
-- origin 约束恢复
ALTER TABLE public.import_items DROP CONSTRAINT IF EXISTS import_items_origin_check;
ALTER TABLE public.import_items ADD CONSTRAINT import_items_origin_check CHECK (origin IN ('imported', 'shared'));
```

## 五、Phase 2：旧数据迁移

### 阶段目标

### 核心任务

#### 任务 2.1：创建 system 账号

在 `public.profiles` 表中插入 system 账号：

```sql
INSERT INTO public.profiles (user_id, username)
VALUES ('00000000-0000-0000-0000-000000000000', 'system')
ON CONFLICT (user_id) DO NOTHING;
```

注意：此操作需要 service_role 权限（Supabase 管理后台执行或 migration 中使用 service_role）。

**替代方案**：在 seed 脚本中使用 Supabase service_role key 直接写入 `import_items`（绕过 RLS）。`import_items` 的 RLS 仅作用于 authenticated 角色，service_role 可绕过。

#### 任务 2.2：种子数据迁移

实现 `migrateLegacyFeaturedArticles()` 函数：

```js
async function migrateLegacyFeaturedArticles() {
  // 1. 读取旧 featured_articles 表
  const legacyArticles = await fetchAllFeaturedArticles()

  // 2. 对每篇旧文章：
  for (const legacy of legacyArticles) {
    // a. 创建 import_item（origin='featured_legacy', user_id=system）
    const importItem = await createLegacyImportItem(legacy)

    // b. 创建 recommendation_submission
    await createLegacySubmission(legacy, importItem.id)
  }

  // 3. 返回迁移计数
  return { migrated: legacyArticles.length, skipped: 0 }
}
```

**迁移字段映射**：

| featured_articles | → | import_items | → | recommendation_submissions |
|----|----|----|----|
| title | → | title | → | title (快照) |
| source | → | source_url (重构) | → | source_url (快照) |
| — | → | author (null) | → | author (null) |
| text + markdown | → | sections (组装为单 section) | → | — |
| description | → | — | → | intro + excerpt (派生) |
| — | → | — | → | keywords (从 source/title 提取) |

- 恢复 `featured_articles` 表需要从备份重建 → Phase 1 时备份旧表数据
- 迁移脚本幂等 → 可安全重新执行

## 十二、延期与回退策略

### 延期原则

- Phase 0 延期 → 阻塞全部后续阶段，优先解决
- Phase 1 延期 → Phase 3 可用 mock 数据做前端预研
- Phase 2 延期 → Phase 3 可用空数据或 mock 推荐数据开发 UI（但需手动创建测试数据）
- Phase 3 延期 → Phase 4 可并行开发（提交 Modal 独立于推荐列表）
- Phase 4 延期 → Phase 5 可并行开发（我的推荐独立于提交 Modal）
- Phase 5 延期 → 不影响核心推荐链路

### 回退原则

**优先局部回退，不优先整体推翻。**

- Phase 0 出问题 → 修补个别 migration，不推翻整体 schema 设计
- Phase 1 出问题 → 修复单个函数，不推翻服务层架构
- Phase 2 出问题 → 保留旧 featured_articles 表（已备份），回退前端数据源
- Phase 3 出问题 → 推荐 Tab 切回旧数据源（若旧表仍在），或 hide 推荐 Tab
- Phase 4 出问题 → 移除提交入口，推荐区退化为只读
- Phase 5 出问题 → 移除管理功能，不影响核心闭环

### 最重要的回退底线

1. **现有书架/阅读区完整功能不被破坏**
2. **旧文章不受任何影响**
3. **阅读、收藏、回顾链路完全不变**
4. **推荐区回滚不影响用户已加入书架的内容**（已加入的 import_items 独立存在）

## 十三、总结

执行计划的核心结论：

- 按 **"Phase 0（数据库）→ Phase 1（服务层）→ Phase 3a（前端双数据源）→ Phase 2（迁移 + DROP）→ Phase 3b（移除 fallback）→ Phase 4-5（前端完善）"** 的顺序推进
- Phase 0 新增 8 个任务——确保 schema + RPC 函数正确是后续一切的前提
- Phase 1 新增 4 个任务——服务层是整个推荐链路的骨干
- **Phase 3a 先于 Phase 2 部署**——双数据源（新推荐优先 + 旧 fallback）消除 DROP 表后的报错窗口
- Phase 2 迁移 3 篇种子数据 + 废弃旧表——确认新系统正常后执行
- Phase 3b 移除 fallback——Phase 2 确认无误后的清理步骤
- Phase 3-5 是用户可感知的前端改造——逐步呈现推荐/评分/提交/管理功能
- 推荐系统完全叠加在现有书架/阅读区之上——不修改任何现有数据流
- 每次回滚从推荐系统一侧进行——现有功能永远是安全的
