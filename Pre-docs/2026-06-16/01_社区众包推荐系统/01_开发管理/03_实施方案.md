## 二、总体技术路线

### 2.1 核心策略：以推荐区为新层叠加在书架上

```
现有架构                          新架构
────────                          ────────
import_items 表      ──保持──→    import_items 表 (+ origin 扩展)
articles 表          ──保持──→    articles 表（不变）
reading_marks 表     ──保持──→    reading_marks 表（不变）
featured_articles    ──废弃──→    (DROP)
featuredArticles.js  ──废弃──→    recommendationService.js
                                +
                                recommendation_submissions 表（新增）
                                recommendation_ratings 表（新增）
                                compute_recommendation_score() 函数（新增）
```

推荐系统不穿透现有的书架/阅读区链路——它在书架之上作为**发现层**运行。推荐区读取 import_items（通过快照），产生新的 import_items（通过加入操作），形成闭环但不修改任何现有路径。

**为什么这么做？**
- 书架/阅读区链路已稳定——导入、移入、阅读、收藏、回顾全部正常工作
- 推荐系统的风险（新表、新 RLS 策略、新前端交互）被隔离在新模块中
- 即使推荐系统完全回滚，现有功能零影响

## 三、后端实施路线

### 3.1 为什么先做数据库再做服务层？

与书架区实施相同的理由：
1. 数据库 schema 是硬基础——migration 发布后回滚成本高
2. 服务层代码错了可以修，但 RLS 策略配置错误会导致数据泄露
3. 先在 staging 验证 SQL（建表、约束、索引、RLS、触发器），再写服务层

#### 3.2.3 addRecommendationToBookshelf 的实现细节

这是最关键的操作——它实现了跨用户的内容复制。由于涉及跨用户数据访问（读取提交者的 import_item、更新 recommendation_submissions.add_count），核心步骤通过 SECURITY DEFINER RPC 函数完成。

```js
async function addRecommendationToBookshelf(submissionId, userId) {
  // 1. 获取推荐条目
  const submission = await getSubmissionById(submissionId)
  if (!submission || submission.status !== 'active') {
    throw new Error('该推荐内容当前不可用')
  }

  // 2. 跨用户获取提交者的 import_item（通过 SECURITY DEFINER RPC 绕过 RLS）
  const sourceItemJson = await client.rpc('get_import_item_for_recommendation', {
    p_import_item_id: submission.import_item_id,
  })
  if (sourceItemJson.error) throw sourceItemJson.error
  const sourceItem = mapImportItemRow(sourceItemJson.data)
  if (!sourceItem || sourceItem.deletedAt) {
    throw new Error('原始内容已被删除')
  }

  // 3. 深拷贝 sections（跨用户独立副本）
  const sections = structuredClone(sourceItem.sections)

  // 4. 构造新 import_item
  const importItem = await createImportItem(
    {
      meta: {
        title:     sourceItem.title,
        author:    sourceItem.author,
        format:    sourceItem.format,
        coverUrl:  sourceItem.coverUrl,
        lang:      sourceItem.lang,
        sourceUrl: sourceItem.sourceUrl,
      },
      sections: sections.map(s => ({
        heading:  s.heading,
        depth:    s.depth,
        order:    s.order,
        body: {
          text:     s.body.text,
          markdown: s.body.markdown,
        },
      })),
    },
    {
      userId,
      origin: 'featured',
      shareSourceId: submissionId,
    }
  )

  // 5. 更新 add_count + recommend_score（通过 SECURITY DEFINER RPC 绕过 RLS）
  await client.rpc('increment_recommendation_add_count', {
    p_submission_id: submissionId,
    p_user_id: userId,
  })

  return importItem
}
```

**为什么 add_count 需要在 RPC 中计算？**
- `add_count` 的更新涉及跨用户的 `recommendation_submissions` 行（当前用户不是 submitter，RLS 拒绝 UPDATE）
- 且 `add_count` 的权威值应反映"当前活跃的去重用户数"，而非简单的 `+1`
- RPC `increment_recommendation_add_count` 在数据库层完成：去重检查 → `COUNT(DISTINCT user_id)` 计算真实值 → 原子更新 `add_count` 和 `recommend_score`
- 用户删除书架内容（`deleteImportItem`）时同样调用此 RPC 重新计算

### add_count 减少触发

当用户删除书架上的 import_item（通过 `deleteImportItem` RPC），且该 item 满足 `origin IN ('featured', 'featured_legacy')` 且 `share_source_id` 非空时，前端在 `deleteImportItem` RPC 成功后额外调用 `increment_recommendation_add_count` 更新 add_count：

```js
// 在 handleDeleteImportItem 或等效的删除处理函数中
if (
  deletedItem.origin === 'featured' ||
  deletedItem.origin === 'featured_legacy'
) {
  if (deletedItem.shareSourceId) {
    await client.rpc('increment_recommendation_add_count', {
      p_submission_id: deletedItem.shareSourceId,
      p_user_id: userId,
    })
  }
}
```

**设计说明**：此调用与 `delete_import_item` RPC 不在同一事务中（前端两次请求），但 `add_count` 是缓存字段——短暂的不一致可接受，且下一次加入/删除操作会通过 RPC 内部的 `COUNT(DISTINCT user_id)` 重新计算权威值。

#### 3.2.4 提交资格校验的实现

```js
// recommendationService.js 顶部——硬编码常量，远期可配置化
const WEEKLY_SUBMIT_LIMIT = 1  // 每人每周最多提交推荐数
```

```js
async function checkSubmissionEligibility(userId, importItemId) {
  // 1. 获取 import_item
  const item = await fetchImportItemById(importItemId)
  if (!item) return { canSubmit: false, reason: '素材不存在' }
  if (item.userId !== userId) return { canSubmit: false, reason: '无权操作此素材' }

  // 2. origin 检查
  if (item.origin !== 'imported') {
    return { canSubmit: false, reason: '仅自导入内容可提交推荐' }
  }

  // 3. 检查是否已读完——需要找到对应的 articles + reading_marks
  const isCompleted = await checkReadingCompleted(userId, importItemId)
  if (!isCompleted) {
    return { canSubmit: false, reason: '请先完成阅读后再提交推荐' }
  }

  // 4. 本周提交数检查
  const weeklyCount = await countWeeklySubmissions(userId)
  if (weeklyCount >= WEEKLY_SUBMIT_LIMIT) {
    return { canSubmit: false, reason: `本周已提交 ${weeklyCount}/${WEEKLY_SUBMIT_LIMIT} 篇，下周再来`, weeklyCount }
  }

  // 5. 重复提交检查
  const duplicate = await checkDuplicateSubmission(item)
  if (duplicate) {
    return { canSubmit: false, reason: '该内容已被推荐过' }
  }

  return { canSubmit: true }
}
```

**`checkDuplicateSubmission` 的实现要点**：

```js
async function checkDuplicateSubmission(item) {
  // 去重策略：按 source_url 或 title 匹配已有 active 条目
  if (item.sourceUrl) {
    // 优先按 URL 去重（更精确）
    const { data } = await client
      .from('recommendation_submissions')
      .select('id')
      .eq('source_url', item.sourceUrl)
      .eq('status', 'active')
      .maybeSingle()
    if (data) return true
  }
  // source_url 为 NULL 时，仅按 title 去重
  const { data } = await client
    .from('recommendation_submissions')
    .select('id')
    .eq('title', item.title)
    .eq('status', 'active')
    .maybeSingle()
  return !!data
}
```

**`checkReadingCompleted` 的实现**：

```js
async function checkReadingCompleted(userId, importItemId) {
  // 单条 RPC 查询——避免应用层 N+1 循环
  const { data, error } = await client.rpc('check_import_item_reading_completed', {
    p_import_item_id: importItemId,
    p_user_id: userId,
  })
  if (error) throw error
  return data  // boolean
}
```

此查询在用户自己的数据范围内（articles + reading_marks 都属于调用者），但通过 SECURITY DEFINER RPC 实现以支持跨表的单条 JOIN 查询。

#### 3.2.5 评分资格校验的实现

```js
async function checkRatingEligibility(userId, submissionId) {
  // 1. 用户是否通过该推荐加入过书架？
  const item = await findImportItemByShareSource(userId, submissionId)
  if (!item) return { canRate: false, reason: '你还没有添加这篇推荐内容' }

  // 2. origin 必须为 'featured'
  if (item.origin !== 'featured') return { canRate: false, reason: '仅推荐区内容支持评分' }

  // 3. 是否已读完？
  const isCompleted = await checkReadingCompleted(userId, item.id)
  if (!isCompleted) return { canRate: false, reason: '请先完成阅读后再评分' }

  return { canRate: true }
}
```

#### 3.2.6 错误处理策略

推荐服务层的所有函数统一使用 `isLibraryAccessError` / `resolveLibraryErrorMessage`（已有的 errorUtils.js），确保 RLS 拒绝 / JWT 过期 / 网络错误的提示与书架/阅读区一致。

**新增错误类型**：
- `SUBMISSION_LIMIT_REACHED`：提交限制——在函数返回的 result 对象中通过 `reason` 字段区分，不抛异常（因为这不是一个"错误"，而是一个预期内的业务规则拒绝）
- `DUPLICATE_SUBMISSION`：重复提交——同样通过 `reason` 返回
- `NOT_COMPLETED`：未读完——返回 `reason`

**设计决策**：业务规则拒绝不抛异常，而是返回 `{ canSubmit: false, reason }` 结构。只有真正的系统错误（网络、权限、数据库）才抛异常。这避免了前端需要用 try-catch 区分业务拒绝和系统故障。

### 4.2 推荐 Tab 改造

#### 4.2.1 当前状态

推荐 Tab 调用 `listFeaturedArticles({ status: 'published' })` 从 `featured_articles` 表读取。展示文章标题、来源、描述、加入书架按钮。

#### 4.2.2 改造后

推荐 Tab 调用 `listRecommendations()` 从 `recommendation_submissions` 表读取。展示内容有本质变化：

- **旧**：管理员写的 description（一行的摘要）
- **新**：提交者写的 intro（介绍）+ keywords（关键词）+ excerpt（摘录）
- **旧**：纯展示
- **新**：展示 + 推荐值 + 评分分布 + 评分交互

#### 4.2.3 新增功能

1. **评分展示**：每个推荐条目卡片底部展示评分分布（推荐 N · 一般 N · 不行 N）
2. **评分交互**：符合条件的用户（通过该推荐加入且已读完）可点击评分按钮
3. **提交推荐入口**：推荐列表顶部或底部的 [提交推荐] 按钮 → 打开 SubmitRecommendationModal

```

```

## 六、技术决策与取舍

### 6.1 add_count 的去重策略

**选择：通过 SECURITY DEFINER RPC 在数据库层保证一致性和原子性。**

```sql
-- RPC increment_recommendation_add_count 内部
SELECT COUNT(DISTINCT user_id) INTO true_count
FROM public.import_items
WHERE share_source_id = p_submission_id
  AND origin IN ('featured', 'featured_legacy')
  AND deleted_at IS NULL;

UPDATE public.recommendation_submissions
SET add_count = true_count,
    recommend_score = public.compute_recommendation_score(p_submission_id)
WHERE id = p_submission_id AND status = 'active';
```

**设计要点**：
- `add_count` 语义为"当前书架上有该推荐内容的去重用户数"（不含已删除 import_items 的用户）
- 权威值从 `import_items` 表实时计算（`COUNT(DISTINCT user_id)`），而非简单的 `+1`/`-1`
- 每次用户加入书架（`addRecommendationToBookshelf`）或用户删除书架内容（`deleteImportItem`）时，均调用此 RPC 重新计算
- 不同于"应用层查询 + 手动 +1"的方案，RPC 内部原子执行避免了并发竞态
- `add_count` 和 `recommend_score` 在同一事务中更新，确保一致性

**为什么不用 UNIQUE 约束？**
- `import_items.share_source_id` 不是唯一字段——多个用户可以加入同一个推荐条目
- 去重是 (user_id, share_source_id) 级别的，COUNT(DISTINCT user_id) 已经天然去重
- 不需要额外的轻量表

**为什么不用 `recommendation_adds` 轻量表？**
- `import_items` 已经记录了每个用户的加入行为（origin='featured' / 'featured_legacy' + share_source_id）
- 从 `import_items` 直接查询作为权威来源——避免两张表数据不一致
- 减少了推荐系统的表数量，降低维护复杂度

### 6.2 跨用户深拷贝：structuredClone + 重走 createImportItem

`addRecommendationToBookshelf` 需要将提交者的 import_item 内容复制到加入者的书架。实现方式：

```js
// 方式 A：直接 INSERT（绕过 createImportItem）
const newItem = {
  id: generateId('imp_'),
  user_id: userId,
  // ... 手动复制所有字段
}
await client.from('import_items').insert(newItem)

// 方式 B：走 createImportItem + ExtractionResult 中转
const result = reconstructExtractionResult(sourceItem)
await createImportItem(result, { userId, origin: 'featured', shareSourceId: submissionId })
```

**选择方式 B**。理由：
- 复用 `createImportItem` 的 sections 装配逻辑（assembleSections、deriveParentIds）
- sections.id / parentId / order 需要重新分配——直接复制会保留原 id，在新用户的 import_items 中造成 id 冲突
- 走工厂函数确保新 import_item 的结构完整性和一致性

**额外处理**：`structuredClone` 深拷贝 sections 后再重新组装，确保两边 sections 完全独立。

**代码同步注意**：`createImportItem` 的 JSDoc（`importItems.js`）标注 `@param {'imported'|'shared'} [options.origin]`，需要在 Phase 1 中更新为 `@param {'imported'|'shared'|'featured'|'featured_legacy'} [options.origin]`。

### 6.3 匿名用户可浏览推荐

推荐区内容的 RLS SELECT 策略：

```sql
CREATE POLICY "Anyone can view active submissions"
  ON public.recommendation_submissions FOR SELECT
  USING (status = 'active');
```

这意味着匿名用户（未登录）也可以通过 Supabase anon key 浏览推荐列表。这是有意的设计：
- 推荐区是发现层——降低发现门槛有助于内容传播
- 匿名用户看到推荐内容后，点击"加入书架"时引导注册（与现有 requireAuth 门控一致）
- 匿名用户无法评分（评分需要 reading_marks.completed，而匿名用户没有持久化的阅读记录）

**隐私注意**：推荐条目的 `source_url` 对所有用户（包括匿名）可见。提交推荐时，前端应清理 URL 中的敏感 query string 参数（`token`、`key`、`auth`、`password`、`secret` 等），防止付费链接或私有链接的凭证泄露。此清理为远期优化项——当前阶段在提交表单中添加确认提示即可。

**对前端的影响**：
- ImportPage 的推荐 Tab 在未登录状态下仍然可用——展示推荐列表
- 与当前"推荐 Tab 需要 Supabase 配置"的逻辑一致
- 未登录时 [加入书架] 按钮触发 `requireAuth` 门控

### 6.4 不做"推荐内容的编辑历史"

提交者可修改自己推荐的 intro / keywords / excerpt，但不记录修改历史。

**理由**：
- intro/keywords/excerpt 是轻量元数据，不是核心阅读内容
- 编辑历史的 UX 复杂度和数据库成本与收益不成比例
- 与现有 import_items 的编辑逻辑一致（书架编辑也不记录历史）

### 6.5 推荐列表不做分页（第一阶段）

预期提交量 < 50 篇。超过这个量级再引入分页/虚拟滚动。

**但 API 保留分页参数**——`listRecommendations({ limit, offset })`——避免后期改动接口。

### 6.6 score 缓存 vs 实时计算

当前设计：`recommend_score` 作为缓存字段存储在 `recommendation_submissions` 上，通过触发器在评分变化时更新。

**为什么缓存？**
- 推荐列表查询（SELECT * ORDER BY score DESC）是高频操作
- 实时聚合评分表（JOIN + GROUP BY）在评分量增长后会变慢
- 缓存值 + 触发器更新 = 写时计算，读时零成本

**为什么不直接实时计算？**
- 推荐列表是首页级展示，延迟敏感
- `compute_recommendation_score` 函数是 STABLE 的，但仍需每次扫描 ratings 表
- 缓存策略在 score 公式升级时容易切换（改触发器逻辑即可）

## 七、风险与缓解

| 风险 | 缓解措施 |
|------|---------|
| 冷启动——推荐区无内容或内容很少 | 迁移旧 3 篇种子数据；鼓励早期用户提交；推荐列表空状态提供引导 CTA |
| 提交质量参差不齐 | 评分机制自然下沉；第一阶段不做额外干预，观察社区行为 |
| 匿名用户无法浏览（RLS 配置错误） | RLS 策略显式 GRANT anon SELECT；staging 环境先用 anon key 测试 |
| add_count 与 import_items 不同步 | 使用触发器或应用层 UPDATE 确保一致性；定期校验脚本检查偏差 |
| 跨用户深拷贝时 sections 包含用户特定的引用 | createImportItem 工厂函数重新分配 section.id/parentId/order，清除原引用 |
| origin 约束变更后旧数据不兼容 | migration 执行 ALTER CONSTRAINT 而非新增约束；确保现有数据无非法 origin 值 |
| 废弃 featured_articles 后某处代码仍引用该表 | 全局 grep `featured_articles` 确认所有引用点；迁移前先标记废弃，迁移后删除 |

## 八、总结

实施方案的核心思路：

> **叠加而非重构。推荐系统是 import_items 之上的新发现层——它引用书架内容（通过快照），产生新的书架内容（通过加入），形成"推荐 → 加入 → 阅读 → 评分 → 推荐值"的完整闭环。现有书架/阅读区链路完全不变。旧 featured_articles 表直接废弃，数据迁移到新模型。新系统以两张表 + 一个函数的最小增量，解决了 RLS 隔离与社区推荐之间的矛盾。**
