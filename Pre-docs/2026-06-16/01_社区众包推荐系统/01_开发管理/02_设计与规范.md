## 二、概念定义

### 2.1 推荐区（Recommendation Zone）

```
社区用户提交自己书架上已读完的自导入内容，供其他用户发现的公共区域。
推荐条目引用书架内容（import_items），但不复制正文。
通过被添加人数和读后评分计算推荐值，按推荐值排序展示。
所有人可见（包括匿名用户）。
```

### 2.2 推荐提交（Recommendation Submission）

```
用户将自己书架上的一个 import_item 提交到推荐区的行为。
提交时需填写介绍、关键词、摘录。
提交后立即公开（无审核），受基本约束限制（每周 1 篇 + 不可重复）。
```

### 2.3 推荐评分（Recommendation Rating）

```
用户A的推荐被用户B通过推荐区加入书架、阅读完毕后的评分。
三级评分：推荐 / 一般 / 不行。
仅当用户确实通过推荐区获取内容并完成阅读后，方可评分。
评分可随时修改。
```

### 2.4 推荐值（Recommendation Score）

```
由数据库函数实时计算的整数值，用于推荐列表排序。
公式：add_count + recommend_count × 2 - not_good_count
通过函数封装，未来可替换为更复杂的算法。
```

### 2.5 核心原则

| 原则 | 说明 |
|------|------|
| **众包策展** | 任何用户可提交推荐，不是管理员特权 |
| **基本约束 + 正向激励** | 无审核门槛，通过限制 + 评分机制自然筛选 |
| **引用不复制** | 推荐条目引用 import_items，字段快照确保展示一致性 |
| **读完才可评分** | 评分资格由 reading_marks.completed 保证——没读完不能评 |
| **RLS 隔离** | 推荐表对所有用户可读，import_items 保持私有——快照机制确保不泄漏 |
| **公式可替换** | 推荐值通过函数封装，内部算法升级不影响上下层 |

## 三、数据模型

### 3.1 新增表：`recommendation_submissions`

```sql
CREATE TABLE IF NOT EXISTS public.recommendation_submissions (
  id                  text PRIMARY KEY,                    -- "rec_" + timestamp + random5
  submitter_user_id   uuid NOT NULL REFERENCES public.profiles(user_id),

  -- 引用（不复制正文）
  import_item_id      text NOT NULL,                       -- 指向 submitter 自己的 import_items.id

  -- 展示快照（提交时刻冻结，避免 RLS 泄漏）
  title               text NOT NULL,
  author              text,
  source_url          text,

  -- 用户填写
  intro               text NOT NULL DEFAULT '',             -- 介绍
  keywords            text[] NOT NULL DEFAULT '{}',         -- 关键词数组
  excerpt             text NOT NULL DEFAULT '',             -- 摘录

  -- 计算/缓存
  add_count           integer NOT NULL DEFAULT 0,           -- 被添加人数（去重计数）
  recommend_score     integer NOT NULL DEFAULT 0,           -- 推荐值（缓存，由函数更新）

  -- 状态
  status              text NOT NULL DEFAULT 'active',       -- 'active' | 'removed'

  -- 时间戳
  created_at          timestamptz NOT NULL DEFAULT timezone('utc', now()),
  updated_at          timestamptz NOT NULL DEFAULT timezone('utc', now())
);
```

#### 字段详解

##### `id`

格式：`rec_{timestamp}_{random5}`。与 `import_items`（`imp_xxx`）、`articles`（`doc_xxx`）前缀区分，便于日志和调试时一眼识别实体类型。

##### `import_item_id`

指向提交者自己的 `import_items.id`。这是推荐条目与书架内容的唯一引用链路。**无 FK 约束**——与项目现有惯例一致（`articles.source_import_id` 也无 FK）。

注意：此字段指向的 import_item 必须满足提交资格（`origin = 'imported'` + 对应 reading_marks.completed = true），但这是应用层校验——数据库不通过 CHECK 约束强制（因为 reading_marks 的状态是跨表的）。

##### 展示快照字段（`title` / `author` / `source_url`）

提交时从 import_item 复制而来的字段快照。理由：
- import_items 受 RLS 保护（`auth.uid() = user_id`），推荐区查询时当前用户不是该 import_item 的 owner，JOIN 会被 RLS 拒绝
- 快照确保提交内容冻结——即使提交者后来修改了书架的 title/author，推荐条目不受影响
- 代价是快照不随源数据更新——但这是设计取舍，不是缺陷

##### `intro`（介绍）

提交者撰写的一段介绍文字，说明为什么推荐这篇文章。长度建议 100-500 字，但不做数据库层限制（由前端 UI 约束）。

##### `keywords`（关键词）

Postgres `text[]` 数组。用于未来的搜索、分类、标签云功能。当前阶段用于展示和过滤。

##### `excerpt`（摘录）

提交者从原文中选取的一段代表性文字。长度建议 50-300 字。让浏览推荐区的用户快速了解文章风格和内容。

##### `add_count`（被添加人数）

缓存字段——**当前书架上有该推荐内容的去重用户数**（不含已删除 import_items 的用户）。语义是"当前活跃添加数"而非"历史累计数"。权威值通过 SECURITY DEFINER RPC 函数从 `import_items` 表实时计算：

```sql
SELECT COUNT(DISTINCT user_id)
FROM public.import_items
WHERE share_source_id = p_submission_id
  AND origin IN ('featured', 'featured_legacy')
  AND deleted_at IS NULL;
```

更新时机：用户加入书架（`addRecommendationToBookshelf`）、用户删除书架内容（`deleteImportItem`）时，均触发 `add_count` 和 `recommend_score` 的重新计算。

##### `recommend_score`（推荐值）

缓存字段。由 `compute_recommendation_score(submission_id)` 函数计算，在评分变化时更新。存储缓存值避免列表查询时每次都 JOIN ratings 聚合。

##### `status`

| 值 | 含义 |
|----|------|
| `'active'` | 正常展示 |
| `'removed'` | 提交者自行下架（或管理端下架） |

不做物理删除——保留评分记录和历史数据。

#### CHECK 约束

```sql
ALTER TABLE public.recommendation_submissions
  ADD CONSTRAINT recommendation_submissions_status_check
  CHECK (status IN ('active', 'removed'));

ALTER TABLE public.recommendation_submissions
  ADD CONSTRAINT recommendation_submissions_intro_check
  CHECK (length(intro) > 0);   -- 介绍不可为空

ALTER TABLE public.recommendation_submissions
  ADD CONSTRAINT recommendation_submissions_excerpt_check
  CHECK (length(excerpt) > 0); -- 摘录不可为空
```

### 3.2 新增表：`recommendation_ratings`

```sql
CREATE TABLE IF NOT EXISTS public.recommendation_ratings (
  submission_id       text NOT NULL REFERENCES public.recommendation_submissions(id) ON DELETE CASCADE,
  user_id             uuid NOT NULL REFERENCES public.profiles(user_id),

  rating              text NOT NULL,                       -- 'recommend' | 'average' | 'not_good'

  created_at          timestamptz NOT NULL DEFAULT timezone('utc', now()),
  updated_at          timestamptz NOT NULL DEFAULT timezone('utc', now()),

  PRIMARY KEY (submission_id, user_id)                     -- 一人一票
);
```

#### 字段详解

##### `rating`

| 值 | 含义 | 对 score 贡献 |
|----|------|---------------|
| `'recommend'` | 推荐 | +2 |
| `'average'` | 一般 | 0 |
| `'not_good'` | 不行 | -1 |

##### 联合主键 `(submission_id, user_id)`

确保一人一票。UPSERT 语义——用户修改评分时更新同一行。

#### CHECK 约束

```sql
ALTER TABLE public.recommendation_ratings
  ADD CONSTRAINT recommendation_ratings_rating_check
  CHECK (rating IN ('recommend', 'average', 'not_good'));
```

### 3.3 推荐值计算函数

```sql
CREATE OR REPLACE FUNCTION public.compute_recommendation_score(p_submission_id text)
RETURNS integer
LANGUAGE sql
STABLE
AS $$
  WITH rating_counts AS (
    SELECT
      COALESCE(SUM(CASE WHEN rating = 'recommend' THEN 1 ELSE 0 END), 0) AS recommend_count,
      COALESCE(SUM(CASE WHEN rating = 'not_good' THEN 1 ELSE 0 END), 0) AS not_good_count
    FROM public.recommendation_ratings
    WHERE submission_id = p_submission_id
  ),
  submission_data AS (
    SELECT add_count FROM public.recommendation_submissions WHERE id = p_submission_id
  )
  SELECT
    COALESCE(s.add_count, 0)
    + COALESCE(r.recommend_count, 0) * 2
    - COALESCE(r.not_good_count, 0)
  FROM submission_data s, rating_counts r;
$$;
```

**公式说明**：

```
score = add_count + recommend_count × 2 - not_good_count
```

- `add_count`：基础分——每多一人添加，+1。反映"兴趣广度"
- `recommend_count × 2`：正向评分加成——推荐权重是被添加的 2 倍，反映"质量深度"
- `not_good_count`：负向信号——每多一人觉得不行，-1

**为什么"一般"不影响 score？**
"一般" = 中立评价。它不提升也不降低推荐值——只有明确的"推荐"或"不行"才改变排序。这避免了"一般"评分稀释信号。

**为什么用 SQL 函数封装？**
- 未来可替换公式（如 Bayesian average、时间衰减）而不影响应用层
- `STABLE` 标记允许在同一个查询中多次调用时复用结果
- 可在触发器中调用以自动更新缓存字段

### 3.4 现有表变更

#### 3.4.1 `import_items.origin` CHECK 约束扩展

```sql
-- 旧约束
ALTER TABLE public.import_items
  DROP CONSTRAINT IF EXISTS import_items_origin_check;

-- 新约束
ALTER TABLE public.import_items
  ADD CONSTRAINT import_items_origin_check
  CHECK (origin IN ('imported', 'shared', 'featured', 'featured_legacy'));
```

| origin 值 | 含义 | 可再次提交推荐？ |
|-----------|------|------------------|
| `'imported'` | 用户自己导入 | ✅ 可以 |
| `'shared'` | 从共享池拉取 | ❌ 不可 |
| `'featured'` | 从新推荐区加入 | ❌ 不可（排除循环推荐） |
| `'featured_legacy'` | 旧 featured_articles 迁移 | ❌ 不可 |

> **`share_source_id` 语义扩展说明**：`import_items.share_source_id` 原先仅用于 `origin='shared'` 场景，存储共享来源的 `import_items.id`。本次重构后，当 `origin='featured'` 或 `origin='featured_legacy'` 时，`share_source_id` 存储的是 **`recommendation_submissions.id`**（如 `rec_1718500000_abc12`），而非另一个 `import_items.id`。这是一个语义扩展——`share_source_id` 从"来源 import_item ID"变为"来源实体 ID（可能是 import_item 或 recommendation_submission）"。应用层通过 `origin` 字段区分实体类型。

### 3.5 旧数据迁移策略

当前 `featured_articles` 表有 3 篇种子文章，分别来自 notion.com、jamesclear.com、paulgraham.com。

#### 迁移步骤

1. **创建 system 账号**：在 `public.profiles` 中插入一条 `user_id` 为 `00000000-0000-0000-0000-000000000000` 的记录（或 Supabase 的 service_role 可绕开 RLS 直接写入）。该账号作为旧系统内容的"名义提交者"。

2. **为每篇种子文章创建 import_item**：
   - `origin = 'featured_legacy'`
   - `user_id = system 账号`
   - `title`、`author`、`source_url`、`sections`（从 featured_articles 的 text/markdown 组装为单 section）等字段从 featured_articles 复制

3. **创建 recommendation_submission**：
   - `submitter_user_id = system 账号`
   - `import_item_id` = 上一步创建的 imp_xxx id
   - `intro` / `excerpt` 从旧 `description` 字段派生
   - `keywords` 从 source 和 title 提取
   - `status = 'active'`

4. **更新 `featuredArticleSeeds.js`**：重写为 `recommendationSeeds.js`，适配新模型（不再使用）。

5. **废弃旧表**：`DROP TABLE featured_articles CASCADE`

## 六、RLS 策略

### 6.1 `recommendation_submissions`

```sql
ALTER TABLE public.recommendation_submissions ENABLE ROW LEVEL SECURITY;

-- 所有人可读 active 条目（包括匿名用户）
CREATE POLICY "Anyone can view active submissions"
  ON public.recommendation_submissions FOR SELECT
  USING (status = 'active');

-- 已登录用户可读自己的所有条目（包括 removed）
CREATE POLICY "Users can view own submissions"
  ON public.recommendation_submissions FOR SELECT
  USING (auth.uid() = submitter_user_id);

-- 已登录用户可提交推荐
CREATE POLICY "Users can insert submissions"
  ON public.recommendation_submissions FOR INSERT
  WITH CHECK (auth.uid() = submitter_user_id);

-- 提交者可以更新自己的条目（用于编辑 intro/keywords/excerpt 或下架）
CREATE POLICY "Users can update own submissions"
  ON public.recommendation_submissions FOR UPDATE
  USING (auth.uid() = submitter_user_id)
  WITH CHECK (auth.uid() = submitter_user_id);

-- 不授权 DELETE——条目通过 status = 'removed' 下架
```

关键点：
- 第一条策略对匿名用户和已登录用户均生效（`USING (status = 'active')`），推荐区内容对所有人可见
- 提交者操作通过 `auth.uid() = submitter_user_id` 限制
- 不做物理删除，保持与现有软删除惯例一致

### 6.2 `recommendation_ratings`

```sql
ALTER TABLE public.recommendation_ratings ENABLE ROW LEVEL SECURITY;

-- 所有人可读评分数据（用于展示评分分布）
CREATE POLICY "Anyone can view ratings"
  ON public.recommendation_ratings FOR SELECT
  USING (true);

-- 已登录用户可提交评分
CREATE POLICY "Users can insert ratings"
  ON public.recommendation_ratings FOR INSERT
  WITH CHECK (auth.uid() = user_id);

-- 用户可更新自己的评分
CREATE POLICY "Users can update own ratings"
  ON public.recommendation_ratings FOR UPDATE
  USING (auth.uid() = user_id)
  WITH CHECK (auth.uid() = user_id);

-- 不授权 DELETE——评分不可删除（可改为"一般"但不能移除）
```

## 八、自动触发器

```sql
-- updated_at 自动更新（与现有 articles / import_items 模式一致）
CREATE TRIGGER trg_rec_submissions_set_updated_at
  BEFORE UPDATE ON public.recommendation_submissions
  FOR EACH ROW
  EXECUTE FUNCTION public.set_record_updated_at();

CREATE TRIGGER trg_rec_ratings_set_updated_at
  BEFORE UPDATE ON public.recommendation_ratings
  FOR EACH ROW
  EXECUTE FUNCTION public.set_record_updated_at();
```

### 评分触发的 score 更新触发器

```sql
CREATE OR REPLACE FUNCTION public.update_recommendation_score()
RETURNS trigger
LANGUAGE plpgsql
AS $$
DECLARE
  target_id text;
BEGIN
  -- DELETE 时 NEW 为 NULL，使用 OLD.submission_id
  target_id := COALESCE(NEW.submission_id, OLD.submission_id);
  UPDATE public.recommendation_submissions
  SET recommend_score = public.compute_recommendation_score(target_id)
  WHERE id = target_id;
  RETURN COALESCE(NEW, OLD);
END;
$$;

CREATE TRIGGER trg_rec_ratings_update_score
  AFTER INSERT OR UPDATE OR DELETE ON public.recommendation_ratings
  FOR EACH ROW
  EXECUTE FUNCTION public.update_recommendation_score();
```

**设计说明**：
- 评分表的变化自动触发 score 缓存更新。使用 AFTER 触发器确保评分已持久化后再计算。
- 使用 `COALESCE(NEW.submission_id, OLD.submission_id)` 处理 DELETE 场景（PostgreSQL 中 FOR EACH ROW 触发器的 DELETE 操作下 NEW 为 NULL）。
- `add_count` 的变化不由此触发器覆盖——`add_count` 的更新（用户加入/删除书架内容）通过 SECURITY DEFINER RPC 函数 `increment_recommendation_add_count` 完成，该 RPC 内部同时调用 `compute_recommendation_score` 重算 score。

## 八点五、SECURITY DEFINER RPC 函数

推荐系统的两个核心操作——"加入书架"（需跨用户读取提交者的 import_item）和"更新 add_count"（需跨用户更新 recommendation_submissions）——涉及当前用户无权访问的数据。以下 3 个 SECURITY DEFINER RPC 函数在数据库层安全地绕过 RLS 执行这些操作，与项目现有的 `delete_import_item`、`soft_delete_article` 模式一致。

### RPC 1：`get_import_item_for_recommendation`

```sql
CREATE OR REPLACE FUNCTION public.get_import_item_for_recommendation(
  p_import_item_id text
)
RETURNS jsonb
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
DECLARE
  result jsonb;
BEGIN
  -- 安全门控：仅当该 import_item 存在活跃推荐条目时才允许读取
  IF NOT EXISTS (
    SELECT 1 FROM public.recommendation_submissions
    WHERE import_item_id = p_import_item_id AND status = 'active'
  ) THEN
    RAISE EXCEPTION '该内容没有对应的活跃推荐条目';
  END IF;

  SELECT row_to_json(ii.*)::jsonb INTO result
  FROM public.import_items ii
  WHERE ii.id = p_import_item_id AND ii.deleted_at IS NULL;

  IF result IS NULL THEN
    RAISE EXCEPTION '原始内容不存在或已被删除';
  END IF;

  RETURN result;
END;
$$;

GRANT EXECUTE ON FUNCTION public.get_import_item_for_recommendation(text) TO authenticated;
```

**用途**：`addRecommendationToBookshelf` 调用——获取提交者的 import_item 完整数据（含 sections），用于跨用户深拷贝。

**安全机制**：只有存在活跃推荐条目的 import_item 才可被读取。这防止了任意 import_item ID 的遍历攻击。

### RPC 2：`increment_recommendation_add_count`

```sql
CREATE OR REPLACE FUNCTION public.increment_recommendation_add_count(
  p_submission_id text,
  p_user_id uuid
)
RETURNS void
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
DECLARE
  true_count integer;
BEGIN
  -- 1. 检查该用户是否已有对应的活跃 import_item（去重）
  --    若已存在，不重复计数——但仍重新计算 score（因为其他用户可能变化）
  -- 2. 从 import_items 表计算权威 add_count 值
  SELECT COUNT(DISTINCT user_id) INTO true_count
  FROM public.import_items
  WHERE share_source_id = p_submission_id
    AND origin IN ('featured', 'featured_legacy')
    AND deleted_at IS NULL;

  -- 3. 原子更新 add_count 和 recommend_score
  UPDATE public.recommendation_submissions
  SET add_count = true_count,
      recommend_score = public.compute_recommendation_score(p_submission_id)
  WHERE id = p_submission_id AND status = 'active';
END;
$$;

GRANT EXECUTE ON FUNCTION public.increment_recommendation_add_count(text, uuid) TO authenticated;
```

**用途**：`addRecommendationToBookshelf` 和 `deleteImportItem` 调用——更新推荐条目的 `add_count` 和 `recommend_score`。

**设计要点**：
- `add_count` 的权威值从 `import_items` 表实时计算（`COUNT(DISTINCT user_id)`），而非简单的 `+1`。这解决了用户删除书架内容后计数不准的问题。
- 同时调用 `compute_recommendation_score` 更新 score（解决 `add_count` 变化不触发 score 重算的问题）。
- `p_user_id` 参数用于去重校验（同一用户多次添加只计一次）。

### RPC 3：`check_import_item_reading_completed`

```sql
CREATE OR REPLACE FUNCTION public.check_import_item_reading_completed(
  p_import_item_id text,
  p_user_id uuid
)
RETURNS boolean
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
BEGIN
  RETURN EXISTS (
    SELECT 1 FROM public.articles a
    JOIN public.reading_marks rm ON rm.article_id = a.id AND rm.user_id = a.user_id
    WHERE a.source_import_id = p_import_item_id
      AND a.user_id = p_user_id
      AND rm.completed = true
      AND a.deleted_at IS NULL
  );
END;
$$;

GRANT EXECUTE ON FUNCTION public.check_import_item_reading_completed(text, uuid) TO authenticated;
```

**用途**：`checkSubmissionEligibility` 和 `checkRatingEligibility` 调用——验证用户是否已完成对某个 import_item 对应文章的阅读。

**设计要点**：
- 单条 SQL JOIN 查询替代应用层 N+1 循环（先查 articles 再逐条查 reading_marks）。
- 使用 SECURITY DEFINER 确保可以跨 `articles` + `reading_marks` 表进行 JOIN 查询。

## 十二、总结

本设计定义了社区众包推荐系统的数据模型和操作规范：

- **废弃 `featured_articles` 表**，以 `recommendation_submissions` + `recommendation_ratings` 两张新表替代
- **推荐条目通过字段快照引用 import_items**——避免 RLS 泄漏，保持数据隔离
- **三级评分 + 推荐值函数**——简单可替换，适应未来算法升级
- **众包策展 + 基本约束**——无审核门槛，靠评分机制自然过滤
- **origin 字段扩展**——支持 `featured` / `featured_legacy`，打通推荐区 → 书架的来源链路
- **所有现有系统不受影响**——书架/阅读区/导入流程/回顾面板全部不变

后续所有实现工作以本文档为唯一设计依据。
