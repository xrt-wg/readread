# 社区众包推荐系统 — 决策记录

- **日期**：2026-06-16
- **状态**：已决策
- **项目阶段**：构建期
- **决策主题**：废弃管理员封闭策展的 `featured_articles` 表，重构为社区众包推荐系统——任何人都可将已读完的自导入内容提交到推荐区，由社区评分驱动排序

---

## 一、背景

当前推荐区的运行机制：

```
管理员 → 手工添加 → featured_articles 表（内容自包含，text/markdown 重复存储）
                                 → 用户在推荐 Tab 浏览 → 点击"加入书架"
```

核心问题：

1. **不规模化**：所有推荐内容依赖管理员手工策展，无法利用用户社群的力量
2. **无反馈闭环**：推荐内容发布后无法获知用户是否阅读、是否喜欢——没有质量信号
3. **数据冗余**：`featured_articles` 表完整复制文章正文（text/markdown），与 `import_items`、`articles` 中的内容形成三份冗余
4. **与书架/阅读区割裂**：推荐区是一张孤立的表，它不感知用户的阅读进度、书架内容、阅读评分——"推荐 → 加入 → 阅读 → 评价"这条链路在数据层面是断裂的

此外，已发现的 bug——`ImportPage.jsx` 向 `createImportItem` 传入 `origin: 'featured'`，但 `import_items.origin` CHECK 约束只允许 `('imported', 'shared')`——暴露了一个更深层的问题：**推荐区本应作为书架的一个来源渠道，但因数据模型隔离而无法正常工作。**

---

## 二、决策目标

1. 废弃 `featured_articles` 表，建立社区众包推荐数据模型
2. 任何用户可提交自己书架上已读完的自导入内容到推荐区
3. 推荐条目需具备：介绍、关键词、摘录、推荐值（动态计算）
4. 推荐值由"被添加人数 + 读后评分分布"综合计算
5. 基本反滥用约束：提交限制 + 重复检测
6. 修复 `origin: 'featured'` 的 CHECK 约束不匹配问题

---

## 三、决策结论

**废弃 `featured_articles` 表，新建 `recommendation_submissions` 和 `recommendation_ratings` 两张表，建立从 import_items 到推荐区的引用链路。**

核心决策：

- **众包提交**：任何用户可提交——不再是管理员特权。提交后直接发布（无审核），靠基本约束 + 评分机制自然过滤
- **引用模型**：推荐条目引用 `import_items.id`，不复制正文。展示用 title/author/source_url 做字段快照（避免 RLS 跨用户查询泄漏）
- **提交资格**：`import_items.origin = 'imported'` 且对应阅读区文章 `reading_marks.completed = true`
- **基本约束**：每人每周限 1 篇 + 同 source_url/title 不可重复提交（应用层校验，硬编码常量但可配置化）
- **评分系统**：三级评分（推荐 / 一般 / 不行），仅通过推荐区加入并读完的用户可评分，允许修改
- **推荐值计算**：通过数据库函数封装，初版公式 `add_count + recommend_count × 2 - not_good_count`，未来可替换
- **旧数据迁移**：3 篇种子文章迁移为 system 账号持有的 import_items（origin=`'featured_legacy'`）和对应 recommendation_submissions
- **origin 字段扩展**：CHECK 约束扩展为 `('imported', 'shared', 'featured', 'featured_legacy')`

---

## 四、候选方案比较

### 方案 A：保留 featured_articles，加评分字段（否决）

在现有 `featured_articles` 表上加 `add_count`、`rating_sum`、`rating_count` 字段，仍由管理员添加内容。

#### 优点
- 改动最小，不新建表

#### 致命问题
- 不解决"管理员瓶颈"——内容仍需管理员添加
- 不解决数据冗余——text/markdown 仍然三份
- 评分字段挂在 featured_articles 上，但用户评分需要验证"是否读过"——featured_articles 不感知 reading_marks
- 本质上只是贴了一层评分 UI 在旧模型上

#### 结论
**否决。** 该方案没有解决核心问题（规模化 + 反馈闭环），只是在旧模型上打补丁。

---

### 方案 B：在 import_items 上直接加推荐字段（否决）

不新建推荐表，而是扩展 `import_items`——添加 `is_recommended` boolean + `intro`/`keywords`/`excerpt` 字段。推荐区 = `SELECT * FROM import_items WHERE is_recommended = true`。

#### 优点
- 零新表，schema 改动少
- 推荐内容天然引用原数据

#### 致命问题
- RLS 冲突：`import_items` 的策略是"用户只能读自己的"，但推荐区需要"所有人可读"。需要为推荐条目开例外——这使得 RLS 策略变复杂且容易出错
- 字段语义混乱：`import_items` 的 `title`/`author` 是用户自己编辑的，推荐区展示时需要确保与原内容一致——但用户可以随时修改，导致已推荐的条目"漂移"
- 提交人信息缺失：需要额外字段记录谁在何时提交的
- 评分无处挂载

#### 结论
**否决。** RLS 冲突是硬伤——要么改 RLS 策略（引入安全隐患），要么接受推荐条目数据不隔离。两者都不可接受。

---

### 方案 C：两新表 + 字段快照（采用）

```
recommendation_submissions（推荐条目）
  ├── 引用 import_items.id（但不跨 RLS 查询）
  ├── 快照 title / author / source_url（展示用）
  ├── 用户提交的 intro / keywords / excerpt
  └── 计算字段 add_count / recommend_score

recommendation_ratings（评分记录）
  └── submission_id + user_id + rating
```

#### 优点
- RLS 策略简洁：推荐表对所有用户可读（独立的 SELECT 策略），写操作仅限提交者本人
- 字段快照解决了"源数据可能被修改"的问题——提交时的 title/author 被冻结
- 评分独立存储，验证逻辑清晰（评分前检查用户是否有对应的 import_item 且已读完）
- 推荐值通过函数计算，封装后可替换
- 两表各自职责单一，未来扩展（如推荐被举报、管理后台标记）不互相污染

#### 代价
- 新增 2 张表 + 1 个 score 函数
- 旧 featured_articles 数据需迁移
- 字段快照在源数据更新后不同步（这是设计取舍，见 5.4）

#### 结论
**采用。** 这是解决 RLS 隔离与社区推荐需求之间矛盾的最佳方案。

---

### 方案 D：单表推荐 + 视图解决 RLS（否决）

新建一张 `recommendation_submissions` 表（包含评分字段，不拆分 ratings），通过数据库视图展示公开推荐。

#### 优点
- 比方案 C 少一张表

#### 致命问题
- 评分挤在 submission 行上（JSONB 存储评分列表或冗余计数），无法支持"用户修改评分"（需要更新 JSONB 数组内的特定元素）
- 无法加 `UNIQUE(submission_id, user_id)` 约束防止重复评分
- `add_count` 的去重计数无法通过行级字段实现（同一用户多次添加/删除）

#### 结论
**否决。** 评分是 (submission, user) 的多对多关系，应该是一张独立的表。这不是"少一张表"的优化——是把关系模型扭曲成了文档模型。

---

## 五、关键决策点与取舍

### 5.1 提交 = 直接发布，无审核

不做 pending → approved → published 的状态机。用户提交后直接进入推荐列表。

**理由**：
- 每周限额 + 重复检测已提供基本防滥用
- 三级评分机制自然下沉低质内容（"不行"投票多的条目 score 低）
- 审核流程引入延迟和管理负担，与"众包"精神相悖
- 未来可加"最低推荐值阈值"隐藏低分内容，效果等同于自动审核

**风险**：极端情况下可能出现 spam 提交。缓解：后续版本可引入"被 N 人点'不行'则自动隐藏"的规则。

### 5.2 推荐值通过函数计算，不存为静态字段

`recommend_score` 在 submission 行上存储缓存值（定期更新），但计算逻辑在数据库函数内。

**理由**：
- 评分变化时（新评分、修改评分）触发 score 重算
- 函数封装让公式可替换——从简单加权升级到 Bayesian average 不需要改表结构
- 缓存值避免每次列表查询都 JOIN ratings 表聚合

### 5.3 字段快照 vs 跨 RLS JOIN

推荐条目展示 title/author/source_url 时，使用提交时刻的快照（存储在 submission 行上），而非 JOIN import_items 实时读取。

**理由**：
- `import_items` 有 RLS `auth.uid() = user_id`——推荐区查询时当前用户不是 import_item 的 owner，会触发 RLS 拒绝
- 修改 RLS 策略开"公开可读"例外会引入安全隐患（且与 import_items 的核心访问控制冲突）
- 快照 = 提交时的内容冻结——即使提交者后来修改了书架内容，推荐条目不受影响（这是 feature，不是 bug）

**代价**：源内容大幅更新后，推荐条目不会自动反映。提交者需要重新提交（产生新条目）。这个代价可接受——推荐条目代表的是"此刻我被提交时的样子"。

### 5.4 评分资格验证

评分前验证三条：
1. 当前用户在 `import_items` 中有一条记录满足 `share_source_id = submission_id` 且 `origin = 'featured'`
2. 该 import_item 已移入阅读区（存在对应的 `articles` 行）
3. 对应的 `reading_marks.completed = true`

**为什么不通过 submission.add_count > 0 推断评分资格？**
- add_count 是冗余计数，存在更新延迟
- 验证链路应走确定性数据（import_items + reading_marks），不依赖聚合缓存

### 5.5 origin 字段扩展策略

当前 CHECK 约束：`origin IN ('imported', 'shared')`

扩展为：`origin IN ('imported', 'shared', 'featured', 'featured_legacy')`

- `'featured'`：用户从推荐区加入书架（修复现有 bug）
- `'featured_legacy'`：旧 featured_articles 种子数据迁移后的标记

**为什么加 `featured_legacy` 而非直接用 `featured`？**
- 区分来源：`featured` = 从新推荐系统加入，`featured_legacy` = 旧系统迁移
- `featured_legacy` 的内容可能质量参差（管理员手工选的，无社区验证），后续可过滤或特殊处理
- 两者在"排除循环推荐"逻辑中等价——都是不可再次提交

---

## 六、决策范围

### 已确认
- 废弃 `featured_articles` 表
- 新建 `recommendation_submissions` + `recommendation_ratings` 表
- 推荐条目引用 import_items + 字段快照
- 三级评分（推荐 / 一般 / 不行）
- 推荐值函数封装，初版简单公式
- 提交约束：每周 1 篇 + 重复检测
- 评分资格：通过推荐区加入 + 已读完 + 一人一票 + 可修改
- 旧种子数据迁移到新模型（system 账号）
- origin CHECK 约束扩展为 4 个值
- 关键词存储格式：`text[]`

### 暂不确认（属于后续设计规范的范围）
- 推荐值缓存更新策略（触发器 vs 定时任务 vs 按需计算）
- "最低推荐值阈值"隐藏低分内容的时机和数值
- 激励机制的细化（推荐被采纳解锁更多提交额度等）
- 举报/下架的管理端功能是否独立于提交者自下架

---

## 七、实施约束

1. 不要修改 articles 表结构——推荐系统不侵入阅读区
2. 不要修改 reading_marks 表结构——评分独立存储
3. 不要修改 import_items 的 RLS 策略（保持 `auth.uid() = user_id`）
4. 现有书架 CRUD、移入操作、阅读流程不受影响
5. 推荐区前端改造在现有 ImportPage 的「推荐」Tab 内完成，不新增顶层页面
6. 所有推荐区内容对所有人可见（包括匿名用户）——通过独立的 RLS SELECT 策略实现

---

## 八、复审条件

若出现以下任一情况，应重新评估当前设计：

1. 社区提交量超过每周 100 篇——需要引入更复杂的排序/过滤/分页策略
2. 评分操纵成为实际问题——需要引入评分权重（如基于用户信誉的加权）
3. 推荐区内容量达到需要分类/标签体系的规模（> 500 篇）
4. 需要支持"推荐 + 笔记"混合提交（即提交时不只推荐，还附上个人读书笔记）
5. 旧 featured_articles 种子数据迁移后发现大量用户重新提交同内容（重复检测规则需要升级）

---

## 九、总结

本次决策的核心结论是：

> **废弃封闭策展的 `featured_articles` 表，以 `recommendation_submissions`（推荐条目）+ `recommendation_ratings`（评分记录）两张新表建立社区众包推荐系统。推荐条目通过字段快照引用 import_items（避免 RLS 泄漏），以数据库函数封装推荐值计算，以三级评分 + 提交约束构成基本的内容质量机制。整个推荐链路——"导入 → 阅读 → 读完 → 提交推荐 → 他人发现 → 加入 → 阅读 → 评分"——形成完整闭环。**
