## 二、逐项处理详情

### 🔴1：`addRecommendationToBookshelf` 跨用户 RLS 阻断

**问题**：`addRecommendationToBookshelf` 调用 `fetchImportItemById(submission.import_item_id)` 读取提交者的 import_item。`import_items` 的 RLS 策略为 `auth.uid() = user_id`——当前用户 B 不是提交者 A，RLS 拒绝读取。整个"加入书架"操作不可用。

**处理**：
1. `02_设计与规范.md`：新增 §八点五「SECURITY DEFINER RPC 函数」，定义 `get_import_item_for_recommendation(p_import_item_id)`——安全门控仅当存在活跃推荐条目时才允许读取
2. `03_实施方案.md`：重写 §3.2.3 `addRecommendationToBookshelf`，步骤 2 改为 `client.rpc('get_import_item_for_recommendation', ...)`
3. `04_执行计划.md`：Phase 0 新增任务 0.6（RPC 函数），完成标志增加 RPC 验证项

**影响文档**：
- `02_设计与规范.md` — 新增 §八点五（RPC 1）
- `03_实施方案.md` — §3.2.3 函数重写
- `04_执行计划.md` — 任务 0.6 + 路线图更新

---

### 🔴2：非提交者无法更新 `add_count`（RLS 阻断）

**问题**：`addRecommendationToBookshelf` 最后一步需要更新 `recommendation_submissions.add_count`，但 RLS 策略限制只有 `submitter_user_id` 可 UPDATE。当前用户 B（加入者）不是提交者，RLS 拒绝。

**处理**：
1. `02_设计与规范.md`：§八点五 定义 `increment_recommendation_add_count(p_submission_id, p_user_id)`——在数据库层原子计算 `COUNT(DISTINCT user_id)` 并更新 `add_count` + `recommend_score`
2. `03_实施方案.md`：`addRecommendationToBookshelf` 步骤 5 改为 `client.rpc('increment_recommendation_add_count', ...)`
3. `03_实施方案.md`：§6.1 `add_count` 去重策略从"应用层查询"改为"RPC 内权威计算"
4. `04_执行计划.md`：Phase 0 任务 0.6 包含此 RPC

**影响文档**：
- `02_设计与规范.md` — 新增 §八点五（RPC 2）+ §3.1 `add_count` 语义重定义
- `03_实施方案.md` — §3.2.3 步骤 5 + §6.1 策略重写
- `04_执行计划.md` — 任务 0.6

### 🔴3：score 更新触发器 DELETE 时 `NEW` 为 NULL

**问题**：`update_recommendation_score()` 触发器使用 `NEW.submission_id`，但 PostgreSQL FOR EACH ROW 触发器的 DELETE 操作下 `NEW` 为 NULL。当前设计不授权 DELETE 评分，但触发器中声明了 `OR DELETE`——若未来通过 RPC 执行 DELETE，触发器会崩溃。

**处理**：
1. `02_设计与规范.md`：§八 触发器函数改为 `COALESCE(NEW.submission_id, OLD.submission_id)` + `RETURN COALESCE(NEW, OLD)`
2. `04_执行计划.md`：任务 0.5 的触发器代码同步更新

**影响文档**：
- `02_设计与规范.md` — §八 触发器函数重写 + 设计说明补充
- `04_执行计划.md` — 任务 0.5 代码同步

---

### 🟡4：`add_count` 变化不触发 score 重算

**问题**：推荐值公式 `score = add_count + recommend_count × 2 - not_good_count`。`recommend_count`/`not_good_count` 变化时触发器更新 score ✅，但 `add_count` 变化时无触发器覆盖 ❌。`add_count` 在 `addRecommendationToBookshelf` 中增加，但没有对应的 score 更新。

**处理**：在 `increment_recommendation_add_count` RPC 函数内部同时调用 `compute_recommendation_score` 更新 score（与 🟡5 一并解决）。

**影响文档**：
- `02_设计与规范.md` — §八点五 RPC 2 说明 + §八 设计说明补充
- `03_实施方案.md` — §6.1 更新逻辑说明

### 🟡5：`add_count` 去重存储方案确定

**问题**：文档讨论了三种去重方案（轻量表、import_items 查询、应用层判断）但未明确选择。应用层判断存在并发竞态；import_items 查询需要突破 RLS。

**处理**：确定方案——SECURITY DEFINER RPC 内部 `SELECT COUNT(DISTINCT user_id) FROM import_items WHERE share_source_id = ? AND origin IN ('featured', 'featured_legacy') AND deleted_at IS NULL` 计算权威值，原子更新。

**影响文档**：
- `02_设计与规范.md` — §3.1 `add_count` 字段详解（D1）
- `03_实施方案.md` — §6.1 完整重写
- `04_执行计划.md` — 任务 0.6 RPC 说明

### 🟡6：Phase 2 与 Phase 3 破坏性时间窗口

**问题**：执行计划原先允许 Phase 2（DROP 旧表）和 Phase 3（前端切换）并行执行。如果 Phase 2 先完成而 Phase 3 尚未部署，前端推荐 Tab 仍调用 `listFeaturedArticles`，但表已 DROP——用户看到报错。

**处理**：重新排序为 **Phase 3a（前端双数据源：新优先 + 旧 fallback）→ Phase 2（迁移 + DROP）→ Phase 3b（移除 fallback）**。Phase 3a 先部署确保新系统可用，Phase 2 在确认后执行。

**影响文档**：
- `04_执行计划.md` — 路线图、依赖图、阶段切换条件、总结（全部 6 处更新）

## 三、执行计划调整说明

审核反馈中最关键的结构性调整是 **Phase 2 与 Phase 3 的重新排序**和 **Phase 0 新增 RPC 函数任务**。

### 调整前后的路线图对比

```
调整前：                              调整后：
Phase 0 (7 任务)                      Phase 0 (8 任务)
  → Phase 1                             → Phase 1
  → Phase 2 + Phase 3 (并行)            → Phase 3a（前端双数据源）
  → Phase 4                             → Phase 2（迁移 + DROP）
  → Phase 5                             → Phase 3b（移除 fallback）
                                        → Phase 4
                                        → Phase 5
```

核心变化：
1. Phase 0 从 7 任务扩展为 8 任务（+RPC 函数）
2. Phase 2 与 Phase 3 不再并行——Phase 3a 先部署（新推荐优先，旧作为 fallback），确认正常后 Phase 2 DROP 旧表，最后 Phase 3b 清理 fallback
3. 服务层和前端代码中所有跨用户数据访问均通过 SECURITY DEFINER RPC 完成
