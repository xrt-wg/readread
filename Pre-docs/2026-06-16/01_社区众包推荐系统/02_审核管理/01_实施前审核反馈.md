## 二、严重问题（必须修正，否则阻塞实施）

### 🔴 问题 1：`addRecommendationToBookshelf` 无法读取提交者的 import_item（RLS 阻断）

**位置**：`03_实施方案.md § 3.2.3`，`04_执行计划.md` 任务 1.1

**问题描述**：

实施方案中 `addRecommendationToBookshelf` 的核心流程：

```js
// 2. 获取提交者的 import_item
const sourceItem = await fetchImportItemById(submission.import_item_id)
```

这里 `fetchImportItemById` 是在 `importItems.js` 中定义的：

```js
// importItems.js:119-122
const { data, error } = await client
  .from('import_items')
  .select(IMPORT_ITEM_COLUMNS)
  .eq('id', id)
  .is('deleted_at', null)
  .maybeSingle()
```

`import_items` 的 RLS 策略（[20260614000001_create_import_items.sql:98-100](supabase/migrations/20260614000001_create_import_items.sql#L98-L100)）：

```sql
CREATE POLICY "Users can view own import items"
  ON public.import_items FOR SELECT
  USING (auth.uid() = user_id);
```

**当用户 B 调用 `addRecommendationToBookshelf` 时**：
- 当前 session 的 `auth.uid()` = B 的 user_id
- `submission.import_item_id` 指向提交者 A 的 import_item
- A 的 import_item 的 `user_id` ≠ B 的 user_id
- **RLS 拒绝读取，返回空结果或权限错误**

设计文档 § 5.3（字段快照 vs 跨 RLS JOIN）已经意识到了展示层面的 RLS 问题（所以用了快照），但遗漏了**加入书架时深拷贝 sections** 这个操作也需要跨用户读取 import_item。

**影响范围**：`addRecommendationToBookshelf` 函数完全不可用——"加入书架"是整个推荐闭环的核心操作，此问题阻塞 Phase 1。

**修复建议**：

**方案 A（推荐）：创建 SECURITY DEFINER RPC 函数**

```sql
-- 新增 migration
CREATE OR REPLACE FUNCTION public.get_import_item_for_recommendation(p_import_item_id text)
RETURNS jsonb
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
DECLARE
  result jsonb;
BEGIN
  -- 仅当该 import_item 存在活跃推荐条目时才允许读取
  IF NOT EXISTS (
    SELECT 1 FROM public.recommendation_submissions
    WHERE import_item_id = p_import_item_id AND status = 'active'
  ) THEN
    RAISE EXCEPTION '该内容没有对应的活跃推荐条目';
  END IF;

  SELECT row_to_json(ii.*)::jsonb INTO result
  FROM public.import_items ii
  WHERE ii.id = p_import_item_id AND ii.deleted_at IS NULL;

  IF result IS NULL THEN
    RAISE EXCEPTION '原始内容不存在或已被删除';
  END IF;

  RETURN result;
END;
$$;

GRANT EXECUTE ON FUNCTION public.get_import_item_for_recommendation(text) TO authenticated;
```

- 符合代码库现有模式（`delete_import_item`、`soft_delete_article` 均使用 SECURITY DEFINER RPC 绕过 RLS）
- 安全门控：只有存在活跃推荐条目的 import_item 才可被读取
- 返回完整行数据，前端调用后深拷贝 sections

**方案 B：在 recommendation_submissions 上添加 `sections_snapshot` 字段**

存储加入书架所需的最小数据。但违反"引用不复制正文"原则，且 sections 可能较大（jsonb）。

**建议**：采用方案 A。与现有代码库惯例一致，实施成本低。

### 🔴 问题 2：非提交者无法更新 `recommendation_submissions.add_count`（RLS 阻断）

**位置**：`02_设计与规范.md § 6.1`，`03_实施方案.md § 3.2.3`

**问题描述**：

RLS 策略规定只有提交者本人可 UPDATE：

```sql
CREATE POLICY "Users can update own submissions"
  ON public.recommendation_submissions FOR UPDATE
  USING (auth.uid() = submitter_user_id)
  WITH CHECK (auth.uid() = submitter_user_id);
```

但 `addRecommendationToBookshelf` 的最后一步需要更新 `add_count`：

```js
// 5. 更新 add_count
await upsertAddCount(submissionId, userId)
```

`upsertAddCount` 需要一个 UPDATE 操作。当前用户 B（加入者）不是 `submitter_user_id`，RLS 拒绝。

**影响范围**：`add_count` 永远为 0，推荐值公式中的 `add_count` 项失效。虽然不影响核心"加入"操作（import_item 仍会被创建），但推荐排序信号受损。

**修复建议**：

**方案 A（推荐）：创建 SECURITY DEFINER RPC 函数**

```sql
CREATE OR REPLACE FUNCTION public.increment_recommendation_add_count(
  p_submission_id text,
  p_user_id uuid
)
RETURNS void
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
BEGIN
  -- 去重：检查该用户是否已有 origin='featured' 且 share_source_id = submission_id 的 import_item
  -- 若已存在且未删除，不增加计数
  IF EXISTS (
    SELECT 1 FROM public.import_items
    WHERE user_id = p_user_id
      AND share_source_id = p_submission_id
      AND origin = 'featured'
      AND deleted_at IS NULL
    -- 注意：这里只检查了 origin='featured'，实际上 'featured_legacy' 也应该算
  ) THEN
    -- 该用户已经添加过，不重复计数
    -- 但可能需要重新计算（如果之前计数因某种原因不准）
    RETURN;
  END IF;

  UPDATE public.recommendation_submissions
  SET add_count = add_count + 1,
      recommend_score = public.compute_recommendation_score(p_submission_id)
  WHERE id = p_submission_id AND status = 'active';
END;
$$;

GRANT EXECUTE ON FUNCTION public.increment_recommendation_add_count(text, uuid) TO authenticated;
```

- 将 add_count 增量 + 去重逻辑封装在数据库层
- 同时触发 score 重算（解决了下面问题 5）
- 调用时传入 `auth.uid()`，在 RPC 内部校验

**方案 B：放宽 RLS 策略**

```sql
-- 允许任何已登录用户更新 add_count 和 recommend_score 字段
CREATE POLICY "Anyone can update add_count"
  ON public.recommendation_submissions FOR UPDATE
  USING (auth.uid() IS NOT NULL)
  WITH CHECK (
    auth.uid() IS NOT NULL
    AND submitter_user_id = (SELECT submitter_user_id FROM public.recommendation_submissions WHERE id = id)
  );
```

不推荐——放宽 RLS 会引入安全风险，且与现有"严格的用户隔离"惯例不一致。

**建议**：采用方案 A。

### 🔴 问题 3：score 更新触发器在 DELETE 时引用 `NEW` 导致空值

**位置**：`02_设计与规范.md § 八`，`04_执行计划.md` 任务 0.5

**问题描述**：

触发器函数和触发定义：

```sql
CREATE OR REPLACE FUNCTION public.update_recommendation_score()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  UPDATE public.recommendation_submissions
  SET recommend_score = public.compute_recommendation_score(NEW.submission_id)  -- BUG: DELETE 时 NEW 为 NULL
  WHERE id = NEW.submission_id;
  RETURN NEW;  -- BUG: DELETE 时 NEW 为 NULL
END;
$$;

CREATE TRIGGER trg_rec_ratings_update_score
  AFTER INSERT OR UPDATE OR DELETE ON public.recommendation_ratings
  FOR EACH ROW
  EXECUTE FUNCTION public.update_recommendation_score();
```

PostgreSQL 中，`FOR EACH ROW` 触发器的 DELETE 操作：
- `NEW` 为 NULL
- `OLD` 包含被删除行的值

当前触发器在 DELETE 评分时会报错（`NEW.submission_id` 为 NULL）。

**影响范围**：虽然设计文档说不授权 DELETE（"评分不可删除"），但触发器定义中声明了 `OR DELETE`，这是一个隐患。如果未来通过 RPC 或 service_role 执行 DELETE，触发器会崩溃。

**修复建议**：

```sql
CREATE OR REPLACE FUNCTION public.update_recommendation_score()
RETURNS trigger
LANGUAGE plpgsql
AS $$
DECLARE
  target_id text;
BEGIN
  target_id := COALESCE(NEW.submission_id, OLD.submission_id);
  UPDATE public.recommendation_submissions
  SET recommend_score = public.compute_recommendation_score(target_id)
  WHERE id = target_id;
  RETURN COALESCE(NEW, OLD);
END;
$$;
```

或者，既然评分不删除，触发器只监听 INSERT OR UPDATE：

```sql
CREATE TRIGGER trg_rec_ratings_update_score
  AFTER INSERT OR UPDATE ON public.recommendation_ratings
  FOR EACH ROW
  EXECUTE FUNCTION public.update_recommendation_score();
```

**建议**：采用 `COALESCE(NEW, OLD)` 方案——即使当前不 DELETE，防御性编码更安全。

## 三、重要问题（建议修正，否则后续返工）

### 🟡 问题 4：`add_count` 变化不触发 score 重算

**位置**：`02_设计与规范.md § 八`（score 更新触发器仅挂在 ratings 上）

**问题描述**：

推荐值公式：

```
score = add_count + recommend_count × 2 - not_good_count
```

- `recommend_count` 和 `not_good_count` 变化时 → 触发器触发 score 重算 ✅
- `add_count` 变化时 → **无触发器，score 不更新** ❌

`add_count` 在 `addRecommendationToBookshelf` 中增加，但没有对应的 score 更新机制。

**修复建议**：在问题 2 的 RPC 函数中同时更新 score（已在上述修复方案中体现）。或者为 `add_count` 增量创建一个专门的 RPC 函数，内部同时调用 `compute_recommendation_score`。

---

### 🟡 问题 5：缺少 `add_count` 的去重存储方案

**位置**：`03_实施方案.md § 6.1`

**问题描述**：

文档讨论了三种去重方案但没有明确选择：

1. `recommendation_adds(submission_id, user_id)` 轻量表 — "第一阶段"不采用
2. 从 `import_items` 表查询 `COUNT(DISTINCT user_id) WHERE share_source_id = submission_id AND origin = 'featured'` — 需要突破 RLS
3. 应用层查询判断 — "第一阶段用应用层查询判断"

方案 3 的问题是：`add_count` 作为缓存字段存储在 submission 行上，应用层查询判断后手动 `add_count + 1` 的方式在并发场景下不安全（race condition）。

方案 2 的问题是：`COUNT(DISTINCT user_id)` 需要跨越多个用户的 import_items，RLS 也会阻断。

**修复建议**：

在问题 2 的 RPC 函数中完成去重判断和原子增量，数据库层保证一致性。`add_count` 的权威来源是第一阶段的 `SELECT COUNT(*) FROM import_items WHERE share_source_id = ? AND origin IN ('featured', 'featured_legacy') AND deleted_at IS NULL`——这个查询在 RPC 内部（SECURITY DEFINER 绕过 RLS）执行。

实现建议：
```sql
-- RPC 内部
SELECT COUNT(DISTINCT user_id) INTO true_count
FROM public.import_items
WHERE share_source_id = p_submission_id
  AND origin IN ('featured', 'featured_legacy')
  AND deleted_at IS NULL;

UPDATE public.recommendation_submissions
SET add_count = true_count
WHERE id = p_submission_id;
```

### 🟡 问题 6：Phase 2 与 Phase 3 之间存在破坏性时间窗口

**位置**：`04_执行计划.md § 十一`（阶段切换条件）

**问题描述**：

```
Phase 2: DROP featured_articles 表
Phase 3: ImportPage 推荐 Tab 切换数据源（featured_articles → recommendation_submissions）

执行计划的依赖图显示 Phase 2 和 Phase 3 **可并行**，但切换条件说"Phase 2 必须早于或同步于 Phase 3"。

Phase 2: 迁移数据 + DROP 旧表

```

### 🟡 问题 7：`checkReadingCompleted` 的查询效率问题

**位置**：`03_实施方案.md § 3.2.4`

**问题描述**：

```js
async function checkReadingCompleted(userId, importItemId) {
  const articles = await fetchArticlesBySourceImportId(importItemId, userId)
  for (const article of articles) {
    const mark = await fetchReadingMark(userId, article.id)  // N+1 查询
    if (mark?.completed) return true
  }
  return false
}
```

`fetchArticlesBySourceImportId` 尚不存在（见问题 11），且在循环中逐条查 reading_mark 会产生 N+1 问题。虽然实际场景中一个 import_item 通常只对应 1-2 篇 article，但在数据库层面可以更高效。

**修复建议**：使用单条 SQL（通过 RPC 或者 JOIN）：

```sql
-- RPC: check_import_item_reading_completed
SELECT EXISTS (
  SELECT 1 FROM public.articles a
  JOIN public.reading_marks rm ON rm.article_id = a.id AND rm.user_id = a.user_id
  WHERE a.source_import_id = p_import_item_id
    AND a.user_id = p_user_id
    AND rm.completed = true
    AND a.deleted_at IS NULL
);
```

此查询在用户自己的数据范围内（articles + reading_marks 都属于调用者），不触发跨用户 RLS 问题，可直接通过 Supabase 客户端执行。

### 🟡 问题 8：`add_count` 未考虑用户移除书架的情况

**位置**：`02_设计与规范.md § 3.1`（add_count 定义）

**问题描述**：

文档定义 `add_count` 为"多少人通过推荐区将该条目加入了书架。去重计数（同用户多次添加/删除只计一次）"。

但如果用户 A 加入了推荐内容后，又在书架上删除了该 import_item（软删除 `deleted_at`），`add_count` 是否应该减 1？

当前设计没有处理这个场景。如果用户 A 删除后重新加入，算 1 次（去重）；但如果用户 A 永久删除，该用户是否仍计入 `add_count`？

**修复建议**：明确语义——`add_count` 是"当前书架上有该推荐内容的去重用户数"还是"历史累计添加过的去重用户数"。建议采用前者（当前活跃数），通过 RPC 直接从 `import_items` 表实时计算：

```sql
SELECT COUNT(DISTINCT user_id)
FROM public.import_items
WHERE share_source_id = p_submission_id
  AND origin IN ('featured', 'featured_legacy')
  AND deleted_at IS NULL;
```

并在 `deleteImportItem` RPC 被调用时（用户删除书架内容），触发 `add_count` 的重新计算。

### 🟠 问题 11：`share_source_id` 语义扩展未在文档中记录

**位置**：`02_设计与规范.md § 3.4.1`，`03_实施方案.md § 3.2.3`

- `origin='featured'` 时，`share_source_id` 存储的是 **`recommendation_submissions.id`**（如 `rec_1718500000_abc12`），而非另一个 `import_items.id`（如 `imp_1718500000_xyz89`）

### 🟠 问题 12：`origin: 'featured'` 的 bug 修复时机

**位置**：ImportPage.jsx 第 332 行

当前代码：
```js
await createImportItem({ ... }, { userId, origin: 'featured' })
```

在 origin CHECK 约束扩展（Phase 0.1）之前，这段代码会因数据库约束拒绝而失败。即：
- **修复前**：点击"加入书架"→ 数据库拒绝 origin='featured' → 报错
- **Phase 0.1 后**：CHECK 约束扩展，`origin='featured'` 可写入

**修复建议**：在 Phase 3（前端改造）之前，Phase 0.1 可以先部署约束扩展（消除数据库层面的拒绝），但 ImportPage 的推荐 Tab 需要整个替换。在过渡期（Phase 0.1 完成 → Phase 3 完成），推荐 Tab 的"加入书架"功能虽然不再因数据库约束报错，但 `share_source_id` 不会被正确设置，导致该条目无法被追踪为"从推荐区加入"。

这个过渡期可以接受——因为 Phase 2 之后 featured_articles 表被 DROP，推荐 Tab 根本无法加载旧数据。

### 🟠 问题 13：匿名用户浏览推荐的 `source_url` 隐私考虑

**位置**：`02_设计与规范.md § 六`（RLS 策略），`03_实施方案.md § 6.3`

推荐条目的 `source_url` 对所有用户（包括匿名）可见。如果用户导入了一篇付费文章或私有链接并提交推荐，`source_url` 中的敏感信息（如带 token 的 URL）会泄露。

**修复建议**：在提交推荐时，前端对 `source_url` 做基本检查——如果包含常见敏感参数（`token`、`key`、`auth`、`password` 等 query string），提示用户确认。或者在提交前清理 URL（去掉 query string）。

这是远期优化项，不阻塞实施。
