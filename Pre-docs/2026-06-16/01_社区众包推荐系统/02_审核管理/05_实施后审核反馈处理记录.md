## 二、逐项处理详情

### 🔴1：`syncAddCountAfterDelete` — `error` 变量未定义

**问题**：`recommendationService.js` L474 调用 `client.rpc('increment_recommendation_add_count', ...)` 但未解构 `{ error }`，导致 L478 的 `error` 始终为 undefined。RPC 失败时错误向上抛出而非被静默处理，与注释所述的"非致命"语义矛盾。

**处理**：在 `client.rpc()` 调用前补全 `const { error } = ` 解构。

**影响文件**：
- `src/services/supabase/recommendationService.js` — L474 补全解构（1 行改动）

---

### 🔴4：`handleDeleteImportItem` 未调用 `syncAddCountAfterDelete`

**问题**：

1. `handleDeleteImportItem` 接收参数为 `id`（字符串），删除后 item 数据从 state 中丢失（`setImportItems(prev => prev.filter(i => i.id !== id))`），无法获知 `origin`、`shareSourceId` 等信息
2. `syncAddCountAfterDelete` 已导出但从未被任何组件调用——add_count 递减链路完全缺失

**处理**：

1. **ImportItemList.jsx**：
   - 新增 `deleteTargetItem` state 存储完整 item 对象
   - `handleDeleteClick` 新增第三个参数 `item`（完整对象）
   - `confirmDelete` 改为调用 `onDelete(deleteTargetItem)`（传完整对象）
   - 所有调用 `handleDeleteClick` 的地方传入完整 `item` 对象

2. **ImportPage.jsx**：
   - `handleDeleteImportItem` 参数从 `(id)` 改为 `(item)`
   - 函数体开头增加：若 `item.origin ∈ {featured, featured_legacy}` 且 `item.shareSourceId` 非空 → 调用 `syncAddCountAfterDelete(item).catch(() => {})`（非致命，失败不阻塞删除）
   - 再执行 `deleteImportItemService(item.id)`

**设计说明**：`syncAddCountAfterDelete` 在删除前调用（需要 item 完整数据），失败不阻塞删除——`catch(() => {})` 确保"非致命"语义。与 `delete_import_item` RPC 不在同一事务中（前端两次请求），但 `add_count` 是缓存字段——短暂不一致可接受。

**影响文件**：
- `src/components/ImportItemList.jsx` — state 扩展 + `handleDeleteClick`/`confirmDelete` 调整（~10 行）
- `src/components/ImportPage.jsx` — `handleDeleteImportItem` 重写（~8 行）
