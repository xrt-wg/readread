### 7.1 越权闸门对「匿名调用」失效（SQL 三值逻辑）— 已修复（a2bf745）

- **现象**：Dashboard 执行 `20260929000000` 迁移后，匿名（`auth.uid() IS NULL`）调用 `get_due_bookmarks` 未按预期被 42501 拒绝，而是穿透闸门直抵触发器，报 `42703: record "new" has no field "quota_consumed"`。
- **根因**：SQL 三值逻辑。原闸门 `IF p_user_id IS NULL OR p_user_id <> auth.uid() THEN` 在 `auth.uid() IS NULL` 时，`p_user_id <> auth.uid()` 求值为 **NULL（非 TRUE）**，`IF NULL` 不进分支，闸门被绕过 → 匿名越权面仍在。
- **处置**：4 函数闸门统一改为 `IF p_user_id IS NULL OR auth.uid() IS NULL OR p_user_id <> auth.uid() THEN`，显式空判堵住匿名越权。
- **状态**：✅ 已修复；4 个 RPC（`get_due_bookmarks` + 3 个 reading-mark RPC）匿名/越权调用均已实测 42501。

### 7.2 JWT 验签算法不符（ES256 vs HS256）— 已修复（9e63484）

- **现象**：已登录用户调用 `proxy` / AI 精译 / `generate-recommendation` 等鉴权函数均 401，登录态形同失效（直译路径因 fail-open 掩盖了该问题）。
- **根因**：`verifyJwt` 用 HS256（`SUPABASE_JWT_SECRET`）验签，但本项目 Supabase 默认签发 **ES256**（非对称）令牌，`alg` 不符 → 验签必失败。审核报告 P0-1「配 `SUPABASE_JWT_SECRET` 与 Supabase 一致」的建议在 ES256 下**不生效**（HS256 密钥无法验 ES256 令牌），属报告遗漏。
- **处置**：重写 [netlify/lib/auth.cjs](../../../netlify/lib/auth.cjs) `verifyJwt`：按 token 头 `alg` 分支——ES256 走 Supabase JWKS（`/.well-known/jwks.json`）取公钥验签（`jwkToPem` + `crypto.createPublicKey`，kid 未命中强制重取、10 分钟缓存），HS256 保留 `SUPABASE_JWT_SECRET` 兜底。三函数（`proxy` / `translate` LLM / `generate-recommendation`）调用点由同步改为 `await verifyJwt(event)`。
- **影响**：此缺陷使三函数鉴权对**所有已登录用户**均 401，属 P0 级功能阻断（此前被直译 fallback 掩盖）。
- **状态**：✅ 代码完成 + 已推送 + 已部署回归确认（URL 导入正常、精译非 401）。SSRF 私网 403 / 非 http 400 分支本次未改动（沿用 fc63907），维持既有实现。
