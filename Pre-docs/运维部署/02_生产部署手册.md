## 1. 分支策略

三个长线分支，一条开发流程：

```
feat/xxx                  develop              internal-test           master
   │                          │                      │                    │
   │  PR → Deploy Preview    │                      │                    │
   ├────────────────────────→│                      │                    │
   │                          │                      │                    │
   │              合并到 develop                    │                    │
   │         push 触发 → 自动部署到                  │                    │
   │          develop--readread.netlify.app          │                    │
   │                          │                      │                    │
   │                          │   merge → push 触发   │                    │
   │                          ├─────────────────────→│                    │
   │                          │     自动部署到         │                    │
   │                          │  internal-test域名     │                    │
   │                          │                      │                    │
   │                          │           内部验证通过  │  merge → push 触发 │
   │                          │                      ├───────────────────→│
   │                          │                      │     自动部署到生产   │
```

| 分支 | 用途 | 部署域名 |
|------|------|----------|
| `feat/xxx` | 功能开发，完成后提 PR → `develop` | PR 时自动生成 Deploy Preview |
| `develop` | 日常集成，随时可查看最新效果 | `develop--readread.netlify.app` |
| `internal-test` | 发布前内部验证 | `internal-test--readread.netlify.app` |
| `master` | 生产环境 | 生产域名（Netlify Production） |

## 2. Netlify 后台配置

```
Site configuration → Build & deploy → Branches and deploy contexts

  Production branch:  master

  Branch deploys:
    ☑ develop
    ☑ internal-test

  Deploy previews:
    ☑ Any pull request against your production branch / branch deploy branches
```

部署由 **Git push 自动触发**，无需手动操作 Netlify CLI。

## 3. 发布操作步骤

### 阶段一：功能开发

```bash
git checkout develop
git checkout -b feat/my-feature

# 本地开发 + 测试
npx netlify dev

git add .
git commit -m "feat: xxx"
git push origin feat/my-feature
```

在 GitHub 上创建 PR：`feat/my-feature` → `develop`。Netlify 自动生成 Deploy Preview 链接，可用于功能级验证。审查通过后合并 PR，**合并时 push 到 develop 会触发自动部署**到 `develop--readread.netlify.app`。

### 阶段二：内部测试部署

```bash
git checkout develop
git pull origin develop

# 将 develop 合并到 internal-test
git checkout internal-test
git merge develop
git push origin internal-test
```

Push 后 Netlify 自动部署到 `internal-test--readread.netlify.app`，在真实环境进行全链路验证。

### 阶段三：生产发布

```bash
# internal-test 验证通过后
git checkout master
git merge internal-test
git push origin master
```

Push 后 Netlify 自动部署到生产环境。

**总结——push 即部署：**

| 推送分支 | 自动部署到 |
|----------|-----------|
| `develop` | `develop--readread.netlify.app` |
| `internal-test` | `internal-test--readread.netlify.app` |
| `master` | 生产域名 |

## 4. 发布前验证清单

在 `internal-test` 部署后、合并到 `master` 之前，逐项确认：

- [ ] 构建成功（无 build error / warning）
- [ ] 书架 → 导入 → 阅读 → 收藏 → 翻译 → 回顾 全链路可用
- [ ] AI 翻译正常（主 Provider + Fallback）
- [ ] AI 推荐生成正常
- [ ] EPUB 导入正常
- [ ] 登录 / 注册 / 匿名模式可用
- [ ] 管理后台权限隔离正常
- [ ] 环境变量注入正确（前端 VITE_* + 服务端 API Keys）
- [ ] 移动端布局无严重错乱

## 5. 回滚

| 层级 | 操作 |
|------|------|
| 前端 / Functions | Netlify 后台 → Deploys → 选择上一个正常部署 → "Publish deploy" |
| 环境变量 | Netlify 后台 → Site configuration → Environment variables → 修改回旧值 |
| 数据库 | **原则上不做数据库回滚**，优先前向修复。紧急情况可在 Supabase 控制台通过 SQL 手动修复，或从备份恢复 |

---

## 6. 环境差异

当前三个部署环境（develop / internal-test / master）共用同一个 Supabase 实例和同一套环境变量。未来如需隔离，可在 Netlify 后台为每个 branch deploy context 配置独立的 **Branch-specific environment variables**。
