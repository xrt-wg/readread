## 1. 项目概览

**ReadRead** 是一个英语阅读学习平台，技术栈如下：

| 层级 | 技术 | 说明 |
|------|------|------|
| 前端框架 | React 18 + Vite 5 | SPA，入口 `src/main.jsx` |
| 样式 | Tailwind CSS 3 + PostCSS | `src/index.css` |
| 后端/数据库 | Supabase | 认证、文章、书签、阅读进度、推荐系统 |
| Serverless | Netlify Functions（4 个） | AI 翻译、推荐生成、URL 代理、EPUB 解析 |
| AI 服务 | Gemini / DeepSeek / Kimi / Zhipu | 通过 Netlify Functions 代理调用 |
| 直译服务 | DeepL / 有道 | 通过 `translate.js` Function 代理调用 |
| 内容提取 | URL / Paste / Markdown / HTML / EPUB | 前端 + Netlify Function（EPUB） |

**三种运行模式：**

| 模式 | 命令 | 说明 |
|------|------|------|
| 纯前端 | `npm run dev` | 仅启动 Vite 开发服务器，Function 调用会失败 |
| 完整本地 | `npx netlify dev` | 同时启动 Vite + Netlify Functions，功能完整 |
| 生产构建预览 | `npm run build && npm run preview` | 构建产物预览 |

## 3. 快速开始（纯前端）

适用场景：仅调试 UI/组件，不需要 AI 翻译、推荐生成等功能。

```bash
# 1. 克隆项目
git clone <repo-url> readread
cd readread

# 2. 切换到开发分支
git checkout feat/bookshelf-zone

# 3. 安装依赖
npm install

# 4. 配置环境变量（复制 .env 文件到项目根目录，见第 5 节）

# 5. 启动开发服务器
npm run dev
```

Vite 开发服务器默认在 `http://localhost:5173` 启动。

> ⚠️ **限制**：此模式下所有 Netlify Function 调用（`/.netlify/functions/*`）将返回 404，因为 Vite 不会代理这些路由。AI 翻译、推荐生成、EPUB 导入等功能不可用。

## 4. 完整本地环境（含 Netlify Functions）

适用场景：全功能本地测试，包括 AI 翻译、推荐生成、EPUB 解析等。

### 4.1 安装 Netlify CLI

```bash
npm install -g netlify-cli
```

验证安装：
```bash
npx netlify --version
```

### 4.2 配置环境变量

确保项目根目录存在 `.env` 文件，内容参见[第 5 节](#5-环境变量说明)。

> 📌 `.env` 文件已在 `.gitignore` 中，不会被提交到 Git。文件中可以存放真实的 API Key。

### 4.3 处理端口冲突

Vite 默认使用 **5173** 端口。如果该端口被其他项目占用，需要在 `netlify.toml` 的 `[dev]` 段中指定备用端口：

```toml
# netlify.toml
[dev]
  command = "npm run dev"
  targetPort = 5174   # Vite 开发服务器端口（避开已被占用的端口）
  port = 8888         # 浏览器访问端口（Netlify CLI 统一代理入口）
```

| 参数 | 作用 | 默认值 |
|------|------|--------|
| `targetPort` | Vite 实际运行的端口 | 框架自动检测（5173） |
| `port` | 用户浏览器访问的端口 | 8888 |

> 📌 Netlify CLI 的端口架构：`浏览器 → :8888 (CLI代理) → :targetPort (Vite)`，用户始终通过 `port` 访问。

### 4.4 启动 Netlify Dev

```bash
# 在项目根目录执行
npx netlify dev
```

Netlify CLI 会自动：
1. 读取 `netlify.toml` 配置（含 `[dev]` 端口设置）
2. 加载 `.env` 中的环境变量
3. 启动 Vite 开发服务器（`targetPort`，默认 5173 / 已占用则自动递增）
4. 启动 Netlify Functions 本地服务
5. 在 `port` 端口（默认 8888）启动统一代理入口
6. 自动代理 `/.netlify/functions/*` 请求到对应 Function

默认访问地址：`http://localhost:8888`

> 📌 `[dev]` 段中已配置 `publish = ""` 覆盖 `build.publish = "dist"`，避免遗留 `dist/_redirects` 在 dev 模式下把 Vite 模块重写为 `index.html` 导致白屏。详见 §9.10。

### 4.5 验证 Functions 是否正常

启动后，在浏览器控制台中可以通过以下方式验证：

```javascript
// 测试 translate function（需要有效的 provider）
fetch('/.netlify/functions/translate', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    prompt: 'Translate "hello" to Chinese',
    maxTokens: 50,
    provider: 'deepseek-preset',
    requestId: 'test-1'
  })
}).then(r => r.json()).then(console.log)
```

## 7. Netlify Functions 本地调试

### 7.1 四个 Function 说明

| Function | 文件 | 请求方式 | 用途 |
|----------|------|----------|------|
| `translate` | `netlify/functions/translate.js` | POST | AI 翻译（Gemini/DeepSeek/Kimi/Zhipu）+ 直译（DeepL/有道） |
| `generate-recommendation` | `netlify/functions/generate-recommendation.js` | POST | 推荐内容生成（intro/keywords/excerpts） |
| `proxy` | `netlify/functions/proxy.js` | GET | URL 代理抓取（绕过 CORS） |
| `parse-epub` | `netlify/functions/parse-epub.cjs` | POST | EPUB 文件解析（服务端运行 epub2md） |

### 7.2 查看 Function 日志

启动 `npx netlify dev` 后，所有 Function 的 `console.log` / `console.error` 会直接输出到终端。

AI 相关 Function 使用了结构化的性能日志：
- `translate_perf` — 翻译请求性能
- `recommendation_perf` — 推荐生成性能
- `recommendation_attempt_failed` — 推荐生成重试
- `direct_perf` — 直译（DeepL/有道）性能

### 7.3 使用 curl 测试 Function

```bash
# 测试 translate function
curl -X POST http://localhost:8888/.netlify/functions/translate \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Translate \"hello world\" to Chinese. Return only the translation.","maxTokens":50,"provider":"deepseek-preset","requestId":"test-1"}'

# 测试 proxy function
curl "http://localhost:8888/.netlify/functions/proxy?url=https://example.com"

# 测试 generate-recommendation function
curl -X POST http://localhost:8888/.netlify/functions/generate-recommendation \
  -H "Content-Type: application/json" \
  -d '{"articleText":"The quick brown fox jumps over the lazy dog. This is a sample article.","title":"Sample Article","author":"Test","requestId":"test-2"}'

# 测试 parse-epub function
curl -X POST http://localhost:8888/.netlify/functions/parse-epub \
  -H "Content-Type: application/json" \
  -d '{"base64":"<base64-encoded-epub-file>"}'
```

### 7.4 超时与性能

| Function | 默认超时 | 说明 |
|----------|----------|------|
| `generate-recommendation` | 26s | 在 `netlify.toml` 中配置 |
| `translate` | 10s | Netlify 默认值（Starter 套餐） |
| `proxy` | 10s | 内部使用 20s fetch 超时 |
| `parse-epub` | 10s | 大文件可能超时 |

前端 `recommendation.json` 中的 `timeout: 25000`（25s）应 ≤ Function 超时 - 1s。

## 8. Supabase 本地替代方案

### 8.1 使用生产 Supabase（推荐用于开发）

项目默认连接的是生产 Supabase 实例。只要配置了 `VITE_SUPABASE_URL` 和 `VITE_SUPABASE_ANON_KEY`，开发环境即可直接使用。

这是**推荐方式**，因为：
- 数据与生产环境共享
- 无需额外搭建
- 认证流程一致

### 8.2 使用 Supabase 本地 CLI（可选）

如果需要完全离线的开发环境：

```bash
# 1. 安装 Supabase CLI
npm install -g supabase

# 2. 初始化（需 Docker）
supabase init

# 3. 启动本地 Supabase
supabase start

# 4. 修改 .env 中的 VITE_SUPABASE_URL 和 VITE_SUPABASE_ANON_KEY
# 为 supabase start 输出的本地地址
```

> ⚠️ 本地 Supabase 需要 Docker 运行。本地数据库表结构需要从生产环境迁移。

### 8.3 匿名模式（无账号）

应用支持不登录使用（`anonymous` 状态）：
- 数据存储在浏览器 `localStorage` 中
- 阅读、收藏、回顾功能均可使用
- 无法使用云端同步、推荐系统等需要认证的功能
- 登录后会自动将本地数据静默导入到 Supabase

测试方式：启动应用后直接使用，不点击登录即可。

## 9. 常见问题

### 9.1 `npm run dev` 后页面空白

**检查清单：**
1. `.env` 文件是否存在且包含 `VITE_SUPABASE_URL` 和 `VITE_SUPABASE_ANON_KEY`
2. 浏览器控制台是否有报错
3. 检查 `node_modules` 是否完整安装：`rm -rf node_modules && npm install`

### 9.2 AI 翻译报错 "服务暂时不可用"

**原因**：使用了 `npm run dev` 而不是 `netlify dev`，Netlify Functions 不可用。

**解决**：使用 `npx netlify dev` 启动。

### 9.3 AI 翻译返回 500

**检查清单：**
1. `.env` 中对应 Provider 的 API Key 是否已填写
2. 查看终端中 Netlify Function 的错误日志
3. 确认 API Key 额度是否充足
4. 确认 Provider 的 API 端点是否可访问

### 9.4 EPUB 导入失败

- 检查 EPUB 文件是否受 DRM 保护
- 大文件（>10MB）可能超时
- 查看终端 `parse-epub` Function 的日志

### 9.5 登录后一直显示 "正在同步阅读数据…"

**原因**：首次登录时应用会将 localStorage 中的旧数据静默导入到 Supabase。如果数据量较大，导入时间较长。

**解决**：等待导入完成（通常几秒到几十秒）。如果持续卡住，在浏览器控制台执行：
```javascript
localStorage.clear()
location.reload()
```

### 9.6 "账号配置缺失" 错误

**原因**：缺少 Supabase 环境变量。

**解决**：检查 `.env` 文件中是否包含 `VITE_SUPABASE_URL` 和 `VITE_SUPABASE_ANON_KEY`。重启开发服务器使环境变量生效。

### 9.7 Windows 下 PowerShell 脚本执行问题

如果遇到脚本执行策略限制：
```powershell
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
```

### 9.8 `npx netlify dev` 启动后 8888 端口白屏

**现象**：访问 `http://localhost:8888/` 页面空白，浏览器控制台报错：

```
Failed to load module script: Expected a JavaScript-or-Wasm module script
but the server responded with a MIME type of "". Strict MIME type checking
is enforced for module scripts per HTML spec.
```

同时终端日志中每个请求都显示 `⬥ Rewrote URL to /index.html`。

**根本原因**：`netlify.toml` 中的 `[[redirects]]` 规则 `/* → /index.html (200)` 在本地 dev 模式下也会生效，且 `status = 200` 的默认行为是 `force = true`（无条件重写），导致所有 JS/CSS 模块请求也被重写为 `/index.html`，浏览器拿到 HTML 文本却缺少 MIME type 头。

**解决**：将 SPA 重定向规则从 `netlify.toml` 移除，改为放入 `public/_redirects` 文件。这样 redirect 规则只在生产构建（`dist/`）中生效，本地 dev 由 Vite 的原生 SPA fallback 接管。

```bash
# public/_redirects — 仅生产环境生效，本地 netlify dev 不读取
/*    /index.html    200
```

```toml
# netlify.toml — 删除或注释掉 [[redirects]] 段
# 本地 dev 和 生产部署 的 redirect 处理路径不同：
#   本地 dev: Vite 内置 SPA fallback
#   生产部署: Netlify CDN 读取 dist/_redirects
```

> 📌 `public/_redirects` 在 `npm run build` 时会被复制到 `dist/_redirects`，Netlify CDN 在部署时读取该文件。CDN 的 200 重写实现正确区分了「真实文件」和「SPA 路由」，而本地 CLI 的模拟没有这个能力。

> ⚠️ **注意前提**："本地 dev 不读取"仅指 netlify dev 不读取源码里的 `public/_redirects`。**一旦本地存在已构建的 `dist/`，netlify dev 会读取 `dist/_redirects` 使本问题原样复发**——见 §9.10。

### 9.9 Vite 端口 5173 被其他项目占用

**现象**：启动 `npm run dev` 或 `npx netlify dev` 时报端口占用，或 Vite 自动跳到其他端口。

**解决**：在 `netlify.toml` 的 `[dev]` 段中显式指定端口：

```toml
[dev]
  command = "npm run dev"
  targetPort = 5174   # 选一个空闲端口
  port = 8888
```

修改后重启 `npx netlify dev` 即可。详见[第 4.3 节](#43-处理端口冲突)。

### 9.10 `npx netlify dev` 白屏复发 —— 本地遗留 `dist/` 触发

**现象**：与 [§9.8](#98-npx-netlify-dev-启动后-8888-端口白屏) 完全相同的报错：

```
Failed to load module script: Expected a JavaScript-or-Wasm module script
but the server responded with a MIME type of "". ...
```

区别在于：**SPA 重定向明明已经移到 `public/_redirects` 了（§9.8 的根治方案），却仍然报错**。

**根本原因**：`netlify dev` 以 `netlify.toml` 中 `publish = "dist"` 为静态发布目录。只要本地**存在 `npm run build` 产生的 `dist/`**，其中的 `dist/_redirects`（由 `public/_redirects` 复制而来）就会被 `netlify dev` 读取，那条 `/* → /index.html 200` 的 catch-all 再次生效，把 Vite dev 的模块请求（`/src/main.jsx`、`/@react-refresh` 等）重写为 `/index.html`。

即：§9.8 把规则移出 `netlify.toml` 只解决了「源码态」的读取；**「已构建态」的 `dist/_redirects` 仍是同一个坑的入口**。

**解决**：删除遗留的构建产物后重启。

```bash
rm -rf dist
npx netlify dev
```

**预防**：
- 用 `netlify dev` 做本地开发时，保持 `dist/` 干净——它是构建产物（已在 `.gitignore`），不该在 dev 期间存在。
- 若需要用 `npm run build` 校验构建，验完即删 `dist/`，或构建到临时目录（`vite build --outDir .build-check` 后清理），避免污染 dev。

> 📌 §9.8 与 §9.10 是**同一根因的两个入口**：SPA catch-all 在本地 CLI 下无法区分「真实文件」与「路由」。§9.8 堵住 `netlify.toml` 源，§9.10 提醒堵住 `dist/` 源。
