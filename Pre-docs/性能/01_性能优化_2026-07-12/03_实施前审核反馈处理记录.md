## 三、方案正确性风险修正

### 3.1 方案 1.5 — saveReadingMark 数据丢失风险

| 项目 | 内容 |
|------|------|
| **审核指出** | 原方案硬编码 `completed: false`、`completedSections: []`，会覆盖已存在的数据 |
| **影响** | 用户已完成的分段阅读进度（completedSections）会被清空 |
| **修正方案** | 改用 3 个独立 Supabase RPC 函数：`upsert_reading_mark_position`（只更新 paragraph_index/progress_percent/section_id，保留 completed）、`clear_reading_mark_position`（只清 paragraph_index）、`set_reading_mark_completed`（设置 completed=true）。使用 `COALESCE(EXCLUDED.field, existing.field)` 确保未指定字段保留原值 |
| **文档** | 优化方案 1.5 完全重写，含完整 SQL + 前端调用代码 |

### 3.2 方案 1.1 — AuthPanel 条件渲染遗漏

| 项目 | 内容 |
|------|------|
| **审核指出** | React.lazy 方案的 Suspense 代码未体现原 `view !== 'admin' ? <AuthPanel ... /> : null` 条件渲染 |
| **修正** | 在 Suspense 内部补回 `{view !== 'admin' ? <AuthPanel onOpenAdmin={...} triggerOpen={...} /> : null}` |
| **文档** | 优化方案 1.1 代码示例已补充 |

### 3.3 方案 1.8 — 批量导入字段映射不一致

| 项目 | 内容 |
|------|------|
| **审核指出** | 直接硬编码字段映射，绕过了 `saveReading` 的数据转换逻辑 |
| **修正** | 新增前置步骤：从 `saveReading` 提取共享字段映射函数 `toReadingDbRow(article, userId)`，批量 upsert 复用该映射，指定 `onConflict: 'id'` |
| **文档** | 优化方案 1.8 拆为 Step 1（提取映射函数）+ Step 2（批量 upsert） |

### 3.4 方案 1.6 — 索引 DROP+CREATE 空窗风险

| 项目 | 内容 |
|------|------|
| **审核指出** | #1 和 #7 的 `DROP INDEX IF EXISTS` + `CREATE INDEX` 在迁移期间有索引不存在的时间窗口 |
| **修正** | 拆为两次 migration：Migration A（`20260712000002_perf_indexes`）全部用 `CREATE INDEX IF NOT EXISTS` 建新索引，#1/#7 使用新名称与旧索引共存；Migration B（后续清理）`DROP INDEX IF EXISTS` 删除旧索引。去掉 `CONCURRENTLY`（Supabase Migration 在事务中执行，不支持） |
| **文档** | 优化方案 1.6 拆为 Migration A + Migration B 两部分 |

### 3.5 方案 4.4 — Web Worker 不可行

| 项目 | 内容 |
|------|------|
| **审核指出** | `@mozilla/readability` 需要 DOM API（`document`、`DOMParser`、`Node`），Web Worker 不提供 DOM 环境 |
| **修正** | 方案改为 `requestIdleCallback` 分片：将 `parseArticle` 和 `resolveImageUrls` 包裹在空闲回调中，避免长任务阻塞主线程。附 `scheduleIdleTask` 工具函数 |
| **备选方案** | 若 Readability 执行时间仍超一帧（16ms），可进一步探索 `linkedom` 在 Worker 中模拟 DOM |
| **文档** | 优化方案 4.4 完全重写 |

## 五、讨论项共识结论

### 5.1 CSS :hover 替换范围

| 讨论 | 结论 |
|------|------|
| **初始分歧** | 审核方建议"逐处审核，只替换静态 hover"；实施方坚持"全部替换，经审查全是静态的" |
| **共识** | 经逐处重新审查，确认全部内联 JS mouseEnter/mouseLeave 仅修改静态样式字符串，无一引用 useState/props。审核方撤回"分类保留"建议。方案 3.3 的「全部替换」策略成立 |
| **实现注意** | CSS 颜色值需与原 JS 中的 fallback 值精确对齐（如 `var(--ink)` vs `#1c1917`） |

### 5.2 服务端书签复习优先级

| 讨论 | 结论 |
|------|------|
| **初始分歧** | 审核方将 4.5 放在"暂缓执行"；实施方认为应提级到第二梯队 |
| **共识** | 量级分析确认：`listDueBookmarks` 的全量下载模式与 1.4（sections）本质相同，均为线性增长的无用传输。RPC 复杂度评估为中等偏下（核心 30 行 SQL）。同意从第三梯队提升到第二梯队 |
| **执行条件** | RPC 需在 Supabase SQL Editor 单独测试；确认返回列与 `mapBookmarkRow` 映射对齐 |

### 5.3 索引替换策略

| 讨论 | 结论 |
|------|------|
| **初始分歧** | 审核方建议"全部用 IF NOT EXISTS"；实施方指出 #1/#7 是替换而非新增 |
| **共识** | #2-#10 全部用 `CREATE INDEX IF NOT EXISTS`（新增）；#1 和 #7 拆为两次 migration（A 建新 → B 删旧）。去掉 `CONCURRENTLY`（Supabase Migration 事务限制，表规模小，普通索引可接受） |
