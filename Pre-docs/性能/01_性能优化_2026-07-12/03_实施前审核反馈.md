## 四、优化方案审核

### 4.1 有正确性风险 — ⚠️ 必须修复后再实施

#### ⚠️ 方案 1.5 — saveReadingMark 消除 fetch-before-upsert（风险：**数据丢失**）

**问题**: 方案建议直接 upsert 并硬编码 `completed: false`、`completedSections: []`、`progressPercent`。

```js
// ❌ 方案中的代码会导致数据丢失
return saveCloudReadingMarkRecord({
  articleId: readingId,
  paragraphIndex,
  completed: false,                    // 错误：应保留现有值
  completedSections: [],               // 错误：会清空已有的已完成 section 列表
  progressPercent,                     // 未传时会是 null，覆盖已有值
  updatedAt: new Date().toISOString(),
}, options.userId)
```

`saveReadingMark` 在阅读中频繁调用（每次滚动到新段落），此时 `completed` 和 `completedSections` 的状态必须保留。方案中 `setReadingMarkCompleted` 是另一个独立调用，它设置 `completed: true`。如果 `saveReadingMark` 将 `completed` 硬编码为 `false`，且 `completedSections` 设为 `[]`，用户已完成的分段阅读进度会丢失。

**建议修正**: 不能简单地去掉 fetch。正确做法是使用 **Supabase RPC 函数**只更新指定列：

```sql
CREATE OR REPLACE FUNCTION upsert_reading_mark_partial(
  p_user_id uuid,
  p_reading_id uuid,
  p_paragraph_index int,
  p_progress_percent int,
  p_section_id uuid DEFAULT NULL
) RETURNS void AS $$
BEGIN
  INSERT INTO public.reading_marks (user_id, reading_id, paragraph_index, progress_percent, section_id, updated_at)
  VALUES (p_user_id, p_reading_id, p_paragraph_index, p_progress_percent, p_section_id, NOW())
  ON CONFLICT (user_id, reading_id)
  DO UPDATE SET
    paragraph_index = EXCLUDED.paragraph_index,
    progress_percent = COALESCE(EXCLUDED.progress_percent, reading_marks.progress_percent),
    section_id = COALESCE(EXCLUDED.section_id, reading_marks.section_id),
    updated_at = NOW();
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
```

注意: `saveReadingMark`、`clearReadingMark`、`setReadingMarkCompleted` 三个函数各有不同的"必须保留的字段"，每个都需要独立的 RPC 或严格的 upsert 列控制。

#### ⚠️ 方案 1.1 — React.lazy 缺少 view 条件处理的完整性

**问题**: 方案中的 Suspense 包裹方式：

```jsx
<Suspense fallback={<PageLoader />}>
  {view === 'admin' ? <AdminPage onExit={() => setView('reader')} />
    : article ? <ReaderPage article={article} onBack={handleBack} />
    : <ImportPage onImport={handleImport} onOpen={handleOpen} ... />}
</Suspense>
```

原代码中 `AdminPage` 渲染时 `AuthPanel` 不渲染（`view !== 'admin'` 条件）。方案中没有体现 `AuthPanel` 的处理。

**建议修正**: 把 `AuthPanel` 的条件渲染也放入 Suspense 外部或内部正确位置，确保不影响现有行为。

#### ⚠️ 方案 1.8 — 批量导入字段映射不一致

**问题**: 方案硬编码了字段映射，但与原 `saveArticle`（实际是 `saveReading`）的映射逻辑可能不同。`saveReading` 内部通过 `mapReadingRow` 的反向映射处理数据，直接调用 `client.from('readings').upsert(chunk)` 绕过了这些逻辑，可能导致字段格式不一致。

**建议**: 
1. 先读取 `saveReading` 的实际数据转换逻辑（包括 `sections` 的序列化）
2. 确保批量 upsert 的字段映射与其一致
3. 指定 `onConflict: 'id'` 避免主键冲突时的默认行为

### 4.2 方案可行性存疑

| 方案 | 问题 | 建议 |

| **4.4** urlImport Web Worker 化 | `@mozilla/readability` 需要完整的 DOM API（`document`、`DOMParser`、`Node` 等），Web Worker 不提供 DOM 环境。直接迁移无法运行 | 方案改为: (a) 使用 `linkedom` 或 `jsdom` 在 Worker 中模拟 DOM；或 (b) 将 `DOMParser.parseFromString` 改为分片调用 `requestIdleCallback`；或 (c) 将整段逻辑保持主线程但包裹在 Scheduler API 中 |

## 七、总结

性能分析报告和优化方案的整体质量良好。42 项发现大多精准，优化方案的梯队划分合理。
