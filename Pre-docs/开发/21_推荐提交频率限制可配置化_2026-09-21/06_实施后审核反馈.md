## 三、发现的问题

### M1（中）　`recommendationService.js` 混入功能 22 的未提交改动，提交边界不干净

**证据：** `git diff src/services/supabase/recommendationService.js` 除本功能的 3 个新函数（`getRecommendationSubmissionQuota` / `getRecommendationSubmissionConfig` / `saveRecommendationSubmissionConfig`）外，还包含功能 22「推荐区正文策展」的改动：
- 新增 `normalizeTransArray`（[recommendationService.js:104-107](../../../src/services/supabase/recommendationService.js#L104-L107)）；
- `updateRecommendationEditorial` 的 `p_keywords_trans`/`p_excerpts_trans` 由 `.filter(Boolean)` 改为 `normalizeTransArray(...)`（[L119-120](../../../src/services/supabase/recommendationService.js#L119-L120)）；
- 新增 `updateRecommendationContent`（调 `admin_update_recommendation_content`，[L134-142](../../../src/services/supabase/recommendationService.js#L134-L142)）。

**影响：**
1. `05` §一「预计 2 个提交：迁移 + 前端」无法干净落地——该文件须在**同一文件内按功能拆成两个提交**，否则两功能互相粘连。
2. `05` §五「按提交 `git revert`」回滚：若按整文件提交，revert 会**连带回退功能 22**（反之亦然），回滚粒度被破坏。

**建议：** 提交时对 `recommendationService.js` 做**逐 hunk 拆分**（`git add -p`），本功能仅提交 3 个新函数 + 迁移 + 弹窗 + 面板 + `AdminPage`；功能 22 的 `normalizeTransArray`/`updateRecommendationContent`/译文数组改造另行提交。回滚亦按该拆分边界执行。

### L1　后台面板 dirty 检测存在字符串/数字类型不一致（false-positive）

[RecommendationConfigPanel.jsx:37-38](../../../src/components/RecommendationConfigPanel.jsx#L37-L38)：`change` 用 `event.target.value`（**字符串**）写入 `config.submissionLimitDays`，而 `saved.submissionLimitDays` 来自 RPC（**数字**）。`dirty = config.submissionLimitDays !== saved.submissionLimitDays` 用严格 `!==`，导致：

- 用户**重敲相同值**（如原值 7，再次输入「7」）时 `"7" !== 7` 为真 → 保存按钮被**误点亮**；
- 此时点保存会发送 `Number("7")=7`，后端做一次**无意义更新**并写一条 `before 7, after 7` 的冗余审计。

无 false-negative（不会漏掉真实改动），不产生错误数据，属轻微 UX 瑕疵。

**建议：** 统一类型后再比较，例如 `change` 内直接存数字（`Number(event.target.value)` 并对空串特殊处理），或 `dirty = Number(config.submissionLimitDays) !== saved.submissionLimitDays`。

### L2　「已提交 1 篇」文案硬编码计数，`usedCount > 1` 时失真

额度查询 RPC 已返回 `usedCount`，但前端 [SubmitRecommendationModal.jsx:22](../../../src/components/SubmitRecommendationModal.jsx#L22) 与后端 [迁移 SQL L130/L132](../../../supabase/migrations/20260921000002_recommendation_submission_config.sql#L130-L132) 均**硬编码「1 篇」**。当管理员把 N 调小（收紧）后，窗口内已存在 ≥2 篇提交的用户会看到「最近 N 天内已提交 **1** 篇推荐」，与事实不符。

**建议（二选一）：** 文案改用真实 `usedCount`（「已提交 X 篇」），或维持「1 篇」并在决策记录注明「默认/常态下单用户窗口内至多 1 篇，收紧 N 的过渡期可能显示不精确」。属产品口径，非必须改。
