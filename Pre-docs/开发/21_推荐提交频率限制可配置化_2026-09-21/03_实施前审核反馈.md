# 推荐提交频率限制可配置化 — 实施前审核反馈

> 日期：2026-09-21
> 审核对象：[01_讨论和决策记录](01_讨论和决策记录.md)、[02_实施方案](02_实施方案.md)
> 审核方式：逐条对照当前代码与全部 `supabase/migrations/*` 脚本，独立复核一致性、分析完备性、方案合理性与有效性。

## 结论（TL;DR）

**方案框架成立、现状调查基本准确，无阻断级缺陷；但存在 1 个高优先级缺口与 2 个中优先级缺口，建议补齐后再进入实施。**

整体判断：本次「现状调查」溯源**没有**出现 20 号文档式的过时问题——提交校验顺序、`first_reading_config` 范式（单行表 + `revoke all` + admin RPC 对 + 乐观并发 + 审计）、时区表达式、`create or replace` 保留 grant 等关键判断均与代码与迁移一致，D1–D6 决策合理且已与需求方确认。问题集中在三处：

1. **高**：提交弹窗新增了对 `get_recommendation_submission_quota` 的**硬依赖**，但方案未规定「迁移先于前端」的执行顺序、也未规定 RPC 失败时的降级——在手工迁移（Dashboard SQL Editor）与前端发布不同步的窗口内，弹窗会**静默退化为「暂无可提交内容」**。
2. **中**：三个新 RPC 只 `grant`、未 `revoke ... from public`，偏离了文档自述「对齐 `first_reading` 范式」的安全惯例。
3. **中**：文档声称 `coalesce(submission_limit_days, 1)` 是「配置行缺失」的防御，但该写法对「零行 `select into`」**不生效**，会静默放行（fail-open），与「不误放行」目标相悖。

---

## 一、高（部署顺序 / 降级缺失，会导致弹窗静默失效）

### H1　提交弹窗硬依赖新 RPC，但方案未规定迁移顺序与失败降级

**证据链：**

1. [02_实施方案.md:240-241](../../../Pre-docs/开发/21_推荐提交频率限制可配置化_2026-09-21/02_实施方案.md#L240-L241) 要求 `useEffect` 中把 `listSubmittableReadings()` 与 `getRecommendationSubmissionQuota()` **并行加载**，但全文未写：① RPC 不存在/报错时如何处理；② 迁移与前端发布的先后顺序。
2. 本项目的迁移**无本地 CLI，须经 Dashboard SQL Editor 手动执行**（见迁移脚本头注释 [02_实施方案.md:42](../../../Pre-docs/开发/21_推荐提交频率限制可配置化_2026-09-21/02_实施方案.md#L42)），与前端发布**天然不同步**。前端先于迁移上线是常态，此时 `get_recommendation_submission_quota` 尚不存在，PostgREST 返回「Could not find the function」。
3. 当前弹窗的加载写法是单 `Promise` 链：[SubmitRecommendationModal.jsx:13](../../../src/components/SubmitRecommendationModal.jsx#L13) 的 `listSubmittableReadings().then(...).catch(...).finally(...)`。若按 §3.3 的「并行加载」用 `Promise.all([list, quota])` 实现，`quota` 一旦 reject，`items` 永不被赋值（保持 `[]`），且 `error` 只在**表单分支**内渲染（[SubmitRecommendationModal.jsx:22-24](../../../src/components/SubmitRecommendationModal.jsx#L22-L24)），空态分支不展示 `error`。于是用户有可提交内容时却**无提示地看到「暂无可提交内容」**，提交入口整块消失。

**问题本质：** 把原本「失败仅影响空态列表」的弹窗，改成了「失败即静默失效整个提交流」；且方案既未声明迁移先行，也未要求对额度查询做**独立容错**。

**修复建议（二选一，推荐 A + B 都做）：**
- A. 方案中明确执行顺序：**先手工执行迁移、确认三个 RPC 可用，再发布前端**（可作为验收前的前置步骤）。
- B. 额度查询与列表查询**拆开**、额度查询失败时**降级为现状行为**（仅展示列表、不做额度门控）：额度 RPC 用独立的 `catch`，失败时 `setQuota(null)`，渲染分支把 `quota && !quota.canSubmit` 之外的路径走原有逻辑；后端提交校验本就是权威兜底，降级不产生安全缺口。

## 二、中（安全惯例 / 一致性）

### M1　三个新 RPC 缺少 `revoke all ... from public`，偏离自述的「对齐 first_reading 范式」

**证据：**

- [02_实施方案.md:191-193](../../../Pre-docs/开发/21_推荐提交频率限制可配置化_2026-09-21/02_实施方案.md#L191-L193) 对三个新函数只写了 `grant execute ... to authenticated`，没有先 `revoke`。
- 而文档自述「结构、RLS 锁定、乐观并发、审计日志全部对齐 `first_reading_config` 范式」（[01_讨论和决策记录.md:58](../../../Pre-docs/开发/21_推荐提交频率限制可配置化_2026-09-21/01_讨论和决策记录.md#L58)）。该范式对新函数**总是先 `revoke all ... from public, anon, authenticated` 再 `grant`**：见 [20260917000003_first_reading_offer.sql:223-226](../../../supabase/migrations/20260917000003_first_reading_offer.sql#L223-L226) 与 [20260917000004_first_reading_admin.sql:64-65](../../../supabase/migrations/20260917000004_first_reading_admin.sql#L64-L65)。
- PostgreSQL 建函数默认 `EXECUTE` 授予 `PUBLIC`（`anon` 是其成员）。缺失 `revoke` 后，`anon` 仍可经 PostgREST 调这三个 RPC——虽然函数内 `auth.uid() is null` / `is_current_user_admin()` 守卫会拦下并报错，**功能上暂不可利用**，但违背了既定安全惯例，也丢掉了「即便未来误改内部守卫也不至于暴露」的纵深防御。

**建议：** 在三个 `grant` 之前补：
```sql
revoke all on function public.get_recommendation_submission_quota(),
  public.admin_get_recommendation_submission_config(),
  public.admin_save_recommendation_submission_config(integer, timestamptz)
  from public, anon, authenticated;
```

### M2　`coalesce(..., 1)` 对「配置行缺失」不生效，缺失时静默放行（fail-open）

**证据：**

- [02_实施方案.md:68-69](../../../Pre-docs/开发/21_推荐提交频率限制可配置化_2026-09-21/02_实施方案.md#L68-L69) 与 [02_实施方案.md:155-156](../../../Pre-docs/开发/21_推荐提交频率限制可配置化_2026-09-21/02_实施方案.md#L155-L156) 均写 `select coalesce(submission_limit_days, 1) into v_limit_days ... where id = true;`，并在关键点注释 [02_实施方案.md:203](../../../Pre-docs/开发/21_推荐提交频率限制可配置化_2026-09-21/02_实施方案.md#L203) 与风险节 [02_实施方案.md:282](../../../Pre-docs/开发/21_推荐提交频率限制可配置化_2026-09-21/02_实施方案.md#L282)、[01_讨论和决策记录.md:103](../../../Pre-docs/开发/21_推荐提交频率限制可配置化_2026-09-21/01_讨论和决策记录.md#L103) 中，把它描述为「配置行缺失时回退 1」的防御。
- 但该列是 `not null default 1`（[02_实施方案.md:50](../../../Pre-docs/开发/21_推荐提交频率限制可配置化_2026-09-21/02_实施方案.md#L50)），`coalesce` **永不触发**，实为死代码。
- 真正的「配置行缺失」场景：`select ... into` 返回 **0 行**时，PL/pgSQL 会把 `v_limit_days` 置为 `NULL`（`coalesce` 拦不住）。随后 `date_trunc(...) - (NULL - 1) * interval '1 day'` 得 `NULL`，`created_at >= NULL` 恒为 `NULL`，`count(*)` 计为 0，于是**额度校验被静默跳过**——额度查询报「可提交」、提交校验也不拦截，与文档「不误放行」的目标相反。

**影响：** 种子行 `insert ... on conflict do nothing` 保证常态下行存在，故**非阻断**；但这是文档把「不存在的防御」当作已解决，且真实缺口恰在「防御」宣称的反面（fail-open 而非 fail-safe）。

**建议：** 改用零行安全的写法，例如：
```sql
select submission_limit_days into v_limit_days
  from public.recommendation_submission_config where id = true;
if not found then v_limit_days := 1; end if;
```
（或 `select coalesce((select submission_limit_days ... where id = true), 1) into ...`），并同步修订 01/02 文档对 `coalesce` 防御语义的表述。

## 三、低（完善性 / 一致性）

### L1　`AdminPage.jsx` 的 `SlidersHorizontal` 图标未纳入 import

[02_实施方案.md:256](../../../Pre-docs/开发/21_推荐提交频率限制可配置化_2026-09-21/02_实施方案.md#L256) 要求 nav 项 `icon: SlidersHorizontal`，但 [AdminPage.jsx:2](../../../src/components/AdminPage.jsx#L2) 当前 lucide-react 导入为 `{ AlertTriangle, FileText, LayoutDashboard, ShieldAlert, ShieldCheck, Users }`，不含 `SlidersHorizontal`。方案应显式补上该 import，避免实现时遗漏导致引用未定义。

### L2　弹窗文案与后端报错文案不一致（`limitDays > 1` 分支）

- 弹窗（[02_实施方案.md:245](../../../Pre-docs/开发/21_推荐提交频率限制可配置化_2026-09-21/02_实施方案.md#L245)）：「最近 {limitDays} 天内已提交 1 篇推荐，**暂不能再次提交**。」
- 后端（[02_实施方案.md:164](../../../Pre-docs/开发/21_推荐提交频率限制可配置化_2026-09-21/02_实施方案.md#L164)）：「最近 % 天内已提交 1 篇推荐，**请稍后再试**。」

虽然后端仅作兜底，但同一状态两处措辞不一致，建议统一为一句，避免用户困惑。

### L3　「额度用尽」态在「同时无可提交内容」时文案略误导

按 §3.3 的优先级，`quota && !quota.canSubmit` 先于 `items.length === 0` 渲染。当用户**已用完额度且已无可提交内容**（例如仅有一篇自导入已完成内容且已提交）时，弹窗显示「今天已提交 1 篇推荐，明天再试」，暗示「明天还能提交」，实则明天也没有可提交内容。D6 已明确两个维度正交，但此交叉态的文案可进一步精确（如额度用尽 + 无内容时合并提示）。属产品取舍，若维持现状亦可在决策记录中注明。

### L4　「今天 / 明天」为北京时间口径，非东八区用户有跨日歧义

D2 决定以「北京时间 0 点重置」，故错误文案（[02_实施方案.md:162-164](../../../Pre-docs/开发/21_推荐提交频率限制可配置化_2026-09-21/02_实施方案.md#L162-L164)）与弹窗文案中的「今天 / 明天」均按北京时间理解。对非 UTC+8 用户，其本地「今天」与北京「今天」可能错位一天，出现「我明明还没提交过却被告知今天已提交」。属既定时区决策的固有代价，建议在文案或帮助说明中带一句「按北京时间」以消歧，或接受并记录。

## 四、已确认正确的部分（无需改动）

- **现状调查溯源准确**：提交校验顺序「已登录 → 归属且未删除 → 仅自导入 → 已读完 → 频率限制 → 去重」与 [20260917000000_recommendation_moderation_workflow.sql:144-166](../../../supabase/migrations/20260917000000_recommendation_moderation_workflow.sql#L144-L166) 一致；`first_reading_config` 单行表（`id boolean pk default true check(id)` + `revoke all`）与 [20260917000003_first_reading_offer.sql:4-14](../../../supabase/migrations/20260917000003_first_reading_offer.sql#L4-L14) 一致——与 20 号文档不同，本次无过时溯源。
- **时区表达式数学正确**：`date_trunc('day', now() at time zone 'Asia/Shanghai') at time zone 'Asia/Shanghai'` 确为「北京时间今日 0 点（timestamptz）」；N 天窗口 `today0 - (N-1)*1 day`，N=7 覆盖 7 个自然日；`Asia/Shanghai` 无 DST，无边界漂移。三处表达式（额度查询 + 提交校验）逐字一致。
- **`create or replace` 保留原 grant**：`submit_recommendation_for_review` 签名 `(text, text, text, text)` 不变，原 `grant execute` 持续有效，无需重 grant——判断正确。
- **提交校验重写无回归**：正文重写完整保留了归属校验、`origin='imported'`、`reading_marks.completed`、正文哈希 / 归一化 URL 去重、快照写入（含 `kind` 列）、`recommendation.pending_created` 审计，仅替换频率校验段——逐行比对无误。
- **迁移文件名**：`20260921000002` 是正确下一个序号（`20260921000000_add_bookmark_status.sql`、`...0001_add_reset_reading_rpc.sql` 已存在）。
- **配置表 RLS**：`enable row level security` + `revoke all ... from anon, authenticated` 与 `first_reading_config` 一致。
- **Admin RPC 守卫**：`auth.uid() is null or not is_current_user_admin() or not exists(profiles.status='active')` 与 [20260917000004_first_reading_admin.sql:7-9](../../../supabase/migrations/20260917000004_first_reading_admin.sql#L7-L9) 一致；乐观并发用 `updated_at is distinct from p_expected_updated_at`、保存写 `clock_timestamp()`，均一致。
- **审计列**：`(actor_user_id, actor_role, action, target_type, target_id, payload)` 与现有 `audit_logs` 用法一致。
- **服务层签名与前端调用一致**：`getRecommendationSubmissionQuota` / `getRecommendationSubmissionConfig` / `saveRecommendationSubmissionConfig` 命名、参数与 RPC 一一对应；AdminPage `navItems` 结构与现有项匹配。
- **D3 口径**：`count(*)` 含所有状态（pending/approved/active/rejected/removed），与现状（无 status 过滤）一致；D4 单旋钮「每 N 个自然日 1 篇」、D5 默认 1（相对现状放宽）均合理并已确认方向。
