# 推荐提交频率限制可配置化 — 讨论和决策记录

> 日期：2026-09-21
> 关联：[02_实施方案](02_实施方案.md)、[03_实施前审核反馈](03_实施前审核反馈.md)、[04_实施前审核反馈处理记录](04_实施前审核反馈处理记录.md)

## 一、背景与需求

社区众包推荐（「提交推荐」）允许用户把「已读完的自导入内容」提交给管理员审核，通过后发布到推荐区。提交资格、去重与正文快照全部在服务端 RPC `submit_recommendation_for_review` 内以单个事务完成。

**现状的关键事实：频率限制已经存在，且是硬编码的。**

当前逻辑（`20260917000000_recommendation_moderation_workflow.sql`）：

```sql
if (select count(*) from public.recommendation_submissions
     where submitter_user_id = auth.uid()
       and created_at >= now() - interval '7 days') >= 1 then
  raise exception '本周已提交 1 篇推荐，请下周再试';
end if;
```

即：**每 7 天（滚动窗口）最多 1 篇**，且 `count(*)` 统计所有状态（含被驳回/下架）。

**需求**（经澄清后确认为四点，非「新增限制」而是「可配置化 + 语义调整」）：

1. 把硬编码的频率上限改为**后台可随时更新的配置项**；
2. 频率语义从「滚动 7 天」改为**自然日**（北京时间 0 点重置）；
3. 被驳回/下架的提交**照常占用额度**（与现状一致）；
4. 弹窗对「额度用尽」与「暂无可提交内容」给出**区分态**。

## 二、现状调查结论

### 2.1 提交链路与校验点

- 入口：[SubmitRecommendationModal.jsx](../../../src/components/SubmitRecommendationModal.jsx) → `listSubmittableReadings()` 列出可提交内容 → `submitRecommendationForReview()` 提交。
- 服务层：[recommendationService.js](../../../src/services/supabase/recommendationService.js)。
- **权威校验全部在服务端 RPC**（`SECURITY DEFINER`，客户端不可绕过），依次：已登录 → 素材归属且未删除 → 仅自导入 → 已读完 → **频率限制** → 去重（正文哈希 / 归一化 URL）。

### 2.2 现有「后台可更新配置」范式（本项目已有先例）

首次阅读弹窗已经落地了一套成熟的「后台可更新配置」范式，本次直接复用，不新造：

- **单行配置表** `first_reading_config`（`id boolean primary key default true`，`revoke all` 且不 grant，只有 SECURITY DEFINER RPC 能读写）——见 `20260917000003_first_reading_offer.sql`。
- **管理端读写 RPC 对** `admin_get_first_reading_config` / `admin_save_first_reading_config`：管理员 + 活跃校验、乐观并发（`p_expected_updated_at` 比对 `updated_at`）、审计日志——见 `20260917000004_first_reading_admin.sql`。

### 2.3 关键结论（技术判断依据）

1. **频率限制应继续留在服务端 RPC**，改为读取配置值判断；不能放到前端（可绕过）或 DB 触发器（难以表达「读配置 + 计数」的清晰语义）。
2. **复用 `first_reading_config` 范式**，不引入通用 KV 设置系统（YAGNI：当前仅一个配置项）。
3. **既有 UX 缺口**：`list_submittable_readings` 不检查额度，额度用尽后弹窗仍列出其它已读完内容，点提交才被后端拒。本次用「区分态」修复（见 D6）。
4. **自然日时区边界**：Postgres 的 `date_trunc('day', now())` 是 UTC 0 点（北京时间早 8 点重置），须显式 `at time zone 'Asia/Shanghai'` 才能做到「北京时间 0 点重置」。

## 三、决策记录

### D1 承载方式 → 复用单行配置表 + admin RPC 范式

- 备选：通用 `app_settings` KV 表统一管理；或把值塞进既有表。
- **决策：新增单行表 `recommendation_submission_config` + 一对 admin RPC**，结构、RLS 锁定、乐观并发、审计日志全部对齐 `first_reading_config` 范式。理由：与既有代码同构、评审成本低、已验证可靠；通用 KV 属过度设计。

### D2 语义 → 自然日（北京时间 0 点重置）

- 备选：滚动 24 小时窗口（现状写法）。
- **决策：自然日**。窗口边界为北京时间当日 0 点：`date_trunc('day', now() at time zone 'Asia/Shanghai') at time zone 'Asia/Shanghai'`。理由：符合「今天 / 明天」心智；滚动窗口不可预测（「昨天 23 点交过，今天 22 点还不能交」）。
- **时区口径（L4）**：报错/弹窗文案中的「今天 / 明天」均按**北京时间**理解；非东八区用户存在跨日歧义（本地「今天」与北京「今天」可能错位一天）。属单时区中文产品既定时区决策的固有代价，**接受并记录，不在用户文案中追加「按北京时间」**（避免文案噪音）。

### D3 额度口径 → 所有状态均占用

- **决策：`count(*)` 统计所有状态（pending/approved/active/rejected/removed）**，与现状一致。
- 已知代价：一篇被驳回后，当天/窗口内不能再提交别的。产品尺度下可接受（兼收压审核队列量的效果），已与需求方确认。

### D4 配置粒度 → 单一旋钮「每 N 个自然日 1 篇」

- **决策：`submission_limit_days integer`，`CHECK (between 1 and 365)`**，含义为「最近 N 个自然日内最多提交 1 篇」。N=1 即每天一次，N=7 即每周一次。
- 暂不引入「每天最多 N 篇」这类双参数（未来确有需求再加一列即可，表结构可扩展）。

### D5 默认值 → 1（每天一次）

- **决策：`DEFAULT 1`**。生效即每天一次；如需收紧，管理员在后台改大 N 即可。
- 说明：这是相对现状「每周 1 篇」的**放宽**，非收紧，已与需求方确认方向。

### D6 前端呈现 → 弹窗区分「额度用尽」与「暂无可提交内容」

- **决策：新增用户侧 RPC `get_recommendation_submission_quota()`** 返回 `{ limitDays, usedCount, canSubmit }`，弹窗并行加载额度与可提交列表：
  - `canSubmit = false` → 显示「额度用尽」态（「今天已提交 1 篇，明天再试」/「最近 N 天内已提交 1 篇」）；
  - `canSubmit = true` 且无内容 → 显示「暂无可提交内容」态（沿用现有文案）。
- 理由：额度与「有无内容」是两个正交维度，拆成两个 RPC/两个状态才能正确表达，而不是把「额度用尽」误报成「无内容」。

### D7 部署顺序与交叉态（实施前审核补充）

- **迁移先行（H1）**：本项目迁移经 Dashboard SQL Editor 手工执行、与前端发布天然不同步，执行顺序定为「先手工跑迁移、确认三个新 RPC 可调用，再发布前端」；前端侧额度查询失败时**降级为仅列表、不做额度门控**（后端提交校验是权威兜底），避免迁移未到位时弹窗静默退化为「暂无可提交内容」。
- **交叉态文案（L3）**：当「额度用尽」且「无可提交内容」同时成立时，在额度文案后追加「当前也暂无其他可提交内容」，消除「明天再试却无事可做」的误导。

## 四、最终方案要点

| 维度 | 决策 |
|---|---|
| 承载 | 单行表 `recommendation_submission_config` + `admin_get/save` 一对 RPC（对齐 `first_reading_config` 范式） |
| 语义 | 自然日，北京时间 0 点重置（`Asia/Shanghai`） |
| 额度口径 | 所有状态均占用（`count(*)`，含驳回/下架，保持现状） |
| 粒度 | 单一旋钮 `submission_limit_days`（1–365），含义「每 N 个自然日 1 篇」 |
| 默认值 | `1`（每天一次） |
| 强制点 | `submit_recommendation_for_review` 内读配置判断（服务端权威，不动客户端限流） |
| 前端 | 新增 `get_recommendation_submission_quota()` + 弹窗区分态；后台新增「推荐提交设置」面板 |
| 迁移 | 1 个迁移脚本 `20260921000002_recommendation_submission_config.sql` |

## 五、风险与注意点

1. **时区表达式正确性**：`date_trunc('day', now() at time zone 'Asia/Shanghai') at time zone 'Asia/Shanghai'` 是「北京时间今日 0 点（timestamptz）」，两处 RPC（提交校验、额度查询）必须写一致，否则边界判断漂移。
2. **配置行不变式（fail-safe 而非 fail-open）**：`recommendation_submission_config` 由 `revoke all` 保护、仅 RPC 可写，种子行 `(true)` 恒定存在。防御写法须用零行安全的 `select ... into; if not found then ... := 1; end if;`，**不能用** `coalesce(submission_limit_days, 1)`——后者对「零行」不生效，零行时 `v_limit_days` 为 NULL，额度校验会被静默跳过（fail-open），与「不误放行」目标相悖。
3. **`create or replace` 保留原 grant**：改写 `submit_recommendation_for_review` 用 `create or replace`，函数签名不变，原 `grant execute ... to authenticated` 依然有效，无需重 grant。
4. **审计**：配置保存须写 `audit_logs`（`recommendation.submission_config_updated`，含 before/after），与 `first_reading.config_updated` 对齐。
5. **乐观并发**：配置保存用 `p_expected_updated_at` 比对，避免两个管理员互相覆盖；冲突时提示重新加载。
6. **颜色规范**：新增 UI（后台面板、弹窗区分态）全部走 `var(--*)`，不引入硬编码颜色（CLAUDE.md 颜色规范）。
