## 三、验收标准与核验方式（对应 `02` §五）

| # | 验收项 | 核验方式 |
|---|---|---|
| 1 | 迁移后 `recommendation_submission_config` 存在且仅一行 `(id=true)`，`submission_limit_days` 默认 `1`；`anon/authenticated` 无法直接读写该表；三个新 RPC 已 `revoke all ... from public`，`anon` 调用被拒 | SQL 查询（Dashboard）：`select id, submission_limit_days from recommendation_submission_config;` 期望仅 `(true, 1)`；`select * from recommendation_submission_config;`（anon 会话）期望空/被拒 |
| 2 | 默认（N=1）下，用户提交一篇后，同日再次提交（不同已读完内容）被拒，报「今天已提交 1 篇推荐，明天再试」 | 运行时人工：提交一篇 → 同日再次提交被拒 |
| 3 | 管理端把 `submission_limit_days` 改为 `7` 后，用户最近 7 个自然日内只能提交 1 篇，报「最近 7 天内已提交 1 篇推荐」 | 运行时人工：后台改 7 → 提交一篇 → 7 日内再提交被拒 |
| 4 | 被驳回/下架的提交占用额度：驳回后同窗口内再提交被拒 | 运行时人工：提交 → 后台驳回 → 同窗口再提交被拒 |
| 5 | 弹窗区分态：额度用尽显示「额度用尽」文案；额度可用但无内容显示「暂无可提交内容」；额度查询 RPC 失败降级为仅列表；额度用尽且无内容显示合并文案 | 运行时人工 + 代码复核（`Promise.allSettled` + `setQuota(null)`） |
| 6 | 后台面板可读改 `submission_limit_days`（1–365），越界/空值被拒；保存写审计日志；并发冲突提示重新加载 | 运行时人工 + 代码复核（`expectedUpdatedAt` 乐观并发） |

## 四、审核重点（请审核者优先复核，按风险排序）

1. **迁移 SQL 的 M2 零行安全兜底**：两处 `select submission_limit_days into v_limit_days ...; if not found then v_limit_days := 1; end if;`（额度查询 + 提交校验），`FOUND` 紧跟目标 `select`、无中间语句干扰；**禁用** `coalesce(submission_limit_days, 1)`（对零行不生效 → fail-open）。
2. **M1 revoke 作用域**：三个**新** RPC 先 `revoke all ... from public, anon, authenticated` 再 `grant ... to authenticated`；未误含 `submit_recommendation_for_review`（其 `create or replace` 保留原 grant，无需 revoke/重 grant）。
3. **弹窗降级（H1）**：`Promise.allSettled` 独立加载；`quota` RPC 失败 `setQuota(null)` → 渲染条件 `quota && !quota.canSubmit` 为假、落到现状「仅列表、不做额度门控」路径（后端提交校验仍为权威兜底，无安全缺口）。
4. **自然日语义 + 额度口径**：两处时区表达式逐字一致 `date_trunc('day', now() at time zone 'Asia/Shanghai') at time zone 'Asia/Shanghai'`；`count(*)` 全状态（含 pending/approved/active/rejected/removed）。
5. **后台面板**：乐观并发（`expectedUpdatedAt` vs `updated_at is distinct from`）、`isLibraryAccessError → refreshAuthState()` 降级、保存写审计 `recommendation.submission_config_updated`（含 before/after）。
6. **颜色规范**：新增面板/区分态全部走 `var(--*)`，无硬编码颜色。
