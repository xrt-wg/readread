## 三、需在实施前修正的问题（Critical）

### C1：`listDueBookmarks()` 池排序与设计意图矛盾

**位置**：`03_实施方案.md §4.1` vs `§4.2`

**问题**：§4.1 的实现代码中：

```js
const pool = [...newCards, ...dueCards]  // 新卡片总是在到期卡片前面
const session = pool.slice(0, 10)
```

而 §4.2 明确声明「不设优先级——新卡片和到期卡片混合后 shuffle」。当前实现将新卡片全部排在到期卡片之前，如果用户有 10+ 张新卡片，`slice(0, 10)` 会全部取新卡片，到期卡片一张都不会出现。这与设计意图矛盾。

**修正建议**：将 §4.2 的决策落地到代码——合并后统一 shuffle，或明确声明新卡片优先并更新 §4.2：

```js
// 方案 A：混合后 shuffle（与 §4.2 一致）
const pool = shuffleArray([...newCards, ...dueCards])
const session = pool.slice(0, 10)

// 方案 B：新卡片优先（与当前实现一致，但需更新 §4.2 的说明）
// 保留当前实现，将 §4.2 改为「新卡片优先于到期卡片——优先接触新内容」
```

**影响**：不修正将导致到期卡片在大量新卡片场景下被永久搁置，削弱间隔复习的核心价值。

### C2：缺少反馈按钮的防重复点击机制

**位置**：`03_实施方案.md §5.3`、`04_执行计划.md §5`

**问题**：反馈按钮点击后执行异步 `saveBookmark` + 推进到下一张。如果用户在 `saveBookmark` 完成前快速双击（或网络延迟导致按钮仍可点击），会触发两次反馈——第一次推进到卡片 B，第二次在卡片 B 上再次触发反馈。这导致：
- 卡片 B 被意外评价（用户还没看到就跳过了）
- 卡片 A 的反馈可能被第二次调用的 `current`（此时已是卡片 B）覆盖

**修正建议**：在 `handleFeedback` 中增加处理中状态锁：

```js
const [saving, setSaving] = useState(false)

const handleFeedback = useCallback(async (feedback) => {
  if (saving) return          // ← 防护
  const captured = current     // ← 捕获当前卡片引用，避免闭包过期
  setSaving(true)
  try {
    const updated = computeNextReview(captured, feedback)
    await saveBookmark({ ...captured, ...updated }, { canUseCloudLibrary, userId })
  } catch (e) {
    // ...错误处理
  }
  // 推进
  if (index + 1 >= cards.length) setFinished(true)
  else { setIndex(i => i + 1); setFlipped(false) }
  setSaving(false)
}, [current, index, cards.length, saving, ...])
```

同时给反馈按钮增加 `disabled={saving}` 属性。

### C3：`handleFeedback` 中 `current` 的闭包过期风险

**位置**：`04_执行计划.md §5` 的 `handleFeedback` 实现

**问题**：

```js
const handleFeedback = useCallback(async (feedback) => {
  // ...
  const updated = computeNextReview(current, feedback)  // current 来自闭包
  // ...
}, [current, index, cards.length, ...])
```

`current` 在依赖数组中，当 `index` 变化时 `current` 会更新。但 `useCallback` 的依赖数组更新是异步的——如果用户在 `saveBookmark` 完成前以某种方式触发了第二次调用（见 C2），第二次调用拿到的 `current` 可能已经是新的卡片。虽然 C2 的锁机制可以防止这个问题，但额外的防御性捕获仍然有价值。

**修正建议**：在函数体内捕获当前值：

```js
const handleFeedback = useCallback(async (feedback) => {
  const bookmark = cards[index]  // 从 state 直接读取，而非依赖闭包
  if (!bookmark || saving) return
  // ...
}, [cards, index, saving, ...])
```

## 四、建议补充的防护措施（High）

### H1：`listDueBookmarks` 缺少对 `reviewCount > 0 && nextReviewAt === null` 的边界处理

**位置**：`03_实施方案.md §4.1`

**问题**：分类逻辑中，`reviewCount > 0` 且 `nextReviewAt === null` 的书签会落入 `futureCards`，可能被随机抽取出。这种情况在当前数据中不存在（现有书签的 `nextReviewAt` 均为 null 且 `reviewCount` 均为 0），但实施后如果 `computeNextReview` 的返回值未正确合并回 bookmark 对象，可能产生这种"半初始化"状态。

**建议**：在 `listDueBookmarks` 中增加防御性处理——将 `reviewCount > 0 && !nextReviewAt` 的书签视为到期（其复习已启动但调度数据异常，应尽快重新排期）：

```js
} else if (bm.reviewCount > 0 && !bm.nextReviewAt) {
  // 防御：已复习但无排期时间的异常卡片，视为到期
  dueCards.push(bm)
}
```

### H2：`computeReviewStats` 与 `listDueBookmarks` 的筛选逻辑重复

**位置**：`03_实施方案.md §4.1` 和 `§6.1`

**问题**：两个函数各自实现了"待复习"的判断逻辑：
- `listDueBookmarks`：`reviewCount === 0` → newCards；`nextReviewAt ≤ now` → dueCards
- `computeReviewStats`：`reviewCount === 0` → due；`nextReviewAt ≤ now` → due

两者逻辑等价但代码独立——未来如果修改"待复习"的定义，需要同步修改两处。

**建议**：抽取共享的判断函数：

```js
export function isDue(bookmark, now = Date.now()) {
  if (!bookmark.reviewCount || bookmark.reviewCount === 0) return true
  return bookmark.nextReviewAt && new Date(bookmark.nextReviewAt).getTime() <= now
}
```

`listDueBookmarks` 和 `computeReviewStats` 均调用此函数。

---

### H3：`shuffleArray` 在 `listDueBookmarks` 末尾消除了到期排序的意义

**位置**：`03_实施方案.md §4.1`

**问题**：到期卡片按 `nextReviewAt` 升序排列（最早到期的优先），但最终 `shuffleArray(session)` 将这个排序完全打乱。排序的意图是合理的（最紧急的卡片优先展示），但 shuffle 后又失去了这个好处。

**建议**：考虑加权随机而非完全 shuffle——到期越早的卡片被抽中的概率越高。或者至少保留"到期排序 → 取前 N 张 → shuffle 这 N 张"的方式（当前实现是直接对 session 做 shuffle），这样至少保证了进入 session 的卡片是"最紧急的 10 张"，只是展示顺序随机。当前的 `[...newCards, ...dueCards].slice(0, 10)` 已经做到了取最紧急的——但新卡片排在前面会挤占到期的。如果采用了 C1 的修正（混合后 shuffle），建议改为：

```js
// 按到期时间排序取前 10，然后 shuffle 展示顺序
const sorted = [...newCards, ...dueCards].sort(/* 到期时间 + 新卡片优先/押后策略 */)
const picked = sorted.slice(0, 10)
return shuffleArray(picked)
```

### H4：初次加载 vs「再来一轮」的数据新鲜度

**位置**：`04_执行计划.md §5` 的 `handleRestart`

**问题**：`handleRestart` 重新调用 `listDueBookmarks()` 从服务端/本地拉取全量数据。但完成一轮 10 张卡片的反馈后，刚刚评价过的 10 张卡片已被 `saveBookmark` 更新了 `nextReviewAt`。如果"再来一轮"立即执行，这些卡片可能仍满足"到期"条件（如 1 天间隔的卡片，`nextReviewAt` 为明天，确实不会出现在本轮）。但如果用户在同一天内多次"再来一轮"，且书签总量不足 20 张，第二轮可能拿不到足够的卡片。

**建议**：在 `handleRestart` 中考虑排除**本轮已评价的卡片**（用一个 `Set` 追踪本轮已评价的 bookmark ID），确保"再来一轮"不会立即把刚评价过的卡片再次拿出来。

```js
const reviewedThisSession = useRef(new Set())

// 在 handleFeedback 中：
reviewedThisSession.current.add(bookmark.id)

// 在 listDueBookmarks 或 buildSession 中过滤：
const filtered = all.filter(b => !reviewedThisSession.current.has(b.id))
```

### H5：移动端窄屏下 4 按钮布局的空间验证

**位置**：`03_实施方案.md §5.2`

**问题**：背面底部按钮布局为 `[看正面]    [生疏] [一般] [熟练]`，4 个按钮一行排列。在 320px 宽的小屏设备上，每个按钮平均可用宽度约 70px（扣除间距），而按钮文案"看正面"（3 字）+"生疏"/"一般"/"熟练"（各 2 字）加上 padding 可能拥挤。

**建议**：在实施时验证 320px 宽度下的表现。如果空间不足，考虑：
- 将 `[看正面]` 放在上一行，三个反馈按钮独占一行
- 或使用 `flex-wrap` + `gap` 允许自然换行

## 五、设计存疑点（Medium — 可推迟但应记录）

### M1：ReviewModal 重构的投入产出比

**位置**：`01_决策记录.md §5.5` + `04_执行计划.md Phase 3`

**现状**：ReviewModal 在代码库中未被任何组件引用（`ImportPage.jsx` 的回顾 Tab 使用的是 `<ReviewPanel />`）。决策记录 §5.5 承认"当前 ReviewModal 在 App.jsx 中未被引用"，但仍决定保留并完整重构。

**考量**：
- Phase 3（ReviewModal 重构）需要完成：容器重写 + 统计指标适配 + overlay 交互验证 + 深色主题适配，预估工作量不低
- 从探索结果看，ReviewModal 是 611 行的完整组件，功能与 ReviewPanel 几乎相同但增加了 overlay/深色主题

**建议**：
- **方案 A（推荐）**：先不重构 ReviewModal，仅完成 ReviewCard + reviewUtils 抽取 + ReviewPanel 重构（Phase 0-2）。ReviewModal 的 CardFront/CardBack 改为从 ReviewCard 导入（最小改动），其余逻辑暂时不动。等确实需要 ReviewModal 作为阅读器快速回顾入口时再完整重构
- **方案 B**：如果要保留 Phase 3，在决策记录中明确 ReviewModal 的启用时间点和触发场景

**理由**：在抽取共享组件后，ReviewModal 的重复代码问题已自然解决——它只需从 ReviewCard 和 reviewUtils 导入即可。剩余 ~100 行容器逻辑（overlay、关闭按钮、深色主题）本身不是重复代码。将"缩减至 ~100 行"视作必须完成的目标，投入产出比存疑。

### M2：首次复习特殊处理的用户感知一致性

**位置**：`03_实施方案.md §3.3`

**问题**：首次复习时"一般"→ familiarity=2（间隔 3 天），后续复习时"一般"→ familiarity + 1（钳制 [1,5]）。这意味着同样是点击"一般"：
- 对一张新卡片：familiarity 从 0 跳到 2，下次复习 3 天后
- 对一张 familiarity=3 的卡片：familiarity 从 3 升到 4，下次复习 14 天后

同样的按钮、同样的反馈，但效果完全不同。用户在界面上看不到区别——他们不知道系统的内部规则。

**缓解**：这是简化算法的固有权衡，不做额外处理是合理的。但如果未来用户反馈"为什么点一样的东西结果不一样"，可以考虑在 CardBack 上展示当前 familiarity 级别或下次复习时间，增加透明度。

---

### M3：`computeReviewStats` 中 `mastered` 指标的分母选择

**位置**：`03_实施方案.md §6.1`

**问题**：
```js
const reviewedTotal = reviewed.length || total  // 无已复习卡片时用总数兜底
```

- 无已复习卡片时：`mastered = "0/N · 0%"`（N = 总收藏数），看起来像是"收藏了 N 张但一张都没掌握"
- 用户刚收藏第一张卡片时看到"已掌握 0/1 · 0%"，可能有挫败感

**建议**：考虑在 `reviewed.length === 0` 时不显示百分比，改为 `"0/-"` 或 `"-"`，表示"尚无复习数据"。或者与 `due` 指标的设计对齐——`due` 将"从未复习的卡片"计入待复习数，那么 `mastered` 也可以将"从未复习的卡片"排除在分母之外，展示"已复习卡片中的掌握率"：

```js
const mastered = reviewed.length > 0
  ? `${masteredCount}/${reviewed.length} · ${Math.round((masteredCount / reviewed.length) * 100)}%`
  : '尚无数据'
```

这与文档中「刚收藏还没复习的卡片不参与掌握率计算，避免新用户看到 0%」的设计意图更一致——当分母用 `total` 兜底时，新用户仍然会看到 0%。

---

### M4：调度算法的间隔天数未经验证

**位置**：`01_决策记录.md §3` 和 `§5.4`

**问题**：固定间隔 `{1:1d, 2:3d, 3:7d, 4:14d, 5:30d}` 是基于 Leitner 系统的经典值，但这些值适用于**每日规律复习**的场景。ReadRead 的用户行为模式未知——他们可能：
- 连续使用几天后中断一周
- 每周只使用 1-2 次
- 某天大量收藏后几天没有收藏

这会导致：用户在中断后重新打开时，大量卡片处于"到期"状态，`listDueBookmarks` 只会返回最紧急的 10 张，其余积压的到期卡片继续等待。间隔表对这种使用模式是否仍然有效？

**建议**：这不是需要在实施前解决的问题，但应在复审条件中增加一条：**如果数据显示用户平均复习间隔 > 3 天，应重新评估间隔表的取值**。或者在统计指标中增加"积压数"（到期但本次未排入 session 的卡片数）。

## 七、总体评价

### 问题分析的完备性：良好

三份文档对问题的诊断是准确的——随机翻阅无记忆巩固、无进展感知、基础设施闲置、代码重复——这四个问题均被代码库验证为真实存在。方案对候选方案（保持现状/SM-2/固定间隔无反馈）的比较和否决有清晰逻辑。

**缺失的分析维度**（对当前决策不构成阻碍，但值得记录）：
- 用户行为数据（收藏量分布、回顾频率）——无数据支撑 10 张/轮的设定
- 不同书签类型（词/短语/句/段）的差异化复习需求——不同类型的记忆难度不同，当前算法一视同仁

### 解决方案的合理性：良好

简易 Leitner + 3 级反馈精准命中了"刚好够用"的设计位。零新表、零新 API、纯客户端计算的约束体现了良好的架构自律。

**核心优势**：
- 调度逻辑 ~10 行，维护成本极低
- 3 级反馈消除选择困难
- 共享组件抽取解决代码重复
- 所有改动局限在回顾面板内部

### 实施方案的有效性：良好（有 3 个待修正项）

实施方案对数据流、交互变化、组件接口、错误处理均给出了具体可执行的设计。C1（池排序矛盾）、C2（防重复点击）、C3（闭包过期）三个问题需要在实施前修正，但修正成本低，不改变整体架构。

### 执行计划的可行性：良好

Phase 0→1→{2∥3}→4 的推进顺序合理，每阶段的完成标志和回退策略清晰。M1（ReviewModal 重构的投入产出比）建议在进入 Phase 3 前重新评估。
