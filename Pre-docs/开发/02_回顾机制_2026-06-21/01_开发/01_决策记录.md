# 回顾机制优化 — 决策记录

- **日期**：2026-06-21
- **状态**：已决策
- **项目阶段**：构建期
- **决策主题**：将回顾功能从"随机闪卡翻阅"升级为基于反馈的间隔复习机制，并建立简明的进展衡量体系

---

## 一、背景

当前回顾功能的运行机制：

```
全部收藏 → 随机洗牌 → 取前 10 张 → 正面看原文 / 背面看翻译 → 翻完结束
```

核心问题：

1. **无记忆巩固**：用户对每张卡片无反馈通道，系统不知道哪些词已经掌握、哪些需要加强——今天是这 10 张，明天还是可能随机到同一批。随机性不服务记忆规律
2. **无进展感知**：用户不知道学了多少、掌握到什么程度。回顾变成了无目标的消遣而非有方向的练习
3. **基础设施闲置**：Bookmark 数据模型中的 `reviewCount`、`familiarity`(0-5)、`nextReviewAt` 三个字段在 schema、类型定义、工厂函数、API 层全链路已贯通，但回顾面板从未读写它们
4. **代码重复**：ReviewPanel（246行）和 ReviewModal（610行）共享 ~200 行几乎相同的 CardFront、CardBack 和工具函数，维护成本翻倍

---

## 二、决策目标

1. 建立基于用户反馈的间隔调度机制，让难的词多练、简单的词少练
2. 建立简明的进展衡量标准（3 个指标），让用户感知学习成果
3. 消除 ReviewPanel 与 ReviewModal 之间的代码重复
4. 零新增数据表、零新增 API、零破坏性改动

---

## 三、决策结论

**利用 Bookmark 已有的 `familiarity` 字段（1-5）驱动固定间隔表，通过卡面背面的 3 级反馈按钮收集用户评价。到期的优先出现+新卡片补足 10 张构成每次回顾队列。3 个纯客户端计算指标置于回顾 Tab 顶部。**

核心决策：

- **调度模型**：简易 Leitner——familiarity 1→5 对应间隔 {1d, 3d, 7d, 14d, 30d}。用户反馈 Δ ∈ {-1(生疏), +1(一般), +2(熟练)}，钳制 [1,5]。首次反馈特殊处理：生疏→1 / 一般→2 / 熟练→3
- **交互约束**：正面保留 `[看翻译]`；背面用 `[生疏]` `[一般]` `[熟练]` 三个反馈按钮替代 `[下一张]`。用户必须给出反馈才能推进——正面不可跳过（只能通过[看翻译]翻到背面后再反馈）
- **回顾队列**：到期卡片(nextReviewAt≤now) + 从未复习卡片(reviewCount=0) → 按到期时间排序取前 10 张；不足 10 张时从未来卡片中随机补齐
- **统计指标**：3 个——待复习数（行动信号）、已掌握数(familiarity≥4)（成果信号）、总收藏数（范围信号）。纯客户端从 `listAllBookmarks()` 一次查询结果中计算。无周趋势追踪
- **代码架构**：抽取 `ReviewCard.jsx`（CardFront + CardBack + 反馈按钮）和 `reviewUtils.js`（调度计算 + 统计计算 + 共享工具函数）为共享模块；ReviewPanel 和 ReviewModal 各自只负责容器逻辑
- **不开放配置**：间隔天数固定、Session 卡片数固定 10 张、不提供用户可调的"密集/正常/轻松"预设

## 四、候选方案比较

### 方案 A：保持现状不修改（否决）

#### 优点
- 零开发成本

#### 致命问题
- 不解决任何问题——回顾仍然是随机翻阅
- 已建模的 SRS 字段持续闲置
- 用户无法感知进展，回顾缺乏方向感

#### 结论
**否决。** SRS 字段的存在本身就说明了原设计意图——当前实现是不完整的。

---

### 方案 B：完整 SM-2 算法实现（否决）

使用 EF 因子（浮点）、质量评分 0-5、I(1)=1, I(2)=6, I(n)=I(n-1)*EF 的复杂公式。

#### 优点
- 算法成熟，社区验证充分

#### 致命问题
- 约 60 行计算逻辑，对于 10 张卡片的场景过度设计
- 5 级质量评分（0-5）对用户来说选择困难——需要纠结"是 3 还是 4"
- EF 因子的连续浮点值增加了状态理解成本
- 实际效果与简化方案的差异在 < 100 张卡片的规模上微乎其微

#### 结论
**否决。** 过度设计，与"不过于复杂"的原则相悖。

---

### 方案 C：固定间隔无反馈（否决）

按 reviewCount 自动推进间隔：第 1 次→1d, 第 2 次→3d, ..., 不收集用户反馈。

#### 优点
- 最简单的实现
- 零用户交互变化

#### 致命问题
- 不与用户记忆实际挂钩——简单词和困难词同一待遇
- 缺少反馈通道意味着算法无法适应个体差异
- 回顾仍然是单向的"系统推，用户看"

#### 结论
**否决。** 缺少反馈 = 不是真正的间隔复习，只是加了延迟的随机翻阅。

---

### 方案 D：简易 Leitner + 3 级反馈（采用）

familiarity 1-5 固定间隔 + 3 级反馈 Δ + 首次特殊处理。

#### 优点
- 约 10 行计算逻辑，维护成本极低
- 3 级反馈无需用户纠结——生疏/一般/熟练，直觉级区分
- 利用已有字段，无需 schema 变更
- 算法自带纠偏：生疏→回退缩短间隔，熟练→加速拉长间隔
- 5 级 familiarity 自然映射到 5 个固定间隔，状态透明

#### 代价
- 相比 SM-2，间隔精度较低（固定值 vs 浮点计算）——在 < 100 卡规模下可忽略
- 相比方案 C，多了 3 个反馈按钮的 UI 变化——这是有价值的设计投入

#### 结论
**采用。** 精准命中"完善但不完美"的设计位——刚好够用，刚好简单。

---

## 五、关键决策点与取舍

### 5.1 交互约束：背面无独立"下一张"

背面只保留三个反馈按钮（+ `[看正面]` 回翻），不提供独立的不反馈推进通道。

**理由**：
- 用户看到翻译后做出的评价就是最自然的推进动作——反馈即推进
- 提供"跳过"会造成大量空值反馈，调度数据不完整
- 正面仍可回翻（`[看正面]`），不担心用户看不到原文

**代价**：用户无法在不给出评价的情况下查看翻译后立即跳过。这是有意的约束——一个微小的"阻力"换取完整的反馈数据。

### 5.2 不设每日上限

Session 上限保持 10 张，但用户完成一轮后可点击"再来一轮"继续。

**理由**：
- 每日上限是行为管理层面的决策，需要观察用户实际行为后再定
- 当前用户基数小，过度约束会损害体验
- 到期自然形成的队列本身就是一种柔性上限——今天的到期卡片就那么多

### 5.3 指标不追踪历史趋势

指标在每个时刻从 `listAllBookmarks()` 的结果中实时计算，不持久化历史快照。

**理由**：
- 三个指标（待复习/已掌握/总收藏）即足以回答"我该做多少"和"我做得怎么样"
- 趋势需要历史存储——引入 localStroage 快照或新表，与"零新增基础设施"的约束冲突
- 掌握率本身就是一个累积趋势——从 20% 涨到 51% 的过程用户自然能感知

### 5.4 间隔天数不开用户可配置

固定间隔表 `{1:1d, 2:3d, 3:7d, 4:14d, 5:30d}` 不暴露为可调参数。

**理由**：
- 参数暴露 = UI 复杂度（设置页面、预设选择、即时预览）
- 当前用户基数小，默认值即可覆盖大多数使用场景
- 若未来有需求，可通过 feature flag 或环境变量快速切换，不需重新设计

### 5.5 ReviewModal 暂时保留

当前 ReviewModal 在 App.jsx 中未被引用，但保留在代码库中。

**理由**：
- 在抽取共享组件后 ReviewModal 的重复代码问题已自然解决——只需将 CardFront/CardBack 的 import 从本地定义切换为从 ReviewCard 导入，其余逻辑不动（最小适配）
- 完整的容器重构（缩减至 ~100 行）待 ReviewModal 有明确的启用场景（如阅读器中的快速回顾入口）后再执行
- 如果下一轮审核确认不需要，可在后续清理

---

## 六、决策范围

### 已确认
- 简易 Leitner 调度模型（familiarity 1-5 + 固定间隔 + 3 级反馈 Δ）
- 首次反馈特殊处理（生疏→1/一般→2/熟练→3）
- 背面三个反馈按钮替代"下一张"，反馈即推进
- 到期优先 + 新卡片补足 + 未来卡片兜底的回顾队列
- 3 个统计指标：待复习 / 已掌握 / 总收藏，置于回顾 Tab 顶部
- 抽取 ReviewCard + reviewUtils 消除代码重复
- 即时单条 saveBookmark 写入反馈结果

### 暂不确认（属于后续迭代范围）
- 每日复习上限
- 间隔天数的用户可配置性
- 掌握率变化的历史趋势追踪
- ReviewModal 的最终去留
- 多设备间的复习进度同步（当前 Supabase 已支持，但未经测试）

---

## 七、实施约束

1. 不新增数据表——仅读写 bookmark 已有字段（reviewCount / familiarity / nextReviewAt）
2. 不新增 API——复用现有 `listAllBookmarks()` 和 `saveBookmark()`
3. 不修改书签创建流程——阅读器中划选收藏的逻辑完全不变
4. 不破坏现有回顾面板的正面/反面视觉和交互
5. 现有书架、阅读、收藏、导入功能不受任何影响
6. localStorage 和 Supabase 两条路径行为一致——调度逻辑纯客户端计算

---

## 八、复审条件

若出现以下任一情况，应重新评估当前设计：

1. 用户平均收藏数超过 500 条——`listAllBookmarks()` 单次拉取全部书签可能产生性能问题
2. 用户反馈行为出现明显的系统性偏差（如始终点"熟练"）——需要引入反馈质量评估
3. 需要支持对同一张卡片的"暂停复习"（用户主动跳过某个词几天/几周）
4. 回顾区需要独立于书签的复习内容（如系统生成的词汇练习）
5. 用户平均复习间隔 > 3 天（非规律使用模式）——需重新评估固定间隔表 `{1:1d, 2:3d, 3:7d, 4:14d, 5:30d}` 在低频使用场景下的有效性

---

## 九、总结

本次决策的核心结论是：

> **在 Bookmark 已有的 `familiarity` 字段（1-5）上建立简易 Leitner 调度机制，通过卡片背面的 3 级反馈收集用户评价，到期优先+新卡片补足构成回顾队列，3 个纯客户端指标提供进展感知。整个机制以约 10 行调度逻辑、零新表、零新 API 的最小增量，将回顾从"随机翻阅"升级为"有反馈、有节奏、有感知"的间隔复习体验。**
