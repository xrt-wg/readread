## 三、调度算法实现

### 3.1 为什么放在客户端计算？

nextReviewAt 的更新时机纯粹在客户端——用户点击反馈按钮时。不涉及跨用户数据、不依赖服务端状态、不需要原子性保证。

**选择**：纯客户端计算。supabase 路径和 localStorage 路径使用同一函数，结果通过 `saveBookmark()` 写入。

### 3.2 核心函数

```js
// src/utils/reviewUtils.js

const INTERVAL_DAYS = { 1: 1, 2: 3, 3: 7, 4: 14, 5: 30 }

/**
 * 根据用户反馈计算下次复习时间。
 *
 * @param {Bookmark} bookmark — 当前书签（含 familiarity, reviewCount）
 * @param {'hard'|'ok'|'easy'} feedback — 用户反馈
 * @returns {{ familiarity: number, nextReviewAt: string, reviewCount: number }}
 */
export function computeNextReview(bookmark, feedback) {
  const current = bookmark.familiarity || 0

  let familiarity
  if (current === 0) {
    // 首次复习：直接映射，跳过 delta 公式
    // 生疏→1、一般→2、熟练→3——首次复习给予更大区分度
    familiarity = { hard: 1, ok: 2, easy: 3 }[feedback]
  } else {
    const delta = { hard: -1, ok: 1, easy: 2 }[feedback]
    familiarity = Math.min(5, Math.max(1, current + delta))
  }

  const days = INTERVAL_DAYS[familiarity]
  const nextReviewAt = new Date(Date.now() + days * 86400_000).toISOString()

  return {
    familiarity,
    nextReviewAt,
    reviewCount: (bookmark.reviewCount || 0) + 1,
  }
}
```

**设计要点**：
- 首次复习（familiarity=0）不使用 delta 公式——delta 会使"一般"(+1)和"生疏"(-1→钳制1)都得到 familiarity=1，不合理的无区分待遇。直接映射让三种反馈在首次就能产生差异化
- 后续复习使用 delta ±1/±2，钳制 [1,5]——familiarity 永久保持在 1-5，不会退回到 0
- 熟练(+2)在首次复习时跳到 familiarity=3——让简单词快速进入低频复习区间

## 四、回顾队列组卷

### 4.1 isDue() 共享判断函数

```js
// src/utils/reviewUtils.js

/**
 * 判断一张书签是否应在当前复习中呈现。
 * 规则：从未复习过（reviewCount=0）→ 是；否则检查 nextReviewAt 是否已到期。
 * 防御性处理：reviewCount > 0 但 nextReviewAt 为空（异常卡片）→ 视为到期，尽快重新排期。
 *
 * @param {Bookmark} bm
 * @param {number} [now] — 当前时间戳（ms），默认 Date.now()
 * @returns {boolean}
 */
export function isDue(bm, now = Date.now()) {
  if (!bm.reviewCount || bm.reviewCount === 0) return true
  if (!bm.nextReviewAt) return true  // 防御：已复习但无排期的异常卡片
  return new Date(bm.nextReviewAt).getTime() <= now
}
```

**设计要点**：`listDueBookmarks` 和 `computeReviewStats` 均调用此函数，保证"待复习"的判断逻辑只有一处定义。

### 4.2 组卷逻辑

```js
// src/services/library.js 新增

export async function listDueBookmarks(options) {
  const all = await listAllBookmarks(options)
  const now = Date.now()

  const newCards = []       // reviewCount === 0
  const dueCards = []       // isDue = true 且 reviewCount > 0
  const futureCards = []    // isDue = false

  for (const bm of all) {
    if (!bm.reviewCount || bm.reviewCount === 0) {
      newCards.push(bm)
    } else if (isDue(bm, now)) {
      dueCards.push(bm)
    } else {
      futureCards.push(bm)
    }
  }

  // 到期卡片按到期时间排序（最早的优先），无 nextReviewAt 的异常卡片排在最前
  dueCards.sort((a, b) => {
    if (!a.nextReviewAt) return -1
    if (!b.nextReviewAt) return 1
    return new Date(a.nextReviewAt).getTime() - new Date(b.nextReviewAt).getTime()
  })

  // 组卷：到期优先 + 新卡片补足，上限 10
  const pool = [...dueCards, ...newCards]
  const session = pool.slice(0, 10)

  // 不足 10 张时从未来池随机补齐
  if (session.length < 10 && futureCards.length > 0) {
    const fill = shuffleArray(futureCards).slice(0, 10 - session.length)
    session.push(...fill)
  }

  // 最终 shuffle 仅改变展示顺序，不影响哪些卡片进入本轮（已在 slice 阶段确定）
  return shuffleArray(session)
}
```

**设计要点**：
- **到期优先**：`pool = [...dueCards, ...newCards]`——到期的卡片先进入候选池。如果到期卡片超过 10 张，session 全部由最紧急的到期卡片组成；新卡片在到期卡片不足 10 张时补足
- 到期卡片按 `nextReviewAt` 升序排列——最早到期（或异常卡片）最优先进入 session
- 末尾 `shuffleArray(session)` 随机化展示顺序，但不改变哪些卡片被选中（已在 `pool.slice(0, 10)` 阶段确定）
- 组卷上限硬编码 10，与现有行为一致

### 5.3 反馈按钮点击行为

```js
const [saving, setSaving] = useState(false)
const reviewedThisSession = useRef(new Set())

const handleFeedback = useCallback(async (feedback) => {
  // ① 防重复点击：保存中忽略后续点击
  if (saving) return

  // ② 从 state 直接读取当前卡片，避免闭包过期
  const bookmark = cards[index]
  if (!bookmark) return

  setSaving(true)
  reviewedThisSession.current.add(bookmark.id)

  try {
    const updated = computeNextReview(bookmark, feedback)
    await saveBookmark({ ...bookmark, ...updated }, { canUseCloudLibrary, userId })
  } catch (e) {
    if (isLibraryAccessError(e)) refreshAuthState()
    setLoadError(resolveLibraryErrorMessage(e, '保存复习进度失败，请稍后重试'))
  }

  // ③ 无论保存成功与否，均推进
  if (index + 1 >= cards.length) {
    setFinished(true)
  } else {
    setIndex(i => i + 1)
    setFlipped(false)
  }
  setSaving(false)
}, [cards, index, saving, canUseCloudLibrary, refreshAuthState, userId])
```

**设计要点**：
- `saving` 状态锁 → 反馈按钮 `disabled={saving}`，防止快速双击导致的误评价
- `const bookmark = cards[index]` 从 state 直接取值，而非依赖 `useCallback` 闭包中的 `current`——即使依赖数组更新延迟也不会拿到错误的卡片引用
- `reviewedThisSession` 用 `useRef(new Set())` 追踪本轮已评价的 bookmark ID——在 `handleRestart` 中过滤，避免"再来一轮"时立即把刚评价过的卡片再次拉入
- 保存失败时仍然推进——与现有错误处理理念一致（不阻塞用户）

### 5.4 handleRestart 的数据新鲜度

```js
const handleRestart = useCallback(async () => {
  try {
    setLoadError('')
    const all = await listAllBookmarks({ canUseCloudLibrary, userId })
    // 过滤本轮已评价过的卡片，避免立即重新出现
    const fresh = all.filter(b => !reviewedThisSession.current.has(b.id))
    const session = buildSession(fresh)  // 复用 listDueBookmarks 的分类+组卷逻辑
    setCards(session)
    setIndex(0)
    setFlipped(false)
    setFinished(false)
    reviewedThisSession.current.clear()
  } catch (e) {
    // ...错误处理同初始化
  }
}, [canUseCloudLibrary, refreshAuthState, userId])
```

## 六、统计指标

### 6.1 计算逻辑

```js
// src/utils/reviewUtils.js

/**
 * 从全部书签中计算三个回顾统计指标。
 *
 * @param {Bookmark[]} allBookmarks
 * @returns {{ due: number, mastered: string, total: number }}
 */
export function computeReviewStats(allBookmarks) {
  const now = Date.now()
  const total = allBookmarks.length

  // 待复习：使用共享的 isDue() 判断
  const due = allBookmarks.filter(b => isDue(b, now)).length

  // 已掌握：familiarity >= 4（仅统计有复习记录的卡片）
  const reviewed = allBookmarks.filter(b => b.reviewCount > 0)
  const masteredCount = reviewed.filter(b => (b.familiarity || 0) >= 4).length

  // 无复习记录时不显示百分比——避免新用户看到"0/N · 0%"的挫败感
  const mastered = reviewed.length > 0
    ? `${masteredCount}/${reviewed.length} · ${Math.round((masteredCount / reviewed.length) * 100)}%`
    : '尚无数据'

  return { due, mastered, total }
}
```

**设计要点**：
- `due` 调用共享的 `isDue()` 函数，保证与 `listDueBookmarks` 的判断逻辑完全一致
- `mastered` 的分母严格限定为"有复习记录的卡片数"（`reviewCount > 0`）——刚收藏还没复习的卡片不参与掌握率计算
- 当尚无任何复习记录时（`reviewed.length === 0`），显示"尚无数据"而非"0/N · 0%"，避免新用户产生挫败感
- 所有计算都是一次遍历，O(n)，bookmark 数量 < 500 时无性能问题

### 6.2 UI 位置

三个指标置于回顾 Tab 顶部，卡片上方，布局为一行三列：

## 八、错误处理

### 8.1 反馈保存失败

`handleFeedback` 的完整实现见 §5.3。核心错误处理策略：

**设计决策**：保存失败时仍推进。理由：
- 阻塞用户比丢失一次反馈更差
- 下一次反馈会覆盖同一个 bookmark 的状态，一次丢失不影响调度
- 与现有 `handleFlip` / `handleNext` 的容错理念一致

### 8.2 空状态

当 `listAllBookmarks()` 返回空数组时——即用户没有任何收藏——保持现有空状态展示：

```
你当前没有可回顾的内容
阅读文章时，划选词句并收藏
即可在这里回顾
```

三个指标在空状态下均显示 `0` / `尚无数据` / `0`。

## 十、风险与缓解

| 风险 | 缓解措施 |
|------|---------|
| 反馈保存失败导致调度状态丢失 | 失败仍然推进；下次反馈时新的状态覆盖旧的——单次丢失不影响整体调度 |
| 用户大量收藏后 `listAllBookmarks()` 性能 | 当前用户收藏量级 < 200，纯 JS 计算可忽略；超过 500 时引入分页查询 |
| 反馈按钮改变用户习惯，用户不适应 | 保留 `[看正面]` 回翻；按钮文案直观（生疏/一般/熟练）；删除操作仍可在 BookmarkPanel 中完成 |
| localStorage 与 Supabase 状态不一致 | 调度逻辑在客户端执行，`saveBookmark()` 使用相同的云端/本地双路径，与现有行为完全一致 |
| 正面无法跳过——用户想跳过当前卡片 | 用户仍可点 `[看翻译]` 翻到背面，然后给任意反馈来推进。反馈 = 推进，无额外成本 |

---

## 十一、总结

实施方案的核心思路：

> **利用 Bookmark 已有的 SRS 字段，在客户端以约 10 行调度逻辑驱动间隔复习。交互上以三个反馈按钮替代"下一张"，反馈即推进。队列以到期优先+新卡补足组卷。三个指标纯客户端计算。共享组件 ReviewCard + reviewUtils 消除 ~200 行重复代码。整个改动局限在回顾面板内部——不穿透到任何现有功能的任何路径。**
