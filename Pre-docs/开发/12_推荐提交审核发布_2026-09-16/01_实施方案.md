# 推荐提交审核发布 实施方案

## 1. 目标和交付边界

将推荐功能从“用户同步调用 AI 后直接公开”改为“用户提交申请，管理员审核、编辑并单独发布”。实施完成后，用户提交不依赖 AI 服务；管理员能够审核来源和正文、补充运营内容、拒绝或发布推荐；用户能在“我的推荐”中查看自己的状态和可见原因。

本方案不实现积分、订阅权益、AI 后台任务或通知系统。数据模型和审计记录将为这些后续能力保留稳定的关联点。

## 2. 现状与改造原则

当前 `recommendation_submissions` 以 `reading_id` 引用原始阅读内容，要求 `intro` 和 `excerpts` 在插入时存在，并使用 `active` 直接公开。前端 `SubmitRecommendationModal` 在提交前调用 `generate-recommendation`，将 AI 生成内容连同基础字段一起写入推荐表。

改造遵循以下原则：

1. 提交操作必须短、确定且不依赖第三方模型。
2. 审核与公开发布必须可分离、可审计、可回退。
3. 发布使用提交时的内容快照，不读取可能变化或已删除的用户书架记录。
4. 权限与状态校验放入数据库 RPC 和 RLS，不以单纯前端校验作为安全边界。
5. 旧的公开推荐维持可用，迁移不改变其对公众的可见性。

## 3. 数据库设计

### 3.1 recommendation_submissions 扩展

保留现有主表，并进行以下调整：

| 字段或约束 | 改动 |
| --- | --- |
| `status` | 扩展为 `pending`、`approved`、`active`、`rejected`、`removed` |
| `intro`、`excerpts` | 在非 `active` 状态允许为空；仅 `active` 强制推荐语和至少一条摘录 |
| `source_url` | 继续可空；新增规范化来源链接字段用于去重 |
| 生命周期字段 | 新增 `reviewed_by`、`reviewed_at`、`approved_at`、`published_at`、`removed_at` |
| 用户可见原因 | 新增 `rejection_reason`、`removal_reason` |
| 管理员内部信息 | 新增 `internal_note`，不向提交者或公众返回 |
| 去重字段 | 新增 `content_hash`；为来源链接和内容指纹建立索引 |

`active` 的完整性应由 CHECK 约束或发布 RPC 保证：推荐语非空、摘录数组长度介于既有约束范围内、运营字段结构合法。`pending` 不应依赖运营字段。

### 3.2 私有快照表

新增 `recommendation_submission_snapshots`：

| 字段 | 用途 |
| --- | --- |
| `submission_id` | 主键并关联推荐提交 |
| `source_reading_id` | 提交时的原阅读记录 ID，用于追溯 |
| `title`、`author`、`source_url` | 提交时基础元数据快照 |
| `sections` | 不可变正文快照，沿用阅读内容的章节 JSON 结构 |
| `content_hash` | 标准化正文的 SHA-256 指纹 |
| `created_at` | 快照生成时间 |

快照表只允许提交者读取自己的快照、管理员读取所有快照；公众无权读取。用户提交后不能更新或删除快照。

### 3.3 审计

复用现有 `audit_logs`，增加推荐提交对应的目标类型和动作值，至少覆盖：

- `recommendation.pending_created`
- `recommendation.approved`
- `recommendation.rejected`
- `recommendation.published`
- `recommendation.removed`
- `recommendation.reopened`

审计载荷记录状态变化、原因、审核字段变更摘要和关联提交 ID。内部备注本体只保存于推荐记录，审计中不复制敏感完整文本。

## 4. RPC 和 RLS 设计

### 4.1 用户提交 RPC

新增 `submit_recommendation_for_review(p_reading_id, p_title, p_author, p_source_url)`，在单个事务中完成：

1. 校验调用者身份与阅读记录归属。
2. 校验内容为用户自导入且已读完。
3. 读取正文并生成标准化来源链接与内容指纹。
4. 对历史提交执行去重，拒绝重复内容。
5. 创建 `pending` 推荐记录和私有快照。
6. 写入创建审计日志。

频率限制应在 RPC 内校验。现有每周一次的策略可保留，但查询必须定义清楚是统计全部尝试，还是仅统计有效提交；建议统计 `pending`、`approved`、`active`，不把被拒绝记录计入新的周期额度。

### 4.2 管理员审核 RPC

新增或拆分以下管理员 RPC，并在每个函数中验证 `is_current_user_admin()`：

| RPC | 前置状态 | 结果 |
| --- | --- | --- |
| `approve_recommendation_submission` | `pending` | 写入审核信息，进入 `approved` |
| `reject_recommendation_submission` | `pending` 或 `approved` | 写入用户可见拒绝原因与内部备注，进入 `rejected` |
| `update_recommendation_editorial_content` | `pending`、`approved`、`removed` | 更新推荐语、标签、摘录和翻译，不公开 |
| `publish_recommendation_submission` | `approved` | 校验内容完整，写入发布时间，进入 `active` |
| `remove_recommendation_submission` | `active` | 写入下架原因，进入 `removed` |
| `reopen_recommendation_submission` | `removed` | 进入 `approved`，供修改后重新发布 |

管理员不应直接通过通用前端 `update` 修改状态。用户也不应获得 UPDATE 权限，以避免篡改审核字段、内部备注或公开状态。

### 4.3 查询策略

- 公开推荐查询固定过滤 `status = 'active'`。
- “我的推荐”查询固定过滤 `submitter_user_id = auth.uid()`，并仅返回用户可见字段。
- 管理员审核查询返回全部状态、私有快照和内部备注。
- “加入书架”与跨用户正文读取改为读取私有快照，且只允许对应提交为 `active` 时执行。

## 5. 前端实施

### 5.1 用户提交弹窗

重构 `SubmitRecommendationModal`：

1. 删除 AI 生成、手动编辑标签/摘录/翻译、缓存与重试逻辑。
2. 列出可提交的已读完自导入内容。
3. 允许确认标题、作者和可选来源链接。
4. 明确显示“提交后不可撤回；未通过后不可重新提交”的说明。
5. 调用用户提交 RPC，并显示“已提交，等待审核”的成功反馈。

移除用户端对 `generateRecommendationContent` 的依赖。Netlify AI 函数和配置本期不作为用户流程的一部分；是否删除在管理员后台稳定后另行决定。

### 5.2 推荐区

在推荐页增加“发现推荐”和“我的推荐”二级标签：

- 发现推荐沿用现有公开列表，仅获取 `active`。
- 我的推荐加载当前用户全部提交，显示状态、提交时间、审核通过时间、发布时间及可见原因。
- 待审核、审核通过、未通过、已下架内容不得出现在公开列表，也不得加入书架或评分。

### 5.3 管理员审核后台

在 `AdminPage` 增加“推荐审核”导航项：

1. 状态筛选和待审核计数。
2. 提交元信息、来源链接、内容快照预览和内容指纹。
3. 运营字段编辑器：推荐语、标签、中英摘录及翻译。
4. 内部备注编辑器。
5. 审核通过、拒绝、发布、下架、恢复待发布按钮；按钮只在有效状态下出现。
6. 拒绝和下架操作要求填写面向用户的原因。
7. 展示生命周期和审计摘要。

## 6. 兼容迁移

1. 现有 `active` 记录保持 `active`，不改变公开可见性。
2. 为历史公开记录补齐 `published_at`。若无可靠原始发布时间，使用 `created_at` 并在迁移说明中记录其含义。
3. 为历史公开记录生成快照。若原阅读记录不存在，保留现有公开读取路径并将记录标记为需要运营补录；不得让迁移失败阻塞线上表结构升级。
4. 修改现有状态 CHECK、`intro`/`excerpts` 约束、索引与 RLS 后，刷新 PostgREST schema cache。
5. 在迁移前导出或备份现有推荐记录与关联阅读记录，验证可回滚策略。

## 7. 测试与验收

### 7.1 数据库与权限

- 用户只能提交自己的已读完、自导入内容。
- 用户无法提交重复内容、修改状态、查看其他用户待审记录或内部备注。
- 管理员可查看快照、审核、发布、下架和重新发布。
- 公众只能看到 `active`，且不能读取待审快照。
- 发布 RPC 在推荐语或摘录缺失时失败。

### 7.2 状态流

- `pending -> approved -> active` 正常。
- `pending -> rejected` 后同一内容再次提交被拒绝。
- `active -> removed -> approved -> active` 正常，原因与时间保留。
- 被删除或编辑的原书架内容不影响管理员审核、发布和其他用户加入书架。

### 7.3 用户体验

- 长文提交不再调用 AI，提交响应不受模型生成时间影响。
- 我的推荐准确展示全部状态与用户可见原因。
- 公开页、加入书架和评分不受待审核或下架记录影响。
- 管理员编辑长摘录、正文预览和状态操作不会产生布局溢出或误发布。

## 8. 推荐实施顺序

1. 编写迁移：状态、字段、快照表、约束、索引、RLS 和 RPC。
2. 为现有公开数据完成兼容回填并验证迁移。
3. 改造服务层，使用户端与管理员端只调用受控 RPC。
4. 简化用户提交弹窗和资格检查。
5. 增加推荐页二级标签与“我的推荐”。
6. 增加管理员审核工作区。
7. 完成数据库、服务层和界面回归测试。
8. 确认用户流程稳定后，再决定是否弃用原用户端 AI 生成函数。
