## 一、阻塞项（实施前必须解决）

### 🔴 B1 — 现有直接 INSERT 通道未显式封堵，审核流可被完全绕过

**位置**：实施方案 §4.2、§6；现状根源在 `20260616000002_create_recommendation_submissions.sql` §4/§5

**问题**：
- 现有 RLS 策略 `Users can insert submissions` 的 WITH CHECK 仅校验 `submitter_user_id = auth.uid()`，**不限制 status 取值**；配合 `GRANT INSERT ON recommendation_submissions TO authenticated`，任何登录用户都可以通过 PostgREST 直接插入 `status='active'` 的记录，完全绕过审核流程。
- 实施方案 §4.2 只明确写了"用户不应获得 UPDATE 权限"，**全文没有一处明确要求撤销 INSERT 策略和 INSERT/UPDATE GRANT**。§6 迁移步骤仅笼统提到"修改现有……RLS"。
- 如果实施者按文档字面执行，新 RPC 上线后旧的直接插入通道仍然敞开，本次改造的核心安全目标（原则 §2.4）即告失败。

**建议**：
- 在迁移步骤中显式列出：`DROP POLICY "Users can insert submissions"`、`DROP POLICY "Users can update own submissions"`、`REVOKE INSERT, UPDATE ON public.recommendation_submissions FROM authenticated`，所有写入改由 SECURITY DEFINER RPC 执行。
- 在验收清单（§7.1）增加对应测试："通过 PostgREST 直接 INSERT `status='active'` 记录必须被 RLS/权限拒绝"。

### 🔴 B2 — `internal_note` 等字段无法靠 RLS 行级策略保护，存在列级泄漏

**位置**：实施方案 §3.1、§4.3；决策记录 §5.4

**问题**：
- 方案要求 `internal_note` "不向提交者或公众返回"，"我的推荐"查询"仅返回用户可见字段"。
- 但 RLS 是**行级**安全：现有 `Users can view own submissions` 策略允许提交者 SELECT 自己的整行，`Anyone can view active submissions` 允许任何人（含匿名）SELECT active 行的**所有列**。只要字段留在主表上，提交者和公众都可以直接 `.select('internal_note, reviewed_by, content_hash')` 读到——前端"只查需要的列"不构成安全边界，这与方案自己的原则 §2.4 直接矛盾。
- 同类风险字段：`reviewed_by`、`content_hash`、规范化来源链接字段。

**建议**（择一并写入方案）：
- **方案 A（推荐）**：将 `internal_note`（可选连同 `reviewed_by`/`content_hash`）拆到仅管理员可读的附属表（如 `recommendation_submission_admin_notes`），主表不留敏感列。
- **方案 B**：保留主表列，新建两个视图/SECURITY DEFINER 查询（公开视图仅含展示列、提交者视图仅含用户可见列 + `rejection_reason`/`removal_reason`），前端只查视图；同时用列级 `REVOKE` 兜底。
- 在验收清单增加测试："提交者和匿名用户直接查询 `internal_note` 必须失败或返回空"。

### 🔴 B3 — 两份文档的状态机相互矛盾：`active` 状态下能否编辑

**位置**：决策记录 §3.1 vs 实施方案 §4.2

**问题**：
- 决策记录 §3.1 状态说明表中，`active` 状态的管理员操作为"**编辑**、下架"。
- 实施方案 §4.2 的 `update_recommendation_editorial_content` 前置状态为 `pending`、`approved`、`removed`——**不含 `active`**。
- 两份文档对同一问题给出相反答案，实施时必然产生歧义：已发布内容被编辑会立即对公众生效，是否允许直接决定 RPC 的状态校验逻辑。

**建议**：
- 统一为一个口径。从运营效率看，建议允许 `active` 直接编辑（修正错别字、补充翻译不应要求先下架），同时将 `update_recommendation_editorial_content` 前置状态改为 `pending`、`approved`、`active`、`removed` 并同步修订决策记录；若选择不允许，则修改决策记录 §3.1 并说明"编辑已发布内容须先下架"的理由。
- 注意该决定与审计动作（S5）和 §7.2 状态流测试用例联动，需一并更新。

### 🔴 B4 — 去重与"永久唯一"规则的状态作用范围未定义

**位置**：决策记录 §2.6、§5.2；实施方案 §4.1 步骤 4

**问题**：决策确定了"同一用户、同一内容永久只能有一个提交记录"和"被拒绝后不能再次提交同一内容"，跨用户相同来源/指纹也阻止新建。但以下状态组合的规则两份文档均未覆盖：

1. `removed` 后能否重新提交？（管理员下架 ≠ 内容永久封杀：误下架与版权下架应区别对待，但当前没有字段区分下架性质）
2. 用户 A 的提交被 `rejected` 后，用户 B 提交同一内容是否允许？（§5.2 的跨用户阻止若覆盖 rejected，则 B 被连坐；若不覆盖，则与"避免多个用户为同一内容重复推荐"的意图冲突）
3. `content_hash` 与规范化 `source_url` 冲突时以谁为准？（同 URL 不同正文、同正文不同 URL 的优先级）
4. 实施方案 §4.1 只说"对历史提交执行去重"，未说明去重扫描哪些状态——这与每周限额"不统计 rejected"的口径叠加后行为不透明。

**建议**：在实施前补充一张「去重决策矩阵」：横轴为已有记录状态（pending/approved/active/rejected/removed），纵轴为匹配维度（同用户同指纹/同用户同链接/跨用户同指纹/跨用户同链接），逐格给出允许/拒绝及用户可见文案；并明确 `removed` 的重提交规则。

## 二、建议项（建议实施前讨论，不阻塞启动）

### 🟡 S1 — 每周限额与"拒绝不占额度"组合存在刷审漏洞

实施方案 §4.1 建议限额只统计 `pending`、`approved`、`active`，不把 `rejected` 计入额度。叠加 B4 的"同内容永久唯一"，用户可以每周用不同垃圾内容各提交一次、被拒不付任何额度代价，审核成本完全转嫁管理员。`removed` 是否计入额度也未说明。

**建议**：RPC 内同时统计"尝试次数"（含 rejected）做软上限（如每周最多 N 次尝试、其中有效提交 1 次），或至少在决策记录中注明"rejected 刷审暂不处理"为已知限制。

### 🟡 S2 — 现有 excerpts CHECK 约束实际无效，新条件约束不要沿用旧写法

`20260617000001` 的约束为 `array_length(excerpts, 1) > 0 AND array_length(excerpts, 1) <= 5`，但 `array_length('{}', 1)` 返回 NULL，CHECK 表达式求值为 NULL 时**放行**——当前"至少一条摘录"实际只靠应用层保证。新方案把约束改为条件约束（仅 active 强制）时，应使用 `cardinality(excerpts)` 或 `COALESCE(array_length(excerpts,1),0)` 写法，避免把旧缺陷带进新约束。

### 🟡 S3 — 提交 RPC 的关键契约细节未定义

`submit_recommendation_for_review` 尚缺：返回值契约（"我的推荐"需要立即展示新记录，建议返回完整插入行）；记录 ID 生成方式（当前由客户端生成 `rec_` 前缀 ID，新 RPC 应在服务端生成）；规范化来源链接规则（host 小写、去尾部斜杠、是否剥离 utm 等跟踪参数）；content_hash 的标准化输入（决策 §8.2 只有建议，未定稿——建议明确为"NFKC + 空白折叠后的正文拼接 title/author 后取 SHA-256"，并写入方案）。

### 🟡 S4 — 管理员读取路径所需的新 RLS 策略未列出

方案 §4.3 提到"管理员审核查询返回全部状态、私有快照和内部备注"，但迁移步骤未列出所需的新策略：`recommendation_submissions` 的管理员 SELECT-all 策略、快照表的提交者 SELECT-own / 管理员 SELECT-all 策略。若管理员查询全部走 SECURITY DEFINER RPC 也应写明，二者择一。同时所有新 SECURITY DEFINER 函数应沿用现有惯例 `SET search_path = public`。

### 🟡 S5 — 审计覆盖不全，且写入路径需要明确

1. 审计动作清单（§3.3）没有覆盖 `update_recommendation_editorial_content` 的内容编辑和 `internal_note` 变更——运营字段谁改的、何时改的不可追溯。
2. `recommendation.pending_created` 的 actor 是普通用户，而现有 `audit_logs` INSERT 策略仅允许管理员写入（`20260511112500`）。方案应明确"本期所有审计一律在 SECURITY DEFINER RPC 内写入，不走客户端 `createAuditLog`"，否则用户提交审计必然写入失败。

**建议**：动作清单补充 `recommendation.editorial_updated`；在 §3.3 增加一句审计写入路径约定。

### 🟡 S6 — 重新发布后的字段语义与"我的推荐"展示字段不全

1. `removed → approved → active` 重新发布时：`published_at` 是更新为最新发布时间还是保留首次？`removal_reason`/`removed_at` 是清空还是保留（§7.2 要求"原因与时间保留"，与"我的推荐"不再展示已恢复记录的下架信息之间存在张力）？建议区分 `first_published_at` 与 `published_at`，或在方案中明确覆盖语义。
2. §5.2 "我的推荐"展示字段未列入拒绝时间和下架时间（`reviewed_at`/`removed_at`），仅有原因没有时间对用户体验不完整。

### 🟡 S7 — 管理员运营编辑范围不含标题/作者/来源链接

`update_recommendation_editorial_content` 只更新推荐语、标签、摘录和翻译。但提交者填写的标题可能有错别字、来源链接可能失效或指向风险站点（决策 §2.8 要求管理员审核来源）——管理员发现元数据问题只能整条拒绝，无法修正后发布。

**建议**：将 title/author/source_url 修正纳入运营编辑 RPC（主表展示字段，快照保持原始不变），或在方案中明确"元数据有误只能拒绝"的产品口径。

### 🟡 S8 — 提交弹窗的资格检查应借 RPC 化一并解决 N+1 与新口径

现状弹窗对每个候选条目**串行**调用 `checkSubmissionEligibility`，每个条目最多发起 4 次查询（条目读取 + 读完校验 RPC + 周计数 + 去重），书架内容多时会明显卡顿。新流程还需额外排除"已有任意状态提交"的条目。

**建议**：新增一个 `list_submittable_readings()` RPC 一次性返回可提交列表，前端不再逐项检查；这同时落实 B4 的排除口径。

### 🟡 S9 — 用户侧旧写入能力的清理清单不完整

§5.1 只提了弹窗重构，未列出服务层需要删除/停用的旧能力：`submitRecommendation`（直接 INSERT active）、`updateRecommendation`、`removeRecommendation`（用户自行下架/编辑已发布内容，与决策 §2.6"不可撤回"冲突）。经核实这些函数目前仅在 `services/supabase/index.js` 导出、无组件使用，属于可安全移除的死出口；但若不显式删除，后续开发可能误用。

**建议**：在 §8 实施顺序的服务层改造步骤中逐项列出待删除函数。

### 🟡 S10 — AdminPage 存在死代码，新增导航项时建议顺带清理

`AdminPage.jsx` 的 `handleSubmit`/`handleStatusChange`/`handleSeedBuiltInArticles` 引用了未导入的 `updateFeaturedArticle` 等函数（位于 `currentPage === '_removed'` 和 `{false && ...}` 的不可达分支），"首页"快捷入口的 `articles` 页只渲染迁移说明。新增"推荐审核"导航项在结构上完全可行，但建议在本期顺带删除死代码，避免后续维护者误读。

### 🟡 S11 — 验收测试清单（§7）缺少关键安全与审计用例

建议补充：
- 直接 INSERT `status='active'` / UPDATE 他人记录被 RLS 拒绝（对应 B1）；
- 提交者与匿名用户读不到 `internal_note` 等管理员字段（对应 B2）；
- 每个管理员 RPC 调用后审计日志逐条校验（动作、actor、payload 摘要）；
- 被拒绝后同一内容（同指纹或同链接）再次提交被拒绝（决策 §2.6）；
- 用户删除或修改原书架内容后，审核、发布、他人加入书架仍正常（§7.2 已含"不影响"，建议补一个"原内容删除后加入书架读取快照成功"的明确用例）。

### 🟡 S12 — 现状描述与代码有一处出入

决策记录 §1 与实施方案 §2 称"用户提交必须等待 AI 生成完成、内容齐备后才写入"。实际 `SubmitRecommendationModal` 在 AI 失败时提供"手动填写"降级路径，用户可完全不经过 AI 直接提交。这不妨碍本期改造方向（恰恰说明用户提交本就不依赖 AI），但"现状"描述应修正，以免后续文档引用失真。

## 三、审核发现的正面确认

以下设计决策和方案要点经审核确认合理有效：

| # | 项目 | 确认理由 |
|---|------|---------|
| ✓ | 私有不可变快照表 | 解决"提交后用户改/删书架内容导致审核与发布失效"的根本问题，与公开字段分离避免 RLS 泄漏，方向正确 |
| ✓ | 沿用 `active` 表示公开状态 | 避免不必要的兼容性改名，历史数据、索引、公开 RLS、前端过滤均可平滑过渡 |
| ✓ | 状态机主路径（pending→approved→active→removed→approved） | 审核与发布分离、可回退，满足"可审计、可回退"原则 |
| ✓ | 权限边界放在 RPC + RLS 而非前端 | 原则正确（但落实完整性见 B1/B2） |
| ✓ | 迁移方案 §6 | 历史记录保持公开、快照回填失败不阻塞表结构升级、PostgREST cache 刷新、迁移前备份，均稳妥 |
| ✓ | 审计不复制内部备注全文 | 只记状态变化与变更摘要，敏感信息最小化 |
| ✓ | 积分扩展边界（独立账本表 + 幂等事件键） | 不在主表维护可变余额，为未来结算保留正确关联点 |
| ✓ | 发布完整性用 CHECK 或发布 RPC 数据库级保证 | 不把运营字段完整性交给前端 |
| ✓ | 频率限制移入 RPC 校验 | 修复当前仅前端校验的弱点 |
| ✓ | 本期不做 AI/积分/通知 | 范围收敛合理，实施顺序 §8 的依赖关系正确 |

## 四、总结

### 阻塞项清单

| # | 类别 | 摘要 |
|---|------|------|
| B1 | 安全边界 | 现有直接 INSERT 策略/GRANT 未显式撤销，审核流可被绕过 |
| B2 | 数据安全 | `internal_note` 等列无法靠行级 RLS 保护，需拆表/视图/列级权限 |
| B3 | 文档矛盾 | 决策记录允许 active 编辑，实施方案不允许，状态机口径冲突 |
| B4 | 规则缺失 | 去重与永久唯一规则对各状态（rejected/removed、跨用户）的作用范围未定义 |

### 建议项清单

| # | 类别 | 摘要 |
|---|------|------|
| S1 | 规则漏洞 | rejected 不占额度 + 永久唯一组合存在刷审漏洞 |
| S2 | 约束缺陷 | 现有 excerpts CHECK 因 NULL 语义实际无效，新约束勿沿用旧写法 |
| S3 | 契约细节 | 提交 RPC 返回值、ID 生成、链接规范化、指纹算法未定稿 |
| S4 | 权限遗漏 | 管理员读取 submissions/快照的新 RLS 或 RPC 路径未列出 |
| S5 | 审计 | 编辑动作无审计；用户动作审计须明确在 RPC 内写入 |
| S6 | 字段语义 | 重发布时 published_at/removal_reason 语义未定；我的推荐缺拒绝/下架时间 |
| S7 | 运营能力 | 管理员无法修正标题/作者/来源链接，只能整条拒绝 |
| S8 | 性能 | 资格检查 N+1，建议一个 RPC 返回可提交列表 |
| S9 | 清理清单 | 服务层旧写入函数（submitRecommendation 等）未列入删除范围 |
| S10 | 代码健康 | AdminPage 存在引用未导入函数的死代码，建议顺带清理 |
| S11 | 测试缺口 | 缺 RLS 绕过、列级泄漏、审计逐条、拒绝后重提交等关键用例 |
| S12 | 文档准确性 | 现状描述夸大了 AI 在用户提交流程中的前置性 |

### 审核结论

**有条件通过**。产品目标、状态机主干、快照与审计的总体设计方向正确，实施顺序合理。但 B1（直接插入通道未封堵）和 B2（敏感字段列级泄漏）直接关系到本次改造"审核不可绕过、内部信息不可泄漏"的核心价值，B3（状态机文档矛盾）和 B4（去重规则作用范围）会在实施中立刻阻塞编码决策——这 4 项必须在动工前修订进方案文档。建议在阻塞项全部解决、S1–S12 经过评审后，再按 §8 顺序开始编码。
