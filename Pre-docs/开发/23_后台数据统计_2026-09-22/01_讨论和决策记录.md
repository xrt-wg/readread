# 后台数据统计（用户增长与使用） — 讨论和决策记录

> 日期：2026-09-22
> 关联：[02_实施方案](02_实施方案.md)

## 一、背景与需求

后台现有「首页」只有 3 个即时数字（用户总量 / 受限用户 / 最近活跃用户），没有时间维度，看不出「增长」；也没有任何「使用」维度的统计。管理员（作者本人）希望新增一块能看「用户增长 + 使用情况」的能力。

需求（经多轮澄清，最终收敛为以下四点）：

1. **顶部卡片只保留「用户 + 活跃」**：用户总量、今日新增、当前 DAU / WAU / MAU；
2. **时间趋势图 4 张（可切日/周/月）+ 1 个留存区**：新增注册趋势、累计用户增长、活跃用户趋势（近似）、阅读活跃趋势（开始读 / 读完 / 新增阅读）；留存/回访以 d1/d7/d30 独立留存区呈现（近似、与粒度无关）；
3. **「活跃趋势 / 留存」采用「有产出行为」近似口径**（详见 D2 / D3）；
4. **明确排除**：内容产出总量卡片（正在读 / 已读完 / 收藏总量）、回顾（复习）统计、收藏趋势、推荐/评分统计、严格登录 DAU 埋点、数据导出、单用户行为下钻。

## 二、现状调查结论

### 2.1 现有后台结构

- 后台入口 [AdminPage.jsx](../../../src/components/AdminPage.jsx) 已有侧栏结构（首页 / 推荐审核 / 首次阅读 / 审计日志 / 用户基础信息），首页为 3 张 `StatCard` + 快捷入口（约 386–409 行），无任何时间趋势或使用统计。
- `StatCard`、`AccessDeniedState`、`resolveAdminErrorMessage` 均为 AdminPage 内部局部组件/函数，暂无共享。

### 2.2 权限与数据可用性

- `profiles` 有 admin 查询策略 `profiles_select_admin`（[20260509175000_establish_access_policies.sql](../../../supabase/migrations/20260509175000_establish_access_policies.sql)，走 `is_current_user_admin()`）；但 `readings` / `bookmarks` 只有「own」策略（`auth.uid() = user_id`），**无 admin 查询策略** → 跨所有用户的聚合统计**必须走 SECURITY DEFINER RPC**，不能前端直查。

### 2.3 关键字段的可得性与可靠性

| 字段 | 来源 | 语义 | 能否回溯历史 |
|---|---|---|---|
| `profiles.created_at` | 触发器 `handle_new_auth_user` 注册时插入；早期用户迁移时用 `auth.users.created_at` 回填 | 注册时间 | ✅ 可靠、不可变 |
| `profiles.last_seen_at` | `ensure_profile()` RPC，每次应用加载/登录/刷新会话时更新（[AuthProvider.jsx](../../../src/providers/AuthProvider.jsx) 约 80 行调用） | 最近一次打开应用 | ❌ 覆盖式，仅能算当前快照 |
| `readings.created_at` | `createReading` 导入/新增时写入 | 新增阅读时间 | ✅ |
| `readings.reading_started_at` | `start_reading`（取书进阅读区）写入，`COALESCE` 保留首次；**`restart_reading` 会重置为 now** | 最近一次开始读 | ✅（近似，见 2.4） |
| `readings.reading_finished_at` | `returnToShelf(completed=true)`（还书标读完）写入；`restart_reading` 清空 | 最近一次读完 | ✅（近似） |
| `bookmarks.created_at` | 划词收藏时写入 | 收藏时间 | ✅ |
| `bookmarks.review_count` / `familiarity` / `next_review_at` | 回顾反馈时由 [reviewUtils.js](../../../src/utils/reviewUtils.js) `computeNextReview` 算好后 upsert | 仅累计计数 + 下次排期 | ❌ 无每次回顾时间戳 |

### 2.4 关键结论（技术判断依据）

1. **RLS 限制决定聚合形态**：`readings` / `bookmarks` 无 admin select 策略，统计 RPC 必须 `SECURITY DEFINER` 并显式 `is_current_user_admin()` 校验。
2. **活跃/留存的历史数据缺失 → 「有产出」近似**：`last_seen_at` 覆盖式、无逐日活跃记录，无法回溯「过去每天有多少人活跃」。唯一能回溯全历史、不可变的时间戳是 `readings.created_at` / `bookmarks.created_at`（产出时间戳）→ 用「有产出行为」近似活跃。**「有产出」按「是否发生过」计：`created_at` 一经写入即不可变，后续删除（`deleted_at`）/归档（`status='archived'`）都不影响「当天曾产出」这一事实，故统计不排除已删除/已归档内容。**
3. **回顾趋势彻底不可回溯**：回顾只有 `review_count` 累计计数，连一个可用的时间戳都没有（`updated_at` 会被翻译/归档/编辑同时改动，无法区分）→ 排除。
4. **`reading_started_at` / `reading_finished_at` 在「重新阅读」时会被重置/清空**，反映的是「最近一次」而非「完整历史」，但对单日趋势计数影响可忽略（一天内反复重启同一本很罕见），接受此近似。
5. **时区口径**：`now()` / `date_trunc` 默认走会话时区（Supabase 会话默认 UTC），会与管理员本地（UTC+8）日历错位。**定稿：RPC 函数级 `SET timezone = 'Asia/Shanghai'`（进入函数生效、退出恢复），使「今日/本周/本月」与管理员本地日历一致。**

## 三、决策记录

### D1 载体 → 后台新增「数据统计」独立子页

- 备选：塞进现有首页；改造首页 dashboard。
- **决策：新增独立 nav 子页「数据统计」，首页保持现状。** 理由：4 张图 + 留存区 + 粒度切换自成一个完整模块，混入「核心统计概览」首页会让首页语义变重、职责不清。

### D2 活跃口径 → 「有产出行为」近似（新增阅读或收藏）

- 备选：新建活跃事件表埋点（历史留白、需持续埋点）；只用 `last_seen_at` 做快照（无历史趋势）。
- **决策：历史活跃趋势 = 每个时间窗「新增 readings 或 bookmarks」的去重 user_id；当前 DAU/WAU/MAU 用 `last_seen_at` 精确算。** 理由：产出时间戳不可变、可回溯全部历史；「新增阅读/收藏」是强活跃信号，比「打开过应用」更代表真实使用；受众是「自己看、够用即可」，不引入埋点表。
- **口径边界（产出=发生过即计入）**：活跃/留存只认 `created_at`（不可变产出时间戳），**不因后续删除（`deleted_at`）或归档（`status='archived'`）排除**——用户当天收藏了就是收藏了，之后删除/归档不改变「当天曾产出」的事实。
- **明确语义**：这是「使用活跃」，不是「登录活跃」；只浏览不产出的用户会被低估（对运营判断影响小）。

### D3 留存口径 → 同产出近似的滚动 cohort（N 日内累计留存）

- **决策：N 日内留存 = 「注册时间落在 [now-(N+7)天, now-N天)（滚动 7 天 cohort 窗口）的用户中，注册后 N 天内仍有产出行为（新增阅读/收藏）的比例」，N ∈ {1, 7, 30}。** 理由：与 D2 同源、无需额外埋点；滚动 7 天 cohort 平滑小样本抖动；窗口下界 `now-(N+7)` 保证 cohort 覆盖整整 7 个注册日、且所有 cohort 内用户均已「满 N 天」、有充分观察期。
- **术语澄清**：这是「**N 日内**留存」（注册后 N 天内**累计**有产出），不是「第 N 天留存」（仅第 N 天当日有产出）；也非业界通行的「次日/7 日登录留存」。UI 须标注「累计留存（注册后 N 天内仍有产出，近似）」。

### D4 聚合形态 → 单一 RPC 返回快照 + 序列 + 留存

- 备选：按指标拆多个 RPC；前端直查（被 RLS 拒）。
- **决策：一个 `admin_get_growth_stats(p_granularity, p_window_days)` 返回 jsonb（`snapshot` + `series` + `retention`），一次往返。** 理由：多张图共享同一时间轴，单 RPC 减少往返与前端拼接；粒度切换通过参数下发，桶化在 SQL 内用 `date_trunc` 完成，保证周/月语义正确（周按 ISO 周一、月按自然月）。

### D5 内容产出卡片 → 排除

- **决策：原方案顶部「正在读 / 已读完 / 收藏总量」为累计快照，无对比基准、价值弱，且与下方趋势图重复，删除。** 顶部只保留「用户 + 活跃」五张卡。

### D6 回顾统计 → 排除（本次）

- **决策：回顾机制无每次回顾时间戳，趋势不可回溯；快照卡价值低，本次不做。** 日后若确需回顾趋势，再另立「回顾事件表」埋点。

## 四、最终方案要点

| 维度 | 决策 |
|---|---|
| 载体 | 后台新增「数据统计」独立子页，首页不动 |
| 快照（5 卡） | 用户总量 / 今日新增 / DAU / WAU / MAU（`last_seen_at`） |
| 序列（可切日/周/月） | 新增注册 / 累计用户 / 活跃(近似) / 阅读活跃三线（开始读/读完/新增阅读） |
| 留存 | d1 / d7 / d30（N 日内累计留存，产出近似，粒度无关） |
| 聚合 | 单 RPC `admin_get_growth_stats(granularity, window_days)`，SECURITY DEFINER |
| 时区 | RPC 函数级 `SET timezone = 'Asia/Shanghai'`，本地日历对齐 |
| 迁移 | 1 个迁移脚本 `20260922000001_admin_growth_stats.sql` |

## 五、风险与注意点

1. **RLS / 权限**：`readings` / `bookmarks` 无 admin select 策略，RPC 必须 `SECURITY DEFINER` 并在函数首行 `is_current_user_admin()` 校验；`revoke all ... from public/anon/authenticated` 后仅 `grant execute ... to authenticated`。
2. **近似口径的诚实标注**：活跃与留存是「使用活跃」近似，不是严格登录 DAU；UI 需区分措辞——顶部卡「DAU（打开应用）」，图表「活跃用户（有产出 · 近似）」，留存「累计留存（近似）」，避免同屏两个「活跃」数值产生混淆。
3. **时间戳重置语义**：`reading_started_at` / `reading_finished_at` 在「重新阅读」时重置/清空，反映「最近一次」；已接受，不另做事件表。
4. **时区口径**：函数级 `SET timezone = 'Asia/Shanghai'` 已定；若日后管理员跨时区使用，需改为可配置或回退 UTC + 显式标注。
5. **部署顺序（对齐既有惯例）**：迁移经 Dashboard SQL Editor 手工执行，须**先跑迁移、确认 RPC 可调用，再发布前端**；前端在 RPC 返回字段缺失（空数据）时降级显示空态，RPC 未部署（404）时走错误态，两种状态区分、不误判。
6. **`create or replace` 无既有 grant**：`admin_get_growth_stats` 为全新函数，默认 `create function` 会授予 PUBLIC，必须显式 `revoke all` 后 `grant`。
7. **颜色规范**：新增 UI（卡片、图表、粒度切换）全部走 `var(--*)`，不引入硬编码颜色（CLAUDE.md 颜色规范）；图表配色遵循亮暗双主题一致。
