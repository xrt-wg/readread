## 三、问题清单（按严重程度）

### P0-1　`jsonb_agg` 参数内嵌套窗口函数，RPC 运行期直接报错

实施方案 §3.1 SQL 的「累计用户」计算：

```sql
select jsonb_agg(
  jsonb_build_object(
    'bucket', bucket,
    'new_users', new_users,
    'cumulative_users', v_baseline + sum(new_users) over (order by bucket),
    ...
  ) order by bucket
)
into v_series
from joined;
```

`sum(new_users) over (order by bucket)` 是**窗口函数**，却出现在**聚合函数 `jsonb_agg(...)` 的参数表达式**内。PostgreSQL 明确禁止此写法，首次调用该 RPC 即报：

```
ERROR:  aggregate function calls cannot contain window function calls
```

（plpgsql 对函数体只做语法校验，该语义错误在运行期首次执行该 SQL 时触发，而非 `create function` 时。因此迁移能建成功、但 RPC 一旦被前端调用整块功能即失效，属「部署到一半才暴露」。）

**修正建议**：先把窗口求和物化到子查询/CTE，再聚合：

```sql
with cum as (
  select j.*,
         v_baseline + sum(j.new_users) over (order by j.bucket) as cumulative_users
  from joined j
)
select jsonb_agg(
  jsonb_build_object(
    'bucket', bucket,
    'new_users', new_users,
    'cumulative_users', cumulative_users,
    'active_users', active_users,
    'reading_started', reading_started,
    'reading_finished', reading_finished,
    'new_readings', new_readings
  ) order by bucket
)
into v_series
from cum;
```

### P1-1　时区语义未定义：「今日新增」与所有日期桶按 UTC 切分，与管理员本地日错位

SQL 中 `date_trunc('day', now())`、`date_trunc(v_granularity, created_at)::date` 均在**会话时区**下截断。Supabase 会话时区默认 UTC，而 `profiles.created_at` 写入时显式 `timezone('utc', now())`。结果是：

- 「今日新增」= **UTC 日**的新增，对 UTC+8 的管理员而言，本地 07:59 的注册会被计入「昨天」，本地 08:00 才翻页；
- 日/周/月桶边界、图表 x 轴日期标签全部是 UTC 日期，与管理员的本地日历不一致。

文档 D4 只讨论了「周按 ISO 周一、月按自然月」的粒度语义，**完全未涉及时区**。

**修正建议**：二选一并显式记录——
- （a）接受 UTC 口径：在文档 §2.4/§五验收 与 UI 上标注「日期按 UTC」，避免误读；
- （b）对齐管理员本地时区：函数内 `set local timezone to 'Asia/Shanghai'`（或 `date_trunc('day', created_at at time zone 'Asia/Shanghai')` 等），使「今日/本周/本月」与管理员日历一致。

鉴于「今日新增」是顶部头号指标、且受众是中文用户，建议选（b）或至少显式声明（a）。

### P1-2　活跃/留存用 `deleted_at is null` 过滤，导致「产出历史可追溯」被删除行为追溯性擦除

D2/D3 的立论核心是「产出时间戳（`readings.created_at` / `bookmarks.created_at`）**不可变、可回溯全部历史**」。但 SQL 的 `activity` CTE 对两表都加了 `where deleted_at is null`：

```sql
activity as (
  select user_id, created_at from public.readings  where deleted_at is null
  union all
  select user_id, created_at from public.bookmarks where deleted_at is null
)
```

而 `restart_reading`（`20260921000001`，:27-31）会把该 reading 的**全部 bookmarks 软删**（`deleted_at = now()`），`delete_reading`/`soft_delete_reading` 会软删 reading。因此：

- 用户某天「有产出」，但之后该产出对象被重新阅读清场/删除，则那天的活跃/留存信号被**追溯性抹掉**；
- 越早的历史数据越可能被后续删除侵蚀，活跃/留存曲线随时间下移，**与「不可变时间戳、可回溯全部历史」的立论自相矛盾**。

**修正建议**：二选一并显式记录——
- （a）「有产出」按「是否发生过」计：去掉 `deleted_at is null`（对 `bookmarks` 可再议是否含 `status='archived'`，见 P2-5）；
- （b）保留 `deleted_at is null` 但显式声明「仅统计当前存活产出，历史值会随删除/清场下移」，并相应弱化 §2.4「可回溯全部历史」的表述。

### P2-1　「5 张趋势图」与「4 张趋势图」在两份文档间不一致

### P2-2　「滚动 7 天 cohort 窗口」实际宽度为 6 天（off-by-one）

D3 与 `02 §二` 写「滚动 **7 天** cohort 窗口」，窗口公式为 `[now-(N+6), now-N)`。该区间宽度 = `(N) - (N+6)` 的差 = **6 天**（例：N=1 时 `[now-7, now-1)` 覆盖 6 个整日）。

**修正建议**：二选一——若要 7 天窗口，下界改为 `now-(N+7)`；若确为 6 天，文档措辞统一为「滚动 6 天」。影响 cohort 样本量（平滑度）与文档可信度。

---

### P2-3　「第 N 天留存」术语与「N 日内留存」实现不符

D3 用「第 N 天留存」表述，但 D3 正文与 SQL 都实现为「注册后 **N 天内**仍有产出」的**累计**口径（`a.created_at < p.created_at + make_interval(days => h.d)`）。「第 N 天留存」（第 N 天当日仍有产出）与「N 日内留存」（N 天内累计有产出）语义不同，d7/d30 尤甚。

**修正建议**：全文统一为「N 日内留存」，并在 UI 注明「累计留存（注册后 N 天内仍有产出，近似）」，避免后续被误读为业界通行的「次日/7 日登录留存」。

### P2-4　快照 DAU 与序列「活跃」同用「活跃」字样、口径不同，UI 未计划区分

- 顶部 DAU/WAU/MAU 卡 = `last_seen_at`（**打开应用**，精确）；
- 序列「活跃用户趋势」= 有产出（**新增阅读/收藏**，近似）。

两者都是「活跃」但口径不同，同一屏可能出现「DAU 卡 = 42」而「活跃趋势今日 ≈ 8」。文档 D2 已认识此差异（「这是使用活跃，不是登录活跃」），但 `02 §3.3` 仅计划给序列标「近似」，未计划给 DAU 卡标注口径。

**修正建议**：UI 上用差异化措辞显式区分——如卡牌「DAU（打开应用）」，图表「活跃用户（有产出 · 近似）」，避免管理员在同一屏对两个「活跃」数值产生混淆。

### P2-5　bookmarks 新增的 `status`/`archived_at` 维度未纳入统计口径考量

`20260921000000_add_bookmark_status.sql` 已给 bookmarks 增加 `status`（'active'/'archived'）。统计的 `activity` 仅按 `deleted_at is null` 过滤，**未提及 `status`**：归档收藏是否计入「活跃/留存」完全未定义。

- 若「有产出」指历史发生过，归档收藏应计入（用户确实收藏过）；
- 若指「当前活跃资产」，则需 `status='active'`。

**修正建议**：在 §2.4 或 §3.1 显式声明归档收藏的归属口径，并在 SQL 中相应处理（当前 `deleted_at is null` 已隐式把「重新阅读清场的软删书签」排除，但「归档」是另一维度，二者语义不同，需一并说清）。

### P2-6　复用对象为 AdminPage 模块私有，GrowthStatsPanel 无法直接「复用」

`02 §3.3` 称「复用 AdminPage 的 `StatCard` 视觉」、§3.3 称「复用 `isLibraryAccessError` / `resolveAdminErrorMessage` 语义」。经核：

- `resolveAdminErrorMessage` 定义在 `AdminPage.jsx:29`，**模块私有**，未从 `errorUtils.js` 导出（`errorUtils.js` 只导出 `isLibraryAccessError` / `resolveLibraryErrorMessage`）；
- `StatCard`（`AdminPage.jsx:37`）同为私有局部组件，且 dashboard、users 页已多处使用。

`GrowthStatsPanel` 是独立文件，无法直接 import 这两个私有对象。

**修正建议**：实施前定夺二选一——
- （a）把 `StatCard`、`resolveAdminErrorMessage`（或统一到 `resolveLibraryErrorMessage`）抽到共享模块，`AdminPage` 与 `GrowthStatsPanel` 共用；
- （b）面板内自实现同款卡片与错误提示，并接受两处视觉/文案可能漂移。
建议（a），避免卡片视觉与错误文案后续漂移。

### P3-1　`count(*)` 赋给 `int` 变量，存在隐式 bigint→int 收窄

`v_total_users` / `v_today_new` / `v_dau` / `v_wau` / `v_mau` / `v_baseline` 均声明为 `int`，但 `select count(*)` 返回 `bigint`，赋值处隐式收窄。当前规模无碍（远超 21 亿才溢出），属类型卫生问题。建议统一声明为 `bigint`，与 `count(*)` 一致。

### P3-2　迁移脚本大小写风格与既有迁移不一致

既有迁移（如 `20260921000001`）用大写 `BEGIN` / `CREATE OR REPLACE` / `REVOKE` / `GRANT`，本迁移用全小写 `begin` / `create or replace` / `revoke` / `grant`。不影响执行，为一致性建议统一为大写。

### P3-3　周/月粒度下首桶可能回退到窗口外（边界说明缺失）

`v_axis_start := date_trunc(v_granularity, now() - make_interval(days => greatest(p_window_days - 1, 1)))` 先把下界 `date_trunc` 到周/月起点，导致第一个桶实际覆盖了比 `window_days` 略早的几天（如 week 粒度下 `now()-364天` 落在周三，首桶回退到周一）。对「看趋势」无实质影响，但建议在 §3.1 关键点补一句「首桶可能含窗口外前置天数」的边界说明。

## 五、正面确认（经独立验证判定正确，予以肯定）
