> 日期：2026-09-21
> 审核对象：[01_讨论和决策记录](01_讨论和决策记录.md)、[02_实施方案](02_实施方案.md)
> 审核方式：逐条对照当前代码与全部 `supabase/migrations/*` 脚本，独立复核一致性、分析完备性、方案合理性与有效性。

## 结论（TL;DR）

**当前方案不可直接实施。** 存在 1 个阻断级缺陷（迁移里的 RPC 重写会让回顾队列在运行时报错），须先修正后复审。

整体判断：数据模型决策（`status` + `archived_at`）、覆盖式 upsert 风险识别、正文高亮保留、导出导入 round-trip 分析均**正确且与代码一致**；方案框架成立。但**「现状调查」的溯源停留在过时的 `20260714000000` 版本**，遗漏了后续两次对 `get_due_bookmarks` 的修复，导致迁移 SQL 出现致命错误；同时把「统计过滤」当作拦截点，而对应的 `computeReviewStats` 实为未被任何组件消费的死代码，使验收项 #7 不可验证。

## 一、阻断级（必须先修）

### B1　迁移重写 `get_due_bookmarks` 用回已被废弃的 `SELECT b.*`，会在运行时破坏回顾队列

**证据链：**

1. 02 文档 §3.1 的 RPC 重写（第 92–136 行）三段子查询均写 `SELECT b.*, r.title AS article_title`；其「关键点」注释（第 139 行）宣称「原函数体 `SELECT b.*`，加列后 `b.*` 多出 `status`/`archived_at`，RETURNS TABLE 必须补齐这两列」。
2. 01 文档 §2.3 点 4（第 55 行）同样断言「`get_due_bookmarks` RPC 用 `SELECT b.*`」。
3. **但当前生效的函数体并非 `b.*` 版本**。`20260717000001_fix_get_due_bookmarks_result_columns.sql` 已把三段子查询改为**显式列清单**（[该文件第 44–52 行](supabase/migrations/20260717000001_fix_get_due_bookmarks_result_columns.sql#L44-L52)），其文件头注释写明原因：`translation_provider` 是后来 `ALTER TABLE ... ADD COLUMN` 追加到 `bookmarks` 末尾的（见 [20260617000003_add_translation_provider_column.sql](supabase/migrations/20260617000003_add_translation_provider_column.sql)），导致 `bookmarks` 的**物理列序**为 `… deleted_at, translation_provider`，而 RETURNS TABLE 约定 `translation_provider` 紧跟在 `translation` 之后。`SELECT b.*` 的输出列序与 RETURNS TABLE 不符，运行时报「structure of query does not match function result type」或静默错位。

**问题本质：** 文档的「现状调查」只追溯到 `20260714000000_get_due_bookmarks_rpc.sql`（`b.*` 版），漏了 `20260717000000`（列歧义修复）与 `20260717000001`（显式列序修复）两次后续迁移。于是重写 SQL 复用了早就被证明错误的 `b.*` 写法，并且新增的 `status`/`archived_at` 也会因物理列序（`… deleted_at, translation_provider, status, archived_at`）与 RETURNS TABLE（`… deleted_at, status, archived_at, article_title`）错位而进一步失真。

**影响：** 迁移执行后，云端 `listDueBookmarks` 调 RPC 直接失败，回顾队列瘫痪；且由于文档把「迁移 + RPC 重写」作为同一会话顺序执行，错误会与加列一起落库。

**修复建议：** 迁移中的 RPC 必须沿用 `20260717000001` 的**显式列清单**写法，仅做两处增量：
1. 在三段 `SELECT` 的列清单中，把 `b.status, b.archived_at` 插到 `b.deleted_at` 之后、`r.title AS article_title` 之前；
2. 在 RETURNS TABLE 中对应位置补 `status text, archived_at timestamptz`；
3. 五个 `WHERE`（两个 COUNT + 三个子查询）统一补 `AND b.status = 'active'`（这部分文档已做对）。

## 二、高（分析完备性 / 验收可验证性）

### B2　`computeReviewStats` 是死代码，却被当作「第二拦截点」并列为验收项 #7

**证据：** 全仓搜索 `computeReviewStats` 的引用，除 [src/utils/reviewUtils.js:102](src/utils/reviewUtils.js#L102) 的定义外**无任何调用方**。`reviewUtils` 的既有 import 只用到 `TYPE_DOT/TYPE_LABEL/formatDate`（ReviewCard）、`computeNextReview`（ReviewPanel）、`shuffleArray`（ReviewModal）、`isDue/shuffleArray`（readings.js）——没有一处消费 `computeReviewStats`。当前头部统计（[ImportPage.jsx:425](src/components/ImportPage.jsx#L425) 的「条收藏」）直接用 `bookmarks.length`，回顾区（ReviewPanel）用的是本轮 `sessionStats`，均不经过 `computeReviewStats`。

**问题：**
- 01 文档 §2.3 点 2（第 53 行）称归档是「单点拦截：队列过滤 + 统计过滤（computeReviewStats）」——把未接线的函数当成现状拦截点，**现状调查不准确**。
- 02 文档 §3.3 修改 `computeReviewStats` 排除归档，验收标准 #7「回顾统计（total/due/mastered）不含归档收藏」——**没有任何 UI 展示这些指标**，该验收项无法通过用户可见行为验证，且该项改动当前是惰性的。

**修复建议（二选一）：**
- 方案 A：把 `computeReviewStats` 接入 BookmarkManager 头部（展示「待复习 / 已掌握 / 总数」三指标，基于 active 集合），使 §3.3 与 #7 有真实落点；
- 方案 B：明确标注 §3.3 为「未接线、仅前瞻性改造」，并把 #7 从验收标准降级或改写为「`computeReviewStats` 单元行为」而非「回顾统计 UI」。

## 三、中（口径 / 跨模式缺陷）

### B3　两个「活着」的可见收藏计数未定义口径，与「total 排除归档」立场脱节

- 头部统计 pill（[ImportPage.jsx:425](src/components/ImportPage.jsx#L425)）用 `bookmarks.length` 显示「X 条收藏」，`bookmarks` 来自 `loadLibrarySnapshot → listAllBookmarks`（**不排除 archived**）。
- 书架的 `bookmarkCount(articleId)`（[ImportPage.jsx:381](src/components/ImportPage.jsx#L381)）同样按 `articleId` 过滤 `bookmarks`，**含 archived**。
- 01 文档 §四 定稿「统计：computeReviewStats 的 total 排除 archived」，但这两个**实际可见**的计数不在任何决策范围内。归档后「条收藏」数字不会下降，是否合意应明确，而非静默。

**建议：** 在方案中显式决定：头部「条收藏」与书架「每篇收藏数」是否排除归档（推荐与「数据保留」语义一致，保留计数；但需写清口径，避免验收歧义）。

### B4　BookmarkManager 在本地（非云端）模式缺 `articleTitle`

`listAllBookmarks` 本地分支返回 `bookmarkStore.getAll()`（[readings.js:699-700](src/services/readings.js#L699-L700)），而本地 bookmark 对象由 `createBookmark` 生成，**不含 `articleTitle`**（[storage.js:298-328](src/store/storage.js#L298-L328)）；仅云端 `mapBookmarkRow` 通过 `readings!inner(title)` join 补上标题（[readings.js:120](src/services/readings.js#L120)）。

02 文档 §3.5 要求列表项展示「来源《articleTitle》」，但在「已登录但未配置云端（`canUseCloudLibrary=false`）/ Supabase 未配置」的本地模式下，BookmarkManager 的来源行会为空。

**建议：** BookmarkManager（或 `listAllBookmarks` 本地分支）需按 `articleId` 从 `articleStore` 解析标题，或标题缺失时优雅隐藏来源行。

### B5　新增索引 `idx_bookmarks_user_status` 与本方案实际查询不匹配

02 文档 §3.1 Step 2 为「归档列表查询索引（管理区按用户+状态过滤）」建 `(user_id, status) WHERE deleted_at IS NULL` 部分索引。但管理区实际走 `listAllBookmarks`（**全量拉取 + 前端分组**，无 status 过滤），唯一按 `status` 过滤的查询是 `get_due_bookmarks` RPC（SECURITY DEFINER，过滤 `user_id + status + review_count/next_review_at`，已有 `idx_bookmarks_user_id` 服务 user_id 定位）。

**建议：** 该索引目前无实际命中场景。可保留（无害）但应修正注释用途，或暂缓创建。

## 四、低（完善性 / 一致性）

### B6　`setBookmarkStatus` 云端 `.select(BOOKMARK_COLUMNS).single()` 存在多余失败面

两个调用方均不消费返回值（ReviewPanel `handleArchive` 忽略；BookmarkManager 成功后重拉列表）。`.single()` 在并发删除/未命中时抛 PGRST116，且 `.select(BOOKMARK_COLUMNS)` 还附带一次 `readings!inner(title)` join。建议去掉 `.select().single()`（或改用不带 `.single()` 的 select / 不 select），降低失败面与往返开销。

### B7　`handleArchive` 规范未显式覆盖 `saving` 锁与访问错误处理

02 文档 §3.5 仅写「仿 `handleFeedback` 的动画流程（exiting → 前进 → entering）」。但 `handleFeedback` 还做了 `setSaving(true)` 上锁（防止飞行中再点反馈/归档）与 `isLibraryAccessError → refreshAuthState` 的降级处理（[ReviewPanel.jsx:62-84](src/components/ReviewPanel.jsx#L62-L84)）。这两点对 `handleArchive` 同样必需，建议在规范中显式列出，避免实现时遗漏导致双写或会话失效后无刷新。

### B8　01 文档 §2.1 的溯源文件已过时（B1 的根因）

01 文档称 bookmarks「定义于 `20260509170000_create_core_user_tables.sql`」，但该文件定义的是 `article_id` 与对 `articles` 的引用；当前 schema 已由 `20260711000000_unify_readings_table.sql` + `20260712000000_cleanup_old_tables_and_rename_columns.sql` 改为 `reading_id` 与 `readings`，且 `translation_provider` 也不在该创建脚本中（后追加）。文档的**列清单本身是对的**，但溯源指向错误文件，正是这一溯源偏差连带造成了 B1。建议统一校正「现状调查」中所有对迁移脚本的引用。

### B9　两处措辞 / 一致性小问题

- 01 文档 §2.3 点 3（第 54 行）「必须显式带上… `status` 会随 spread 保留」两句方向相反，易误读。准确含义是：JS 层 spread 会保留对象上的 `status`，但 DB 层 upsert 仍必须显式写入该字段，二者不矛盾但需改写表述。
- 02 文档 §3.4 只给 `createBookmark` 加 `status: 'active'`、不加 `archivedAt`；而云端 `mapBookmarkRow` 恒输出 `archivedAt: null`（显式）。功能等价（写库时 `?? null` 兜底），但对象形状不对称，建议 `createBookmark` 也补 `archivedAt: null` 以保持领域模型一致。

## 五、已确认正确的部分（无需改动）

- **数据模型决策（D1/D2）**：`status` 枚举 + `archived_at` 与 `deleted_at` 正交，`familiarity`/`review_count`/`next_review_at` 归档时不动——均与代码与迁移一致。
- **覆盖式 upsert 风险识别**：`saveBookmark` 确为覆盖式 upsert（`onConflict:'id'`），反馈（ReviewPanel）与翻译（useBookmarkAI）两条写入路径确基于 `{...bookmark}` 展开，新增字段需在 upsert 显式带出——识别准确。
- **正文高亮保留**：`listBookmarksByArticle` 仅过滤 `deleted_at IS NULL`，归档收藏的高亮与侧栏展示会自然保留——判断正确。
- **队列本地拦截**：`listDueBookmarks` 本地分支加 `if (bm.status === 'archived') continue` 位置正确。
- **管理区数据源**：`listAllBookmarks` 不过滤 status，恰好满足「管理区需展示全部」——判断正确。
- **导出导入 round-trip（§3.6）**：`mapBookmarkRow` 映射 `status/archivedAt` + `saveBookmark` upsert 显式写 `status/archived_at`，云/本地两端字段命名一致，导出导入可正确恢复归档状态——分析成立。
- **RLS 满足性**：`bookmarks_update_own` 策略（`using … deleted_at is null` / `with check auth.uid()=user_id`）与 `setBookmarkStatus` 的 `.eq('user_id',…).is('deleted_at',null)` 更新匹配，无需新增策略。
