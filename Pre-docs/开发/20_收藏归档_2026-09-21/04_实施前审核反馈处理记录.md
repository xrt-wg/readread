### B1 残留缺陷（阻断，需二次修订）

**问题**：`02` §3.1 迁移 SQL 中，两个 COUNT 子查询的 `review_count` / `next_review_at` **未加 `b.` 限定**：

```sql
SELECT COUNT(*) INTO v_new_count
FROM public.bookmarks b
WHERE b.user_id = p_user_id
  AND (review_count IS NULL OR review_count = 0)   -- ❌ 未限定，review_count 是输出变量
  AND b.status = 'active'
  AND b.deleted_at IS NULL;

SELECT COUNT(*) INTO v_due_count
FROM public.bookmarks b
WHERE b.user_id = p_user_id
  AND review_count > 0                              -- ❌ 未限定
  AND next_review_at <= NOW()                       -- ❌ 未限定
  AND b.status = 'active'
  AND b.deleted_at IS NULL;
```

**根因**：`RETURNS TABLE` 中 `review_count`、`next_review_at` 是输出变量。PL/pgSQL 默认 `plpgsql.variable_conflict = use_variable`，未限定的同名标识符会被解析为**变量（初始为 NULL）而非列**。这正是 `20260717000000_fix_get_due_bookmarks_column_ambiguity.sql` 当初修复的问题（其注释明言「RETURNS TABLE 列名即输出变量，未限定列名如 `user_id` 与之同名则歧义」），生产版 `20260717000001` 的 COUNT 用 `b.review_count`/`b.next_review_at` 已全限定。修订稿在 COUNT 里把 `user_id`/`status`/`deleted_at` 限定了，却漏了这两个调度字段。

**后果**：`v_new_count` 条件退化为恒真（`NULL IS NULL` 为真），`v_due_count` 恒 0（`NULL > 0` 与 `NULL <= NOW()` 均为 NULL），三段 LIMIT 算术失真——到期卡被饿死、回顾队列静默返回错误子集（不报错，比 B1 原始的显式列序错误更难察觉）。

**修复**：两个 COUNT 子查询中 `review_count` → `b.review_count`、`next_review_at` → `b.next_review_at`（与 `b.deleted_at` 一致全限定）。同时 `02` §六「RPC 列序（已规避）」的表述应改为「已规避显式列序问题，另需复核 COUNT 列限定」。
