# 收藏归档功能 — 讨论和决策记录

> 日期：2026-09-21
> 关联：[02_实施方案](02_实施方案.md)、[03_实施前审核反馈](03_实施前审核反馈.md)、[04_实施前审核反馈处理记录](04_实施前审核反馈处理记录.md)、[05_实施后审核请求](05_实施后审核请求.md)

## 一、背景与需求

回顾区是 Leitner 间隔重复复习系统：阅读中划选收藏 → 按熟悉度排期 → 到期回到回顾区 → 三档反馈（生疏/模糊/熟练）更新排期。

当前收藏（bookmark）数据模型**缺少生命周期状态**，只存在两个隐式生命态：

| 生命态 | 字段 | 含义 |
|---|---|---|
| 活跃（默认） | — | 参与复习队列 |
| 软删除 | `deleted_at` | 数据移除、正文高亮消失、不可恢复 |

由于熟悉度封顶 5、间隔封顶 30 天，**任何收藏都无法「毕业」**——已彻底掌握的收藏要么每 30 天回来一次，要么只能删除。

**需求**：增加「归档」能力，给「已掌握 / 不再复习」的收藏一个出口，区别于「熟练」（拉长间隔但仍会回来）与「删除」（连数据一起没）。

## 二、现状调查结论

### 2.1 收藏数据模型（bookmarks 表）

定义链路（溯源校正后，审核 B8）：

- **原始定义**：`20260509170000_create_core_user_tables.sql`（当时为 `article_id` 指向 `articles` 表）。
- **演进**：`20260711000000_unify_readings_table.sql` + `20260712000000_cleanup_old_tables_and_rename_columns.sql`（`article_id` → `reading_id`，指向 `readings` 表）。
- **追加**：`translation_provider` 由 `20260617000003_add_translation_provider_column.sql` 后追加。

当前生效列清单（`src/services/readings.js` 的 `BOOKMARK_COLUMNS`）：

```
id, user_id, reading_id, type, text, translation, translation_provider,
context_sentence, context_translation, translation_status, paragraph_index,
char_offset, review_count, next_review_at, familiarity, section_id,
section_heading, created_at, updated_at, deleted_at
```

- **无 `status` 字段、无任何归档字段**。现存的「状态式」字段各自正交，不构成生命周期状态机：
  - `type`：word/phrase/sentence/paragraph，内容类型
  - `translation_status`：pending/done/error，翻译状态
  - `deleted_at`：软删除（唯一的「归档近亲」，但语义是删除、不可恢复）
  - `review_count` / `next_review_at` / `familiarity`：回顾调度状态
- 对比：`readings` 表有真正的状态枚举 `reading_status`（unread/reading/in_progress/completed），收藏无对等物。

### 2.2 回顾机制

- **调度**（`src/utils/reviewUtils.js`）：简易 Leitner，`familiarity` 1–5，间隔 `{1:1,2:3,3:7,4:14,5:30}` 天；首次反馈 hard→1/ok→2/easy→3，后续 delta hard-1/ok+1/easy+2，钳制 [1,5]。
- **队列来源**（两条路径，归档要拦截的正是这两处）：
  1. 云端 `get_due_bookmarks` RPC：当前生效版本为 `20260717000001_fix_get_due_bookmarks_result_columns.sql` 的**显式列清单**版本。历史演进：`20260714000000`（`b.*` 版）→ `20260717000000`（列歧义修复，列名加 `b.` 限定）→ `20260717000001`（显式列序修复——`translation_provider` 是后来追加到 `bookmarks` 物理列末尾的，`b.*` 输出列序与 RETURNS TABLE 约定不符）。三段 UNION ALL：新卡（review_count=0）> 到期卡（next_review_at<=now）> 未来卡补位，每段只带 `deleted_at IS NULL`。
  2. 本地 `listDueBookmarks`（`readings.js`）：用 `isDue()` 分流。
- **反馈写入**：`ReviewPanel` 反馈后 `computeNextReview` → `saveBookmark({...bookmark, ...updated})` **覆盖式 upsert**（`onConflict: 'id'`）。
- **翻译写入**：`useBookmarkAI.translateBookmark` 用 `{ ...bookmark, translation, ... }` 展开后 `saveBookmark`。

### 2.3 关键结论（技术判断依据）

1. **数据模型零归档支撑**，必须新增字段，否则只能退化为 localStorage-only、云端不可靠的半成品。
2. **归档对回顾队列是单点拦截**：队列过滤（`get_due_bookmarks` + `listDueBookmarks`）+ 统计口径。其中 `computeReviewStats` 当前为**无调用方的死代码**（全仓仅定义处出现），本次随收藏管理区一并激活（见 D5）。
3. **`saveBookmark` 是覆盖式 upsert**：DB 层 upsert 必须显式写入新字段，否则任何反馈/翻译保存都会把归档状态重置（**必要条件**）；同时所有写入路径（反馈、翻译）都基于 `{...bookmark}` 展开，JS 层会保留对象上的 `status`（**安全前提**）。两者相互独立、缺一不可。
4. **`get_due_bookmarks` 当前生效版本已是显式列清单**（`b.xxx` 逐个列出，原因见 §2.2）：给 bookmarks 加列后，不能回退为 `b.*` 写法；正确做法是在三处显式列清单中插入新列、RETURNS TABLE 补齐对应列、五个 WHERE（两个 COUNT + 三个子查询）补 `status='active'`。

## 三、决策记录

### D1 归档语义 → 「毕业/永久移出」

- 备选：临时暂停/隐藏、可反悔的清理。
- **决策：毕业/永久移出**。归档后不再进入复习队列，数据与正文高亮保留；可手动恢复，恢复后按原排期回到队列；与「删除」「熟练」三者正交。

### D2 数据模型 → `status` 状态字段（可扩展）+ `archived_at`

- 由单一 `archived_at` 演进为**通用状态枚举**，便于未来扩展。
- **决策**：`status text NOT NULL DEFAULT 'active' CHECK (status IN ('active','archived'))`，并加辅助列 `archived_at timestamptz` 记录归档时刻。
- 理由：枚举可扩展（未来加 `mastered`/`snoozed` 只需扩 CHECK 约束 + 前端枚举映射）；与 `deleted_at` 正交（`status` 管生命周期/参与度，`deleted_at` 管可见范围）。

### D3 承载位置 → 专门的「收藏」管理区（新 tab）

- **决策**：新增 top-level tab「收藏」+ `BookmarkManager` 组件，承载全部收藏查看、归档/恢复/删除及未来扩展。
- 职责切分：回顾 tab = 闪卡复习；收藏 tab = 收藏管理。二者不再互相耦合。

### D4 归档动作入口 → 管理区 + 回顾卡片快捷归档

- 备选：仅管理区。
- **决策：管理区 + 回顾卡片快捷归档**。复习中可顺手归档（发现已掌握）；管理区做完整管理（含恢复/删除）。

## 四、最终方案要点

| 维度 | 决策 |
|---|---|
| 语义 | 归档 = 毕业/永久移出，可恢复，恢复后按原排期回队列 |
| 数据层 | `status`（active/archived）+ `archived_at`，1 个迁移脚本，无新 RPC（update 走现有 RLS） |
| 队列 | `get_due_bookmarks`（显式列清单 + `status='active'`）+ 本地 `listDueBookmarks` 均排除 archived |
| 统计 | 管理区头部复习统计（`computeReviewStats` 激活，**active 口径**）；首页「条收藏」与书架「每篇收藏数」**保留含归档**（收藏总量口径） |
| UI | 新 tab「收藏」`BookmarkManager` + 回顾卡片快捷归档 |
| 调度 | 归档不动 review_count/familiarity/next_review_at |

## 五、风险与注意点

1. **RPC 列清单**：`get_due_bookmarks` 必须沿用 `20260717000001` 的显式列清单写法（`b.*` 因 `translation_provider` 物理列序问题不可用），新增列插入位置为 `b.deleted_at` 之后、`r.title` 之前；两个 COUNT 子查询的调度字段（`review_count`/`next_review_at`）同样必须全限定 `b.`，防 RETURNS TABLE 输出变量名歧义（`20260717000000` 曾修复此类问题）。
2. **覆盖式 upsert**：`saveBookmark` 必须显式带 `status`/`archived_at`，否则反馈/翻译会重置归档。
3. **正文高亮保留**：归档不删除数据，`listBookmarksByArticle` 不过滤 status，故归档收藏的正文高亮与单篇侧栏展示保持不变（符合设计）。
4. **统计口径并存**：收藏总量（含归档）与复习统计（active 口径）是两个不同语义的口径，分别在首页头部/书架与管理区头部呈现，标签语义不同，需在文案上避免混淆。

## 六、实施前审核及处理决策（2026-09-21）

审核者对照当前代码与全部迁移脚本独立复核，提出 9 条反馈（详见 [03_实施前审核反馈](03_实施前审核反馈.md)）。经逐条验证，**全部属实/合理，无异议**，处理决策如下：

| 编号 | 审核反馈要点 | 处理决策 |
|---|---|---|
| B1（阻断） | 迁移重写 RPC 回退到已被修复的 `b.*` 写法，会导致回顾队列运行时报错 | 迁移 SQL 改用显式列清单（沿用 `20260717000001` 写法），`b.status, b.archived_at` 插在 `b.deleted_at` 之后、`r.title` 之前；RETURNS TABLE 同步补列 |
| B2 | `computeReviewStats` 是无调用方的死代码，却被当作现状拦截点并列为验收项 #7 | 采纳方案 A：接入 BookmarkManager 头部（待复习/已掌握/总数，active 口径），激活为真实功能，验收 #7 变为可验证 |
| B3 | 首页「条收藏」与书架「每篇收藏数」两处可见计数的归档口径未定义 | 两处**保留含归档**（收藏总量口径：归档是数据保留而非删除）；与管理区 active 口径并存，文档写明 |
| B4 | 本地（非云端）模式 `listAllBookmarks` 缺 `articleTitle` | 本地分支按 `articleId` 从 `articleStore` 解析补 title；BookmarkManager 渲染缺失时优雅隐藏来源行（防御） |
| B5 | 新增索引 `(user_id, status)` 无实际命中场景 | 暂缓创建，保持迁移最小 |
| B6 | `setBookmarkStatus` 的 `.select().single()` 是多余失败面 | 去掉 select，返回 void，与 `deleteBookmark` 风格一致 |
| B7 | `handleArchive` 规范未显式覆盖 saving 锁与访问错误降级 | 规范中显式列出：`saving` 锁防双写、`isLibraryAccessError → refreshAuthState` 降级、成功后防本轮重复 |
| B8 | 01 文档溯源指向过时文件（B1 的根因） | 校正溯源为演进链路（见 §2.1） |
| B9 | 措辞方向相反易误读；`createBookmark` 对象形状不对称 | 改写 §2.3 点 3；`createBookmark` 补 `archivedAt: null` |

审核确认正确的部分（数据模型 D1/D2、覆盖式 upsert 风险、正文高亮保留、队列本地拦截位置、管理区数据源不过滤 status、导出导入 round-trip、RLS 满足性）无需改动。
