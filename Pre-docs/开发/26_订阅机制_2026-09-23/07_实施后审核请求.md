## 三、重点核验问题清单

### 3.1 🔴 P1 收藏双计修复链路（最高优先级）

06 P1 的修复是「触发器 `not exists` + 前端 `mapBookmarkRow` 不 round-trip」双重封死。请逐环核验这条链路是否每一环都成立：

1. **触发器层**：`guard_reading_user_write` 中两段 consume 分支是否都叠加了 `and not exists (select 1 from public.bookmarks/readings where id = new.id)`？该 `not exists` 在 `saveBookmark` 的 upsert 语义下（BEFORE INSERT 即使最终落 UPDATE 也触发）能否正确区分「真新增」与「翻译回写/重试」？
2. **前端不变式**：`BOOKMARK_COLUMNS` 与 `mapBookmarkRow` 是否**仍不**映射 `quota_consumed`？这是「不 round-trip」的前提——若被顺手映射，回写 `{ ...bookmark, translation }` 会携带 `quotaConsumed=true` 泄漏。
3. **首次消费链**：`createBookmark`（`quotaConsumed: true`）→ `saveBookmark` 首次 INSERT（`quota_consumed: true`）→ 触发器消费 → 返回 `mapBookmarkRow`（不带该字段）→ `translateBookmark` 回写 `{ ...savedBookmark, ... }`（无该字段）→ `saveBookmark` 再 upsert（`?? false`）→ 触发器 `not exists` 挡下。请确认这条链无断点。
4. **迁移恢复**：`importLibraryData` 是否显式剥离 `quotaConsumed`，防 localStorage→云端迁移时历史收藏误触发每周计数？（方案 §10.7「备份恢复误触额度」）

### 3.4 超出方案的防御性补充（请复核其合理性）

实施中额外加入两处方案未明写的防御，请复核**是否正确、有无副作用**：

1. **`grant_contribution_pro` 首行 `if p_user_id is null then return;`** —— 防历史/管理员补录行 `submitter_user_id` 为空时，发布动作因 `pro_grants.user_id` 违反 NOT NULL 而整单回滚。请确认：正常路径（有提交人）不受影响；NULL 提交人「不发奖励、照常上架」是期望行为。
2. **`importLibraryData` 恢复路径强制剥离 `quotaConsumed: false`** —— 与 §3.1 第 4 点同源。请确认：不会误伤「本应计额度」的场景（结论应为不误伤，恢复本就该不计）。
