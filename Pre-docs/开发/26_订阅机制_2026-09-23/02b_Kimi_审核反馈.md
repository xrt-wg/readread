## 四、发现的问题

### P1 — 阻塞项（实施方案动笔前必须有答案）

#### 4.1 🔴 未登录用户的配额语义完全缺失，成本闸门有结构性漏洞

**问题**：机制文档通篇以"用户"为主体，但当前架构下未登录用户可以完整使用产品（本地数据源，见事实 #2），包括**收藏 + AI 精译**——`useBookmarkAI` 不检查登录态，翻译请求照常发出，LLM 成本照花。而承载成本的 `translate` 函数**无鉴权**（事实 #5）。

这意味着：收藏额度若只作用于登录用户，则"成本闸门"对未登录用户完全失效，且"不登录 = 无限额度"会被用户发现并成为公开绕过路径。同时，未登录用户的导入也无从计数（本地数据，服务端不可见）。

**必须决策**（三选一或组合）：
- A. 收藏/导入变为登录后功能（配额机制间接强制注册——这本身是产品决策，需明确）；
- B. 未登录也给本地额度（前端计数，可清除绕过，只挡善意用户），并在 `translate` 函数加匿名限流（IP 级）；
- C. 明确接受"验证期未登录不计费不限制"，把配额机制整体定位为仅登录用户，风险记录在案。

无论选哪条，`translate` 函数是否加 JWT 鉴权（登录用户携带 Supabase token）都是实施方案必须回答的架构问题——**不加鉴权，则配额只在 UI 层，懂技术的人可直接调函数绕过**。

#### 4.2 🔴 收藏计数时点与成本发生时点错位，"每条计 1"缺乏可执行定义

**问题**：文档说"每条收藏触发一次 LLM 精译，每条计 1"，但代码现实是（事实 #3）：
1. 收藏先以 `pending` 落库，精译是**之后的异步过程**；
2. 三级降级链意味着一条收藏可能触发 **1~3 次**付费 API 调用（主力失败→备用→直译），"一次精译"不是一次调用；
3. 翻译可能彻底失败（`translationStatus: 'error'`），收藏已存在但没有精译结果。

**必须决策**：
- 扣额时点：收藏创建时扣（推荐，闸门在动作入口），还是精译成功时扣（成本准确但闸门后置）？
- 精译失败的收藏是否返还额度？（若创建时扣且失败不还，用户会为失败买单；若返还，需要补偿逻辑。）
- 重试精译（`translationStatus: 'error'` 后用户重试，ReaderPage L408 存在该路径）是否重复扣额？（成本确实重复发生。）
- 成本估算口径：按"1 条收藏 ≈ 最坏 3 次调用"还是"≈ 1.x 次"做成本模型，直接影响每周 N 的定价。

#### 4.3 🔴 Pro 到期回 Free 的存量处置规则未定义

**问题**：文档说"到期自动回 Free，无惩罚"，但三个杠杆的到期处置均未定义：

| 杠杆 | 到期时的矛盾 | 需要答案 |
|------|-------------|---------|
| 导入（终身累计 N） | Pro 期间无限导入；回 Free 后终身累计数怎么算？ | Pro 期间的导入**是否计入**终身累计 N？若计入，到期即永久撞墙（等于惩罚，与"无惩罚"矛盾）；若不计入，计数器需要按身份分段记账 |
| 同时在读（5 本） | Pro 期间可能 >5 本在读；回 Free 后怎么办？ | 强制放回？按什么规则选（最久未读？用户自选？只读冻结？）。`init_reading_status` 已有"超过上限转回 in_progress"先例，但选择规则需定义 |
| 收藏（每周 N） | 无存量问题，下周一起自然受限 | ✅ 无需决策 |

建议的默认原则（供决策参考）：**存量不动、增量受限**——已导入的书不删、Pro 期间导入不计入 Free 累计（或计入但给足缓冲）、在读超额的转回规则沿用现有 `init_reading_status` 逻辑但改为用户下次打开时引导自选。

#### 4.4 🔴 "导入"的计数口径未定义——4+1 个入口逐一界定

**问题**：导入是转化引擎，计数口径直接决定转化漏斗的形状。当前导入入口（事实 #6）：

| 入口 | 是否计入终身 N？ | 备注 |
|------|:---:|------|
| URL 导入 | 待决策 | 解析失败/超时/内容为空时计不计？ |
| 文件导入（EPUB/MD/HTML） | 待决策 | EPUB 解析失败计不计？ |
| 粘贴导入 | 待决策 | — |
| 推荐区"加入书架" | 待决策 | **关键**：若计入，则免费用户靠推荐区内容也烧额度，"发现 → 导入"循环被额度掐断，与"给足探索"的调法提示冲突；若不计入，则推荐区是免费燃料补充通道（这可能是故意的） |
| `importLibraryData` 批量恢复 | 待决策 | 用户导出再导入自己的备份，若计入则恢复数据会撞墙 |
| 重复导入同一内容 | 待决策 | 02 §4 说"重导旧内容给不了新学习材料"，那重导计不计数？若计数，误操作浪费额度；若不计数，需定义去重判定（URL 相同？内容指纹？） |
| 导入后删除再导入 | 待决策 | 终身累计不重置意味着删除不返还——需明文 |

#### 4.5 🔴 Pro 身份的存储与"自动回 Free"的判定机制未提

**问题**：文档只说"按天计时、到期自动回 Free"，实现层面必须回答：
- 存哪：profiles 加 `pro_expires_at` 单列，还是独立 `subscriptions` 表（含来源：购买/奖励，便于审计与追溯）？奖励时长需要**逐笔台账**（哪次上架发的几天）才能支撑每月上限 M 的核算与防刷追查，单列存不下。
- 怎么"自动"：惰性判定（每次读身份时比对 `expires_at`，过期即视为 Free——无定时任务依赖，推荐）还是 pg_cron 定时翻转？注意项目当前 Supabase 无本地 CLI，migration 走 Dashboard SQL Editor 手动执行，pg_cron 可用性需确认。
- 并发与幂等：支付回调重试、管理员重复发奖、购买与奖励同时到账——时长累加必须是原子操作（单行 `expires_at = greatest(expires_at, now()) + N days` 这类语义需写死）。

### P2 — 需要决策（不阻塞方案动笔，但阻塞定稿）

#### 4.6 ⚠️ 配额检查的执行位置与原子性

文档未提配额的技术执行方式。实现上必须明确：**扣减必须走 SECURITY DEFINER RPC 原子完成"检查 + 扣减"**（防并发绕过），前端只做预检与提示。项目已有成熟先例（事实 #9 `get_recommendation_submission_quota`）。同时注意收藏有**两条写路径**——云端 RPC 与本地 store（事实 #2/#4），闸门设计必须覆盖或显式排除本地路径（与 4.1 联动）。另外复习反馈（ReviewPanel L76）与归档恢复也走 `saveBookmark` upsert，**闸门若挂在 `saveBookmark` 上会误伤复习与归档写路径**——必须只挂在"创建"事件上。

#### 4.7 ⚠️ 每周重置的周边界与时区实现

"北京时间周一 0 点重置"——PostgreSQL `date_trunc('week', ...)` 本身从周一开始，与需求吻合，但需在 `Asia/Shanghai` 时区下先转换再截断（项目已有自然日先例：`date_trunc('day', now() at time zone 'Asia/Shanghai') at time zone 'Asia/Shanghai'`，20260921000002 L40）。周版本写法需在实施时验证边界（周日 23:59 与周一 00:00 两侧的归属），并写进验收用例。

#### 4.8 ⚠️ 收藏额度的计数范围：删除/归档是否计入

从"成本闸门"定位推断应**计入**（LLM 成本已发生，删除不回收成本），且每周重置天然兜底。但需明文写出：软删（`deleted_at`）、归档（`status='archived'`）的收藏仍计入本周已用额度。否则用户会"删了再收"期待额度回收。归档恢复路径（`setBookmarkStatus`）不触发精译（翻译已存），不应重复扣额——需确认恢复路径不经过创建闸门。

#### 4.9 ⚠️ 上架奖励的重复发放与追回

`admin_publish_recommendation` 是天然发奖钩子，但存在 removed → approved → active 的**重新上架路径**（20260917000000 L218、L235-236：removed 可回 approved，approved 可再 publish）。`first_published_at` 已存在，可实现"仅首次上架发奖"，但 02 §6 只说"上架才计"，未说重复上架。需决策：仅首次上架发奖（推荐，字段已备好），还是每次上架都发。另外：上架后若因违规被下架，已发时长是否追回？（建议不追回、记审计，追回涉及的负时长调整复杂度不值得。）

#### 4.10 ⚠️ 每月赚取上限 M 的窗口与存储

"每月赚取上限 M 天"：窗口是自然月（北京时间）还是滚动 30 天？需要逐笔奖励台账（见 4.5）按月聚合。沿用项目惯例建议自然月 + 北京时间。另需决策：达到上限后用户继续上架的时长是**作废**还是**顺延到下月**？（作废简单但有负激励；顺延需要队列，复杂。）

#### 4.11 ⚠️ 时长累加的边界

02 §6 说"赚取时长与购买时长累加到到期日之后"。需决策：累计上限（如最多囤 365 天？无上限？）；Free 用户赚取的时长从到账日立即生效还是？（推断立即生效，但文档未写。）

#### 4.12 ⚠️ "同时在读 5 本改可配置"的范围与结构

01 说"顺手时改、非必须"。若纳入本次：改动面 = 前端常量 + RPC 入参默认值（事实 #7），配置表需支持**按身份分档**（Free 5 / Pro 待定）而非单值——与现有 `recommendation_submission_config` 单值模式不同，结构要提前设计。若不纳入本次，实施方案需显式声明"本次仍硬编码 5，Pro 档暂不开放此差异"。**建议纳入**，因为 Pro 权益表里"同时在读：更多"是已承诺的差异化，不做则 Pro 权益少一条。

#### 4.13 ⚠️ 撞墙后的既有内容可用性需明文

文档隐含"撞导入墙后已有书籍的阅读/收藏（周额度内）/复习不受影响"，但未明写。实施方案的 UX 设计（撞墙提示文案、入口状态）依赖这条边界，建议补进 02 §7。

#### 4.14 ⚠️ 存量用户的额度追溯

上线时既有用户已有导入历史。终身累计从 0 起算（既往不咎）还是按 `readings.created_at` 回溯统计？若回溯，部分老用户可能上线即撞墙。建议从 0 起算并明文写出。

### P3 — 建议（不阻塞，提升质量）

#### 4.15 💡 Pro 收藏"无限"缺公平使用兜底

02 §3 权益表 Pro 收藏"无限"。Pro 用户的 LLM 成本无任何闸门——账号共享、脚本滥用会直接烧钱。建议实施方案补一条"Pro 公平使用上限"（如每周 500 条，仅防滥用、正常用户永远碰不到），哪怕当前不启用，字段先留。

#### 4.16 💡 生词本独立性是本次最便宜的处理时机

02 §10 留意项（删书不毁学习）与现状相反（事实 #10：删书硬删收藏）。本次实施要动 bookmarks 的计数链路，是顺手评估解耦成本的最便宜时机。若决定不动，实施方案需显式声明"本次保持级联删除，留意项留待未来"，避免实施者顺手改了引入回归。

#### 4.17 💡 划词直译的成本暴露

"划词弹窗永远在线"是铁律，但直译也走同一无鉴权 `translate` 函数（DeepL/Youdao，成本虽低但非零）。与 4.1 一并考虑函数层鉴权/限流时，注意**直译路径必须永远放行登录用户**，匿名路径至少加 IP 限流。

#### 4.18 💡 验证期的最小 Pro 发放路径

支付渠道是后置项，但机制要端到端跑通，必须有一条**当前可用的 Pro 发放路径**：管理员后台手动授予 Pro（admin RPC + audit_log，沿用现有惯例）。建议实施方案把"人工授予"列为必需项，否则整个机制在支付接入前无法验证。

#### 4.19 💡 订阅相关指标接入既有统计

23_后台数据统计已建 `admin_growth_stats`。订阅上线后需要撞墙率、升级转化、额度使用率等指标。建议实施方案列出"统计接入点清单"，哪怕本次只做埋点不做报表。

## 六、审核结论

### 总体评价

| 维度 | 评价 |
|------|------|
| 机制设计质量 | ⭐⭐⭐⭐⭐ 5/5 —— 两个杠杆的分工（燃料做转化、速率控成本）逻辑自洽，"卖更多不卖功能"的边界清晰且与代码现状兼容 |
| 与代码现状的兼容性 | ⭐⭐⭐⭐ 4/5 —— 配置化、上架钩子、审计、频率限速均有成熟先例可直接复用；扣分在未登录双数据源与 translate 函数无鉴权这一结构性缺口 |
| 实现层面完备性 | ⭐⭐½ 2.5/5 —— 机制语义完整，但 5 个 P1 实现问题（未登录口径、计数时点、到期处置、导入口径、身份存储）目前完全没有答案 |

### 通过状态：⏸️ 有条件通过（机制方向成立，实施方案动笔前需先闭环 5 个 P1 决策）

- 机制本身逻辑自洽、与代码架构的接口点（配置表、RPC、审核流、审计）全部存在且成熟，**不需要推翻任何决策**；
- 但 5 个 P1 问题不是实现细节，而是**机制语义尚未覆盖的空白**（未登录用户、计数时点、到期处置、导入口径、身份存储），它们的不同答案会产生完全不同的实施方案架构；
- 建议流程：产品侧先对 A1-A5 给出决策（可作为 01 的补充决策记录），再产《实施方案》；B 组事项可在方案撰写过程中并行敲定。

### 关键风险提示

最值得警惕的一条：**如果 A1 选择"配额只管登录用户"而 `translate` 函数维持无鉴权，那么收藏额度作为"成本闸门"在技术上是无效的**——成本发生在函数层，闸门在 UI 层，中间没有墙。这是整个机制从"设计成立"到"实现成立"之间唯一可能塌掉的环节。
