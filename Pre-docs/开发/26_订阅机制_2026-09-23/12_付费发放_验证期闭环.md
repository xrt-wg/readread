# 付费发放 — 验证期闭环（扫码支付 + 人工确认）

> 日期：2026-09-24
> 性质：验证期临时发放路径说明（支付接入前的过渡方案，非最终支付）
> 关联：[02_订阅机制说明](02_订阅机制说明.md) · [04_实施方案](04_实施方案.md) §1 · [11_设计备忘_Pro期间额度口径](11_设计备忘_Pro期间额度口径.md)

---

## 1. 定位

04 §1.1「不接入任何支付」在本轮收口被**部分放宽**：为让「付费 → Pro」链路在验证期端到端跑通，新增一条**不依赖支付回调**的临时发放路径：

> 贴微信收款码 → 用户扫码支付 → 点击「我已支付」→ 管理员人工核对到账 → 后台「确认发放」。

选它的理由：验证期无需大而全的支付/发放机制；人工确认已足以闭环，且后端复用既有 `subscriptions` / `pro_grants` 的累加语义，几乎零新造。代价是「到账核验靠人、无回调」，这是本路径**有意接受**的边界（见 §5）。

## 2. 全流程

**用户侧（免费身份）**
1. 账号面板「开通 Pro」区块展示收款码 + 价格（验证期固定 ¥9.9 / 30 天）。
2. 扫码支付后点击「我已支付，申请开通」→ 落一条 `status='pending'` 申请。
3. 面板进入「已提交，等待管理员核对到账后开通」；重复点击不重复建单。

**管理员侧**
1. 后台「付费发放」页列出全部申请（含用户邮箱，便于核对到账）。
2. 核对到账后点「确认发放」→ 累加 30 天 Pro、申请置 `granted`、记审计。
3. 未到账可点「拒绝」→ 申请置 `rejected`；用户可重新提交。

## 3. 数据与接口

迁移：[`20260924000000_payment_requests.sql`](../../../supabase/migrations/20260924000000_payment_requests.sql)（申请台账 + 发放/拒绝）· [`20260924000001_payment_qr.sql`](../../../supabase/migrations/20260924000001_payment_qr.sql)（收款码配置）

### 3.1 表 `payment_requests`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid PK | `gen_random_uuid()` |
| user_id | uuid → auth.users | 申请人，级联删除 |
| amount_cents | integer | 验证期固定 990（¥9.9） |
| requested_days | integer | 验证期固定 30 |
| status | text | `pending` / `granted` / `rejected` |
| created_at / granted_at | timestamptz | |
| granted_by | uuid → auth.users | 发放管理员 |
| rejected_reason | text | 拒绝原因 |

索引：`(user_id, created_at desc)`；部分唯一索引 `(user_id) where status='pending'`（同一用户至多一笔待处理）。

### 3.2 RPC（7 个，全 security definer，RLS 全 `revoke all`）

| RPC | 方向 | 作用 |
|---|---|---|
| `submit_payment_request()` | 用户 | 幂等建单（已有 pending 则复用） |
| `get_my_payment_request()` | 用户 | 查最近一笔（待确认/已开通/已拒绝），无则 null |
| `admin_list_payment_requests()` | 管理员 | 全量队列（含邮箱） |
| `admin_confirm_payment(request_id, days=null)` | 管理员 | 锁行 → 累加 Pro → 置 granted → 记审计 |
| `admin_reject_payment(request_id, reason=null)` | 管理员 | 置 rejected → 记审计 |
| `get_payment_qr()` | 用户 | 读收款码 data URL（无则 null） |
| `admin_set_payment_qr(data_url)` | 管理员 | 设置/清除收款码（`data:image` 校验） |

### 3.3 关键实现点

- **发放走 `source='paid'`**：`admin_confirm_payment` 内联累加 `subscriptions.pro_expires_at`（`greatest(now(), coalesce(...,now())) + N天`）并写 `pro_grants` 一行 `source='paid'`、`external_ref=request_id`——正好启用 `pro_grants` 预留的「支付幂等键」字段，与人工授予（`admin`）/社区奖励（`contribution`）在台账上分得开。
- **幂等防重**：申请侧靠部分唯一索引 + `on conflict do nothing`；发放侧靠 `for update` 锁行 + `status='pending'` 判定（已处理则报「该申请已处理」），不会二次发放。
- **不消耗 Free 额度**：发放只改 `subscriptions`，不碰 `user_quotas`；Pro 期间额度口径与 [11_设计备忘_Pro期间额度口径](11_设计备忘_Pro期间额度口径.md) 一致。

### 3.4 收款码配置

收款码以 data URL 存于 `subscription_config.payment_qr_data_url`（不引入 Storage，验证期一张小图足够）。管理员在「付费发放」页上传/替换/清除（`admin_set_payment_qr`），账号面板经 `get_payment_qr` 读取展示。正式接支付时可迁移至 Supabase Storage 公有桶。

## 4. 与既有发放路径的分野

| 路径 | `pro_grants.source` | 触发 | 状态 |
|---|---|---|---|
| 社区贡献 | `contribution` | `admin_publish_recommendation` 首次上架 | 已实现（04 §4.3） |
| 人工授予 | `admin` | `admin_grant_pro` | 已实现（04 §4.4） |
| 付费确认 | `paid` | `admin_confirm_payment` | **本文件新增** |

## 5. 尚未接入（接支付前必办）

- **支付回调 / 到账自动核验**：当前靠管理员人工核对，`payment_requests` 无回调态。
- **`translate` 函数层 JWT 鉴权**（04 §5.5 遗留，成本闸门函数层缺口）。
- **计额度路径收敛进 security definer RPC**（04 §10.4：`quota_consumed` 可被直接 API 置 false 的两面风险）。
- **价格 / 天数入配置**：当前硬编码 ¥9.9 / 30 天（迁移列默认值 + 前端常量），未来移入 `subscription_config`。

## 6. 验收要点（迁移落库后手动冒烟）

1. 免费账号打开账号面板 → 见「开通 Pro」区块（¥9.9 / 30 天）。
2. 点「我已支付」→ 状态变「已提交待确认」；再点一次不重复建单（`get_my_payment_request` 仍返回同一笔 pending）。
3. 管理员「付费发放」页 → 见该申请（含邮箱）。
4. 「确认发放」→ 用户 `get_subscription_status` 变 `plan='pro'`、`proExpiresAt +30 天`；`pro_grants` 多一行 `source='paid'`、`external_ref=request_id`；`audit_logs` 多 `subscription.payment_granted`。
5. 「拒绝」另一笔 → `rejected`；该用户可重新提交。
6. 到期自动回 Free，额度从升级前继续（与 11 备忘一致）。
