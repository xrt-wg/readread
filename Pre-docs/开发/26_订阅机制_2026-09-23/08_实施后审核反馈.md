## 四、审核中新观察（低严重度，均不阻塞落库）

### N1（P3）— P3#2 注释未落库：06 声称「已补注释」，实际未落到迁移 SQL

- **事实**：06 §二 P3#2 声称「已补注释『`quota_consumed` 仅对新增写路径有意义，存量行额度语义由回填计数承载』」，落点为「04 §3.2」。但迁移 SQL 的 §3 加列处（L71-74）仅有 `alter table … add column quota_consumed boolean not null default false`，**无该注释**。
- **影响**：语义通过回填注释（L82-83 的 origin 口径）、前端注释（storage.js:330、readings.js:787）间接承载，**不构成功能缺陷**；但严格对照 07 §3.3#2「迁移 §3 加列处是否有该注释」，答案是「没有」。
- **建议**：落库前顺手在迁移 §3 加列处补一行注释，使「代码层修复」与 06 声明完全一致（一次性小改动）。

### N2（P3）— `get_subscription_status` 用标量 SELECT INTO 而非 04/07 声称的「LEFT JOIN」

- **事实**：04 §4.4 / 07 §3.2#6 写「LEFT JOIN 兜底」，实际实现为三条独立标量 `select … into`（L196、L199）。
- **影响**：**功能等价**——无 `subscriptions`/`user_quotas` 行的新用户，标量 select 得 NULL，`coalesce`/`case` 兜底到 free/0/默认 limit，与 LEFT JOIN 结果一致。属措辞与实现风格出入，非 bug。
- **建议**：无需改动；仅提示后续文档引用应以代码为准。

### N3（P3，附带，**非本次引入**）— 备份恢复在读内容会因 `saveReading` D7 守卫抛错

- **事实**：`loadLibrarySnapshot` 导出 `articles: [...shelf, ...activeReadings]`（[readings.js:939-941](src/services/readings.js#L939-L941)），即导出快照**包含** reading_status='reading' 的在读内容；而恢复路径 [readings.js:974](src/services/readings.js#L974) `importLibraryData → saveReading(article)`，`saveReading` 的 D7 守卫（[readings.js:365-367](src/services/readings.js#L365-L367)）对 `readingStatus === 'reading'` 直接抛「正在阅读中的内容不可编辑」。故**若导出时存在在读书籍，恢复会在此处抛错并中断**。
- **定性**：D7 守卫与快照含在读内容均为「阅读区」特性引入，**非订阅机制本次改动引入**，也不属于额度/订阅逻辑缺陷。但会阻碍 §11 用例 4「备份恢复」对有在读书籍用户的完整走通（额度剥离本身正确，恢复流程卡在 D7）。
- **建议**：作为**单独事项**处理（不在订阅机制范围内）——恢复路径对在读内容应「重建而非编辑」（绕过 D7 或恢复为 unread/reading 均可），建议另起一项跟踪。

### N4（说明，非问题）— 触发器 L249-251 账户转移守卫位于 `lock` 之前

- 04 §4.1 表述顺序为「lock → 级联检查 → …」，实际 L249-251 的「UPDATE 不得跨账户转移」守卫在 L252 `lock` 之前执行。该守卫仅读 NEW/OLD 记录、立即抛错（fail-fast），不涉及并发读，**顺序无正确性影响**。仅记录，不改。
