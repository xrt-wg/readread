## 三、文档一致性问题（五份间）

### 3.1 🔴 收藏额度扣减依赖客户端 flag 经 upsert 传播 —— 存在「双计/误伤」风险（P1）

**这是本轮最需要动笔前解决的正确性问题。**

方案的意图是「新建收藏计 1、重试/翻译回写/复习/归档恢复不重复计」（04 §2.3、§9、§10.7），其实现机制是：

```sql
if tg_table_name = 'bookmarks' and tg_op = 'INSERT' and coalesce(new.quota_consumed, false) then
  perform public.consume_bookmark_quota(v_user);
end if;
```

但代码现实（事实 #3/#4/#5）与方案的意图**存在结构性错位**：

1. `saveBookmark` 是 `INSERT ... ON CONFLICT (id) DO UPDATE`（upsert）。PostgreSQL 对 upsert **即使最终落入 UPDATE，也会先触发 BEFORE INSERT 触发器**（`tg_op='INSERT'`）。因此「翻译回写 = UPDATE、不触发 INSERT 计数」这句（04 §2.3/§5.3 的隐含假设）**在触发器层不成立**——回写同样会经过 `tg_op='INSERT'` 分支。

2. 回写是否重复扣额，**完全取决于 `quota_consumed` 是否泄漏到回写 payload**：
   - `translateBookmark` 用 `{ ...bookmark, ... }` 展开首次保存返回的映射对象（事实 #4）。若 `mapBookmarkRow` 把 `quota_consumed` 映射为 `quotaConsumed`（实现者的自然倾向，为了字段完整性），则回写 payload 携带 `quotaConsumed=true` → BEFORE INSERT 分支再次 consume → **一条收藏计 2 次**。
   - 若 `mapBookmarkRow` 不映射（当前确实没映射，事实 #5），则回写 `quotaConsumed ?? false` = false → 不双计。**但这依赖一条未写入方案的、反直觉的不变式**：「quota_consumed 只进不出、不得 round-trip」。

3. 另一条双计向量：客户端网络重试（首次 INSERT 超时后重发同一 id）→ upsert 落到 UPDATE → 若 flag 仍为 true → 再次 consume。

**方案只记录了「flag 可被恶意置 false 绕过（少计）」，没记录「flag 可被正常流程泄漏为 true（多计）」——后者是正确性 bug，前者是已接受的绕过风险，二者不是一回事。**

**建议修复（任选其一，推荐 a）**：

- **(a) 触发器加「真新增」判定（最小改动、防御纵深）**：
  ```sql
  if tg_table_name = 'bookmarks' and tg_op = 'INSERT'
     and coalesce(new.quota_consumed, false)
     and not exists (select 1 from public.bookmarks where id = new.id) then
    perform public.consume_bookmark_quota(v_user);
  end if;
  ```
  回写/重试时该 id 已存在 → `not exists` 为 false → 不消费；备份恢复（新 id 但 flag=false）→ 不消费；真新增（新 id + flag=true）→ 消费。`lock_reading_user` advisory lock 已保证同用户串行，无 TOCTOU 风险。readings 同理加 `not exists` 防御（虽然 `createReading` 是纯 INSERT，风险低）。

- **(b) 把新建收藏收敛为专用 security definer RPC**（`check + consume + insert` 原子，不再走通用 `saveBookmark` upsert）。改动更大，但一劳永逸。

无论选哪条，方案必须**显式声明**：`BOOKMARK_COLUMNS` / `mapBookmarkRow` 不得映射 `quota_consumed`；并加一条验收用例「翻译回写 / 复习反馈 / 归档恢复后，本周已用收藏数不增加」。

## 四、方案合理性与有效性核验（04 实施方案）

### P2 问题

#### 4.1 ⚠️ 首次上架判定在「同一事务内」不可得；撞月上限后作废/顺延未明

04 §4.3 要求「首次上架（`first_published_at` 由 NULL→非 NULL）时，与上架同事务发放」。但事实 #6：现有 RPC 是单条 `UPDATE ... first_published_at = coalesce(first_published_at, now()) ... returning`，`returning` 出的 `first_published_at` **恒非 NULL**，同事务内无法据此区分「首次 / 重新上架」。

实现必须二选一并写清：

- **(a) UPDATE 前先 `SELECT first_published_at` 判断 NULL**，再决定是否发放；或
- **(b) 完全依赖 `pro_grants.submission_id` 唯一索引幂等**（重新上架 insert 冲突 `do nothing`），「首次」判定交给索引。此时「首次上架撞月上限」场景（某用户首月已赚满 60 天，其第 3 篇内容**首次**上架）会**静默不发且永久丢失**——因为 `first_published_at` 已置位，下月不再视为首次。

方案需显式回答：**撞月上限的奖励是「作废」还是「顺延到下月」？** 03 A4 决策文字「每月 M 触发后内容照常上架、奖励不发」偏向「作废」，但未点明「首次上架也作废、不设补发队列」。建议按「作废、不顺延、记审计」写死并进 §9 边界表。**P2**。

#### 4.2 ⚠️ `consume_bookmark_quota` 伪码是注释级 stub，周滚动重置分支未写

04 §4.2 两个消耗函数中，`consume_import_quota` 基本可执行，但 `consume_bookmark_quota` 是 stub：

```sql
v_week := date_trunc('week', ...);          -- v_week 未声明
insert into user_quotas(user_id, bookmark_week_start) values(p_user, v_week) on conflict do nothing;
-- for update 锁行后判定周是否滚动；滚动则重置为 1，否则 count+1；达限 raise Q0002
```

缺：`v_week`/`v_limit` 声明；「周滚动」判定与两条 UPDATE 分支的具体 SQL；`for update` 与既有 `lock_reading_user` advisory lock 冗余（触发器已持锁，函数内 `for update` 非必需但无害）。**最关键的分支是「周滚动时 `bookmark_week_start` 必须同步更新为新周起点、计数置 1」**——若实现者漏改 `bookmark_week_start`，后续每笔都会误判「仍在旧周」。

建议补全为可执行 SQL（含 `update ... set bookmark_week_start=v_week, bookmark_week_count=1 where user_id=... and bookmark_week_start is distinct from v_week` 与 `... count=count+1` 两条分支），并把周边界写进验收（§11.9 已有，但需对应到这段 SQL）。**P2**。

#### 4.3 ⚠️ 触发器扩展的插入位置与既有 reading-limit 检查的顺序未定

04 §4.1 只说「在已 `lock_reading_user` 之后追加两段」，未指定与现有 `>=5` 检查、`user_first_reading_states` 抑制插入的相对位置。影响：

- 若 consume 放在 `>=5` 检查**之前**：一个「已满 5 本 + 撞导入墙」的用户先收到 `Q0001`（导入墙）而非「阅读区已满」，撞墙 UX 与预期不符（虽然「加入上架内容」默认 `reading_status='unread'` 不触发 reading-limit，重叠极少）。
- 若 consume 放在「抑制插入」之后：额度异常回滚时连抑制插入一起回滚（本就应回滚，无实际危害）。

建议明确顺序为「lock → 删级联检查 → reading-limit 检查 → **consume 两段** → 抑制插入 → return」，并在方案中落笔。**P2**（低概率，但顺序未定会让两个实施者写出不同语义）。

#### 4.4 ⚠️ 周边界 `now()` vs `clock_timestamp()` 自相矛盾

04 §10.6 要求「跨周一 0 点瞬间的插入，归属周判定用同一 `now()`/`clock_timestamp()` 求值，避免一次事务内两处 now 不一致」，但 §4.2 伪码用的是 `now()`（事务开始时间）。两者语义不同：`now()` 在整个事务内恒定，`clock_timestamp()` 每次调用取实际时间。advisory lock 下同用户串行，`now()` 其实更稳（不存在「两处 now 不一致」）；§10.6 的担忧不适用于本方案。建议统一为 `now()` 并删掉 §10.6 的 `clock_timestamp()` 字样，消除矛盾。**P2/P3**。

#### 4.5 ⚠️ 迁移后新注册用户无 `subscriptions` 行，`get_subscription_status` 需 NULL 兜底

回填（§3.4）只对「存量用户」insert `subscriptions`。迁移后新注册用户没有 `subscriptions` 行，也没有 `user_quotas` 行。`consume_*` 的 `if exists(subscriptions...)` 能容忍无行（按 Free 计），但 `get_subscription_status()`（§4.4）与前端 `useSubscription` 必须对「无 subscriptions 行 / 无 user_quotas 行」做 `coalesce`（plan='free'、额度 0）。方案未写。建议在 §4.4 明确 RPC 用 LEFT JOIN 兜底。**P2**。

### P3 问题

#### 4.6 quota_consumed 存量行语义矛盾

加列 `quota_consumed boolean not null default false` 后，存量已导入/已收藏行全部为 `false`；而 §3.4 回填又用 COUNT 把这些存量行**计入了** `import_lifetime_count`。于是「该行是否消耗过额度」这一语义上，存量行 `quota_consumed=false` 却已被计数。二者双轨运行（触发器只读 `new.quota_consumed`，不读存量行），**功能上无碍，但列名有误导**。建议改名或注释明确「`quota_consumed` 仅对新增写路径有意义，存量行语义由回填计数承载」。**P3**。

#### 4.7 Pro 在读权益与触发器硬限 5 的张力

A6 决定「同时在读可配化不纳入本次」，意味着 Pro 用户同样被触发器 `>=5` 硬限（事实 #2）。但 `get_subscription_status` 返回 `plan='pro'` 后，前端若据此展示「Pro 更多在读」权益，会与触发器实际行为矛盾。建议在方案 §5.4 补一句「Pro 权益本次不含在读差异化，前端不得展示『更多在读』」，并与 02 权益表的「Pro 更多（待定）」同步标注「本次不生效」。**P3**（与 §2.2 同一根因）。

#### 4.8 验收用例缺 `admin_grant_pro`（人工授 Pro）

§11 验收标准覆盖了导入/收藏/删书/备份/上架发奖/到期/未登录/核心闭环/周边界，但**没覆盖 `admin_grant_pro`**——而这是 §4.4 明确的「支付接入前唯一 Pro 发放路径、Phase 1 必需」。若验证期无法人工授 Pro，整个 Pro 身份/额度绕过/到期回退链路都测不了。建议补一条「管理员人工授予 N 天 Pro → 用户 plan 变 pro → 到期自动回 free」。**P3**。

#### 4.9 「划词翻译永远在线」铁律 vs 降本/匿名限流的张力

02 §5/§7 铁律「划词弹窗直译永远在线」，而 04 §7 附带发现建议「直译兜底切免费 myMemory」、§5.5 建议「匿名 IP 级限流」。两条建议都可能弱化铁律：myMemory 质量/可用性未知，匿名限流过严会挡善意匿名用户。建议明确「降本与限流以不破坏『直译永远在线』为前提」，直译兜底切换前先评估可用性。**P3**。

#### 4.10 isQuotaError 具体覆盖点未列全

04 §5.2 说「所有相关 catch 链在 isLibraryAccessError 之前先判 isQuotaError」，但未列举具体位置。实际收藏创建入口不止 ReaderPage 划词一处，还有**预读模式**（ReaderPage L315-336）、**ReviewPanel/BookmarkManager** 里的收藏写路径。建议方案列出需插 `isQuotaError` 的完整文件/函数清单，避免漏改导致撞墙误报「会话失效」触发 `refreshAuthState`。**P3**。

#### 4.11 发 Pro 时 `pro_source` / `updated_at` 维护未提

`subscriptions.pro_source` 设计为「最近一次来源，仅展示」，但 §4.3（社区发奖）与 §4.4（`admin_grant_pro`）的发放逻辑只写了 `GREATEST` 累加 `pro_expires_at`，未写同步更新 `pro_source` 与 `updated_at`。建议在发放路径中显式带上 `pro_source=source`、`updated_at=now()`，否则展示字段永远为空。**P3**。

#### 4.12 导入口径未说明 `manual` / `shared` 历史 origin

事实 #8：`origin` 约束含 `manual`/`shared`，`manual` 出现在历史迁移（`20260711000000` L106-134 把无 `source_import_id` 的旧 article 标为 `manual`）与测试数据，`shared` 无当前写路径。回填（§3.4）只计 `imported` + `featured/featured_legacy`，**未说明 `manual`/`shared` 为何不计**。当前结论（不计，且存量仅测试用户）可接受，但建议补一句「`manual`（历史迁移残留）/`shared`（已废弃）不计入导入额度」，并明确未来若出现新写路径需同步更新口径。**P3**。
