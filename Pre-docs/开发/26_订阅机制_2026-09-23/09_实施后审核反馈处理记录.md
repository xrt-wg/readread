## 二、逐条处置

### N1（P3）— 已修

- **08 事实**：06 §二 P3#2 声称「已补注释」，实际未落到迁移 SQL §3 加列处。
- **处置**：在迁移 §3 加列处（`alter table … add column quota_consumed` 上方）补注释：

  ```sql
  -- quota_consumed 仅对新增写路径有意义（触发器只读 new.quota_consumed）；存量行该列为 false，
  -- 其额度语义由 §4 回填计数承载，二者双轨、不冲突。
  ```

  与 06 声明、04 §3.2 措辞对齐。

### N2（P3）— 已加固（实施者独立修正 N2′）

- **08 结论**：「功能等价、无需改」。**展示层成立，但其「`coalesce` 兜底到 0」推理不精确**，实施者独立核对后修正如下：
  - `get_subscription_status` 用标量 `select coalesce(import_lifetime_count, 0) into v_import_used …`（L199-200）。当新注册用户**无 `user_quotas` 行**时，该查询返回 0 行，PL/pgSQL 将 `v_import_used` 置 **NULL**（覆盖函数开头的 `:= 0` 初始化），`coalesce` 因「无行」不执行。
  - 故新用户 `get_subscription_status` 实际返回 `importUsed: null`，**偏离 04 §4.4 要求的「额度 0」**。前端 `Math.max(0, 30 - null) === 30` 恰好渲染正确，属隐性脆弱而非无懈可击。
- **处置**：return 处补兜底，使「额度 0」名副其实：

  ```sql
  'importUsed',  coalesce(v_import_used,  0),
  'bookmarkUsed', coalesce(v_bookmark_used, 0),
  ```

  （`bookmarkUsed` 经 L202-205 周滚动分支已置 0，此 coalesce 为对称加固；`importUsed` 为必要修复。）

### N3（P3，非本次引入）— 转独立跟踪

- **08 事实**：`loadLibrarySnapshot` 导出 `articles` 含 `reading_status='reading'` 在读内容；恢复路径 `importLibraryData → saveReading(article)` 遇 `saveReading` 的 D7 守卫（`readingStatus === 'reading'` 抛「正在阅读中的内容不可编辑」）会中断。
- **定性**：D7 守卫与快照含在读内容均为「阅读区」特性，**非订阅机制本次引入**，不属额度/订阅逻辑缺陷。
- **处置**：**不纳入本次订阅机制收口**，另起独立跟踪项。建议方向：恢复路径对在读内容「重建而非编辑」（绕过 D7，或恢复为 unread/reading 均可）。

### N4（说明）— 记录不改

- **08 事实**：触发器 L249-251「UPDATE 不得跨账户转移」守卫在 L252 `lock` 之前。
- **处置**：该守卫仅读 OLD/NEW、立即 fail-fast，无并发读，顺序无正确性影响。仅记录，不改。
