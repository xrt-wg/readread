# 预读模式 — 讨论和决策记录

> 日期：2026-07-18
> 状态：已确认

---

## 背景

测试反馈揭示了翻译弹窗的两个体验问题：

1. **弹窗响应慢** — 弹窗翻译走 Netlify Function → 有道 API，耗时 1-5s
2. **收藏卡翻译偶现空响应** — 超时导致字段为空

深入排查发现一个结构性问题：**同一段文本被翻译了两次**。

```
划词 → 弹窗直译（有道/MyMemory，60-70分）→ 点收藏 → 收藏卡 AI 精译（DeepSeek，85-90分）
              ↑ 第一次翻译                                ↑ 第二次翻译（覆盖第一次）
```

弹窗翻译是"用了就扔"的临时结果，收藏后再被 AI 精译覆盖。这不仅浪费 API 配额，更关键的是**弹窗本身就打断了阅读流**。

---

## 关键洞察

用户（Kaven）提出了一个范式转换的思路：

> 将"标注"和"翻译"解耦为两个独立阶段。阅读时只标注不翻译，阅读后批量精译。

这符合严肃阅读者的自然行为：遇到不认识的内容 → 标记 → 继续读 → 读完后再统一消化。

---

## 方案演进

### 起点：优化弹窗翻译速度

- MyMemory 替代有道（200ms vs 1-5s）
- 添加上下文句子提升准确度
- 添加翻译缓存
- 文章词汇预加载

### 转折：预读模式

用户提出预读模式后，上述优化的大部分变得不再必要 — 预读模式下弹窗根本不会出现。

### 最终决策：双模式共存

| | 普通模式（现有） | 预读模式（新增） |
|---|---|---|
| 划词行为 | 弹窗翻译 → 可选收藏 | 直接静默收藏 |
| 翻译时机 | 弹窗即时（直译） + 收藏异步（AI） | 收藏异步（AI） |
| 翻译质量 | 弹窗 60-70 / 收藏 85-90 | 统一 85-90 |
| 阅读打断 | 每次划词都打断 | 不打断 |
| API 调用 | 弹窗直译 + AI 精译（两次） | 仅 AI 精译（一次） |
| 触发方式 | 默认 | 手动开启 |

## 决策记录

### D1：预读模式下是否需要任何视觉反馈？

**决策：不需要额外 UI。** 仅依赖已有的收藏文本下划线作为标注确认。不添加 toast、弹窗或任何提示。

**理由：** 用户明确要求"不添加任何多余的提示弹窗"。下划线已足够告知用户"已标注"。零打扰是预读模式的核心价值。

### D2：预读模式关闭时是否自动触发批量翻译？

**决策：是。** 关闭预读模式 = 结束标注阶段 = 开始翻译阶段。遍历所有 `translationStatus === 'pending'` 的收藏，逐个调用 `translateBookmark()`。

**理由：** 预读模式关闭是一个明确的用户意图信号（"我读完了/标注完了"），此时启动翻译最自然。不需要额外的"开始翻译"按钮。

### D3：离开文章时预读模式的收藏如何处理？

**决策：保持 pending 状态，不强制翻译。** 下次打开文章时，BookmarkPanel 中仍显示"翻译生成中…"，用户可手动触发或等待。

**理由：** 用户可能只是暂时切换文章，不应在离开时静默消耗 API 配额。pending 状态的收藏在打开收藏面板时会自然可见。

### D4：预读模式是否持久化？

**决策：不持久化。** 每次进入文章默认关闭，需手动开启。

**理由：** 预读是主动选择的行为模式，不应成为默认。降低误操作风险（用户忘记关预读模式，划词后困惑"弹窗去哪了"）。

### D5：弹窗翻译的其他优化（MyMemory、缓存、上下文）还做吗？

**决策：暂缓。** 预读模式绕过了弹窗，这些优化的 ROI 大幅降低。如果后续普通模式的弹窗体验仍有问题，再单独评估。

### D6：批量翻译是并行还是串行？

**决策：串行。** `for...of` 逐个翻译，每个完成后再启动下一个。

**理由：** AI API（DeepSeek）有并发限制，并行可能触发 429。串行也更利于显示进度（"翻译中 3/12..."）。
