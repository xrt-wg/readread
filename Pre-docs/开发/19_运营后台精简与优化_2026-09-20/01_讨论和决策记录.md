# 运营后台精简与优化：讨论和决策记录

- 状态：理解自查完成，精简方案已收敛；待实施前审核
- 配套文档：[实施方案](./02_实施方案.md)
- 任务来源：用户要求「全面审视当前后台的业务与功能设计，只做减法或优化，不做加法」，并授权我以产品设计者视角自行判断理解是否完备、自行决定方案。

## 1. 任务边界

「后台」在本项目中指**运营后台**：AdminPage 及其子面板（推荐审核、首次阅读、审计日志、用户基础信息），加 admin 服务层（recommendationService、auditLogs、profile、firstReading）与 admin 相关的数据库表 / RLS / RPC。它区别于「后端（Supabase 数据底座）」。

本次范围严格限定为对运营后台做**减法或优化**：不新增功能、不新增状态、不新增数据列、不新增页面能力。任何「补全一个半成品能力」的动作，若需要新数据源或新交互，都视为加法、排除在本次之外。

## 2. 理解自查（本次最重要的结论）

我按三层完成理解：页面与交互（三个后台页面）→ 服务层（四个服务模块）→ 数据与权限（admin_roles / audit_logs / 推荐审核 / 首读选文的全部 migration 与 RPC），并回查了 15_运营后台方案.md 的原定边界。

自查发现我此前有两处**初判错误**，均因未先读近期已确认的产品决策：

1. 我曾建议「合并推荐审核的 approved + publish 状态，精简 5 态状态机」。读 `../12_推荐提交审核发布_2026-09-16/01_讨论和决策记录.md` 后发现：**「审核通过与公开发布是两个独立动作」是明确产品目标**，且 approved_at / published_at / removed_at / 审核人需保留供未来积分与订阅结算。该建议**撤回**。
2. 我曾建议「把首读选文降级为推荐区置顶两条，删掉整套触发器 / 配置 / 状态表」。读 `../13_首次阅读选文弹窗_2026-09-17/01_讨论和决策记录.md` 后发现：这是带 **11 条明确决策（D01–D11）** 的刚确认功能，且「两篇文章必须可由后台指定」。该建议**撤回**。

结论：**后台的业务与功能设计本身是有据、且近期刚收敛过的，不适合做结构性减法。** 真正安全、有价值的空间集中在三类：死代码清理、后台界面自身的冗余与缺陷、实现层重复。方案据此从「结构性精简」收敛为「纯减法 + 界面收敛 + 实现层去重」。

## 5. 最终决策

- **D1 删除前端写审计链路。** 删除 `createAuditLog` 与 `getCurrentActorUserId`、`index.js` 中 `createAuditLog` 导出，并新增迁移删除 `audit_logs_insert_admin` 策略与 `grant insert on audit_logs`。审计写入仅保留服务端 RPC（SECURITY DEFINER，不受 revoke 影响）。保留 `listAuditLogs`。
- **D2 删除服务层死导出。** 删除 `getRecommendationStats`、`getRecommendation`、`checkRatingEligibility`（及其独占助手 `findImportItemByShareSource`、本地 `checkReadingCompleted`）与 `index.js` 中对应导出。评分资格门控的现实依据为「已完成」UI 状态，删除不改变行为。
- **D3 收敛 dashboard 首页。** 删除误标的「管理员数量」卡与噪声的「最近审计记录」卡；「快捷入口」section 仅保留「处理推荐审核」按钮作为直链，删除与左侧导航重复的「前往审计日志」「前往用户基础信息」两个按钮；删除「系统快照」section 整体，将其中的「最近活跃用户数」（`profileSummary.activeSeen`）提升为一张 `StatCard`。首页最终为「用户总量 / 受限用户 / 最近活跃用户」三张统计卡 + 「处理推荐审核」直链。
- **D4 收敛审计日志页。** 删除空的动作下拉、过时的对象下拉、顶部 4 张噪声 StatCard，统一保留「时间范围 + 文本搜索 + 刷新」这一套有效筛选。
- **D5 复用错误分类函数。** AdminPage 删除自写的 `isAdminAccessError` / `resolveAdminErrorMessage`，复用 errorUtils 的 `isLibraryAccessError`，仅保留后台专属的提示文案字符串。
