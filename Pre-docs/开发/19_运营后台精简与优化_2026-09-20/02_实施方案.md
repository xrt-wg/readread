# 运营后台精简与优化：实施方案

- 日期：2026-09-20
- 状态：待实施前审核
- 配套文档：[讨论和决策记录](./01_讨论和决策记录.md)
- 原则：只做减法或优化，不改既有产品语义，不新增状态 / 列 / 交互 / 数据源。

## 1. 目标

把运营后台中已死、冗余或失准的部分清理掉，降低维护面与误读风险，同时保持后台能力与既有产品决策完全一致。

## 3. 逐项实施

### D1 删除前端写审计链路

现状：审计写入已全部下沉到服务端 RPC（`submit_recommendation_for_review` 及 admin_* 系列，均为 SECURITY DEFINER），前端 `createAuditLog` 全仓零调用；`audit_logs_insert_admin` 插入策略与 `grant insert` 因此是死路径。

- `auditLogs.js`：删除 `getCurrentActorUserId` 与 `createAuditLog`，保留 `AUDIT_LOG_COLUMNS`、`mapAuditLogRow`、`listAuditLogs`。
- `index.js`：删除 `createAuditLog` 导出，保留 `listAuditLogs`。
- 新增迁移 `supabase/migrations/20260920000000_drop_frontend_audit_insert.sql`：

```sql
-- 运营后台精简：删除已被服务端 RPC 审计取代的前端审计写入链路
begin;
drop policy if exists "audit_logs_insert_admin" on public.audit_logs;
revoke insert on public.audit_logs from authenticated;
commit;
```

说明：`audit_logs` 的 select 策略（admin 只读）与 no-update / no-delete 追加触发器保持不变；服务端 SECURITY DEFINER 函数写审计不受 `revoke` 影响。

### D2 删除服务层死导出

现状：`getRecommendationStats`、`getRecommendation` 全仓零调用；`checkRatingEligibility` 是未接线的旧校验（评分资格现由「已完成」UI 状态门控），其独占助手 `findImportItemByShareSource` 与本地 `checkReadingCompleted` 删除后不再被引用。

- `recommendationService.js`：删除 `getRecommendationStats`、`getRecommendation`、`checkRatingEligibility`、`findImportItemByShareSource`、`checkReadingCompleted`。保留 `getMyRating` / `listMySubmissions` / `rateRecommendation` / `listRecommendations` / `addRecommendationToBookshelf` / `syncAddCountAfterDelete` 及其共用助手 `mapRatingRow`、`getSubmissionById`。
- 清理 `rateRecommendation`（`recommendationService.js:408`）JSDoc 中引用 `checkRatingEligibility` 的「前置校验」说明，改为「评分资格由『已完成』UI 状态门控」。
- `index.js`：删除 `checkRatingEligibility` / `getRecommendation` / `getRecommendationStats` 三个导出。

标注 1：`checkRatingEligibility` 删除不改变行为；若未来要服务端强制评分资格校验，属加法、另立不在本次。

标注 2（index.js 未提交基线）：`index.js` 当前工作区含 18 号任务未提交的 `checkRatingEligibility` / `getMyRating` / `rateRecommendation` 新增导出。本次仅逐行删除 `checkRatingEligibility` / `getRecommendation` / `getRecommendationStats`，**保留** `getMyRating` / `rateRecommendation`，**禁止 `git checkout`**（会丢失 18 号任务的未提交成果）。

### D3 收敛 dashboard 首页

现状（`AdminPage.jsx` 首页分支）：`管理员数量` 实为 `adminProfiles.length`（`listAdminProfiles` 返回全部 profiles），与 `用户总量` 数值恒同、标签不实；`快捷入口` 三按钮与左侧导航重复；`系统快照` 的当前身份 / 账号状态 / 会话有效性为调试信息。

- 删除 StatCard 行中的「管理员数量」「最近审计记录」两张卡。
- 「快捷入口」section 仅保留「处理推荐审核」按钮作为直链，删除「前往审计日志」「前往用户基础信息」两个与导航重复的按钮。
- 删除「系统快照」section 整体，将其中的「最近活跃用户数」（`profileSummary.activeSeen`）提升为一张 `StatCard`。
- 首页最终形态：三张统计卡（用户总量 / 受限用户 / 最近活跃用户）+ 一个指向「推荐审核」的入口按钮。

### D4 收敛审计日志页

现状（`AdminPage.jsx` 审计分支）：`动作` 下拉只有「全部动作」一项（失效）；`对象` 下拉枚举为 profile / admin_role，而实际日志 target_type 为 recommendation_submission / first_reading_config（过时）；顶部 4 张 StatCard（日志总量 / 可见结果 / 筛选动作 / 筛选对象）为噪声；服务端筛选与客户端文本搜索两套并行。

- 删除 `动作` 下拉与 `对象` 下拉；删除 4 张 StatCard。
- 同步删除 `auditActionFilter` / `auditTargetTypeFilter` 两个 state、`reloadAuditLogs` 中 action / targetType 的回退读取分支、`应用筛选` 按钮 onClick 传入的 action / targetType 字段。
- 保留：`刷新日志` 按钮、两个日期输入（起 / 止）、文本搜索框、`应用筛选` 按钮；`reloadAuditLogs` 只传时间范围参数。
- `listAuditLogs` 服务的 action / targetType 入参不再有调用方传入，保留函数签名不变（不额外改动服务层，避免触及共享代码）。

### D5 复用错误分类函数

现状：`AdminPage.jsx` 自写 `isAdminAccessError` / `resolveAdminErrorMessage`，检测逻辑与 `errorUtils.isLibraryAccessError` / `resolveLibraryErrorMessage` 逐字符一致，仅提示文案不同。

- 删除 `AdminPage.jsx` 中 `isAdminAccessError` 与 `resolveAdminErrorMessage`。
- 从 `../services/errorUtils` 引入 `isLibraryAccessError`，保留一个仅含后台文案的最小包装：

```js
function resolveAdminErrorMessage(error, fallback) {
  return isLibraryAccessError(error)
    ? '后台权限已失效或当前会话已过期，系统正在刷新身份状态。'
    : error?.message || fallback
}
```

- 将页面内所有 `isAdminAccessError(...)` 替换为 `isLibraryAccessError(...)`。

## 4. 验证

1. `grep -rn "createAuditLog\|getRecommendationStats\|getRecommendation\b\|checkRatingEligibility" src` 无残留调用（`getRecommendationModerationDetail` 等仍被使用的同名不同名函数不受影响，逐条确认）。
2. `npm run build` 通过。
3. 手动走查后台：登录管理员 → 首页三张统计卡正确、无「管理员数量」误标；推荐审核 / 首次阅读 / 用户信息页行为不变；审计日志页能列出服务端写入的日志，时间范围与文本搜索有效。
4. 确认 `audit_logs` 无 update / delete 策略（追加触发器仍在），select 仍 admin-only。

## 5. 风险与回滚

- **D1 迁移**：`revoke insert` 仅影响前端直写路径（已死）；服务端 RPC 为 SECURITY DEFINER 不受影响。若意外有其它前端直写，回滚为重新 `create policy audit_logs_insert_admin` + `grant insert`。
- **D2**：删除前用 grep 全仓确认零调用；若发现遗漏调用方，仅需回退对应函数定义与导出。
- **D3 / D4**：纯 UI 删除，不涉及数据与接口，回滚为还原 JSX 分支。
- **D5**：文案保持原「后台权限已失效…」不变，仅替换检测逻辑来源，行为等价。

## 6. 执行顺序

1. D5（改动最小、行为等价，先落地验证错误分类复用）。
2. D3、D4（同一文件 `AdminPage.jsx` 的界面收敛，可合并提交）。
3. D2（服务层死导出删除）。
4. D1（前端删除 + 迁移，最后落地并单独验证迁移）。

除 D1 含迁移外，其余为纯前端改动，可整体或分项提交；提交前按仓库规范核对 `git status` / `git diff` 范围。
