### 1.2 决策完备性 — 需澄清的问题

#### Q1：D1「10% 粒度」与实施精度不一致

决策写「10% 粒度即可」（10%, 20%, 30%），但实施存储 `INTEGER` 0-100（1% 精度）。这两个不矛盾——存储精度 1% + 展示粒度 10% 是合理的工程选择。但决策和实施方案之间缺少明确桥接：读决策的人可能以为存储也是 10 的倍数。

**建议**：在决策中明确：
> 存储精度 1%（`INTEGER 0–100`），UI 展示可按 10% 步长取整。保留 1% 存储精度为未来可能的精细化展示留空间，无额外成本。

#### Q2：scroll% 作为「阅读进度」的语义迁移未讨论

当前模型：段落位置 / 总段落数 → 「已标记段落的文本占比」
新模型：`window.scrollY / scrollable` → 「标记时页面滚动位置」

两者语义不同：
- 段落模型：代理指标是**内容量**（你读到了全文的第 N 段）
- 滚动模型：代理指标是**视口位置**（你滚动到了页面的 X%）

决策文档将此描述为「不一致修复」，但实际是**进度定义本身的变更**。这不是问题——滚动百分比对读者同样直观，且与顶部栏视觉一致——但决策记录应明确这一语义变化，说明为什么滚动百分比是合理的「阅读进度」代理。

**建议**：在「放弃的方案」之后增加一节说明：
> 进度定义的迁移：从「段落位置比例」迁移到「视口滚动比例」。两者都是阅读进度的合理代理指标，但后者具有「与阅读器顶部栏视觉一致」和「不依赖内容解析」的优势。

#### 2.4.2 ❌ `calcMultiSectionProgressAtMark` 引用未定义变量

方案 §4.3 的函数定义：

```js
function calcMultiSectionProgressAtMark(article, currentSection, sectionScrollPercent) {
  const totalWords = article.sections.reduce((sum, s) => sum + s.body.wordCount, 0)
  if (totalWords === 0) return sectionScrollPercent

  //                            ^^^^
  //                            mark 未定义！
```

**问题**：`mark` 不在函数作用域内——函数签名只有 3 个参数 `(article, currentSection, sectionScrollPercent)`，但函数体引用了 `mark?.completedSections`。

**根因**：此函数从 `calcMultiSectionProgress(article, mark)`（原版，接受 mark 参数）重构而来，改为用 `scrollPercent` 替代段落索引计算当前章节进度，但遗漏了 `mark` 参数。`completedSections` 仍然需要从 `readingMark` 获取。

**修复方案**（二选一）：

**方案 A**：增加 `readingMark` 参数
```js
function calcMultiSectionProgressAtMark(article, currentSection, sectionScrollPercent, readingMark) {
  const completedIds = new Set(readingMark?.completedSections ?? [])
  // ...
}

// 调用处：
const progressPercent = hasMultipleSections
  ? calcMultiSectionProgressAtMark(article, currentSection, scrollPercent, readingMark)
  : scrollPercent
```

**方案 B**：将函数定义移入 `handleSetReadingMark` 内部，从闭包访问 `readingMark`
```js
const handleSetReadingMark = useCallback(async (paraIndex) => {
  // ...
  function calcMultiSectionProgressAtMark(article, currentSection, sectionScrollPercent) {
    const completedIds = new Set(readingMark?.completedSections ?? [])
    // ...
  }
  // ...
}, [...])
```

**建议**：方案 A 更清晰，函数不依赖闭包。

### 3.2 发现的额外注意事项

#### N1：`clearReadingMark` 语义审查

方案中 `clearReadingMark` 保留 `progressPercent`。审查确认：

- `mapReadingMarkRow`（[library.js:70-71](src/services/library.js#L70-L71)）：当 `paragraph_index === null && completed === false` 时返回 `null`
- 因此清除后 mark 为 null → ImportPage 不显示进度 → **功能正确**
- 后续重新标记时，`saveReadingMark` 传入新 `progressPercent` → 覆盖已有值 → **无残值风险**

数据库中残留的旧 `progressPercent` 无功能影响。但如果希望保持数据语义清洁，可考虑将 `clearReadingMark` 中的 `progressPercent` 设为 `null`（而非保留）。**当前方案可接受，非阻塞。**
