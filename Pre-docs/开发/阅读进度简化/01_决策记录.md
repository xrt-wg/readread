# 决策记录 — 阅读进度计算简化

- **日期**：2026-06-20
- **参与者**：Kaven, Claude
- **状态**：待确认

---

## 一、背景

列表进度（ImportPage 阅读标签）与阅读器顶部栏进度长期不一致——顶部栏 65% 对应列表 99%——根源在于两端使用完全不同的计算模型：

- 列表端：`getParagraphs(markdown)` → 段落解析 → 词数比例（独立重算）
- 阅读器端：`window.scrollY / scrollable`（浏览器原生）

历经多轮修复（CRLF 归一化、引用块处理、段落模型简化），偏差缩小但未根除——因为两个数字永远来源于不同的计算路径。

## 二、决策

| # | 决策 | 理由 |
|---|------|------|
| D1 | **不追求精度**——10% 粒度即可（10%、20%、30%……） | 阅读进度不需要「73.4%」这种精度；10% 步长对读者足够直观，且能容忍字体变化等微小漂移。**存储精度 1%（INTEGER 0–100），UI 展示按需取整**——保留 1% 存储精度为未来可能的精细化展示留空间，无额外成本 |
| D2 | **列表端不再独立计算**——进度值直接取自阅读器标记时的**即时快照** | 根除「两端不一致」的唯一方式：记录端 = 展示端 = 同一个值 |
| D3 | **单章节文章**——存 `scrollY / scrollable × 100`（顶部栏当时的百分比） | 阅读器顶部栏已经在实时计算，直接复用；零额外解析成本 |
| D4 | **多章节书**——进度 = Σ(已完成章节 wordCount) + 当前章节 wordCount × scroll% / Σ(全部章节 wordCount) | 纯章节计数太粗糙（5000 词的章和 200 词的章权重相同）；wordCount 在导入时已算好，直接使用，无需重新解析 |
| D5 | **段落解析模块（progress.js）保留 `getParagraphs`，删除 `calcProgress` 等进度计算函数** | `getParagraphs` 仍被 ReaderPage 非 markdown 渲染路径使用；进度计算职责移交至 ReaderPage 标记时 |
| D6 | **`reading_marks` 新增 `progress_percent INTEGER` 列** | 存储标记时的进度快照；`paragraph_index` 保留——阅读器恢复书签位置仍需要它 |

## 三、放弃的方案

| 方案 | 放弃原因 |
|------|---------|
| 段落比例（position / totalParagraphs） | 仍需 `getParagraphs` → AST vs regex 矛盾依然存在 |
| 存段落索引 + 列表端复算百分比 | 绕了一圈回到同一个问题——列表端仍需要 `getParagraphs` |
| 多章节用纯章节计数 | 章节大小差异大，5000 词和 200 词各算 1 章 → 偏差显著 |

## 四、进度定义的迁移

此方案不仅是技术实现的变更，也是「阅读进度」语义的迁移：

| | 旧定义 | 新定义 |
|---|--------|--------|
| **代理指标** | 段落位置 / 总段落数（内容量） | `window.scrollY / scrollable`（视口位置） |
| **含义** | 「已标记段落占全文段落的比例」 | 「标记时页面滚动位置的比例」 |
| **与顶部栏关系** | 独立重算，来源不同 → 不一致 | 同一值，同源 → 一致 |

两种定义都是阅读进度的合理代理：

- **段落比例**：隐式假设「每段阅读耗时均等」——但段落长短差异可达 10 倍以上
- **滚动比例**：隐式假设「页面的视觉密度均匀」——但图片、代码块、空白区域会影响滚动高度

**选择滚动比例的理由**：
1. 与阅读器顶部栏视觉一致——用户看到的就是存下来的
2. 不依赖内容解析（无需 `getParagraphs`、`cleanInlineMarkdown`）——根除了偏差源
3. `wordCount` 加权（多章节场景）弥补滚动比例在大尺度上的偏差

## 五、架构原则

```
之前：
  标记时：存 paragraphIndex（AST 计数）
  列表时：getParagraphs(markdown) → 重新解析 → 计算进度
  问题：两次计算路径不同 → 结果不一致

之后：
  标记时：取顶部栏 scroll% → 直接存入 progressPercent
  列表时：读取 progressPercent → 直接展示
  原则：记录即展示，零重算
```
