## 二、阻塞项（实施前必须解决）

### 🔴 B1 — Header 统计数据来源与计算规则未明确

**位置**：执行计划 §3.1、Step 2

**问题**：
- 计划写"统计数据来源：`readingMarks` + `bookmarks` + `articles`"，但未给出三个统计项的具体计算逻辑
- 当前代码的阅读区统计使用不同数据源（已读篇数来自 `readingMarks`、收藏条数来自 `bookmarks`、累计词数依赖 `readingZoneItems.filter(a => readingMarks[a.id]?.completed)`）
- 设计草图中三个统计分别有独立 accent 颜色：已读=teal、收藏=gold、累计=ink——这些颜色传达了不同的语义权重

**建议**：
- 在计划中明确三项统计的精确计算：
  - `completedCount` = `Object.values(readingMarks).filter(m => m.completed).length`
  - `bookmarkCount` = `bookmarks.length`
  - `wordsRead` = `articles.filter(a => readingMarks[a.id]?.completed).reduce((sum, a) => sum + (a.wordCount ?? 0), 0)`
- 明确 accent 颜色的 CSS 实现（teal 需要新增 CSS 变量，见 B2）

---

### 🔴 B2 — 缺少 `teal` 色彩体系 CSS 变量定义

**位置**：执行计划 Step 6、设计草图 `:root` 变量

**问题**：
- 设计草图定义了三个 teal 变量：`--teal: #0d9488`、`--teal-border: rgba(13,148,136,0.18)`、`--teal-bg: rgba(13,148,136,0.05)`
- 现有 `index.css` 中**没有 teal 变量**——当前代码在 `ImportItemList.jsx` 中以 inline 方式硬编码 `#0d9488` 和相关 rgba 值
- teal 在草图中用于三个位置：Header 已读统计、条目状态 pill（completed）、kind 标签（book）。缺少 CSS 变量会导致这些位置的 teal 颜色硬编码分散，且不支持夜间模式（`[data-theme="night"]`）
- 计划 Step 6 仅写"确认/新增需要的 CSS 变量"，未明确列出 teal

**建议**：
- 在 `index.css` `:root` 中新增：
  ```css
  --teal: #0d9488;
  --teal-border: rgba(13,148,136,0.18);
  --teal-bg: rgba(13,148,136,0.05);
  /* night theme */
  --teal: #2dd4bf;
  --teal-border: rgba(45,212,191,0.2);
  --teal-bg: rgba(45,212,191,0.08);
  ```
- 将 `ImportItemList.jsx` 中硬编码的 teal 值替换为 CSS 变量引用

### 🔴 B3 — 自适应按钮的 onClick 行为映射未定义

**位置**：执行计划 §3.4、Step 4

**问题**：
- 计划明确了三种按钮的视觉样式（文字、颜色），但未定义 onClick 行为：
  - `unread` "开始阅读" → 应调用 `startReading()` 还是 `onMoveToReading()`？
  - `in_progress` "继续 XX%" → 应打开阅读器继续阅读（`onOpen`）还是等同于"开始阅读"？
  - `completed` "重新阅读" → `onReset` 还是打开阅读器？
- 当前 `ImportItemList` 只有一个 `onMoveToReading` prop 和一个 `onReset` prop，分别对应不同的行为。自适应按钮需要三种不同的 handler
- 父组件 `ImportPage` 目前有 `handleMoveToReading`（调用 `startReading`）和 `handleResetReading`（调用 `resetReading`），但缺少"继续阅读"的 handler

**建议**：
- 明确三种按钮的行为映射：
  | 状态 | 按钮文字 | onClick | 调用的 ImportPage handler |
  |------|---------|---------|--------------------------|
  | unread | 开始阅读 | `onStartReading(item)` | `startReading(item.id, ...)` |
  | in_progress | 继续 XX% | `onContinueReading(item)` | 打开阅读器 `onOpen(item)`（将 item 转为 ReaderPage 接受的格式） |
  | completed | 重新阅读 | `onResetReading(item)` | `resetReading(item.id, ...)`（含 confirm 弹窗） |
- `ImportItemList` 新增 `onContinueReading` prop（或复用 `onOpen` 语义）
- 确认"继续阅读"是否需要先将 item 转回阅读区、还是直接打开（当前流程是移入阅读区后才可阅读——应明确此约束）

---

### 🔴 B4 — 条目行 More menu 弹出方向与草图不一致

**位置**：执行计划 §3.3、Step 4

**问题**：
- 设计草图 CSS：`.item-more-menu { left: 0; bottom: 100%; margin-bottom: 4px; }` ——**向上弹出**
- 当前代码：`className="absolute left-full bottom-0 ml-1"` ——**向右弹出**
- 向上弹出在列表底部条目时可能被视口裁剪；向右弹出在右侧空间不足时可能溢出。两个方案各有取舍
- 计划未提及这一差异——实施者可能保留当前向右弹出，导致与草图不一致

**建议**：
- 明确决策：采用向上弹出（对齐草图），并在靠近视口顶部时改为向下弹出（添加位置自适应逻辑，或至少加 `overflow-y: auto` 保护）
- 或者保留向右弹出但记录为"有意偏离草图（右侧空间通常充足，向上弹出可能被截断）"

## 三、建议项

### 🟡 S1 — 计划对"3 个图标按钮"的描述有数量矛盾

**位置**：执行计划 §3.2、Step 3

计划 §3.2 表格写"操作按钮：`⊕` `✦` 两个 34×34 图标按钮"，但 Step 3 写"按钮：3 个图标按钮（⊕ 导入, ✦ 推荐）"。设计草图中控制栏仅展示 2 个按钮（⊕ + ✦），无第三个。CSS 中 `.ctrl-icon.active` 样式在草图中未被任何按钮使用——可能是预留或已废弃。

**建议**：统一为 2 个按钮（⊕ 导入 + ✦ 推荐），删除"3 个"的表述。

---

### 🟡 S2 — Header stats 容器的暗色主题适配缺失

**位置**：执行计划 Step 2、设计草图 `:root` 变量

设计草图为 `.header-stats` 指定了 `background: rgba(255,255,255,0.6)`，在当前浅色主题中效果很好。但项目已支持 `[data-theme="night"]` 暗色模式——白色半透明背景在暗色模式下会异常刺眼。

**建议**：
- 将 `.header-stats` 的背景替换为 CSS 变量引用（如 `var(--surface-bg)`，对应现有的 `rgba(255,255,255,0.6)` / `rgba(26,24,20,0.6)`）
- 或将 header-stats 作为新 CSS 变量加入全局样式（建议方式：新增 `--stats-bg` 变量）

---

### 🟡 S3 — `ShelfTabs` 组件已存在但配色需从金色改为灰色

**位置**：执行计划 §3.2、Step 3

计划说"子Tab：改为胶囊样式"，但现有 `ShelfTabs` 组件**已经是胶囊样式**（`borderRadius: '10px'`），仅 active 配色不同：
- 当前 active：`rgba(196,154,60,0.08)` 背景 + `var(--gold-dark)` 文字 + 金色边框
- 草图 active：`rgba(28,25,23,0.06)` 背景 + `var(--ink)` 文字 + 无边框/透明边框

**建议**：将 Step 3 的表述改为"子Tab：**保持**胶囊样式，将 active 配色从金色调整为灰色（`background: rgba(28,25,23,0.06)`, `color: var(--ink)`, `font-weight: 600`），移除金色边框"。

---

### 🟡 S4 — 缺少筛选空状态（filter empty state）

**位置**：设计草图 `#filterEmptyState`

设计草图为筛选 Tab（未读/未读完/已读完）的零结果状态提供了差异化文案：
- 未读=0 → 🎉 "所有内容均已开始阅读"
- 未读完=0 → 📚 "没有正在阅读的内容"
- 已读完=0 → 📖 "还没有读完的内容"

当前 `ImportItemList` 仅处理了全局空书架状态，未处理筛选后的空状态。计划未提及此需求。

**建议**：在 Step 4（ImportItemList 重写）中增加筛选空状态的实现。这需要 `ImportItemList` 知道当前的 `shelfTab` 值——需新增 prop（如 `activeFilter`）。

---

### 🟡 S5 — 缺少条目 hover 过渡动画的具体规格

**位置**：设计草图 `.item-row:hover`

设计草图定义了完整的 hover 效果：
```css
.item-row:hover {
  border-color: rgba(196,154,60,0.25);
  box-shadow: 0 4px 20px rgba(28,25,23,0.07);
  transform: translateY(-1px);
}
transition: all 0.2s cubic-bezier(0.4, 0, 0.2, 1);
```

当前代码的 hover 仅在阅读区文章列表中使用（ImportPage.jsx 中的 inline style `onMouseEnter`/`onMouseLeave`），书架条目（ImportItemList）**没有 hover 效果**——是纯静态的。

**建议**：在 Step 4 中明确条目行的 hover 过渡细节（边框色、阴影、translateY、transition 参数），建议优先使用 CSS class 实现而非 inline event handler。

---

### 🟡 S6 — "继续阅读"按钮的进度百分比数据流不完整

**位置**：执行计划 §3.4、风险点 #2

计划的风险点 #2 正确识别了"进度百分比需要从 `readingMarks` 中读取 `progressPercent`"。但解决路径不完整：

1. `ImportItemList` 当前接收 `items` 数组——每个 item 已有 `readingStatus` 字段，但**没有 `progressPercent`**
2. 需要在传给 `ImportItemList` 之前，将 `readingMarks` 中的进度数据合并到 items 中（如添加 `readingProgress` 字段）
3. 或者直接传 `readingMarks` 作为 prop（计划 Step 4 的方案），在 `ImportItemList` 内部做查找

**建议**：明确采用方案 B（传 `readingMarks` prop），并在组件内部通过 `readingMarks[item.id]?.progressPercent` 获取进度。在 Step 4 的实施描述中补充此细节。

### 🟡 S7 — More menu 中"重新阅读"功能的位置

**位置**：设计草图 vs 现有代码

设计草图的 more menu 仅有"编辑"+"删除"两个选项。当前代码的 more menu 有"编辑"+"重新阅读"+"删除"三个选项（仅对 in_progress/completed 条目显示"重新阅读"）。草图中摘掉"重新阅读"的意图可能是：completed 条目有"重新阅读"主按钮 → 不再需要在 more menu 中重复。

**建议**：
- 确认是否从 more menu 移除"重新阅读"（对齐草图）
- 如果移除：确认 `completed` 状态的 more menu 仅含"编辑"+"删除"，而"重新阅读"功能通过主按钮触发
- 如果保留：记录为"有意偏离草图（为 non-completed 条目保留重置能力）"

---

### 🟡 S8 — 阅读区文章列表分隔符需同步更新

**位置**：执行计划 §3.5、现有 ImportPage.jsx 阅读区文章列表

计划 §3.3 要求将条目行的分隔符从 `·` 改为 `|`，但这仅覆盖书架 Tab 下的 ImportItemList。**阅读区**（view === 'reading'）的文章列表中同样使用了 `·` 中点作为分隔符（ImportPage.jsx 约第 728 行）。

**建议**：在 Step 5 或 Step 6 中确认阅读区文章列表的分隔符也同步改为 `|`，保持全局一致。

### 🟡 S9 — Header 的 `max-width` 从 840px 缩小为 640px 的影响

**位置**：设计草图 `.app-header-inner { max-width: 640px }`、现有 Header 的 `maxWidth: '840px'`

设计草图的 Header 内容区限制为 640px（与书架区同宽），但当前 Header 使用 840px（与阅读区空状态等宽）。640px 在 Header 中放置统计行 + 4 个图标按钮是足够的，但因为更窄，统计文字和标签需要更紧凑的排版。

**建议**：确认是否将 Header 宽度从 840px 改为 640px。若确认，需在计划中明确记录（当前仅写了统计行和图标 Tab 的内容变化，未写宽度变化）。
