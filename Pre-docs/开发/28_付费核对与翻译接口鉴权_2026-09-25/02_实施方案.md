# 付费核对与翻译接口鉴权 — 实施方案

> 日期：2026-09-25（修订 2026-09-26）
> 性质：实施文档
> 关联：[01_讨论和决策记录](01_讨论和决策记录.md)

## 目标与范围

- **S1**：`payment_requests` 增三列 + 核对码 partial unique index + 存量回填；三层限流 RPC（互斥沿用 / 冷却 / 复位）+ 发码即建单前端流程。
- **S2**：`translate.js` LLM 路径加 JWT 鉴权与按 `sub` 限流、直译路径仅 IP 限流；计数与阈值落 Supabase（可后台配置）。
- **顺手修**：面板重开/pending 轮询刷新订阅状态；`PRICE_TEXT`/`PAID_DAYS` 改读行字段。
- 不改订阅机制本身、不动 `pro_grants` 账本语义、不动 `uq_payment_requests_open`。

## 关键口径

- **发码即建单语义**：打开支付弹窗即 `begin_payment_request()` 建单发码（`claimed_at=NULL`，「发码未提交」）；点「我已支付」才 `submit_payment_request()` 置 `claimed_at=now()`。管理员可凭码定位「付了款但从未提交」的用户。
- **`claimed_at` 语义**：`NULL` = 发码未提交，非 `NULL` = 已提交。仅作区分标记，不改变 `status` 三态枚举（`pending/granted/rejected`）。
- **前端「已提交」判别**：一律用 `claimedAt != null`，**不得**用 `status === 'pending'`（发码即建单后 status 恒 pending，会误藏「我已支付」按钮）。
- **互斥不变**：`uq_payment_requests_open`（`(user_id) where status='pending'`）沿用——同一用户同时至多一笔 open 单；`begin` 对已有 open 单幂等复用同一码（不新建、不重新生成）。
- **冷却口径**：`admin_reject_payment` 置 `cooldown_until = now() + interval '24 hours'`；`begin` 与 `submit` 均校验冷却——**读该用户最近 rejected 行的 `cooldown_until`**（`select max(cooldown_until) ... where cooldown_until > now()`，而非当前 pending 行，否则冷却形同虚设）；`admin_reopen_payment` 只清 `cooldown_until`、不翻 status + 记审计。
- **核对码碰撞**：partial unique index `uq_payment_requests_open_code on (verification_code) where status='pending'`；`begin` 生成新码时 `insert ... on conflict (verification_code) where status='pending' do nothing` + 冲突重生成重试。无 TOCTOU、无需 advisory lock；历史 granted/rejected 行不受影响（不在 partial 索引范围）。
- **submit 幂等衔接**：`begin` 已建 open 单 → `UPDATE ... SET claimed_at=now() WHERE claimed_at IS NULL`（重复提交不重置换）；被直调无 open 单 → 自建单并补码（杜绝 `verification_code=NULL` 坏单）。抽共享 `generate_code()`（含重试）。
- **S2 分层**：LLM 精译（`isDirect===false`，L161 后分支）要求 JWT + 按 `sub` 限流；直译（`isDirect` 分支，L184 早 return）仅 IP 限流、不登录。分层靠「直译先 return」天然隔离，无需改路由结构。
- **S2 计数（`consume_translate_quota(scope, scope_id, kind)`）**：security definer + `set search_path=public`；单条 `insert ... on conflict (scope, scope_id) do update` 原子固定窗口递增（窗口起点过期则重置为 1）；返回 `{allowed, used, limit, windowSeconds, resetAt}`。阈值从 `translate_rate_limit_config` 读（`coalesce` 兜底默认）。**仅 service_role 可调用**：`revoke all ... from public, anon, authenticated`（service_role 天然保留 execute）。
- **S2 失败语义**：LLM 计数后端不可用 → 拒绝（fail-closed）；直译计数不可用 → 放行（fail-open，保永远在线）。
- **S2 环境变量（Netlify 新增）**：`SUPABASE_URL`、`SUPABASE_SERVICE_ROLE_KEY`（函数直连计数 RPC）、`SUPABASE_JWT_SECRET`（与 Supabase 项目 JWT 密钥一致，验签用）。`@supabase/supabase-js` 若不在根依赖则补。
- **阈值可后台配置**：`translate_rate_limit_config` 单行表（`llm_per_user_limit`/`llm_window_hours`/`direct_per_ip_limit`/`direct_window_hours`），admin RPC 沿用 `recommendation_submission_config` 的乐观并发（`for update` + `updated_at` 比对）+ 审计；改配置即时生效，函数每次调用读 DB。
- **直译永远在线**：IP 限流仅对 DeepL/有道生效，超限 429 → 客户端回落免费 myMemory（不经 Netlify），划词仍出结果、质量降级。
- **单一事实源**：价格/天数由 `begin` 返回的 `amountCents`/`requestedDays` 派生展示；`PRICE_TEXT`/`PAID_DAYS` 常量仅兜底 + 注释漂移风险（避免「价格走常量、天数走行」的混合漂移）。
- **安全模式**：所有新函数沿用仓库既有——`security definer set search_path=public`；`revoke all ... from public, anon, authenticated` 后按需 `grant execute to authenticated`（`begin`/`submit` 用户侧；`admin_reopen_payment`/admin 配置 RPC 走 `is_current_user_admin()` 闸门）。

## 落库

迁移经 Supabase Dashboard SQL Editor 手动执行（仓库无 CLI）。执行顺序：
1. `20260926000000_payment_verification.sql`（依赖已落库的 `20260924000000_payment_requests.sql` / `20260923000000_subscription_mechanism.sql`）。
2. `20260926000001_translate_rate_limit.sql`（S2 独立，无前置依赖）。

Netlify 环境变量（`SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`/`SUPABASE_JWT_SECRET`）在 Netlify 控制台配置后，随函数与前端部署生效。
