## 一、定位与增量

本轮审核对象是**一份决策记录（01）+ 一份实施方案（02）**，二者同批产出、尚未经过任何独立复核。特性分两块：**S1** 在既有 `payment_requests` / `subscriptions` / `pro_grants` 之上加固付费核对的可靠性（三层限流、4 位核对码、发码即建单）；**S2** 在既有 `translate.js` 之上加成本闸门（LLM 路径 JWT + 每用户限流、直译路径仅 IP 限流）；外加两处「顺手修」。

**先说结论**：决策方向成立、三点裁决（1 天缓冲不做 / 三层限流 / 4 位码服务端生成）忠实还原、S1 数据模型与既有 partial unique index 的衔接思路基本正确；但**存在一处动笔前必须解决的有效性风险**（S2 的「每用户 / IP 限流」在无状态 Netlify 函数中缺持久化计数后端，方案当作常量/环境变量一笔带过），以及若干 P2 交付物缺失与并发/边界细节。

## 三、文档一致性问题

### 3.1 🔴 交付物自相矛盾：前端要展示核对码/claimed_at，但两个读取 RPC 的返回未纳入改动（P2）

02 §交付物「前端 S1 PaymentRequestsPanel」要求「队列显示核对码与 claimed_at」，「前端 S1 PaymentModal」要求展示 4 位码；02 §关键口径还要求「弹窗关闭再打开保持同一码」。但事实 #3/#4：`admin_list_payment_requests` 与 `get_my_payment_request` 的 jsonb 返回都**不含** `verification_code / claimed_at / cooldown_until`，而 02 §交付物「RPC（S1）」行只列了 `begin_payment_request`（新增）、`submit_payment_request`（改）、`admin_reject_payment`（改）、`admin_reopen_payment`（新增）四个，**漏掉了这两个读取 RPC 的返回字段扩展**。

前端拿不到字段就无法展示；「重开展示同一码」也依赖 `get_my_payment_request` 返回 verification_code。这是一处「文档声称成立、但交付物不足以支撑」的断点。

**建议**：交付物「RPC（S1）」行补上「改 `get_my_payment_request` / `admin_list_payment_requests` 的 jsonb 返回，各加 verificationCode/claimedAt/cooldownUntil」。

### 3.2 ⚠️ 「碰撞检查重生成」与「幂等复用同一码」在同一决策内张力（P2）

01 §S1.1#3 同时写了「码在弹窗关闭再打开时保持稳定（同一 open 单重复发码幂等返回同一码）」和「服务端生成时做碰撞检查（**同用户**或全局已存在则**重生成**）」。二者字面冲突：若「同用户已存在则重生成」被字面执行，每次重开弹窗都会换码，直接违背「保持稳定」。

真实意图应是「仅**新生成**时做全局碰撞检查；已有 open 单则复用其码」。且「同用户已存在」这一条被 `uq_payment_requests_open`（同用户至多一笔 open）天然保证，属冗余措辞。建议把碰撞检查明确限定为「仅新建 open 单、生成新码时，做**全局**碰撞检查」，删掉「同用户」字样与「重生成」在幂等场景的歧义。

### 3.3 ⚠️ `admin_reopen_payment` 「必要时连同状态复位」语义未定（P3）

01 §S1.4 与 02 §关键口径对 `admin_reopen_payment` 均用「清除 cooldown_until（必要时连同状态复位为可再次提交）」的模糊措辞，未定义：是否把 `rejected` 行翻回 `pending`？若翻回，会重新占用 `uq_payment_requests_open` 的互斥槽位；若不翻回，用户需重新走 `begin_payment_request` 才能再提交。两种语义对前端「复位后用户下一步动作」影响不同，应写死其一，并明确是否记 `audit_logs`（其余 admin 动作均记审计，此函数若不记则破坏审计闭环）。

### 3.4 ✅ 三点裁决忠实还原

01 §S1.1 三点裁决——「1 天缓冲不做」「三层限流替代 29 天一刀切」「4 位码服务端生成支付前展示」——齐备且与 02 一致；§多方讨论对「29 天一刀切 vs 三层」「1 天缓冲」两处取舍的理由记录完整。**决策链一致性通过**。

## 四、方案合理性与有效性核验

### 🔴 4.1 S2 「每用户 / IP 限流」在无状态 Netlify 函数中缺持久化计数后端（P1）

**这是本轮最需要动笔前解决的问题。** 02 §交付物写「translate.js LLM 路径加 JWT 鉴权 + 按 sub 每用户限流；直译路径仅 IP 限流」，§落库写「限流阈值走环境变量 / 常量」。但事实 #12：`translate.js` 是**无状态** Netlify 函数，冷启动即失忆、多实例不共享内存。「按 sub 每用户限流」和「IP 限流」都需要一个**跨请求、跨实例持久化的计数器**，而方案对此只字未提——「阈值走环境变量/常量」只能定阈值，定不了「已用多少次」。

可选后端（方案必须拍板其一，并评估成本）：
- 外部 KV/Redis（Upstash 等，Netlify 常见搭配）；
- 复用 Supabase：新增一张 `translate_rate_limits` 表 + service_role 直连或一个新 RPC（注意：函数层直连 Supabase 需 service_role key 环境变量，且引入函数层→DB 的新信任边界）；
- 内存 Map + TTL（仅单实例 best-effort，冷启动清零，验证期可接受但不抗并发实例）。

不拍板则 S2 的核心交付物「限流」无法正确实现——两个实施者会写出语义完全不同的「限流」。**这是本方案有效性的根基，动笔前必须定。** 与 08 §五/09 §三遗留「`translate.js` 匿名 IP 限流未实现（接支付前必办）」同源，但 01/02 把它上升为本次交付，就必须给到可落地的计数方案。

### ⚠️ 4.2 JWT（HS256）校验需新增环境变量与依赖决策（P2）

事实 #13：根 `package.json` 无 `jsonwebtoken`；Node 内置 `crypto` 可手写 HS256 校验（`translate.js` 已用 crypto 做 sha256）。因此「是否需新依赖」结论是**可不加依赖**。但**必须新增环境变量** `SUPABASE_JWT_SECRET`（与 Supabase 项目的 JWT 签名密钥一致），否则函数无法验签。02 只笼统说「阈值走环境变量」，未列出这个关键密钥变量及其来源（Supabase Dashboard → Settings → API → JWT Secret），也未说明验签失败的响应码（401）与前端降级行为。建议在交付物补一行「新增 Netlify 环境变量 `SUPABASE_JWT_SECRET`」，并明确 `sub` 提取、`exp` 校验、非法 token 返回 401。

### ⚠️ 4.3 4 位码「不加唯一索引、碰撞检查」的并发安全性不成立（TOCTOU）（P2）

02 §关键口径「4 位码碰撞：不加唯一索引，begin_payment_request 生成时做碰撞检查（同用户或全局已存在则重生成）」。**无唯一索引、无 advisory lock 的 SELECT-then-INSERT 存在 TOCTOU 窗口**：两个用户并发 `begin_payment_request` 同时生成同码、同时通过「全局不存在」检查、同时提交，落成两笔同码 open 单。

后果（4 位码、10000 空间、生日碰撞在 ~100 笔活跃单时即约 50%）：admin 核对口径「码 + 金额 + 时间」下，同码会让 admin 面临两笔无法仅凭码区分的待核对单——靠邮箱 + 时间兜底可解，但方案应如实标注该极小概率后果（核对码只作辅助定位，最终以邮箱+到账为准）。

更简单的修复是**沿用既有 `uq_payment_requests_open` 同一模式**：加 partial unique index `on (verification_code) where status='pending'`，`begin_payment_request` 生成时 `insert ... on conflict (verification_code) where status='pending' do nothing` + 冲突则重生成重试。这样既无 TOCTOU，也无需 advisory lock，且与既有「部分唯一索引 + on conflict」的仓库先例一致。01 的「不加硬唯一索引（避免撞码报错）」理由不成立——partial（仅 pending 行）索引不会影响 granted/rejected 的历史行。**建议改为 partial unique index + 冲突重生成。**

### ⚠️ 4.4 冷却校验的落点未定义 + `submit` 与「发码即建单」的幂等衔接缺失（P2）

两层问题：

1. **冷却落点**：`admin_reject_payment` 置的是**被拒行**的 `cooldown_until`；而用户被拒后重新 `begin_payment_request` 会新建一笔 `status='pending'` 的新行（`cooldown_until` 为 NULL）。若 `submit_payment_request` 只读**当前 pending 行**的 `cooldown_until`，冷却形同虚设（新行恒 NULL）。必须明确 submit 读「该用户最近一笔 `rejected` 行的 `cooldown_until`」（如 `max(cooldown_until) over user's rows` 或最近 rejected 行），并在 `cooldown_until > now()` 时拒绝。

2. **begin 是否查冷却**：方案只写 submit 查冷却，未写 begin 是否查。若 begin 不查，被拒用户冷却期内仍能开弹窗拿码（只是 submit 被拒）——不是安全洞，但应写清是「begin 也拦」还是「begin 放行、submit 拦」，否则两个实施者写法不一致。

3. **幂等衔接**：事实 #2——现有 `submit_payment_request` 是 `insert on conflict do nothing` + 读回。改造后，正常路径是「begin 已建 pending 行 → submit 需 UPDATE 该行置 claimed_at」，而「用户未开弹窗直接调 submit」路径下 insert 才生效。方案说「保留 on-conflict 幂等」但没写这条 UPDATE 及「重复点我已支付不重复置 claimed_at（`where claimed_at is null` 或 `coalesce`）」的幂等细节。

### ⚠️ 4.5 提交被直接调用（不经 begin）时 `verification_code` 为 NULL 的边界未处理（P2）

「发码即建单」假设 submit 恒尾随 begin。但 `submit_payment_request` 是公开的 authenticated RPC，用户可绕过弹窗直接调用。此时 insert 创建的行 `verification_code = NULL`、`claimed_at = now()`——admin 无码可核对，而这笔单还占用了互斥槽位。方案应规定 submit 要么「要求存在 begin 建的 open 单（无则报错）」，要么「submit 时若无码则补发码」。否则产生一类「无法核对、又堵住重提」的坏单。

### ⚠️ 4.6 「发码未提交」堆积单无清理机制 + 队列语义污染（P2）

01 §S1.2 只把「用户根本没打开过 App 就付款」标注为设计边界，但**漏了另一类更常见的情形**：用户开了弹窗、拿了码、**既不付款也不提交**就离开——这笔 `status='pending'`、`claimed_at=NULL` 的「发码未提交」单会**永久**留在库里，占着互斥槽位，并出现在 `admin_list_payment_requests` 的 pending 队列里制造噪声（admin 需要靠 claimed_at 才能区分「没提交」与「待核对」）。方案未提供任何清理/超时机制。

**建议**：至少写一条「begin 时对同用户已存在的『发码未提交且超 N 天未提交』旧单做复用或作废」的策略，或在后置清单注明「验证期靠人工忽略，正式接支付后加超时清理」。否则「发码即建单」会随时间累积大量孤儿 pending 单。

### ⚠️ 4.7 顺手修「refresh」的 premise 弱：submit 不授 Pro（P3）

01 §顺手修#1 声称「提交支付成功后调用 refresh()（提交后 Pro 状态/额度不刷新）」。但事实 #9：`submit_payment_request` 只建 pending 单，**不改变订阅身份**——提交时刻用户仍是 Free，`refresh()` 后 status 仍 free，几乎是无意义的空刷新。

真正的陈旧场景是「admin 确认发放后，长期挂载的 AuthPanel 徽标仍是 Free/『已提交待确认』」。当前 `useSubscription.refresh` 仅 mount 触发，该场景恰恰**没有被这次顺手修覆盖**。建议把顺手修改为「面板重新打开时 refresh」或「pending→granted 轮询/重拉」，至少修正措辞，避免实施者误以为空 refresh 解决了陈旧问题。

### ⚠️ 4.8 新函数需遵循仓库既有的 `revoke all + grant` / `set search_path` / `is_current_user_admin` 闸门（P3）

新迁移的两个新函数 `begin_payment_request`（用户侧）与 `admin_reopen_payment`（管理员侧）必须沿用既有模式（事实 #2/#6/#14 的迁移均如此）：
- `security definer set search_path = public`（否则 `auth.uid()`/`now()` 解析可能失效）；
- Postgres 新函数默认 `EXECUTE` 授 PUBLIC——必须显式 `revoke all ... from public, anon, authenticated` 再 `grant execute ... to authenticated`（否则 anon 可达，虽 `auth.uid()` 为 NULL 会拦，但违反仓库安全模式）；
- `admin_reopen_payment` 必须 `is_current_user_admin()` 闸门（否则任意登录用户可复位自己的冷却）。

02 §交付物只列了函数名，未列出这些伴随改动。建议在迁移交付物中显式补一句「沿用 revoke/grant/search_path/admin 闸门模式」，防止实施者漏 revoke。

### ⚠️ 4.9 PRICE_TEXT / PAID_DAYS 单一事实源只收敛前端，前端 vs DB 仍双源漂移（P3）

01 §后置清单已如实承认「本次仅收敛前端常量单一来源，迁移列默认值仍是硬编码 990/30」。但需点明：**收敛后仍存在两个事实源**——DB 列默认值（990/30）与前端常量（PRICE_TEXT/PAID_DAYS）。且现有 UI 已出现「价格用常量、天数用行」的混合（`PaymentRequestsPanel` 显示 `{PRICE_TEXT} / {r.requestedDays} 天`），一旦 admin 用 `p_days` 覆盖发放或改列默认值，展示即漂移。建议顺带把前端展示改为优先读行字段（`amountCents/requestedDays`），价格文案与天数都从 DB 行派生，才真正消除漂移；或明确接受双源并在注释中标出漂移风险。当前「单一事实源」的表述名不副实。

### ⚠️ 4.10 成本闸门目标下 `generate-recommendation.js` 未纳入（P3）

S2 的目标是「翻译接口（成本闸门）鉴权与限流」。但事实 #15：`generate-recommendation.js` 是**同样无鉴权**的 Netlify 函数，调用同一批 LLM provider，且单次输入上限 100000 字符、输出 4096 tokens，**比 translate 更昂贵**。若成本闸门的目的是堵住「匿名刷 LLM 烧钱」，这个端点仍是敞开的。它可能只在管理员/投稿流程触发（范围较小），但方案未说明为何排除。建议在 02 补一句「generate-recommendation 走管理员/投稿链路、非匿名可达，本轮不纳入」的边界说明，或纳入后置清单。

### ⚠️ 4.11 「直译永远在线」铁律在 IP 限流下靠 fallback 保在线，需写清（P3）

02 §关键口径「直译永远在线：阈值放宽、失败静默降级（回落既有 fallback）」。事实 #11 与 `directTranslation` 的 `translateDirectWithFallback`（L139-159）：直译路径被 IP 限流返回 429 时，客户端 `!res.ok` 抛错 → 落入 `fallbackProvider='myMemory'`（**不经 Netlify**，客户端直连）。因此「永远在线」实际是靠 myMemory fallback 保住的，而非「阈值放宽」本身。方案应如实写明「IP 限流只对 DeepL/有道生效，超限即回落到免费 myMemory，划词仍出结果但质量降级」，否则实施者可能误以为要在限流层做「永远不拒」，与限流目的矛盾。

### ⚠️ 4.12 冷却/互斥的「换号绕过」与 `admin_reopen` 「放水」为有意接受，需落笔（P3）

审计要点要求核验「冷却是否覆盖拒绝后换邮箱/换号绕过」。结论：**不覆盖**——`cooldown_until` 是 per-user，换新邮箱即得新 user、冷却归零。但这在三层模型下是**有意接受**的：冷却/互斥的目的是减少对 admin 的重复申请噪声，而非阻止发 Pro（发 Pro 的最终闸门是 admin 人工核对到账，换号拿不到到账记录也不会被确认）。同理 `admin_reopen_payment` 的「放水」是 admin 手动允许重试、本就有意为之。这两点应写进 01/02 的分析完备性，避免将来被当作漏洞重复讨论。

### ⚠️ 4.13 迁移后存量 pending 行的 `claimed_at` 语义回归（P3）

加列 `claimed_at timestamptz null`（无默认值）后，**迁移前已存在的 pending 行**（旧语义下用户已点「我已支付」）会全部落到 `claimed_at=NULL`，新代码据此判为「发码未提交」——与真实状态相反，admin 若依赖 claimed_at 区分，会误读这批在途单。验证期量小、靠邮箱+时间仍可核对，但建议在迁移中回填 `update payment_requests set claimed_at = created_at where status='pending' and claimed_at is null`（旧 pending 均视为已提交），消除语义回归。
