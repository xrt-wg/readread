# 付费核对与翻译接口鉴权 — 讨论和决策记录

> 日期：2026-09-25（修订 2026-09-26）
> 性质：需求与实现路径决策存档（非实施文档）
> 关联：[02_实施方案](02_实施方案.md) · [26_订阅机制/12_付费发放_验证期闭环](../26_订阅机制_2026-09-23/12_付费发放_验证期闭环.md)

## 定位

付费已在验证期以「扫码支付 + 管理员人工核对到账后发放」闭环跑通（26 §12）。本特性分两块：**S1** 加固这条付费核对的可靠性/防滥用（限流、核对码、发码即建单）；**S2** 加固翻译接口（成本闸门）的鉴权与限流。二者都**不改动订阅机制本身**，只在既有 `payment_requests` / `translate.js` 之上收紧闸门。

## 需求

1. **S1 付费核对加固**：三层限流（互斥 / 冷却 / 复位）、4 位核对码、发码即建单（消除孤儿支付）。
2. **S2 翻译接口鉴权限流**：LLM 精译路径 JWT 鉴权 + 按 `sub` 每用户限流；直译路径仅 IP 级限流、不设登录要求。
3. **顺手修**：支付提交后刷新订阅状态；`PRICE_TEXT` / `PAID_DAYS` 收敛单一事实源。

## 背景（既有代码事实）

- 订阅身份 = `subscriptions.pro_expires_at > now()` 派生，**无 enum 列**（`20260923000000_subscription_mechanism.sql` §1）。
- Pro 发放走 `pro_grants` 账本：`source in ('paid','contribution','admin')`、`submission_id` 幂等（贡献）、`external_ref` 预留（支付幂等键）。
- 付费为**验证期人工确认**闭环：贴收款码 → 用户付 ¥9.9 → 点「我已支付」→ 管理员核对到账后开通（`admin_confirm_payment` 累加 30 天，`source='paid'`、`external_ref=request_id`）。
- 既有 `payment_requests` 表已含部分唯一索引 `uq_payment_requests_open`（`(user_id) where status='pending'`），是 S1 三层限流的第一层。
- 翻译函数 `netlify/functions/translate.js` 的 handler（L142）**无鉴权、无限流**，任何人可免费调用 LLM 精译（`UPSTREAM_TIMEOUT_MS = 8000`）。
- 项目已有「配置可后台调」先例：`recommendation_submission_config` 单行表 + `admin_get_*`/`admin_save_*` RPC（乐观并发 + 审计）+ `RecommendationConfigPanel.jsx`。

## 决策

### S1.1 三个提案的裁决

1. **提案 3（自动先发 1 天 Pro 缓冲）—— 不做**。理由：绕过人工核对直接发身份，破坏「验证期人工确认」闭环，且与「身份 = 付费核对的唯一闸门」矛盾。
2. **限流 —— 用三层模型，不用「29 天一刀切」**：
   - 第一层 **互斥**：沿用现有 partial unique index `uq_payment_requests_open`（`(user_id) where status='pending'`）——同一用户同时只能有一单 pending。
   - 第二层 **冷却**：管理员拒绝后置 `cooldown_until = now() + interval '24 hours'`，冷却期内不可再提交；这是「人工确认延迟」下的防滥用主闸。
   - 第三层 **复位**：新增 `admin_reopen_payment()`，管理员清除冷却（对应「后台撤销申请可重新复位」）。**只清冷却、不翻 status**——用户重开弹窗自然走 `begin_payment_request` 拿新码，语义最简且避免与「核对码 partial unique index」撞唯一。
3. **核对码 —— 4 位数字，服务端生成，支付前展示**：
   - 服务端在**打开支付弹窗时**生成 4 位码（不是点「我已支付」才生成），因为用户在微信支付备注里填码，码必须先于支付被看到。
   - 码在弹窗关闭再打开时**保持稳定**（同一 open 单重复发码幂等返回同一码）。
   - 4 位码并发安全用 **partial unique index** `uq_payment_requests_open_code on (verification_code) where status='pending'` + 生成时 `on conflict do nothing` 冲突重生成兜底——**仅新建 open 单、生成新码时**做全局碰撞检查，幂等复用同一码走「已有 open 单」分支、不参与碰撞。（4 位码、万空间，约百笔活跃单时碰撞概率已近 50%，故必须用索引兜底而非无锁 SELECT-then-INSERT。）
   - 管理员核对口径：备注中的码 + 金额 ¥9.9 + 时间，三者匹配；核对码只作辅助定位，最终以邮箱 + 到账为准。

### S1.2 发码即建单（消除孤儿支付）

- 打开弹窗即调用 `begin_payment_request()` 建单并发码（`claimed_at` 为 NULL），此时状态为「发码未提交」。
- 用户点「我已支付」调用 `submit_payment_request()` 置 `claimed_at = now()`，进入 pending。
- 这样管理员即使面对「付了款但用户从未点我已支付」也能凭码定位到用户；唯一不可消除的剩余情形是「用户根本没打开过 App 就付款」（无码可发），文档如实标注为**设计边界**。
- **前端判别随之调整**：`status='pending'` 从发码即建单起即为真，「已提交」的 UI 判别必须由 `claimed_at != null` 驱动（而非 `status`），否则一开弹窗就把「我已支付」按钮藏掉、流程断掉。

### S1.3 数据模型变更（`payment_requests` 表）

- 新增三列：`verification_code text`、`claimed_at timestamptz null`、`cooldown_until timestamptz null`。
- 新增 partial unique index `uq_payment_requests_open_code on (verification_code) where status='pending'`。
- 存量 pending 行回填 `claimed_at = created_at`（旧语义下 pending 均视为已提交，消除列语义回归）。
- 不动既有 `uq_payment_requests_open`。

### S1.4 RPC 变更

- 新增 `begin_payment_request()`：打开弹窗建单发码；已有 open 单幂等返回同一码；**冷却期拦截**（返回 `cooldown_until` 供前端提示）。
- 修改 `submit_payment_request()`：校验冷却（读该用户**最近 rejected 行**的 `cooldown_until`，而非当前行）；`begin` 已建单时 `UPDATE ... SET claimed_at=now() WHERE claimed_at IS NULL`，被直调无 open 单时自建单并补码（消除 `verification_code=NULL` 边界）；重复提交不重置换。
- 修改 `admin_reject_payment()`：拒绝时置 `cooldown_until = now() + interval '24 hours'`。
- 新增 `admin_reopen_payment()`：只清 `cooldown_until`（不翻 status）+ 记 `audit_logs`。
- 修改 `get_my_payment_request()` / `admin_list_payment_requests()`：jsonb 返回补 `verificationCode`/`claimedAt`/`cooldownUntil`。

### S2 翻译接口鉴权（成本闸门加固）

- 现状：`translate.js` handler 无鉴权、无限流，任何人可免费调用 LLM 精译。
- 分层策略：
  - **LLM 精译路径**：要求 JWT 鉴权（HS256），按 `sub` 做每用户限流；验签失败返回 401。
  - **直译（划词）路径**：仅做 IP 级限流，**不做登录要求**——守住「划词直译永远在线」铁律。
- **计数后端 = 复用 Supabase（决策 A）**：新增 `translate_rate_limits` 表 + `consume_translate_quota(scope, scope_id, kind)` security-definer RPC，单条 upsert 原子递增（固定窗口），由 Netlify 函数以 **service_role** 直连调用。选型理由见「多方讨论」。
- **阈值后台可调**：新增 `translate_rate_limit_config` 单行表 + `admin_get_translate_rate_limit_config()`/`admin_save_translate_rate_limit_config(...)` RPC + 后台面板（沿用 `recommendation_submission_config` 先例，乐观并发 + 审计）。阈值存 DB、改配置即时生效，无需重部署函数。
- **失败语义**：LLM 路径 **fail-closed**（计数后端不可用 → 拒绝，防烧钱）；直译路径 **fail-open**（计数不可用 → 放行，保永远在线）。
- JWT 校验用 `jsonwebtoken`（显式 `algorithms: ['HS256']`，规避手写 crypto 的算法混淆风险），密钥为新增环境变量 `SUPABASE_JWT_SECRET`（与 Supabase 项目 JWT 密钥一致）。

### 顺手修（并入本次，不算独立需求）

1. **刷新修复（重定位）**：`submit` 只建 pending、**不授 Pro**，提交后 `refresh()` 是空刷。真正的陈旧场景是「admin 确认发放后，长期挂载的 AuthPanel 徽标仍是 Free/『已提交』」——而 `AuthPanel` 常驻不重挂载、`refresh` 仅 mount 触发，恰恰覆盖不到。改为：**面板重新打开时 / pending 期间轮询**刷新订阅与支付单状态。
2. **`PRICE_TEXT` / `PAID_DAYS` 单一事实源**：`paymentService.js` 里 `¥9.9`（L10）与 `30` 天（L11）硬编码，与 DB 列默认值（990/30）双源漂移。改为 **`begin_payment_request` 返回 `amountCents`/`requestedDays`，前端优先读行字段**，常量仅作兜底并注释漂移风险。

## 多方讨论

本讨论未组织多角色圆桌，仅就关键取舍达成一致：

- **「29 天一刀切」vs「三层模型」**：29 天一刀切简单但会误伤「管理员核对后允许重试」的正常路径，且把防滥用窗口与发放周期强耦合。三层模型把「互斥（唯一索引）、冷却（24h 可复位）、复位（admin 手动）」解耦，冷却只兜住「人工确认延迟」窗口、管理员可随时复位，粒度更贴验证期人工核对的实际操作，故取三层。
- **「1 天缓冲」做不做**：自动先发 1 天 Pro 缓冲能提升付费体验，但等于在人工核对之前就发出 Pro 身份，让「身份 = 付费核对唯一闸门」名存实亡，也打开「白嫖 1 天」的口子。验证期宁可牺牲体验也要守住闭环，故不做。
- **限流计数后端选型（S2）**：无状态 Netlify 函数无跨请求跨实例的持久化计数器。三选一——外部 KV/Redis（要另养服务）、内存 Map+TTL（冷启动清零、多实例不共享）、**复用 Supabase 计数表**（现成、精确、与既有 `consume_*` 原子计数同构）。取 Supabase：项目全栈已在 Supabase 上，「翻译次数」与「收藏额度」同类，无需引入新依赖面；代价是函数层引入 service_role 直连这一新信任边界（可接受——函数只暴露「计数递增 + 是否超限」，爆炸半径小）。

## 分析完备性（有意接受的风险，落笔防重复讨论）

- **换号绕过 / 冷却不覆盖**：`cooldown_until` 是 per-user，换新邮箱即得新 user、冷却归零。但冷却/互斥的目的是减少对 admin 的重复申请噪声，**不是**阻止发 Pro——发 Pro 的最终闸门是 admin 人工核对到账，换号拿不到到账记录也不会被确认。属有意接受。
- **`admin_reopen_payment` 的「放水」**：管理员手动允许重试，本就有意为之，非漏洞。
- **直译「永远在线」的实现**：IP 限流只对 DeepL/有道生效，超限返回 429 时客户端回落免费 myMemory（不经 Netlify）——「永远在线」实靠 fallback 保住，质量降级但不断线。

## 后置清单

- 支付回调 / 到账自动核验（验证期仍靠人工核对，接正式支付时必办，沿用 26 §5）。
- `generate-recommendation.js` 鉴权（同为无鉴权昂贵 LLM 端点；本轮不纳入——它走投稿/管理员链路、非匿名可达，范围小，留待成本闸门二期）。
- 「发码未提交」超时清理（`begin` 复用已有 open 单，堆积仅限「永不回来」的用户；验证期靠 admin 人工忽略，正式接支付后加 TTL 清理）。
- S2 限流阈值成本观测与调优（阈值入后台配置后，上线按成本调档）。
- 直译路径若后续观察到成本异常，再评估是否加「匿名每日上限」而不破坏永远在线。
