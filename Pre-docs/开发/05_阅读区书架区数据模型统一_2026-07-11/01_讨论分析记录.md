# 阅读区与书架区数据模型统一 — 讨论分析记录

> 日期：2026-07-11
> 参与：Kaven, Claude

## 一、调查背景

本次讨论的前置工作是对当前代码库中阅读区、书架区、内容条目、阅读数据的数据模型进行全面调查。调查结论见下文第二节。

## 二、现状分析

### 2.1 当前数据模型

系统存在两张核心内容表：

**`public.import_items`（书架区）**

| 关键字段 | 说明 |
|---|---|
| `id` | `imp_<timestamp>_<random5>` |
| `sections` | jsonb，内容章节数组 |
| `format` | url / epub / pdf / paste / markdown / html |
| `kind` | 自动推断：epub → book，其他 → article |
| `origin` | imported / shared / featured / featured_legacy |
| `share_source_id` | 指向 recommendation_submissions.id |

**`public.articles`（阅读区）**

| 关键字段 | 说明 |
|---|---|
| `id` | `doc_<timestamp>_<random5>`（新版）或 `art_` 前缀（旧版） |
| `sections` | jsonb，从 import_items 深拷贝而来 |
| `source_import_id` | 回链到 import_items（可空） |
| `kind` | article 或 book |

**阅读数据表：**

- `public.bookmarks` — 书签（含翻译、间隔重复数据），FK → articles.id
- `public.reading_marks` — 阅读进度（复合 PK: user_id + article_id），FK → articles.id

### 2.2 三区架构

```
ImportItems (书架区)  ──copyToReadingZone──▶  Articles (阅读区)  ──ReaderPage──▶  阅读数据
   import_items          深拷贝 sections        articles                    bookmarks + reading_marks
```

### 2.3 识别的问题

| # | 问题 | 说明 |
|---|---|---|
| P1 | **两表字段高度重合** | title, author, format, cover_url, lang, sections, source_url, kind 完全重复 |
| P2 | **用增删实体模拟状态变化** | 取书 = 创建 article + 深拷贝 sections；还书 = 删除 article。同一本书变成两个数据库实体 |
| P3 | **阅读数据挂在错误的对象上** | bookmarks 和 reading_marks 的 FK 指向 article（临时副本），article 被删除时阅读数据面临丢失风险 |
| P4 | **还书动作缺失** | 只有 copyToReadingZone（单向），没有对应的「移回书架」操作 |
| P5 | **编辑隔离的原始动机值得商榷** | 深拷贝的初衷是防止编辑影响阅读，但阅读器没有任何修改原文的入口（只有划线和翻译），且需重新审视编辑需求 |

## 三、核心理念对齐

### 3.1 情景式设计

功能不是抽象满足，而是在**特定情景下的特定满足**。追求在最合适的地方以最自然的方式让该发生的事情发生。

### 3.2 物理世界隐喻

- **书架是放书的**，阅读区是阅读的，不是堆书或管理书的
- 阅读区除了在读的书，其他书都放在书架上
- 一本书读完了或不读了，自然要放回书架
- 用户可以从书架上取已读过的书继续阅读，也可以清除数据重新阅读

### 3.3 阅读区的设计初衷

让阅读不受打扰地发生——专一化、极简化满足，最大地保护阅读本身不受打扰。

### 3.4 阅读区 = UI 概念，不是数据概念

书架区和阅读区的区分是**用户在特定情景下看到什么、能做什么**，不是数据存在哪里。两区是同一个物品在不同情景下的不同呈现。

## 四、核心分歧与辨析

### 4.1 单模型 vs 双模型

**问题**：是否需要 `import_items` 和 `articles` 两张表？

**分析**：
- 双模型用增删实体模拟状态变化——取书创建 article，还书删除 article。这是一种迂回。
- 书籍在书架和手上是同一本书，双模型破坏了这种同一性。
- 阅读区本质上只是一个过滤条件 `WHERE reading_status = 'reading'`。

**结论**：统一为单表，用状态字段的枚举转换表达流转，UI 层表达情景差异。

### 4.2 阅读数据应该挂在哪里

**问题**：bookmarks 和 reading_marks 的 FK 指向 readings 还是某次阅读会话？

**分析**：
- 物理隐喻下，笔记是写在书上的——折角、划线、批注跟着书走
- 用户在书架和阅读区之间来回流转时，阅读痕迹应该毫发无伤
- 「多次独立阅读记录」在产品里不成立，因为 D3 决定了重新阅读是显式的清除动作

**结论**：阅读数据直接挂在 readings 上，不挂在某次阅读会话上。

### 4.3 location 字段是否必要

**问题**：是否需要独立的 `location` 字段与 `reading_status` 配合？

**分析**：

| reading_status | location |
|---|---|
| unread | 书架 |
| reading | 阅读区 |
| in_progress | 书架 |
| completed | 书架 |

`location = '阅读区'` 当且仅当 `reading_status = 'reading'`。不存在两个字段才能表达的合法状态。双字段引入同步负担和不一致风险。

**结论**：只用 `reading_status` 一个字段。阅读区 = `WHERE reading_status = 'reading'`，书架 = 其余。

### 4.4 编辑隔离策略

**问题**：合并为单表后，如何保证阅读期间内容的稳定性？

**分析**：编辑操作对阅读数据的影响程度不同：

| 类型 | 操作 | 威胁 |
|---|---|---|
| 元数据编辑 | 修改标题、作者、封面 | 无 |
| 内容编辑 | 修改 sections、增删章节、调整段落 | paragraph_index、char_offset、section_id 可能错位 |

讨论中提出了三种策略：
- A. reading 状态下禁止编辑
- B. 编辑即自动放回
- C. 客户端快照隔离

最初提出「副本策略」（非 unread 状态编辑时先创建副本再更新），但存在两个问题：
1. reading 状态下编辑会产生并发矛盾——阅读区渲染旧版本，编辑产生新版本，阅读数据归属混乱
2. in_progress/completed 下改一个错别字也要牺牲所有笔记，过度保护

**结论**：分情景处理（见决策记录 D7）。

## 五、关键推演

### 5.1 语义命名分歧

- 「读过」用于描述未读完的书在中文里天然带有「已完成」的意味 → 改为「未读完」（in_progress）
- 表名 `books` 与 `kind = 'book'` 冲突 → 改为 `readings`（阅读内容）

### 5.2 书架信息架构

三种状态的书籍在书架上的功能角色不同：
- **unread**：用户需要预览信息（"这本书讲的什么？值得读吗？"）
- **in_progress**：用户需要进度信息（"我读到哪了？还差多少？"）
- **completed**：用户需要回顾信息（"这本书讲了什么？我当时的评价？"）

三种状态的卡片信息层级不应相同，排序应为 in_progress > unread > completed。
