## 四、详细分析

### 🟡 I1 · `init_reading_status.sql` 可能突破阅读区上限

**SQL**（`20260712000000_init_reading_status.sql`）：
```sql
UPDATE public.readings
SET reading_status = 'reading', ...
WHERE reading_status IN ('unread', 'in_progress')
  AND deleted_at IS NULL;
```

将所有 unread + in_progress 的书**全部**转入 reading 状态，不检查数量上限。

**影响**：
- D1 决策规定阅读区上限 N=5，此 SQL 可能使存量用户同时持有数十本 "reading" 状态的书籍
- `start_reading` RPC 的 `SELECT ... FOR UPDATE` 检查仅对**后续取书**生效——存量数据不受限
- 前端 `listReadingZone()` 会返回所有 reading 状态的书籍，阅读区 Tab 可能展示远超 5 本

**评估**：本迁移的目的是解决「迁移后 reading_status 无 `reading` 状态」的问题。但全量转入过于激进。更精准的方案应限制转入数量（如每人最多 5 本最新的 in_progress）。

**建议**：考虑补充一个修正 migration，将超出上限的 reading 状态书转回 in_progress：
```sql
-- 每人保留最新 5 本 reading，其余转回 in_progress
WITH ranked AS (
  SELECT id, user_id,
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY updated_at DESC) AS rn
  FROM public.readings
  WHERE reading_status = 'reading' AND deleted_at IS NULL
)
UPDATE public.readings r
SET reading_status = 'in_progress', updated_at = now()
FROM ranked
WHERE r.id = ranked.id AND ranked.rn > 5;
```

### 🟡 I4 · ReaderPage.jsx 引用已 DROP 的 `import_items` 表

[ReaderPage.jsx:141-166](src/components/ReaderPage.jsx#L141-L166)：
```js
if (!article.sourceImportId) return                  // ← 现在总为 undefined，必然 return
// ...
const { data: item } = await client
  .from('import_items')                                // ← 此表已被 DROP
  .select('id, origin, share_source_id')
  .eq('id', article.sourceImportId)
```

**当前安全性**：
- `article.sourceImportId` 在 `mapReadingRow` 中不设置 → 始终 `undefined`
- `if (!article.sourceImportId) return` 在 L141 必然触发 → 后续代码永不执行
- 最坏情况（被意外触发）：错误被 `catch (_) { /* 非致命 */ }` 吞没

**结论**：不是运行时 bug，但是引用已删除表的死代码，增加维护困惑。

**建议**：删除 L128-166 的整个 fallback 逻辑块（含 TODO 注释）。推荐评分已通过 L132-139 的 `article.origin` 路径正确实现。
