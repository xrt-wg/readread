### 2.3 风险与缓解

| 风险 | 缓解措施 |
|---|---|
| 数据迁移时某些 article 的 source_import_id 指向不存在的 import_item | migration 中用 LEFT JOIN + NULL 检查，将孤儿 article 作为独立 reading 处理（情况 B） |
| reading_marks 复合 PK 冲突 | Step 6 的去重逻辑确保每个 (user_id, reading_id) 只保留一条 |
| import_items.user_id 无 CASCADE，合并后改为 CASCADE 可能暴露旧数据问题 | migration 前检查是否有已删除 profile 的孤儿 import_items |

### 3.2 状态流转的防御性编程

`startReading` 函数需包含以下检查：

```
检查项：
1. reading 存在且未删除
2. reading.readingStatus !== 'reading'（不能重复取书）
3. 当前活跃 reading 数量 < N（上限检查）
4. 如果 reading.readingStatus === 'unread'，set reading_started_at = now()
5. 如果 reading.readingStatus === 'in_progress'/'completed'，保留原有 reading_started_at
```

`returnToShelf` 函数需包含以下检查：

```
检查项：
1. reading 存在且未删除
2. reading.readingStatus === 'reading'（只能还正在读的书）
3. completed=true → 状态 'completed'，set reading_finished_at = now()
4. completed=false → 状态 'in_progress'
```

## 八、回滚计划

### 8.1 回滚触发条件

- Phase 1 migration 执行后数据完整性校验失败
- Phase 2/3 重构后发现不可接受的回归
- 生产环境上线后出现数据丢失或不一致

### 8.2 各阶段回滚方案

**Phase 1 后回滚**：
1. articles 和 import_items 表未被删除，数据完好
2. 删除 readings 表 `DROP TABLE public.readings CASCADE`
3. 前端代码回退到旧版本

**Phase 2/3 后回滚**：
1. 代码回退到 Phase 1 前的版本（library.js + importItems.js 原版）
2. 数据库保持 Phase 1 状态（readings 存在 + 旧表存在）
3. 或执行 DROP readings + 删除新 RPC 的 migration

**Phase 4 后回滚（最坏情况）**：
1. articles 和 import_items 已被删除
2. 需要通过数据库备份恢复
3. Phase 4 执行前务必确认有可用的数据库备份

### 8.3 回滚安全线

**Phase 4 是回滚的不可逆点**。在此之前（Phase 1-3），旧表未被删除，可以安全回退。建议：

- Phase 1-3 在 staging 环境充分验证
- Phase 4 在生产环境验证通过至少 24 小时后再执行
- Phase 4 执行前创建数据库完整备份

## 十一、关键风险与缓解

| # | 风险 | 等级 | 缓解 |

| 6 | localStorage 兼容性问题 | 低 | rr_articles key 保持不变，数据格式不变，仅 JS 属性命名变更（通过 row mapper 隔离） |
| 7 | 推荐系统引用断裂 | 中 | recommendationService.js 在 Phase 2 早期适配，Phase 3 端到端验证覆盖完整推荐闭环 |
