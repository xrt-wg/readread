## 二、事实性错误

### ❌ F1 · R12 声称的 bug 不存在（风险分析报告 §R12）

**R12 原文**：
> `IMPORT_ITEM_COLUMNS` SELECT 列表中不包含 `kind`，但 `mapImportItemRow` 中却读取了 `row.kind || 'article'`。由于 kind 不在 SELECT 中，`row.kind` 始终为 undefined，fallback 总是生效——所有 import_items 在前端都被映射为 `kind: 'article'`，即使数据库中的正确值是 `'book'`

**代码实测**（[importItems.js:15](src/services/importItems.js#L15)）：
```js
const IMPORT_ITEM_COLUMNS = 'id, user_id, title, author, format, cover_url, lang, source_url, sections, total_word_count, section_count, kind, origin, share_status, share_source_id, created_at, updated_at, deleted_at'
```

**`kind` 在 SELECT 列表中**。`row.kind || 'article'` 是防御性编程——处理旧数据中 kind 为 NULL 的边界情况（数据库列定义有 `DEFAULT 'article'`，但历史数据可能缺失）。这不是 bug。

**影响**：
- R12 的错误结论「建议在合并重构时一并修复」——无需操作
- 风险分析报告中对"两个已识别的独立 bug"（§8.3 第 6 点，R11+R12）的引用需修正——实际只有 R11 一个有效的代码卫生问题（蛇形命名耦合）

**建议**：在 03_风险分析报告.md 中修正 R12 的结论，或降级为「防御性代码，无需处理」。

## 四、方案缺陷

### 🔴 D1 · 迁移 SQL 的 article_info CTE 设计有缺陷（04_实施方案 Step 4）

```sql
WITH article_info AS (
    SELECT
        a.source_import_id,
        a.id AS article_id,
        ...
    FROM public.articles a
    LEFT JOIN public.reading_marks rm
        ON rm.article_id = a.id AND rm.user_id = a.user_id
    WHERE a.source_import_id IS NOT NULL
      AND a.deleted_at IS NULL
)
UPDATE public.readings r
SET ...
FROM article_info ai
WHERE r.id = ai.source_import_id
  AND r.user_id = (SELECT a.user_id FROM public.articles a WHERE a.id = ai.article_id LIMIT 1);
```

**问题**：
1. CTE 未包含 `user_id`，迫使 UPDATE 使用低效的 correlated subquery
2. 若 `source_import_id` 在极端情况下跨用户冲突（虽然概率极低但理论存在——import_items.id 含随机数，但不能保证全局唯一），subquery 会错误匹配

**修正**：
```sql
WITH article_info AS (
    SELECT
        a.source_import_id,
        a.user_id,           -- ← 加入 CTE
        ...
    FROM public.articles a
    ...
)
UPDATE public.readings r
SET ...
FROM article_info ai
WHERE r.id = ai.source_import_id
  AND r.user_id = ai.user_id;   -- ← 直接 JOIN，无需 subquery
```

### 🔴 D2 · 阅读区上限 N=5 仅客户端检查，无服务端约束（04_实施方案 §3.1）

`startReading()` 函数通过先查询活跃 reading 数量再判断是否超限来实施 D1 决策。但这是典型的 **check-then-act 竞态条件**——两个客户端/标签页同时取第 5 本书时，各自查询到的活跃数量都是 4，都能通过检查，最终活跃 reading 变成 6。

**建议**（三选一）：
- **方案 A（推荐）**：将 `startReading` 逻辑封装为 RPC，使用 `SELECT ... FOR UPDATE` 或 advisory lock
- **方案 B**：在 readings 表上使用 partial unique index：`CREATE UNIQUE INDEX ON readings (user_id) WHERE reading_status = 'reading' AND reading_count > N` ——但 PostgreSQL 不支持带聚合的 partial index，此方案不可行
- **方案 C（务实）**：接受极小概率的竞态（同一用户几乎不会在两个设备上同时取书），但至少应在 RPC 中以原子方式检查

**补充**：当前代码库中 library.js 未找到任何 `MAX_ACTIVE` 或 reading limit 的实现——说明这是全新功能，应在服务端正确处理而非仅客户端检查。

### 🟡 D3 · `get_reading_for_recommendation` RPC 仍引用 `recommendation_submissions.import_item_id`（04_实施方案 Step 8）

```sql
WHERE rs.import_item_id = p_reading_id AND rs.status = 'active'
```

`recommendation_submissions` 表的列名 `import_item_id` 在迁移后语义过时（指向 readings 而非 import_items）。虽然功能上因为 ID 保留策略而正常工作，但这是技术债的延续。

**建议**：在 Phase 4 中增加 `recommendation_submissions.import_item_id → reading_id` 的重命名（或至少记录为已知技术债）。

### 🟡 D4 · 迁移只处理 `deleted_at IS NULL` 的数据，软删除记录被忽略（04_实施方案 Step 3-4）

两个 INSERT 都过滤 `WHERE deleted_at IS NULL`。这意味着：
- 已被软删除的 import_items 和 articles **不会**被迁移到 readings 表
- 如果 bookmarks/reading_marks 指向已软删除的 articles，Step 5 的 FK 重定向会因 `a.deleted_at IS NULL` 条件而跳过它们，导致 FK 约束建立失败

**建议**：
- 评估生产环境中是否有软删除记录需要迁移（可能需要保留用于审计/恢复）
- 明确文档化：软删除记录的处理策略——是丢弃还是迁移（reading_status = 'unread' + deleted_at 保留）
- 至少处理指向已删除 article 的 bookmarks/reading_marks，避免 FK 建立失败

## 五、分析缺失

### 📋 M1 · 回顾区（Review Zone）与统一模型的关系未分析

Git 提交记录显示最近有「回顾区UX全面重构」，且 ImportPage 的 Tab 中有"回顾"。但全部 5 份文档中，对回顾区的分析仅限于 R21（「ReviewPanel 无影响」）。

**缺失的分析**：
- 回顾区的数据来源是什么？是 bookmarks 的聚合视图还是独立数据？
- 统一模型后，回顾区的查询路径是否变化？
- `reading_status = 'completed'` 的书籍在书架上的「回顾」功能与回顾区 Tab 的关系是什么？

### 📋 M2 · 书架与阅读区 Tab 在 ImportPage 中的交互未完整设计

D4 决策采用 Tab 分组（unread / in_progress / completed），但以下交互细节缺失：

- 阅读区 Tab（当前展示 articles 列表）合并后如何呈现？是保留独立 Tab 还是融入书架？
- 阅读区 Tab 中已取出的书（reading_status = 'reading'）在书架 Tab 中是否可见？如果可见，展示什么状态？
- 回顾 Tab 是否受影响？

04_实施方案 §4.1 提到「书架 Tab：shelfReadings」和「阅读 Tab：activeReadings」，但没有说明两者之间的导航关系（用户从阅读 Tab 点击一本书进入 ReaderPage，读完后返回——看到的是哪个 Tab？）。

### 📋 M3 · 编辑策略中「sections 编辑影响提示」的具体实现未定义

D7 决策：
> in_progress 状态：元数据直接编辑；内容编辑做影响提示后执行。提示：「此操作可能影响阅读进度和书签位置」

但以下问题未被讨论：
- 提示后用户确认了，具体怎么处理？bookmarks 中的 `paragraph_index`、`char_offset`、`section_id` 可能需要批量失效或重新映射
- 如果 sections 的结构变化很小（修正一个错别字），所有书签都被清除是否过度？
- 如果 sections 结构变化很大（增删章节），书签如何保留？

04_实施方案 §3.1 的 `updateReading` 函数只写了注释「内容编辑（sections）做影响提示」，但无具体处理逻辑。

## 六、其他发现

### 建议项

1. **Doc 03 R11（蛇形命名耦合）**：确认为真实技术债，合并时自然消除。建议在代码清理时一并检查是否还有其他 snake_case/camelCase 混用的隐式耦合。

2. **Phase 4 列重命名应为强制而非可选**：bookmarks 和 reading_marks 保留 `article_id` 列名但指向 readings 表，是永久性的认知负担。建议将 Phase 4.5/4.6 从「可选」升级为「推荐」或「必做」。

3. **Silent migration 更新可跳过**（05_执行计划 任务 2.8）：迁移窗口已于 2026-06 关闭（03_风险分析 R15/R22/R26 已确认），更新 migration 服务代码的投入产出比低。建议将任务 2.8 降级为「确认无影响后跳过」或直接移除。

4. **建议在 Doc 05 中补充：Phase 3 每一步的独立回滚验证方式**。虽然 §4.3 提到「每一步都可以独立提交和回滚」，但没有具体说明如何验证单步回滚后的系统状态。

5. **测试数据准备脚本（任务 1.2）应覆盖的边界场景建议**：
   - 同一 import_item 有多个 article（多次取书-还书循环，应只保留最新状态）
   - bookmark 的 article 已被软删除
   - reading_marks 存在但 articles 已被软删除
   - 用户 A 的 article 的 source_import_id 指向用户 B 的 import_item（共享推荐场景）
   - kind 为 NULL 的历史数据

6. **建议考虑 `reading_started_at` 和 `reading_finished_at` 的时区语义**：使用 `timestamptz` 是正确的，但需确认 `now()` 在 Supabase 中返回的是 UTC 还是 session 时区。
