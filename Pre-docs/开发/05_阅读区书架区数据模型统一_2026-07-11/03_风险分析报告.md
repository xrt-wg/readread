## 二、数据库层风险

### R1 · bookmarks 和 reading_marks 的复合 FK 重定向

- **位置**：`supabase/migrations/20260509170000_create_core_user_tables.sql`
- **当前行为**：两张阅读数据表均定义了复合外键 `(user_id, article_id) REFERENCES public.articles(user_id, id) ON DELETE CASCADE`
- **影响**：合并为 `readings` 表后，FK 目标需变更为 `readings(user_id, id)`。这不是简单的表名替换——迁移过程中旧数据先迁移到新表，FK 才能建立。需要在新 migration 中先创建表、迁移数据、再建立 FK
- **风险等级**：🔴 高
- **可控性**：可控。FK 可在数据迁移完成后通过 ALTER TABLE ADD CONSTRAINT 建立。需要验证迁移后的数据完整性（所有 bookmark.reading_id 和 reading_mark.reading_id 在 readings 表中存在）

### R2 · delete_import_item RPC 的双表原子操作

- **位置**：`supabase/migrations/20260614000003_create_delete_import_item_rpc.sql`
- **当前行为**：SECURITY DEFINER 函数，先 `UPDATE articles SET source_import_id = NULL WHERE source_import_id = p_import_item_id`，再软删除 import_items。返回受影响的 article 数量
- **影响**：合并后不再有跨表 NULL 操作。该函数简化为单表软删除。但调用方 `ImportPage.jsx` 中的 `handleDeleteImportItem` 依赖返回值来判断删除确认文案——需同步修改
- **风险等级**：🔴 高
- **可控性**：可控。新 RPC 逻辑更简单（单表 UPDATE SET deleted_at），但需要与前端删除流程联动修改。推荐先改 RPC、再改前端、最后清理旧 RPC

### R3 · check_import_item_reading_completed RPC 的三表 JOIN

- **位置**：`supabase/migrations/20260616000006_create_recommendation_rpc_functions.sql`
- **当前行为**：三表 JOIN——`articles JOIN reading_marks ON rm.article_id = a.id WHERE a.source_import_id = p_import_item_id AND rm.completed = true`
- **影响**：合并后简化为两表 JOIN——`readings JOIN reading_marks ON rm.reading_id = readings.id WHERE readings.id = p_reading_id AND rm.completed = true`。逻辑等价但查询路径变更
- **风险等级**：🟡 中
- **可控性**：可控。这是功能等价的简化，只需同步更新函数体内的表名和 JOIN 条件。调用方 `recommendationService.js` 无需改动（RPC 接口不变）

### R4 · increment_recommendation_add_count RPC 的 import_items 计数

- **位置**：`supabase/migrations/20260616000006_create_recommendation_rpc_functions.sql`
- **当前行为**：`SELECT COUNT(*) FROM import_items WHERE share_source_id = p_submission_id AND origin IN ('featured', 'featured_legacy')`
- **影响**：查询目标变更为 `readings` 表。origin 字段需迁移到 readings 表中。语义不变
- **风险等级**：🟡 中
- **可控性**：可控。纯粹的表名和字段引用替换。函数接口不变

### R5 · get_import_item_for_recommendation RPC 的跨用户读取

- **位置**：`supabase/migrations/20260616000006_create_recommendation_rpc_functions.sql`
- **当前行为**：SECURITY DEFINER 函数，绕过 RLS 读取其他用户的 import_item（通过 recommendation_submissions 的存在性做访问控制）
- **影响**：读取目标从 `import_items` 变为 `readings`。这是跨用户读取——合并表后，RLS 策略必须允许此 RPC 绕过行级安全（已是 SECURITY DEFINER，无需额外调整）
- **风险等级**：🟡 中
- **可控性**：可控。函数已是 SECURITY DEFINER，合并后保持该属性即可。需确认 readings 表的 RLS 策略不阻止此函数的操作

### R6 · import_items 的 NO CASCADE FK 与 profiles 的 CASCADE FK

- **位置**：`supabase/migrations/20260614000001_create_import_items.sql`
- **当前行为**：`import_items.user_id REFERENCES profiles(user_id)` 无 ON DELETE 子句，意味着删除 profile 会因 FK 约束而失败（除非先手动清理 import_items）。这与 `articles.user_id ON DELETE CASCADE` 行为不一致
- **影响**：合并为 readings 后必须统一策略。推荐 ON DELETE CASCADE（与 articles 当前行为一致，语义上正确——删除用户应清除其所有阅读内容）
- **风险等级**：🟡 中
- **可控性**：可控。合并后的 migration 中显式指定 CASCADE。需注意：如果生产环境已有被软删除用户的 import_items 孤儿记录，迁移时需处理

### R7 · recommendation_submissions.import_item_id 的软引用

- **位置**：`supabase/migrations/20260616000002_create_recommendation_submissions.sql`
- **当前行为**：`import_item_id text NOT NULL`，无 FK 约束，纯文本引用 `import_items.id`
- **影响**：合并后指向 `readings.id`。由于无 FK 约束，无数据库层面的级联依赖。但需要迁移已有数据的引用（如果原 import_items 的 ID 在合并时发生变化）。如果使用直接迁移策略（import_items.id 保留为 readings.id），则无需修改
- **风险等级**：🟢 低
- **可控性**：完全可控。无 FK 约束意味着无数据库层面的修改需求。需确认迁移策略中 import_items.id 的保留方案

### R8 · 20+ 个索引的重建

- **位置**：分布在 21 个 migration 文件中
- **影响**：合并后需要为新 readings 表创建对应索引。条件索引 `idx_articles_source_import` (WHERE source_import_id IS NOT NULL) 可完全移除。其余索引需要以 readings 表名为目标重建
- **风险等级**：🟢 低
- **可控性**：完全可控。是标准 DDL 操作，在新的 migration 文件中集中创建即可

### R9 · RLS 策略的统一

- **位置**：articles 和 import_items 各自的 migration 文件
- **当前行为**：
  - articles RLS：SELECT (deleted_at IS NULL), INSERT, UPDATE (deleted_at IS NULL)。无 DELETE
  - import_items RLS：SELECT, INSERT, UPDATE。无 DELETE
- **影响**：合并后统一为 readings RLS。两者的策略高度一致（所有者只能操作自己的行），合并无冲突。需决定 SELECT 是否过滤 deleted_at（articles 过滤，import_items 不过滤——但 import_items 有删除 RPC，软删除后应过滤）
- **风险等级**：🟢 低
- **可控性**：完全可控。策略一致性高，合并后只需在一个新 migration 中统一定义

### R9b · 软删除记录的迁移策略（审核补充）

- **位置**：04_实施方案 Step 3-4 的 INSERT 语句
- **当前行为**：实施方案中的 INSERT 均过滤 `WHERE deleted_at IS NULL`，即只迁移活跃记录。软删除的 import_items 和 articles 被丢弃
- **影响**：
  1. 若生产环境存在软删除记录，它们将丢失（无法恢复）
  2. 若 bookmarks 或 reading_marks 引用了已软删除的 article，且该 article 的 source_import_id 指向某 import_item，Step 5 的 FK 重定向会因 `WHERE a.deleted_at IS NULL` 条件跳过该 article，导致 Step 7 建立 FK 时约束失败
- **风险等级**：🔴 高（可能导致 migration 执行失败）
- **可控性**：可控。策略：INSERT 语句移除 `WHERE deleted_at IS NULL` 条件，软删除记录一并迁移（保留 deleted_at 值）。同时 Step 5 的 UPDATE 条件也需相应调整以覆盖软删除 article。若生产环境无软删除记录则无实际影响

## 三、服务层风险

### R10 · copyToReadingZone 的函数消除——核心桥梁

- **位置**：[importItems.js:237-273](src/services/importItems.js#L237-L273)
- **当前行为**：这是整个双表模型的代码核心。从 importItem 深拷贝 sections → 调用 createDocument 生成新 ID → 设置 source_import_id 和 imported_at → 调用 saveArticle 写入 articles 表
- **影响**：
  - 函数本身被消除，取而代之的是 readings 表上的状态更新（reading_status: 'unread' → 'reading'）
  - `structuredClone(sections)` 的深拷贝逻辑被消除——不再需要，sections 只有一份
  - 调用方 `ImportPage.jsx` 的 `handleMoveToReading` 需要完全重写
- **风险等级**：🔴 高
- **可控性**：可控但需精心设计。消除此函数是整个重构的核心目标，逻辑上由"创建实体"变为"更新字段"，复杂度大幅降低。风险在于所有调用方必须同步更新

### R11 · saveArticle 中 source_import_id 的蛇形命名耦合

- **位置**：[library.js:206-207](src/services/library.js#L206-L207)
- **当前行为**：
  ```js
  source_import_id: article.source_import_id ?? null,
  imported_at: article.imported_at ?? null,
  ```
  这两个字段使用 snake_case key 直接访问 document 对象的属性，而 saveArticle 中其他所有字段都使用 camelCase。这之所以能工作，仅仅因为 copyToReadingZone 在 Document 对象上手动设置了这两个 snake_case 属性（[importItems.js:266-267](src/services/importItems.js#L266-L267)）
- **影响**：这是隐藏最深的技术债。合并后 source_import_id 和 imported_at 字段被消除，这个隐式耦合自然解决。但如果在消除 copyToReadingZone 之前先修改 saveArticle，可能导致其他路径的 article 保存行为变化（尽管这些字段在其他路径中始终为 undefined/null）。风险低但值得记录
- **风险等级**：🟢 低（非功能性风险，属代码卫生问题，合并时自然消除）
- **可控性**：不需要单独处理。合并后该代码被移除

### R12 · importItems.js 中 kind 列的防御性 NULL 处理（经核实不是 bug）

- **位置**：[importItems.js:15](src/services/importItems.js#L15)，[importItems.js:31](src/services/importItems.js#L31)
- **当前行为**：`IMPORT_ITEM_COLUMNS` SELECT 列表中**确实包含 `kind`**（经代码核实）。`mapImportItemRow` 中的 `row.kind || 'article'` 是防御性编程——处理历史数据中 kind 为 NULL 的边界情况（数据库列定义有 `DEFAULT 'article'`，但迁移前创建的旧数据可能缺失默认值）
- **影响**：无 bug。合并后的服务层可保留此防御性写法，确保 NULL-safe 映射
- **风险等级**：🟢 无风险（防御性代码，无需处理）
- **可控性**：无需单独处理

### R13 · recommendationService.js 的全量 import_items 引用

- **位置**：[recommendationService.js](src/services/supabase/recommendationService.js) — 708 行，引用散落在多个函数中
- **当前行为**：
  - `findImportItemByShareSource`：查询 import_items 表
  - `checkReadingCompleted`：调用 RPC，间接依赖 import_items
  - `checkSubmissionEligibility`：查询 import_items 表
  - `checkRatingEligibility`：查询 import_items 表
  - `submitRecommendation`：读取和更新 import_items
  - `addRecommendationToBookshelf`：通过 RPC 读取 + createImportItem 写入
  - `syncAddCountAfterDelete`：读取 importItem.origin/sharedSourceId
  - `migrateLegacyFeaturedArticles`：直接 INSERT 到 import_items
- **影响**：所有 `.from('import_items')` 变更为 `.from('readings')`。`createImportItem` 调用变更为统一的 readings 创建函数。`updateImportItem` 调用变更为 readings 更新。函数逻辑本身不变——只是数据源变更
- **风险等级**：🔴 高
- **可控性**：可控。引用虽多但模式统一——全部是表名替换和函数签名变更。`addRecommendationToBookshelf` 是其中最复杂的函数（跨用户深拷贝 + 创建），但合并后逻辑反而简化（无需先建 import_item 再等用户 copyToReadingZone）

### R14 · countImportReferences 参考计数的消除

- **位置**：[importItems.js:199-212](src/services/importItems.js#L199-L212)
- **当前行为**：查询 articles 表中 source_import_id 匹配的活跃行数，用于 ImportItemList 中展示"已被 n 次阅读"和删除确认文案
- **影响**：合并后没有独立的 articles 表可以计数。如果仍需要展示"阅读次数"或"阅读状态"，应从 reading_marks 读取。或者这个信息在合并后的产品中就失去意义（一本书只有一条记录）。根据决策记录，该功能可直接消除
- **风险等级**：🟡 中
- **可控性**：可控。前端 `ImportItemList.jsx` 的 refCount 展示和 `ImportPage.jsx` 的 importCounts 状态需同步移除

### R15 · migration 服务的步骤引用

- **风险等级**：🟢 低

### R16 · createDocument 工厂的 ID 前缀统一

- **影响**：统一为单一前缀（如 `rd_`）。这不影响功能——ID 只是字符串主键——但影响调试和日志的可读性
- **风险等级**：🟢 低
- **可控性**：完全可控。`generateId` 函数天然支持任意前缀，只需统一调用参数。需在迁移脚本中处理已有数据的 ID 前缀（建议保留原有 ID 不变，仅新建记录使用新前缀）

## 四、组件层风险

### R17 · ImportPage.jsx — 受影响最重的组件

- **位置**：[ImportPage.jsx](src/components/ImportPage.jsx) — 676 行
- **当前行为**：维护两组平行的状态数组——`articles`（阅读区，来自 library.js）+ `importItems`（书架区，来自 importItems.js）+ `importCounts`（参考计数）。三个 tab（推荐/书架/阅读/回顾）各自查询不同的数据源
- **影响**：
  - 两组状态数组合并为一组（readings），通过 reading_status 过滤
  - `importCounts` 状态消除——不再有跨表参考计数
  - `handleMoveToReading` 逻辑重写——从 `copyToReadingZone(item) + refresh` 变为 `updateReadingStatus(item, 'reading') + refresh`
  - `handleDeleteImportItem` 逻辑简化——不再有关联 articles 的 NULL 处理，直接软删除或状态变更
  - Tab 的筛选逻辑从"查不同的表"变为"查同一个表的不同 reading_status"
  - `importItemTitleById` 的标题回查逻辑可消除（所有 readings 都在同一列表中）
- **风险等级**：🔴 高
- **可控性**：可控但工作量大。这是前端改动最集中的组件，需要仔细重构状态管理。好消息是逻辑方向是简化（两组状态 → 一组），不会引入新的复杂度。建议以 ImportPage 的前端重构为核心里程碑来组织开发工作

### R18 · ImportItemList.jsx 的删除确认文案

- **位置**：[ImportItemList.jsx:175-179](src/components/ImportItemList.jsx#L175-L179)

- **影响**：合并后不再有"阅读副本"概念。删除确认文案需重新设计——根据决策记录 D7，reading 状态禁止编辑（包括删除），in_progress/completed 状态下删除的语义是"从书架移除本书及其所有阅读数据"
- **风险等级**：🟡 中
- **可控性**：可控。是 UI 文案级别的修改，不涉及数据流变更。需要产品确认新的删除确认文案

### R19 · ReaderPage.jsx 的推荐评分回查

## 七、跨切面风险

### R29 · 字段命名的映射链路

- **位置**：贯穿全栈
- **映射链路**：
  ```
  DB column:         article_id / source_import_id
         ↓ library.js mapArticleRow / mapBookmarkRow
  JS property:       articleId / sourceImportId
         ↓ component props
  Component usage:   article.id, bookmark.articleId, article.sourceImportId
  ```
- **影响**：合并后，DB 列 `article_id` → `reading_id`，JS 属性 `articleId` → `readingId`。这个映射链条跨越类型定义 → 服务层 row mapper → 组件 props → 组件内部解构。每一层都需要同步变更
- **风险等级**：🔴 高（非因复杂度，而因覆盖面广——任何一处遗漏都会导致运行时错误）
- **可控性**：可控。策略：
  1. 数据库列名直接使用 `reading_id`（新 migration 中定义）
  2. JS 层面的 `articleId → readingId` 重命名可通过全局搜索替换完成
  3. 使用 TypeScript/JSDoc 类型检查作为静态安全网（虽然当前项目是 JSX + JSDoc）
  4. 建议分步骤实施：先改数据库列名和映射层，再改组件层，每一步独立验证

### R30 · localStorage key rr_articles 的语义

- **位置**：[storage.js:10](src/store/storage.js#L10)
- **当前行为**：localStorage key 为 `rr_articles`
- **影响**：如果不改动 key 名称，已有用户的本地数据不受影响。如果改动 key 名称（如 `rr_readings`），需要兼容读取旧 key 并迁移。根据决定——合并后 localStorage 结构是否需要变更尚未讨论
- **风险等级**：🟡 中
- **可控性**：可控。建议初期保留 `rr_articles` key 名不变（它是 localStorage 命名空间，不是数据库表名），避免引入不必要的迁移复杂度

### R31 · 阅读区上限 N=5 的客户端竞态（审核补充）

- **位置**：04_实施方案 §3.1 `startReading()` 函数设计
- **当前行为**：函数通过先 `listReadingZone()` 查询活跃数量再判断是否超限来实施 D1 决策。这是典型的 check-then-act 模式——两个客户端/标签页同时取第 N 本书时，各自查询到的活跃数量都是 N-1，都能通过检查
- **影响**：极小概率（同一用户几乎不会同时从两个设备取书）下，活跃 reading 可能变为 N+1。这不是数据损坏或安全问题，仅 UX 约束被轻微突破。当前代码库中此功能为全新引入，无历史负担
- **风险等级**：🟢 低（概率极低 + 影响轻微）
- **可控性**：可控。使用 RPC 封装原子检查——`SELECT COUNT(*) FROM readings WHERE user_id = $1 AND reading_status = 'reading' FOR UPDATE`——在事务中完成检查 + 更新。成本低，实现简单。实施方案已更新为 RPC 方式
