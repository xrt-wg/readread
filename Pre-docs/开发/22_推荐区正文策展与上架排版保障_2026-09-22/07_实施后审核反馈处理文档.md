## 一、处理结论总览

对 `06` 的 M1（中）/ L1（低）/ L2（低）三项反馈逐条独立复核，**全部认同，无阻断级异议、无需升级讨论的问题**：

- **M1（中，SQL 三值逻辑漏洞）**：属实，必须修。`<>` 遇 SQL NULL 求值 NULL、`IF` 视为非真，导致「缺 body / 空 body / text 错型且 markdown 缺失」三类坏结构**静默通过**结构校验。已改 `IS DISTINCT FROM`。
- **L1（低，错误文案可能漂移）**：属实，顺手修。判非数组与判空数组同处一个 `OR`，PostgreSQL 不保证短路顺序，`jsonb_array_length` 对非数组会抛系统错误。拆两个 `if` 保证报错文案确定。
- **L2（低，parentId 被丢弃）**：观察属实，但修复方向**采「记录」不采「携带」**（详见 §五），另补充一处反馈未点名的前置缺口（§四）。

代码改动仅 1 个文件（迁移 SQL），文档改动 2 个（01、02），另产出本处理文档。无前端代码变更。

## 五、关键决策

- **L2 采「记录」不采「携带 parentId」**：`parentId` 是派生字段（[document.js:99-101](../../../src/types/document.js#L99-L101)），编辑改了 `heading/depth` 后携带的是旧父关系——stale 错误值比缺失更误导。正确语义是「编辑后由创建链路重推导」，而该链路已存在（`assembleSections + deriveParentIds`）。故不引入 `parentId: s.parentId ?? null` 的携带改动。
- **M1 统一三处用 `IS DISTINCT FROM`**：审核建议仅 `body`/`text`/`markdown` 三处改、`v_section` 保留 `<>`；因 `v_section` 来自 `jsonb_array_elements` 恒非 SQL NULL，`<>` 本安全，但统一 `IS DISTINCT FROM` 更防御一致，故三处全改。
