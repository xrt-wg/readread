## 一、高（共享组件抽取契约未定，回归风险未被方案消化）

### H1　§3.3 与 §3.4 对 sections 数据形态与「保存映射来源」描述互相矛盾，且伪代码 `sections={item.sections}` 与现状不符

**证据链：**

1. [02_实施方案.md:172](../../../Pre-docs/开发/22_推荐区正文策展与上架排版保障_2026-09-22/02_实施方案.md#L172)（§3.3）规定共享组件 `SectionContentEditor` 接收**完整形态** sections `[{id, heading, depth, order, body:{text, markdown, wordCount}}]`，内部转编辑态 `{heading, bodyMarkdown, bodyText}`，保存时「映射回 `{id, heading, depth, order, body:{text, markdown, wordCount}}`（`id/depth/order` 从**输入 sections** 原样保留）」。
2. [02_实施方案.md:179](../../../Pre-docs/开发/22_推荐区正文策展与上架排版保障_2026-09-22/02_实施方案.md#L179)（§3.4）却要求 ImportItemEditor 内容页替换为 `<SectionContentEditor sections={item.sections} onSave={...} />`，且 `onSave` 复用现有 `handleSave`。
3. 现状与上述两处均对不上：
   - `item.sections` 对列表项是**空的**：书架列表列 `READING_LIST_COLUMNS` 不含 `sections`（[readings.js:21](../../../src/services/readings.js#L21)），正文是 `useEffect` 内 `getReading` 懒加载进 `sections` state（[ImportItemEditor.jsx:115-137](../../../src/components/ImportItemEditor.jsx#L115-L137)）。按 §3.4 传 `item.sections` 会渲染出**空编辑器**。
   - 现有 `sections` state 是**编辑态** `{id, heading, bodyText, bodyMarkdown}`（[ImportItemEditor.jsx:99-103](../../../src/components/ImportItemEditor.jsx#L99-L103)），而 §3.3 声明组件接收**完整态** `{...body:{...}}`——两者形态不一致，直接喂给共享组件要么二次转换、要么崩。
   - 现有 `handleSave` 的 `id/depth/order` 来自 `...item.sections[i]`（[ImportItemEditor.jsx:164-167](../../../src/components/ImportItemEditor.jsx#L164-L167)），即**原始 `item` prop**，而非 §3.3 声称的「输入 sections」；当 `item.sections` 为空时 `...undefined` 为空展开，`id/depth/order` 会被**静默丢弃**。

**问题本质：** §3.3（共享组件自持完整态 → 编辑态 → 完整态）与 §3.4（ImportItemEditor 自持编辑态 + 复用 `handleSave`）是**两套互斥的状态所有权方案**，方案未裁决哪一套为真。而 ImportItemEditor 重构要动到的 `isDirty`（对 `sections` state 做 `JSON.stringify` 比较，[ImportItemEditor.jsx:139-146](../../../src/components/ImportItemEditor.jsx#L139-L146)）与 `snapshot` 快照（[ImportItemEditor.jsx:112](../../../src/components/ImportItemEditor.jsx#L112)）也绑定在现有编辑态上，「只移动、不改行为」在契约未定的前提下无法达成。

**修复建议（实施前定稿，二选一并写进方案）：**

- **方案 A（推荐，改动最稳）**：`SectionContentEditor` 只收完整态 `sections`、内部自持编辑态、`onSave(fullSections)` 回调完整态。ImportItemEditor 的 `sections` state **改为保存完整态**（懒加载后存 `fullSections`），`handleSave` 的映射改为「从 `onSave` 回调拿到的完整 sections 直接提交」，`isDirty`/`snapshot` 改比较完整态。§3.4 伪代码改为 `sections={sections}`（完整态 state），并显式写出 `handleSave` 不再依赖 `...item.sections[i]`。
- **方案 B**：`SectionContentEditor` 收编辑态 `{id, heading, bodyText, bodyMarkdown}`，`onSave` 回调编辑态，由 ImportItemEditor 与审核面板各自做「编辑态 → 完整态」映射。则 §3.3 中「输入完整态」与「id/depth/order 从输入保留」的表述需整体改写，且审核面板侧需新增「快照完整 sections → 编辑态」的前置转换。

无论选哪套，都要在方案中**明确写出**：① 组件 `sections` prop 的精确形态；② `onSave` 回调的精确形态；③ `id/depth/order/wordCount` 的保留/重算规则；④ ImportItemEditor 的 `isDirty`/`snapshot`/懒加载如何跟随改造。

## 二、中（语义 / 健壮性）

### M1　`coalesce(s.author, x.author)` / `coalesce(s.source_url, x.source_url)` 会「复活」被管理员清空的值，与 D4「取发布态值」相悖

**证据：**

- [02_实施方案.md:94-99](../../../Pre-docs/开发/22_推荐区正文策展与上架排版保障_2026-09-22/02_实施方案.md#L94-L99) Step 3 写 `'author', coalesce(s.author, x.author)`、`'source_url', coalesce(s.source_url, x.source_url)`。
- 但 `admin_update_recommendation_editorial` 对作者/来源是**直接赋值**：`set ... author = p_author, source_url = p_source_url`（[20260917000000_recommendation_moderation_workflow.sql:214-215](../../../supabase/migrations/20260917000000_recommendation_moderation_workflow.sql#L214-L215)），前端传入 `patch.author?.trim() || null`（[recommendationService.js:106-108](../../../src/services/supabase/recommendationService.js#L106-L108)）。即管理员**清空作者/来源**时，`s.author` 会变成 `NULL`。
- 此时 `coalesce(s.author, x.author)` 落到 `x.author`（提交时冻结值），用户「加入书架」拿到的仍是旧作者——**恰好违背 D4「标题/作者/来源取发布态值」的初衷**。`title` 因 `title = coalesce(p_title, title)` 永非空（[20260917000000_recommendation_moderation_workflow.sql:215](../../../supabase/migrations/20260917000000_recommendation_moderation_workflow.sql#L215)）不受影响，故问题集中在 author/source_url 两个**可空**字段。

**问题本质：** `get_recommendation_snapshot` 用 `join`（inner join）保证 `s` 恒存在，`coalesce(s.x, x.x)` 等价于 `s.x` 只在「`s.x` 非空」时成立；对可空发布字段，coalesce 反而把「清空」语义吞掉、回退到冻结值。

**建议：** 直接取发布态列，去掉 coalesce：

```sql
select jsonb_build_object(
  'title', s.title, 'author', s.author, 'source_url', s.source_url,
  'sections', coalesce(x.curated_sections, x.sections),
  'format', x.format, 'cover_url', x.cover_url, 'lang', x.lang, 'kind', x.kind)
from ...
```

（`sections` 的 coalesce 仍必须保留——它是「无策展回退提交原样」的正确语义。）

### M2　`admin_update_recommendation_content` 只校验顶层 array，不校验元素结构；坏结构会一路流到「加入书架」的 `s.body.text.split(...)` 并 500

**证据链：**

1. [02_实施方案.md:68-70](../../../Pre-docs/开发/22_推荐区正文策展与上架排版保障_2026-09-22/02_实施方案.md#L68-L70) Step 2 仅校验 `jsonb_typeof(p_sections) <> 'array'`，未校验数组元素是否含 `heading/depth/order/body.text/body.markdown` 及类型。
2. 策展正文是**原样**透传链路：`get_recommendation_snapshot` 返回 `coalesce(curated_sections, sections)` → [addRecommendationToBookshelf](../../../src/services/supabase/recommendationService.js#L272) `structuredClone` → [recommendationService.js:286-295](../../../src/services/supabase/recommendationService.js#L286-L295) 逐段映射 `body: {text: s.body?.text, markdown: s.body?.markdown}` → `assembleSections` 里 `wordCount: s.body.text.split(/\s+/).filter(Boolean).length`（[extractors/index.js:28](../../../src/services/extractors/index.js#L28)）。
3. 若任一元素缺 `body.text`（如 H1 契约没对齐、或保存映射写错字段名、或管理员经 PostgREST 手工调用），`s.body.text.split` 直接 `TypeError`，「加入书架」对**所有**用户 500，且报错远离策展源头、难定位。

**问题本质：** 策展正文是「管理员 UI → 用户书架」的第一手数据源，但当前校验深度停留在「是数组」，把结构正确性完全押在「前端 editor 一定写对」这一单一前提上；而 H1 恰说明这个前提目前并不牢靠。

**建议（二选一或都做）：**

- **A（首选）**：RPC 内对数组逐元素做结构校验（`heading/depth/order/body` 存在性 + `body.text`/`body.markdown` 至少其一），不合法即 `raise exception`，把脏数据挡在写入前。可复用 `assembleSections` 的字段约定作为校验依据。
- **B（纵深防御）**：在 `addRecommendationToBookshelf` 的 sections 映射与 `assembleSections` 的 `wordCount` 计算处做 `s.body?.text ?? ''` 兜底，避免单点脏数据拖垮整条「加入书架」链路。

## 三、低（完善性 / 边界语义）

### L1　§3.5 伪代码 `detail.snapshot.curated_sections ?? detail.snapshot.sections` 缺空守卫，加载期会崩

[02_实施方案.md:187](../../../Pre-docs/开发/22_推荐区正文策展与上架排版保障_2026-09-22/02_实施方案.md#L187) 写 `const displaySections = detail.snapshot.curated_sections ?? detail.snapshot.sections`，但 `detail` 是异步拉取、初始为 `null`（[RecommendationModerationPanel.jsx:149](../../../src/components/RecommendationModerationPanel.jsx#L149)、[RecommendationModerationPanel.jsx:180](../../../src/components/RecommendationModerationPanel.jsx#L180)），且现代码用 `detail?.snapshot?.sections` 三级可选链（[RecommendationModerationPanel.jsx:226](../../../src/components/RecommendationModerationPanel.jsx#L226)）。建议伪代码改为 `detail?.snapshot?.curated_sections ?? detail?.snapshot?.sections`，并与「正在加载正文快照…」空态分支对齐。

### L2　策展审计未写 `payload`，内容变更缺少前后指纹，追溯需外求快照

[02_实施方案.md:84-85](../../../Pre-docs/开发/22_推荐区正文策展与上架排版保障_2026-09-22/02_实施方案.md#L84-L85) 的审计 `insert ... (actor_user_id, actor_role, action, target_type, target_id)` 未带 `payload`。内容类变更（正文覆盖）相比 editorial 的元信息变更，更有价值在 `payload` 里留 `jsonb_build_object('from_hash', content_hash)`（或「是否首次策展」），否则事后只能靠 `curated_at` 时间戳反查、无法直接看出「改了什么」。属完善项，与现有 editorial 审计风格一致、非阻断，可后续补。

### L3　`curated_sections` 空数组 `[]` 不被拒绝，且 `coalesce`/`addRecommendationToBookshelf` 对 `[]` 均不兜底

- RPC 仅校验「是数组」，空数组 `[]` 合法入库。
- `coalesce(curated_sections, sections)` 对 `[]` **不回退**（`[]` 非 NULL）。
- `addRecommendationToBookshelf` 的 `if (!row?.sections)`（[recommendationService.js:263](../../../src/services/supabase/recommendationService.js#L263)）对 `[]` 判真（空数组 truthy），会继续 `structuredClone([])` 生成一篇**空正文** reading。
- 管理员 UI 正常路径不会产出空数组，但建议 RPC 拒绝 `[]`（或前端保存时防呆），把「空正文」这一退化态挡在源头。

### L4　编辑纯文本 section 会被静默转成 markdown，渲染路径随之切换

编辑态映射 `bodyMarkdown: s.body?.markdown ?? s.body?.text ?? null`（[ImportItemEditor.jsx:101](../../../src/components/ImportItemEditor.jsx#L101)）与保存映射 `markdown: s.bodyMarkdown ?? null`（[ImportItemEditor.jsx:166](../../../src/components/ImportItemEditor.jsx#L166)）共同导致：**原本 `body.markdown = null` 的纯文本 section，一经编辑保存后 `body.markdown` 变为 text**，阅读渲染路径由 `PlainTextContent` 切到 `MarkdownContent`（[SectionFlow.jsx:237](../../../src/components/SectionFlow.jsx#L237)）。这是 ImportItemEditor 的既有行为，共享组件会原样继承——对「策展排版」场景意味着：管理员想给一段纯文本只改个标点，也会把它的渲染语义改成 markdown（行首 `#`/`*`/`>` 等会被解释）。属边界语义，建议在决策记录里明确「策展后统一按 markdown 交付、纯文本语义不再保留」这一事实，避免日后当 bug 追。
