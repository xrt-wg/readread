# 推荐区正文策展与上架排版保障 — 讨论和决策记录

> 日期：2026-09-22
> 关联：[02_实施方案](02_实施方案.md)

## 一、背景与需求

社区众包推荐的正文在提交时被冻结进 `recommendation_submission_snapshots`（含 `content_hash` 去重指纹），用户「加入书架」时深拷贝这份快照生成自己的 `import_item`。这条链路上有两个长期缺口：

1. **后台看不到排版后的正文**：审核面板把快照 sections 拍平成纯文本（`whitespace-pre-wrap` 小滚动框），管理员看到的是 markdown 源码而非排版结果，既不利于逐字摘抄，也不利于判断内容质量。
2. **后台无法修正正文排版**：快照 sections 冻结后无人可改——提交者要改只能重新导入再重新提交，管理员则完全没有编辑入口。结果是差排版原样流到「加入书架」的用户手里，用户还得自己在书架区折腾。

**需求**（经澄清确认为四点）：

1. 后台以与阅读区一致的排版**渲染**正文（替代原始文本堆）；
2. 后台能像书架区那样**「编辑 + 预览」**正文，修正标题层级、段落、列表、图、引用等排版；
3. **上架前**完成排版修正，用户加入书架即拿到已排版内容；
4. 顺手修复「卡片显示标题 vs 加入书架标题」的不一致（管理员改了卡片标题，但用户导入拿到的是提交时旧标题）。

## 二、现状调查结论

### 2.1 正文渲染缺口

- 审核面板 [RecommendationModerationPanel.jsx](../../../src/components/RecommendationModerationPanel.jsx)（约 225–226 行）把 `detail.snapshot.sections` 渲染为 `section.body?.text || section.body?.markdown` 用 `\n\n` 连接、塞进 `max-h-44 overflow-y-auto whitespace-pre-wrap`——丢标题层级、markdown 当纯文本、无正文排版。
- 阅读区 [SectionFlow.jsx](../../../src/components/SectionFlow.jsx) 才是正确消费方式：`section.heading + depth → h2/h3/h4` + `ReactMarkdown(remarkGfm)` 渲染 `body.markdown`，`body.text` 走纯文本降级。

### 2.2 正文编辑缺口

- [admin_update_recommendation_editorial](../../../supabase/migrations/20260917000000_recommendation_moderation_workflow.sql) 只写 `recommendation_submissions`（title/author/source_url/intro/keywords/excerpts/internal_note），**不碰 sections，也不碰快照**。
- 全库无任何「管理员编辑快照正文」的 RPC 路径（已确认）。

### 2.3 标题不一致（第 2 点）

- 管理员编辑标题写进 `recommendation_submissions.title`（卡片显示用）；
- 但「加入书架」读的 [get_recommendation_snapshot](../../../supabase/migrations/20260917000000_recommendation_moderation_workflow.sql) 返回的是**快照自己的** `title/author/source_url`（提交时冻结值）；
- 结果：管理员改卡片标题后，用户导入拿到的仍是旧标题。根因是 `get_recommendation_snapshot` 取 `x.title` 而非 `s.title`。

### 2.4 书架区编辑/渲染（复用的来源）

- [ImportItemEditor.jsx](../../../src/components/ImportItemEditor.jsx) 提供「编辑 + 预览」统一体：`FormatToolbar`（H2/H3/引用/加粗/斜体/链接/图片）+ markdown textarea + 编辑/预览切换 + `MarkdownPreview`（`ReactMarkdown + remarkGfm`，与阅读区同一套 `article-*` 样式）。
- `FormatToolbar` / `MarkdownPreview` 目前**只在 ImportItemEditor 内部使用**（已确认），抽取为共享组件无外部依赖破坏。

### 2.5 关键结论（技术判断依据）

1. **不可原地改快照**：`content_hash`（sections 的 SHA256）承担去重（提交查重 + 唯一索引）与「提交指纹」语义。原地覆盖 sections 要么让指纹失效、要么抹掉「提交者到底提交了什么」的审计基线。
2. **策展层是正确锚点**：提交原样 `sections` 永不动；新增可空 `curated_sections` 作为「上架时实际交付给用户」的内容；`get_recommendation_snapshot` 用 `coalesce(curated_sections, sections)`。这样不可变性、去重、审计、加入书架链路全部零改动。
3. **标题一致性顺手修**：`get_recommendation_snapshot` 的 title/author/source_url 改取提交表现行值（管理员已编辑好的发布值），而非快照冻结值。
4. **编辑时机对齐 editorial**：`pending/approved/removed` 可编辑正文，`active`（已上架）需先下架——与 `admin_update_recommendation_editorial` 一致。

## 三、决策记录

### D1 排版 QA 归属 → 管理员上架前兜底

- 备选：驳回让提交者改（现状）——但重新提交会重置状态机、撞「每周 1 篇」限额、撞去重，摩擦极高。
- **决策：由管理员在审核流程内兜底修正正文排版**。理由：审核者已在上架链路中，是天然的最后一公里 QA；把「排版过关」前置到上架前，直接消除「用户导入后自己折腾」。

### D2 存储锚点 → 策展层（curated_sections），不改不可变快照

- 备选：原地改快照 sections（改动最小但破坏不可变性/指纹/审计）。
- **决策：快照表新增可空 `curated_sections jsonb` + `curated_at timestamptz`**；`sections`/`content_hash` 保持为提交原样与去重基线。`get_recommendation_snapshot` 返回 `coalesce(curated_sections, sections)`。
- 理由：不可变性是整套机制的地基（去重、审计、加入书架可信源）；策展层是**可加可减**的覆盖，不破坏任何既有不变式。

### D3 编辑体验 → 抽取共享「内容编辑 + 预览」核心

- 备选：整套搬 `ImportItemEditor`（带属性页、kind 选择、保存到用户书架的语义，后台不需要）；或在面板内复制一份简化 markdown 编辑器（与阅读区漂移）。
- **决策：把 ImportItemEditor 的「内容编辑 + 预览」核心（`FormatToolbar`/`MarkdownPreview` + 章节目录 + 标题输入 + markdown 编辑器 + 编辑/预览切换）抽取为共享组件**，后台只复用这一块，不搬属性页/kind/保存语义。
- 理由：后台要的是「正文排版修复」，元信息（title/author/kind）已有 editorial 表单承载；共享组件保证「后台看到的 = 阅读区看到的 = 用户导入后看到的」，且不复制逻辑。

### D4 标题一致性 → get_recommendation_snapshot 取提交表现行值

- **决策：`get_recommendation_snapshot` 的 `title/author/source_url` 由快照值改为提交表现行值 `s.title/s.author/s.source_url`**（`sections` 取策展层，`format/cover_url/lang/kind` 仍取快照）。
- 理由：标题/作者/来源是「发布态」元信息，管理员已通过 editorial 编辑，用户导入应拿到发布值；format/cover/lang/kind 无管理员编辑入口，仍取快照。
- **修正（M1）**：author/source_url 不做 `coalesce(s.x, x.x)`——`coalesce` 只在 `s.x` 非空时等价 `s.x`，一旦管理员清空作者/来源（`s.author` 落 NULL），coalesce 会「复活」提交时冻结值，违背「取发布态值」。直接取 `s.author/s.source_url`，清空即空。

### D5 编辑时机 → 状态门对齐 editorial

- **决策：`admin_update_recommendation_content` 仅允许 `pending/approved/removed`**，`active` 报「已发布内容请先下架」。与 `admin_update_recommendation_editorial` 的门控一致，避免「上架后正文被静默改动」。

### D6 共享组件契约 → 完整态 Section[] 为唯一对外形态（顺带修复丢字段隐患）

- 审核反馈 H1 指出原方案 §3.3/§3.4 对 `sections` 形态与保存映射来源互相矛盾。定稿：`SectionContentEditor` 受控于**完整态** `Section[]`（`{id, heading, depth, order, body:{text, markdown, wordCount}}`），`onChange(fullSections)` 回写；组件内部派生编辑态，`id/depth/order` 原样携带/写回。
- **附带修复**：原 `ImportItemEditor.handleSave` 用 `...item.sections[i]` 取 id/depth/order，而书架列表项 `item.sections=[]`（列表列不含 sections），每次编辑保存都会静默丢弃 id/depth/order，多章节/深层标题内容编辑后退化为 h2。改为完整态 state 后该隐患一并消除。
- **parentId 不随编辑回写（实施后审核 L2）**：完整态契约只保留 `id/heading/depth/order/body`，不携带 `parentId`——`parentId` 是 `deriveParentIds()` 推导的派生字段（[document.js](../../../src/types/document.js)），编辑改了 `heading/depth` 后携带旧父关系反而 stale 错误，正确语义是「编辑后由创建链路重推导」。「加入书架」路径本就 `assembleSections + deriveParentIds` 重推导，无影响。另记录一处前置缺口：`updateReading`（书架编辑）写 sections 时**不重推导 parentId**，属既有行为、当前无消费方故无害；若未来有功能消费 `section.parentId`（如目录树），需让 `updateReading` 也走 `deriveParentIds`——范围外，另行立项。

### D7 纯文本 section 编辑语义 → 策展后统一按 markdown 交付

- 编辑态派生 `bodyMarkdown = body.markdown ?? body.text ?? null` 与保存 `markdown = bodyMarkdown ?? null` 共同导致：原本 `body.markdown=null` 的纯文本 section 一经编辑保存即转为 markdown，阅读渲染路径由 `PlainTextContent` 切到 `MarkdownContent`。这是 ImportItemEditor 的既有行为，共享组件原样继承。
- **决策：明确「策展后统一按 markdown 交付、纯文本语义不再保留」这一事实**（L4 记录而非修复）。理由：纯文本 section 在本系统已罕见；管理员策展的本意就是「把排版修到位」，统一按 markdown 交付反而消除「同一篇文章混合两种渲染路径」的歧义。日后若确需保留纯文本语义，再另立独立 RPC 补上。

## 四、最终方案要点

| 维度 | 决策 |
|---|---|
| 存储 | 快照表新增可空 `curated_sections`/`curated_at`；`sections`/`content_hash` 不变 |
| 编辑 RPC | 新增 `admin_update_recommendation_content(submission_id, sections)`，仅管理员、状态门 pending/approved/removed、写审计 |
| 加入书架 | `get_recommendation_snapshot` 改为 `coalesce(curated_sections, sections)` + 标题/作者/来源取提交表现行值 |
| 编辑体验 | 抽取共享「内容编辑+预览」组件，后台复用，不搬属性页/kind/保存语义 |
| 后台渲染 | 默认只读排版预览（标题层级 + markdown 渲染），「编辑正文」进入编辑态 |
| 标题一致 | 修复（D4），用户导入标题 = 卡片标题 |
| 迁移 | 1 个迁移脚本 `20260922000000_recommendation_content_curation.sql` |

## 五、风险与注意点

1. **ImportItemEditor 抽取回归**：把内容编辑核心抽成共享组件会动到阅读主线文件；采用「只移动、不改行为」的抽取 + 全量回归（编辑→预览→保存→加入书架）。
2. **content_hash 语义不变**：策展不重算 `content_hash`，它始终是「提交时指纹」；去重、唯一索引、面板指纹显示均不受影响。
3. **部署顺序（对齐 H1 惯例）**：迁移经 Dashboard SQL Editor 手工执行，须**先跑迁移、再发布前端**；`admin_update_recommendation_content` 与 `admin_get_recommendation_submission_detail` 的新增返回字段（`curated_sections`/`curated_at`）依赖新迁移。
4. **`create or replace` 保留 grant**：`get_recommendation_snapshot`、`admin_get_recommendation_submission_detail` 用 `create or replace` 改写，签名不变，原 `grant execute` 依然有效；仅新增 RPC 需 grant。
5. **快照缺失（snapshotMissing）**：无快照的历史记录不能编辑正文，RPC 对「快照行不存在」显式报错；面板在快照缺失时保持现有「需运营补录」提示、不提供编辑入口。
6. **颜色规范**：新增 UI（正文预览/编辑、已策展徽标）全部走 `var(--*)`，不引入硬编码颜色（CLAUDE.md 颜色规范）。
7. **范围外**：「还原为提交原版」（清空策展层）不在本次范围，可后续加独立 RPC 补上。
