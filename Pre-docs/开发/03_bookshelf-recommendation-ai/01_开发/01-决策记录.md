# 决策记录：书架区提交推荐 AI 化改造

> 版本：v1.1（已根据审核反馈修订）
> 日期：2026-06-23
> 状态：待审核

---

## D1 — 文本不截断

**决策**：将 import_item 的完整原文全文发送给 AI，不做任何截断。

**理由**：
- 典型英文阅读材料 500–5000 词，远在现代模型上下文窗口（100K–1M tokens）之内
- 截断会缩小摘录候选池，最具代表性的段落可能出现在文章中后部
- 成本差异微不足道——

**定量成本分析**（以 5000 词文章为例）：

| 参数 | 数值 |
|------|------|
| 输入（5000 词 ≈ 7000 tokens） | ~$0.002（DeepSeek $0.27/1M） |
| 输出（intro + keywords + excerpts ≈ 3500 tokens） | ~$0.004（DeepSeek $1.10/1M） |
| **单次总成本** | **~$0.006（0.6 美分）** |
| 月均 100 次提交 | ~$0.60 |

**边界条件**：对于极端长内容（如整本书 EPUB 导入，> 50K 字），Netlify function 设有 100K 字符输入上限校验（见实施方案 §3.3），超出时返回 413 错误并建议用户在书架编辑器中拆分为多篇后再提交。

**影响**：Prompt 需包含全文；function 需加输入上限校验；不做前端截断。

## D2 — AI 生成时机：弹窗内按需触发

**决策**：用户打开提交弹窗并选中条目后，手动点击按钮触发 AI 生成。不预生成（导入时），不自动触发。

**理由**：
- 预生成浪费算力：用户书架可能有几十篇，但只提交少数
- 自动触发浪费 token：用户可能只是看看弹窗内容，并不打算提交
- 手动触发让用户对 AI 调用有明确的控制感

**影响**：弹窗需新增「生成推荐内容」按钮 + loading 状态；同一 item 的生成结果需缓存避免重复调用。

---

## D3 — 生成结果缓存

**决策**：以 `importItemId` 为键，在父组件（`ImportPage.jsx`）中维护 `useState` 缓存，通过 props 传入弹窗。同一 item 在同一会话中重复打开弹窗时直接复用缓存，不重复调用 AI。缓存生命周期 = ImportPage 挂载周期 = 用户在书架区的整个停留时段。

**理由**：
- 避免用户因关闭弹窗后再次打开而重复消耗 token
- 缓存存储在父组件（而非弹窗内 state），可规避弹窗条件渲染卸载导致 state 丢失的问题（见审核反馈 B2）
- 页面刷新则自然清除，零维护

**影响**：`ImportPage.jsx` 新增 `recommendationCache` state；`SubmitRecommendationModal` 通过 props 接收缓存及 setter。

---

## D4 — 触发方式：手动

**决策**：选中 item 后展示基本属性，用户需点击「生成推荐内容」按钮才发起 AI 调用。

**理由**：
- 给用户明确的控制权
- 避免用户仅查看属性就触发不必要的 AI 调用
- 与 D2 一致

**影响**：按钮放置于基本属性区下方、AI 策展区上方；生成完成后按钮变为「重新生成」（可选）。

## D5 — 关键词：中英双语，≤ 4 个

**决策**：AI 生成 3–4 个英文关键词，同时生成对应的中文翻译。分别填充 `keywords`（英文）和 `keywords_trans`（中文）字段。数量上限从当前的 5 个收紧为 4 个。

**理由**：
- 当前 DB 已设计 `keywords` 和 `keywords_trans` 双字段
- 4 个关键词在精确性和简洁性之间取得平衡
- 中英对照便于社区中英文用户的检索和浏览

**影响**：Prompt 需明确要求输出两个数组；UI 展示双语配对标签；AI 配置分离后推荐生成的 provider 可独立选择。

---

## D6 — 摘录：固定 3 条，原文 + 翻译对照

**决策**：AI 从原文中**选取**（非创作）3 段最具代表性的文字作为摘录，同时生成中文翻译。分别填充 `excerpts`（原文摘录）和 `excerpts_trans`（中文翻译）。

**理由**：
- 摘录的价值在于真实呈现原文风貌，AI 必须「选取」而非「改写」
- 3 条在丰富性和阅读负担之间取得平衡
- 中文翻译降低社区用户的阅读门槛
- Prompt 中需明确指令：摘录必须是原文中的 verbatim 片段

**关于文章 vs 书籍的摘录策略**：Prompt 中针对 `kind` 做微调——文章强调选取论证核心段落，书籍强调选取关键章节代表性段落。

**影响**：Prompt 需强调 verbatim 约束 + kind 区分策略；UI 展示每条摘录 + 对应翻译的配对关系。

---

## D7 — AI 配置分离

**决策**：推荐内容生成使用独立的 AI provider 配置，与翻译功能完全分离。

**分离层面**：
1. **Netlify Function**：新建 `netlify/functions/generate-recommendation.js`，不与 `translate.js` 共享
2. **Provider 适配层**：抽取共享模块 `netlify/lib/aiProviders.js`，两个 function 共同引用（消除重复代码维护隐患）
3. **配置**：新建 `config/recommendation.json`（JSON 格式，ESM 和 CJS 均可消费），指定独立的 activePreset / fallbackPreset / tokenLimits
4. **前端 AI 服务层**：在 `aiProviders/` 中新增推荐生成专用函数，不混入翻译的 `translateText()`
5. **环境变量**：可使用独立的 API key（如 `PRESET_RECOMMENDATION_GEMINI_API_KEY`），也可复用现有 keys

**理由**：
- 推荐生成（长文输入 + 结构化输出）与翻译（短文本 + 简单返回）的模型需求不同
- 独立配置便于为两项功能选择不同性价比的模型
- 独立 API key 便于成本核算和配额管理
- 独立 Netlify function 便于各自的性能监控和错误追踪
- 共享 provider 适配层消除维护隐患（审核反馈 B4）

**影响**：新增 `config/recommendation.json`；新增 `netlify/lib/aiProviders.js`；`translate.js` 改为引用共享模块；`presetModels.json` 新增推荐专用条目。

## D8 — 基本属性回写

**决策**：提交推荐时，如果用户修改了基本属性（title / author / kind / sourceUrl），**先**调用 `updateImportItem()` 将修改同步回 `import_items` 表，**再**调用 `submitRecommendation()` 写入推荐记录。

**事务顺序**（修订于审核反馈 B7）：
```
updateImportItem()  ← 先回写 ── 失败 → 终止，不提交推荐，告知用户
        │
        ▼ 成功
submitRecommendation()  ← 再提交 ── 失败 → 属性已更新（良性），告知用户重试
```

**理由**：
- 避免推荐记录用新属性但书架保留旧属性的不一致状态（审核反馈 B7）
- 回写失败时阻止提交，防止脏数据进入推荐区
- `updateImportItem` 已是成熟接口，无需额外开发

**影响**：`submitRecommendation` 内部增加前置回写步骤；提交按钮增加回写失败的错误处理。

## D9 — 降级策略

**决策**：AI 生成失败时，不阻塞提交流程，回退到手动填写模式。

**触发条件**：
- Netlify function 返回错误
- AI API 不可达（primary 重试 1 次 + 切换 fallback preset 后仍失败）
- 前端超时
- AI 返回的结果不符合预期格式（JSON 解析失败，含 1 次重试）

**降级行为**：
- 展示错误提示 + 原因（如「AI 生成失败：服务暂时不可用，请手动填写」）
- 将 intro / keywords / excerpts 区域切换为可编辑的空表单
- 用户可以手动填写后继续提交（回退到旧有行为）

**影响**：弹窗需维护 `generationFailed` 状态以控制降级 UI；AI state 和手动填写共用同一套 state（审核反馈 B5）。

## D10 — Prompt 设计职责

**决策**：Prompt 由开发者（我）先行设计初版，用户后续优化迭代。

**理由**：Prompt 质量直接影响推荐内容质量，需在实际调用中调优；初版提供可工作的基线，后续根据生成效果迭代。

**影响**：实施方案中包含初版 Prompt 设计；文档中标注为「初版，待优化」。

---

## D11 — 多标签页并发（已知限制）

**决策**：当前版本不处理多标签页并发场景，作为已知限制记录。

**场景**：
- 同一用户可能在多个标签页中打开应用
- 两个标签页各自有独立的会话缓存，可能生成不同结果
- 两个标签页可能尝试提交同一 import item 的推荐

**缓解**：
- `checkSubmissionEligibility` 包含服务端重复提交校验，第二个标签页提交时会触发"该内容已被推荐过"拒绝
- 缓存不一致属于边界场景，实际影响极小

**影响**：不额外开发多标签页同步机制。

---

## D12 — 输入大小保护

**决策**：Netlify function 中增加 `articleText` 长度上限校验（100K 字符），超出时返回 HTTP 413。

**理由**：
- 防止异常大文本导致 function 内存或 payload 超限（审核反馈 S12）
- 100K 字符覆盖所有正常英文阅读材料（5000 词文章 ≈ 30K 字符），留足余量
- 超出时在前端给出明确提示，而非静默失败

**影响**：function 增加校验逻辑；错误处理矩阵增加 413 条目。
