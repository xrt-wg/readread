**影响文档**：02-§2.2, 02-§10, 03-Step0

### 🔴 B6 — maxOutputTokens 估算不足 → ✅ 已处理

**处理**：`maxOutputTokens` 调整为 `4096`。同时在 Prompt 中增加输出长度软约束（intro ≤250 字、每条摘录翻译 ≤500 字等），从 prompt 和 token 两端控制。

**影响文档**：02-§2.2, 02-§8.2, 03-Step1

### 🔴 B7 — 提交与属性回写缺少事务性保护 → ✅ 已处理

**审核发现**：`submitRecommendation()` 先写入推荐 → 再 `updateImportItem()` 回写，若第一步成功第二步失败会导致数据不一致。

**处理**：调整事务顺序——**先 `updateImportItem()` → 再 `submitRecommendation()`**。回写失败则阻止提交（错误展示、弹窗保持）；回写成功但提交失败则属性已更新（良性），推荐未创建（用户重试）。

**影响文档**：01-D8/D12, 02-§7.2, 03-Step5

### 🔴 B8 — 缺少 token 估算与成本预警 → ✅ 部分处理

**审核发现**：D1 声称"成本微不足道"但未做定量分析；缺少输入边界条件。

**处理**：
- **已处理**：在 D1 增加了定量成本分析表格（单次 ~$0.006 / 月 100 次 ~$0.60），证实了"成本微不足道"的判断
- **已处理**：在 function 中增加 100K 字符输入上限校验（D12），覆盖极长文本的边界条件
- **已处理**：在 function 返回的 `perf` 中增加 `inputTokens` / `outputTokens` 字段（若 API 返回）
- **未采纳**：审核建议的前端展示 token 消耗提示。理由：0.6 美分的信息不会改变用户行为，反而在 UI 中引入噪音

**影响文档**：01-D1, 01-D12, 02-§4.2, 02-§4.3

## 阻塞项复核

### B1 — JS→JSON 模块系统冲突 → ✅ 通过

**处理决策**：`config/recommendation.js` → `config/recommendation.json`

**复核**：
- JSON 格式确实可被 ESM `import` 和 CJS `require()` 同时消费，与现有 `presetModels.json` 模式一致
- 原始方案中 `config/recommendation.js` 仅导出静态数据对象（无函数），转为 JSON 无功能损失
- `_comment` 字段标注服务端/前端归属是务实的文档手段
- ⚠️ 微注：JSON 不支持尾随逗号和注释，编写时需注意语法；`_comment` 仅为人读，工具不解析

**结论**：✅ 处理正确，完全解决 B1。

---

### B2 — 缓存提升至父组件 → ✅ 通过

**处理决策**：`generationCache` 从弹窗 `useState` 提升至 `ImportPage.jsx` 的 `useState`，通过 props 传入

**复核**：
- 正确识别了根因：弹窗卸载时 `useState` 丢失
- 提升至 `ImportPage` 合理：ImportPage 在书架区会话期间保持挂载，满足 D3"弹窗关闭不清除"的要求
- 与现有代码模式兼容：ImportPage 已有 state 管理先例（管理 `importItems` 等），新增一个 state 不破坏现有架构
- ⚠️ 微注：`generationCache` 以 `importItemId` 为键存储 `GeneratedContent` 对象，随着用户浏览多个条目，缓存可能累积。建议在实施方案中注明缓存上限或清理策略（如保留最近 5 条）

**结论**：✅ 处理正确，完全解决 B2。

---

### B3 — Netlify 超时修复 → ⚠️ 通过（附注）

**处理决策**：
- `netlify.toml` 中为 function 单独配置超时
- 前端 timeout = function 超时 - 1s（Pro 默认 25s，Starter 设为 8s）
- Function 内部在 deadline 前 1s 主动 throw

**复核**：
- `netlify.toml` 配置 function 超时是标准做法，可行
- 前端 timeout < function timeout 的逻辑正确（避免前端先超时放弃，function 仍在执行浪费资源）
- Function 内部 deadline 感知是好的防御性编程
- ⚠️ **关注点**：Pro 套餐 function 同步超时上限为 26s，设定 25s 仅留 1s 余量——对于正常 AI 响应足够，但若 Netlify 基础设施有微小延迟，可能触发边界。建议设为 24s 留 2s 余量
- ⚠️ **关注点**：Starter 套餐下 8s 可能不足以处理 5000+ 词长文的 AI 调用（典型响应时间 3-8s）。如果目标部署环境为 Starter，需要确认是否可接受偶尔超时降级，或建议升级至 Pro
- ⚠️ **微注**：新增的 `netlify.toml` function 超时配置需在部署前验证——Netlify Dev 本地环境不模拟超时限制

**结论**：⚠️ 处理方向正确，建议微调 Pro 超时余量（25s→24s），Starter 场景需明确预期。

---

### B4 — Provider 共享适配层 → ✅ 通过

**处理决策**：新增 Step 1.5，从 `translate.js` 抽取 provider 适配函数至 `netlify/lib/aiProviders.js`

**复核**：
- 这是正确的工程决策。审核原建议的方案 A 即为此方案
- 共享模块不仅消除了重复，还为未来新增 provider 提供单一修改点
- ⚠️ **关注点**：`translate.js` 改为引用共享模块——这意味着本次改造会触及 `translate.js`（现有生产功能）。执行计划 Step 1.5 需包含对 `translate.js` 的回归验证，确保翻译功能不受影响
- ⚠️ **微注**：共享模块应保持纯函数风格（输入 prompt + config → 输出 response），不耦合任何业务逻辑，以便两个 function 各自组装参数

**结论**：✅ 处理正确，完全解决 B4。需补充 translate.js 回归验证。

---

### B5 — 统一 state 消除矛盾 → ✅ 通过

**处理决策**：取消移除旧 state。策展内容统一使用一套 state（`intro`, `keywords`, `keywordsTrans`, `excerpts`, `excerptsTrans`），AI 填充和手动填写绑定同一套字段

**复核**：
- 方案比原设计更简洁：消除 `aiXxx` 和普通 `xxx` 两套 state 的冗余
- 降级模式的可编辑表单自动获得 state 绑定——B5 的矛盾被根除
- 提交时统一从一套 state 取值，逻辑更清晰
- ⚠️ **微注**：需确保在"AI 生成成功 → 用户编辑 → 提交"路径中，`keywords` 和 `keywordsTrans` 的索引对应关系不被用户编辑破坏（如用户删除一个英文关键词但未删除对应中文）

**结论**：✅ 处理正确，完全解决 B5。建议在实施方案中补充关键词中英配对编辑的约束说明。

---

### B6 — maxOutputTokens 调整 → ✅ 通过

**处理决策**：`maxOutputTokens` 1024 → 4096，同时在 Prompt 中增加输出长度软约束

**复核**：
- 4096 tokens 对于预期输出（~2600 字符混合中英文 ≈ 1500-2000 tokens）有约 2x 余量，合理
- Prompt 端增加长度软约束是好的双保险设计（token 硬限制 + 语义软约束）
- 审核建议值为 2048-3072，4096 更充裕且不会显著增加成本（输出 token 按实际消耗计费，非按上限计费）

**结论**：✅ 处理正确，完全解决 B6。

---

### B7 — 事务顺序调整 → ✅ 通过

**处理决策**：先 `updateImportItem()` → 再 `submitRecommendation()`

**复核**：
- 调整后的事务语义正确：
  - 回写失败 → 阻止提交，弹窗保持，用户可修正后重试 ✅
  - 回写成功 + 提交失败 → 属性已更新（书架数据最新），推荐未创建（用户重试即可）✅
  - 无变更 → 跳过回写，直接提交 ✅
- 比原顺序（先提交后回写）的失败模式更安全：原顺序在提交成功但回写失败时，推荐记录和书架数据永久不一致
- ⚠️ **微注**：如果 `submitRecommendation` 内部仍从 `import_items` 读取 title/author 作为默认值（方案 §6.2），由于 `updateImportItem` 已先执行，读取到的将是更新后的值——此时参数中的覆盖值实际是冗余的。这是正确行为，但代码注释应标注此顺序依赖

**结论**：✅ 处理正确，完全解决 B7。

---

### B8 — Token 估算与成本预警 → ✅ 通过（部分采纳合理）

**处理决策**：
- 采纳：D1 增加定量成本分析、100K 字符输入上限（D12）、perf 中增加 token 计数字段
- 未采纳：前端展示 token 消耗提示

**复核**：
- 未采纳理由"0.6 美分的信息不会改变用户行为，反而在 UI 中引入噪音"——**合理**。对于个人用户，单次 ~$0.006 的成本确实不足以影响决策
- 100K 字符输入上限：对于英文阅读材料（500-5000 词 ≈ 3K-30K 字符），100K 相当于约 15000+ 词的文章，覆盖绝大多数场景，边界合理
- `_comment` 中标注"timeout 需根据套餐调整"——务实，但建议在部署文档中显式说明
- ⚠️ **微注**：`perf` 中的 `inputTokens`/`outputTokens` 字段依赖于 AI API 在响应中返回 `usage` 对象。Gemini 和 OpenAI-compatible API 均有此字段，但建议在 function 中做防御性读取（`usage?.prompt_tokens ?? null`），避免 API 变更导致解析失败

**结论**：✅ 处理合理，采纳/未采纳的边界清晰。B8 标记为"部分处理"准确。
