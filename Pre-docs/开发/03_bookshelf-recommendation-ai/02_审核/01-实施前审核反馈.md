## 一、阻塞项（实施前必须解决）

### 🔴 B1 — `config/recommendation.js` 的模块系统与前端消费冲突

**位置**：实施方案 §2.2，执行计划 Step 1

**问题**：
- 方案中 `config/recommendation.js` 使用 CommonJS 写法（`module.exports = { ... }`）
- 但前端 `aiProviders/index.js` 需要导入此配置——前端是 ESM 环境（已验证现有 `config/translation.js` 使用 `export const`）
- 同时 Netlify function（`translate.js`）是 CommonJS，也需要消费此文件
- CommonJS 文件无法在前端 ESM 环境中直接 `import`

**现有代码基准**：
- `config/presetModels.json` → JSON 格式，两边都能消费 ✓
- `config/translation.js` → ESM，仅前端消费 ✓
- 不存在"同一个 JS 配置文件被前端 ESM + 后端 CJS 同时消费"的先例

**建议**：
- **方案 A（推荐）**：`config/recommendation.js` 采用 ESM 写法（`export const`），Netlify function 通过 `createRequire` 或改用 `.mjs` 动态 import 消费
- **方案 B**：保持 CommonJS，前端通过构建工具（Vite/Webpack）的 CommonJS 互操作消费（需确认构建工具是否已配置）
- **方案 C**：拆分为 `config/recommendation.json`（静态数据）+ `config/recommendation.js`（ESM，仅前端逻辑）。JSON 部分两边都能消费

### 🔴 B2 — 缓存生命周期与 D3 决策的矛盾

**位置**：决策 D3，实施方案 §5.1，执行计划 Step 4

**问题**：
- D3 明确要求"弹窗关闭不清除（缓存）"
- 实施方案 §5.1 将 `generationCache` 定义为 `useState({})`——组件级 state
- 执行计划 Step 4.1 再次确认 `generationCache` 是 state
- **但现有 `SubmitRecommendationModal` 在被关闭时组件卸载，所有 state 丢失**

**现有代码基准**：
- 当前弹窗由父组件条件渲染（通过 `onClose` 回调控制显隐）
- 组件卸载 → `useState` 全部销毁
- 这意味着关闭弹窗再打开同一 item → 缓存必然丢失

**建议**：
- **方案 A（推荐）**：将 `generationCache` 提升到弹窗的父组件，通过 props 传入（或用 `useRef` + 条件渲染保持组件挂载）
- **方案 B**：改用 `useRef` 存储缓存，但弹窗组件必须保持挂载（用 CSS `display:none` 代替卸载），否则 ref 也会丢失
- **方案 C**：修改 D3 决策，接受"关闭弹窗后缓存丢失，仅在同一弹窗实例内缓存"
- 无论哪种方案，D3/实施方案/执行计划三者必须一致

### 🔴 B3 — Netlify Function 超时与前端超时设置不匹配

**位置**：决策 D9，实施方案 §2.2/§9，执行计划 Step 2

**问题**：
- 方案设置前端超时为 15 秒（`timeout: 15000`）
- Netlify 同步 Function 默认超时仅 **10 秒**（Starter 套餐），Pro 套餐为 26 秒
- 若部署在 Starter 套餐，Netlify 会在 10 秒时强制终止 function → 前端永远收不到响应 → 前端 15 秒超时永远不会触发 → 用户体验为"一直 loading 直到 15 秒"
- 对于处理 5000+ 词长文的 AI 调用，10 秒极可能不够

**建议**：
- 确认当前 Netlify 套餐的 Function 超时上限
- 若为 Starter（10s）：前端超时应设为 ≤ 9 秒（比 function 超时略短），或升级套餐
- 若套餐允许 ≥ 26s：前端超时设为 25s，方案中的 `15000` 也需相应调整
- 在 function 内部增加超时感知：如果在 9 秒时 AI 还未返回，主动 throw 避免 Netlify 硬杀

### 🔴 B4 — Provider 适配代码重复（维护风险）

**位置**：实施方案 §3.4，执行计划 Step 2 改动要点 2

**问题**：
- 方案明确写"复刻 `translate.js` 中已有的 `callGemini()` / `callDeepSeek()` / `callKimi()` / `callZhipu()` 模式"
- 这意味着将 4 个 provider 适配函数（每个 ~30-50 行）完整复制到新 function 中
- 未来任何 provider 的 API 变更、模型升级、bug 修复需要同时修改两处
- 现有 `translate.js` 中这些函数是文件内私有函数，无法直接复用

**建议**：
- **方案 A（推荐）**：将 provider 适配函数抽取到共享模块 `netlify/lib/aiProviders.js`，两个 function 共同引用
- **方案 B**：如短期无法重构，至少在代码中用注释标注"与 translate.js 保持同步"，并在执行计划中新增一个 Step 做重构
- 评估：共享模块需要约 30 分钟额外工作量，但可避免长期维护隐患

### 🔴 B5 — 降级模式下旧 state 的移除冲突

**位置**：实施方案 §5.1，执行计划 Step 4.1

**问题**：
- 执行计划 Step 4.1 明确写入"移除旧 state：`intro`, `keywords`, `keywordInput`, `excerpts`"
- 但 D9 降级策略要求"AI 区域切换为可编辑的空表单……用户可以手动填写"
- 如果移除了 `intro` / `keywords` / `excerpts` 这些手动填写的 state，降级模式下的可编辑表单就没有绑定的 state
- 矛盾：降级 UI 需要可编辑的表单字段，但旧的表单字段 state 被移除了

**建议**：
- 不移除旧 state，改为复用：AI 生成成功时填充 `aiIntro` 等专用 state，降级时仍用 `intro` / `keywords` / `excerpts` 作为可编辑表单的绑定
- 或者统一使用同一套 state：AI 生成成功 → 填入值；降级 → 展示空的可编辑字段；提交时统一从这套 state 取值
- 在实施方案 §5.1 和 执行计划 Step 4.1 中明确此设计

### 🔴 B6 — `maxOutputTokens: 1024` 估算不足

**位置**：实施方案 §2.2

**问题**：
- 方案设置 `maxOutputTokens: 1024`
- 按方案要求，AI 需要输出：intro（2-4句中，~200字符）+ keywords（3-4个英文+中文，~80字符）+ excerpts（3条×≤400字符原文）+ excerpts_trans（3条中文翻译）
- 仅 3 条摘录原文（≤400字符/条）= 1200 字符；中文翻译再 1200 字符；总计约 2600+ 字符
- 混合中英文 token 估算：中文 ~2 tokens/字 → 摘录翻译 ~800 tokens；英文 ~0.3 tokens/字 → 摘录 ~360 tokens；intro + keywords ~300 tokens。合计约 **1500-2000 tokens**
- 1024 tokens 上限可能导致输出被截断，尤其摘录部分

**建议**：
- `maxOutputTokens` 至少设为 **2048**，建议 3072 以留有余量
- 在 Prompt 中增加输出长度约束（如每条摘录翻译不超过 200 字），从两端控制

### 🔴 B7 — 提交与属性回写缺少事务性保护

**位置**：实施方案 §6.3，执行计划 Step 5

**问题**：
- 逻辑分两步：`submitRecommendation()` 写入 `recommendation_submissions` → 然后 `updateImportItem()` 回写 `import_items`
- 如果第一步成功、第二步失败 → 数据不一致：推荐库中的记录使用了修改后的标题，但书架上仍是旧标题
- 如果第一步失败、第二步没有执行 → 用户修改的标题丢失，下次打开弹窗仍是旧值

**建议**：
- 调整顺序：先调用 `updateImportItem()` 回写 → 再 `submitRecommendation()` 写入推荐记录
  - 若回写失败 → 不提交推荐，弹窗保持打开，告知用户
  - 若回写成功但提交失败 → 属性已更新（良性），推荐未创建（告知用户重试）
- 或者用 Supabase 的 `maybeSingle` + 错误补偿逻辑（成本较高）
- 至少在执行计划中增加此项验证

### 🔴 B8 — 缺少 token 估算与成本预警机制

**位置**：决策 D1，实施方案 §3

**问题**：
- D1 声称"典型英文阅读材料 500–5000 词"、"成本差异微不足道"
- 但未做任何定量分析：5000 词 ≈ 7000-10000 tokens（输入）+ ~2000 tokens（输出）= ~9000-12000 tokens/次
- 如果用户频繁重新生成（关闭弹窗再打开 → 缓存丢失，见 B2），成本可能快速累积
- 方案中未设计任何 token 计数或用户提示（如"正在生成，本次预计消耗约 X tokens"）
- D1 没有讨论"如果文章超过某个阈值（如 20K words）怎么办"的边界条件

**建议**：
- 在 function 返回的 `perf` 对象中增加 `inputTokens` / `outputTokens` 字段（若 API 返回）
- 前端展示"正在生成…"时附带 token 消耗提示
- 在 D1 中补充边界条件讨论：文章超过 N 字时是否截断或提示用户
- 在配置中增加 `maxInputTokens` 阈值，超过时前端警告用户

## 二、建议项（建议实施前讨论，不阻塞启动）

### 🟡 S1 — Prompt 缺少摘录位置溯源信息

**位置**：实施方案 §7.2

Prompt 模板要求 AI 返回 verbatim 摘录，但没有要求 AI 标注摘录在原文中的位置（如段落编号）。这对用户验证摘录真实性非常重要——用户无法快速确认 AI 是否真的从原文选取。

**建议**：在 `excerpts` 结构中加入可选的 `position` 字段（如 "paragraphs 3-5"），或在 Prompt 中要求 AI 标注来源位置。前端可选展示此信息。

### 🟡 S2 — 缺少对 `importItem.sections` 为空或格式异常的处理

**位置**：实施方案 §5.2 核心流程

流程写"遍历 `item.sections` → 拼接所有 `body.text`"，但未覆盖：
- `sections` 为 `null` / `undefined`
- `body` 为 `null` / `undefined`
- 拼接后文本为空字符串

**建议**：在核心流程和错误处理矩阵中补充此场景。建议在拼接后增加长度校验：若文本为空或过短（< 100 字符），禁用生成按钮并给出提示。

### 🟡 S3 — 前端超时的实现机制未明确

**位置**：实施方案 §4.2、§9

方案提及 `AbortSignal` 和 15 秒超时，但：
- `generateRecommendationContent` 接受 `signal` 参数，但谁创建 AbortController？
- 超时（15s）和用户取消（关闭弹窗）是否使用同一个 AbortController？
- 现有 `aiProviders/index.js` 的 `makePresetTranslate` 已使用 `fetch(..., { signal })`——新函数是否复用此模式？

**建议**：在实施方案 §4.2 中明确 AbortController 的创建位置（建议在弹窗组件中创建，同时绑定超时 `setTimeout` 和弹窗关闭事件）。

### 🟡 S4 — 关键词和摘录的编辑交互细节缺失

**位置**：实施方案 §5.3 UI 结构，执行计划 Step 4.4

方案提到"tag 列表展示，可单个删除，可手动添加（上限 4 个）"，但未描述：
- 双语关键词如何配对展示和编辑？（英文 tag + 中文 tag 的视觉关联）
- 用户手动添加关键词时，是否需要同时输入中英文？还是一个一个加？
- 摘录编辑区的原文和翻译如何配对视效？

**建议**：在实施方案中补充关键词/摘录编辑的交互细节（至少包括配对关系、添加流程）。

### 🟡 S5 — `kind` 字段的 `article` vs `book` 对 Prompt 生成质量的影响未讨论

**位置**：决策 D5/D6，实施方案 §7.2

Prompt 模板中仅将 `kind` 作为信息字段传入（`TYPE: {kind}`），但未在 Prompt 指令中区分书籍和文章的策展策略差异：
- 书籍可能需要不同的摘录选取策略（章节级别的代表性）
- 书籍的 intro 可能需要不同的推荐角度

**建议**：在 Prompt 中针对 `kind` 值微调指令（如书籍强调"选取各章节最具代表性的段落"）。在 D6 中补充此考量。

### 🟡 S6 — 缺少 API key 轮换/故障转移的说明

**位置**：实施方案 §2.4、§3.3

方案提到 `activePreset` 和 `fallbackPreset`，function 内部有重试一次的逻辑，但：
- 重试是同 provider 重试还是切换 provider 重试？
- `fallbackPreset` 何时被使用？（当前仅在配置中声明，function 逻辑未引用）
- 如果 primary provider 的 API key 配额耗尽，如何自动切换？

**建议**：明确重试策略——同 provider 重试 1 次 → 仍失败则切换 `fallbackPreset` → 仍失败则降级。在 Netlify function 逻辑中引用 `fallbackPreset`。

### 🟡 S7 — 执行计划遗漏：环境变量配置步骤

**位置**：执行计划

执行计划未包含以下必要步骤：
- 在 Netlify Dashboard 配置新增的 API key 环境变量（或确认复用现有 keys）
- 在 `.env.example` / `.env` 中新增推荐相关环境变量
- 更新环境变量文档（若有）

**建议**：在 Step 1 或 Step 2 之前新增"Step 0：环境变量准备"，或在 Step 2 验收标准中增加环境变量检查项。

### 🟡 S8 — 缺少对已有推荐记录的兼容性验证

**位置**：执行计划 Step 6 集成验证

检查项未覆盖：
- 已有的 `recommendation_submissions` 记录（`keywordsTrans` / `excerptsTrans` 之前为 null）现在是否正常展示
- 混合场景：旧提交（手动填写）+ 新提交（AI 生成）在推荐列表中共存是否正常

**建议**：在集成验证中增加 1-2 条兼容性检查项。

### 🟡 S9 — 并发问题未考虑

**位置**：全局

同一用户可能在多个标签页中打开应用，此时：
- 两个标签页各自有独立的缓存，可能生成不同结果
- 两个标签页可能同时提交同一 import item 的推荐（`checkSubmissionEligibility` 在第二个标签页可能已过期）

**建议**：当前方案中 `checkSubmissionEligibility` 已有服务端校验，第二个问题可能已有保护。但建议在决策记录中注明"多标签页场景暂不处理"作为已知限制。

### 🟡 S10 — `tokenLimits` 配置仅在服务端有效，前端无法使用

**位置**：实施方案 §2.2

`config/recommendation.js` 中的 `tokenLimits` 在 Netlify function 中使用 `require` 消费（正确），但前端服务层也导入此配置——`tokenLimits` 在前端无意义（前端不直接调 AI API，不构造请求体中的 maxTokens），且可能导致困惑。

**建议**：将 `tokenLimits` 标注为"服务端专用"，或将其拆分到仅服务端消费的配置段中。

### 🟡 S11 — 执行计划缺少 Step 间接口契约定义

**位置**：执行计划

各 Step 有依赖关系，但未定义 Step 间的接口契约：
- Step 2 产出什么？（function URL + request/response schema）
- Step 3 期望消费什么格式？
- Step 4 期望 `generateRecommendationContent` 返回什么类型？

**建议**：在执行计划中为每个 Step 增加"产出物"描述，使各 Step 可独立验证。

### 🟡 S12 — Netlify function 缺少请求大小保护

**位置**：实施方案 §3.3

Function 接收完整的 `articleText`，第 2 步"校验必填字段（articleText, title）"仅检查是否为空，未检查大小上限。如果前端 bug 导致发送异常大的文本，function 可能因内存或 payload 超限而崩溃。

**建议**：增加 `articleText` 长度上限校验（如 50K 字符），超出时返回 413 错误。
