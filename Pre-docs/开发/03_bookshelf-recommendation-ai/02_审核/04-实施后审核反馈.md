## 三、阻塞项清单

### 🔴 X1 — `kind` 字段全链路缺失（F1, F4, J1 关联）

**影响范围**：弹窗 UI → Netlify function → 提交服务，共涉及 3 个检查项不通过。

**具体表现**：

1. **UI 层（F1, F4）**：`SubmitRecommendationModal.jsx` 中没有 `kind` state，没有「文章/书籍」segment toggle 控件。设计方案 §6.4 明确要求"形态 [文章] [书籍] (segment toggle)"。

2. **Function 层**：`generate-recommendation.js` 的 `buildPrompt()` 硬编码 `TYPE: article`，不接受 `kind` 参数。前端虽然发送了 `kind` 字段（recommendation.js:43），但 function 完全忽略。设计方案 §8.2 明确要求根据 `kind` 动态注入 `{EXCERPT_STRATEGY}`（文章强调论证核心，书籍强调章节代表性）。

3. **提交服务层（J1）**：`submitRecommendation()` 不接受 `kind` 参数，无法在属性变更时将 `kind` 回写到 `import_items`。设计方案 §7.1 明确要求 `kind` 可选参数"仅用于回写 import_items.kind"。

**修复建议**：
- 弹窗中新增 `kind` state（默认值取自 `item.kind`），添加 segment toggle UI
- `generate-recommendation.js` 的 `buildPrompt()` 接受 `kind` 参数，实现 `{EXCERPT_STRATEGY}` 动态注入
- `submitRecommendation()` 接受 `kind` 参数，加入属性变更检测和回写逻辑

### 🔴 X2 — `perf` 对象缺少 `inputTokens` / `outputTokens`（C5）

**位置**：`netlify/functions/generate-recommendation.js:216-231`

**具体表现**：返回的 `perf` 对象包含 `inputChars`（字符数），但不包含 `inputTokens` 和 `outputTokens`。反馈处理记录 B8 明确要求"在 function 返回的 `perf` 中增加 `inputTokens` / `outputTokens` 字段（若 API 返回）"。

**影响**：无法追踪实际 token 消耗，成本核算缺失数据来源；与设计方案的 `perf` schema（§4.2）不一致——方案明确列出 `"inputTokens": 7200, "outputTokens": 3400`。

**修复建议**：
- 在 `callProvider()` 返回后，从 AI API 的原始响应中提取 `usage.prompt_tokens` / `usage.completion_tokens`（Gemini 和 OpenAI-compatible API 均有此字段）
- 在 `perf` 对象中添加 `inputTokens` / `outputTokens` 字段（若 API 未返回则为 null）
- 需要在共享适配层（`aiProviders.cjs`）中返回 token 信息，或单独从原始响应中提取

## 四、建议项清单

### 🟡 Y1 — 共享模块文件名与设计文档不一致（B1）

**位置**：`netlify/lib/aiProviders.cjs`

审核请求和设计文档中引用路径为 `netlify/lib/aiProviders.js`，实际文件名为 `aiProviders.cjs`。`.cjs` 扩展名明确标识了 CommonJS 模块类型，在 Netlify function 环境中是正确的选择。但文档引用需同步更新，且 `translate.js` 中已正确使用 `.cjs` 扩展名引用，说明实施时已意识到此问题。

**建议**：更新设计文档中的文件引用路径为 `aiProviders.cjs`，或在文档中注明"实际文件使用 `.cjs` 扩展名以明确 CommonJS 模块类型"。

---

### 🟡 Y2 — `constraints` 的 `_comment` 标注不准确

**位置**：`config/recommendation.json:7`

`_comment.constraints` 标注为"前端专用"，但 `generate-recommendation.js` 中同样读取了 `recConfig.constraints.maxKeywords` 和 `recConfig.constraints.maxExcerpts` 用于 `normalizeResult()` 截断。实际为**前后端共用**。

**建议**：将 `_comment.constraints` 修正为"前端+服务端共用。控制 UI 输入限制和 API 返回结果截断"。

---

### 🟡 Y3 — 重试策略与设计文档不完全一致（C8）

**位置**：`generate-recommendation.js:194-253`

设计方案 §4.4 的故障转移路径是"同 provider 重试 1 次 → 切换 fallbackPreset"，未区分错误类型。实际实现中：JSON 解析失败 → 同 provider 重试；API 错误 → 直接切换 provider（不重试同 provider）。

**评估**：实施中的分类处理实际上是**更合理**的设计——API 错误（如 401 无效 key、429 限流）在同 provider 上重试几乎必然失败，直接切换 fallback 减少了无效等待。JSON 解析失败重试同 provider 是合理的（AI 的 JSON 输出具有随机性）。

**建议**：在代码注释中说明分类重试的理由，或在设计文档中更新故障转移路径说明。

---

### 🟡 Y4 — 关键词最小数量无后端强制校验（C4）

**位置**：`generate-recommendation.js:98-109`

Prompt 要求 3-4 个关键词，`normalizeResult` 仅做了上限截断（≤ 4）。若 AI 仅返回 1-2 个关键词，后端不会拒绝。虽然这是合理的容错策略（不过度阻塞用户），但与 Prompt 的"3-4 English keywords"要求存在软性不一致。

**建议**：当前策略可接受（容错优先）。若希望更严格，可在 `normalizeResult` 后增加 warning 日志（关键词不足 3 个时记录 warn），便于后续监控 AI 输出质量。

---

### 🟡 Y5 — 弹窗提交时 `excerpts` / `excerptsTrans` 过滤空条目后可能少于 3 条

**位置**：`SubmitRecommendationModal.jsx:272-273`

`handleSubmit` 中 `excerpts: excerpts.filter(e => e.trim())` 和 `excerptsTrans: excerptsTrans.filter(e => e.trim())` 会过滤掉空条目。如果 AI 返回的 excerpts 不足 3 条且用户未手动补充，提交的 excerpts 数组长度可能为 0/1/2。虽然 `canSubmit` 仅要求"至少 1 条非空"，但 `excerpts` 和 `excerptsTrans` 过滤后的索引对应关系可能被打破。

**建议**：过滤 `excerpts` 时同步过滤 `excerptsTrans`（保持索引对应），或提交时使用配对过滤逻辑。

---

### 🟡 Y6 — `buildPrompt` 不支持 `author` 为空的优雅降级

**位置**：`generate-recommendation.js:29-30`

```js
const authorDisplay = author || 'Unknown'
```

当 author 为空时，Prompt 中显示 `AUTHOR: Unknown`。AI 可能会在 intro 中写出"作者 Unknown 的这篇文章..."这样的尴尬表述。设计方案的 Prompt 模板中使用 `{author or "Unknown"}`，但更优雅的做法可能是不显示作者行或写"AUTHOR: Unknown (anonymous)"。

**建议**：将 `'Unknown'` 改为空值时的提示措辞，或在 Prompt 中调整为"如果作者未知则不强调作者信息"。

---

### 🟡 Y7 — `title` 变更检测逻辑忽略空字符串覆盖场景

**位置**：`recommendationService.js:359`

```js
if (overrideTitle && overrideTitle !== item.title) attrChanges.title = overrideTitle
```

条件 `overrideTitle &&` 意味着如果用户将 title 清空后再提交（虽然 `canSubmit` 阻止了这种情况），变更检测不会触发。这在实际使用中不会造成问题（因为 `canSubmit` 要求 title 非空），但逻辑不够防御性。

**建议**：改用 `if (overrideTitle !== undefined && overrideTitle !== item.title)`，与 `author` 和 `sourceUrl` 的检测逻辑保持一致。
