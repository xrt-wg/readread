### 2.3 Solution Rationality — 方案合理性 ⭐⭐⭐⭐☆

**优点：**

1. **核心原则正确**。"优先使用现有 CSS 变量，不新建变量"——这与根因分析（令牌体系完整，执行偏离）完全对齐。

2. **令牌速查表实用**。§1.2 的设计令牌速查表将每种硬编码模式映射到对应 CSS 变量，是高质量的工程参考。

3. **阴影处理方案有明确的决策过程**。§1.3 给出了方案 A（新建 `--card-shadow`）和方案 B（复用 `--popup-shadow`），并说明了选择 A 的理由（卡片阴影比弹窗阴影更轻）。这符合 DRS Phase 4 的要求。

4. **品牌 Slogan 修复巧妙**。将 `linear-gradient(175deg, #1c1917 10%, #3d2b1e 100%)` 改为 `linear-gradient(175deg, var(--ink) 10%, var(--ink-light) 100%)` ——利用 `--ink` 在日间是深色、夜间是浅色的特性，一行改动解决了两个模式下的可读性。这是"用系统而非硬编码思考"的范例。

5. **HIGHLIGHT_STYLES 的修复方案有对比度补偿意识**。夜间模式下 `--hl-word-bg` 从 `0.35` 提升到 `0.45` 不透明度以在深色背景上保持可辨识性——这体现了对视觉原理的理解，而不仅仅是机械替换。

**问题：**

1. **`#2d2926` → `#3d3934` 替换违反自身原则** 🔴（详见 [关键问题 P1](#31-p1-2d2926--3d3934-替换方案违反设计令牌原则)）。修复方案自身的原则是"优先使用现有 CSS 变量"，但当遇到 dark hover 场景时，选择了创建一个新的硬编码值 `#3d3934`，且该值会被复制到 5+ 个文件中。正确做法应是新增一个 CSS 变量（如 `--btn-hover-bg`）。

2. **`#3d3934` 的选择逻辑有缺陷**。§2.2.3 解释为"在两种模式下都能与周边区分"。但这个值在日间模式下表现为中灰色（与原 `#2d2926` 不同），在夜间模式下比背景 `#1a1814` 略亮。由于这是一个同时在两种模式下使用的单一值，它是对比度的折衷而非最优解。如果用 CSS 变量，可以为两种模式分别指定最优值。

3. **ImportPage 推荐卡片 hover 阴影使用了新的硬编码**。§3.1.3 中 `onMouseEnter` 的 `boxShadow` 使用了 `rgba(0,0,0,0.12)` ——虽然是纯黑系（在两种模式下都可用），但仍然是硬编码。建议统一使用 `var(--card-shadow)` 或将 hover 态阴影也定义为变量。

4. **导航 Tab 按钮的阴影使用了新的硬编码**。§3.2.10 中 `boxShadow: view === id ? '0 1px 3px rgba(0,0,0,0.06)' : 'none'` ——又一个新硬编码。应统一使用 CSS 变量。

**建议：**
- 将 `#3d3934` 替换方案改为新增 CSS 变量 `--btn-hover-bg`（见下方具体建议）。
- 统一所有阴影引用为 CSS 变量，消除新增的纯黑硬编码阴影。
- 对应修正执行计划中的相关步骤。

### 2.4 Alternative Review — 方案比较 ⭐⭐⭐☆☆

**优点：**

1. **阴影方案做了二选一比较**（方案 A vs 方案 B），有决策理由。
2. **HIGHLIGHT_STYLES 做了二选一比较**（JS 动态读取 vs CSS 变量），选择了与项目现有策略一致的方案 B。

**问题：**

1. **整体策略层面未做方案探索**。三份文档都默认采用"逐组件替换硬编码为 CSS 变量"的策略，但未讨论是否有其他可行路径，例如：
   - **CSS 文件方案**：将组件的内联 `style` 提取到 CSS 文件中，通过 `.theme-night` 类选择器覆写，减少 JSX 改动量。
   - **PostCSS/Tailwind 主题插件**：利用 Tailwind 的 `dark:` 前缀或自定义主题函数，一次性解决所有 Tailwind 硬编码类（如分析中提到的 `border-amber-200`、`bg-amber-50`）。

2. **hover 暗色没有方案比较**。`#2d2926` → `#3d3934` 看上去是拍脑袋的一个值，未比较其他选项（如使用 CSS 变量、使用 `var(--ink)` 的半透明叠加、使用 `filter: brightness()` 等）。

**建议：**
- 在修复方案中补充一个"被排除的方案"小节，简要列出未采用的路径及排除原因。这不影响实施，但能提升方案的说服力和可维护性。

**优点：**

4. **对比度补偿策略可复用**。夜间模式下略微提高半透明颜色的不透明度（如高亮色 +0.10）是一个可复制的微调策略。

## 三、关键问题（Critical Issues）

### 3.1 P1：`#2d2926` → `#3d3934` 替换方案违反设计令牌原则 🔴

**问题描述：**

修复方案将 5 个文件中的 `#2d2926` hover 色替换为 `#3d3934`。但 `#3d3934` 本身就是一个新的硬编码值——这恰恰是本次修复要消除的反模式。此外：

| 出现位置 | 文件 | 是否在方案中覆盖 |
|---|---|---|
| ReviewPanel L170 | `ReviewPanel.jsx` | ✅ 已覆盖 |
| ReviewModal L283 | `ReviewModal.jsx` | ✅ 已覆盖 |
| ImportPage L613 | `ImportPage.jsx` | ✅ 已覆盖 |
| ImportItemEditor L159 | `ImportItemEditor.jsx` | ❌ 未覆盖（P2 范围但未明确） |
| ImportPanel L196 | `ImportPanel.jsx` | ❌ 未覆盖（P2 范围但未明确） |
| index.css L327 | `index.css` | ❌ 未提及 |

**影响：** 如果按当前方案实施，`#3d3934` 将成为一个分散在 5+ 处的硬编码值，未来调整需要全局搜索替换——与本次修复之前的 `#2d2926` 问题完全相同。

**建议修改：**

在 `index.css` 中新增 `--btn-hover-bg` 变量：

```css
/* :root 块中 */
--btn-hover-bg: #2d2926;  /* 日间：深色 hover */

/* [data-theme="night"] 块中 */
--btn-hover-bg: #3d3934;  /* 夜间：比背景略亮 */
```

然后所有 `#2d2926` 位置统一替换为 `var(--btn-hover-bg)`。同时修复 `index.css` L327 中的 `background: #2d2926;`。

**优先级：** 实施前必须修正。这会连带影响执行计划的 Phase 1.2、1.3、2.1、4.3 以及 Phase 0 的 CSS 变量清单。

### 3.3 P3：存在未覆盖的硬编码阴影 🟡

**问题描述：** 修复方案在多处使用硬编码的纯黑阴影值，如：
- §3.1.3：`rgba(0,0,0,0.12)` — 推荐卡片 hover 阴影
- §3.2.10：`rgba(0,0,0,0.06)` — 导航 Tab 阴影
- §2.3.2：直接复用 `var(--popup-shadow)` — 这是正确做法

这些纯黑阴影虽然比原来的 ink 色阴影（`rgba(28,25,23,...)`）更通用，但仍然是分散的硬编码值。如果以后需要全局调整阴影的视觉权重，需要多处修改。

**建议修改：** 将 hover 态阴影也纳入 CSS 变量体系，例如扩展现有的 `--card-shadow` 或新增 `--card-shadow-hover`：

```css
/* :root */
--card-shadow-hover: 0 2px 16px rgba(0,0,0,0.08), 0 0 0 1px rgba(196,154,60,0.12);

/* [data-theme="night"] */
--card-shadow-hover: 0 2px 16px rgba(0,0,0,0.35), 0 0 0 1px rgba(196,154,60,0.2);
```

**优先级：** 中。可以当前方案先行实施，在 P2 阶段统一收尾。但如果希望本次修复"一步到位"，建议在 Phase 0 一并定义。
