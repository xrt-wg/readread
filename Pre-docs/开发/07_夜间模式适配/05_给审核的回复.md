## 讨论 1：量化成功标准 — 指标 vs 清单

### 你的建议

> 定义量化的成功标准：夜间模式使用率、回顾区完成率、推荐区点击率、主题切换次数。

### 我的顾虑

这个项目目前**没有埋点基础设施**。没有 Google Analytics、没有 Supabase events 表、没有任何用户行为数据采集。如果以"先搭建 analytics → 采集基线 → 修复 → 对比数据"作为前置条件，一个 3.75 小时的视觉修复会膨胀为数天的工程任务，而最终回答的问题本质上仍然是"夜间模式看起来对不对"。

**这不是反对埋点**——埋点确实应该做，但它是一个独立的 feature，不应阻塞视觉 bug 修复。

### 我的替代方案

用**结构化的人工走查**替代数据指标，本质上回答的是同一个问题——"修完之后，用户在夜间模式下能正常使用吗？"

| 维度 | 检查项 | 判定标准 |
|---|---|---|
| 回顾闭环 | 闪卡正面/反面可读、翻面动画正常、反馈按钮可区分 | 3/3 通过 |
| 推荐浏览 | 推荐列表可读、卡片 hover 可辨识、详情弹窗正常 | 3/3 通过 |
| 阅读体验 | 正文可读、目录面板正常、结束标记可见、「已读完」按钮不刺眼 | 4/4 通过 |
| 品牌区域 | Slogan 文字在夜间模式下清晰可见 | 1/1 通过 |
| 日间回归 | 以上所有区域在日间模式无视觉回退 | 对照截图一致 |
| 用户走查 | 2-3 人实际使用，无阻塞性问题 | ≥2/3 通过 |

全部通过即视为成功。这个方法**可量化**（通过/不通过）、**可复现**（checklist 是固定的）、**不依赖额外基础设施**。

## 讨论 2：`--card-shadow-hover` 的设计范围

### 你的建议

```css
--card-shadow-hover: 0 2px 16px rgba(0,0,0,0.08), 0 0 0 1px rgba(196,154,60,0.12);
```

### 我的顾虑

第二个值 `0 0 0 1px rgba(196,154,60,0.12)` 是金色外描边。这是**推荐卡片 hover 的专属设计**——当用户 hover 推荐卡片时，出现金色边框表示"这是可交互的精选内容"。但回顾闪卡 hover 不会也不需要金色描边。如果把这个写入变量：

- 变量名叫 `--card-shadow-hover`，但实际上包含了一个**语义化的设计决策**（金色 = 精选/推荐），而不只是阴影抬升
- 用到回顾区时会产生错误的设计效果，或者需要额外覆盖
- 违背了"令牌是纯视觉值，不是设计决策"的原则

### 我的替代方案

`--card-shadow-hover` 只做一件事：阴影抬升的视觉权重。

```css
/* :root */
--card-shadow-hover: 0 2px 16px rgba(0,0,0,0.08);

/* [data-theme="night"] */
--card-shadow-hover: 0 2px 16px rgba(0,0,0,0.35);
```

金色描边保留在推荐卡片的组件内联样式中，作为那个组件独有的设计决策——它本来就应该在那里：

```jsx
// 推荐卡片 onMouseEnter
e.currentTarget.style.boxShadow = 'var(--card-shadow-hover), 0 0 0 1px rgba(196,154,60,0.12)'
```

这样阴影是系统级的，"金色描边"是推荐卡片专属的。职责分离清晰。

### 需要你对齐

你是否接受 `--card-shadow-hover` 只包含阴影、不包含金色描边？还是你认为推荐卡片的 hover 态是一个足够通用的模式，值得作为一个整体令牌？

## 讨论 3：stylelint 规则的引入时机

### 你的建议

> 考虑引入 stylelint 或 ESLint 规则检测硬编码颜色（可作为后续优化，不阻塞本次实施）。

### 我的判断

你的原文已经标注了"可作为后续优化，不阻塞本次实施"——所以这一点其实我们已经共识了。但我想补充为什么不应在本次迭代引入：

1. **stylelint 配置需要独立的设计讨论**：哪些颜色允许硬编码（语义色如红/绿/琥珀反馈按钮？gold 色系？），哪些必须走变量。这些规则的边界需要团队约定，不是一个人拍板的。
2. **需要独立验证**：引入 lint 规则后必然有大量 existing violations，需要决定是修还是 suppress，这本身是一个独立的工程任务。
3. **修复先行，规则兜底**：先把本次 60+ 处修完，再上规则防止回归——这是正确的顺序。

### 需要你对齐

确认 stylelint/ESLint 规则作为独立 issue 跟踪，不在本次修复范围内。如果你希望我在本次修复的 Phase 5 中产出一份"推荐的 lint 规则草案"作为后续输入，我可以做。
