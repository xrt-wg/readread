# 订阅信息展示 — 讨论和决策记录

> 日期：2026-09-24
> 性质：需求与实现路径决策存档（非实施文档）
> 关联：[26_订阅机制](../26_订阅机制_2026-09-23/02_订阅机制说明.md)

## 定位

订阅机制（26）已上线，但存在两处「看不到身份/期限/额度」的展示缺口：账户弹窗 Pro 无有效期；后台用户列表无 Free/Pro 与额度/期限。本特性补齐这两处展示，**不改动订阅机制本身**。

## 需求

1. 账户弹窗：Pro 用户显示有效期。
2. 后台「用户基础信息」：每个用户显示 Free/Pro；Free 显示额度，Pro 显示期限。

## 决策

- **口径**：Free 显示「剩余导入 + 本周收藏」两项；Pro 只显示到期日（不显示来源）；日期只到 YYYY-MM-DD。
- **实现路径（需求 2）**：方案 A —— 独立 admin RPC + 前端 merge（见下方多方讨论）。
- **时区**：到期日定死北京时间（Asia/Shanghai），防跨时区差一天。
- **静默降级**：订阅 RPC 未就绪时，后台列表降级为「仅基础信息」，不阻断。

## 多方讨论（方案 A vs B）

组织 4 角色（数据架构 / 前端 / 安全 / 产品）独立评估，一致否决 D（放开 RLS 直查——列级不可控、越权泄露）、C（security barrier 视图——过度设计、承载不了派生口径）、E（profiles 冗余——双源真相必漂移）；分歧在 A vs B（2:2）：

- **A**（数据架构 + 安全）：独立 `admin_list_user_subscriptions()` RPC，与 profiles 并行、按 userId merge；不动稳定的 profiles 查询，订阅口径集中服务端，与 `get_subscription_status` 同源。
- **B**（前端 + 产品）：合并 RPC（profile+订阅）替换 `listAdminProfiles`，单次往返、零 merge。

最终定 **A**：订阅口径本就应服务端集中、与用户端 RPC 同源；不碰 profiles 读路径、爆炸半径最小；B 的「单次往返」收益在 merge 近零成本、后台已并行拉取的前提下很弱，却要付出「把 profiles 从 RLS 直读改成 security definer + 与订阅耦合」的代价。
