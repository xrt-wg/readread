## 二、总体技术路线

### 2.1 核心策略：增量叠加，不重构

```
现有架构                        新架构
────────                        ────────
articles 表         ──保持──→   articles 表 (+2 字段)
提取器 EXTRACTORS    ──复用──→   提取器 EXTRACTORS（不变）
Document 模型        ──复用──→   Document 模型（不变）
createDocument()    ──复用──→   createDocument()（不变）
                              +
                              import_items 表（新增）
                              createImportItem()（新增工厂函数）
                              copyToReadingZone()（新增操作）
```

一切现有能力保持原样。新功能是在现有基础上**叠加**，不是替代。

**为什么这么做？**
- 当前 articles → Bookmark / ReadingProgress / 回顾面板的整个下游链路已经稳定
- 重构这些链路风险高、收益低——它们不需要感知 import_items
- 叠加策略让回滚成本趋近于零——最坏情况只是 hide 导入区入口

## 三、后端实施路线

### 3.1 为什么先做数据库再做服务层？

数据库 schema 是后续一切工作的硬基础。服务层代码错了可以改，但 migration 一旦执行，回滚成本高。因此：

1. **先在 staging 分支验证 SQL**——建表、索引、RLS、约束
2. **用现有测试数据验证回填逻辑**——确保旧数据迁移后查询正常
3. **再写服务层代码**——建立在已验证的 schema 之上

### 3.2 服务层设计

#### 3.2.1 模块组织

```
src/services/
  importItems.js       ← 新增：导入区 CRUD + copyToReadingZone
  library.js           ← 修改：mapArticleRow 增加 source_import_id / imported_at
  extractors/
    index.js           ← 不变
    ...
```

不创建 `importItemStore`——导入区是纯云端数据（仅登录用户可用），不需要 localStorage 同步。直接通过 `importItems.js` 服务层操作 Supabase。

**为什么不用 localStorage？**
- 导入区内容需要编辑，编辑体验在 localStorage 上不可靠（多 tab、清理浏览器数据）
- 共享池依赖云端数据，本地存储无法共享
- 与当前"匿名用户仅体验阅读"的门控策略一致

#### 3.2.2 importItems.js 接口设计

```js
// 查询
fetchImportItems(userId)           → ImportItem[]
fetchImportItemById(id)            → ImportItem | null
fetchImportItemTitlesByIds(ids)    → Map<string, string>  // 批量查询，避免 N+1

// 写入
createImportItem(extractionResult, { userId, origin?, shareSourceId? }) → ImportItem
updateImportItem(id, patch)        → ImportItem

// 删除（RPC 原子操作）
countImportReferences(importItemId) → number
deleteImportItem(importItemId)      → void  // 调用 RPC delete_import_item

// 移入操作
copyToReadingZone(importItem)      → Document
```

#### 3.2.3 copyToReadingZone 的实现细节

```js
async function copyToReadingZone(importItem) {
  // 1. 深拷贝 sections——这是"独立副本"的保证
  const sections = structuredClone(importItem.sections)

  // 2. 构造 ExtractionResult-like 对象（复用 createDocument 工厂）
  const extractionResult = {
    meta: {
      title:     importItem.title,
      author:    importItem.author,
      format:    importItem.format,
      coverUrl:  importItem.cover_url,
      lang:      importItem.lang,
      sourceUrl: importItem.source_url ?? undefined,  // 保留 URL 导入溯源
    },
    sections: sections.map((s, i) => ({
      heading:  s.heading,
      depth:    s.depth,
      order:    s.order,
      body: {
        text:     s.body.text,
        markdown: s.body.markdown,
      },
    })),
  }

  // 3. 工厂函数生成 Document（分配新 id、新 wordCount、deriveParentIds）
  const document = createDocument(extractionResult)

  // 4. 设置溯源字段
  document.source_import_id = importItem.id
  document.imported_at = new Date().toISOString()
  document.sourceType = importItem.format  // 映射格式到 source_type，避免全部标记为 'manual'

  // 5. 写入 articles 表
  await saveArticle(document, { userId: importItem.user_id })

  return document
}
```

#### 3.2.4 sections 装配逻辑抽取为共享函数

`createDocument` 和 `createImportItem` 都需要相同的 sections 装配逻辑（分配 id、deriveParentIds、计算 wordCount）。当前 `createDocument` 将此逻辑内联在函数体中——需要抽取为独立函数以避免代码重复。

在 `src/services/extractors/index.js` 中新增两个导出：

```js
/**
 * 从 ExtractionSection 数组装配完整的 Section 数组。
 * 职责: 分配 id、计算 wordCount。
 * 注意: parentId 由 deriveParentIds 单独推导。
 */
export function assembleSections(extractionSections) {
  return extractionSections.map((s, i) => ({
    id:       `s_${i}`,
    heading:  s.heading,
    depth:    s.depth,
    parentId: null,  // 下一步由 deriveParentIds 填充
    order:    s.order,
    body: {
      text:      s.body.text,
      markdown:  s.body.markdown,
      wordCount: s.body.text.split(/\s+/).filter(Boolean).length,
    },
  }))
}

/**
 * 根据 depth 推导每个 section 的 parentId。
 * 规则: 向前找最近的 depth 更小的 section，若存在则为父节点，否则为顶层节点。
 */
export function deriveParentIds(sections) {
  const stack = []
  for (const section of sections) {
    while (stack.length > 0 && stack[stack.length - 1].depth >= section.depth) {
      stack.pop()
    }
    section.parentId = stack.length > 0 ? stack[stack.length - 1].id : null
    stack.push(section)
  }
}

/**
 * 生成业务 ID。
 */
export function generateId(prefix) {
  return `${prefix}${Date.now()}_${Math.random().toString(36).slice(2, 7)}`
}
```

重构后的调用关系：

```
createDocument(result):
  sections = assembleSections(result.sections)
  deriveParentIds(sections)
  id = generateId('doc_')
  // ... 组装 Document

createImportItem(result, options):
  sections = assembleSections(result.sections)
  deriveParentIds(sections)
  id = generateId('imp_')
  // ... 组装 ImportItem
```

**为什么这样做？**
- 避免两处 sections 装配逻辑漂移
- `assembleSections` 和 `deriveParentIds` 可独立单元测试
- `generateId` 统一 ID 生成规则，避免 `"imp_" + Date.now() + "_" + random5` 散落在多处

**为什么通过 ExtractionResult 中转而不是直接写 articles？**
- 复用 `createDocument` 的 id 生成、parentId 推导、wordCount 计算逻辑
- 避免两套 Document 创建路径（一套从提取器、一套从 import_items），降低维护成本
- `structuredClone` 在 ExtractionResult 构造之前完成，确保 sections 的深拷贝语义

#### 3.2.5 错误处理复用

`library.js` 中的 `isLibraryAccessError` 和 `resolveLibraryErrorMessage` 负责识别 RLS 拒绝 / JWT 过期并给出友好提示。`importItems.js` 的操作同样需要这套逻辑——当用户会话失效时，应提示"会话已失效"而非原始 PostgREST 错误。

**做法**：将 `isLibraryAccessError` 和 `resolveLibraryErrorMessage` 提取到公共模块 `src/services/errorUtils.js`，`library.js` 和 `importItems.js` 均从该模块导入。

```js
// src/services/errorUtils.js
export function isLibraryAccessError(error) { ... }
export function resolveLibraryErrorMessage(error) { ... }
```

这避免了在 `importItems.js` 中复制粘贴错误判断逻辑。

### 3.3 数据库 migration 策略

#### 3.3.1 为什么 migration 和业务代码分开管理？

Supabase 的 migration 文件是有序的 SQL 脚本。本次需要两个 migration 文件：

1. **建表 migration**：`CREATE TABLE import_items` + 约束 + 索引 + RLS + GRANT + 触发器
2. **RPC migration**：`CREATE FUNCTION delete_import_item`（依赖表已存在）

分开管理的理由：
- migration 负责 **schema 变更**：建表、加字段、建索引、加约束、触发器
- 业务代码负责 **运行时操作**：CRUD、深拷贝、RPC 调用
- 建表 migration 先行，RPC migration 紧随其后——按时间戳排序

日常的 `SET NULL` 级联由 RPC 函数在数据库事务中原子执行，不放在前端代码中。这与项目中 `soft_delete_article` RPC 的模式一致。

#### 3.3.2 回填策略

```
现有 articles 表:
  source_import_id  → 全部为 null（无来源导入项）
  imported_at       → 全部为 null

不需要回填——null 是合法状态。
旧文章在阅读区正常存在，只是"没有来源素材"。
```

#### 3.3.3 RLS：复制现有模式，不创新

articles 的 RLS 策略已经被验证有效。import_items 的 RLS 策略直接复制同一模式——`auth.uid() = user_id`。不引入新的策略模式，降低出错概率。

- 否。导入统一收归素材区。文章库标签仅展示和管理已有文章。

### 4.3 导入流程：从一步改为两步，匿名用户保留旧路径

```
登录用户的新流程（两步）:
  选择文件/输入URL → 提取 → 出现在素材列表
                              │
                              └─ 用户可编辑
                              └─ 用户点击 "移入阅读区"
                              └─ 出现在文章库

匿名用户的保留路径（一步，与现有行为一致）:
  选择文件/输入URL → 提取 → createDocument() → saveArticle() → localStorage
  （导入区仅对已登录用户开放——与当前"匿名用户仅体验阅读"的门控策略一致）
```

**ImportPage 提交路径的分支逻辑**：

```js
// 导入提交时
if (!isAuthenticated) {
  // 匿名用户：保持旧路径
  const document = createDocument(result)
  await saveArticle(document, { userId: null })  // → localStorage
  await loadLibraryState()
} else {
  // 登录用户：新路径 → 导入区
  const importItem = await createImportItem(result, { userId, origin: 'imported' })
  toast('已保存到素材区')
}
```

**对用户体验的影响**：
- 登录用户多了一步操作——这是引入"编辑"能力的必要代价
- 匿名用户体验完全不变——"现有功能不退化"原则
- 未来可以为"快速导入"提供一键直达阅读区的快捷方式（当前不做）

### 4.4 编辑面板：内联编辑 + 节级编辑

```
ImportItemEditor 的双视图:

┌─ 元数据编辑 ──────────────────────────┐
│  标题  [___________________________]  │
│  作者  [___________________________]  │
└──────────────────────────────────────┘

┌─ Sections 列表 ──────────────────────┐
│  § 0: Chapter 1          [展开编辑]   │
│  § 1: Chapter 2          [展开编辑]   │
│  ...                                  │
└──────────────────────────────────────┘
```

展开某个 section 后，内联编辑 `heading`、`body.text`、`body.markdown`。

**为什么不支持新增/删除 section？**
- 第一阶段保持 sections 的完整性——提取器产出的章节结构通常不需要增删
- heading 和 body 的编辑覆盖了 90% 的编辑需求（修正标题错误、清理正文格式）
- 增删 section 涉及 order 重新分配、parentId 重新推导，复杂度高，边际收益低
- 若用户确实需要增删 section，可以在后续版本中评估

### 4.5 移入按钮的位置与交互

```
素材卡片上:

  └─────────────────────────────┘
```

移入操作：
1. 点击"移入阅读区"→ 调用 `copyToReadingZone()`
2. 短暂 toast: "已移入阅读区"
3. 素材卡片更新"已移入 N 次"
4. 文章库刷新，新文章出现

**为什么不做"移入并立即打开"？**
- 移入是一次性操作，打开阅读器是另一个独立动作
- 合并两个操作会让用户困惑"我到底在哪个区？"
- 保持操作边界清晰是双区概念成立的前提

## 五、关键交互设计

### 5.1 删除导入项

```
用户点击素材卡片的 [删除]

↓

1. 调用 countImportReferences(importItemId)

├─ 返回 0（无关联文章）→ 直接调用 RPC delete_import_item(id)
│
└─ 返回 > 0（有关联文章）→ 弹窗:
    "该素材已产生阅读副本。删除后：
     · 副本将保留在你的文章库中，可继续阅读
     · 副本不再显示「来源」信息
     确认删除？"
     [取消]  [确认删除]
     ↓
     用户确认 → 调用 RPC delete_import_item(id)

RPC 内部（单次原子操作）:
  BEGIN
    UPDATE articles SET source_import_id = NULL
      WHERE source_import_id = $id AND user_id = auth.uid() AND deleted_at IS NULL
    UPDATE import_items SET deleted_at = NOW()
      WHERE id = $id AND user_id = auth.uid() AND deleted_at IS NULL
  COMMIT
  RETURN affected_articles

toast: "素材已删除"（如有阅读副本则补充"已保留阅读副本"）
```

**为什么用 RPC 而非两次独立 UPDATE？**
- `countImportReferences` 和 RPC 之间可能竞态新增引用——但 RPC 内 WHERE 条件覆盖所有当前存在的引用，SET NULL 操作是全面的
- 弹窗不展示具体数量（避免计数偏差），仅告知"有副本"
- RPC 的 `user_id = auth.uid()` 双重校验防止跨用户操作
- 与项目中已有的 `soft_delete_article` RPC 模式一致

### 5.2 删除关联文章

```
用户在文章库删除文章（无论是否有 source_import_id）

→ 走现有的文章软删除流程
→ 不影响 import_items 中的素材
→ 素材的"已移入 N 次"计数相应减少
```

**"已移入 N 次"是实时计算还是冗余存储？**

选择实时计算：

```sql
SELECT COUNT(*) FROM articles
WHERE source_import_id = $importItemId AND deleted_at IS NULL
```

**为什么不冗余存储？**
- 冗余字段（import_items.import_count）需要在每次 articles 增删时同步更新
- 引入了一致性问题——RPC 更新可能失败，导致计数不准
- COUNT 查询在 source_import_id 有索引的情况下性能足够
- 素材列表不是高频访问页面，不需要极致性能

## 六、技术决策与取舍

### 6.1 structuredClone vs JSON.parse(JSON.stringify())

选择 `structuredClone`：

- 浏览器原生支持（Chrome 98+, Firefox 94+, Safari 15.4+）
- 正确处理 `undefined`（保留而非丢弃）
- 比 JSON 序列化更快（不经过字符串中间态）
- 但要注意：`structuredClone` 不支持函数和 DOM 节点——sections JSONB 不包含这些，安全

### 6.2 不做"同步更新"

当导入区素材被编辑后，**不自动更新**已移入的文章。

- 这违背了"独立副本"的核心原则
- 如果用户想要更新后的版本，他应该**重新移入**
- 多次移入自然形成版本链，比自动同步更可预期

### 6.3 导入区不做分页（第一阶段）

预期每个用户的素材数 < 100。超过这个量级再引入分页。

### 6.4 导入区不支持离线编辑

导入区是纯云端——需要网络连接。这是有意的设计选择：
- 编辑操作需要即时持久化，离线编辑的冲突解决复杂
- 阅读区（核心消费体验）已经可以离线阅读
- 导入区是"工作台"而非"消费区"，在线要求合理

## 七、风险与缓解

| 风险 | 缓解措施 |
|------|---------|
| 用户不理解"双区"概念 | UI 用清晰的标签和提示文字引导；首次进入素材区时展示 onboarding tooltip |
| 旧用户习惯直接导入→阅读 | 导入后自动跳转到素材区，素材卡片上有醒目的"移入阅读区"按钮 |
| import_items 表数据量增长 | 加索引；软删除超过 90 天的素材可考虑物理清理（远期） |
| structuredClone 在旧浏览器不可用 | 检查兼容性，必要时 polyfill；ReadRead 目标浏览器均支持 |
| 两区数据不一致的困惑 | "移入后独立"在 UI 中用 tooltip 说明；可用不同颜色/图标区分两区 |

---

## 八、总结

实施方案的核心思路：

> **叠加而非重构。import_items 是 articles 的上游，不是替代。提取器不变，Document 模型不变，阅读消费链路不变。唯一新增的是"导入 → 导入区 → 策展 → 移入 → 阅读区"这条数据流。所有现有能力保持原样。**
