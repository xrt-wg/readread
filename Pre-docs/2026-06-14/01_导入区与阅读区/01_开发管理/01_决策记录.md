# 书架与阅读区 — 决策记录

- **日期**：2026-06-14
- **状态**：已决策
- **项目阶段**：构建期
- **决策主题**：引入书架（Import Zone）将内容策展与内容消费分离，为远期用户间共享池做架构铺垫

---

## 一、背景

ReadRead 当前的导入流程是：

```
文件/URL → 提取器 → createDocument() → 直接写入 articles 表（阅读区）
```

导入即进入阅读库。用户无法在导入后、阅读前对内容进行编辑（修正格式、调整章节、补充元数据）。同时，当前架构中不存在"内容策展"与"内容消费"的分离——两者耦合在同一张 `articles` 表中。

随着产品演进，有两个需求浮出水面：
1. **导入后编辑**：用户想在正式阅读前打磨内容
2. **内容共享**（远期）：用户间分享策展好的素材

---

## 二、决策目标

1. 定义书架与阅读区的概念边界与数据模型
2. 确定两区之间的引用策略（有/无引用、引用强度）
3. 为共享池预留数据结构和扩展路径
4. 最大化复用现有 Document/Section 模型和提取器

---

## 三、决策结论

**引入"书架"概念，新增 `import_items` 表，articles 表加轻量引用字段。**

核心决策：

- **两区分离**：书架 = `import_items` 表，阅读区 = 现有 `articles` 表
- **移入 = 复制**：从书架移入阅读区是深拷贝，非移动。书架源内容保留
- **轻量引用**：`articles.source_import_id` 指向 `import_items.id`，无 FK 约束，应用层管理
- **删除策略**：书架删除 → RPC 原子操作（SET NULL articles.source_import_id + 软删除 import_items 在同一事务中），文章保留
- **匿名用户兼容**：匿名用户导入保留 `requireAuth` 门控（与云端过渡计划一致）。书架仅对登录用户开放，匿名用户可通过"立即体验"阅读示例文章
- **共享池预留**：`import_items` 的 `origin` / `share_status` / `share_source_id` 三个字段构成远期共享的完整数据结构
- **完全复用**：sections JSONB 结构、提取器、createDocument 工厂函数全部不变

---

## 四、候选方案比较

### 方案 A：无需书架，articles 加 status 字段

在 articles 表加 `status = 'draft' | 'published'`，draft 状态的文章不进入正常阅读流。

#### 优点
- 零新增表，schema 改动最小
- 实现最快

#### 致命问题
- 编辑与阅读混在同一张表：draft 编辑影响 published 副本（因为它们本质上是同一行）
- 同一素材多次移入 = 同一行复制多份——articles 表出现大量同质内容
- 共享池时无法区分"我自己导入的"和"从共享池拉取的"
- 本质上没有策展层，只是在阅读库上贴了个状态标签

#### 结论
**否决。** 该方案在共享池阶段需要推倒重建。

---

### 方案 B：书架独立 + 强 FK 引用（采用书架独立，但不用强 FK）

```
import_items 独立表
articles.source_import_id FK → import_items.id ON DELETE SET NULL
```

#### 优点
- 数据完整性由数据库保证
- 引用链路清晰

#### 代价
- 软删除场景下 FK 仍然有效（行还在），但应用层不应展示已删除的素材
- import_items 物理删除（如用户注销）时 FK 级联会拖慢操作
- 当前项目中 articles ↔ bookmarks 也没有 FK 约束，引入 FK 打破了现有惯例

#### 结论
**部分采用。** 保留独立表结构，但不加 FK 约束。删除级联由应用层 repository 函数处理。

---

### 方案 C：书架独立 + 无引用（否决）

articles 和 import_items 完全独立，articles 不记录来源。

#### 优点
- 最简 schema

#### 致命问题
- 用户无法区分同名文章来自哪个素材
- 共享池溯源链路断裂
- 书架删除时无法清理关联
- 数据统计不可行

#### 结论
**否决。** 省下的 2 个字段不是免费的——它拿走了所有可扩展性。

---

### 方案 D：书架独立 + 轻量引用（采用）

```
import_items 独立表
articles.source_import_id text（可空，无 FK）
articles.imported_at timestamptz（可空）
```

#### 优点
- 两区数据完全独立，编辑互不影响
- 轻量引用支持溯源，但不因上游删除而丢失下游数据
- sections JSONB 结构复用，提取器复用
- 共享池数据结构已预埋
- 无 FK 约束与现有架构风格一致

#### 代价
- 新增 1 张表 + 2 个 articles 字段
- 删除时需要应用层处理级联

#### 结论
**采用。** 在最小成本和最大扩展性之间的最佳平衡点。

---

## 五、关键决策点与取舍

### 5.1 移入 = 复制，非移动

移入阅读区产生的是独立副本。这意味着：
- 书架的后续编辑不会魔法般地更新已移入的文章
- 用户可以多次移入同一素材，每次产生独立的阅读副本
- 书架删除不影响阅读区已有副本

如果采用"引用同一份 sections"而非复制，表面上更节省存储，但会导致：
- 书架的编辑污染阅读体验
- 共享池的内容需要锁住不可编辑
- "多次移入"无法支持不同版本

**结论：复制是正确选择。** 存储成本可忽略（文本内容），独立性收益巨大。

### 5.2 共享池是 import_items 的逻辑视图

不新增 `shared_pool` 表。共享池 = `SELECT * FROM import_items WHERE share_status IN ('shared', 'public') AND deleted_at IS NULL`。

这避免了：
- 数据同步问题（import_items 更新后需同步到 shared_pool 表）
- 额外的 RLS 策略
- 不必要的表膨胀

### 5.3 书架不做本地存储

书架是纯云端功能（仅对已登录用户开放）。理由：
- 书架内容需要编辑——本地 localStorage 的编辑体验和可靠性不如云端
- 共享池依赖云端数据
- 保持与当前"匿名用户仅可体验阅读"的门控策略一致

### 5.4 `origin` 字段显式声明来源

虽然 `share_source_id` 非空可以隐式推断来源，但显式 `origin` 字段：
- 允许查询时直接过滤（`WHERE origin = 'shared'` 比 `WHERE share_source_id IS NOT NULL` 语义更清晰）
- 未来可能增加新来源类型（如 `'admin_curated'`），不需要依赖 null/not null 推断

---

## 六、决策范围

### 已确认
- 书架独立存储：`import_items` 表
- 阅读区轻量引用：`articles.source_import_id` + `imported_at`（可空，无 FK）
- 移入语义：深拷贝，非移动
- 删除策略：SECURITY DEFINER RPC 原子操作（SET NULL + 软删除在同一事务中），与现有 `soft_delete_article` 模式一致
- 共享池数据结构预留：`origin` / `share_status` / `share_source_id`
- sections 结构与提取器完全复用

### 暂不确认（属于后续设计规范的范围）
- 共享池的可见性规则与交互流程
- 书架编辑器的具体 UI 设计
- 书架到阅读区的"移入"按钮放置位置
- 书架是否支持批量移入

---

## 七、实施约束

1. 不要新增提取器——现有 `EXTRACTORS` 完全不变
2. 不要修改 Document/Section 类型定义
3. 不要修改 Bookmark / ReadingProgress 模型
4. articles 表的现有数据不受影响，`source_import_id` 为 null 是合法状态
5. 书架功能仅对已登录用户开放

---

## 八、复审条件

若出现以下任一情况，应重新评估当前设计：

1. 共享池实际落地时发现 origin/share_status/share_source_id 三字段不足以支撑
2. 书架内容量大到需要考虑分页/归档策略（当前预期每人 < 100 条素材）
3. 需要支持书架内容直接分享给指定用户（非公开共享池）
4. sections 结构在书架编辑场景下发现不足（如需要章节级版本历史）

---

## 九、总结

本次决策的核心结论是：

> **以独立的 `import_items` 表作为书架存储，以 `articles.source_import_id` 建立到阅读区的轻量引用，以 `origin` + `share_status` + `share_source_id` 三个字段预埋共享池扩展空间。移入阅读区是深拷贝，两区数据完全独立。提取器和 Document 模型完全复用。**
