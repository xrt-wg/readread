## 二、P0 — 实施阻塞项（必须修正后进入实施）

### P0-1：`saveArticle` 不会"自动透传"新字段

**来源文档**：[03_实施方案.md](../01_开发管理/03_实施方案.md) 第 173 行

> `saveArticle`：已支持任意字段写入，不需要改动。`source_import_id` 和 `imported_at` 作为 Document 对象的可选字段自然流入 `articles` 表。

**实际代码**：[src/services/library.js:195-234](src/services/library.js#L195-L234)

`saveArticle` 采用**显式字段映射**而非展开运算符——upsert 对象逐字段列出：

```js
// library.js L204-218 — 字段逐一手动映射
.upsert({
  id: article.id,
  user_id: options.userId,
  title: article.title,
  text: article.text,
  // ... 每个字段显式写出 ...
  sections: article.sections ?? [],
  section_count: article.sectionCount ?? 1,
  deleted_at: null,
}, { onConflict: 'id', ... })
```

**`source_import_id` 和 `imported_at` 不在这个映射中。** 如果在 Document 对象上设置这两个字段后直接调用 `saveArticle`，它们会被丢弃——数据库中的对应列永远为 null。

此外，`ARTICLE_COLUMNS` 常量（第 5 行）也需要添加这两个字段，否则 upsert 后的 `.select(ARTICLE_COLUMNS)` 不会返回它们，`mapArticleRow` 自然也拿不到。

**修正要求**：

1. `ARTICLE_COLUMNS` 添加 `source_import_id, imported_at`
2. `saveArticle` 的 upsert 对象添加：
   ```js
   source_import_id: article.source_import_id ?? null,
   imported_at: article.imported_at ?? null,
   ```
3. `mapArticleRow` 添加对应的 camelCase 映射（文档中已正确规划）

**影响范围**：[04_执行计划.md](../01_开发管理/04_执行计划.md) Phase 1 / 任务 1.2

### P0-2：`deleteImportItem` 存在竞态条件，需改为 RPC

**来源文档**：[02_设计与规范.md](../01_开发管理/02_设计与规范.md) 第 252-267 行

删除导入项流程分三步：
```
1. COUNT articles WHERE source_import_id = $id  → 获得 N
2. 弹窗确认
3. UPDATE articles SET source_import_id = NULL WHERE source_import_id = $id
4. UPDATE import_items SET deleted_at = NOW() WHERE id = $id
```

**问题**：步骤 1 和步骤 3 之间存在时间窗口。在此期间，用户可能通过"移入阅读区"新建了引用该素材的文章。步骤 3 的 SET NULL 会覆盖新文章的 `source_import_id`，导致新文章丢失溯源。

在 Supabase 客户端 JS 中，无法将多条 SQL 包裹在数据库事务中。

**现有惯例**：项目已经使用 SECURITY DEFINER RPC 函数处理类似事务性需求——[`soft_delete_article`](supabase/migrations/20260614000000_add_soft_delete_article_rpc.sql) 和 `soft_delete_bookmarks_for_article` 正是此模式。

[03_实施方案.md](../01_开发管理/03_实施方案.md) 第 228-229 行意识到了这个风险：

> countImportReferences 与 deleteImportItem 间出现竞态 | 两者在同一事务中（或先后调用，中间无用户操作）

但"中间无用户操作"是不可靠的保证。"同一事务"在 Supabase JS 客户端中也无法实现（只有 Edge Functions 或 RPC 可以做事务）。

**修正建议**：创建 `delete_import_item` RPC 函数：

```sql
CREATE OR REPLACE FUNCTION public.delete_import_item(p_import_item_id text)
RETURNS integer  -- 返回受影响的 articles 数量
LANGUAGE plpgsql
SECURITY DEFINER
AS $$
DECLARE
  affected_articles integer;
BEGIN
  -- 1. SET NULL 已移入文章的溯源引用
  UPDATE public.articles
  SET source_import_id = NULL
  WHERE source_import_id = p_import_item_id
    AND user_id = auth.uid()
    AND deleted_at IS NULL;
  
  GET DIAGNOSTICS affected_articles = ROW_COUNT;

  -- 2. 软删除素材
  UPDATE public.import_items
  SET deleted_at = timezone('utc', now())
  WHERE id = p_import_item_id
    AND user_id = auth.uid()
    AND deleted_at IS NULL;

  RETURN affected_articles;
END;
$$;
```

前端调用变为：
1. 调用 `countImportReferences(importItemId)` → 获得 N
2. 若 N > 0 → 弹窗确认
3. 调用 `deleteImportItem(importItemId)`（RPC，单次原子操作）
4. RPC 返回 `affected_articles` 供日志/提示

**影响范围**：[04_执行计划.md](../01_开发管理/04_执行计划.md) Phase 1 / 任务 1.1；需新增 migration 文件

### P0-3：`copyToReadingZone` 缺少 `sourceUrl` 映射

**来源文档**：[03_实施方案.md](../01_开发管理/03_实施方案.md) 第 152-187 行

`copyToReadingZone` 中构造的 `ExtractionResult`：

```js
const extractionResult = {
  meta: {
    title:    importItem.title,
    author:   importItem.author,
    format:   importItem.format,
    coverUrl: importItem.cover_url,
    lang:     importItem.lang,
    // ⚠ 缺少 sourceUrl
  },
  sections: sections.map(...)
}
```

对比 `ExtractionMeta` 类型定义（[src/types/extractor.js:25-33](src/types/extractor.js#L25-L33)）：

```js
@property {string|null} [sourceUrl]
```

以及 `createDocument` 的映射（[src/services/extractors/index.js:46](src/services/extractors/index.js#L46)）：

```js
sourceUrl: result.meta.sourceUrl ?? null,
```

`import_items` 表有 `source_url` 字段（记录 URL 导入时的原始 URL），但在 `copyToReadingZone` 中构造 `ExtractionResult` 时未被传递。这意味着从 URL 导入的素材移入阅读区后，文章的 `source_url` 字段为 null，丢失了溯源信息。

**修正**：在 `meta` 中添加 `sourceUrl: importItem.source_url ?? undefined`。

## 三、P1 — 重要问题（实施中应解决）

### P1-1：需将 sections 装配逻辑抽取为共享函数

`createDocument`（[extractors/index.js:16-53](src/services/extractors/index.js#L16-L53)）内联了 sections 装配逻辑：分配 id、deriveParentIds、计算 wordCount。`createImportItem` 需要相同的逻辑。

[04_执行计划.md](../01_开发管理/04_执行计划.md) 任务 1.1 说"内部复用 sections 处理逻辑（与 createDocument 相同的 wordCount 计算、deriveParentIds）"，但**未说明复用方式**。

当前 `createDocument` 的装配逻辑是内联的，无法被部分调用。有三种方案：

| 方案 | 做法 | 评价 |
|------|------|------|
| A | 抽取 `assembleSections(extractionSections) → Section[]` 共享函数 | **推荐。** 干净、可测试、无重复 |
| B | `createImportItem` 内部调用 `createDocument` 然后转换 | 会产生一个中间 Document 对象，语义扭曲 |
| C | 在 `createImportItem` 中复制粘贴 sections 装配逻辑 | 维护负担，两处逻辑可能漂移 |

**建议**：在 `extractors/index.js` 中导出 `assembleSections(extractionSections)` 和 `generateId(prefix)`，两者分别被 `createDocument` 和 `createImportItem` 调用。

### P1-2：匿名用户的导入路径需显式保留

当前行为：匿名用户可直接导入 → `saveArticle` → localStorage → 文章库。

计划的改动是将 `ImportPage` 中所有导入路径从 `createDocument → saveArticle` 改为 `createImportItem → saveImportItem`。但 `saveImportItem` 是纯云端操作（需要 userId），匿名用户调用会失败。

[02_设计与规范.md](../01_开发管理/02_设计与规范.md) 第 160-165 行和第 480 行说书架仅对登录用户开放。但**匿名用户的现有导入能力不应该被移除**。

**执行计划中缺失的决策**：Phase 2 改道时，匿名用户走哪条路径？

- **选项 A**：匿名用户保持旧路径（`createDocument → saveArticle → localStorage`）
- **选项 B**：匿名用户完全不展示导入功能（仅保留推荐阅读标签）

选项 A 更符合"现有功能不退化"的原则。需要在 `ImportPage` 提交逻辑中加 `isAuthenticated` 分支判断。

**建议**：在 Phase 2 任务中显式加入：

> 匿名用户导入路径保持现状（直接写入 localStorage articles）。仅已登录用户的导入路径改道至 import_items。

并补充测试用例：匿名用户导入 → 文章库出现新文章；登录用户导入 → 书架出现新素材。

fetchImportItemTitlesByIds(ids: string[]) → Map<string, string>

在 Phase 4 文章列表加载时一次性调用，避免 N+1。

### P1-5：`mapArticleRow` 缺少 `deleted_at` 映射 + 前端过滤的隐患

当前 `mapArticleRow`（[library.js:39-59](src/services/library.js#L39-L59)）不映射 `deleted_at` 字段。但 `ARTICLE_COLUMNS` 包含了 `deleted_at`。这在前端使用 `mapArticleRow` 返回值时，`deleted_at` 信息被丢弃。

在现有流程中这不是问题——RLS 策略 `articles_select_own` 已经用 `deleted_at IS NULL` 过滤。但对于新增的 `countImportReferences` 查询（需要 COUNT 已删除文章？不，只需要 COUNT 未删除的），以及"已移入 N 次"的展示逻辑——计数查询需要过滤 `deleted_at IS NULL`。

**确认**：在 Phase 1 任务 1.1 的 `countImportReferences` 实现中使用 `.eq('deleted_at', null)` 或等效过滤（通过 RLS 自动过滤亦可，但显式过滤更安全）。

### P1-6：`import_items` 表缺少 `updated_at` 自动触发器和 GRANT 授权

[02_设计与规范.md](../01_开发管理/02_设计与规范.md) 第 387-388 行给出了 RLS 策略，但**缺少**：

1. **`updated_at` 自动更新触发器**：现有 `articles` 表有 `trg_articles_set_updated_at`，`import_items` 同样需要。
2. **GRANT 授权**：需要 `GRANT SELECT, INSERT, UPDATE ON public.import_items TO authenticated`。注意：不应 GRANT DELETE——与现有 articles 惯例一致（软删除通过 RPC）。
3. **用户级 id 唯一约束**：现有 articles 有 `UNIQUE (user_id, id)`，`import_items` 同理需要，防止跨用户 ID 碰撞（虽然概率极低，但约束防御最安全）。

## 四、P2 — 改善建议（可延后处理）

### P2-1：考虑在 `copyToReadingZone` 设置有意义的 `source_type`

当前 `saveArticle` 中 `source_type` 默认值为 `'manual'`（[library.js:211](src/services/library.js#L211)）。从书架移入的文章全部标记为 `'manual'`，无法区分是 URL 导入、EPUB 导入还是粘贴导入。

`import_items.format` 已经记录了原始格式。建议在 `copyToReadingZone` 中将 `format` 映射到 `sourceType`：

```js
document.sourceType = importItem.format  // 'url' | 'epub' | 'pdf' | 'paste' | 'markdown' | 'html'
```

这样在阅读区统计/筛选时能区分内容来源。

现有最新 migration 是 `20260614000000_add_soft_delete_article_rpc.sql`。`import_items` 的 migration 需要更高时间戳。

建议使用 `20260615000000_create_import_items.sql`（如果次日执行）或 `20260614000001_create_import_items.sql`（同日执行，Supabase 按字典序排列，更长的数字排在后面）。

## 五、架构与设计观察

### 5.1 关于"独立副本"语义的边界情况

决策中"移入 = 复制，非移动"的原则是正确的。但有一个隐含边界情况值得注意：

**用户编辑素材后再次移入**：第二次移入会生成新的独立副本，而第一次移入的副本不受影响。这意味着同一个素材可以产生多个版本的文章。在 Phase 4 的"已移入 N 次"展开列表中，展示的是所有版本。但用户可能困惑"为什么我有两个同名文章"。建议在 Phase 4 的"已移入文章列表"中为每次移入显示时间戳，帮助区分版本。

### 5.2 sections 结构复用的实际验证

文档说 sections JSONB 结构与 articles.sections 完全一致。验证证实了这一点：

- `articles.sections`（[migration 20260613140000](supabase/migrations/20260613140000_extend_articles_for_document_model.sql)）：`[{ id, heading, depth, parentId, order, body: { text, markdown, wordCount } }]`
- `import_items.sections`（计划）：同样结构

字段命名均为 camelCase（JSONB 内部）。映射路径正确。

### 5.3 执行计划阶段划分的合理性

Phase 0-2（纯后端/服务层）对用户零感知——这是正确的风险控制策略。但有一个小问题：

**Phase 2（导入改道）与 Phase 3（书架前端）之间的空窗期**：在 Phase 2 完成后、Phase 3 开始前，用户导入的内容会进入 `import_items` 表，但没有任何 UI 可以看到或操作它们——素材从用户视角"消失了"。虽然 Phase 2 只是代码切换的瞬间，但如果 Phase 2 部署到 staging 后有测试期，需要告知测试者这个行为。

建议 Phase 2 和 Phase 3 尽量在同一次发布中上线，减少用户可见的中断。

### 5.4 共享池的远期设计在数据模型中的影响

`origin` / `share_status` / `share_source_id` 三个字段已预留在 `import_items` 中，这是好的。但有一个 RLS 相关问题：

当 `share_status = 'shared'` 或 `'public'` 时，**其他用户需要能 SELECT 该行**。当前 RLS 策略（`auth.uid() = user_id`）会阻止。远期实施共享池时需要：
1. 新增 RLS 策略允许 SELECT `share_status IN ('shared', 'public') AND deleted_at IS NULL`
2. 拉取者创建 `origin = 'shared'` 的副本后，引用 `share_source_id` 指向源条目

这个扩展路径是清晰的，设计预留是充分的。

## 七、总结

**审核结论：有条件通过。**

四份设计文档的架构方向和数据模型设计是正确的。双区分离、叠加策略、独立副本语义、轻量引用——这些核心决策经得起代码库验证。

需要阻塞的三件事都在"文档假设 vs 代码实际"这个交叉面上：

1. **`saveArticle` 显式字段映射**——必须手动加上 `source_import_id` / `imported_at`
2. **`deleteImportItem` 事务安全**——必须改为 RPC 原子操作
3. **`copyToReadingZone` 丢失 `sourceUrl`**——少了一行映射

这三项修正量小（总计 < 50 行代码变更），但若不修正，功能会出现"看起来成功但实际上没有写入"的静默错误。

P1 六项中最关键的是 **P1-2（匿名用户路径保留）** 和 **P1-1（sections 装配逻辑抽取）**——前者影响现有用户体验，后者影响代码维护性。

整体评估：修正 P0 三项后即可进入 Phase 0 实施。P1 项在对应 Phase 中逐一处理即可。
