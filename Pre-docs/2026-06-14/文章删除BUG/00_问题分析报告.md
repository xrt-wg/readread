# 问题分析报告 — 文章删除 403 Forbidden

- **日期**：2026-06-14
- **分支**：internal-test
- **问题**：删除文章返回 403 Forbidden
- **严重程度**：P0 阻断
- **状态**：✅ 已修复

---

## 1. 现象

- UI 弹窗：「当前云端会话已失效或访问权限已变化，系统正在刷新身份状态」
- 控制台：
  ```
  PATCH https://...supabase.co/rest/v1/articles?user_id=eq.3f0a83cd-...&id=eq.doc_...&deleted_at=is.null
  403 (Forbidden)
  ```

---

## 2. 排查过程

### 2.1 第一轮：客户端 + 服务端五维度排查（全部排除）

| 维度 | 验证方式 | 结果 |
|------|---------|------|
| 客户端代码 | 代码审查 `deleteArticle` → `executeCloudDelete` → PATCH 逻辑 | ✅ 无 bug |
| JWT 有效性 | [jwt.io](https://jwt.io) 解码：`role=authenticated`, `exp` 未过期, `sub` 匹配 | ✅ |
| 数据库行数据 | Supabase Dashboard 查询：`user_id` 匹配, `deleted_at IS NULL` | ✅ |
| RLS 策略定义 | `pg_policies` 查询：3 条 PERMISSIVE，无 RESTRICTIVE，定义正确 | ✅ |
| SQL 直连 | `UPDATE + ROLLBACK` 成功返回行 | ✅ |

**结论**：五维度全部排除。403 不在代码、JWT、数据、策略、SQL 引擎中。

### 2.2 第二轮：对照实验（锁定 PostgREST 层）

| 方式 | 校验逻辑 | 操作 | 结果 |
|------|---------|------|------|
| PostgREST PATCH | RLS `using` + `with check` | `UPDATE articles SET deleted_at` | 403 ❌ |
| RPC `SECURITY DEFINER` | 函数内 `WHERE user_id = auth.uid()` | 相同 `UPDATE` | 200 ✅ |

两者校验逻辑和 SQL 操作完全等价，唯一变量是是否经过 PostgREST 的 PATCH 处理层。**问题锁定在 PostgREST 对 PATCH 的内部处理环节。**

### 2.3 第三轮：PostgREST 层内精确归因

PostgreSQL 返回的错误信息给予了关键突破：

```
new row violates row-level security policy for table "articles"
```

这是 `WITH CHECK` 违反，不是 `USING` 违反。但策略的 `WITH CHECK` 只有一条：

```sql
with check (auth.uid() = user_id)
```

且 `user_id` 在本次 PATCH 中**未被修改**（PATCH body 仅含 `{"deleted_at": "..."}`）。

**数学上 `auth.uid() = user_id` 应为 TRUE，但 PostgreSQL 报告它失败了。**

---

## 3. 根因

### 精确定位

**PostgREST 在评估 RLS `WITH CHECK` 时，基于 PATCH body 构建新行表示，而非将 body 合并到旧行之上。** 未出现在 body 中的列在检查上下文中被当作 NULL/default 处理。

具体机制：

```
PATCH body: {"deleted_at": "2026-06-14T10:00:00.000Z"}
              ↑ 只含 deleted_at，不含 user_id

PostgREST 内部构造的"新行"表示用于 WITH CHECK 评估：
  { user_id: NULL,  deleted_at: "2026-...", ... }
       ↑ 缺失的列被填充为 NULL

WITH CHECK 评估：
  auth.uid() = user_id
  auth.uid() = NULL
  → NULL（三元逻辑，非 TRUE）
  → RLS 拒绝 → 403
```

### 为什么 PATCH body 中缺少 `user_id`

客户端 `executeCloudDelete` 的查询：

```js
client
  .from('articles')
  .update({ deleted_at: now })          // ← body 只含 deleted_at
  .eq('user_id', userId)                // ← user_id 在 URL 过滤条件中
  .eq('id', articleId)
  .is('deleted_at', null)
```

Supabase JS client 将 `.update({ deleted_at: now })` 序列化为 PATCH body：`{"deleted_at": "..."}`。`user_id` 出现在 **URL 查询参数**（`?user_id=eq.xxx`）中，作为 WHERE 过滤条件，但不出现在 body 里——因为客户端不认为 `user_id` 需要被修改。

### 为什么 RPC 没有这个问题

```sql
-- RPC 函数内部
UPDATE public.articles
SET deleted_at = timezone('utc', now())
WHERE id = article_id
  AND user_id = auth.uid()      -- ← user_id 直接取自数据库行，不经过 PostgREST 行构造
  AND deleted_at IS NULL;
```

`SECURITY DEFINER` 函数在 PostgreSQL 引擎内部执行，`user_id` 是行的实际列值。`auth.uid()` 与数据库行 `user_id` 的比较在 SQL 引擎中正确运行，不经过 PostgREST 的行构造逻辑。

### 为什么 SQL 直连 `UPDATE + ROLLBACK` 能通过

SQL Editor 中执行的 UPDATE 同样在 PostgreSQL 引擎内部运行，行数据直接来自表，不经 PostgREST 处理。

---

## 4. 完整证据链

| 步骤 | 发现 | 结论 |
|------|------|------|
| 五维度排查 | 代码/JWT/数据/策略/SQL 全部正确 | 问题不在应用层，不在数据库引擎层 |
| PATCH vs RPC 对照 | RPC 通过，PATCH 被拒 | 问题在 PostgREST 层 |
| PostgreSQL 错误码 | `new row violates row-level security policy` | 是 `WITH CHECK` 违反，不是 `USING` 违反 |
| `WITH CHECK` 表达式 | `auth.uid() = user_id`，`user_id` 未被修改 | 数学上应为 TRUE，却报告 FALSE |
| body 内容分析 | `{"deleted_at": "..."}` 不含 `user_id` | PostgREST 行构造缺失 `user_id` → 填充 NULL |
| NULL 在三元逻辑中的行为 | `anything = NULL → NULL ≠ TRUE` | RLS 要求 TRUE，NULL 被拒绝 |

---

## 5. 修复方案

新建 RPC 函数 `soft_delete_article`，`SECURITY DEFINER` + 函数内 `auth.uid()` 校验，将 PATCH 替换为 `.rpc()` 调用。

**有效性原理**：绕过 PostgREST 的 PATCH 行构造逻辑，让 `user_id` 直接从数据库行取值。

**安全性**：等效于 RLS `using (auth.uid() = user_id)`，无权限提升。

## 6. 为什么现在才出现

`articles` 表的 `deleted_at` 列和 RLS `articles_update_own` 策略在 Phase 0（Document 模型改造）之前已存在，并非本次新增。但此 403 问题直到本次测试才首次暴露，原因是：

1. **云端删除路径此前从未被实际触发**：ReadRead 的前序版本中，Supabase 主要用于 auth 身份认证。文章库的增删改查走 `localStorage`（`useCloudSource` 返回 false）。用户即使登录，`saveArticle` / `deleteArticle` 也落在 `articleStore.save()` / `articleStore.delete()` 本地路径上，PATCH 请求从未发送到 Supabase。

2. **本次 PR 首次启用完整云端路径**：Document 模型改造完成后，`useCloudSource` 在用户已认证且 Supabase 已配置时返回 true，所有文章库操作真正走 Supabase。用户导入 EPUB 后点击删除，是 `executeCloudDelete` 第一次在生产环境发送 PATCH 到 Supabase，首次触发 PostgREST 的 body 构造行为与 RLS `WITH CHECK` 的冲突。

3. **bookmarks 的同类 PATCH 未触发**（见下文 §7）：理论上 bookmarks 表也受影响，但该路径同样此前未被实际调用。当前修复后 bookmarks PATCH 在删除文章时一并执行且未报错，推测是因为 bookmarks 表此用户的测试数据中尚无为空的关联行（外键约束使 `deleteArticle` 的 bookmark 分支在无关联书签时匹配 0 行，不触发 RLS 评估），或 PostgREST 对不同表的行为存在微小差异。但作为防御性措施，建议同步迁移。

---

## 7. 经验教训

1. **PostgREST PATCH 的 `WITH CHECK` 评估基于 body 构造新行**，缺失列被填充为 NULL。当 RLS `with check` 表达式依赖未出现在 body 中的列时，即使语义上不应失败，NULL 在三元逻辑中也会导致拒绝。排障时关注 PostgreSQL 错误消息中的 `new row violates` 字样可快速定位此类问题。

2. **云端路径应在真实环境中尽早验证**：本地开发时 Supabase 路径未被覆盖（`useCloudSource` 返回 false），导致此类 PostgREST 交互问题直到上线测试才暴露。建议后续对 Supabase 路径做 staging 环境联调。
