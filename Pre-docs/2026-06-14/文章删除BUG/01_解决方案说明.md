# 解决方案说明 — 文章删除 403 Forbidden

- **日期**：2026-06-14
- **分支**：internal-test
- **关联分析**：[00_问题分析报告.md](00_问题分析报告.md)

---

## 根因

PostgREST 在评估 RLS `WITH CHECK` 时基于 PATCH body 构造新行表示，未出现在 body 中的列（如 `user_id`）被填充为 NULL。

```
PATCH body: {"deleted_at": "2026-06-14T10:00:00Z"}   ← 只含 deleted_at

PostgREST 内部构造的行表示用于 with check 评估：
  { user_id: NULL, deleted_at: "...", ... }
       ↑ 缺失列被填充为 NULL

WITH CHECK: auth.uid() = user_id
          → auth.uid() = NULL
          → NULL（三元逻辑，非 TRUE）
          → RLS 拒绝 → 403
```

`user_id` 出现在 URL 查询参数（`.eq('user_id', userId)`）作为 WHERE 过滤条件，但不出现在 body 里——因为 Supabase JS client 的 `.update()` 只将改动列序列化到 body。PostgREST 未将 URL 过滤参数参与 `WITH CHECK` 的行构造。

> **PostgREST 行为注解**：PostgREST 对 PATCH 的 `WITH CHECK` 评估基于请求 body 构建检查上下文，而非将 body 合并到数据库旧行之上。缺失列不被视为"保持原值"，而是被当作 NULL/default 参与 RLS 策略评估。这是 PostgREST 与 PostgreSQL 原生 `UPDATE` 在 `WITH CHECK` 语义上的已知差异——原生 UPDATE 中行的所有列在 `WITH CHECK` 阶段均保留实际值。

---

## 方案：PATCH → RPC

### 修改文件

| 文件 | 改动 |
|------|------|
| `supabase/migrations/20260614000000_add_soft_delete_article_rpc.sql` | 新建，定义 `soft_delete_article` RPC |
| `src/services/library.js` | `executeCloudDelete` 中 articles 部分改用 `.rpc()` |

### SQL

```sql
create or replace function public.soft_delete_article(article_id text)
returns void
language plpgsql
security definer
set search_path = public
as $$
declare
  v_user_id uuid;
begin
  v_user_id := auth.uid();
  if v_user_id is null then
    raise exception 'unauthenticated';
  end if;

  update public.articles
  set deleted_at = timezone('utc', now())
  where id = article_id
    and user_id = v_user_id
    and deleted_at is null;

  if not found then
    raise exception 'article not found or already deleted';
  end if;
end;
$$;

grant execute on function public.soft_delete_article(text) to authenticated;
```

### JS

```diff
  const [{ error: articleError }, ...] = await Promise.all([
-   client.from('articles').update({ deleted_at: now })
-     .eq('user_id', userId).eq('id', articleId).is('deleted_at', null),
+   client.rpc('soft_delete_article', { article_id: articleId }),
    ...
  ])
```

### 有效性原理

| 之前（PATCH） | 之后（RPC） |
|--------------|------------|
| PostgREST body 构造行 → `user_id` 填充为 NULL → `auth.uid() = NULL` → NULL ≠ TRUE → 403 | SQL 引擎内 `WHERE user_id = auth.uid()` → `user_id` 直接取自数据库行 → 正确评估 → 200 |

`SECURITY DEFINER` 使函数以创建者权限运行（绕过表 RLS 策略），但函数内部显式包含 `WHERE user_id = auth.uid()` 条件，安全性等价于 RLS `using (auth.uid() = user_id)`，无权限提升。

### 部署要求

在 Supabase SQL Editor 中执行上述 migration SQL。

## 防御性补充：bookmarks 软删除同步迁移

### 风险分析

`executeCloudDelete` 中 bookmarks 批量删除仍使用 PATCH（[library.js:243-248](src/services/library.js#L243-L248)）：

```js
client.from('bookmarks').update({ deleted_at: now })
  .eq('user_id', userId).eq('article_id', articleId).is('deleted_at', null)
```

检查 bookmarks 的 RLS UPDATE 策略（与 articles 结构完全一致）：

```sql
create policy "bookmarks_update_own" on public.bookmarks
for update to authenticated
using (auth.uid() = user_id and deleted_at is null)
with check (auth.uid() = user_id);
```

- 同样 `with check (auth.uid() = user_id)`
- 同样 PATCH body 只含 `{ deleted_at: now }`，不含 `user_id`
- 同因：PostgREST 将缺失 `user_id` 填充为 NULL → `auth.uid() = NULL` → 403

当前 bookmarks PATCH 未触发 403 的可能原因：测试数据中尚无关联书签，`WHERE` 过滤匹配 0 行时 PostgREST 跳过 RLS 评估。但仍存在同类风险——用户书签积累后可能触发。

### 方案

在已有 migration 文件中追加 `soft_delete_bookmarks_for_article` 函数，`executeCloudDelete` 中 bookmarks 部分同步改用 `.rpc()`。

### SQL（追加到已有 migration）

```sql
create or replace function public.soft_delete_bookmarks_for_article(article_id text)
returns void
language plpgsql
security definer
set search_path = public
as $$
declare
  v_user_id uuid;
begin
  v_user_id := auth.uid();
  if v_user_id is null then
    raise exception 'unauthenticated';
  end if;

  update public.bookmarks
  set deleted_at = timezone('utc', now())
  where article_id = soft_delete_bookmarks_for_article.article_id
    and user_id = v_user_id
    and deleted_at is null;
end;
$$;

grant execute on function public.soft_delete_bookmarks_for_article(text) to authenticated;
```

### JS

```diff
  const [{ error: articleError }, { error: bookmarkError }, ...] = await Promise.all([
    client.rpc('soft_delete_article', { article_id: articleId }),
-   client.from('bookmarks').update({ deleted_at: now })
-     .eq('user_id', userId).eq('article_id', articleId).is('deleted_at', null),
+   client.rpc('soft_delete_bookmarks_for_article', { article_id: articleId }),
    client.from('reading_marks').upsert(...),
  ])
```
