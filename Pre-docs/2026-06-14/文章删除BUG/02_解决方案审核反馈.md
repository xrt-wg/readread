## 三、解决方案根因定位审核

### 3.1 根因机制分析

解决方案文档提出了具体的根因机制：

```
PATCH body: {"deleted_at": "2026-06-14T10:00:00Z"}

PostgREST 内部构造的行表示用于 WITH CHECK 评估：
  { user_id: NULL, deleted_at: "...", ... }

WITH CHECK: auth.uid() = user_id
          → auth.uid() = NULL
          → NULL（三元逻辑，非 TRUE）
          → RLS 拒绝 → 403
```

### 3.2 RLS 策略交叉验证

实际 RLS 策略（[`20260509170000_create_core_user_tables.sql:102-107`](supabase/migrations/20260509170000_create_core_user_tables.sql#L102-L107)）：

```sql
create policy "articles_update_own" on public.articles
for update to authenticated
using (auth.uid() = user_id and deleted_at is null)
with check (auth.uid() = user_id);
```

验证结论：
- `with check` 表达式为 `auth.uid() = user_id`
- 若 PostgREST 将行表示中的 `user_id` 填充为 NULL → `auth.uid() = NULL` → **NULL（非 TRUE）** → RLS 拒绝
- SQL 直连不受此影响（因为 PostgreSQL 引擎直接使用行的实际 `user_id` 值）
- ✅ **根因分析在逻辑上自洽，与所有交叉验证证据一致**

### 3.3 根因分析评价

| 项目 | 评价 |
|------|------|
| 定位精度 | ✅ 精确到 PostgREST 行构造阶段的具体行为 |
| 机制解释 | ✅ 清晰展示了 PATCH body → 行构造 → NULL 填充 → RLS 拒绝的完整链条 |
| 与证据一致性 | ✅ 与直接 SQL 成功、RPC 成功、PATCH 失败的实验数据完全一致 |
| 可复现性 | ✅ 逻辑模型可解释现象，但缺少 PostgREST 源码/文档引用作为旁证 |

**建议**：补充 PostgREST 官方文档或 GitHub issue 引用，增强说服力。PostgREST 文档中关于 PATCH 的 `with check` 行为有相关说明。

## 四、解决方案合理性审核

### 4.1 方案评估

| 替代方案 | 可行性 | 评价 |
|---------|-------|------|
| **A. PATCH → RPC**（采用） | ✅ | 最简洁，绕过 PostgREST RLS 交互问题 |
| B. 修改 RLS `with check` 为 `true` | ❌ | 降低安全性，允许越权修改其他用户的 article |
| C. PATCH body 中包含 `user_id` | ⚠️ | 技术上可行但丑陋——`user_id` 不应出现在 body 中，且 PostgREST 可能拒绝修改 PK/FK 列 |
| D. 使用 `Prefer: return=representation` header | ❌ | 不解决 `with check` 行构造问题 |

**方案 A（RPC）是唯一合理的选项。**

### 4.2 安全性审核

RPC 函数 [`20260614000000_add_soft_delete_article_rpc.sql`](supabase/migrations/20260614000000_add_soft_delete_article_rpc.sql)：

| 安全检查项 | 结果 |
|-----------|------|
| `SECURITY DEFINER` | ✅ 已正确声明 |
| `search_path = public` | ✅ 已设置，防止 search_path 注入 |
| 函数内权限验证 | ✅ `WHERE user_id = auth.uid()` — 权限等价于 RLS |
| 未认证用户防护 | ✅ `IF v_user_id IS NULL THEN RAISE EXCEPTION 'unauthenticated'` |
| 已删除行幂等防护 | ✅ `AND deleted_at IS NULL` + `IF NOT FOUND THEN RAISE EXCEPTION` |
| GRANT to authenticated | ✅ 仅授权给已认证角色 |

**安全性等价于 RLS `using (auth.uid() = user_id)`，无权限提升。** ✅

### 4.3 幂等性

`soft_delete_article` 对已删除的文章抛出异常（`IF NOT FOUND`），而非静默成功。这与 UI 预期一致——用户不会重复删除同一篇文章。

## 五、解决方案有效性审核 — ⚠️ 存在遗漏

### 5.1 关键发现：bookmarks 存在同类漏洞

当前 `executeCloudDelete`（[`library.js:240-264`](src/services/library.js#L240-L264)）中，仅 **articles** 改为 RPC：

```js
const [{ error: articleError }, { error: bookmarkError }, ...] = await Promise.all([
  client.rpc('soft_delete_article', { article_id: articleId }),   // ✅ 绕过
  client.from('bookmarks').update({ deleted_at: now })            // ⚠️ 仍用 PATCH
    .eq('user_id', userId).eq('article_id', articleId).is('deleted_at', null),
  client.from('reading_marks').upsert(...),                       // — upsert 非纯 UPDATE
])
```

检查 bookmarks 的 RLS 策略（[`20260509170000_create_core_user_tables.sql:123-129`](supabase/migrations/20260509170000_create_core_user_tables.sql#L123-L129)）：

```sql
create policy "bookmarks_update_own" on public.bookmarks
for update to authenticated
using (auth.uid() = user_id and deleted_at is null)
with check (auth.uid() = user_id);
```

**与 articles 的 UPDATE 策略结构完全相同**：
- 同样的 `with check (auth.uid() = user_id)`
- 同样的 PATCH body 只含 `{ deleted_at: now }`，不含 `user_id`
- 如果根因分析正确（PostgREST 填充 NULL），**bookmarks 更新理论上会触发同样的 403**

### 5.2 为什么当前可能没有暴露

| 可能原因 | 分析 |
|---------|------|
| Promise.all 快速失败 | 当 articles RPC 成功但 bookmarks PATCH 失败时，Promise.all 整体 reject。UI 收到的错误来自 bookmarks。但用户反馈"修复后删除成功"说明 bookmarks 并未失败 |
| PostgREST 行为差异 | 不同表（列数、约束）可能导致 PostgREST 的行构造行为略有不同 |
| 偶发性 | 可能 bookmarks 的 403 是偶发的，取决于 PostgREST 内部状态 |
| `articles` 表的 trigger 干扰 | `articles` 表有 `trg_articles_set_updated_at` trigger（BEFORE UPDATE 自动设置 `updated_at`），这可能导致 PostgREST 的行构造分歧。`bookmarks` 表也有相同 trigger，因此此解释不成立 |

**无法从代码审查中确定 bookmarks 为何没有触发同样的 403。** 需要在实际运行环境中验证。

### 5.3 建议

**为防御性编程，建议同步将 bookmarks 软删除也改为 RPC：**

```sql
create or replace function public.soft_delete_bookmarks_for_article(article_id text)
returns void
language plpgsql
security definer
set search_path = public
as $$
declare
  v_user_id uuid;
begin
  v_user_id := auth.uid();
  if v_user_id is null then
    raise exception 'unauthenticated';
  end if;

  update public.bookmarks
  set deleted_at = timezone('utc', now())
  where article_id = article_id
    and user_id = v_user_id
    and deleted_at is null;
end;
$$;
```

**不必阻塞当前发布**（当前 bookmarks PATCH 实际工作正常），但建议作为技术债务记录，在下一个迭代中修复。
