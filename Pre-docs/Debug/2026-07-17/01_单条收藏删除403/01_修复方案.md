# 修复方案：恢复单条收藏删除 RPC 路径

- 日期：2026-07-17
- 前置条件：`00_问题分析报告.md` 已确认
- 状态：待确认实施

## 1. 目标

恢复云端单条收藏的软删除能力，避免 `PATCH /rest/v1/bookmarks` 触发 RLS 403，同时保持用户只能删除自己的未删除收藏。

## 2. 实施内容

### 2.1 补齐可追溯的数据库 migration

新增一条 migration，通过 `CREATE OR REPLACE FUNCTION` 声明：

```sql
public.soft_delete_bookmark(bookmark_id text)
```

函数要求：

- `SECURITY DEFINER`；
- 固定 `search_path = public`；
- 未认证时明确失败；
- 仅更新同时满足以下条件的行：
  - `id = bookmark_id`；
  - `user_id = auth.uid()`；
  - `deleted_at IS NULL`；
- 没有匹配行时明确失败；
- 显式 `GRANT EXECUTE` 给 `authenticated`。

该 migration 即使线上函数已存在也可安全执行，并使当前仓库成为新环境可复现的数据库定义来源。

### 2.2 恢复前端服务调用

修改 `src/services/readings.js` 的 `deleteBookmark` 云端分支：

```js
client.rpc('soft_delete_bookmark', { bookmark_id: bookmarkId })
```

替换现有 `.from('bookmarks').update(...)` PATCH 链。

本地存储路径 `bookmarkStore.delete(bookmarkId)` 保持不变；组件调用方无需修改。

## 3. 有效性原理

RPC 在受控的 `SECURITY DEFINER` 上下文执行数据库更新，避开当前 REST PATCH 与 RLS 的失败边界。

这不等于放宽权限：函数仍以 `auth.uid()` 作为书签所有权条件。调用者无法通过传入他人书签 ID 删除他人数据；未认证调用和目标书签不匹配都会失败。

## 4. 预期效果

| 场景 | 预期结果 |
| --- | --- |
| 正文入口删除自己的收藏 | 删除成功，页面刷新后高亮消失 |
| 侧边栏入口删除自己的收藏 | 删除成功，列表同步移除 |
| 网络请求 | 调用 `/rest/v1/rpc/soft_delete_bookmark`，不再 PATCH `bookmarks` |
| 删除他人的收藏 | 被函数所有权条件拒绝 |
| 重复删除已软删除收藏 | 返回明确失败，不改变数据 |
| 本地模式 | 保持原有删除行为 |

## 5. 验证步骤

1. 部署 migration。
2. 打开含至少一条收藏的阅读内容。
3. 分别从正文与侧边栏删除一条收藏。
4. 在 Network 确认请求为 RPC 且成功返回。
5. 刷新页面，确认被删除收藏不再显示。
6. 使用不同账户或构造非本人书签 ID 验证所有权保护。

## 6. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 线上函数与仓库定义漂移 | 通过新 migration 重新声明并纳入版本控制 |
| `SECURITY DEFINER` 扩大权限 | 函数内显式使用 `auth.uid()` 限定所有权，并固定 `search_path` |
| 已删除书签重复操作 | 使用 `deleted_at IS NULL` 条件及未找到记录错误 |
| 组件调用受影响 | 服务函数签名不变，ReaderPage 无需调整 |
