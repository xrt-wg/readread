## 2. 原因定位

### 2.1 结论

**根因与 [[00_问题分析报告]] 中诊断的文章删除 403 完全相同——PostgREST PATCH + RLS `WITH CHECK` 交互问题。** `bookmarks` 表的 RLS `WITH CHECK` 是 `auth.uid() = user_id`，但 `deleteBookmark` 函数发送的 PATCH body 仅含 `{"deleted_at": "..."}`，不含 `user_id`。PostgREST 在评估 `WITH CHECK` 时基于 body 构造新行表示，缺失的 `user_id` 被填充为 NULL：

```
auth.uid() = NULL  →  NULL（三元逻辑非 TRUE）  →  RLS 拒绝  →  403
```

### 2.2 完整推理链

| 步骤 | 发现 | 结论 |
|------|------|------|
| ① 问题表现 | PATCH `/rest/v1/bookmarks` → 403 | 服务端拒绝请求 |
| ② RLS 策略定义 | `bookmarks_update_own` → `with check (auth.uid() = user_id)` | 必须有 `user_id` = `auth.uid()` |
| ③ PATCH body 内容 | `{"deleted_at": "2026-..."}` 仅含 `deleted_at` | body 中无 `user_id` |
| ④ PostgREST 行构造 | 基于 PATCH body 构造新行 → `user_id` 被填充为 NULL | `auth.uid() = NULL` 结果为 NULL |
| ⑤ NULL 在三元逻辑 | RLS 要求 TRUE，NULL 被拒绝 | → 403 |
| ⑥ 与 articles 案例对照 | 同样的 RLS 结构、同样的 PATCH 模式、同样的 403 | 已知根因，未经修复的同类问题 |

### 2.3 详细分析

**问题代码**：[`src/services/library.js:367-384`](src/services/library.js#L367-L384)

```js
export async function deleteBookmark(bookmarkId, options) {
  if (!useCloudSource(options)) {
    bookmarkStore.delete(bookmarkId)
    return
  }

  const client = getSupabaseClient()
  const { error } = await client
    .from('bookmarks')
    .update({ deleted_at: new Date().toISOString() })   // ← body 只含 deleted_at
    .eq('user_id', options.userId)                       // ← user_id 在 URL 中，不在 body 中
    .eq('id', bookmarkId)
    .is('deleted_at', null)

  if (error) {
    throw error
  }
}
```

**RLS 策略**：[`supabase/migrations/20260509170000_create_core_user_tables.sql:123-129`](supabase/migrations/20260509170000_create_core_user_tables.sql#L123-L129)

```sql
create policy "bookmarks_update_own"
on public.bookmarks
for update
to authenticated
using (auth.uid() = user_id and deleted_at is null)
with check (auth.uid() = user_id);        -- ← 依赖 user_id 列
```

**PostgREST 内部处理逻辑（已在上次 articles 分析中验证）**：

```
PATCH body: {"deleted_at": "2026-06-17T..."}
              ↑ 只含 deleted_at，不含 user_id

PostgREST 内部构造的"新行"表示用于 WITH CHECK 评估：
  { id: NULL, user_id: NULL, article_id: NULL,  deleted_at: "2026-...", ... }
                        ↑ 缺失的列被填充为 NULL

WITH CHECK 评估：
  auth.uid() = user_id
  auth.uid() = NULL
  → NULL（三元逻辑，非 TRUE）
  → RLS 拒绝 → 403
```

### 2.4 为什么 articles 删除已修复但 bookmarks 删除仍失败

| 操作 | 机制 | 状态 |
|------|------|------|
| 删除文章 (`deleteArticle`) | `soft_delete_article` RPC (SECURITY DEFINER) | ✅ 已修复 (提交 `215be43`) |
| 删除文章关联书签 | `soft_delete_bookmarks_for_article` RPC | ✅ 已创建 RPC |
| **单独删除书签 (`deleteBookmark`)** | **PATCH `/rest/v1/bookmarks`** | ❌ **未迁移，仍为 PATCH** |

上一次修复（文章删除 403）时，创建了两个 RPC：
- `soft_delete_article` — 替换单篇文章软删除的 PATCH
- `soft_delete_bookmarks_for_article` — 替换删除文章时批量软删除关联书签的 PATCH

但**单条书签的独立删除路径**（`deleteBookmark` 函数）没有被迁移到 RPC。该函数仅在阅读区 `ReaderPage.jsx:375` 被调用——当用户直接删除一条收藏/摘录时触发。

### 2.5 上一次分析的预警

在 [[00_问题分析报告]] §7 中已明确指出：

> *"bookmarks 的同类 PATCH 未触发……但作为防御性措施，建议同步迁移。"*

该预警未被执行，导致当前用户在阅读区删除收藏时触发此 bug。

## 3. 为什么错误提示显示"会话已失效"

`isLibraryAccessError()` ([`src/services/errorUtils.js:10-26`](src/services/errorUtils.js#L10-L26)) 将所有 `status === 403` 归类为"库访问错误"，统一映射为：「当前云端会话已失效或访问权限已变化，系统正在刷新身份状态。」

但实际上本例中 **JWT/会话完全有效**，403 是 RLS 拒绝，而非认证问题。错误消息存在误归类——这是另一个需要关注的问题，但不是本次 bug 的根因。
