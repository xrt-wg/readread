## 二、A 级阻断（必须修正后方可实施）

### A1 · I-5 修复方向自相矛盾：预览「剥离+隐藏」无法达成与阅读区一致

**位置**：[01_修复方案.md](01_修复方案.md) §五 I-5；[00_问题分析报告.md](00_问题分析报告.md) §三 I-5

方案 §五 I-5 的修复动作：

> 在 `MarkdownPreview` 渲染前剥离 frontmatter……剥离后正文交给 ReactMarkdown；**frontmatter 不展示**。

但阅读区（对齐原则下的「目标态」）对同一份 frontmatter 的行为是**剥离后渲染为顶部引用块**（[SectionFlow.jsx:116-150](../../../src/components/SectionFlow.jsx#L116-L150)），并非隐藏。分析报告 §三 I-5 自身的两句话即相互冲突：

1. 「阅读区将其剥离并**渲染为顶部引用块**」——目标态展示；
2. 「frontmatter 是元数据，**不应展示**给读者，预览应与其一致」——主张不展示。

按此实施后，预览 = 完全隐藏，阅读区 = 顶部引用块，**两表面仍然不一致**——与本次「使预览与阅读区一致」的目标相反。

**需要明确一个决策点**（实施前二选一）：

- (a) 若「引用块展示元数据」是有意设计（导入书在顶部露出标题/作者/来源），则预览应**镜像该引用块**：需把 [SectionFlow.jsx:116-150](../../../src/components/SectionFlow.jsx#L116-L150) 的「frontmatter → 引用块」渲染抽为共享组件，供 `MarkdownPreview` 复用，而非「剥离+隐藏」；
- (b) 若「frontmatter 不应展示」才是原则，则阅读区的引用块本身也是缺陷：需**一并移除**阅读区引用块及其 `data-para-index="-1"` 的收藏挂载（[SectionFlow.jsx:132-150](../../../src/components/SectionFlow.jsx#L132-L150)），改动面远大于方案所述的单行剥离。

无论 (a)/(b)，方案 §五 I-5 目前的一行描述都未覆盖完整语义。**建议选 (a)**：改动集中在「抽组件 + 预览复用」，且与「阅读区=目标态、预览=镜像」的总原则一致。

## 三、B 级（建议修正）

### B1 · I-4 前提失实：全库共 3 处 `1.6em`，「阅读区统一 1.8em」不成立

**位置**：[01_修复方案.md](01_修复方案.md) §五 I-4；[00_问题分析报告.md](00_问题分析报告.md) §一/§五

分析把「阅读区 = 1.8em」当作干净的目标态，实为失实。全库 `marginBottom: '1.6em'` 共 **3 处**，方案只列了 1 处：

| 位置 | 组件 | 所属表面 | 方案是否覆盖 |
|------|------|---------|------------|
| [SectionContentEditor.jsx:70](../../../src/components/SectionContentEditor.jsx#L70) | `MarkdownPreview` 的 `p` | 书架编辑预览（markdown） | ✅ 已覆盖 |
| [SectionContentEditor.jsx:106](../../../src/components/SectionContentEditor.jsx#L106) | `PlainTextPreview` 的 `p` | 书架只读预览（纯文本，经 `SectionPreview` 供推荐审核用） | ❌ 未覆盖 |
| [SectionFlow.jsx:194](../../../src/components/SectionFlow.jsx#L194) | `PlainTextContent` 的 `p` | **阅读区纯文本降级路径** | ❌ 未覆盖 |

后果：

- 「阅读区 = 1.8em」只对 markdown 段落成立；阅读区**自身**在 markdown（1.8em）与纯文本降级（1.6em）之间就存在内部分裂，分析报告从未察觉。
- 若按方案只改 `MarkdownPreview`，markdown 节会变成预览 1.8 / 阅读 1.8（一致），纯文本节仍是预览 1.6 / 阅读 1.6（一致），但**阅读区内部 1.8 vs 1.6 的错位被原样保留**。

**修正**：I-4 应把三处 `1.6em` 一并列出，并明确纯文本路径的目标值。建议统一收敛到 1.8em（三处全改），消除阅读区内部分裂；若决定纯文本保持 1.6em，则需在文档中写明该决策，而不是默认「阅读区=1.8em」。

### B2 · I-2 方案缺两个关键细节，需在单独评审前补齐

**位置**：[01_修复方案.md](01_修复方案.md) §三 I-2

方案方向（`extractSegments` 扩展 tag + `ParagraphRenderer` 按 tag 包裹切片）正确，且「格式标签零字符宽、charOffset 不受影响」的不变量判断成立。但有两个具体问题未覆盖：

1. **merge 条件须 tag 化**：`extractSegments` 现有合并逻辑 [markdownUtils.js:41](../../../src/utils/markdownUtils.js#L41) `if (last && !last.img && last.href === href) last.text += text` 只比较 `href`。引入 tag 后，同一条链接内「粗体段」与「普通段」会被误合并成一个段，**粗体边界丢失**。合并条件必须升级为 `href 相等 && tag 栈相等`，否则「粗体里含链接」这类嵌套直接退化。

2. **段级 tag 与 range 级高亮切片的映射未设计**：`ParagraphRenderer` 的高亮层（`renderBgs`/`renderSpan`，[ParagraphRenderer.jsx:62-127](../../../src/components/ParagraphRenderer.jsx#L62-L127)）基于**整段 `text` 的 charOffset 区间**切片，而非按 `segments` 段切片。方案只说「按该切片所属段的 tag 包裹」，但段边界（`seg.start/end`）与高亮区间边界（bookmark range）是两套正交的切分网格，如何在对高亮切片 emit 的同时命中正确 tag、以及「格式标签在内/高亮在外」的层级如何落到代码，方案未给出。实施前需给出：tag 与 `seg` 的绑定结构 + 一次能同时消解「高亮 range」和「格式 tag」的切片算法（哪怕伪代码）。

另注意：`li` 同样经 `extractSegments` + `ParagraphRenderer`（[SectionFlow.jsx:90-99](../../../src/components/SectionFlow.jsx#L90-L99)），I-2 对列表项同样生效——方案未显式点明，但改动面已自然覆盖，属表述遗漏而非设计缺口。

### B3 · I-1 依赖未验证的 Context 穿透机制，轻量替代被一句带过

**位置**：[01_修复方案.md](01_修复方案.md) §二 I-1

方案的核心机制是：`blockquote` 组件返回 `<InQuoteContext.Provider>` 包裹 `children`，`p` 组件内 `useContext` 读标志。该机制依赖 **React Context 能穿透 react-markdown v10.1.0 的自定义组件树**（`blockquote` → Provider → 自定义 `p`），这一点**未经验证**，且存在两个需 spike 确认的风险点：

- `createContext(false)` 必须定义在模块作用域（或稳定引用），不能落在 `useMemo`/组件体内，否则每次重建 context 身份；
- react-markdown v10.1.0 传入 `blockquote` 的 `children` 是已构建的 React 元素，理论上经 Provider 重渲染时 `p` 会落入其作用域，但需一次最小 spike 实证，而不是直接进入实施。

方案的「轻量替代」（CSS 选择器 `.article-quote > div > p` 适配嵌套 + 引用块内不放按钮）仅被一句话标「未推荐」，**未给出与 Context 方案的成本/风险对照**。该替代改动面小得多、无 hook 依赖，缺点是按钮位置语义仍与预览不同。建议实施前补一个两方案对照表，或在 spike 阶段同时验证 Context 可行性后再定。

## 四、C 级（补充与澄清）

### C1 · I-3 容器只设 `fontSize`，未同步预览容器的其余排版令牌

**位置**：[01_修复方案.md](01_修复方案.md) §四 I-3

预览容器的字号之外还携带 `lineHeight: 1.9`、`letterSpacing: '0.01em'`、`fontFamily`、`color`（[SectionContentEditor.jsx:67](../../../src/components/SectionContentEditor.jsx#L67)）。I-3 的容器只设 `fontSize`，于是：

- 阅读区 `li` 目前继承 body 的 `letter-spacing: 0`，而预览 `li` 经容器继承 `0.01em`——即使 I-3 落地，**列表项的字距仍与预览差 0.01em**（极轻微，但恰是本问题「列表项观感脱节」的同类残留）。
- 建议 I-3 的容器承载与预览容器**同一组排版令牌**（fontSize + lineHeight + letterSpacing + fontFamily + color），一次对齐，而非只补字号。

### C2 · 「夜间模式：本文所涉类均走 CSS 变量」不准确

**位置**：[00_问题分析报告.md](00_问题分析报告.md) §六完备性核对

`.article-inline-code`（[index.css:473-480](../../../src/index.css#L473-L480)）与 `.article-code-block`（[index.css:482-493](../../../src/index.css#L482-L493)）使用硬编码 `rgba(28,25,23,0.07/0.05)` 背景与 `rgba(28,25,23,0.1)` 边框，**既非 CSS 变量，也无 `[data-theme="night"]` 覆盖**。I-2 恰好会新增「阅读区段落内渲染行内代码」，把这些类首次带入正文段落的高频路径，夜间模式下该硬编码背景观感需一并评估。结论宜改为「本文所涉类**大部分**走 CSS 变量，`.article-inline-code`/`.article-code-block` 属未变量化、无夜间覆盖的既有例外」。

### C3 · 「段落序号一致性 ✅」过于绝对，多行引用块存在既有分歧

**位置**：[00_问题分析报告.md](00_问题分析报告.md) §六完备性核对

两点需降级澄清：

1. **收藏索引实为 DOM 派生，非 progress.js 派生**：bookmark 的 `paragraphIndex` 取自选区锚点的 `data-para-index`（[ReaderPage.jsx:292-293](../../../src/components/ReaderPage.jsx#L292-L293)），与 `progress.js` 无运行时强绑定。I-1 的「关键约束——保持 `paraIdxRef.current++`」方向正确且充分，但「与 progress.js 逐段对齐」并非收藏正确性的硬前提。

2. **多行引用块上两套计数可能已分歧**：`getMarkdownParagraphs` 对连续 `> 行` 补空行（[progress.js:41-44](../../../src/services/progress.js#L41-L44)），把 `> a\n> b` 拆成 2 段；而 react-markdown/CommonMark 对 `> a\n> b` 解析为**单段落**（软换行），阅读区 `paraIdxRef` 只计 1 段。二者在该边界上不一致。鉴于进度已迁移为 scroll% 快照、bookmark 走 DOM 索引，当前影响有限，但 §六的「✅ 对齐」建议改为「基本对齐（多行引用块为已知分歧点，需补对照用例）」。

### C4 · 验证清单缺口

**位置**：[01_修复方案.md](01_修复方案.md) §七

建议补充三组回归用例：

- **I-1 后**：引用块内段落**仍可划选收藏/高亮**（去 `div.group` 按钮后，收藏高亮经 `ParagraphRenderer` 应照常），验证清单 #3 仅验「charOffset 不偏移」，未验「引用块内收藏入口仍在」；
- **I-5 后**：含 frontmatter 文章的 `paraIndex=-1` 引用块（若保留方案 (a)）的收藏回归；
- **I-2 后**：链接内嵌粗体（`[**粗**](url)`）在阅读区同时保留链接图标与粗体语义的用例。

## 六、结论与建议

1. **分析报告可作事实依据直接使用**：I-1/I-2/I-3/F-1 的定位与根因全部属实，无需返工。
2. **I-1、I-3、F-1 方向正确**，修正 B3（I-1 先 spike）、C1（I-3 容器令牌）、F-1 与否随评审后即可实施。
3. **I-4、I-5 暂缓**：须先修正 A1（I-5 方向）与 B1（I-4 三处 1.6em + 前提失实）再动工，否则「使预览与阅读区一致」的目标无法达成。
4. **I-2 维持单独立项**：补齐 B2 两个细节（merge 条件 tag 化、段级 tag × range 级高亮切片映射）后再进入评审，不随本轮捆绑交付。

建议实施顺序（修正后）：I-1（先 spike Context）→ I-4（三处统一 1.8em）→ I-5（按 A1 决策）→ I-3（容器令牌）→（I-2 单独评审）→（F-1 可选）。
