# 问题分析报告 — 列表进度异常显示 99%

- **日期**：2026-06-20
- **分支**：feat/translation-test
- **问题**：阅读器顶部栏滚动进度 65%，添加书签后回到列表显示进度 99%，偏差达 34%
- **严重程度**：P0（核心功能数值错误）
- **状态**：🔴 待修复

---

## 1. 现象

1. 在阅读器中阅读文章，顶部进度条显示约 **65%**（滚动进度）
2. 在当前位置点击段落标记（书签按钮）
3. 返回文章列表，该文章卡片显示进度 **99%**
4. 偏差达 34 个百分点，远超段落高度差异可解释的范围

---

## 2. 根因定位

### 2.1 直接原因：`getWordOffsetAtParagraph` 溢出路径

**位置**：[`src/services/progress.js:87-93`](src/services/progress.js#L87-L93)

```js
export function getWordOffsetAtParagraph(article, paragraphIndex) {
  const paragraphs = getParagraphs(article)
  if (paragraphIndex < 0 || paragraphIndex >= paragraphs.length) {
    return countWords(paragraphs.join(' '))  // ← 返回全部词数！
  }
  return countWords(paragraphs.slice(0, paragraphIndex + 1).join(' '))
}
```

当 `paragraphIndex >= paragraphs.length` 时，该函数返回**全部段落的总词数**。随后：

```js
function calcSingleProgress(article, paragraphIndex) {
  const totalWords = getTotalWords(article)
  const readWords = getWordOffsetAtParagraph(article, paragraphIndex)  // ← 返回总词数
  return Math.min(99, Math.round((readWords / totalWords) * 100))      // ← ≈ 100% → 99%
}
```

`readWords ≈ totalWords` → 除法结果 ≈ 1.0 → `Math.min(99, 100)` → **99%**。

**结论**：99% 不是接近完成的真实进度，而是溢出路径的固定输出值。任何 `paragraphIndex` 超出 `getParagraphs` 的段落数组长度时，都无条件返回 99%。

---

### 2.2 根本原因：`MarkdownContent` 与 `getMarkdownParagraphs` 的段落计数不一致

溢出为什么会发生？因为 `paragraphIndex` 来自 `MarkdownContent`（AST），而 `paragraphs` 来自 `getMarkdownParagraphs`（正则）。两者对同一篇 markdown 文章产生的段落数量不同。

#### 2.2.1 核心矛盾：引用块（blockquote）

**`MarkdownContent`** 中 blockquote 的自定义组件（[ReaderPage.jsx:114](src/components/ReaderPage.jsx#L114)）：

```jsx
blockquote: ({ children }) => <blockquote className="article-quote">{children}</blockquote>,
```

此组件**本身**不递增 `paraIdxRef`。但 `react-markdown` 会**递归处理其 children**——blockquote 内部的 `<p>` 和 `<li>` 元素会通过自定义的 `p` 和 `li` 处理器 → **递增 `paraIdxRef`**。

**`getMarkdownParagraphs`** 中（[progress.js:84-85](src/services/progress.js#L84-L85)）：

```js
// 跳过引用块（以 > 开头的连续行，在 MarkdownContent 中不递增 paraIdxRef）
if (/^>\s/m.test(block)) continue
```

整个引用块被**完全跳过**，内部段落不计入。

**结果**：每个引用块，MarkdownContent 计数 N 个 `<p>` + M 个 `<li>`，而 getMarkdownParagraphs 计数 0。

#### 2.2.2 对段落索引的影响

```
示例 markdown:

普通段落一。

> 引用中的段落 A。
>
> 引用中的段落 B。

普通段落二。

- 列表项 1
- 列表项 2
```

**MarkdownContent 的段落索引**：
| 元素 | paraIdxRef |
|------|-----------|
| `<p>普通段落一。</p>` | 0 |
| `<p>引用中的段落 A。</p>` | 1 |
| `<p>引用中的段落 B。</p>` | 2 |
| `<p>普通段落二。</p>` | 3 |
| `<li>列表项 1</li>` | 4 |
| `<li>列表项 2</li>` | 5 |

**getMarkdownParagraphs 的段落数组**：
| 索引 | 内容 |
|------|------|
| 0 | "普通段落一。" |
| 1 | "普通段落二。" |
| 2 | "列表项 1" |
| 3 | "列表项 2" |

用户点击「引用中的段落 A」（`paragraphIndex = 1`，来自 MarkdownContent）：
- `getParagraphs` 返回 4 个段落（索引 0~3）
- `paragraphIndex = 1`，`1 < 4`，正常路径 → 计算 OK 但引用内容未被计入词数

用户点击「列表项 2」（`paragraphIndex = 5`，来自 MarkdownContent）：
- `getParagraphs` 返回 4 个段落（索引 0~3）
- `paragraphIndex = 5`，`5 >= 4` → **溢出路径** → 返回全部词数 → **99%**

**这正是用户遇到的场景**：引用块使 MarkdownContent 的计数膨胀，导致后续段落的索引在 getMarkdownParagraphs 中越界。

#### 2.2.3 其他可能贡献计数偏差的因素

| 因素 | MarkdownContent | getMarkdownParagraphs | 偏差方向 |
|------|----------------|----------------------|---------|
| 引用块内的 `<p>` | 递增 | 跳过 | regex 少计 |
| 引用块内的 `<li>` | 递增 | 跳过 | regex 少计 |
| 图片独立段落 `![]()` | 递增（`<p><img/></p>`） | 递增（空字符串） | 一致（但词数=0） |
| 空段落（连续换行） | 不产生 `<p>` | filter 去除 | 一致 |
| 代码块内的内容 | 不递增 | 占位符跳过 | 一致 |
| 标题 h1-h6 | 不递增 | 跳过 | 一致 |

**引用块是段落计数偏差的唯一显著来源。**

---

### 2.3 滚动进度（65%）vs 段落进度（99%）的差异

- 顶部进度条：`window.scrollY / (documentHeight - windowHeight) × 100` — 视觉滚动位置
- 列表进度：`readWords / totalWords × 100` — 段落词数比例

即使段落计数一致，这两个指标也不会相等（段落高度不同）。但 65% → 99% 的差距（34 个百分点）远超段落高度差异可解释的范围。**溢出路径是唯一能产生固定 99% 输出的机制。**

## 3. 证据链

| 步骤 | 发现 | 结论 |
|------|------|------|
| ① | 列表进度始终显示 99%（而非 98% 或 100%） | `Math.min(99, ...)` 的固定上限值，说明除法结果 ≥ 0.995 |
| ② | `calcSingleProgress` 中 `readWords / totalWords ≥ 0.995` | `readWords ≈ totalWords` |
| ③ | `getWordOffsetAtParagraph` 第 89 行 `paragraphIndex >= paragraphs.length` 分支返回 `countWords(paragraphs.join(' '))` | 当越界时返回全部词数 |
| ④ | `paragraphIndex` 来自 MarkdownContent（AST），`paragraphs` 来自 getMarkdownParagraphs（regex） | 两个不同源的段落数可能不一致 |
| ⑤ | MarkdownContent 的 blockquote 子元素（`<p>`、`<li>`）递增 paraIdxRef，但 getMarkdownParagraphs 跳过整个引用块 | 引用块使 MarkdownContent 计数 > getMarkdownParagraphs 计数 |
| ⑥ | 用户点击引用块之后的段落 → `paragraphIndex`（AST）大于 regex 段落数 → 越界 | → 99% |

## 4. 为什么上一轮修复未能解决此问题

上一轮修复（2026-06-19）的核心策略是创建 `progress.js` 统一端点：
- **ImportPage** 的 `calcProgress` 改用 `getParagraphs` ✅
- **ReaderPage** 的 `paragraphs` 变量改用 `getParagraphs` ✅（但仅对非 markdown 路径生效）

**但 `MarkdownContent` 组件本身未被修改**——它仍然使用 `paraIdxRef`（react-markdown AST 计数）来确定段落索引。对于 markdown 文章，`paragraphIndex` 的值仍然来自 AST，而 `calcProgress` 的段落数组来自 regex。两端仍然不一致。

**修复的缺口**：我们统一了"非 markdown 路径"的段落来源，但没有处理 markdown 路径的核心矛盾——`MarkdownContent` 的 AST 计数与 `getMarkdownParagraphs` 的 regex 计数之间的差异。

---

## 5. 不完备性说明

### 5.1 已确认的事实

- 溢出路径的存在和触发条件（`paragraphIndex >= paragraphs.length`）
- 引用块导致段落计数偏差的机制（MarkdownContent 计数 N 个内部 `<p>`/`<li>`，getMarkdownParagraphs 计数 0）
- 99% 是溢出路径的固定输出（`Math.min(99, ...)`）

### 5.2 推测部分

- 用户的测试文章包含引用块（`> `），且用户在引用块之后的段落点击了标记——这是最可能触发溢出的场景。但**未经用户确认文章内容**。
- 可能存在其他导致计数偏差的 markdown 结构（如 setext 标题 `===`，但概率极低）

### 5.3 验证推测的行动方案

1. **确认文章内容**：用户在 Supabase Dashboard 或浏览器控制台获取该文章的 `markdown` 字段内容，搜索 `> ` 前缀
2. **确认段落索引**：在 ReaderPage 中添加 `console.log('paraIndex:', idx)` 临时日志，确认点击时 `paragraphIndex` 的值
3. **确认 regex 段落数**：在 `calcProgress` 中添加 `console.log('paragraphs.length:', paragraphs.length)` 临时日志

---

## 6. 总结

| 项目 | 内容 |
|------|------|
| **直接原因** | `getWordOffsetAtParagraph` 溢出路径：`paragraphIndex >= paragraphs.length` → 返回全部词数 → 99% |
| **根本原因** | `MarkdownContent`（AST）对引用块内部 `<p>`/`<li>` 递增段落索引，而 `getMarkdownParagraphs`（regex）完全跳过引用块，导致两套计数不一致 |
| **严重程度** | P0 — 含引用块的文章中，引用块之后的段落标记全部显示 99% |
| **修复方向** | 需要消除 `MarkdownContent` 的 `paraIdxRef` 与 `getParagraphs` 之间的计数偏差。要么让 MarkdownContent 使用 `getParagraphs` 的索引，要么让 `getMarkdownParagraphs` 对引用块内部段落也进行计数 |
