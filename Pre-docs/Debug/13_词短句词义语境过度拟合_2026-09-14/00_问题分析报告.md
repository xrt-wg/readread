# 问题分析报告：词/短句卡片的"词义"被语境句内容过度拟合

- 日期：2026-09-14（分析）/ 2026-09-15（消融实验确证）
- 状态：**根因已确证** —— `meaning` 槽位定义模糊（关键诱因是 `"in this context"` 短语），诱导模型把语境句内容（`the result of ___` 的关系）折进词义槽位。已通过离线复现 + 消融实验锁定（见 §3.5）
- 影响范围：收藏卡片「词义」字段（`bookmark.translation`）—— 词/短句类型收藏的**悬浮卡 / 收藏面板 / 复习卡**三处同源同数据
- 本文只做问题定位，不含修复方案（遵循 `.windsurf/rules/problem-analysis-guide.md`）

---

## 1. 现象

用户提供的样本（来自单词收藏的悬浮卡片）：

| 卡片字段 | 显示内容 |
| --- | --- |
| 原词（`bookmark.text`，小字斜体） | `neglect` |
| 词义（`bookmark.translation`，主字号加粗） | **忽视造成的后果** |
| 语境句（`bookmark.contextSentence`，词加粗） | `And it's simply the result of neglect.` |
| 语境句译文（`bookmark.contextTranslation`，小字灰） | `而这不过是忽视的结果。` |

- 期望：词义 = `忽视`。
- 实际：词义槽位填入了**语境句的主干内容**（the result of neglect）改写成的名词短语。
- 特征：**不是每次发生**（用户描述"有时候"），且用户主观描述为"过于冗余拟合"。

关键定性：`忽视造成的后果` 与 `忽视` 不是同层级的差异，而是**语义层级错位**——前者是"名词短语级"的描述（且含 `造成`/`结果` 这一**只存在于语境句中、不属于 neglect 词义本身**的成分），后者才是"词级"的词典式对应。这是"语境内容泄漏进词义槽位"的直接指纹。

## 2. 结论（已由代码链路确证）

### 2.1 四个字段的来源与唯一映射（逐行核对）

| 卡片字段 | 数据来源 | 代码位置 |
| --- | --- | --- |
| `text` | 划选文本，`detectSelectionType` 判为 `word`（单词，无换行、1 个词） | `src/utils/textUtils.js:5-14`；`src/components/ReaderPage.jsx:217` |
| `contextSentence` | `findContainingSentence(paraText, selected)`，只对 word/phrase 求值 | `src/components/ReaderPage.jsx:248`；`src/utils/textUtils.js:20-40` |
| `translation` | AI 返回 JSON 的 `meaning` 字段 | `src/hooks/useBookmarkAI.js:9-16` → `src/services/aiProviders/index.js:164-166` |
| `contextTranslation` | 同一次 AI 返回 JSON 的 `contextTranslation` 字段 | 同上 |

渲染侧无二次加工：`BookmarkHoverCard.jsx:138-140`（词义）、`:152-156`（语境句译文）直接输出字段值；`BookmarkPanel.jsx:230 / 274` 同构。落库侧也无加工：`src/services/readings.js:798-801`（云端 upsert）、`src/store/storage.js:177-187`（本地）。读取回填：`readings.js:128-151`。

### 2.2 `忽视造成的后果` 只可能来自 AI 释义环节（推理链）

**Step 1｜词/短句的 `translation` 只有两条写入路径**

| 路径 | 触发条件 | `translation` 取值 | `contextTranslation` |
| --- | --- | --- | --- |
| (a) AI 精译 | 主力 AI 成功，或备用 AI 成功 | `parseWordPhraseBundle(raw).meaning` | 同响应中的 `contextTranslation` |
| (b) 直译兜底 | (a) 的两级都抛错，且 `aiConfig.fallbackToDirect` | `translateDirectWithFallback(bookmark.text).text`（即对**单字** `neglect` 的机器翻译） | **恒为 `null`** |

依据：`src/hooks/useBookmarkAI.js:29-66`（①②③④ 串行链路），`src/services/aiProviders/index.js:125-148`（解析），`config/translation.js:8-12`（`aiConfig`）。

**Step 2｜两条路径互斥，且 (b) 必然抹掉语境句译文**

`useBookmarkAI.js:59-61` 在 (b) 中显式 `contextTranslation = null`；渲染侧 `BookmarkHoverCard.jsx:152` 仅在 `contextTranslation` 为真时渲染该行。
⇒ 卡片上**同时出现语境句与语境句译文**，即等价于"走的是路径 (a) 且 AI 调用成功且返回了合法的双字段 JSON"。

**Step 3｜(b) 在语义上也不可能产出该串**

(b) 的兜底链是 有道（`netlify/functions/translate.js:121`，`callYoudaoOne` 提取 `translation[0]`）→ MyMemory（`src/services/directTranslation/myMemory.js:9-17`，`translateOne`），二者都是**单段机器翻译**，输入就是 `neglect` 这一个词。单字 MT 的输出是词级对应词（`忽视`/`疏忽`），其机制中不存在"把语境句的 `the result of` 关系折进译文"的能力，也不可能凭空产出含 `造成的` 这一关系词的 7 字短语。

**Step 4｜解析失败也不会呈现为该串**

若 AI 返回非法 JSON，`parseWordPhraseBundle` 的 fallback 会把**整段原始输出**塞进 `meaning`（`aiProviders/index.js:126-131, 145-147`）。观测到的词义既无花括号也无 JSON 残片，说明 JSON 解析**成功**。

> **结论①**：该字符串由大模型（`deepseek-preset` 或备用 `kimi-preset`）在 `word_phrase_bundle` 调用中生成，作为 JSON 的 `meaning` 字段返回，解析后**原样落库、原样渲染**。
> **即：这不是字段错位、不是传参错误、不是渲染错配，而是模型输出的内容本身。**

### 2.3 已排除项（含排除理由）

| 假设 | 排除理由 |
| --- | --- |
| `meaning` / `contextTranslation` 两字段被互换 | 若互换，词义应等于整句译文（`而这不过是忽视的结果。`）或等于 `忽视`。观测值是**第三种**字符串，二者都不是 |
| 传参错位：把语境句当成了 `word`（或反之） | `word`/`context` 的唯一构造点是 `useBookmarkAI.js:11`（`bookmark.text` / `bookmark.contextSentence`）与 `aiProviders/index.js:100-104`；全库无第二处调用 `prompts.bookmarkCard`（`grep` 已核）。且若 `word` 是整句，模型无从产出与 `neglect` 对应的词义 |
| 直译兜底产出了它 | 见 2.2 Step 2/Step 3：兜底会抹掉语境句译文，且单字 MT 无此能力 |
| JSON 截断 / 空响应（即 Debug/08 的旧病复发） | 空响应会走 fallback 进备用 AI 或直译；截断会导致解析失败 → `meaning` 退化为含花括号的原文。两者均与观测不符 |
| 会话缓存串味 | 直译 LRU 缓存按**文本**归一化 key，**同时服务弹窗直译与收藏直译兜底**，且仅缓存直译结果、从不缓存 AI 释义（`src/services/directTranslation/index.js:74-98`）——收藏 **AI** 链路（路径 a）无任何缓存 |
| 收藏记录跨条串写 | 本地 `bookmarkStore.save` 按 `id` 覆盖（`storage.js:177-187`）；云端 upsert `onConflict: 'id'`（`readings.js:789-816`）；`translateBookmark` 用自身闭包内的 `bookmark.id` 回写。无跨条污染通道 |
| 复习/回顾等其它入口重写了译文 | 全库 `translateBookmark` 调用点仅 3 处，均在 `ReaderPage.jsx`（`:274`、`:339`、`:357`），均为实时收藏/预读链路 |

## 3. 机制分析：模型为什么把语境折进了词义

### 3.1 现行 prompt（`config/translation.js:15-25`；JSON bundle 自 46df1b4 引入，366ac0c 迁至 config/translation.js 后语义未再改动）

```
You are a translation assistant.
Translate according to the context and return STRICT JSON only (no markdown, no explanation):
{"meaning":"...","contextTranslation":"..."}

Rules:
- "meaning": concise Chinese meaning of "neglect" in this context, <= 12 Chinese characters.
- "contextTranslation": Chinese translation of this sentence: "And it's simply the result of neglect.".
- Keep wording natural and accurate.
```

### 3.2 该 prompt 中与本次漂移**相关**的五个属性

| # | 属性 | 为何构成漂移通道 |
| --- | --- | --- |
| P1 | 首句把角色与任务定为**翻译器**，且明确要求 `Translate according to the context` | 整段指令的基调是"按语境翻译"，而非"给出可替换该词的词典对应" |
| P2 | `meaning` 的定义是"**in this context** 的含义" | "语境中的含义"天然包含"该词在此处承担的语义角色"。当词处于 `the result of neglect` 这类属格结构中，"结果"这一关系成分就在模型的可解释空间内 |
| P3 | **同一次响应里同时要求输出整句译文**（`contextTranslation`） | 模型在生成 `meaning` 之前，已经（在同一个 JSON 里）确定了 `the result of neglect → 忽视的结果` 这一内容；`meaning` 槽位没有任何"词级/可替换"的约束，存在把刚写好的句子内容改写后填入的空间。观测到的 `忽视造成的后果` 正是 `忽视的结果` 的改写（补了关系词 `造成的`），与 P3 的"泄漏"路径吻合 |
| P4 | 唯一的硬约束是 **字符数上限**（`<= 12 Chinese characters`） | 只约束长度、不约束语义层级。`忽视造成的后果` = 7 字，**合规**。（对比：更早的单输出版本 `3db5d16` 上限是 8 字，7 字同样合规 —— 说明字符数上限对该类漂移没有防线作用） |
| P5 | prompt 中**没有给出一个"好词义"的样例**，JSON 示例里 `meaning` 的位置只有 `"..."` | 模型只能自行校准 `meaning` 的粒度；既无正例也无"不得包含语境句内容"的负例 |

补充事实：解析成功后**没有任何后处理校验**（无长度校验、无语义合理性校验、无与 `contextTranslation` 的重复/包含检查），`aiProviders/index.js:139-147` 解析完即返回，`useBookmarkAI.js:68-70` 直接以 `translationStatus: 'done'` 落库。因此**一旦模型漂移，全链路没有任何环节会拦下它**。

### 3.3 为什么是"有时候"（已由实验修正）

实验（§3.5）推翻了"采样随机性"与"模型切换"作为主因的猜测：

1. **对单个词是确定性的**：`neglect` 在该语境下，deepseek 20 次**全部漂移**（13× `忽视造成的后果`、6× `忽视所致`、1× `疏忽造成的后果`），零次词级对应。`temperature: 0.2` 只带来同义改写（`造成的后果` vs `所致`），**并不改变"是否漂移"这个结论**。
2. **模型切换基本不发生**：主力 deepseek 极少失败（thinking 已关闭，无空响应），而备用 kimi 在生产参数下**双重失效、从未成功兜底**（见 §8），直译兜底又不会产出这类短语。因此漂移样本几乎**全部由 deepseek 稳定产出**。
3. **"有时候"的真正来源是输入条件依赖**：漂移只在"该词在句中处于某种句法结构、承担了额外语义成分"时才发生。`neglect` 处于 `the result of ___` 属格结构，`"in this context"` 诱导模型输出"该词在此处的语义角色"而非"词本身"；换一个平铺语境（如 `He neglected his duty.`）就缺少可被折进词义的成分。即：**跨词/跨句是"有时候"，单词单句是"稳定复现"**。

### 3.4 与历史版本的对比（结构变化点）

| 版本 | prompt 形态 | 词义槽位约束 | 同响应是否含整句译文 |
| --- | --- | --- | --- |
| `3db5d16`（早期） | 单输出：`Reply with ONLY its Chinese meaning in this context, maximum 8 characters.` | 有（8 字） | **否** |
| `46df1b4` 起（现行；366ac0c 迁至 `config/translation.js`） | JSON bundle：`{meaning, contextTranslation}` | 有（12 字） | **是** |

即：**"整句译文"是在同一次生成中与 `meaning` 并置产出的**。这是本次现象在结构上新增的泄漏面（对应 P3）。此观察属于**推理**，见 §4/§5 的验证设计。

### 3.5 实验确证（2026-09-15 消融实验）

复现脚本 `scripts/reproduce-translation-drift.mjs`，逐字段复刻生产 prompt（`config/translation.js:15-25`）与请求参数（`netlify/lib/aiProviders.cjs`）；原始数据在 `experiment/` 目录。变量：`word=neglect`、`context=And it's simply the result of neglect.`。分类口径：`meaning` 含 `结果/后果/造成/导致/所致` 或（>4 字且含"的"）判为「语境改写（DRIFT）」，否则「词级对应（OK）」。

| 变体 | 改动 | 漂移率 | `meaning` 分布（deepseek-v4-flash） |
| --- | --- | --- | --- |
| **A（原样）** | — | **100%**（20/20） | 13× `忽视造成的后果`、6× `忽视所致`、1× `疏忽造成的后果` |
| B | 删首行 `Translate according to the context` | 100%（15/15） | 13× `疏忽造成的后果`、2× `忽视造成的后果` |
| **C** | 删 `meaning` 定义里的 `in this context` | **0%**（15/15） | 12× `忽视；疏忽`、3× `忽视，疏忽` |
| **D** | `WORD:` / `SENTENCE:` 分行标注，规则改 `the WORD`/`the SENTENCE`（**保留** `in this context`） | **0%**（15/15） | 15× `忽视；疏忽` |
| **E** | `meaning` 规则改为「可直接替换原词的简短对应词」 | **0%**（15/15） | 12× `忽视`、3× `疏忽` |

**结论②（消融交叉验证）**：

1. **根因是 `meaning` 槽位定义模糊，`"in this context"` 是关键必要诱因**：单一改动（C）把漂移率从 100% 打到 0%，证明 `in this context` 是必要条件；但 D 在**保留** `in this context` 的情况下仅靠显式锚定 `WORD`/`SENTENCE` 也归零，说明该短语并非充分条件——真正的根因是"`meaning` 槽位没有把输出锚定到词本身"，`in this context` 只是把注意力引向语境句、放大模糊性的关键措辞。C（删短语）/D（锚定 WORD）/E（定义为可替换词）是从三个不同方向消除同一个模糊性，互相印证。
2. P1（首行 `Translate according to the context`）**不是根因**：删掉它（B）漂移率仍 100%。
3. P3（同响应含整句译文）**不是根因**：D 保留整句译文输出，仅通过显式标注 WORD/SENTENCE 就消除漂移——说明漂移不在于"要不要译整句"，而在于 `meaning` 槽位"针对什么"被模型误解。
4. 三个独立改法（C 删短语 / D 分行标注 / E 改定义）都能彻底消除漂移，互相印证根因定位准确。
5. `温度 0.2 的采样随机性`（原 H2）被排除：A 变体 20 次全漂移，非随机。

## 4. 推测与待验证（按可信度排序）

> §3.5 的消融实验已把下列 H1 从**推测升级为结论**，并把 H2 **排除**。保留原文表述以记录推演过程。

### H1（✅ 已证实）：prompt 中 `"in this context"` 诱导的语境泄漏

模型把该词"在此语境中的语义角色"当作词义输出（P2 是根因，P3/P5 为放大因素）。
- 证据：消融变体 C（仅删 `in this context`）漂移率 100% → 0%；变体 D、E 同样归零；变体 B（删首行翻译基调）无效果，证明根因精确落在 `"in this context"` 上。
- 原支持论据（语义反推）与实验结论一致：`造成的` 是关系词，只可能来自对 `the result of` 的处理。

### H2（❌ 已排除）：模型随机性/能力差异

- 排除证据：A 变体 20 次全部漂移（100%），非随机；且漂移可被 prompt 单一改动**确定性**地消除，证明是 prompt 诱导而非模型固有随机。

### H3（低概率，仍保留）：该条收藏的 `text` 并非用户以为的单词

若实际划选是 `the result of neglect`（4 词 → `phrase`），则 `meaning` 显示 `忽视造成的后果` 属"短语释义"的合理范围，用户看到的 `neglect` 则来自……
- 排除倾向：卡片第一行渲染的就是 `bookmark.text`（`BookmarkHoverCard.jsx:129`），且 `highlightWord` 能在语境句中按该 text 命中加粗；用户样本中三者自洽。
- 若要彻底排除：直接读该条记录的 `text` 字段（见 §6）。

### 不能被任何假设解释的说法（提前排除）

- "字符数上限失效"：上限**没有失效**，`忽视造成的后果` 是合规的 7 字。问题不在长度校验被绕过，而在约束维度本身与错误类型不匹配（P4）。

## 5. 验证行动方案（按性价比排序）

| # | 动作 | 目的 | 说明 |
| --- | --- | --- | --- |
| V1 | 读该条收藏落库记录的 `translation_provider`（Supabase `bookmarks.translation_provider`，或本地 `localStorage` 的 bookmarks 项） | 判定是**主力 deepseek** 还是**备用 kimi** 答的 | 该字段已被持久化（`readings.js:798-799`、`mapping :134`），但 UI 未展示；这是零成本、可直接区分 H1/H2 的第一步 |
| V2 | 离线复现：用**完全相同**的 prompt（word=`neglect`，context=`And it's simply the result of neglect.`）对 `deepseek-v4-flash` 与 `kimi-k2.5` 各跑 20 次，逐次记录原始输出，统计 `meaning` 为"词级对应"与"语境改写"的比例 | 把 §3.3 的随机性假设量化 | 需要动用 `.env` 中的 `PRESET_DEEPSEEK_API_KEY` / `PRESET_KIMI_API_KEY`（会产生少量 API 费用，需用户授权） |
| V3 | 消融实验（同一批 20 次 × 下列 prompt 变体，A 为对照） | 分离"prompt 诱导"与"模型随机" | A=原样；B=删去首行 `Translate according to the context`；C=删去 `in this context`；D=把词与句改为显式分行标注（`WORD:` / `SENTENCE:`）；E=把 `meaning` 规则改为"一个可直接替换原词的简短对应词"。**若 B/C/E 的漂移率显著低于 A → 支持 H1；若各变体漂移率接近 → 支持 H2** |

## 7. 根因边界说明

- **已确证**（代码级、可复核）：词义字段由 AI 的 `meaning` 字段直接决定；本次样本必然来自一次成功的 AI 调用；链路中不存在字段错位、传参错误、缓存串写、跨条污染、JSON 截断等可能；解析后无任何校验环节。
- **已确证**（观测级）：产出串的语义层级与 `neglect` 的词义不匹配，而与语境句主干一致。
- **已确证**（实验级）：漂移由 prompt 中 `"in this context"` 短语确定性诱导；deepseek 在该输入上 100% 漂移，可被 prompt 单一改动彻底消除（消融 C/D/E 均归零）。
- **边界**：实验只覆盖 `neglect` 一词 + 单一属格结构语境。结论"`in this context` 是根因"对该输入成立；对其它词/语境的**漂移发生率**（§3.3 第 3 条的输入条件依赖）未做全面量化——但这不影响"该短语是漂移的必要诱因"这一结论，只影响"影响面有多广"的估计。

- **附带发现**（独立于本次根因）：生产 kimi 备用 AI 双重失效，见 §8。

## 8. 附带发现：生产 kimi 备用 AI 双重失效

复现过程中发现（与本次"过度拟合"根因**无关**，但属同一翻译链路的重要缺陷）：

| # | 现象 | 证据 | 影响 |
| --- | --- | --- | --- |
| 1 | `kimi-k2.5` 仅接受 `temperature: 1`，生产适配层误传 `0.2` | 实测 `temperature=0.2` → `HTTP 400 invalid temperature: only 1 is allowed for this model`；生产代码 `netlify/lib/aiProviders.cjs:110` 写死 `0.2` | 备用 kimi **每次调用必 400 失效** |
| 2 | 即便 temperature 修正为 1，模型名 `kimi-k2.5` 亦无效 | 实测 `temperature=1` → `HTTP 404 Not found the model kimi-k2.5 or Permission denied` | 该 key 下 `kimi-k2.5` 模型名不存在/无权访问 |

推论：`config/translation.js:10` 配置的 `fallbackPreset: 'kimi-preset'` 在当下环境中**从未成功兜底过**。当主力 deepseek 失败时，实际会直接跌到有道 → MyMemory 直译。这有两个副作用：

1. 用户拿到的收藏词义**几乎全部由 deepseek 产出**（deepseek 极少失败），本报告根因样本因此可确定性归因于 deepseek。
2. 真正的 AI 级"备用模型"形同虚设——若 deepseek 因故不可用，用户只能得到直译（有道的单字机器翻译），失去 AI 精译的语境理解。

> 此发现需另行立项修复（改模型名 / 改 temperature），不在本报告范围内。
