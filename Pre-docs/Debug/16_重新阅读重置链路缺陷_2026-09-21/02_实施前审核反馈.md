## 二、A 级阻断（必须修正后方可落库）

### A1 · 迁移文件名与现有文件冲突

**位置**：[01_修复方案.md](01_修复方案.md) §三「迁移落库说明」

方案声明：

> 迁移命名接续当前最新 `20260920000000_drop_frontend_audit_insert.sql`，采用 `20260921000000_add_reset_reading_rpc.sql`。

**事实不符**：`supabase/migrations/` 目录当前最新迁移不是 `20260920000000_drop_frontend_audit_insert.sql`，而是 **`20260921000000_add_bookmark_status.sql`**（收藏归档功能，今日已落库，见 [20260921000000_add_bookmark_status.sql](../../../supabase/migrations/20260921000000_add_bookmark_status.sql)）。

**后果**：拟用的 `20260921000000_add_reset_reading_rpc.sql` 与现有文件**同名**。若按方案落库，要么覆盖/混淆既有收藏归档迁移，要么因命名重复在登记与审计时产生歧义。

**修正**：改为 `20260921000001_add_reset_reading_rpc.sql`（或更晚时间戳）。同时 §三「执行前需确认」里「当前最新」的表述一并更新。

## 三、B 级（建议修正）

### B1 · 方案 A RPC 鉴权异常未带 `errcode='42501'`，JWT 重试失效

**位置**：[01_修复方案.md](01_修复方案.md) §三 方案 A SQL 与 JS 侧

方案 A 的 RPC 用旧式 `RAISE EXCEPTION 'unauthenticated'`（无 errcode）。而 2026-09-17 起新 RPC 已统一为 `raise exception 'unauthenticated' using errcode='42501'`（见 [20260917000003_first_reading_offer.sql](../../../supabase/migrations/20260917000003_first_reading_offer.sql) 的 `start_reading`、`increment_recommendation_add_count`）。

`isLibraryAccessError`（[errorUtils.js](../../../src/services/errorUtils.js#L10-L25)）只识别 `42501/401/403/jwt/session/unauthorized/forbidden/permission denied/row-level security`，**不识别字面量 `unauthenticated`**。因此：

- 无 errcode 的 `RAISE EXCEPTION 'unauthenticated'` 会以 SQLSTATE `P0001`（默认 `raise_exception`）返回，PostgREST 映射为 400，`isLibraryAccessError` 判 false；
- 方案 A JS 的 `if (isLibraryAccessError(error))` 分支不会命中 → **JWT 鉴权重试路径失效**，错误落入 `handleResetReading` 的 catch 报「重置失败」（不静默，但失去与 `deleteReading` 一致的重试能力）。

**修正**：RPC 中 `RAISE EXCEPTION 'unauthenticated' USING ERRCODE = '42501'`，与最新 RPC 模式对齐。

**附带建议**：方案 A 未显式 `perform public.lock_reading_user(auth.uid())`。当前虽因 `first_reading_guard` 触发器（[20260917000003](../../../supabase/migrations/20260917000003_first_reading_offer.sql#L63-L68)）对三条语句隐式加 advisory lock，功能上不阻塞，但与新版 RPC「显式加锁」约定不一致；建议补上，避免未来触发器变更后失去串行保护。

### B2 · P2-2「completed→继续阅读」复用 `start_reading` 未处理完成标记

**位置**：[01_修复方案.md](01_修复方案.md) §四推荐方案

方案建议把 `completed` 主按钮改为「继续阅读」调 `onMoveToReading`（即 `startReading` → RPC `start_reading`）。但 `start_reading`（[20260917000003](../../../supabase/migrations/20260917000003_first_reading_offer.sql#L212-L221)）只更新 `reading_status/reading_started_at/updated_at`，**不清 `reading_finished_at`，也不清 `reading_marks.completed=true`**。

`readingMark.completed=true` 在阅读器内的实际行为（[ReaderPage.jsx](../../../src/components/ReaderPage.jsx)）：

- 末尾显示「✓ 已读完」徽标（[ReaderPage.jsx:973](../../../src/components/ReaderPage.jsx#L973)）；
- 「跳转到阅读标记」被禁用（[ReaderPage.jsx:546](../../../src/components/ReaderPage.jsx#L546)）；
- 进度保存的 `isSameMark` 恒为 false（[ReaderPage.jsx:504-506](../../../src/components/ReaderPage.jsx#L504-L506)），完成态无法自然解除；
- 读完态触发评分加载等（[ReaderPage.jsx:219](../../../src/components/ReaderPage.jsx#L219)）。

**后果**：completed 书点「继续阅读」进入阅读区后，界面仍是「已读完」态，与「继续阅读」语义相悖；放回书架时又因 `completed=true` 归入 completed，形成「继续不了」的闭环。

**需要产品明确一个决策点**：`completed → 继续阅读` 到底指
- (a) 保留完成标记、仅重新打开（则阅读器的「已读完」行为须被接受，或需额外逻辑允许在读完态下继续标记进度）；还是
- (b) 解除完成标记、保留段落位置继续读（则 `start_reading` 不足，需新增一个「uncomplete + 保留进度」的 RPC/逻辑）。

无论 (a)/(b)，当前方案与验证清单 #6「保留书签/进度重新进入阅读区」都**未覆盖「completed 标记是否解除」这一维度**，需在实施前补齐。

## 四、C 级（补充与澄清）

### C1 · 方案 B upsert 残留 `progress_percent/section_id/completed_sections`

**位置**：[01_修复方案.md](01_修复方案.md) §三 方案 B

方案 B 的 upsert 只写 `paragraph_index=null, completed=false`。`ON CONFLICT DO UPDATE` 仅更新 payload 内的列，故 `progress_percent=100`、旧 `section_id`、旧 `completed_sections` 都会残留。

**影响评估**：`mapReadingMarkRow`（[readings.js:127-144](../../../src/services/readings.js#L127-L144)）对 `paragraph_index===null && completed===false` 返回 null，当前 UI/阅读器观察不到这些残留，**功能上等价清除**，不构成功能 bug；但 DB 层残留脏数据，与分析报告「进度与完成标记被清除」的表述有出入。此点恰好支撑「推荐方案 A（DELETE 全删）」的结论，作为补充论据记录，无需单独修 B。

### C2 · P3 弹窗复用跨组件，未说明抽取路径

**位置**：[01_修复方案.md](01_修复方案.md) §五

方案 §五称「将 `ImportPage.jsx:189` 的 `confirm()` 替换为复用/抽取 `ImportItemList` 中删除弹窗」。但删除弹窗（焦点圈 + `aria-modal` + Escape）位于 [ImportItemList.jsx:413-469](../../../src/components/ImportItemList.jsx#L413-L469)（`createPortal` 到 body），而 reset 的 `confirm()` 在 `ImportPage` 的 `handleResetReading` 内。二者分属不同组件，复用有两条路径：

- (a) 把 reset 确认弹窗下沉到 `ImportItemList`，与删除弹窗并列（reset 已在 more menu / 主按钮触发，`onReset` 已是其 prop，最顺）；
- (b) 抽取共享可访问确认弹窗组件，`ImportPage`/`ImportItemList` 共用。

方案未明确选哪条。不阻断，但实施前建议定死为 (a)，与「删除」保持同层同构。

### C3 · 方案 §4 引用「设计草图」未指明路径

**位置**：[01_修复方案.md](01_修复方案.md) §四实施点 3

「同步更新设计草图对应的 more menu 描述」——未给出设计草图的具体文件名/路径。实施时需确认指向哪份文档（疑为 `Pre-docs/开发/06_书架区设计刷新_2026-07-12` 下的视觉/草图文档），避免执行时无处落笔。

### C4 · 验证清单 #2 两套预期并列

**位置**：[01_修复方案.md](01_修复方案.md) §六验证清单

> `SELECT * FROM reading_marks WHERE reading_id='<id>'` 无行（或 completed=false 且 paragraph_index=null）

「无行」对应方案 A（DELETE），「completed=false 且 paragraph_index=null」对应方案 B（upsert）。二者并列，实施后验收时无法判断到底该符合哪条。建议在方案定稿（A/B 二选一）后，把 #2 的预期收敛为单一表述。

## 六、结论与建议

1. **分析报告可作为事实依据直接使用**，无需返工。
2. **P1-1、P1-2（方案 A）方向正确**，修正 A1（文件名）与 B1（errcode）后即可进入 P1 实施。
3. **P2 属产品决策项，暂缓编码**：若选「补齐入口」，必须同时解决 B2（completed 继续阅读的完成标记语义），否则「继续阅读」是坏的；若选「修订文档」，则无代码动作。
4. **P3、C1-C4 为收尾澄清**，不阻塞 P1 交付，随 P2 决策一并定稿。

建议在开始编码前，先回填 A1/B1/B2 三处修正，再执行 P1 实施。
