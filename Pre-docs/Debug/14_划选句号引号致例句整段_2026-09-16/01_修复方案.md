# 修复方案：划选句号引号致例句整段

- 日期：2026-09-16
- 前置：根因已确证，见 `00_问题分析报告.md`（§2、§3）
- 范围：仅修复 `findContainingSentence` 的句子切分正则；不触碰 `detectSelectionType`、渲染层、落库层

---

## 1. 根因（一句话）

`findContainingSentence` 的切分正则 `/[^.!?]+(?:[.!?]+(?:\s|$))?/g` 只认「标点后跟空白/结尾」为句尾，无法处理英文「句号在引号内」（`."`）——句号被丢弃、右引号被甩进下一句，选文含句号时跨边界匹配失败 → 兜底整段。

---

## 2. 核心修复：切分正则允许「句尾标点后紧跟闭合符」

文件：`src/utils/textUtils.js`（`findContainingSentence`，仅改第 28 行正则，加一行注释）。

### 2.1 改动

```diff
   // 将多点省略号（..）统一替换为单字符 …，避免正则将其误判为句子结束符
   const ELLIPSIS = '…'
   const normalized = paragraphText.replace(/\.{2,}/g, ELLIPSIS)

+  const regex = /[^.!?]+(?:[.!?]+["'”’)\]]*(?:\s|$))?/g
   let match
```

说明：在 `[.!?]+` 与 `(?:\s|$)` 之间插入 `["'”’)\]]*`（零个或多个闭合符：直引号 `"` `'`、弯引号 `”` `’`、右括号 `)` `]`）。`*` 保证不匹配任何闭合符时（普通句尾）行为与原来完全一致，纯向后兼容。

### 2.2 选型理由

| 维度 | 说明 |
| --- | --- |
| 最小改动 | 只改一行正则，函数签名、唯一调用点、渲染/落库全部不动 |
| 向后兼容 | `*`（零个或多个）使无闭合符的普通句尾路径不变 |
| 覆盖面 | 一次覆盖 `"` `”` `'` `’` `)` `]` 六种常见句尾闭合符，不止报告中的直引号 |
| 已实测 | 用用户原文复现：两种划选均返回完整正确例句（见 §3） |

### 2.3 备选方案（未采用）

| 方案 | 思路 | 未采用原因 |

| B：基于选区 offset 定位句子 | 改 `findContainingSentence` 签名为 `(paraText, offset, length)`，按偏移左右扫描句界 | 需改函数签名与唯一调用点（`ReaderPage.jsx:300`）并新增 offset 传参；改动面大，而当前 `selectedText` 语义已足够，正则修复即可精准解决 |

### 2.4 结论

**采用方案 A（2.1 的正则微调）**：一行改动、向后兼容、根因级修复，且把「例句截断」的次要表现一并解决。

## 4. 边界与不做的事

- **不处理**缩写句号（`e.g.`/`Mr.`/`U.S.`）导致的切分——本次未涉及、属既有已知脆弱性，需单独评估。
- **不处理**省略号+引号（`…"`）等更复杂组合——`findContainingSentence` 已对省略号做过单独归一化（`textUtils.js:24-25`），但 `."…"` 这类仍会退回旧行为，罕见且非本次症状。
- **不处理**闭合符后无空格（如 `."Next`）——因 `(?:\s|$)` 仍要求闭合符后跟空白/结尾，此类缺失空格的异常文本仍会兜底整段；属正常排版前提下的合理取舍，不处理。
- **不动** `detectSelectionType`：它对 `an "executive."` 判 `phrase` 是**正确**的（末字符是引号非 `.`），正是期望的「词/短语收藏带例句」。
- 闭合符集合若后续遇到新场景，可再扩（如 `}`、`»`）。
