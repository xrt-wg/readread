# 问题分析报告 — 阅读区进度计算逻辑

- **日期**：2026-06-19
- **分支**：feat/translation-test
- **问题**：阅读进度计算逻辑存在多处根本性缺陷
- **严重程度**：P0（段落索引不对齐）+ P1（数据丢失）
- **状态**：🔴 待修复

---

## 1. 现象

在阅读区测试中发现以下异常：

1. 阅读区文章列表中显示的进度百分比与用户在阅读器的实际进度不匹配
2. 多章节书（EPUB）的进度完全无法正确反映
3. 用户清除阅读标记后，数据库中的 `completed_sections` 被意外清空
4. 多章节书中切换章节后点击段落标记 → 前一章节的标记被意外清除

---

## 2. 架构概览

阅读进度涉及两条数据流：

```
写入链:
  用户在阅读器点击「标记读到这里」
    → handleSetReadingMark(paraIndex)
    → saveReadingMark(articleId, paragraphIndex, options, sectionId)
    → reading_marks 表写入 { paragraph_index, completed: false, section_id }

读取链:
  文章列表展示进度 (ImportPage 阅读标签)
    → listReadingMarks → readingMarks[articleId] = { paragraphIndex, completed }
    → calcProgress(article, mark)
    → (readWords / totalWords) × 100 → 显示为百分比
```

**核心瓶颈**：写入链的 `paragraphIndex` 来自阅读器的 markdown AST 渲染（`react-markdown`），读取链的 `calcProgress` 用 `article.text.split(/\n+/)` 分割段落。两者对"段落"的定义从根源上不一致。

---

## 3. 问题分析

### 3.1 🔴 问题 1：段落索引 Markdown/纯文本不对齐（P0）

**相关文件**：
- [`src/components/ImportPage.jsx:49-56`](src/components/ImportPage.jsx#L49-L56) — `calcProgress`
- [`src/components/ReaderPage.jsx:48-176`](src/components/ReaderPage.jsx#L48-L176) — `MarkdownContent`

**机制分析**：

当文章有 `markdown` 字段时，阅读器使用 `MarkdownContent` 渲染段落。段落索引来自 `paraIdxRef`，该计数器在以下组件中递增：

| Markdown 元素 | 是否递增 paraIdxRef | 说明 |
|---------------|-------------------|------|
| `<p>` | ✅ 递增 | 普通段落 |
| `<li>` | ✅ 递增 | 列表项 |
| `<h1>` ~ `<h4>` | ❌ 不递增 | 标题不占段落索引 |
| `<blockquote>` | ❌ 不递增 | 引用块 |
| frontmatter | — | 固定 `data-para-index="-1"` |

而 `calcProgress` 中段落由 `article.text.split(/\n+/).filter(p => p.length > 0)` 定义——对纯文本按空行分割。

**举例**：假设文章 markdown 为：
```markdown
# Chapter 1

First paragraph of the story.

Second paragraph here.

- Point A
- Point B

Final paragraph.
```

在阅读器中 `MarkdownContent` 的段落索引：
```
<p>First paragraph of the story.</p>    → paraIdx = 0
<p>Second paragraph here.</p>           → paraIdx = 1
<li>Point A</li>                        → paraIdx = 2
<li>Point B</li>                        → paraIdx = 3
<p>Final paragraph.</p>                 → paraIdx = 4
```
（h1 `# Chapter 1` 不递增）

而 `calcProgress` 对 `article.text` 的分割结果取决于 `text` 列的实际内容——若 `text` 列将标题作为独立行保留，所有后续段落索引偏移至少 +1。且 `text` 列和 `markdown` 列的行分割语义完全不同。

**结论**：阅读器端和列表端对同一篇文章的"段落"定义和索引从源头不一致，进度百分比必然错误。

#### 3.1.1 实测验证：引用块导致 99% 假阳性（2026-06-20 发现）

测试中发现的具体案例：阅读器顶部栏滚动进度 65%，标记段落后回列表显示 99%。

**根因**：`getMarkdownParagraphs` 中对引用块的处理存在漏洞：

- `MarkdownContent` 的 `blockquote` 组件不递增 `paraIdxRef`，但 `react-markdown` 递归处理引用块**内部**的 `<p>` 和 `<li>` → **递增**
- `getMarkdownParagraphs` 用 `/^>\s/m` 匹配后 **continue 跳过整个引用块** → 内部段落完全不计数

结果：含引用块的文章中，`MarkdownContent` 计数 > `getMarkdownParagraphs` 计数 → 用户在引用块之后的段落点击标记 → `paragraphIndex`（AST）超出 `getParagraphs`（regex）数组长度 → `getWordOffsetAtParagraph` 溢出分支返回全部词数 → `readWords ≈ totalWords` → **99%**。

详细分析见 [2026-06-20 独立分析报告](../../2026-06-20/01_阅读进度99pct异常/修复/01_问题分析报告.md)。

### 3.2 🔴 问题 2：多章节文章段落索引归零（P0）

**相关文件**：
- [`src/components/ReaderPage.jsx:953`](src/components/ReaderPage.jsx#L953) — `key={currentSection?.id || 's_main'}`
- [`src/components/ImportPage.jsx:49-56`](src/components/ImportPage.jsx#L49-L56) — `calcProgress`

**机制分析**：

多章节文章（book 类型，如 EPUB）的每个 section 在 `MarkdownContent` 中通过 React `key` 属性独立挂载：

```jsx
<MarkdownContent
  key={currentSection?.id || 's_main'}   // ← 切换 section 时强制重新挂载
  markdown={currentBody.markdown}
  ...
/>
```

`MarkdownContent` 内部的 `paraIdxRef` 是组件实例的局部状态，重新挂载后从 0 开始。因此 `paragraphIndex` 始终是**当前 section 内的相对索引**。

而 `calcProgress` 使用全局的 `article.text`：
```js
const paragraphs = article.text.split(/\n+/).map(p => p.trim()).filter(p => p.length > 0)
const readWords = paragraphs.slice(0, mark.paragraphIndex + 1).join(' ').split(/\s+/).filter(Boolean).length
```

`mark.paragraphIndex` 是"某 section 内的第 N 段"，「`paragraphs.slice(0, N+1)`」却把它当成"全文的第 N 段"。

**举例**：
```
书有 3 个章节：
  Section A: 500 词，10 段
  Section B: 800 词，15 段
  Section C: 300 词，8 段

用户在 Section B 读到第 5 段 → paragraphIndex = 4
calcProgress 在全文 33 段中取前 5 段的词数 → 仅覆盖 Section A 前半
实际用户已读 Section A 全部 + Section B 前 5 段 → calcProgress 严重低估
```

此外 `saveReadingMark` 只保存最后操作的 section 信息，无法汇总多章节的整体进度——`completedSections` 字段从未被更新。

**结论**：多章节书的进度完全不可靠。

### 3.3 🟡 问题 3：`clearReadingMark` 云端路径误清空 `completedSections`（P1）

**相关文件**：[`src/services/library.js:432-448`](src/services/library.js#L432-L448)

**机制分析**：

```js
export async function clearReadingMark(articleId, options) {
  if (!useCloudSource(options)) {
    readingMarkStore.delete(articleId)
    return null
  }

  await saveCloudReadingMarkRecord(
    {
      articleId,
      paragraphIndex: null,
      completed: false,
      // ← completedSections 未传递！
      updatedAt: new Date().toISOString(),
    },
    options.userId
  )
  return null
}
```

`saveCloudReadingMarkRecord` 对未传递字段的处理：
```js
completed_sections: record.completedSections ?? [],  // undefined ?? [] → []
```

**影响链**：
1. 用户在多章节书中逐个读完多个 section → `completed_sections` 累积有数据
2. 用户在某 section 中点击段落标记按钮切换位置 → 触发 `clearReadingMark`
3. `completed_sections` 被覆写为 `[]` → 全部章节完成记录丢失

**结论**：这是一个数据丢失 bug。`clearReadingMark` 应保留已有的 `completedSections`。

### 3.4 🟡 问题 4：云端/本地 `completed` 保留行为不一致（P2）

**相关文件**：
- [`src/services/library.js:415-429`](src/services/library.js#L415-L429) — `saveReadingMark`（云端）
- [`src/store/storage.js:196-209`](src/store/storage.js#L196-L209) — `readingMarkStore.save`（本地）

**机制分析**：

| 路径 | `completed` 处理 | 行为 |
|------|-----------------|------|
| 云端 `saveReadingMark` | 写死 `completed: false` | 总是覆盖为 false |
| 本地 `readingMarkStore.save` | `existing?.completed ?? false` | 保留已有状态 |

**场景**：用户已读完一篇文章（`completed = true`），重新打开并把标记移到更早的段落 → 云端路径将 `completed` 改为 `false`，本地路径保留 `true`。

**结论**：云端路径应与本地路径一致，仅在显式操作时改变 `completed` 状态。

### 3.5 🟢 问题 5：阅读器内进度条与列表进度无关（P3，设计问题）

**相关文件**：[`src/components/ReaderPage.jsx:574-604`](src/components/ReaderPage.jsx#L574-L604)

阅读器顶部进度条：
```js
const pct = scrollable > 0 ? Math.round((window.scrollY / scrollable) * 100) : 0
```

这是**滚动进度**，而非**段落进度**。用户向下滚动到底部但不标记任何段落 → 阅读器显示 100%，文章列表的 `calcProgress` 仍为 0%。两种进度语义不同，但非 bug——是设计层面的不一致。

### 3.7 🟡 问题 7：`handleSetReadingMark` 缺少 `sectionId` 比对（P1）

**相关文件**：[`src/components/ReaderPage.jsx:427`](src/components/ReaderPage.jsx#L427)

**机制分析**：

```js
const handleSetReadingMark = useCallback(async (paraIndex) => {
  // ...
  if (readingMark?.paragraphIndex === paraIndex && !readingMark?.completed) {
    const clearedMark = await clearReadingMark(articleId, options)  // 清除
  } else {
    const mark = await saveReadingMark(articleId, paraIndex, options, currentSection?.id ?? null)
    // 保存
  }
}, [...])
```

缺陷在于 `readingMark?.paragraphIndex === paraIndex` 仅比对段落索引，未比对 `sectionId`。在多章节文章中：

```
Section A 段落 0 已标记 → readingMark = { paragraphIndex: 0, sectionId: "s_0" }
切换到 Section B → 点击段落 0 → paraIndex = 0
  → readingMark.paragraphIndex (0) === paraIndex (0) → true
  → 触发 clearReadingMark 清除 Section A 的标记
  → 而非在 Section B 保存新标记
```

**影响**：多章节书的阅读标记无法在不同 section 中独立设置。用户在 Section A 设置标记后切换到 Section B 设置标记 → Section A 的标记被意外清除。阅读位置记录在章节间互相覆盖。

**结论**：应引入 `sectionId` 比对——仅当段落索引和章节 ID 同时匹配时才视为「同一位置」。

### 3.8 🟢 问题 8：`completedSections` 字段完全未使用（P3，技术债务）

`completed_sections` 列在整条数据链中已完整支持：
- 数据库 schema（`reading_marks` 表）
- `saveCloudReadingMarkRecord` 的 upsert body（`library.js:137`）
- `mapReadingMarkRow` 的映射（`library.js:82`）
- `readingMarkStore.save` 的保留逻辑（`storage.js:204`）

但 `ReaderPage.jsx` 中**零引用**——没有 UI 能展示哪些章节已完成，也没有逻辑更新它。

## 4. 问题汇总

| 编号 | 严重程度 | 问题 | 根因 | 影响 |
|------|---------|------|------|------|
| 1 | **P0** | 段落索引 markdown/纯文本不对齐 | `MarkdownContent` 和 `calcProgress` 用不同段落定义 | 所有 markdown 文章进度错误 |
| 2 | **P0** | 多章节文章进度不可用 | `paragraphIndex` 是节内索引，`calcProgress` 用全文索引 | 多章节书进度完全不可靠 |
| 3 | **P1** | `clearReadingMark` 误清空 `completedSections` | 云端路径未传递该字段 | 已完成章节记录丢失 |
| 4 | **P2** | 云端/本地 `completed` 保留不一致 | 云端写死 `false`，本地保留原值 | 重标记已读完文章时行为分裂 |
| 5 | **P3** | 阅读器进度条与列表进度无关 | 滚动进度 vs 段落进度 | 用户可能困惑 |
| 6 | **P1** | `handleSetReadingMark` 缺少 `sectionId` 比对 | `paragraphIndex` 比对未包含 `sectionId` | 多章节标记在章节间互相覆盖 |
| 7 | **P3** | `completedSections` 完全未使用 | UI 层缺失 | 多章节进度无记录 |

---

## 5. 根因推导

所有问题的根源指向同一个架构缺陷：

> **段落索引在写入端和读取端使用了完全不同的段落模型。**

写入端基于 `react-markdown` 的 AST 渲染来定义段落（`<p>` + `<li>`），读取端基于纯文本的换行分割来定义段落。两者之间没有任何桥接或统一抽象。多章节书的 section 切换引入索引归零，且 `handleSetReadingMark` 中的标记比对缺少 `sectionId` 维度，阅读位置在章节间互相覆盖，进一步放大了这一矛盾。
