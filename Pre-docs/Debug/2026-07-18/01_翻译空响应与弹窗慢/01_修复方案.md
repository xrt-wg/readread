# 修复方案：翻译服务空响应治理与全链路提速

- 日期：2026-07-18
- 前置条件：`00_问题分析报告.md` 已确认
- 状态：待确认实施

## 1. 目标

1. 空响应不再被当成功落库：任何"200 但内容为空"都视为失败并进入降级链。
2. 消除推理模型思考耗尽 token 预算的直接诱因，同时降低收藏卡片翻译耗时。
3. 全链路具备超时与快速失败能力，失败状态 UI 可见、可手动重试。
4. 弹窗同词秒出，慢请求有明确错误反馈而非无限转圈。

## 2. 实施内容

按 A（根因修复，必做）→ B（快速失败与可重试）→ C（弹窗提速）分层，A 可独立先上线。

### 2.1 A 层：根因修复

**A1. 关闭 DeepSeek 思考模式 + 调整 token 上限**

- `netlify/lib/aiProviders.cjs` `callDeepSeek` 请求体增加关闭思考的参数（DeepSeek V4 支持思考模式开关，确切参数名/取值以官方文档 `https://api-docs.deepseek.com/zh-cn/guides/thinking` 为准，实施时以一次真实请求验证生效）。
- `config/translation.js` `tokenLimits.bookmarkCard` 由 260 上调至 512，为长语境句留余量。
- Kimi 未传 thinking 参数、默认不思考，无需改动。
- 备选：若该 API 档不支持关闭思考，则改为上调三档上限（bookmarkCard → 1024、sentence → 1024、paragraph → 2048），单独实施同样有效，但响应速度收益小于关思考。

**A2. 空响应视为失败（后端）**

- `aiProviders.cjs` 四个 `call*` 函数在解析结果为空串时 `throw`，错误信息携带 `finish_reason`；同时补一行 `console.warn` 记录 `finish_reason`/`usage`，为根因边界（报告 §5）留下验证数据。
- 效果：`translate.js` 走既有 catch 返回 500，前端自然进入 fallback，空串不再触达落库逻辑。

### 2.2 B 层：快速失败与可重试

**B1. 上游超时**：`aiProviders.cjs` 与 `translate.js`（有道/DeepL）的全部上游 fetch 加 `signal: AbortSignal.timeout(8000)`，在 Netlify 10s 强杀前主动失败、快速进入下一级降级。

**B2. 前端收藏链路**（`src/hooks/useBookmarkAI.js`）：

- 每级 `translateText` / `translateDirectWithFallback` 传入 signal（每级约 12s 的 AbortController 超时）；
- `runAI` 对空 `translation` 视为失败抛错，继续降级；
- 全部失败落 `translationStatus: 'error'`（现有逻辑保留）。

**B3. UI 区分 error 并支持重试**：`BookmarkPanel.jsx`、`BookmarkHoverCard.jsx`（复习卡若复用同一数据源一并覆盖）对 `translationStatus === 'error'` 显示"翻译失败"与重试按钮，点击重新调用 `translateBookmark`。

### 2.3 C 层：弹窗提速

**C1. 会话内缓存**：直译服务层加 Map 缓存（key 为归一化文本，上限约 200 条，仅存活于页面会话），命中即秒出，并减少有道调用量。

**C2. 超时与错误可见**：

- 弹窗请求加 8s 超时（并入现有 AbortController 逻辑）；
- `translateDirectByProvider` 对空结果视为失败以触发 fallback；
- 超时 / 全部兜底失败 / 空结果时，`TranslationPopup.jsx` error 分支显示明确文案，消除 `result === ''` 时三分支全不渲染的静默区。

**C3.（可选，低优先级）** `netlify.toml` 为 translate 函数配置 `timeout`：Starter 套餐固定 10s 无法上调；Pro 可配 26s。B1 到位后此项意义有限。

## 3. 有效性原理

- 关闭思考模式后，简单翻译任务不再产生思考 token，max_tokens 耗尽导致空 content 的诱因消除；推理开销消失同时带来 2–5 倍的速度提升（A1 同时治理两个问题）。
- "空即失败"把空响应从"静默成功"变为"可降级事件"，配合既有四级 fallback，任一上游异常都能收敛到兜底结果或明确的 error 状态，不再出现永久静默。
- 上游 8s 超时 < Netlify 10s 强杀 < 前端每级 12s 超时，三层时限由内到外递增，保证每一级都能在合理时间内让位给下一级。

## 4. 预期效果

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 思考耗尽 max_tokens | 200 空串 → done 落库，永久静默 | 视为失败 → 降级 kimi/直译，或落 error 可重试 |
| 上游单级缓慢/挂起 | 整链 20–30s+ 或无限转圈 | 8s 内主动失败换路，最坏情况有明确终态 |
| 翻译失败 | 与"无译文"外观相同 | UI 显示失败态 + 手动重试 |
| 弹窗首划 | 1–3s+ 无反馈 | 仍有网络延迟，但超时/错误有明确提示 |
| 同词重复划选 | 重复完整请求 | 缓存命中秒出 |
| 收藏卡片翻译耗时 | 含思考开销 | 关闭思考后显著下降（以 providerMs 实测为准） |

## 5. 验证步骤

1. 复现原空字段场景（长难句/生僻词收藏），确认不再出现 `done` + 空译文；Netlify 日志确认空响应时返回 500 且带 `finish_reason` 告警。
2. DevTools Console 过滤 `[AI_PERF_FUNCTION]`，对比修复前后 `providerMs`，确认关思考生效。
3. 通过停用 key / 断网模拟逐级失败，确认 fallback 链收敛、最终 error 状态可见且重试按钮可用。
4. 同一词重复划选，确认第二次 `totalMs` 接近 0（缓存命中）。
5. 抽查若干卡片译文质量，确认关思考后翻译质量无可见回退。

## 6. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 关思考参数名/取值与文档漂移 | 实施时以官方文档与一次真实请求验证；无效则退到上调 max_tokens 的备选方案 |
| 关思考影响翻译质量 | 卡片翻译为简单任务（temperature 0.2 + 严格 JSON prompt），质量风险低；上线后按验证步骤 5 抽查 |
| 8s 上游超时误杀慢网请求 | 超时后仍有 fallback 链与 error 重试兜底，不会更差于现状 |
| 缓存展示陈旧译文 | 仅存会话内存、刷新即清；直译结果本身无时效性 |
| error 重试被频繁触发刷量 | 重试为手动触发；如需要可后续加冷却时间 |
