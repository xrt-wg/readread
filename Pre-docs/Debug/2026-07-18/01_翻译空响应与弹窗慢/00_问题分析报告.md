# 问题分析报告：收藏卡片翻译空响应与翻译弹窗响应慢

- 日期：2026-07-18
- 状态：已完成根因定位，待确认修复方案
- 影响范围：收藏卡片 AI 翻译（生成与落库、面板/悬停卡/复习卡展示）、划词翻译弹窗

## 1. 现象

1. 收藏卡片的翻译有时直接没有响应。查看接口响应发现字段为空（HTTP 200 但 `result` 为空串），卡片永久停留在无译文状态：无错误提示、无自动重试。
2. 划词翻译弹窗响应速度慢，经常长时间转圈；部分情况下弹窗只剩原文，外观上同样是"没有响应"。

## 2. 结论

**问题 1 的根因不是超时，而是"上游 200 空响应被全链路静默吞掉，最终以成功落库空译文"。**

直接诱因：主力模型 `deepseek-v4-flash` 是推理型模型，默认开启思考模式（non_think / think_high / think_max 三档，非简单调用默认带思考）；而收藏卡片翻译的 `max_tokens` 仅为 **260**（`config/translation.js:38`）。思考 token 计入 max_tokens 预算，预算被思考耗尽时上游返回 **200 但 `content` 为空**（`finish_reason: 'length'`）。思考长度随输入变化，因此表现为"有时"为空。

此后每一环都把"空"当"成功"透传（见 3.1），最终以 `translationStatus: 'done'` 落库空译文；UI 对空串与 error 状态均不渲染，形成用户看到的"没有响应"，且失败后永不自动重试。

**问题 2 的根因是五个叠加因素**：全链路非流式、有道经 Netlify 函数中转（冷启动叠加上游延迟）、失败后兜底到慢且可无限挂起的 MyMemory、全链路无任何超时控制、无结果缓存。

## 3. 证据链

### 3.1 空响应的静默透传链（已逐环核实代码）

| 环节 | 位置 | 行为 |
| --- | --- | --- |
| 上游适配 | `netlify/lib/aiProviders.cjs:72` | `data.choices?.[0]?.message?.content?.trim() ?? ''` —— 200 空 content 不报错，返回 `''` |
| 函数出口 | `netlify/functions/translate.js:227` | 空串照样返回 200 `{result: ""}` |
| 前端解析 | `src/services/aiProviders/index.js:125-131` | `parseWordPhraseBundle('')` 返回 `{meaning:'', contextTranslation:''}`，不报错 |
| 收藏编排 | `src/hooks/useBookmarkAI.js:30-34` | 未抛错即 `success=true`，空译文以 `translationStatus:'done'` 落库 |
| UI 渲染 | `BookmarkPanel.jsx` / `BookmarkHoverCard.jsx` / 复习卡 | 空串与 `error` 状态都不渲染任何内容，外观一致 |

四级串行 fallback（deepseek → kimi → 有道 → MyMemory，`useBookmarkAI.js:29-66`）每一级的 catch 只打日志，且**全部调用未传 `signal`**：无客户端超时、无法取消。Netlify 函数未配置 timeout（`netlify.toml` 只给 `generate-recommendation` 配了 26s），默认 10s 强杀；上游 fetch 也无超时。最坏情况卡片"翻译生成中…"持续 20–30s+ 才出兜底结果，MyMemory 兜底（浏览器直连、无 timeout）可无限挂起。

### 3.2 模型身份与思考模式（已核实公开资料）

- `deepseek-v4-flash`：DeepSeek V4 系列真实模型，2026-04 发布，OpenAI 兼容接口，支持 non_think / think_high / think_max 三种思考模式，默认带思考（[DeepSeek V4 Preview](https://www.atlascloud.ai/pt/blog/ai-updates/deepseek-v4-preview-launch)、[模型卡](https://fe-static.deepseek.com/chat/transparency/deepseek-V4-model-card-EN.pdf)）。
- `kimi-k2.5`：Moonshot 真实模型；未显式传 `thinking` 参数时默认不思考，作为备用 AI 不受同一问题影响。
- 推理型模型在 max_tokens 过小时"思考耗尽预算 → content 为空"是 DeepSeek 官方文档明确的已知行为。

### 3.3 弹窗慢的叠加因素

| 因素 | 位置 | 说明 |
| --- | --- | --- |
| 非流式 | 全链路 | 必须等完整响应，1–3s 无任何中间反馈 |
| 函数中转 | `src/services/directTranslation/index.js:41-72` | 有道经 Netlify 函数代理，冷启动（常见 1–3s）+ 上游延迟叠加 |
| 慢兜底 | `src/services/directTranslation/myMemory.js` | 有道失败退 MyMemory：免费公共 API，慢且匿名限流，GET 无 timeout 可长期挂起 |
| 无超时 | `src/hooks/useDirectTranslation.js` | AbortController 仅用于"新选区取消旧请求"，无 setTimeout 超时，慢请求一直转圈 |
| 无缓存 | — | 同一词反复划选反复请求 |
| 空结果静默 | `TranslationPopup.jsx:134` | `result === ''` 时 loading/result/error 三分支均不渲染 |

### 3.4 已排除项

- **prompt 过长**：bookmarkCard prompt 约 60 词 + 语境句，长度不是慢的来源。
- **模型名不存在**：若模型名错误，上游返回 4xx，代码走 `!res.ok` 抛错进 fallback，现象应为"慢但最终有兜底结果"，与观测到的 200 空字段不符。
- **`config/directTranslation.json`**：死配置，src 中无任何 import，与本问题无关（易误导，建议另行清理）。
- **会话/权限问题**：翻译链路不依赖用户会话，与已修复的收藏删除 403 无关。

## 4. 影响

- 收藏的单词/短语卡片可能永久无译文，且以 `done` 状态落库，不会自愈、不会重试；面板、悬停卡、复习卡三处同时受影响。
- 句子/段落收藏使用同一链路（`max_tokens` 分别为 200/600），同样存在空响应风险。
- 弹窗体验：首划 1–3s+ 无反馈，兜底路径下可达 10s+ 或挂起；重复划选重复等待。

## 5. 根因边界说明

- 已核实：全部代码路径、配置值、两个 preset 模型的真实身份与思考模式支持情况。
- 推断待最终验证：上游空 content 的确切触发为"思考耗尽 max_tokens"。当前函数日志未记录 `finish_reason`/`usage`，无法从既有日志直接确认。验证方式：复现时查 Netlify 函数日志 `translate_perf` 的 `provider`/`providerMs`，并在修复时顺带补记 `finish_reason`。
- 即使该推断不成立（空 content 另有触发，如内容过滤），"空响应视为失败 + 全链路快速失败"的修复方向依然成立；关闭思考模式对简单翻译任务同时是提速手段。
