# 机制定位报告 — 划选选区异常过扩（第三次分析）

> **日期**：2026-09-15（同日第二轮，基于用户新测试）
> **前置文档**：`01_问题分析报告.md`（H1 结构说）、`02_问题再分析报告_2026-09-15.md`（H5 硬件说）
> **决定性新信息**：
> 1. 发现**高频触发场景**：划选并收藏一个词之后，**紧接着**划选并收藏下一个词，很大概率触发（误选前面很大一段文本）；
> 2. **更换鼠标后现象不变**。
> **本文性质**：仅分析定位，不含修复方案。

## 一、假说清理

### H5 / H6（鼠标硬件 / OS 软件层）→ **排除**

- 更换鼠标现象不变 → 硬件微动抖动排除；
- 触发与「刚完成收藏」这一**应用状态**强相关（高频、可重复），而非随机 → 与硬件故障的随机性、渐进性特征不符；
- 硬件说解释不了「为什么偏偏在收藏后的下一次划选高发」。

### H1 / H1b（嵌套 span / 包裹 span 结构说）→ **降级为无关或次要**

- 结构是静态、确定性的，无法解释「收藏后紧接着划选」这一**时序条件**为何是高频触发前提；
- 结构无法解释触发与「收藏动作」的相关性。

### H2（重渲染替换锚点节点）→ **恢复并升级为主机制；第一份的「排除」是误判**

第一份报告第三节称预读模式「无重渲染」从而排除 H2，**该推理有漏洞**：当时只核查了 hover 链路（`showHoverCard` 预读首行 return），**漏掉了收藏管线本身就会触发重渲染**——预读模式「划词即收藏」（ReaderPage.jsx:254-281），每次收藏都执行 `saveBookmark → loadReaderState → setBookmarks` → React 重渲染。因此预读实验从未排除重渲染机制，反而与之完全相容。

## 二、根因机制（M-render）：拖选途中锚点文本节点被异步重渲染销毁

### 2.1 完整机制链（代码事实 → 推断）

**事实 1：每次收藏触发两波异步重渲染。**
- 预读模式（ReaderPage.jsx:254-281）：mouseup → `saveBookmark` → `loadReaderState` → `setBookmarks`（第一波）；`translateBookmark(saved, async () => { await loadReaderState() })`（第二波，翻译完成后，可能滞后数秒）。
- 非预读弹窗模式（ReaderPage.jsx:306-349 `handleBookmark`）：点收藏 → `closePopup()` → 同样两波。

**事实 2：异步窗口很宽。**
云端路径下 `saveBookmark`（Supabase upsert，readings.js:783）+ `loadReaderState`（`listBookmarksByArticle` + `getReadingMark` 两个查询，readings.js:708）= **3 次顺序网络往返**，典型耗时数百毫秒到秒级。本地路径快得多（窗口窄），这解释了频率的波动性。

**事实 3：重渲染会销毁并重建刚收藏段落的文本节点。**
- `setBookmarks` → ReaderPage 重渲染 → SectionFlow 重渲染；`bookmarksRef.current.filter(...)` 每次生成新数组（SectionFlow.jsx:98/159/211），`ParagraphRenderer` 的 `memo` 被引用变化击穿 → 全段落重渲染。
- 对**刚加入新收藏的段落**，渲染输出从纯文本节点变为 `[文本, <span>背景, 文本]` 等结构 → React  reconciliation 会**移除旧文本节点、插入新节点**。其余无结构变化的段落 DOM 不动。

**事实 4：用户「紧接着」的划选，大概率落在同一个段落。**
第一份报告即记录「划选紧挨上一个收藏词的词语」易发——下一个词通常就在刚收藏词的同句/同段，其文本节点正是事实 3 中被销毁重建的那批。

**推断（机制核心）：若 React commit 落在用户下一次拖选的 mousedown 与 mouseup 之间，选区锚点所在的文本节点在拖选途中被移出 DOM。** 浏览器对「活动拖选中锚点节点被移除」的恢复行为是把锚点回落到块级容器（`<p>`）起点（contenteditable 编辑器中广为人知的一类选区跳变），于是选区过扩为「段首 → 当前光标」，视觉上即「光标之前的所有文本被选中」；mouseup 时 `handleMouseUp`（ReaderPage.jsx:197）忠实读取该大区间 → 大段错误文本被收藏。

### 2.2 对全部历史证据的拟合（逐条）

| 证据 | M-render 拟合 |
|------|--------------|
| 收藏后**紧接着**划选下一个词 → 高频 | ✓ 异步 commit 窗口与下一次手势重叠是触发条件；「紧接着」使重叠大概率发生 |
| 更换鼠标现象不变 | ✓ 与输入设备无关 |
| 早期「偶尔出现、难以稳定复现」 | ✓ 竞态：commit 落在 mousedown 前或 mouseup 后则不发作；本地存储窗口窄、网络波动 → 间歇性 |
| 预读模式同样复现 | ✓ 预读「划词即收藏」走同一异步重渲染管线（第一份排除 H2 系误判） |
| 误选内容 = 光标之前所有文本 | ✓ 锚点回落段首 |
| 大段文本被收藏 | ✓ mouseup 读取到过扩选区 |
| 「划选紧挨上一个收藏词的词语」易发 | ✓ 同段文本节点被重建 |
| 移除 padding 后「更难复现但未消失」（实验 2） | ✓ 与本机制无关，观测差异归因于低样本噪声（低频竞态下小样本不可区分） |
| 嵌套结构时间线吻合（c82db8c 后出现） | ✓ 相容但不必要：c82db8c 引入收藏后段落结构变化（文本节点被 span 切分重建）正是「锚点节点被销毁」的前提——旧版贪心丢弃重叠、且收藏不重排已有 DOM 结构，锚点节点被替换的机会少。**时间线证据实际支持的是「收藏导致 DOM 重建」而非「嵌套本身」** |

### 2.3 为何高频但不是 100%

- 竞态窗口：commit 早于 mousedown 或晚于 mouseup → 不发作；
- 下一个词在**其他段落**（该段 DOM 未被触碰）→ 不发作；
- 本地存储路径快，窗口窄 → 低频；云端慢 → 高频。网络/设备性能差异 → 频率因人而异、因时而异。

## 三、结论与推测的边界

**【结论（代码事实，可直接查验）】**
1. 每次收藏触发两波异步 `setBookmarks` 重渲染（收藏保存后一波、翻译完成后一波），云端路径窗口达数百毫秒~秒级；
2. 重渲染会销毁并重建刚收藏段落的文本节点（memo 被 filter 新数组击穿，结构变化段落发生 DOM 替换）；
3. 第一份报告「预读模式排除重渲染」的推理存在漏洞，H2 的排除无效；
4. H5/H6（硬件/OS）被换鼠标实验排除；H1（结构说）无法解释时序触发条件，降级。

**【推测（机制核心，待直接观测确认）】**
React commit 落在拖选途中 → 锚点文本节点被移除 → 浏览器将锚点回落段首 → 选区过扩。该推断与全部证据相容且目前无反例，但「锚点节点在拖选途中被移除」及「回落段首」两步尚未被探针直接观测，故不定为 100% 结论。

## 四、最终确认方案（按成本排序，均为验证手段）

1. **延迟对照实验（零代码，最优先）**：
   - A 组：收藏后**等 3–5 秒**（确保两波重渲染落地）再划选下一个词，×20 次；
   - B 组：收藏后**紧接着**划选，×20 次。
   - 预期：A 组几乎不发作、B 组高频 → 竞态机制确认。
2. **网络节流放大实验（零代码）**：DevTools → Network → Slow 3G 节流后重复「紧接着划选」。预期：复现率显著上升（异步窗口被人为拉宽）→ 强支持。
3. **探针（决定性，只记录不改行为）**：
   - `MutationObserver` 挂 `contentRef`，记录 childList 变更时间戳与涉及段落；
   - `mousedown`/`mouseup` 时间戳 + `selectionchange` 中记录 `anchorNode` 身份与 `anchorNode.isConnected`；
   - 判据：发作的那次拖选中，「锚点段落发生 DOM 变更」且「变更时刻 anchorNode.isConnected === false」→ 机制实锤。
4. **补充确认（问用户）**：误选的那一大段，起点是否总是**刚收藏词所在段落的段首**？若是 → 与「锚点回落段首」吻合；若跨段/起点不定 → 需重新审视。
