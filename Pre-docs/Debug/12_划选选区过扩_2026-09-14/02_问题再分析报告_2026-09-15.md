## 〇、对上一份结论的置信度修正（重要）

上一份报告将 H1（嵌套内联 span 结构）定为「高置信度根因」。本次复核其证据链，认为**置信度应下调为「候选之一」**，理由如下：

1. **预读实验的真实证明力被高估了一步。**
   预读模式确实停用了全部应用层交互逻辑（hover 卡、弹窗、mousedown 清选区），因此 H2/H3/H4 的排除是扎实的。但预读实验**不能排除**以下层面的因素：
   - 浏览器原生选区行为（与 DOM 结构有关，也可能无关）；
   - OS 鼠标事件层（驱动、辅助功能、第三方注入）；
   - **鼠标硬件**（抖动在任何模式下都照常发生）。
   上一报告由「排除 JS」直接推导至「锁定 DOM 结构」，中间跨越了 OS/硬件两个未排除层。

2. **「时间线吻合」对低频间歇问题是弱证据。**
   问题频率低到「难以稳定复现」，则旧版本「无此问题」从未被统计性证实——要证明阴性，需要旧版本下的长时间使用样本，而该样本不存在。时间线相关性因此只能作为弱旁证。

3. **H1 的机制从未被正面观测。**
   「拖选跨越嵌套内联边界时锚点被吸附到祖先内联盒起点」是一个合理的机制猜想，但：无任何探针数据支持；非 Chrome 有明确文档记载的典型行为；且预读模式下无 DOM 变更，「锚点节点被移除导致回落」这条常见机制不适用。

4. **新信息反向削弱 H1。**
   结构是确定性的：若嵌套结构是触发条件，则对同一段含嵌套的文本反复执行同样划选，应能以较高概率复现。用户报告问题出现过但仍「难以复现」——这更符合**随机触发源**（硬件抖动、时序竞争）的特征，而非确定性结构触发。

5. **判别实验 2 的双刃剑。**
   移除 padding/borderRadius 后「更难复现但未消失」，上一报告将其解读为「样本不足」。但同一「样本不足」反对意见适用于围绕此问题的一切实验——包括最初的预读观察。在低频问题上，所有单次观察的证据力都应打折。

**【结论】** H1 从「高置信度根因」下调为「未被排除的候选」。当前没有任何假说达到可定案的证据标准。

## 二、H5：鼠标微动抖动（推测，当前解释力最强）

### 2.1 机制链

鼠标微动开关老化后，单次物理按下会产生**触点抖动（bounce/chatter）**：在几十毫秒内出现一次或多次额外的「释放+按下」。OS/浏览器按系统双击时间窗判定，同一坐标附近的快速连续按下被识别为**多次点击**，`MouseEvent.detail` 递增：

- `detail = 2`（双击）：选中当前词；按住继续拖 = **按词扩展模式**，锚点吸附到词首；
- `detail = 3`（三击）：Chrome 中选中整段；按住继续拖 = **按段扩展模式**，**锚点钉在段落起点**。

若抖动恰好发生在用户**起笔按下的一瞬间**，浏览器已进入段落扩展模式：锚点 = 段首，用户向后拖动时选区以整段为单位扩展——视觉上即「一下子选中光标之前的所有文本」。mouseup 时 `selection.toString()` 忠实返回该大区间 → 大段错误文本被收藏。

### 2.2 对全部已有证据的拟合

| 证据 | H5 拟合情况 |
|------|------------|
| 低频、难以稳定复现 | ✓ 微动老化是间歇性、渐进性、随机性故障 |
| 预读模式同样复现 | ✓ 硬件层与应用 JS 完全无关 |
| 选中「光标之前的所有文本」 | ✓ 段落扩展模式锚点 = 段首 |
| 移除 padding 后「更难复现但未消失」 | ✓ 与 padding 无关，本就该低频随机 |
| 大段文本被收藏 | ✓ mouseup 时选区确实已是大区间 |
| 时隔一日再次出现 | ✓ 老化故障不会自愈，会渐进加重 |

**先验**：微动双击（常见于欧姆龙系开关）是鼠标最高发的硬件老化故障，无充分理由排除时应给予较高先验权重。

### 2.3 可证伪预测

1. 纯文本无嵌套页面（Wikipedia、textarea、记事本）用相同手势也会偶发；
2. 其他应用出现单击变双击现象（文件管理器单击即打开、点按误连击）；
3. 更换鼠标后问题消失；
4. 发作时 `mousedown` 序列存在 <100ms 的 down-up-down，或 `event.detail ≥ 2`；
5. 频率随时间逐渐上升（老化渐进）。

## 三、H6：OS/软件层改写点击序列（推测）

能产生与 H5 等价症状（点击序列被改写/注入）的软件层因素：

- 鼠标驱动与宏软件：Logitech G Hub / Razer Synapse / X-Mouse Button Control / 连点器；
- 划词翻译/屏幕取词工具：有道词典、沙拉查词等（监听并可能注入鼠标/键盘事件）；
- 笔记本触摸板误触（划选时手掌接触产生额外 click）；
- 远程桌面、屏幕共享、辅助功能（如 ClickLock）。

**与 H5 的关系**：二者在应用层不可区分（都表现为异常点击序列），只能靠环境排查与更换设备分离。

## 四、H7：复合假说——硬件触发、DOM 塑形（推测）

H1 与 H5 不互斥，存在一个有解释力的统一图景：

- **触发源** = 鼠标抖动/多次点击误判（随机性来源，解释低频难复现）；
- **表现形态** = 段落扩展模式锚定 `<p>` 边界，而本应用按段落渲染 `<p>`，故过扩选区恰好表现为「段首至光标的全部文本」，在本应用中格外醒目。

这同时解释了：为何用户在普通网页浏览中可能也有同类硬件问题但表现为「划词偶尔变成选中整段」而不易察觉，唯独在本应用中以「大段文本被收藏」的破坏性形式暴露。

## 六、验证方案（按成本排序，均为验证手段，非修复）

1. **零成本观察（1–2 周）**：日常使用中留意其他应用的单击变双击、划词异常选中整段现象。出现即强支持 H5。
2. **在线双击测试页**：对鼠标左键连击百次，观察是否有非预期的双击记录。阳性 → H5 基本实锤。
3. **纯文本对照实验**：在 Wikipedia 等无嵌套内联结构的页面，以相同手势反复划选。若纯文本也偶发 → 应用代码洗清（H1 排除）；若只在应用内出现 → H5 削弱、H1 回升。
4. **换设备 A/B**：换一只鼠标（或改用触摸板）使用数日。最直接的双假说判别。
5. **应用内诊断探针**（只记录、不改行为，dev-only）：
   - 记录 `mousedown`/`mouseup` 序列：时间戳、`event.detail`、clientX/Y；
   - 记录拖选期间 `selectionchange`：锚点节点身份（data-bookmark-id / 段内路径）与 offset 是否跳变；
   - 记录 mouseup 时 `selection.toString()` 长度与首尾文本。
   发作时回看日志一次定案：
   - <100ms 的 down-up-down 或 `detail ≥ 2` → H5/H6 实锤；
   - 单次干净 drag 且锚点中途跳变至段首 → H1 实锤（锚点吸附机制首次正面观测）；
   - 单次干净 drag 且锚点本来就在段首 → 用户起笔即段首，考虑误报/操作习惯。
6. **浏览器内核矩阵**（沿用上份报告）：Chrome / Edge / Firefox 分别验证。仅某内核复现 → 指向浏览器原生行为（H1 方向回升）。

## 七、当前结论陈述

**【结论】**
1. 上一报告的 H1 根因结论证据不足，下调为候选假说；预读实验只排除了应用 JS 层，未排除 OS/硬件层。
2. 在现有证据下，无任何假说可定案；问题具备「随机触发源」特征（低频、对确定结构不可重复），与纯结构假说的预测不符。

**【推测（按当前解释力排序）】**
1. **H7 / H5**：鼠标微动抖动被误判为多次点击，进入词/段扩展模式，锚点钉在段首——拟合全部证据，先验高；
2. **H6**：等价症状的软件层来源（驱动/宏/取词工具/触摸板），待环境排查；
3. **H1 / H1b**：DOM 结构因素，未排除但证据力下降，需探针正面观测「锚点跳变」才能回升。

**下一步**：优先执行第六节中零成本项（1、2、3、4）与信息收集（第五节表格），探针（5）作为一锤定音手段在简单排查无结论后启用。
