## 一、根因（结论，探针直接观测 + 代码事实双重确认）

**每一次收藏都会触发整篇文章内容的全量重挂载（remount），而非局部更新。若重挂载落在用户下一次拖选途中，选区锚点的文本节点被销毁，浏览器将选区基准回落到段首（或直接塌缩），产生过扩误选。**

完整因果链（每一环均有证据）：

1. **收藏触发两波异步状态刷新**（代码事实，ReaderPage.jsx:254-281 / 306-349）：
   - 第一波：mouseup → `saveBookmark` → `loadReaderState()` → `setBookmarks` + `setReadingMark`（实测滞后 mouseup 约 0.5–0.7 秒）；
   - 第二波：`translateBookmark` 完成回调 → 再次 `loadReaderState()`（实测滞后约 1.5–3 秒）。
2. **`loadReaderState` 每次都产生新引用的 `readingMark` 对象**（代码事实，ReaderPage.jsx:156-163：`setReadingMark(nextReadingMark)`，内容相同也是新对象）。
3. **`MarkdownContent` 的 `components` 以 `readingMark` 为 useMemo 依赖**（代码事实，SectionFlow.jsx:52-127）→ readingMark 引用变化 → components 映射整体重建 → 其中每个渲染器（`p`/`li`/...）都是**新的函数标识**。
4. **react-markdown 按组件标识渲染：组件类型变了 → React 将整棵 Markdown 树 unmount/remount**（探针实测：每次爆发恰好 104 条 childList 变更 = 52 个段落 div 全部移除 + 全部重建；全程共 12 次爆发，每次收藏后恰好成对出现，与两波管线一一对应）。
5. **重挂载销毁所有段落文本节点。若此刻用户正在拖选**（「紧接着划下一个词」），锚点节点被移出文档 → 浏览器重定位选区基准（探针实测两种结局）：
   - **锚点回落到段首**，焦点继续跟随鼠标 → 过扩选区，mouseup 被忠实收藏（手势 14：74 字符误收藏）；
   - **选区直接塌缩为空**（手势 4、7：拖到一半选区消失，len=0）——这是同一根因的姊妹症状。

## 二、对全部历史证据的最终拟合

| 证据 | 解释 |
|------|------|
| 「收藏后紧接着划选下一个词」高频 | 两波重挂载窗口（+0.5s / +1.5~3s）与下一次划选手势重叠 |
| 换鼠标现象不变；与起笔位置无关（06 实验 C≈D） | 触发源是异步重挂载的**时机**，不是输入设备或落点 |
| 「吞空格」与过扩 5/5 绑定 | 吞空格 = 边界光标规范化（无害本身）；过扩 = 重挂载把锚点从该位置炸回段首——同一手势的两个阶段 |
| 跨段落误选 | 锚点回落目标取决于重建后的 DOM 状态，可落到段首或更靠前 |
| 预读模式复现 | 预读「划词即收藏」走同一收藏管线（01 报告「预读无重渲染」系误判，02/03 已修正） |
| 04 实验（延迟对照）双零 vs 06 实验 20-30% | 发作取决于异步波与手势的**随机重叠**；04 的操作节奏未撞上窗口，06 撞上了。与时延相关的随机性正是竞态特征 |
| 移除 padding「更难复现但未消失」 | padding 影响的是起笔落点分布（边界命中率），与真正的触发源（重挂载）无关——低频噪声下的观测偏差 |
| c82db8c 后问题出现 | 双层叠加渲染后收藏才触发段落结构变化 + 阅读标记/收藏管线完善后重挂载波及面变大；时间线与「收藏触发重挂载」相容 |

**遗留离群点（诚实声明）**：手势 9（len=100，位于无 `data-para-index` 的内容区，窗口内无重挂载爆发）未被主机制覆盖——可能是用户主动的长划选，或另一低频子路径。主机制已被手势 4/7/14 三次独立实锤，离群点不影响定案，修复后可用探针回归确认。

## 三、修复方案（待批准后实施）

### F1（治本）：消除整树重挂载 —— `readingMark` 引用稳定化

- 将 `components` 内对 `readingMark` 的闭包引用改为 `readingMarkRef`（与既有 `bookmarksRef`/`onHoverRef` 同模式），useMemo 依赖从 `[readingMark, sectionId]` 收窄为 `[sectionId]`；
- 或在 `setReadingMark` 前做内容比较（paragraphIndex/sectionId/completed 相同则保留旧引用）。
- **效果**：收藏后 React 正常 reconciliation，只有新收藏所在段落局部更新，其余 51 个段落 DOM 不再被触碰。附带收益：消除每次收藏的全树重挂载性能浪费。

### F2（治本·兜底）：拖选途中延迟落地收藏状态

- 增加「选区活跃」跟踪（内容区 mousedown → 活跃；mouseup / 选区折叠 → 解除）；
- 收藏管线的 `setBookmarks`/`setReadingMark` 落地前检查：若有进行中的拖选，则排队到 mouseup/选区折叠后再应用。
- **必要性**：F1 之后，新收藏所在段落仍会局部重建文本节点，而用户下一个划选目标往往就在同段（「紧邻已收藏词」）——F2 覆盖这一残余窗口，且对两波异步回调统一生效。

### 推荐：F1 + F2 组合。F1 解决波及面（全树 → 单段），F2 解决时序（单段也不再在拖选途中变更）。

### 修复后验证

1. 探针回归：重复本次测试流程，预期——收藏后**不再出现** 104 条/次的重挂载爆发（F1）；拖选途中零 mut（F2）；
2. 按 06 清单手势复测 20 次，预期零发作；
3. 回归通过后移除探针（`src/debug/selectionProbe.js` + ReaderPage 接入点）。

## 四、经验记录（问题是我们的老师）

1. 低频间歇问题的「时间线吻合」和「排除法」都是弱证据——三轮假说（结构/硬件/位置）都死于直接观测之前；
2. 预读实验当年「排除重渲染」的教训：排除一个机制前，要穷尽该机制的所有触发路径（hover 只是其一，收藏管线才是大头）;
3. 探针（直接观测）是对抗「鬼魅问题」的终极手段：一次发作现场胜过十轮推理。
