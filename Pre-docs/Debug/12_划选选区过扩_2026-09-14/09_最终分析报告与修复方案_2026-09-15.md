## 一、根因（结论，探针直接观测 + 代码事实双重确认）

**每一次收藏都会触发整篇文章内容的全量重挂载（remount），而非局部更新。若重挂载落在用户下一次拖选途中，选区锚点的文本节点被销毁，浏览器将选区基准回落到段首（或直接塌缩），产生过扩误选。**

完整因果链（每一环均有证据）：

1. **收藏触发两波异步状态刷新**（代码事实，ReaderPage.jsx:256-282 / 307-350）：
   - 第一波：mouseup → `saveBookmark` → `loadReaderState()` → `setBookmarks` + `setReadingMark`（实测滞后 mouseup 约 0.5–0.7 秒）；
   - 第二波：`translateBookmark` 完成回调 → 再次 `loadReaderState()`（实测滞后约 1.7–3.2 秒，6 次实测 1677–3142ms）。
2. **`loadReaderState` 在云端路径下每次都产生新引用的 `readingMark` 对象**（代码事实，ReaderPage.jsx:152-164：`setReadingMark(nextReadingMark)` 在 :163）。
   **环境限定（审核 P1 补正）**：新引用断言对**云端路径**成立（`mapReadingMarkRow` 每次新建对象，readings.js:153-168）；**本地路径**下 `readingMarkStore.get` 返回 `_marksCache[articleId]` 共享缓存引用（storage.js:128-131、209-211），内容不变时引用稳定 → `setReadingMark` 同引用 → React bailout → **本地模式不触发全树重挂载**。探针会话观察到 12 次全树爆发，可反推当时运行在云端路径。
   **精化（处理记录 #1）**：本地模式下 `setBookmarks` 仍获新数组，新收藏所在段落的**局部重建**仍会发生（即 F2 覆盖的残余窗口），故本地预测为「**无全树重挂载爆发、发作率大幅下降**」而非绝对不发作；本地对照验证的硬判据是「无 104 条级爆发」，「是否发作」仅作软观察。
3. **`MarkdownContent` 的 `components` 以 `readingMark` 为 useMemo 依赖**（代码事实，SectionFlow.jsx:52-127，依赖数组 `[readingMark, sectionId]` 在 :127）→ readingMark 引用变化 → components 映射整体重建 → 其中每个渲染器（`p`/`li`/...）都是**新的函数标识**。
4. **react-markdown 按组件标识渲染：组件类型变了 → React 将整棵 Markdown 树 unmount/remount**（探针实测：每次爆发恰好 104 条 childList 变更 = 52 个段落 div 全部移除 + 全部重建；全程共 12 次爆发，每次收藏后恰好成对出现，与两波管线一一对应）。
5. **重挂载销毁所有段落文本节点。若此刻用户正在拖选**（「紧接着划下一个词」），锚点节点被移出文档 → 浏览器重定位选区基准（探针实测两种结局）：
   - **锚点回落到段首**，焦点继续跟随鼠标 → 过扩选区，mouseup 被忠实收藏（手势 14：74 字符误收藏）；
   - **选区直接塌缩为空**（手势 4、7：拖到一半选区消失，len=0）——这是同一根因的姊妹症状。

| 证据 | 解释 |

| 「收藏后紧接着划选下一个词」高频 | 两波重挂载窗口（+0.5s / +1.7~3.2s）与下一次划选手势重叠 |

## 三、修复方案（已过实施前审核，选型已确认）

### F1（治本）：消除整树重挂载 —— `readingMark` 引用稳定化（**选型：选项 1**，已批准）

- 将 `components` 内对 `readingMark` 的闭包引用改为 `readingMarkRef`（与既有 `bookmarksRef`/`onHoverRef` 同模式，SectionFlow.jsx:43-48），useMemo 依赖从 `[readingMark, sectionId]` 收窄为 `[sectionId]`；
- **关键实施约束（审核 P2，必须遵守）**：`readingMark` 必须**保留为 prop** 传入 `MarkdownContent`——它是 memo 组件重渲染的唯一触发源，`p` 渲染器执行时经 `readingMarkRef.current` 读到最新值，`isMarked` 视觉更新才不丢失。**若实施时误删该 prop，阅读标记将静默失更（功能回归且极难察觉）**。
- **效果**：收藏后 React 正常 reconciliation，只有新收藏所在段落局部更新，其余段落 DOM 不再被触碰；用户真实移动阅读标记时也不再全树 remount。附带收益：消除每次收藏的全树重挂载性能浪费。

### F2（治本·兜底）：拖选途中延迟落地收藏状态（**采纳审核简化的 dirty 标志方案**，审核 P3）

- **设计**：内容区 mousedown → 置「选区活跃」标志；mouseup / 选区折叠 → 解除。收藏管线的两波状态刷新落地前检查：若活跃，则**仅置 dirty 标志、跳过落地**；待 mouseup/折叠后**统一执行一次 `loadReaderState`**。该设计天然规避两波排队去重（flush 即取最新状态，不存在旧值覆盖新值）与预读时序问题（预读 mouseup 内先 `removeAllRanges`，本次收藏的状态不会被自己刚设的标志误排队）。
- **三重兜底（审核 P3.1）**：mouseup 在内容区外释放（拖出窗口松手）/ 窗口 blur / 超时（5s）任一触发即解除活跃标志并 flush，防止队列永不落地。
- **flush 时序保护**：flush 经 `setTimeout(0)` 延迟到当前 mouseup 事件的所有监听器完成之后执行，确保应用的 `handleMouseUp` 已同步捕获选区文本与偏移，不受落地重渲染影响。
- **必要性**：F1 之后，新收藏所在段落仍会局部重建文本节点，而手势 14 正是「从刚收藏词 'student' 末尾起笔划下一个词」——F2 覆盖的正是这个同段残余窗口。

### 推荐组合：F1 解决波及面（全树 → 单段），F2 解决时序（单段也不再在拖选途中变更）。

### 修复后验证

1. 探针回归：重复本次测试流程，预期——收藏后**不再出现** 104 条/次的重挂载爆发（F1）；拖选途中零 paragraph 区 mut（F2）；
2. 按 06 清单手势复测 20 次，预期零发作；
3. **本地模式对照（审核 P1，零成本反向验证）**：本地（无云库）重复「收藏后紧接划选」——硬判据「无 104 条级爆发」；「是否发作」仅作软观察（同段局部窗口理论存在，若偶发需结合 mut 记录判读，不直接归咎第二触发路径）；

## 四、经验记录（问题是我们的老师）

1. 低频间歇问题的「时间线吻合」和「排除法」都是弱证据——三轮假说（结构/硬件/位置）都死于直接观测之前；
2. 预读实验当年「排除重渲染」的教训：排除一个机制前，要穷尽该机制的所有触发路径（hover 只是其一，收藏管线才是大头）;
3. 探针（直接观测）是对抗「鬼魅问题」的终极手段：一次发作现场胜过十轮推理。
