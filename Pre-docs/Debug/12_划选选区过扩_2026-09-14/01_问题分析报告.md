# 问题分析报告 — 划选选区异常过扩（光标前所有文本被选中）

> **日期**：2026-09-14
> **状态**：**搁置（待稳定复现后处理）**
> **关联功能**：10_收藏重叠高亮渲染（双层叠加渲染）
> **引入提交**：`c82db8c`（收藏重叠高亮改为双层叠加渲染）
> **诊断提交**：`b27e7cc`（临时移除 padding/borderRadius，已还原）

---

## 一、问题现象

1. 划选「某个已收藏词所在的句子」，或划选「紧挨上一个收藏词的词语」时，**偶尔**会一下子选中「光标之前的所有文本」，而非目标文本。
2. 打开收藏列表可见：**大段被错误选中的文本已被收藏**（即 `selection.toString()` 在 mouseup 时已是一个大区间）。
3. 出现频率：**偶尔出现、很难稳定复现**。

---

## 二、初步假设（4 条）

| 编号 | 假设 | 类别 |
|------|------|------|
| H1 | 嵌套内联 span（词背景 span 嵌在句下划线 span 内）破坏浏览器原生拖选，锚点被吸附到祖先内联盒起点 | 结构 |
| H2 | 拖选过程中 hover 重渲染替换了持锚点的文本节点，锚点落空回落段首 | 交互/重渲染 |
| H3 | 悬浮卡（fixed、`data-popup="true"`）盖在文字上打断拖选 | 交互 |
| H4 | 弹窗未关时 mousedown 触发 `closePopup` → `removeAllRanges()` 干扰新选区建立 | 交互 |

---

## 三、判别实验 1：预读模式是否复现 → **复现**

预读模式下，拖选期间**所有交互逻辑均为空转**：

- `showHoverCard` 首行即 `if (preReadMode) return`（ReaderPage.jsx:129）→ 无 `setHoverBookmark`、无重渲染
- 悬浮卡不渲染（渲染条件含 `!preReadMode`）
- 无弹窗（预读分支不 `setPopup`）
- 无 mousedown 清选区（`handleClickOutside` 仅在 `popup` 存在时生效）

**结论：H2 / H3 / H4 全部排除。** 问题只可能来自 DOM/CSS 结构本身（H1 方向）。

---

## 四、证据：旧版代码对比

`git show HEAD~1:src/components/ParagraphRenderer.jsx`（即 `c82db8c` 之前）显示：

- 旧版高亮 span **已经带有** `borderRadius: '3px'`、`padding: '1px 1px'`、`cursor: 'default'` —— 这些样式**非本次引入**，且旧版无此选区问题。
- 旧版是**扁平结构**：每个 segment 是 `<p>` 下直接子 span，无嵌套；根是 `<>` Fragment，**无整段包裹 span**。
- 旧版重叠时会**贪心丢弃其一**，故「句下划线里嵌套词背景」的结构在旧版**不可能存在**。

**推论：** `padding`/`borderRadius` 单独不足以致病；触发项锁定为本次新增的两个结构性差异之一或二者——**嵌套**（bg span 嵌在 ul span 内）与**整段包裹 span**。而「嵌套」恰好只可能出现在本次改动后（旧版重叠即丢弃），与问题只在本次改动后出现的时间线吻合。

---

## 五、收敛结论（置信度：高，但非 100%）

**根因 = 双层叠加渲染引入的「嵌套内联 span」结构**：词/短语背景 span（带 padding）嵌在句/段下划线 span 内部，拖选跨越这个嵌套内联边界时，浏览器把选区锚点吸附到祖先内联盒起点，产生「光标前所有文本」的过度选区；`selection.toString()` 忠实返回该大区间，导致大段错误文本被收藏。`padding`/`borderRadius` 是可能的协同因子（旧版扁平结构下无害）。

支撑推理（三段独立成立）：
1. 预读模式同样复现 → 交互层全部停用仍复现 → 结构问题。
2. 旧版「扁平 + padding」正常、新版「嵌套 + padding」异常 → 触发项是嵌套。
3. 旧版从不嵌套 → 该结构全新引入，与「问题只在本次改动后出现」时间线吻合。

---

## 六、判别实验 2：移除 padding/borderRadius → **仍偶尔出现（不彻底）**

临时从 `bgStyle` 移除 `borderRadius` 与 `padding`（保留 `backgroundColor`，提交 `b27e7cc`），实测：**仍偶尔出现，但更难复现**。

**解读（不彻底，不推翻结论）：**
- 说明 `padding`/`borderRadius` **不是唯一/充分**触发条件；
- 触发条件可能是「嵌套本身」或「整段包裹 span」，与 padding 无直接关系；
- 亦可能样本不足、频率本就低，无法在有限测试内做统计区分。

---

## 七、尚未排除项

- **嵌套本身**：bg span 嵌在 ul span 内（与 padding 无关的纯嵌套边界）。
- **整段包裹 span**：`<span onMouseOver onMouseLeave>` 包住整段（无样式，理论上选区透明，但未实测排除）。
- **浏览器内核差异**：Chrome / Edge / Firefox / Safari 未分别验证。
- 上述二者的组合。

---

## 八、搁置原因与复现条件

- **搁置原因**：问题「偶尔出现、很难稳定复现」，缺少可反复触发的确定性步骤，继续做隔离实验成本高、结论不可靠。
- **后续处理前提**：能找到**稳定复现步骤**（含具体文本、操作路径、浏览器内核/版本）。

---

## 九、稳定复现后的下一步验证方案（按序）

1. **内核差异测试**：分别在 Chrome / Edge / Firefox / Safari 复现，记录是否仅某内核出现。
2. **结构隔离 A（去嵌套）**：把词背景 span 从句子 span 内部抽为同级（下划线与背景不再嵌套），看是否消失。
3. **结构隔离 B（去包裹层）**：移除整段包裹 `<span>`（临时牺牲 hover 委托），看是否消失。
4. **探针**：监听 `selectionchange`，记录锚点节点身份在拖选期间是否跳变到段首，确认「锚点跳变」而非「本就来就拖大」。
