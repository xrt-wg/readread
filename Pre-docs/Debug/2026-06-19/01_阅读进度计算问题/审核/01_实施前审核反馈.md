## 二、修复方案审核

### 2.1 方案架构：✅ 方向正确

创建统一的 `progress.js` 模块作为段落解析和进度计算的「唯一权威来源」——这个架构决策完全正确。两端共用一个段落定义是从根源上解决索引不对齐的正确方式。

### 2.2 Fix 1+2：`progress.js` 模块 — ⚠️ 条件性通过

#### 2.2.1 `getMarkdownParagraphs` 的近似性风险

**核心问题**：`getMarkdownParagraphs` 使用纯文本正则解析（`\n\n+` 分割 → 跳过 `#` 块 → 拆分列表块），而 ReaderPage 的 `MarkdownContent` 使用 `react-markdown` AST 渲染决定 `paraIdxRef`。两者使用不同的解析引擎。

**对于标准、格式良好的 markdown，两者的段落计数大概率一致。** 但以下边缘情况可能导致偏差：

| 边缘情况 | `MarkdownContent` (AST) | `getMarkdownParagraphs` (Regex) | 偏差 |
|---------|------------------------|-------------------------------|------|
| h5/h6 标题 (`#####`) | 不递增 paraIdxRef | `/^#{1,4}\s/` 不匹配 → 被当作段落 | **+1 偏移** |
| 代码块 (```) 内含空行 | 不递增 paraIdxRef | `\n\n+` 在空行处分裂 → 产生幽灵段落 | **+N 偏移** |
| 引用块内嵌段落 | 不递增 paraIdxRef | `cleanInlineMarkdown` 仅去除 `>` 标记 → 引用块文本被当作段落 | **+1 偏移** |
| 水平线 (`---`) | 不递增 paraIdxRef | 在 `\n\n+` 分割后成为独立块 → 非标题、非列表 → 被当作段落 | **+1 偏移** |
| 表格 | 不递增 paraIdxRef | 表格行被当作普通文本块 → 多行偏移 | **+N 偏移** |

**影响评估**：ReadRead 的文章来源主要是 EPUB 导入（通过 `epub2md` 转换）和手动粘贴。这些来源通常产生结构简单的 markdown（段落 + 标题 + 列表），较少包含代码块、表格、引用块。**在当前使用场景下风险较低，但作为唯一的进度计算引擎，其健壮性值得关注。**

**建议**：
- 修复 h5/h6 问题：将 `/^#{1,4}\s/` 改为 `/^#{1,6}\s/`
- 添加代码块处理：在 `\n\n+` 分割前，先提取/移除围栏代码块（```...```），将其内容暂存，分割后复原
- 添加水平线跳过：`/^[-*_]{3,}\s*$/`
- 添加引用块处理：识别以 `>` 开头的连续行块，跳过（与 AST 行为一致，blockquote 不递增 paraIdxRef）

#### 2.2.2 ReaderPage 中段落来源变更的作用分析

方案中 ReaderPage 的改动：

```diff
-const paragraphs = parseText(text)
+const paragraphs = article.markdown != null
+  ? getParagraphs(article)
+  : parseText(text)
```

需要明确的是：`paragraphs` 变量仅在**非 markdown 路径**中使用（[ReaderPage.jsx:962](src/components/ReaderPage.jsx#L962)），markdown 文章走 `MarkdownContent` 渲染。因此这个改动对 markdown 文章**不改变运行时行为**（markdown 路径不引用 `paragraphs`）。它的作用是：

1. 为纯文本文章提供一致的段落分割（`getParagraphs` 对文本文章回退到 `text.split(/\n+/)`，与 `parseText` 等效）——**无行为变化**
2. 未来如果 ReaderPage 需要为 markdown 文章渲染纯文本回退（如阅读模式切换），段落索引能保持一致——**有前瞻性价值**

→ **改动正确，但需注意它对 markdown 文章的段落索引不一致问题不产生直接影响**。真正的修复效果来自 `calcProgress` 改用 `getParagraphs`，而非 ReaderPage 的改动。

#### 2.2.3 `calcMultiSectionProgress` 算法审核

```js
function calcMultiSectionProgress(article, mark) {
  const totalWords = getTotalWords(article)
  if (totalWords === 0) return null

  const completedIds = new Set(mark.completedSections ?? [])
  let cumulativeWords = 0

  for (const section of article.sections) {
    if (completedIds.has(section.id)) {
      cumulativeWords += section.body.wordCount           // 已完成章节：全词数
    } else if (section.id === mark.sectionId) {
      const sectionArticle = { ... }                       // 当前章节：按节内索引
      cumulativeWords += getWordOffsetAtParagraph(sectionArticle, mark.paragraphIndex)
      break                                                // 后续章节不计入
    }
  }

  return Math.min(99, Math.round((cumulativeWords / totalWords) * 100))
}
```

**审核结论**：
- ✅ 已完成章节 → 计全词数（正确）
- ✅ 当前章节 → 用节内 `paragraphIndex` + 节 scoped 的段落解析（正确——本质上 Fix 1 使得节内索引对齐有效）
- ✅ `break` 在找到当前章节后跳出，未到达的章节不计入（正确）
- ✅ 由于 P3-6（`completedSections` UI 缺失），当前 `completedSections` 始终为空，多章节进度仅反映当前章节的进度——**这仍是部分修复，但比修复前完全错位的进度值有本质改善**
- ⚠️ `sectionArticle` 构造仅包含 `{ text, markdown, wordCount }` — 传递给 `getWordOffsetAtParagraph` 再传给 `getParagraphs`，后者检查 `article.markdown != null`。如果 section 级别的 `body.markdown` 不为 null 但为空字符串，`!= null` 为 true，会走 markdown 路径。建议使用更精确的 truthy 检查

### 2.3 Fix 3：`clearReadingMark` 保留 `completedSections` — ✅ 正确

**审核**：
- 新增 `fetchCloudReadingMarkRow` 读取已有记录 ✅
- `completedSections: existing?.completed_sections ?? []` 保留已有数据 ✅
- 遵循现有 `setReadingMarkCompleted` 的 read-before-write 模式 ✅

### 2.4 Fix 4：`saveReadingMark` 保留已完成状态 — ✅ 正确，含性能提示

**审核**：
- `completed: existing?.completed ?? false` 匹配本地行为 ✅
- `completedSections: existing?.completed_sections ?? []` 保留章节记录 ✅
- 与 Fix 3 共享 read-before-write 模式 ✅

**⚠️ 性能提示**：`saveReadingMark` 的调用频率高于 `clearReadingMark` 或 `setReadingMarkCompleted`——用户在阅读过程中每点击一次段落标记按钮就会触发一次。增加 `fetchCloudReadingMarkRow` 意味着每次点击从 1 个 Supabase 请求变为 2 个。在弱网环境下用户可能感知到延迟增加。

**建议**：考虑将 read + write 合并为一个 RPC（类似 `soft_delete_bookmark`），将网络往返从 2 次减为 1 次。这会增加一个 migration 文件但提供更好的用户体验。也可以作为后续优化——当前 2 次请求对阅读标记这种低频操作（非滚动触发）来说，延迟在可接受范围内。

## 三、额外发现：预存的多章节缺陷

### F1：`handleSetReadingMark` 缺少 `sectionId` 比对

**位置**：[ReaderPage.jsx:427](src/components/ReaderPage.jsx#L427)

```js
if (readingMark?.paragraphIndex === paraIndex && !readingMark?.completed) {
  const clearedMark = await clearReadingMark(articleId, options)  // 清除
} else {
  const mark = await saveReadingMark(...)                          // 保存
}
```

**缺陷**：当用户在 Section A 的段落 0 标记后，切换到 Section B 再点击段落 0，`paraIndex` 都是 0，条件为 true → 触发 `clearReadingMark` 清除 Section A 的标记，而非在 Section B 保存新标记。

**影响**：多章节书的阅读标记无法在不同 section 中独立设置。

**修复**：比对应包含 `sectionId`：
```js
const isSameMark = readingMark?.paragraphIndex === paraIndex 
  && (readingMark?.sectionId ?? null) === (currentSection?.id ?? null)
  && !readingMark?.completed
```

**建议**：在本次修复中一并处理——与 Fix 2（多章节进度）紧密相关。
